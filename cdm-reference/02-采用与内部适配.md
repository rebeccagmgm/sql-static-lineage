# 采用 CDM 与内部适配的分工

本轮目标：把模型的组织方式和基础定义先立起来。下表是采用建议，尚未成为内部正式标准；不把缺少映射解释成 CDM 不适配。

## 1. 先采用什么

| 内容 | 建议 | 需要形成的结果 |
|---|---|---|
| 按职责组织公共组件、产品、事件、协议 | 作为组织基准 | 清楚的模型模块及相互引用关系 |
| 参与方与角色、标识与编码体系、数量与单位 | 优先逐项采用适用定义 | 标准名称、中文说明及适用边界 |
| 经济条款与支付组件组合 | 用于组织期权、互换等产品差异 | 共同组件与品种特有组件的清楚分工 |
| 交易、事件、状态分别表达 | 作为梳理原则 | 避免把交易快照、业务事件、加工记录混同 |
| 官方约束与产品识别函数 | 随采用的类型阅读，按实际需要验证 | 已满足、差异或尚未验证的记录 |
| 执行引擎、模型代码生成、跨源查询 | 有具体执行需求时单独评估 | 本轮不建立运行时依赖 |

本目录原文均基于 CDM 7.0.0。不同版本的类型、字段路径和映射机制可能改变，采用时记录版本，不把网上不同版本的示例拼成一个模型。

## 2. 留给内部适配的内容

| 内部问题 | 如何处理 |
|---|---|
| 我们所谓“合约”到底对应什么 | 核对它承载经济条款、交易、法律协议还是其组合，再决定标准对应 |
| 资金账户、账簿、Bundle 等对象 | 逐项检查标准定义；含义不一致时保留内部对象，不强行改名 |
| 内部产品分类 | 保留内部分类口径及来源，可与外部分类建立有范围的对应 |
| 表、字段、关系类型码 | 记录物理映射、字段角色和适用范围，由内部事实确认 |
| 历史、快照、有效期 | 将业务有效时间与数据加工/快照时间分开说明 |
| 内部专有属性和规则 | 明确属于内部扩展，说明依附哪个共享对象及为何需要 |

内部扩展使用独立标识，并引用标准定义；不修改本目录上游原文件，使本地含义与标准原意始终可对照。

## 3. 分别记录两种对应

### 业务定义与 CDM 的对应

至少记录：内部概念、标准限定名与版本、采用方式、适用范围、差异说明、确认依据。

采用方式可以用普通说明表达：采用定义、采用部分结构、对应但存在差异、内部扩展、暂未确定。无需先创建新的规则语言。

同名不能证明等价，字段结构相似也不能证明业务等价。

### 业务定义与内部数据的对应

至少记录：内部概念或属性、实际资产、字段/表达式、行范围、标识与时间含义、来源证据。

关系的数据实现还应说明两端字段，以及关系类型、来源限制等。标准定义并不能替代这些内部条件。

SQL、元数据、字典、文档及 data-graph 继续用于核实内部实现；它们不会因为采用 CDM 而失去作用。

## 4. 现有整理工作怎样接上

下一步建议让抽取同时读取“已确认的内部定义＋相关 CDM 定义选集＋当前数据证据”，提出复用、补充、差异和映射候选。

人工判断主要回答：

1. 这条内部含义是否与所引用的标准含义一致？
2. 是同一概念的另一个数据实现，还是应保留独立定义？
3. 表字段和行范围是否足以承载所声称的含义？

这项建议尚未写入现有提示词、状态库或前端。目录仍可直接收录普通资产；不要求先把所有表完整建模。

## 5. 如何判断这条路线是否有用

选择涉及不同产品的少量现有材料，检验：公共定义是否真正复用；产品差异是否表达清楚；内部适配是否能保留特殊口径；业务页面是否能沿定义找到数据与证据。

不以采用类的数量衡量进展。如果为了贴合标准而抹掉内部重要含义，应调整采用范围；如果适配只是反复改名却不能帮助理解对象和数据，也应重新检验价值。

## 6. 三种选择的评估

| 选择 | 好处 | 代价/风险 | 本轮判断 |
|---|---|---|---|
| 全部自行定义 | 起步自由 | 容易重复发明，跨品种含义难统一 | 仅用于标准无法合理承载的部分 |
| 以 CDM 为基准，选择采用并保留内部扩展 | 获得共同表达及可追溯差异 | 仍需认真做概念和数据适配 | 当前采用的研究方向 |
| 所有内部数据完整转换为 CDM 并运行其逻辑 | 可对接标准执行和交换流程 | 增加覆盖、运行和持续版本维护责任 | 尚无这项完整实施要求 |

判断依据见 [金融机构案例](03-金融机构案例.md)。那些机构证明这种分工可落地；它们没有证明我们应当一次性全量转换。
