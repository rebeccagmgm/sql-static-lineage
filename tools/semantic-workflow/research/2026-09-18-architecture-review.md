# OTC 数据地图与语义整理：架构评审

评审日期：2026-09-18。对象：当前 `tools/semantic-workflow`、已生成候选、既有图谱认知资料。本文是调研与判断记录，未变更程序、人工审核状态或图谱，没有新增模型 API 调用，也未部署竞品。

## 决策结论

**继续当前方案的小范围使用与验证是合理的。保留独立工具、现有界面和 data-graph；优先减少重复定义和人工返工，暂不引入查询引擎。**

这个结论有明确边界：当前目标是按业务找数据、理解内容、维护定义、追溯依据。不是认定现有抽取已经准确，也不是批准将小工具无限扩成企业治理平台。

成熟产品和标准已经提供目录、术语、实体、关系、物理映射、候选确认等机制。可沿用其职责划分；没有证据表明必须采用某一个完整产品才能实现当前目标，也没有证据证明自建的长期维护成本一定更低。

## 2. 竞争方案与判断

| 方案 | 成立条件 | 优点 | 对当前目标的主要缺口 | 本次判断 |
|---|---|---|---|---|
| 只做目录和表字段说明 | 用户主要需要找到表 | 最轻，容易维护 | 通用关系表的多种含义、同一对象跨表表达不足 | 可作为大部分普通资产的起点，无需每张表都实体化 |
| 目录＋必要业务定义/关系＋证据映射 | 用户还要理解复杂 OTC 关联 | 可复用现有图谱、底稿和界面 | 要控制词汇重复，保留人工决定和适用范围 | 当前最合适；正式使用效果仍需验证 |
| 引入成熟目录/治理平台 | 多团队正式使用，权限、Owner、审核、变更协作成为主要需求 | 复用通用治理能力 | 接入与运营成本，复杂业务含义仍需整理 | 保留为迁移选项，不立即部署 |
| 引入可执行语义建模平台 | 必须自动查询、验证类型、跨源执行 | 可使用成熟映射与执行机制 | 新增语言、运行环境与查询正确性责任 | 当前暂缓；需求出现后优先比较现成产品 |

最重要的反对意见不是“实体关系很复杂”，而是：**如果每个包都重新发明实体、属性名和分类，再由人逐包改正，候选越多，维护负担越大。** 当前两个合约包已经提供了这一风险的直接证据。

## 4. 现有实现的评价

### 应保留

- **独立工具边界**：只读元数据和图谱，写自己的状态库，不把人工业务定义混进事实生成链。`sources.mjs:68-79,114-133`。
- **实体与物理映射分开**：已存在实体、属性、关系、映射、分类、证据。`model.mjs:9`。
- **模型仅提候选**：提示明确不把 JOIN、目录、历史行直接当作实体或业务关系。`model.mjs:4-10`。提示本身不是正确性保证。
- **同版本人工编辑优先**：审核历史保留，同一输入版本的人工作业不会被后续模型结果直接覆盖。`state.mjs:40-60`。
- **有界取证**：按已有整理条目组包，而不是向模型一次提交整张图。它适合辅助整理，不等于全量自动发现。

### 当前具体不足

1. **命名与复用没有收敛。** T03-021、T03-066 都生成“场外期权合约”，未设置统一编号；属性名出现中英文两套，主题也生成近义名称。相同 `canonicalId` 的不同属性集合目前会被当作冲突，尚不能自动区分互补覆盖。`runner.mjs:61-75`。
2. **分类仅关联实体。** 同一合约的基本资料、条款、估值属于不同数据入口。分类还需要能落到对应资产/范围映射，而不应要求复制实体。`model.mjs:9,70-72`。
3. **关系实现没有单独位置。** 当前关系只有名称、两端实体、含义和证据。T03-021 的文字提及关系表与 A18，但其三个实体映射不能准确代替该关系的双端实现。`model.mjs:9,54-68`。
4. **跨版本保留待明确。** 导出只取当前且 accepted 的记录；输入证据变更后，旧确认仍有历史，却会从当前正式导出退出。当前样例全部 pending、尚无正式消费，这属于进入正式使用前的门槛，不是现有生产事故。`runner.mjs:57-60`。
5. **尚非完整维护工具。** 可以编辑已有候选，但新增/删除、逐条采用、批量合并等未齐备。不要将现状包装成完整语义建模平台。`web/app.js:59-100`、README。

另外，包内字段、表、任务、绑定数量都有限制，SQL 摘录与图谱 SQL 哈希尚未统一核对。有证据 ID 只表示有引用，不能推导为证据覆盖完整或业务含义正确。

## 5. 最小演进边界

### A. 先减少重复整理

保留少量人工确定的目录选项和稳定实体编号。模型优先复用它们；新词作为建议，不能每包直接扩充正式词表。不同包可以补充同一实体的不同属性与证据，不要求定义文本一字不差，也不能按中文同名自动合并。

业务目录主要组织数据资产及必要的数据范围。业务实体定义可以被多个目录入口复用。不要求每张表先抽出实体才能进目录；字段含义优先覆盖标识、关键业务属性、单位及容易歧义的字段。

### B. 确实需要沿关系找数据时，补一条实现说明

最少保留：关系、实现表、起点字段、终点字段、适用范围、来源证据。范围可以继续用可读文本，不引入条件 AST 或 SQL 编译器。

合约例子仅作为当前候选表达：

- 关系：场外期权合约关联资金账户。
- 实现：`T03_AGT_RELA_H`。
- 两端：`Agt_Id`、`Rela_Agt_Id`，修饰符等身份条件仍需核实。
- 范围：A18 及相应来源限制；时间选择规则单独说明，不永久固化一次加工日期。
- 状态：业务含义、字典时效及完整身份仍待核验。

未知可以保留缺口；不强迫所有关系立即具备完整实现说明。上述条件不能解释成目标表所有行都表示同一种关系。

### C. 正式使用前，保证人工决定不因刷新而丢失

保留最近确认的参考内容；新证据出现时清楚提示需复核、允许查看新旧差异；接受后替换。旧结论不能继续伪装成已验证最新，也不应直接从读者视野消失。拒绝、改名、归并决定应能被后续整理复用。

这不要求审批引擎、复杂发布平台或多人协同系统。多人协作成为实际需求时再评估成熟平台。

## 6. 打标与抽取的工作粒度

| 工作 | 默认粒度 | 复杂情况 |
|---|---|---|
| 业务目录归类 | 表/数据集 | 通用表中不同内容可按有条件的数据范围分别归类 |
| 业务定义 | 可复用的实体或术语 | 同名异义保留区别；不是一个输入包一个新实体 |
| 属性解释 | 关键字段/表达式 | 同字段在不同范围扮演不同角色时，说明范围 |
| 业务关系 | 一种关系及其一个或多个实现 | 两端字段、来源、类型和时间限制随实现保存 |
| 证据采集 | 相关任务、写入分支、文档、字典快照 | 调度关系、同任务共现不能当作业务关系证明 |

抽取过程：已有底稿定位范围 → 程序归集事实 → 模型参照已有定义提出补充/修正 → 程序核对字段和引用 → 人工确认。7000 多任务是可用证据范围，不是需要逐节点生成业务标签的工作量定义。

## 8. 验证与重新选型条件

下一次使用验证可以直接复用 T03-021、T03-066，再加入一个收益互换或公共资料条目；无需现在扩量。

观察四件事：能否从业务目录找到正确资产；是否看懂同表不同范围；第二个条目能否复用已确认定义且无需新页面/代码；证据更新后是否能保留人工工作并准确提示复核。记录人工改正次数与耗时，但当前没有实测基线，不预报节省比例。

以下情况应重新比较成熟产品，而不能因为已经写了代码就继续自建：

- 每新增业务品种都需要专属字段、页面和处理逻辑。
- 权限、Owner、审批、通知、跨团队审计、连接器和版本运营成为主要开发任务。
- 出现明确的自动查询、跨源执行、类型验证和可执行规则需求；优先实测 Legend/Ontop 等适合该能力的工具。
- 成熟平台通过标准接口能完成同一组样例，并明显减少后续维护代码和人工成本。

反过来，仅仅图谱有很多节点、竞品有本体图、界面更漂亮，都不足以构成迁移理由。
