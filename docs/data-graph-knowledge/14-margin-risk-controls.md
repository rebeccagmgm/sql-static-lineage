# 为什么同一份风险结果里，会有几种不同的“保证金余额”？

看保证金结果，首先要问：这一行描述合约、账户还是组合？金额是账户余额、模型计算结果，还是已经发生的资金变动？本轮核验发现，同一张保证金明细表甚至会在不同分支给同名字段装入不同来源的金额。

本篇沿两条真实路径阅读：组合日结果经 PDATA/NDS 标准化进入风险报表；账户日余额和资金变动经过关联、汇总，补进合约或组合明细。它们在所查图中处于末端，不代表学习价值低——报表正是在这里选择范围、组合口径并解释状态。

## 合约、账户和组合怎样接起来

`pdata_n.t03_otc_deri_agt_agt_grp_rela_adtnl_info` 保存两类来源不同的关系。141595 从账户与组合映射读取组合编号、保证金账户编号和资金账户编号，关系类型固定为 `14`；141596 从组合与合约映射读取组合、产品、内部合约编号，关系类型固定为 `13`，再补合约身份。

所以，查某合约关联哪个保证金账户，需要从合约或产品找到组合，再经组合找账户。两类记录不能因在同一张表就直接互换；这里也没有证明合约、组合、账户必然一对一。

176330 的互换单合约分支尤其直观：按产品匹配关系后，以组合编号排序取 `ROW_NUMBER()=1`。这是可见的选取规则，不是“该产品天然只有一个账户”的证据。[公共账簿知识](01-book-foundation.md)还会参与是否报送风控的控制，但账簿不是保证金账户。

## 第一条链：消费已有模型结果，再组织风险视图

源 `odata_n_tit.d_bundle_margin_daily_result` 经 160816 进入 `pdata_nds.bundle_margin_daily_result`，再被 200078 的 `dm_rsk_n.adm_v_risk_daily_bundle_margin` 读取。这条链中的动态名义本金、履约保障比例、需追加金额、可提取金额和履保状态，主要来自已有系统结果。

并行的 147139 将同一源结果写入 `pdata_n.t03_otc_cutp_marg_acct_perf_guar_rslt`，供合约保证金明细使用。虽然表名含“账户”，这份生产 SQL 用 `BUNDLE_ID` 填组合编号，把保证金账户编号、合约编号留空。不能仅凭表名把它解释成逐账户结果。

200078 还读取 199157 标准化的组合日参数，取得初始线、预警线、追保线、提取线、基础保证金率和估值等。参数子集要求 `IS_BUNDLE_VIEW='Y'`，按组合与源业务日期左连接日结果。

这里没有重新执行完整保证金模型：履保状态只是把源代码译为正常、预警、追保、未知或平仓。客户系数来自计划表，追保线来自参数表，需追加金额来自结果表；把这些字段放在一起，不足以证明本 SQL 用系数和追保线算出了该金额。

但也不是全量搬运。报表新增了：

```sql
DR.MGR_REMARGINABLE + NVL(DR.ADVANCE_AMOUNT,0)
    AS ADD_REMARGINABLE
```

即合计应追加金额包含源需追加金额与垫资金额；垫资是否大于零还决定一个展示状态。源需追加金额为空时，这个表达式仍可能为空，因为只对垫资做了空值补零。

## 两个余额并排，是为了保留不同来源

200078 同时输出批次保证金余额 `MGR_BALANCE` 和名为实时保证金余额的 `CURRENT_BALANCE`。前者直接取组合日结果；后者以已启用保证金账户为底，左连账户当前余额，经账户—组合关系换算到组合盯市币种，再求和。余额缺失的账户仍可能以零参与：

```sql
SUM(账户余额 * NVL(账户币种汇率,1) / NVL(盯市币种汇率,1))
```

上式是中文化的公式示意。174015 实际将源账户当前余额写入按运行日期选择的分区，因此“实时”是报表字段名称，不是本次已经证实实时刷新。SQL 缺少账户余额时补零，缺少汇率时补一，这些默认值也是口径的一部分。

**教学示意，非实际数据：**一个组合关联两个已启用账户，折算后余额分别为 80 和 20，报表当前余额可能为 100；同一组合批次模型记录为 95，也不能立刻判定少了 5。应先核对结果时点、账户范围和汇率，再讨论差异。

还要注意进入报表的门槛：组合用途须属于 SQL 指定的四类，并且必须存在账户—组合映射。`IS_CALC='Y'` 的过滤在所读 SQL 中被注释，报表保留 `IS_CALC` 字段；不能认定所有输出都满足已计算条件。

## 第二条链：余额是存量，追加与提取来自变动流水

107280 把保证金账户日余额的 `BALANCE` 写入通用账户余额表的 `Begn_Bal`，并只保留能匹配保证金账户的记录。目标名叫“期初余额”，并不能单凭命名证明源数值就是日初时点。

173965 将保证金台账的流水号、账户、发生金额、发生日期与生效日期分别保留，转换资金变动类型。176330/176360 再按账户关联这些流水，累加截至余额日期的记录：类型 `47` 计入 `Had_Apd_Amt`，类型 `54` 计入 `Had_Draw_Amt`。判断条件是余额日大于等于流水业务日，因此它们不是“当天新增金额”。

这说明几类看似相近的数值必须分开：

| 数值                   | 当前证据中的来源或作用                   |
| ---------------------- | ---------------------------------------- |
| 账户余额               | 账户日余额或当前余额快照，属于某时点存量 |
| 已追加、已提取         | 指定类型资金变动的累计发生金额           |
| 应追保、可提取         | 系统日结果给出的要求或可用结果           |
| 初始线、预警线、追保线 | 参数字段；已读 SQL 未重建原计算公式      |
| 估值、名义本金、利息   | 合约或持仓指标，不能直接当作保证金或到账 |

与[收付款及结算监控](09-cash-settlement-monitoring.md)一样，内部状态和台账结果不能替代真实银行到账证据。

## 同一张明细表，内部还会改变粒度

176360 的期权分支先统计组合中能匹配期权合约产品的记录数。未命中“计数大于一”的组合进入合约分支；命中的则进入组合分支。这里使用 `COUNT(*)`，不能未经数据核验就把计数等同独立合约数。

两分支的 `Marg_Bal` 已经不同：合约分支取模型结果的保证金余额，组合分支取账户日余额 `Begn_Bal`。组合行还把合约编号写为空。Facts 能同时定位这两个物理来源，说明这是需要按分支讲解的字段，不适合用一条统一释义遮住差异。

176330 的互换单合约分支限定组合计数为一，且只取三类互换；组合分支最终按账户代码和持仓业务日聚合。追保金额、比例、账户余额等使用 `MAX`，利息、多空本金和部分收益使用 `SUM`。本金换算又区分币种与结算币种，并选用期初汇率或期初定价日汇率。

这里已存在实质的报表口径重组。`MAX` 说明实现没有把重复关联的模型金额直接相加，但不能证明同组值一定相同，更不能替代账户、组合多重映射的业务确认。

## 日期与证据边界

组合风险视图同时保留源计算业务日和本次分区日。合约明细还会重取当天更新涉及的持仓日期及近期日期，再关联当天关系和合约资料。这种历史结果与当前关系的配合是否符合预期，需要单独核实。

本轮能确认三类工作：上游保存系统结果，关系决定对象如何连接，消费层再筛选、折算、汇总和展示。原始履保算法、系数合同、账户与组合真实基数、各金额的实际时点与资金真实性均未验证；不能由静态 SQL 判定风险结果已经正确或业务已获保障。
