# 当事人、客户和交易对手：先弄清编号属于哪一套业务

加工里出现“客户编号”，并不意味着全公司已经共用一套客户主数据。当前 SQL 展示了至少两种身份：TIT 来源的交易对手当事人，以及销售等业务系统中的客户。两者依靠明确映射连接。**学习这些公共对象，最有用的是记住编号的来源、关系方向和使用时点，而不是背一张客户表名单。**

## 同一个主体，会有不同方面的资料

在本批 TIT 加工中，`t01_pty_name` 提供名称，`t01_pty_cutp` 提供交易对手属性，`t01_otc_deri_cust` 提供 OTC 客户业务资料。它们都生成带 `TIT060-` 前缀的 `Pty_Id`，方便按当事人身份连接；但分别回答不同问题。

名称表将 `LONG_NAME`、`SHORT_NAME` 写成中文全称、简称，英文全称填空。交易对手表则把 `COMPANY/PRODUCT/INDIVIDUAL` 分成机构、产品、个人，并保留法律主体、产品编号和删除标志。其较粗的 `Pty_Cate_Cd` 只区分个人与其余分支，不能用它恢复全部交易对手分类；`MARKET` 等值也没有被 SQL 自动变成已知三类。

OTC 客户表保存另一组资料：主协议、补充协议、引入机构、客户经理、经办人及部分费率条件。所读写者从交易对手主来源取 ID，再按 `ID=KEY_CTPTY_ID` 左连扩展参数。主协议编号来自扩展参数，很多其他业务字段填空。**进入了客户表，只证明进入这一模型，不能据此认定协议已签署、资质已通过或所有资料齐备。**

## 前缀统一了格式，来源一致性还需要证据

名称与交易对手表各有两个已核对写者：一组读取 `d_ref_counter_party`，另一组读取 `d_ref_counterparty`。两者都把 `ID` 拼为 `TIT060-ID`，目标 `Src_Tbl` 标签也相同。交易对手产品编号在前一来源直接读取，在后一来源需要关联扩展参数取得。

这说明模型在吸收不同来源结构。SQL 能证明采用相同格式，却不能证明两份来源中相同 ID 永远指同一主体，或两个写者在同一天共同生效。判断一个编号时，要保留其具体生产路径；不能仅靠前缀或目标分区标签完成跨来源去重。

“历史”也有两种保存方式。名称表按来源、业务日期覆盖写入，没有 `Strt_Date/End_Date`；它提供按日快照，不能直接套用拉链区间。OTC 客户写者将当天来源与上一交易日快照比较，再生成当天记录，保留更新或删除信息。读取历史名称、客户状态和当前合约时，需要明确各自取哪个日期。

## 三种连接，分别解决三个问题

| 关系 | 已核实的左右方向 | 阅读时需要保留什么 |
|---|---|---|
| `pdata_n.t01_pty_rela_h` 当事人关系 `01` | `TIT060-KEY_CTPTY_ID` → `OUTSIDE_CTPTY_CODE` | 来源映射、关系代码与有效区间 |
| `pdata_n.t01_pty_rela_h` 当事人关系 `29` | 账户组交易对手 → 绑定的交易对手，两端均添加当事人前缀 | 左右方向；不能把两端直接合并成一个主体 |
| `pdata_n.t03_agt_pty_rela_h` 协议当事人关系 `06`，本章的 TRS 分支 | 互换合约编号／`20206` → `TIT060-KEY_CTPTY_ID` | 合约类别、关系角色与有效区间 |

第一种让 TIT 当事人找到外部业务客户码；第二种保存账户组的绑定；第三种把[合约对象](07-contract-objects.md)接到当事人。它们共同使用“关系表”，但不是同一种关系，也不能把账户组绑定直接解释为最终受益人穿透。

关系历史的 SQL 才使用 `Strt_Date <= 查询日 < End_Date`。当事人映射的历史匹配还包含右端编号，因此不能假设一个左端永远只对应一个客户。变化后如何开闭链可参照[协议关系历史](02-agreement-history.md)，具体使用时仍要筛选对应关系和来源。

## 一个真实消费：销售结果里的客户编号已经换了身份体系

期权销售加工 86840 先用合约的源交易对手编号连接当天映射表，再用 `OUTSIDE_CTPTY_CODE` 连接境内或香港客户来源的 `client_id`。该输出的 `Cutp_Pty_Id` 直接等于外部客户码，客户简称、全称也从业务客户来源取得。直接字段 Facts 确认了这些来源。

```text
合约.KEY_CTPTY_ID
  → 映射.KEY_CTPTY_ID
  → 映射.OUTSIDE_CTPTY_CODE
  → 业务客户.client_id
```

与之对照，已核实的子交易消费 107481 通过期权主表连 `t01_pty_cutp`，再按 `Pty_Id` 连名称表；其输出同样叫 `Cutp_Pty_Id`，保存的却是带当事人前缀的编号。**同名输出字段可以属于不同身份体系。**后续查询或字段分簇必须读到映射规则，不能把两个字段直接等值连接。

销售分支对映射和客户资料都使用左连接。映射缺失时，客户码和名称首先无法补齐；不能擅自用源 ID 替代。若同一源对手方映射多条记录，后续又没有压缩到唯一记录，合约行也可能被展开。当前没有实际数据，尚不能断言缺失或重复已发生。

销售客户资料还分别过滤删除标志与境内外来源范围。这是具体消费者选用的业务资料，不等同于名称表的所有当事人名称。理解了这一层，再阅读[合约销售收入](03-sale-foundation.md)，才能知道收入归集到了哪套客户身份。

## 客户身份与客户归属，需要分开理解

管理关系加工 105743 继续读取销售结果的客户码，再接引入信息和经办人资料。它还为一个明确指定的业务主体设置了例外：满足相应凭证条件时，以凭证中的交易客户码替换用于关联的客户码。本章不展示实际主体编号，也不把这个例外概括成通用客户穿透规则。

由此可以区分两件事：身份映射说明“这个编号对应谁”；管理归属说明“这个客户或合约在当前规则下由谁引入、由谁负责”。客户表里的客户经理字段、销售管理关系的归属结果，可能来自不同来源及规则，不能因为都与客户相关就互相替代。

举一个纯教学示意：源交易对手 42 在名称表里是 `TIT060-42`，外部业务客户码为 C900。账户组 G5 又绑定到 `TIT060-42`。查询名字可以使用当事人编号，汇总销售需要采用销售加工实际使用的客户码，查看账户组成员则沿绑定关系读取。三个编号共同服务于理解业务，但不意味着三个对象已经被证明完全等同。

这些知识可以反复复用：先确定对象和编号体系，再选名称、关系与日期，最后讨论归属和指标。表级热点告诉我们这里被大量连接；字段级分析还要区分名称展示、身份转换、关系选择和管理归属，才不会把所有“客户相关字段”聚成一个含义模糊的主题。
