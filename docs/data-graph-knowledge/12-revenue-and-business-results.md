# 创收、盈亏、规模和奖励为什么不能混读

同一张创收日报可以同时保存规模、持仓盈亏、模拟对冲盈亏、期权 NPV 计提和创收。下游又可能从中计算公司年度创收或每日规模。理解这条路线，关键是识别每个字段具体经过了什么计算，以及报表最终取了哪一列。

本篇检查 `dm_otc_n.otc_rev_daily_rpt` 在当前发布中的两个生产任务 230202、223867，以及年度创收 227701、每日规模 227697。它们构成从合约与金额材料到日报，再到不同业务结果的真实消费路径。

## 日报的一行有两个日期

日报生产者读取运行日的销售合约信息，再按 `Agt_Id` 内连接合约有效期内的销售附加明细。输出同时保留：

- `busi_date`：本次运行的业务日期，表示这份结果快照何时形成。
- `Accrued_Date`：附加明细的计提日期，表示这一行金额对应哪一天。

因此，日报的一个运行日快照可以包含历史多个计提日，不是每个合约只保留当日一条。实际行数还受其他关联影响，当前没有证明合约、计提日和来源分支能够唯一标识输出。

230202 从销售基础表的期权分支候选出发，分别组织静态与非静态对冲来源；223867 选金仕达分支并排除指定客户。当前发布仅见这两个写者，不能据此宣称四类销售基础来源都有完整对应日报路径。静态分支还会回连运行日全体合约快照，关联唯一性仍须核验。

基础合约与按日展开的来源见[销售合约](03-sale-foundation.md)和[交叉销售案例](04-contract-to-cross-sale.md)。

## 期权：不同类型采用不同创收逻辑

230202 的 `Curr_Rev` 用一个有先后顺序的 CASE 选择公式。产品类型先于柜台分支判断，所以不能把多个条件视为独立累加。

| 分支 | SQL 实际组织的金额逻辑 |
| --- | --- |
| 指定 `RISKY/AIRBAGX` 产品 | 按日费用、期权费、资金成本、保证金比例等参与计算；币种和跨币种类型进一步决定公式 |
| 动态对冲柜台 | 合约模拟对冲盈亏、合约相关持仓盈亏，以及按 Delta 分摊的标的剩余盈亏共同组成创收 |
| 静态对冲柜台 | 按初始名义本金在关联合约组中的比例分配组内盈亏；比例分母还含特定客户排除条件 |
| 其他未命中情况 | 此表达式输出 0 |

这些公式都已写在 SQL 中，但为什么采用这些资本成本、分配依据和客户例外，仍需要业务口径材料。部分参与乘除的值未统一补默认值；不能把“未命中分支为 0”扩展成“任何缺失输入都按 0 处理”。

证据：[230202](../../../sql-static-lineage-data/task-projections/tasks/230202/versions/054fea93fea9ed6256ee5087deea9b8e94b43aef5625415a20840276b3a06ae3.evidence-v3.json)，query 第 92–100、156–184 行。

## 动态对冲：先汇总到标的，再分回合约

动态对冲公式可以按 SQL 分成三部分：

```text
合约创收 = [合约模拟对冲盈亏
          + 合约相关持仓盈亏
          + Delta占比 ×（账簿侧标的汇总盈亏 − 同组模拟对冲盈亏合计）]
          × 对应日期汇率
```

Delta 占比使用绝对值，窗口按模拟侧的标的汇总标识和日期划分。账簿侧盈亏先通过[账簿映射](01-book-foundation.md)汇总到标的与日期，再与模拟侧连接；这里要同时理解两个标的标识之间的实际连接，不能仅因列名近似就视为同一键。

教学示意：假设同一窗口两份合约的绝对 Delta 为 30、70，账簿侧汇总盈亏 120，同组模拟盈亏合计 100，且全部关联唯一、汇率为 1。待分摊的剩余盈亏是 20，两份合约在这一项分别分到 6 和 14。这只是公式中剩余盈亏项的贡献，尚未加上各自模拟盈亏和合约相关持仓盈亏。

这个例子解释了为什么一个聚合又接一个窗口分摊仍然有必要：先得到共同标的层面的量，再按合约权重分配。它也提出必须核实的问题：窗口和连接是否覆盖同一组对象、分母是否可能为零、同一合约是否被重复关联。静态 SQL 本身不能保证分配守恒。

证据：230202 query 第 95、139–144、200–249 行。金额原始角色的区别见[持仓与估值](08-positions-valuation-pnl.md)。

## 金仕达：创收还包含成本和增量处理

223867 的 `Curr_Rev` 只对指定多空互换类型使用下列组成，其余该表达式为 0：

```text
日计提利息
− 实际占资 × 资金成本率 ÷ 365
+ 当日交易佣金
− 当日成交金额 × 固定费率
− 当日客户费用
```

利息来自销售附加明细，其中金仕达来源利息已在上游乘以 -1。佣金、成交额和客户费用在此使用窗口差分表达式，将来源累计值组织为当日增量；占资则按计提日关联对应交易日材料。不能看到上游名称为“累计佣金”就直接按每日记录相加。

资金成本率来自运行日取得的系数资料，先按生效日期形成期间，再展开到计提日匹配。这里同时使用了快照日期、生效日期、计提日期和交易日期，分别回答“取哪份资料”“规则何时适用”“费用归哪天”“选哪条市场日记录”。

系数缺失、窗口记录重置、同日多条累计记录怎样影响结果，尚未验证。表中的“实际占资”是来源字段职责，不是本篇完成的资金对账结论。

证据：[223867](../../../sql-static-lineage-data/task-projections/tasks/223867/versions/6c5c97670353118b223099fd048aca3f8b4d5176d58c54edd0e6f4c1ebf74fd5.evidence-v3.json)，query 第 92、147–197 行；利息符号见 107491 query 第 28 行。

## 期权 NPV 与创收在日报中分列保存

230202 另计算 `Opt_Npv_Curr_Rev`，在指定对冲柜台分支的起始日记录或分配期初 NPV 计提。它与 `Curr_Rev` 是不同输出列。223867 则把这一 NPV 列写成 0。

据此只能说日报分别提供两种量，不能自行把两列相加当成任意下游的正式收入。具体消费者是否使用 NPV 列，必须继续看实际 SELECT。Facts 在外层投影中可能把常量的中间列标为 `DERIVED_OUTPUT`，这不应误读为存在一个尚未找到的物理金额源；本篇用内层 SQL 核对了常量分支。

## 同一日报被下游问出了三个不同问题

### 公司年度创收

227701 先选运行日的日报快照，再取上年年初到运行日的计提日期。它按统一社会信用代码、客户全称及计提年份汇总：期权和互换分别累计 `Curr_Rev`，另一列将标的币种不等于人民币的记录累计为跨境创收，并把金额除以 10,000。

这段 SQL 没有把 `Opt_Npv_Curr_Rev` 加入上述创收。所谓“跨境”在此也对应一个具体币种条件，不是已核验的完整跨境业务制度定义。跨境列与期权、互换列可能覆盖同一批记录，不能把三列相加当总收入。

### 每日规模曲线

227697 也读取运行日快照，却按客户与计提日汇总 `Dyna_Nom_Prin`。字段名含 `amount_change`、注释称“规模变动”，但 SQL 没有计算相邻日之差：它给出各日规模值。若要解释实际增减，需要另算日期间差额，不能直接把这个字段当差分结果。

### 交叉销售奖励金额

227701 还从 `pdata_n.t98_otc_deri_undrl_income_rwd_sum` 汇总 `Dev_Dept_Rwd`，按客户名称和年份连接到公司年度结果。这是一条奖励金额来源，并非[交叉销售规模日均](04-contract-to-cross-sale.md)的另一种名称。

名称相同或相似不代表键与口径相同：这次奖励连接使用客户名称与年份，而日报主聚合还带统一社会信用代码；同名、名称变更及多重匹配的实际影响仍需数据核验。奖励来源的业务计算过程也尚未在本篇展开。

证据：[227701](../../../sql-static-lineage-data/task-projections/tasks/227701/versions/56bc3d521850db14663cd55d76c21c53516335189eea1cde089db9c8f0342c2b.evidence-v3.json)，query 第 10–44 行；[227697](../../../sql-static-lineage-data/task-projections/tasks/227697/versions/dde02898bbcc610245d3e308de389be76c8094f2531be7b7802b18a9601ee6d9.evidence-v3.json)，query 第 8–21 行。

## 怎样判断自己是否读懂了

看到日报中的一个数，应能区分它是本金规模、持仓或模拟盈亏、按规则分配后的创收、另列的 NPV 计提，还是另一来源的奖励。随后确认它的计提日、快照日、单位转换、参与范围及最终消费者。

本篇已解释当前两条生产路径和两类真实消费，但未确认财务收入确认制度、客户例外理由、生产数值、所有分支覆盖或累计来源重置机制。金额进入报表也不能证明已经收付，相关状态边界见[现金结算与监控](09-cash-settlement-monitoring.md)。
