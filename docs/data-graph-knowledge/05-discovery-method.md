# 从加工图重建业务知识：方法与本轮复盘

复盘更新：2026-09-08。

本轮沉淀出一套可以继续使用的分析顺序：**结构找候选 → 业务问题定范围 → 按具体写入取证 → 分开解释值、控制、粒度和时间 → 比较分支与反例 → 登记覆盖及缺口。**

这些方法已经在知识库第一版的多个实例中帮助发现规则、纠正解释和缩小问题。它们尚未组成经全图验证的自动分类算法，也没有证明整个图谱的业务语义已经分析完。本页记录方法上的收获和纠偏，不代表修复了原始加工。

**后续进展（2026-09-08）：**第一版之后，已直接消费同一发布版本的 Neo4j 图，复算全图表级结构，并补做路径中介性、全图 `VALUE` 与 `CONDITION`／`DATASET_CONTROL` 字段聚合、2-core／双连通结构及探索性分簇。策略、发现和证据边界集中记录在[图消费的策略与新增发现](20-graph-consumption-method.md)。下表及本页案例保留第一版当时的取证范围；后续全图统计没有把 109 个任务的业务解释覆盖扩大为全图语义覆盖，也没有完成业务簇验证。

## 一、让结构指标负责选题，保留业务判断

**解决的问题：**高连接数、看起来居中或经过同一个大节点，很容易被直接解释成公共资产、核心模型或业务簇。

本轮先对源表—目标表身份全局去重，排除自连，再计算度数，最后按 schema 展示。不能先切 PDATA 子图，再把其中的度数称为全图权重；同名对象也不能未经身份核验就合并。

选题时分别看几项证据：

| 结构观察                 | 适合提出的问题                                     |
| ------------------------ | -------------------------------------------------- |
| 不同下游表数、消费任务数 | 哪些对象经常被使用，是否值得先解释一次？           |
| 入度与汇聚位置           | 哪些输出把多种对象组织成共同结果？                 |
| 下游 schema 分布         | 是否跨多个消费区域？这些区域是否真的承担不同职责？ |
| 排除公共输入前后的变化   | 当前角色是否主要由公共连接造成？                   |
| 零入／零出、多个写者     | 是否存在采集缺口、任务内部消费、导出或并行来源？   |

本轮按 `出度 + sqrt(入度×出度)` 安排了 55 个结构候选的探索顺序，又补查高入度终点、风险和香港区域。这只是启发式排序，未校准为业务重要性总分。权限整合表的高入度没有让它自动成为 OTC 核心；风险终点则因具体业务问题进入正文。

**可复用结论：**保留可解释的指标分量，再用 SQL 验证职责。下游多说明复用线索，汇聚多说明整合线索，均不直接证明学习价值。[结构发现](06-graph-findings.md)、[选题账本](coverage.md)

## 二、把公共资产的降噪作用和知识价值分开

**解决的问题：**剔除几张公共表后，图变化不大，容易误以为公共知识没有价值；反过来，按规则被排除的表也容易从讲解中消失。

四张基础表临时排除后，222 张保留表度数改变，49 张跨越度数角色类别；194 条完整链保持不变，最大弱连通分量仍有 2,340 个节点。它对拆开网络的帮助有限，不能据此宣布得到清晰加工簇。

但另外两类价值已经出现：

- **解释复用。**账簿的组织、柜台、标的映射，以及关系的来源和有效期，能够反复帮助理解持仓、结算和经营加工。
- **规则控制。**230202 的账簿附加表只覆盖一个最终输出的输入足迹，却还通过柜台条件控制盈亏池；159763 的公共 `grp_def` 既转换组身份，又通过内连接限制结果范围。

因此，粗图可以折叠公共输入，讲到具体规则时仍须恢复其作用。“公共”和“核心”也允许重叠：一个对象可以同时提供复用知识、承载身份，并决定重要结果。

**还没有解决的部分：**本版未实测“减少了多少重复解释或阅读时间”。解释复用是已得到案例支持的价值判断，不是已经量化的收益指标。[账簿](01-book-foundation.md)、[关系历史](02-agreement-history.md)、[字段主题](18-field-themes.md)

## 三、先固定最终写入，再计算字段比例

**解决的问题：**统计中间 `SELECT *`、混合多次输出、忽略未知状态，会让字段数量看起来精确，实际却回答了不同问题。

本轮采用以下计算单位：

1. 从投影的 `localClosure.finalWrites` 选择具体输出。
2. 同时用 `target_dataset` 和 `write_observation_id` 限定 `bindings`；保留对应语句信息。
3. 以 `binding.expression_id` 精确查找表达式，检查重复目标和缺失表达式；不能先把不同写入混在一起去重。
4. 分别统计绑定目标数、各依赖状态、有已知输入列表的目标数，以及去重输入字段数。
5. 对每个来源，统计其 `input_fields` 覆盖的不同目标字段数。同一来源对同一目标只计一次；不同来源对同一目标允许重叠。

如果以全部绑定目标为分母，来源覆盖比例是：

```text
某来源覆盖比例
  = 已记录该来源输入的不同目标字段数
    ÷ 本次限定写入的全部绑定目标字段数
```

这叫 **Facts 暴露的输入足迹**。它可能包含分支判断等上下文，也可能缺少关系控制，不能直接称为纯数值贡献。若改用“有已知输入足迹的目标”作分母，必须明确说明；没有进入绑定的静态分区列也不能悄悄补入分母。

| 真实样本              | 绑定目标数 | 至少有一项输入足迹的目标 | 各来源覆盖次数合计 | 方法上的发现                                             |
| --------------------- | ---------: | -----------------------: | -----------------: | -------------------------------------------------------- |
| 207284 净值加工       |         23 |                       20 |                 20 | 行情源覆盖 16、证券源覆盖 4；三项无物理输入另报          |
| 230202 创收日报       |         72 |                       54 |                 64 | 多来源落在同一输出，覆盖次数不能相加成互斥份额           |
| 159763 交叉销售月日均 |         11 |                        5 |                  7 | 五个有足迹目标包括一个 PARTIAL；一列金额也可能有复杂分配 |

230202 中 `Curr_Rev` 暴露八个来源，`Opt_Npv_Curr_Rev` 三个，`Map_Undrl_Cd` 两个。这支持按字段用途组织重叠主题，没有证明整张日报只能属于一个簇。

`PARTIAL`、`DERIVED_OUTPUT`、空绑定均保留原状态。没有输入列表不等于没有影响；`PHYSICAL` 也不代表实际运行已验证。完整定义与来源计数见[字段主题](18-field-themes.md)。

## 四、区分“谁给出值”和“谁决定怎样取值”

**解决的问题：**把所有关联表都算成值来源，会夸大字段依赖；只看直接取值列，又会漏掉决定口径的少数字段。

本轮把字段及关系用途分开解释：

| 用途         | 要追问什么                               | 证据入口                   |
| ------------ | ---------------------------------------- | -------------------------- |
| 值与数值运算 | 哪些字段提供金额、日期值，或参与算术？   | 输出表达式、直接输入       |
| 分支选择     | 哪个条件决定采用哪条公式或哪个日期？     | CASE 条件及分支角色        |
| 纳入与关联   | 哪些条件决定记录存在、接上谁、匹配几行？ | WHERE、JOIN 及连接方式     |
| 分组与粒度   | 哪些键决定记录被汇在一起？               | GROUP BY、展开和去重       |
| 窗口与时间   | 用哪一组记录、哪一天、哪个有效区间？     | 窗口表达式、日期和历史条件 |

这不是把 SQL 关键字机械分成“值”与“控制”两类。Delta 在动态创收公式中参与算术，是数值计算的一部分；JOIN 也可能通过增行改变求和结果，不能称为与金额无关。

最清楚的例子是 107481：结构字段 `Ko_Yield_Pay_Type_Cd='EXPIRY'` 决定选到期日，否则沿触发、触线、终止日期等回退。结构表不提供最终日期值，却决定日期口径。Facts 的 `BRANCH_SELECTOR` 与 `RESULT_VALUE` 帮助分开定位；完整选择逻辑仍须读 SQL。

**可复用结论：**字段数量衡量引用范围，字段职责解释业务作用。少字段可以有关键控制作用，不能按比例直接删除或忽略。[结构参数](17-option-structure.md)、[持仓与创收](08-positions-valuation-pnl.md)

## 五、用粒度变化和新增决定划定知识片段

**解决的问题：**强迫一张表只属于一个主题，或把连通块当作业务片段，解释范围容易过大，也可能切断关键规则。

本版改为先写一个具体问题，再圈定需要解释的输出字段、对象、时间和规则。例如：

> 合约规模为什么会进入某客户、机构、员工的月日均？

这个问题需要销售基础、按计提日期展开的日明细、归属关系、纳入条件、比例、标签和分母。片段可以跨越多张表；创收主题又会复用其中部分对象。两者重叠是有意义的。

寻找值得停下来讲的位置时，优先看：

- **一行含义改变。**合约快照 → 合约某日规模 → 客户／机构／员工的月指标 → 去员工维度的客户机构标准资产。
- **本步新增决定。**付款安排选择日期、组织条件决定归属、固定系数改变折算结果、分支选择不同收益公式。
- **身份或来源改变。**外部客户码与统一当事人编号、父合约与子交易、源市场码与标准市场码。

“粒度”先按 SQL 的分组和选择解释；没有数据检验，不能顺带声明键唯一。元数据中的“历史拉链”等描述也须核对实际区间列和维护逻辑。

“规则首次出现”更要限定范围：只能说在已核验路径的哪一步引入或执行；生产端直传参数、消费端才应用参数，不证明源系统此前没有定义过该规则。[规模路线](04-contract-to-cross-sale.md)、[标准资产](13-standard-assets.md)、[合约对象](07-contract-objects.md)

## 六、比较相似分支，主动寻找不能合并的差异

**解决的问题：**统一目标结构、相同字段名、相同来源标签或相同 query，容易让不同业务实现被讲成一套规则。

本轮有效的比较维度是：对象编号、来源身份、行粒度、日期、过滤、公式、空值／常量，以及最终写入步骤。

| 比较对象                   | 发现的实质差异                                 | 应保留的解释                   |
| -------------------------- | ---------------------------------------------- | ------------------------------ |
| 四路销售基础               | 同样的输出结构，编号、本金和选择来源各异       | 统一字段不等于统一业务口径     |
| 动态／静态创收与金仕达分支 | 分配依据、成本和差分公式不同                   | 必须解释分支条件及分子、分母   |
| 标准资产月／年结果         | OTC 年度另取年内日均并用固定系数               | 不能默认年度是月结果加权       |
| 风险报表普通／h15 路径     | 部分 query 相同，finish 是否写备份不同         | 比较完整加工槽，不能只比主查询 |
| 不同结构写者               | 实际读源含普通与 _P 变体，目标来源标签可能相同 | 目标标签不能反推唯一物理输入   |

这些差异可以是合理变体、源模型约定或历史问题。方法上先记录实现及影响的解释，再把制度理由、币种前提等放入待确认问题，避免先判对错。[销售基础](03-sale-foundation.md)、[创收](12-revenue-and-business-results.md)、[风险报表](16-risk-pnl-report.md)

## 七、完整线性链要逐跳核对选择范围

**解决的问题：**链越长就越值得讲，或者图上存在连续路径就说明数据能够一路传到结果，这两种判断都不可靠。

完整链只表示：中间单入单出节点已延伸到两端结构边界。公共对象已被排除时，图上的单输入主干不等于 SQL 只读一张表。多输出任务的读表×写表组合也不能直接作为每个输出的字段因果。

本轮最长两条链给出不同取舍：

- **L001：运输为主。**多跳直传可以合讲，但原分区改成来源批次、固定日期与参数日期、末端刷新方式仍应保留。
- **L002：标准化和消费选择值得深讲。**事件／客户／产品编号转换、市场转码、受影响交易日重建，以及下游重新选择源编码、清空审计字段，均改变了结果含义。

尤其有用的核对是**相邻两跳的范围能否接上**：202899 可因当天修改回补较旧交易日；202186 只读取基准日前 10 天至当日。若回补涉及窗口之外，该次后续查询便不会选中。这个条件差异已由 SQL 支持，尚不能断言实际发生漏数。

因此逐跳保留：读写对象与身份、日期参数、纳入条件、维护范围、字段变换、最终落点及未知边界。结构连续、静态条件可接续、实际数据到达是不同结论。[完整链复盘](19-linear-chain-lessons.md)、[结构清单](structural-inventory.md)

## 八、复核要寻找会推翻讲解的具体反例

**解决的问题：**写完后只检查链接和哈希，会保留“整体听起来合理、关键细节却错了”的解释。

本轮独立复核实际纠正了这些问题：

| 最初容易采用的概括             | 复核后的准确说法                                           | 可复用的核对点                                   |
| ------------------------------ | ---------------------------------------------------------- | ------------------------------------------------ |
| 静态分配就是同池本金占比       | 分子与分母引用不同来源表达式，分母还排除指定客户           | 看分子、分母和窗口集合是否相同，不先假定比例守恒 |
| 当前余额汇总从余额表出发       | 以启用账户为底，左连余额；缺余额账户仍可能参与             | 看 FROM 的底表与 JOIN 类型，不只看金额来自哪张表 |
| 到期后延续就是冻结终止日数值   | 还将当日损益、数量及动态本金置零，本年指标另受年度条件控制 | 比较逐字段处理，不能以一项日期规则概括全行       |
| LIKE 是字面子串匹配            | 规则中若含 % 或 _，仍可能按模式解释                        | 用原操作符含义，避免自然语言概括扩大保证         |
| 旧交易日已回补，后续就能导出   | 下游日期窗口可能不包含该旧日                               | 比较跨跳维护与消费范围                           |
| 已讲过相关概念，就算该表已覆盖 | 相似表或相似业务词不足以证明精确对象已解释                 | 逐项对照表身份、正文和证据                       |

金额命名也提供了需要继续核实的线索：部分“已实现”输出实际引用总结构化收益。当前记录为实现与命名差异，保留源口径问题，没有据此更改 SQL。[保证金](14-margin-risk-controls.md)、[风险报表](16-risk-pnl-report.md)、[待确认问题](open-questions.md)

## 九、用可回查的覆盖账本约束“完成”

**解决的问题：**看过图、预览 SQL、写过一个消费、讲过整条主线，容易混在一个“已分析”计数里。上一轮“第一版完成”的简略表述也造成了“是否整个图谱都分析完”的误解。

今后至少分开以下覆盖状态：

| 状态               | 应记录的具体内容                                       |
| ------------------ | ------------------------------------------------------ |
| 结构已观察         | 精确对象、度数／候选依据；尚不代表语义解释             |
| 生产侧简讲         | 已读生产者、来源字段与映射；尚未闭合消费               |
| 消费侧解释         | 哪个消费者使用哪些字段或条件；不替代生产规则           |
| 指定范围已深入     | 已解释的问题、生产／消费分支、关键字段和规则、证据缺口 |
| 后续候选／边界保留 | 为什么还不能解释，缺哪类证据                           |

现有[候选账本](coverage.md)经正文核对，部分表已从“已深入／消费侧解释”退回候选或边界。不能把 `D_REF_TRS_LEG` 的解释当作 `D_REF_TRS` 的覆盖，也不能把讲过客户或公共常量概念当作某张具体客户／常量表已解释。

每次汇报先说完成了哪一层、哪些问题及哪些分支，再给数量。109 个任务和 224 段 SQL 哈希核验是材料范围与一致性证据；学习是否连贯，还需读者验收。第一版完成的目标是形成重点问题的知识骨架，不能升级为全图语义完成。

## 下一轮可直接沿用的工作顺序

1. **固定证据和范围。**发布版本、对象身份、排除规则、分析层次与当前未知要明确；来源变化后不能直接沿用旧统计。
2. **选一批互补候选。**同时考虑高复用、汇聚终点、业务区域与具体问题，记录入选和暂缓理由。
3. **先提出要回答的问题。**圈定输出、字段用途、对象和期间；允许知识片段重叠，避免先为全部表分组。
4. **从具体写入取证。**绑定到目标与写入身份，再读表达式、关系和 SQL 各槽；对缺口保留状态。
5. **解释发生了什么变化。**从身份、值、粒度、时间、控制、来源差异中挑真正改变理解的内容；重复运输可合讲。
6. **找一个能够挑战解释的检查点。**例如分母排除、NULL、左连接、跨年、窗口外回补、多输出或同名异义；只核验与当前结论有关的范围。
7. **写回知识和覆盖账本。**记录已确认实现、解释判断、待确认理由与精确证据，分别报告结构、语义、字段和链的完成程度。

这是一套人工与 Agent 可共同执行的工作法。本轮执行了临时只读统计复算，没有建设新的统计工具或分类平台。继续实施时，优先增加可解释的业务问题与规则，工程投入应服务于这些解释需要。
