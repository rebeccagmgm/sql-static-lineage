# 合约规模怎样成为交叉销售月日均

这里回答一个具体问题：**一份 OTC 合约的规模，经过哪些步骤，才能进入某个客户、机构和员工的交叉销售月日均？**

在已核验的任务 159763 中，结果来自四类决定：每天有多少规模、哪些合约和日期纳入、规模归给谁，以及用多少天作为分母。最终还要匹配客户、机构和员工的组合定义，才能形成输出。

目标表为 `dm_index_n.index_grp3_compscal_otcderi_cs_mthapd`。本文解释固定 SQL 中的实现，尚未用真实数据验证数值，也未取得全部纳入规则的制度依据。

## 先看三份材料怎样汇合

```text
销售合约基本信息 ─────────────── 当前客户、产品属性 ───┐
      │                                              │
      ├─ 107491：展开计提日期 → 每日规模明细 ──────────┼─ 159763：筛选、分配、月内日均
      │                                              │
      └─ 105743：组织管理关系 → 机构、员工、分配比例 ──┘
```

证券属性和组合定义也参与最后一步，图中省略以突出主线。这里是并行准备材料后汇合；不能把三张输入表排成一条首尾相接的线。

| 材料           | 实际表                                     | 在 159763 中的作用                 |
| -------------- | ------------------------------------------ | ---------------------------------- |
| 运行日合约     | `pdata_n.t98_otc_deri_comp_sale_info`      | 当前客户、产品类型、标的及来源分支 |
| 月内每日规模   | `pdata_n.t98_otc_deri_comp_sale_adtnl_det` | 各计提日的 `Dyna_Nom_Prin`         |
| 运行日管理关系 | `pdata_n.t98_otc_comp_mng_rela_info`       | 至多三组机构、员工和分配比例字段   |

## 第一步：从合约快照变成按日规模

107491 读取运行日的销售合约基本信息。它把提前终止日优先作为结束日，没有提前终止日才使用到期日；保留结束日晚于 2021-09-30 且起始日不晚于结束日的记录，然后利用日期表达式和 `posexplode` 展开 `Accrued_Date`。

展开起点表达式是 `default.gfgreatest(起始日, 运行日前150日)`，意图是结合合约开始与回看范围生成日期。本轮没有核验这个自定义函数实现，不把异常、空值或未来起始日下的精确行为当成已证明事实。

**同名 `Busi_Date` 在这一步改变了含义。**输入用它选运行日快照；输出则把 `Accrued_Date` 写入 `Busi_Date`。因此，运行日一次加工可以产生或重写多个计提日期的分区。输出的加工日期字段仍保留运行日。这直接解释了为什么不能只看到两个表都有 `Busi_Date` 就按同一种时间理解。

每日规模还要重新计算，而不是把当日规模复制到所有历史日：

| 来源分支      | 每日规模的主要实现                                                                     |
| ------------- | -------------------------------------------------------------------------------------- |
| 期权 `01`     | 起始日使用初始规模；之后结合已生效的部分终止、提前锁盈事件累计变动并折算；结束日后置 0 |
| 普通 TRS `02` | 起始日使用初始规模；之后取对应历史日持仓的规模并折算；结束日后置 0                     |
| 金仕达 `03`   | 将来源记录按业务日期区间展开，取动态名义本金                                           |
| 极速互换 `04` | 按工具与历史日期汇总日终持仓动态名义本金，再关联每日明细                               |

这些分支仍依赖不同标识关联。它们的基础来源差异见[销售合约文章](03-sale-foundation.md)。当前“合约×计提日”是意图粒度，不能据此保证连接后每天只有一行。

证据：[107491](../../../sql-static-lineage-data/task-projections/tasks/107491/versions/96d77f8bf4a0634557b1b3273438c9874160e9119146701ccf295167033dc1dc.evidence-v3.json)，query 第 11–50 行、53–131 行。

## 第二步：补上管理关系

105743 从运行日合约中取 `Agt_Id`、客户等标识，组织三组机构、客户经理和分配比例。多项输出使用 `coalesce(合约级值, 客户级值)`，表达了优先使用合约级非空值、缺失时回退客户级值的实现。它还涉及客户替换和经办人等分支，本文只解释 159763 直接使用的部分。

这里有两个需要保留的细节：`coalesce` 判断的是 NULL，不能自动解释为空字符串也会回退；SQL 使用 `select distinct`，也不能保证每个 `Agt_Id` 只有一条管理关系。

证据：[105743](../../../sql-static-lineage-data/task-projections/tasks/105743/versions/9c728eb8cb3d3dff34755347b93b1a3e69aae4393bc2b6f11065ebd0f44f0152.evidence-v3.json)，query 第 102–128、163–182 行。

## 第三步：哪些材料实际进入交叉销售

159763 读取上述三份材料时，已经施加了多层条件。

| 位置     | 已确认实现                                                                       | 对理解结果的影响                                                                                         |
| -------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 合约输入 | 取运行日，要求 `Src_Contr_Type != 'FEE_SWAP'`，仅选 `grp_id in ('01','02','03')` | `FEE_SWAP` 和类型为 NULL 的记录都不能通过该比较；`04` 没有被这段合约输入选中，不能推广到所有交叉销售加工 |
| 每日明细 | 取月初至运行日，且日期位于合约起止日闭区间内                                     | 只对月内有效日期的明细累加                                                                               |
| 连接方式 | 合约与每日明细内连接；管理关系左连接，均以 `Agt_Id` 为条件                       | 缺少每日明细的合约无法经过该内连接；是否跨分支碰撞、是否多行匹配需要数据核验                             |
| 管理纳入 | 根据三组机构编码、少量合约例外名单、客户经理标识条件继续筛选                     | 名义上左连接的管理资料仍可能影响记录是否留下                                                             |
| 指标标签 | 根据部门、标的类别、币种、产品类型等分成两个 `tag_id`                            | 同一客户与机构还可能形成不同指标标签结果                                                                 |

两个标签的正式业务定义、例外名单理由及全部机构编码含义尚未核实，不从代码形状推定制度名称。尤其是证券币种这一小部分字段，会影响标签分支；图上临时排除证券基础表并不意味着业务解释时可以忽略它。

还有时间口径：这里用**运行日的客户与管理关系**组织**月内不同日期的规模**，没有逐日读取历史归属。这是可明确询问业务的一个问题：制度期待当前归属口径，还是历史逐日归属口径？

证据：[159763](../../../sql-static-lineage-data/task-projections/tasks/159763/versions/c87821fad514ef930309c036b4a8b04a78b1be5539385b41aa0ce1a3ddc81a31.evidence-v3.json)，query 第 1–44 行。

## 第四步：按比例分配，还会调整分给谁

SQL 将三组比例分别乘每日规模，通过 `UNION ALL` 形成分配记录。但它没有在所有情况下简单采用“第 i 组比例→第 i 组机构与员工”。

在“三组机构至少一组满足数值编码小于 8000”的分支中，各组按不同顺序寻找满足条件的归属对象：

| 使用的分配比例 | 选择机构与配套员工的顺序                                 |
| -------------- | -------------------------------------------------------- |
| 第 1 组比例    | 第 1 组满足条件则用第 1 组，否则看第 2 组，再回退第 3 组 |
| 第 2 组比例    | 第 2 组满足条件则用第 2 组，否则看第 3 组，再回退第 1 组 |
| 第 3 组比例    | 第 3 组满足条件则用第 3 组，否则看第 2 组，再回退第 1 组 |

**比例取哪一组，与最后归给哪一组对象，可以分离。**例如，只有第 2 组机构满足条件时，来自不同组的比例可能都归到第 2 组机构及其员工。机构编码条件的正式业务含义仍待确认。

另外三条 `UNION ALL` 分支，要求三组机构各自经条件表达式归一后都等于 `8848`；这些分支直接输出各组原有机构和员工。这里的归一用于判断是否纳入，并没有把输出机构统一改写成 `8848`。不能将其笼统讲成覆盖所有剩余情况的兜底分支。

SQL 未在此保证三组比例合计为 1，也没有统一证明空比例可以得到有效分配值；第二、三组还各有非零比例条件。例子可以帮助理解公式，但真实比例质量需要数据验证。

证据：159763 query 第 65–133 行。

## 第五步：汇总并除以当月自然日数

分配后的记录按客户、机构、员工及 `tag_id` 汇总。核心计算为：

```text
月内日均 = 月内纳入的每日分配规模之和 ÷（运行日距当月第一天的天数 + 1）
```

分母是月初至运行日的自然日数，包括运行日，不是明细行数、交易日数或合约实际存续天数。没有明细的日期不会增加分子，分母也不会随之缩小；这不证明缺失日期在业务上应该视为零。

**教学示意，假定全部关联、纳入与比例条件均满足，单位为假设的规模单位：**运行日在某月第 10 日，一份合约仅第 9、10 日各有规模 100，分给某员工的比例为 60%。该员工贡献为 `(100×60% + 100×60%) ÷ 10 = 12`。若错用两天作为分母，会得到 60，回答的是另一个问题。

随后 SQL 排除汇总值为 0 的组，并通过 `grp_def` 将客户、机构和员工映射到组合 ID。最终三处组合内连接意味着：即使此前算出了值，缺少相应组合定义也可能不能出表；客户、员工的最终组合查询还要求有效状态。已检查的机构查询没有同样的状态条件，应保留这个区别。

最终行在本次月份上下文中对应客户组合、机构组合、员工组合和标签。是否存在重复组合定义或其他多行匹配，仍需实际数据检查。

证据：159763 query 第 46–63、135–144 行。

## 这段加工教会了什么

一个“月日均规模”并不只是一条 SUM 公式。日期展开决定可计量的日序列，产品分支决定各日金额，当前归属和机构选择决定分给谁，过滤决定哪些记录纳入，分母决定怎样平均，组合定义决定结果能否落到目标对象。

当前最值得继续确认的业务问题是：为什么这一版不选择 `04` 合约输入；为什么使用运行日管理归属；机构间回退和例外名单的业务依据是什么。与之分开，需要数据核验的是编号唯一性、每日覆盖、关联倍增、比例合计及组合映射覆盖率。

本篇已经可以解释固定 SQL 的这条加工链；它尚不是业务制度验收，也未继续解释后续标准资产折算。
