# 同一交易为什么又出现在香港加工表中

`dm_hk_n.trd_otc_trade` 并非简单把所有源交易换个表名。已核验的 134545 根据账簿所属公司与映射规则，选择面向香港账簿的交易视角；同一交易编号可以保留原始账簿，也可以配上规则指定的目标账簿。

本篇用交易、期权观察值和汇率三种输出，说明应用层如何选择业务范围并重新组织字段，也区分业务整理与后续文件交付。它解释的是当前发布中的代表性香港加工，不代表完整香港业务系统或全部 168 张可见表都已核验。

## 交易身份保留，账簿视角可以改变

134545 保留来源交易编号、产品键、业务类型和内部合约编号。账簿字段与 `BOOK_SIDE` 则随分支变化：

| 分支 | 纳入依据 | 输出账簿与标记 |
| --- | --- | --- |
| 原账簿属于指定香港公司 | 交易内连账簿，筛账簿公司 `GFS_HK` | 保留原 `KEY_BOOK_ID`，`BOOK_SIDE='0'` |
| 合约编号与映射规则条件相等 | 交易连 TRS、规则、账簿映射及目标账簿 | 写目标 `key_book_id_to`，`BOOK_SIDE='1'` |
| 规则标为 `IN` 的合约条件分支 | 实际 SQL 使用 `contract_code LIKE '%条件%'`，再校验原账簿与目标账簿 | 写目标账簿，`BOOK_SIDE='1'` |
| 交易对手规则分支 | 用交易对手简称匹配规则条件，再校验账簿映射 | 写目标账簿，`BOOK_SIDE='1'` |

第三行尤其需要按表达式解释：规则字段虽然写 `IN`，此处执行的是 `LIKE` 模式匹配，在规则条件前后拼接 `%`；条件本身若含 `%` 或 `_`，仍会作为模式字符，不能直接当作解析后的合约清单成员判断。简称匹配、规则重叠及多目标映射是否符合业务预期，需要对应配置和数据核验。

四个分支使用 `UNION` 合并，会去掉整行完全相同的结果；它不保证每个交易编号只有一行。不同账簿或不同 `BOOK_SIDE` 的记录仍可以并存。

教学示意：如果同一交易的原账簿和某条映射的目标账簿都满足香港范围，它可以以原始账簿视角和映射账簿视角各出现一行。此时两行共享交易身份，但表达的账簿视角不同。不能仅按交易编号把其中一行视为重复脏数据，也不能直接把交易金额按两行相加。

证据：[134545](../../../sql-static-lineage-data/task-projections/tasks/134545/versions/5a6826729dca1aeac7f07f2cb773714bd4481be569017d7750a919ac0e3d62e6.evidence-v3.json)，query 第 14–172 行。与公共[账簿](01-book-foundation.md)、[关系模型](02-agreement-history.md)相关，但本任务直接读源账簿和映射材料，不必先经过对应 PDATA 公共表。

## 期权观察值：行情记录还要经过业务对象筛选

134518 从期权行情中取记录标识、观察日、结算价，分别写入香港输出的期权内码、观察日期和 reset 值。标的内部编码则从备注 JSON 中的来源产品编号解析而来。

这段加工又按产品键内连运行日子交易，再按账簿编号内连香港账簿范围。因此，输出不是所有期权行情的全集：只有能接上相应子交易和香港账簿的记录才能留下。

这里同时出现行情日期与运行日期：`OBS_DATE` 由行情日期转换，输出 `busi_date` 写运行日。源行情子查询没有统一按运行日裁剪为一天，不能把观察日期与输出快照日期混同。

证据：[134518](../../../sql-static-lineage-data/task-projections/tasks/134518/versions/ec34e927356c38904c521d41584c16728d8fc097511ee2515948088012bfa966.evidence-v3.json)，query 全文 31 行。子交易与父合约的关系见[合约对象](07-contract-objects.md)。

## 汇率输出：有些加工可以简讲

166014 从 `pdata_news_n.t02_fxr_cfets_quot` 选择指定来源与分组，将币种、中间价和行情日期映射为香港表字段，并另写运行日。没有在这里重新计算汇率。

它适合与[证券、汇率和时间基础](11-security-market-time.md)共用解释：先确定币种、行情日和取值口径，再说明字段搬运即可。无需给每一次相同映射重复写一篇长文，但要保留来源筛选和日期含义。

## 相似路径仍要核对真实来源

245498 的交易整理结构与 134545 相似，读取的是一组 `_p` 来源，输出 `dm_hk_n.trd_otc_trade_info`。当前保存的 SQL 多处写 `busi_date='h13'`，同时输出日期又使用运行日参数。

本篇只能确认这个表达式出现在证据中，尚未验证来源分区定义以及它与预期运行参数是否一致。不能据任务名补写成另一个日期条件，也不能把这条路径当成已经通过运行验证的同义复制。

## 加工结果与交付动作需要分别理解

任务 198512 的 SQL 从香港交易表选择字段，将空值或空串转成导出占位文本，并增加导出时间。这说明它承担交付前的表示转换；原始 SQL 没有体现前述业务范围与账簿规则的再次计算。

其发布投影把该表记录在最终写入位置，而外部读列表为空；实际 SQL 又明确从同名表读取。因此，图中“写者名单”的任务数不能自动解释成同样数量的独立业务生产路径。这个边界也说明为什么我们要回查 SQL，而不是直接把所有表级关联讲成业务流程。

本轮未核验导出文件、接收端加载、调度结果或下游可见数据，不能以已存在导出 SQL 证明交付成功。

证据：[198512](../../../sql-static-lineage-data/task-projections/tasks/198512/versions/340d561e68805a65d377845044de0dd81901a14c9a75fa4f1ba004b00fb4f940.evidence-v3.json)，query 全文 13 行，以及同任务投影的外部读与最终写观察。

## 这条路线适合怎样复用

它提供了三个不同深度的知识片段：账簿映射改变业务视角，值得深讲；行情与业务对象内连接改变范围，应讲清筛选与键；汇率改名与导出表示转换可以简讲。它们虽然同在一个 schema，承担的职责和所需解释深度不同。

后续最有价值的确认点是：映射规则的唯一性与匹配语义、同一交易多账簿视角的消费约定、参数化路径的分区条件，以及最终交付端采用了哪些字段和键。
