# 先理解这些数据在回答什么问题

这份知识库从当前加工证据出发，帮助你理解股衍／OTC 数据里的对象和结果。第一版的主线是：**先认清合约、客户、账簿等对象，再区分持仓、估值、现金与保证金，最后看这些事实怎样形成创收、规模考核和风险报表。**

发现候选时看的是当前 data-graph 全图，包含 PDATA、源端快照、风险、香港、经营指标等区域；深入解释以 OTC 相关问题为中心。它不是对全公司业务的完整建模，也不是按 schema 名称划分的一本数据库字典。全部文章使用固定发布批次中的静态 SQL、Machine Facts 和表元数据，具体范围见[覆盖与选题](coverage.md)。

## 先认清对象，后看金额

源端交易编号、统一合约编号、产品编号、客户码和账簿编号承担不同职责。把它们连在一起，才知道一笔金额属于哪个对象；同名字段并不保证是同一种编号。

| 需要认清的对象 | 在已核验加工中承担什么职责 | 最容易误解的地方 |
| --- | --- | --- |
| 当事人／客户 | 识别交易对手，补名称，连接业务客户及管理归属 | `Cutp_Pty_Id` 在不同输出中可能是外部客户码，也可能是 TIT 当事人编号 |
| 协议／产品合约 | 组织共同身份与期权、互换等产品属性 | 通用协议与产品表常是对源对象的并行表达，不能仅凭层次名称画成逐层生成链 |
| 子交易／腿／结构元素 | 保存合约内部对象、规模、条款或收益分项 | 父合约本金随多个子记录出现时不能直接相加；结构条款也不等于已计算的 Greeks |
| 账簿 | 补组织和柜台，控制纳入范围、标的映射 | 只参与少量字段或过滤，也可能改变整份结果的范围和归属 |
| 对象关系与有效期 | 把账户、账簿、合约等在具体来源和时间上下文中接起来 | 同一个 `Rela_Agt_Id` 不能脱离关系类型、来源和时间解释 |
| 证券／汇率／日历 | 统一产品身份、提供折算依据和日期集合 | 同一金额可能按不同业务日期取汇率；日历记录数不自动等于交易日数 |

这些是可反复使用的基础知识。账簿和协议关系适合先学，因为它们在现金、持仓、保证金和经营加工中反复出现。销售合约基本信息、合约内部结构、组合履保结果则承载更具体的业务组织。**公共资产和核心模型可以重叠，不能只靠出度分成两堆。**

## 同一合约会进入几条不同的事实路线

可以先用下面这张表建立认识。行与行之间可能共享编号和来源，但不是互相替代的金额。

| 你想知道什么 | 先看什么 | 本知识库已解释到哪里 |
| --- | --- | --- |
| 合约内部是什么，哪些条款影响后续判断 | 产品合约、子交易、腿、结构元素 | 父子键、实际终止日期选择、来源差异；尚未重建源系统定价模型 |
| 某天持有多少，估值与收益怎样表达 | 腿持仓、账簿持仓、估值和 Greeks | 行粒度、金额字段映射、动态／静态分配与风险报表整合 |
| 产生了什么收付义务，走到哪一步 | 事件、TRANSFER、结算通知、现金流报表 | 标准化、状态与时间筛选、异常监控；未接银行实际到账证据 |
| 哪些账户与合约一起承担履约风险 | 账户—组合、组合—合约关系和履保结果 | 组合粒度、模型余额与账户余额、合约／组合明细差异；未解释源风险模型算法 |
| 业务贡献怎样被组织成结果 | 销售日明细、归属、创收、标准资产 | 两条完整经营路线及其不同分母、公式、归属和折算规则 |

例如，“已实现收益”“结算金额”“保证金余额”“创收”都可能带金额单位，但分别回答收益确认、收付义务、担保资源和经营口径的问题。SQL 中名字相近不意味着数值可直接对账；需要先统一对象、日期、币种和规则。

## 两条经营路线要分开学

第一条回答：**合约规模怎样进入客户、机构、员工的考核？**

```text
销售合约基本信息 ──→ 按计提日期展开的日规模
管理关系与分配规则 ──────────┘
        ↓
交叉销售月日均（保留客户、机构、员工等维度）
        ↓ 去员工维度，按客户与机构等汇总
折算前月标准资产 → 月系数及机构等规则 → 折算后月标准资产
```

这条路线中的关键变化是“一份合约快照”变成“某个计提日的规模”，再变成“客户与机构等维度的期间日均”。条件筛选、比例分配、回退归属和自然日分母共同决定结果。它不是简单把本金一路相加。

年度 OTC 标准资产还有一个必须记住的分叉：已查 SQL 另从日明细计算年内日均，再应用固定系数；它没有沿用一般资产的月结果加权路径。因而不能默认“年度＝月度的平均”，也不能默认年度固定系数与月配置相同。完整推导见[规模到交叉销售](04-contract-to-cross-sale.md)和[标准资产](13-standard-assets.md)。

第二条回答：**估值及收益怎样进入经营创收？**

```text
销售日明细 + 账簿持仓／标的盈亏 + 模拟盈亏、Delta、汇率
        ↓ 按产品与对冲方式选择公式
TITANS 创收日报 ─┐
金仕达收益／成本差分 → 同一日报模型的另一来源分支
                 ↓
年度经营汇总：在已查输出中累加 Curr_Rev，另接奖励等来源
```

动态分配、静态分配、金仕达成本分支不能互换。日报里单独保存的期初 NPV 创收也没有被已查年度汇总自动计入 `Curr_Rev`。更直接的提醒是：一个名为“规模变动”的输出，已查实现其实取当天动态本金合计，并没有计算前后差分。学习时应从表达式回到名称，而不是由名称猜公式。详见[创收与经营结果](12-revenue-and-business-results.md)。

## 风险与香港加工提供另外两种观察角度

风险盈亏报表把合约、腿、持仓、估值与公共属性汇到一起。它还改变时间组织：临时表承接运行日的查询结果，正式表改按源业务日写近期分区，部分任务继续复制到备份。到期后延续分支会冻结部分取值日期、将当日损益及规模等置零，并对跨终止年度的本年指标另作处理。它的重点是报告整合与时间表达，不能视为每日重新定价。[风险盈亏报表](16-risk-pnl-report.md)

香港路线则说明，同一交易可以按本方或映射后账簿形成不同展示视角；多个输出行不必代表新增交易。观察价格也可能按观察日取值后保存到运行日快照。另有任务只是导出或格式处理，图上被列成写者，并不能证明又计算了一次交易。[香港投影](15-hong-kong-projections.md)

## 读加工时，反复问五个具体问题

1. **一行代表什么？**是合约、腿、日期、账户、组合，还是客户与机构的期间结果？表名和 DDL 注释只提供线索，实际键与唯一性仍需核验。
2. **谁提供值，谁控制选择？**价格、收益、Delta 参与数值；账簿开关、关系类型、付款方式也可能决定是否纳入、如何选日期。少字段不等于小影响。
3. **这一步新增了什么决定？**日期展开、纳入筛选、归属回退、分摊分母和折算系数，通常比重复搬运更值得深讲。
4. **相似分支差在哪里？**统一输出并不抹平产品来源、空值填充、币种前提和公式差异。
5. **已确认到哪一层？**静态 SQL 可以证明这里写了什么；不能单独证明源模型正确、运行成功、关联唯一或实际到账。

这些问题已经决定了本版文章的边界。同一张宽表可进入规模、创收、客户归属等不同片段；同一个片段也需要跨表追踪。我们把能够连贯解释的问题组织成学习单元，没有强迫整个图拆成互斥的表簇。
