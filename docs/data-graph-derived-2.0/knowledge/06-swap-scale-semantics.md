# 互换规模：动态本金与年、月新增口径

任务 `204172` 从 `pdata_n.t98_sb_otc_swap_comp_info`（核心互换合约日快照）生成 `dm_fii_n.adm_trd_bond_swap_scal_sum_day_titans`。本篇解释这一任务的实际计算，不把结论推广到所有互换规模指标。

最关键的认识是：三个金额都读取同一天的合约快照，但当日规模取动态名义本金，年／月新增取初始名义本金并增加起始定价日窗口。它们不是把每天的同一种规模分别累加成年、月值；也不是收益金额。

## 从快照到一行业务类型指标

三个分支共同筛选当日 `Busi_Date`，只保留账簿 `10218`、`10231`，状态 `101`、`226`，并排除 `FEE_SWAP`。这里能确认代码集合，不能在未查定义时把它们翻译成“存续”“生效”等状态名称。

随后按交易对手简称分类：精确等于“广发全球资本FICC”时归到“北向收益互换-利率债”，其他情况走“境内收益互换-利率债”。这是一条具体实现规则，不能据此认为所有业务系统都用同一名称判断北向身份。

每条入选快照记录先计算人民币方向的本金换算值，再按 `busi_type` 汇总。输出一行对应该次业务日期下的一种业务类型，包含三个金额、业务日期及生成时间；不再保留合约或账簿粒度。源快照是否严格一合约一行，本篇没有数据唯一性证据。

## 三个金额究竟差在哪里

| 输出字段           | 本金来源                                                  | 额外日期范围                                          | 当前 SQL 所表达的口径                                      |
| ------------------ | --------------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------- |
| `Nom_Prin`         | `Ori_Crrd_Dyna_Nom_Prin`，原币动态名义本金                | 无起始定价日窗口                                      | 当日符合共同条件的记录，其动态本金换算后合计               |
| `Nom_Prin_YearAdd` | `Ori_Crrd_Nom_Prin`，原币名义本金，本任务作为初始本金使用 | `Strt_Pric_Date` 在当年 1 月 1 日到业务日之间，含边界 | 当日符合共同条件且当年起始定价的记录，其初始本金换算后合计 |
| `Nom_Prin_MthAdd`  | 同上                                                      | `Strt_Pric_Date` 在当月 1 日到业务日之间，含边界      | 当日符合共同条件且当月起始定价的记录，其初始本金换算后合计 |

因此，历史上曾经满足条件、但今天状态不再属于 `101/226` 的合约，不会因为“年内新增过”就被保留。它可能从今日的年新增结果中退出。该指标能否称为完整年内发行／成交累计，需要业务口径确认；SQL 本身计算的是当日快照上满足条件的子集。

依据：`root.casttable.d.t.filter`、`root.casttable.y.t.filter`、`root.casttable.m.t.filter` 三个 relation；本金表达式见下方证据定位。

## 换算有先后顺序，空值不会自动寻找下一种汇率

三条分支共用换算因子：

```sql
CASE WHEN Crrc_Cd = 'CNY' THEN 1
     WHEN Lcrrc_Crrc_Cd = 'CNY' THEN Lcrrc_Ori_Bgng_Rate
     WHEN Sett_Crrc_Cd = 'CNY' THEN Sett_Bgng_Rate
END
```

原币为人民币优先乘 1；否则先检查本币是否为人民币，再检查结算币种。没有 ELSE，均不命中时因子为空。如果本币分支已经命中但该汇率为空，即使结算汇率存在，也不会继续回退到结算分支。

本金乘空因子得到空值。SUM 忽略空值；组内全为空时汇总为空，最终 `NVL(...,0)` 再显示为 0。故结果为 0 可能是缺失被替换，不能直接解释为没有业务。

## 一个小例子

以下是示意数据，不是真实记录。假设业务日为 2026-09-09，四条记录均属于同一业务类型、同一入选账簿，每条代表一条独立快照记录，原币均为人民币。

| 记录 | 起始定价日 | 状态 | 初始本金 | 动态本金 |
| ---- | ---------- | ---- | -------: | -------: |
| A    | 2025-12-01 | 101  |      100 |       60 |
| B    | 2026-02-01 | 101  |      200 |      120 |
| C    | 2026-09-02 | 226  |      300 |      240 |
| D    | 2026-09-03 | 218  |      400 |      350 |

共同过滤排除 D，剩余 A/B/C：当日动态规模为 `60+120+240=420`；年新增为 `200+300=500`；月新增为 `300`。年新增大于当日动态规模并不自动说明出错，因为它们使用不同的本金字段。

若把年新增的来源改成动态本金，年新增会变成 `120+240=360`。若把 218 加进状态集合，则 D 同时进入三个分支，分别增加 350、400、400。后续 SUM 不会消除这些差异，因为改变的是被纳入的金额。

## 这里的 JOIN 为什么不等同于明细扩行

`d`、`y`、`m` 三个分支先各自 `GROUP BY busi_type`，之后才以业务类型做两次 LEFT JOIN。每个分支在 SQL 结果中每种业务类型至多一行，因此这两个汇总结果之间的等值连接不会因右侧同业务类型多条明细而扩行。这一点可从当前加工结构确定，无需先证明源表主键。

但源快照若有重复记录，重复本金已经进入 SUM；聚合后的连接不扩行，并不意味着源金额没有重复累计。

此外，年／月分支的记录范围是 d 分支的子集，分类表达式也相同。按当前 SQL，年／月存在的业务类型也会存在于 d；d 驱动的 LEFT JOIN 不会单独丢掉一个只在年／月出现的类型。若未来各分支筛选或分类发生变化，需要重新判断这一性质。某类型在三个分支都无记录时，任务不会主动生成该类型的全零行。

依据：三个 `.aggregate` relation 的 `group_by_exprs=['busi_type']`，以及 `root.casttable.join.1`、`root.casttable.join.2`。这比泛泛说“JOIN 可能扩行”更贴近本任务。
