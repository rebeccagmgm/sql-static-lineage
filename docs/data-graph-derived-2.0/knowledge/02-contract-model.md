# 核心合约模型：同一张表为何保留四种规模

`pdata_n.t98_otc_deri_comp_sale_info` 在新版有 34 个来源表对、44 个去向表对，是同时汇聚和复用的候选。核读四个具体写者后，可以把它理解为供规模、归属等加工使用的合约综合基础；不能因为表名含“销售收入”就把每行当成已确认收入。

本篇围绕编号与规模，重新核读新版 SQL。每个写者的 Facts 都有 90 个输出绑定；这证明了本次输出绑定数量，不能证明每日每合约唯一，也不能把全表所有字段都记为已解释。

## 输出结构相同，来源分支不同

| 写者            | 本表分支分区 | 产品类型 | 编号、初始规模与动态规模                                           |
| --------------- | ------------ | -------- | ------------------------------------------------------------------ |
| 86840 期权      | `01`         | OPTION   | 合约号取交易内部号；初始本金、当前本金来自产品条款，按币种条件折算 |
| 86841 普通 TRS  | `02`         | TRS      | 合约号取交易内部号；初始/当日规模先按腿组织，再接合约              |
| 86842 金仕达    | `03`         | TRS      | 合约号取确认编号；初始规模含多空互换条件，动态规模取来源值         |
| 220650 极速互换 | `04`         | TRS      | 合约号取交易内部号；历史与当日持仓按工具汇总                       |

四条 SQL 都覆盖写入业务日与对应分支分区。本表的 `grp_id` 表示来源分支，和 `grp_def` 的组合 ID 不是相同含义。只筛 `Busi_Type='TRS'` 仍会混入三种不同处理。

TITANS 三条分支的 `Agt_Id` 为 `internal_trade_id`，`Inr_Seri_No` 为 `key_otc_trade_id`，`Otc_Seri_No` 为 `key_instrument_id`。金仕达则分别是 `key_trade_comfirm_id`、`contract_code`、NULL。编号看起来相似也不能跨分支直接当成同一个键。

## 哪一步改变了一行的含义

期权的本金主要是条款值乘折算因子。名义本金币种为 CNY 时因子为 1；否则如果结算币种为 CNY，取初始名义本金汇率；其他情况取所连接的中间价。动态本金还要求参数日处于起始日与提前终止日/到期日的闭区间内，区间外本金取零。若折算因子缺失，不能把表达式整体一概说成零。

普通 TRS 初始持仓先按 `(key_leg_id, underlying_ins_id)` 按源业务日期升序取第一行，再按腿汇总 `Init_Price × Init_Quantity`。当日持仓按腿汇总 `Init_Price × Quantity`，只取源业务日期为计算日的记录。这说明“初始”来自历史择一，“当日”来自当前数量；它们不是统一把两列从源表搬下来。初始分支在 SUM 前还补证券属性，若关联不唯一可能改变汇总，SQL 未证明唯一性。并列最早日期也没有额外排序键。

极速互换初始记录的择一单位为 `(key_instrument_id, wind_code)`，之后按工具汇总 `dynamic_notional`；当日记录限定 `EOD_POSITION` 和当日源业务日期，也按工具汇总。这个中间单位与普通 TRS 的“腿”不同，不能用同一个结构模板抹掉。该分支把本表汇率写成 1；金仕达汇率写 NULL，不能据此断言不同源金额原本使用相同币种。

金仕达初始规模在 `trs_type='B_LONG_SHORT_SWAP'` 时使用动态本金，否则使用来源本金；动态规模始终取 `dynamic_notional`。这是同一个目标列内的条件差异，和普通 TRS 的最早持仓算法不同。

## 哪些变化可能保留，哪些可能被汇总消除

假设普通 TRS 同一腿两条已纳入持仓的初始价格都为 10，当前数量分别为 3、7，合计规模为 100。如果两条数量改成 4、6，且来源范围、价格、关联倍数和币种因子全部不变，腿级动态规模仍为 100。记录级变化被这次求和消除了。

若两条价格不同、调整跨腿、改变最早持仓选择，或改变某条记录是否纳入，上述抵消就不成立。即使金额相同，拼接的标的列表、分类属性仍可能改变；“汇总金额不变”不等于整行输出不变。这里是有前提的表达式推导，不是已观测到的数据结果。

下游 107491 再按计提日恢复每日规模，159763 又只选 `01/02/03` 的合约输入。因此 `04` 在基础模型存在，不能直接推导它已经进入这条交叉销售指标。详见 [日期、分配和日均](03-daily-scale-and-attribution.md)。
