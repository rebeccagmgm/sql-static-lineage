# 账簿附加信息表消费方式核验

> 面向业务学习的连贯说明见 [账簿表业务使用说明.md](账簿表业务使用说明.md)。它按“表提供什么—消费者怎样使用—哪些差异必须保留—遇到问题如何定位”组织，并保留对应 Facts 证据 ID。

## 结论

本轮把 `pdata_n.t03_otc_deri_book_adtnl_info` 的高出度消费拆成了 **13 个可理解、可重叠的使用模式**，但结论边界是：**消费者结构已列全，Facts 细粒度提取与业务解释覆盖 20/170 个不同 SQL 材料组（21/171 个任务，含 1 个完全相同材料复用），不能把样本模式推广为剩余 150 个未核读任务的已确认结论。**

固定缓存中共有 171 个直接读任务，覆盖 159 张不同候选下游表和 177 个具体写入观察。这里的“候选下游/写入”是任务级 read×write 覆盖，不等于目标表必然影响该任务的每个输出。Facts 的 `bindings → expressions` 可直接确认值字段到目标字段和 write observation；控制条件与任务写入同时存在仍需结合 relation 路径解释，不能只因输出出现在 bindings/write targets 就宣称控制路径已经绑定。

本版已改为 **Facts-first**：程序直接消费读取位置、scope、JOIN 类型、双方物理字段、过滤、表达式、分组/聚合、输出字段和 write observation；模型只负责给局部证据命名业务作用、解释条件差异。CASE/IF/NVL 等尚未统一为完整 AST 的细节，按需读取 Facts 内的 `expression_text`，不再默认通读整段原 SQL。

账簿表在已核读范围内并非单纯“补部门”。它至少承担五类价值：

- **属性补充**：补 `Bel_Dept`、`Bel_Co`、`Cntr`、开关、有效期和映射代码；例如 200078/200030 直接补部门，215700 还用原风险部门回退。
- **身份/代码映射**：把原账簿映射到目标账簿，或用 `Map_Undrl_Cd` 映射底层标的；209119、107018、230202 的规则不同，不能合并成一个笼统说明。
- **范围控制**：通过 INNER JOIN、部门/公司/报送标志、日期、状态和白名单决定哪些交易或合约能进入输出；114782、184662、143830、171179、221300、234175、243650、138186 属于这一类或同时承担其他作用。
- **计算或条件取值**：账簿属性进入 `CASE`、`NVL`、标签分类或映射/分组表达式；176610、215700、230202、241773、209119 有明确证据。
- **粒度变化**：230202 先按动态对冲账簿筛选并映射底层，再按“映射标的×业务日期”汇总收益；这是本轮唯一确认到的明确粒度变化模式。

因此，这张表更接近“账簿主数据快照 + 业务资格控制 + 映射配置”的组合，而不是普通维表。即使某条路径看起来只补属性，缺少账簿键唯一性和 JOIN 前后行数证据时，也不能承诺不影响行数。

## 可以共用的解释

1. **完全相同材料**：任务 200030 与 200078 的目标表相关 SQL 哈希完全相同，可共用“当日账簿快照按账簿 ID 左连接、直接补 `Bel_Dept`”的局部说明。它们写入不同 schema，因此只能复用局部规则，不能称最终输出等价。
2. **已核对的局部规则一致**：114782 与 184662 的互换净值/期权净值分支均以账簿 ID+修饰符 INNER JOIN 当日 OTC 账簿作为资格闸门；后续汇总层级和输出数量不同。
3. **同类范围控制**：209894、221300 都以当日 `GFS_FICC` 账簿限定分支范围；143830 与 171179 都用报送标志控制资格，但 `Rep_Risk_Flag` 与 `Rep_Fin_Flag` 不能互换。
4. **同类维表投影**：134167、145871、243918 都把目标表作为账簿属性来源，但分别限定香港、全量派生、固收范围，并存在开关值转换、补充维表和代码解释差异。

## 必须保留的特殊规则

- **215700**：`NVL(账簿部门, 原风险部门)` 的回退会改变缺匹配时的输出，不能与 200078/200030 归一化。
- **138186**：范围条件是 `Bel_Dept='ED'` 与特定合约/标的白名单的 OR 组合；白名单分支必须原样保留。
- **209119**：五次物理读取分担“映射目标存在性、原账簿映射标的、目标账簿部门/柜台/名称”等不同角色；首个映射分支没有另外两支的 `src_tbl` 限制，不能合并别名或抹平条件。
- **230202**：只取动态对冲账簿，`Map_Undrl_Cd` 为空时回退证券分类，再按映射标的×日期汇总收益；收益数值来自持仓表，账簿表提供范围控制及映射/分组依据，不能说账簿字段提供收益值。
- **243650**：只有一个 UNION 分支消费目标表，且 OTC 部门条件还叠加状态、日期和非内部互换条件；不能把整张输出都归因于账簿表。
- **241773、234256**：同一任务中不同别名的连接类型、字段和业务角色不同，必须分开解释。

## 本轮新增认识

已有 200078、230202 两例只覆盖“补部门”和“动态对冲映射/收益”。本轮新增确认了：

- 账簿表被多类任务当成 **INNER JOIN 资格闸门**，不输出任何账簿字段也可能直接改变结果范围。
- `Rep_Fin_Flag`、`Rep_Risk_Flag`、`Bel_Dept`、`Bel_Co`、`Cntr` 和多种 enable flag 是不同控制面，不能统一成“账簿属性”。
- 多别名、多分支任务中，同一物理表会同时承担原账簿、目标账簿、有效期账簿和分类账簿角色。
- 维表投影存在“原值透传、0/1 转 Y/N、代码转中文、补名称/持有人”等不同输出契约。
- SQL 文本命中不等于物理读取：171179 的若干命中只是 `T98_OTC_DERI_BOOK_INFO` 常量，Facts 对应的目标物理读取只有两个。

## 字段统计口径

`field-usage.csv` 只统计上述 21 个已覆盖任务，并改为每行一个“源字段×JOIN直接对侧×同一表达式/分组其他来源×Facts 结构用途”：

- “不同消费任务数”按任务 ID 去重；
- “不同 SQL 材料组数”按本次目标表相关材料组去重；
- JOIN、过滤、输出取值、条件/回退、计算、分组、聚合等用途分别统计去重任务数和材料组数，不再只保存用途集合；
- JOIN 对侧按 `condition_tree` 的单个比较 ATOM 配对；AND/OR 中其他条件单列为附加条件。复杂表达式的其他物理来源不冒充一对一 JOIN 键；
- 同一任务多别名的实际角色保留在 `evidence.json`，汇总表不把重复出现冒充独立消费者；
- `select *` 展开的字段单列为“源侧通配投影（未证明下游使用）”，不冒充已进入最终输出；
- 未核读项不能解释为字段未使用。

已确认的高频关联主线是 `Book_Agt_Id` 对交易、持仓、映射结果或名称表中的账簿 ID，并常与 `Busi_Date`、`Src_Tbl` 一起限制快照。它们是常用连接/过滤字段，不是本轮证明的主键。对方字段组合、用途分布和精确分母见 `field-usage.csv`。

## 需要人工判断

本轮留下 38 个去重问题，完整清单在 `evidence.json.manualQuestions`。最关键的是：

- 账簿 ID（有时还含修饰符、来源、业务日期）在实际快照中是否唯一，JOIN 前后是否扩行；
- 映射规则分支是否互斥、优先级是否正确、目标账簿是否唯一；
- 209119 首个映射分支缺少 `src_tbl` 限制是否有意；
- 138186 硬编码白名单的维护责任、有效期和实际命中占比；
- `Map_Undrl_Cd` 空值回退的命中率、冲突口径及聚合前后收益是否守恒；
- 多输出任务中各分支的实际贡献量，以及未匹配账簿导致的排除量；
- 测试 schema 逻辑是否与对应生产版本一致。

这些问题需要数据分布、业务规则或运行结果，不能由静态 SQL/Facts 代替。

## 哪些步骤值得批量复用

可批量复用：从固定缓存列全消费者、映射候选写入、检查证据文件可用性、按目标引用 SQL 哈希去重，以及从 Facts 直接生成读取 scope、JOIN/过滤、字段对、表达式、聚合、输出 binding、写入 observation 和分项统计。

仍需人工判断：复杂多输出中的真实控制路径、别名的业务角色、INNER/LEFT JOIN 的业务含义、例外常量和回退逻辑是否可归组、字段唯一性和实际倍增、业务分类是否准确。也就是说，**Facts 程序消费可以替代大部分机械 SQL 阅读，但不能替代业务解释与数据验收。**

## 已知问题修正状态

- **模式串用：本批已修正。** 209119 的“账簿重映射/原目标账簿输出”和 243918 的“GFS_FICC范围/维表投影”使用显式 Facts scope/用途切片；这只证明本批四个切片互不串用，不代表已经形成通用的自动别名/输出路径切片能力。
- **用途只有集合：已修正。** `field-usage.csv` 按用途拆行，分别给出去重任务数、材料组数和细粒度 Facts 证据 ID。
- **跨版本表述过强：已修正。** `readOccurrenceId` 只记为固定读取定位仍存在；内容哈希匹配仅声明于有直接证据的 200078、230202。
- **JOIN配对与完整条件：已修正。** 直接对侧字段来自单个 `condition_tree` ATOM；`condition_expr`/完整 `source_text` 和条件树作为正式证据，可能截断的 `condition_display` 只保留为预览。
