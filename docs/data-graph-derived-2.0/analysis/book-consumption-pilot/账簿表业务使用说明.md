# 账簿附加信息表：它怎样进入业务加工

## 先说结论：这不是一张只用来补部门的普通维表

`pdata_n.t03_otc_deri_book_adtnl_info`（账簿附加信息表）在已核对的消费中，同时承担四种职责：说明“这是哪个账簿”、补充“账簿属于哪里”、决定“这条业务是否有资格进入结果”，以及通过 `Map_Undrl_Cd` 提供“账簿应映射到哪个标的”的配置。不同任务可以同时使用其中几种职责。目标账簿重映射则要分开理解：映射目标由外部关系规则给出，本表用于验证目标账簿存在并补充原账簿或目标账簿属性。

这一区分直接影响问题定位：LEFT JOIN 后取 `Bel_Dept`，主要改变字段值；INNER JOIN 或 `WHERE` 中的部门、公司、报送标志，直接改变结果范围；`Map_Undrl_Cd` 或原/目标账簿映射会改变业务身份和分组口径；如果账簿侧连接键不唯一，以上三类用法都可能进一步影响匹配基数。静态证据能确认规则写在哪里，却不能证明实际数据唯一、没有扩行或业务结果正确。

本说明的消费者结构范围是完整的：固定缓存中有 **171 个直接读任务、159 张不同候选下游表、177 个写入观察**。业务解释只覆盖达到核读上限的 **20/170 个 SQL 材料组，对应 21/171 个任务**；其中任务 200030 复用任务 200078 的完全相同目标引用材料。文中的用法来自这 21 个任务，13 个主题模式是整理这些已核证据的观察角度，**不是其余 150 个任务的完整规则目录**。

## 先把表看成一份“账簿配置快照”

现有元数据把这张表描述为每天一份快照，保存账簿的生效到期日、所属机构、交易与风控开关、底层标的映射等附加配置。业务上可以把字段分成四组来理解：

| 它回答的问题                   | 主要字段（中文含义）                                                                  | 在消费中的典型作用                                                    |
| ------------------------------ | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 这是哪个账簿                   | `Book_Agt_Id`（账簿协议编号）、`Book_Agt_Modifr`（账簿协议修饰符）                    | 与交易、持仓、账簿关系或名称记录对齐                                  |
| 取哪一版配置                   | `Busi_Date`（业务日期）、`Src_Tbl`（源表）、`Eff_Date` / `Exp_Date`（生效/到期日期）  | 选择当日、指定来源或仍有效的账簿记录                                  |
| 账簿属于哪里                   | `Bel_Dept`（所属部门）、`Bel_Co`（所属公司）、`Cntr`（柜台）                          | 补属性、筛业务范围、生成标签或系统分类                                |
| 账簿允许做什么、映射到哪个标的 | `Rep_Fin_Flag`、`Rep_Risk_Flag`、多种 `Enable_*_Flag`、`Map_Undrl_Cd`（映射标的代码） | 财务/风控报送资格、业务开关、标的映射；目标账簿映射需结合外部关系规则 |

“每天一份快照”只说明表的时间组织方式。现有证据没有证明一行的业务唯一粒度，也没有证明 `Book_Agt_Id` 单列或“编号 + 修饰符 + 来源 + 日期”就是主键。下文凡涉及“不会扩行”“只匹配一条”之处，都必须以数据侧唯一性或 JOIN 前后计数另行验证。

## 用法一：补属性时，直接取值和回退取值不是同一条规则

最容易理解的用法是把风险结果中的账簿身份接到账簿快照，再补出所属部门。任务 200078 先把目标表限定为当日 `D_REF_BOOK` 来源，然后以 LEFT JOIN 将账簿编号接到风险结果，最终把 `Bel_Dept` 写入 `dm_rsk_n.adm_v_risk_daily_bundle_margin.department`。在已追踪路径中，部门没有继续用于过滤、计算或分组；未匹配到账簿时，输出部门为空。

> 证据：任务 200078 的关联为 `TOT.KEY_BOOK_ID = RB.KEY_BOOK_ID`，过滤为 `SRC_TBL='ODATA_N_TIT.D_REF_BOOK' and BUSI_DATE='${yyyy-MM-dd}'`。参见 [evidence.json](evidence.json) 中 `E-200078`、`FU-200078-6fdea7e7f9ce`、`FU-200078-43bd0a5145bc`、`FU-200078-ca7fb2a3d164`、`FU-200078-e63642dbe584`，以及输出绑定 `output-binding:200078:task:200078:slot:query:statement:0:51`。任务 200030 的目标引用 SQL 与它完全相同，可复用这段局部解释，但写入 schema 不同。

任务 215700 看起来也在补部门，但输出语义不同：它写的是 `NVL(RB.DEPARTMENT, DR.DEPARTMENT)`。账簿匹配且部门非空时使用账簿部门；否则保留原风险结果的部门。因此，200078 的“缺匹配写空”和 215700 的“缺匹配回退原值”必须分别说明，不能归一成“补部门”。

> 证据：参见 [evidence.json](evidence.json) 中 `E-215700`、回退表达式 `FU-215700-5e85afe8c639`、账簿关联 `FU-215700-d29ffe44e106`、最终输出 `FU-215700-a9c1d9951d72`，以及输出绑定 `output-binding:215700:task:215700:slot:query:statement:0:51`。

两条规则都是 LEFT JOIN，但 LEFT JOIN 只保证左侧记录不会因为“没有匹配”而被连接本身删除，并不保证行数不增加。如果同一账簿键在被选中的快照里有多条匹配，仍可能产生多行。200078 外层存在 `DISTINCT`，也只有在扩出的行对所有投影列完全相同时才可能去重；它不能证明多匹配没有发生，更不能消除同一账簿对应不同部门时的差异。

## 用法二：账簿也被当作资格闸门，虽然它未必向结果补列

账簿表的第二类价值不是“给结果增加什么”，而是“决定什么能留下”。这类路径通常把账簿作为 INNER JOIN 一侧，或在账簿子查询中增加部门、公司、报送标志等条件。即使最终没有输出任何账簿字段，账簿条件仍会改变进入后续加工的数据集合。

任务 114782 和 184662 是可以共用局部说明的一组：互换净值、期权净值两个分支都按“账簿编号 + 修饰符”内连接各自指定业务日期的账簿，并要求 `Bel_Dept='OTC'`；114782 样本固定为 2026-05-18，184662 样本固定为 2026-05-20，不能把它们泛化为运行当日或同一日期实例。账簿表在这里不负责提供最终资产金额，而是把两个资产分支限定到 OTC 账簿，再由后续临时表按客户或账户汇总。两项任务的日期、临时表链和最终写入集合不同，所以可复用“OTC 账簿资格闸门”这一局部规则，不能声称整条 SQL 或最终输出等价。

> 代表证据：`E-114782`，条件 `FU-114782-946872e54008`，编号与修饰符关联 `FU-114782-24e6b79bcfa0`、`FU-114782-fb6b72042c8a`；对应的另一任务为 `E-184662`，条件 `FU-184662-8a9cd2c86804`、关联 `FU-184662-df7630fe1c84`、`FU-184662-f7f9c3b9ae13`。

同样是资格控制，字段含义不能互换：

- `Rep_Risk_Flag='1'` 在任务 143830 中限定进入风险合约与保证金账户映射的账簿；另一 UNION 分支写固定部门且不消费目标表。证据为 `E-143830`、`FU-143830-53dd5eb089ff`。
- `Rep_Fin_Flag='1'` 在任务 171179 的两个互换分支中限定财务报送范围，并同时输出 `Bel_Dept`。证据为 `E-171179`、`FU-171179-21e67b13a2c7`、`FU-171179-7ea0cf51bd53`、`FU-171179-ff57165a1386`。
- `Bel_Dept='GFS_FICC'` 在任务 221300 中限定固收账簿，账簿属性不进入最终输出。证据为 `E-221300`、`FU-221300-6cc96b3dc399`、`FU-221300-5d5b1a9549e6`。
- `Bel_Co='GFS_HK'` 在任务 234175 中限定香港公司账簿；当前写入是测试 schema，不能自动推广为生产同名逻辑。证据为 `E-234175`、`FU-234175-18b16a077b6a`。

任务 138186 必须单独保留。它不是简单要求 `Bel_Dept='ED'`，而是“ED 部门 **或** 特定合约/标的白名单”的 OR 条件。白名单分支可以绕过部门条件，因此会直接改变权益 TRS 标的输出范围；把它概括为“筛 ED 账簿”会漏掉例外。

> 证据：参见 `E-138186`、账簿关联 `FU-138186-25f0f0a6969b`、完整 OR 条件 `FU-138186-04cb528272c7`。白名单的维护责任、失效日期和实际命中占比仍需人工确认。

## 用法三：209119 中同一张表的五次读取代表三个不同角色

任务 209119 说明了为什么不能把同一物理表的多个别名合并解释。目标表在一条任务中被物理读取五次，至少承担三类角色：

1. **验证映射后的目标账簿存在。** 三条账簿重映射分支把 `KEY_BOOK_ID_TO` 与目标表的 `Book_Agt_Id` 做 INNER JOIN。三条分支的映射来源不同，不能合并成一条简单等值映射。
2. **读取原账簿的标的映射。** `rb_ori` 按原账簿编号 LEFT JOIN，提供 `Map_Undrl_Cd`；为空时回退到证券基础信息的 `summary_mapping`。
3. **读取目标账簿属性。** 另一个账簿别名连接映射后的目标账簿，提供 `Bel_Dept`、`Cntr`，并与账簿名称共同形成目标账簿说明。

这里的目标账簿编号不是本表计算出来的：现有 Facts 显示 `KEY_BOOK_ID_TO` 来自 `t03_otc_deri_agt_rela_adtnl_info.rela_book_agt_id` 所代表的外部关系规则；账簿附加信息表负责验证该目标账簿存在，并为原账簿或目标账簿补充属性。

这些角色共同影响最终的期权子交易明细：`Bel_Dept` 写入 `department`，`Cntr` 写入 `desk`，`Map_Undrl_Cd` 与证券分类共同写入 `underlying_summary_mapping`。因此它既是身份映射、属性补充，也是范围控制和条件取值，不能用“补部门”覆盖。

> 证据：参见 [evidence.json](evidence.json) 中 `E-209119`。五次读取定位为 `FU-209119-3d82cc0d4584`、`FU-209119-02642e83a477`、`FU-209119-1b57c8341e91`、`FU-209119-93a2c34910fa`、`FU-209119-a39354560f38`；三条目标账簿存在性关联为 `FU-209119-090a0bec91e7`、`FU-209119-0b78e77f6f2d`、`FU-209119-0a3eb0372cbf`；原账簿回退为 `FU-209119-73a6569399c6`；三个最终输出为 `FU-209119-ef13fcbd90bf`、`FU-209119-19b9958d0697`、`FU-209119-36cb57cbb0ac`。

有一项条件差异不能抹平：第一条目标账簿存在性分支只限定 `Busi_Date`，后两条还限定 `Src_Tbl='ODATA_N_TIT.D_REF_BOOK'`。静态证据能确认条件不同，却不能回答这是有意的业务例外还是遗漏；需要规则负责人或数据分布核验。

## 用法四：230202 中账簿决定范围和分组，但收益数值来自持仓

任务 230202 先从账簿快照中只保留 `Cntr='DYNAMIC_HEDGING'` 的动态对冲账簿，再按 `Book_Agt_Id` INNER JOIN 账簿持仓汇总表。这里，账簿首先决定哪些持仓有资格进入计算。

进入计算后，任务使用 `NVL(IF(rb.Map_Undrl_Cd='', NULL, rb.Map_Undrl_Cd), ins.undrl_clas)` 生成映射标的：空字符串先转成 NULL，再回退到证券分类。结果随后按“映射标的 × 业务日期”分组汇总 `Tdy_Yield`，并按映射标的与业务日期接回创收明细。账簿字段因此决定了身份映射和汇总桶，但 `Tdy_Yield` 的数值来源是 `pdata_n.t98_otc_book_hold_sum`，不是账簿附加信息表。

> 证据：参见 [evidence.json](evidence.json) 中 `E-230202`。动态对冲条件为 `FU-230202-d6e6cd0b28b6`，持仓关联为 `FU-230202-00e2b6bbee73`，回退表达式为 `FU-230202-fe9631e8f9f5`，分组键为 `FU-230202-efa8a667f24d`，映射标的写入为 `FU-230202-a400ebd23134`。输出绑定 `output-binding:230202:task:230202:slot:query:statement:0:57` 明确 `tdy_yield` 来自持仓，`output-binding:230202:task:230202:slot:query:statement:0:60` 明确 `map_undrl_cd` 来自账簿字段与证券分类，`output-binding:230202:task:230202:slot:query:statement:0:61` 明确标的收益仍来自持仓。

这是已核范围中唯一明确确认的粒度变化：持仓记录进入按映射标的和日期汇总的结果。若账簿连接发生多匹配，后续 `SUM(Tdy_Yield)` 不会自动修复重复，反而可能把重复匹配带来的金额重复累计；只有真实数据、连接前后计数和金额守恒核验才能判断是否发生。

类似地，任务 241773 把 `Cntr`、`Bel_Dept`、`Bel_Co` 放进分类 CASE，生成跨境合约标签；期权分支是 LEFT JOIN，互换分支是 INNER JOIN。前者缺账簿仍可能保留并走其他 CASE，后者缺账簿会被排除。这说明“都用账簿做分类”仍不足以共用完整解释。证据为 `E-241773`、`FU-241773-abe5257af6f1`、`FU-241773-b1de45bfa88f`、`FU-241773-9c170c1fcf46`。

## 哪些差异会改变什么

| 差异                                          | 首先影响什么                         | 什么时候可能被后续处理弱化                                                         | 不能据此声称什么                                         |
| --------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 直接取 `Bel_Dept` 与 `NVL` 回退               | 未匹配或空值时的属性值               | 后续如果完全不使用该字段，业务影响可能有限                                         | 不能说两个输出字段口径相同                               |
| LEFT JOIN 与 INNER JOIN                       | 未匹配记录是否保留，进而改变结果范围 | 后续若本来就有等价过滤，影响可能重合；当前需逐路径证明                             | 不能仅凭 JOIN 类型判断业务规则正确                       |
| 部门、公司、报送标志、白名单条件              | 资格集合和输出覆盖范围               | 后续 UNION 只有对全列完全相同的行才可能去重                                        | 不能把一个分支的控制条件推广到整项输出                   |
| `Book_Agt_Id` 单键与“编号 + 修饰符”等复合连接 | 匹配基数和错配风险                   | `DISTINCT` 只可能消除投影后完全相同的重复行；GROUP BY 只折叠到组，不保证金额不重复 | 不能把常用键宣布为主键，也不能把潜在多匹配当成已发生倍增 |
| `Map_Undrl_Cd` 回退、原/目标账簿重映射        | 业务身份、分类和分组桶               | 只有不同分支最终生成完全相同结果时，UNION 去重才可能合并                           | 不能忽略空串转 NULL、常量、来源条件或分支优先级          |

任务 234256 还提供了一个小而重要的反例：同一任务中的一个别名只做当前账簿资格关联，另一个别名增加 `Eff_Date <= 当日 < Exp_Date` 后输出部门。即使物理表相同，生效区间条件也让两个别名承担不同角色。参见 `E-234256`、`FU-234256-548b114ff204`、`FU-234256-1942d31ed84a`、`FU-234256-99636fa117e3`。

## 证据边界：可以学到规则，不能把静态规则当运行事实

本说明绑定的固定图版本为 `44e87de15ca82eb40480569c1db59c87b3636f7194b50576137889162425224e`，固定缓存生成于 2026 年 9 月 8 日。旧固定 batch manifest 在核读时已不存在；固定 baseline 的 `readOccurrenceId` 在当前 Facts 中仍可定位，只能证明读取位置延续，不能证明跨版本 SQL 语义完全相同。只有任务 200078、230202 另有既有 SQL 哈希与 Facts manifest 哈希完全匹配的直接证据。

因此，这篇说明适合回答“已核样本中账簿表怎样参与加工、规则差在哪里、下一步应查什么”，不证明任务实际运行成功、数据已经到达、键唯一、JOIN 没有扩行或规则符合最终业务意图。需要人工判断的 38 个问题仍保存在 `evidence.json.manualQuestions`；其中最关键的是账簿快照唯一性、映射分支优先级、白名单维护、回退命中率、聚合前后金额守恒和多输出分支的实际贡献量。
