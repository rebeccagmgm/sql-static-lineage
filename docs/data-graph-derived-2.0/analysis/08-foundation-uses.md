# 公共基础表如何被下游真正使用

## 结论

本轮核验固定图版本 `44e87de...25224e` 下的 4 张公共基础/参数表、5 个具体消费任务，共形成 6 条可复用用途记录，其中代码转换由主执行者补核。缓存只负责给候选，最终分类均回到 manifest 固定的当前 SQL 与 Facts 确认。

这三张表不能统一理解为“补字段”。`grp_def` 在两个指标任务中承担身份映射，并通过内连接和状态/类型条件控制哪些结果能留下；证券基本信息表在 `159763` 中补入货币代码并参与标签计算；账簿附加信息表既可以在 `200078` 中只补所属部门，也可以在 `230202` 中同时控制范围、映射底层标的、改变汇总粒度并进入创收计算。

## 同一张基础表为什么会有不同用途

`grp_def` 的共同角色是把业务编码对到统一 `grp_id`，但消费粒度不同。`154068` 只映射员工一维；`159763` 同时映射交易对手、机构和员工三维。二者都使用最终内连接，因此它同时是结果范围闸门：缺映射会少行，重复映射会倍增或拆分结果。不能把它描述成“纯 JOIN、不影响指标”。

账簿附加信息表的差异更明显。`200078` 读取 `book_agt_id + bel_dept`，用左连接把部门带到风险结果；在账簿快照键唯一时，它只是属性补充。`230202` 则先用 `cntr='DYNAMIC_HEDGING'` 限定账簿，以 `book_agt_id` 内连接持仓，再用 `map_undrl_cd`（空值时回退证券分类）形成“映射标的×业务日期”汇总，汇总值随后参与创收公式。这一用法已经越过“补属性”，覆盖范围、身份、粒度和计算四类影响。

证券基本信息表在 `159763` 中通过 `in_code` 左连接，`crrc_cd` 决定标签 CASE 分支。若每个 `TIT/01/in_code` 唯一，基础表只改变标签桶；若重复，连接会在汇总前复制合约行并可能放大金额；若缺失，行仍保留，但空货币代码会落入其他标签分支。因此“只改标签、不影响金额”是一条有唯一键前提的结论。

## 影响结果的前提

本轮没有数据侧键基数和匹配率，因此以下条件仍决定真实影响：

- `grp_def` 的类型、值、状态组合是否唯一，三类身份映射覆盖率是否完整；
- 证券基础信息的 `(src_id, grp_id, in_code)` 是否唯一，空匹配是否符合标签规则；
- 账簿快照的 `(src_tbl, busi_date, book_agt_id)` 是否唯一，映射标的是否稳定；
- 左连接只能保证左侧行理论上保留，不能保证中间或最终行数不增加；外层 `DISTINCT` 也不能消除部门值不同造成的多行；
- 内连接会过滤未匹配行，重复匹配则可能在聚合前倍增数值。

## 证据与缺口

最终结构化底账在 [consumer-uses.json](../classification/consumer-uses.json)。初始5项研究快照保留为 [`foundation-uses.json`](./foundation-uses.json)。记录保留 `sourceDatasetId`、`taskId`、`writeObservationId`、中文字段注释、SQL 槽位哈希和行范围及具体 Facts 依据，便于后续分类持续复用。230202 另补 query 第95、143行，明确汇总收益进入创收公式及输出字段的位置。

代码转换任务61476的 query 第7–8行以标准代码填内部机构类型/状态，未命中时用原始代码；第26–43行按目标表/字段、源表/字段和源系统选映射域，再按源代码左连接。映射域不唯一可能放大行数，NVL也不保证空串回退。依据为 [固定SQL摘录](role-code-map-evidence.json)，其SQL实际哈希与发布证据一致。这是字段值转换，不是仅补名称。

当前缺口包括这4张表的实际唯一性、匹配覆盖率和 JOIN 前后行数；未证明任何任务的运行成功、数据到达或业务验收；代码值 `156` 的业务原因也未从本轮静态证据中得到确认。以上缺口不影响这6条限定范围内的SQL用途解释，但会影响对真实行数和金额影响程度的判断。其他消费者尚未核验，不属于本批结论。
