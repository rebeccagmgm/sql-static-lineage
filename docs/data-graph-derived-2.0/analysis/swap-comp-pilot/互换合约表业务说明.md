# 互换合约表：它怎样形成、怎样被使用

## 1. 先给业务判断

`pdata_n.t98_sb_otc_swap_comp_info` 可以先理解成“按业务日期保存的互换合约主数据快照”。但“快照”不等于已经证明一行就是一个合约，也不等于 `Swap_Comp_Agt_Id` 单列是主键。本轮静态证据只能确认：表按 `Busi_Date` 分区形成，合约协议编号、协议修饰符、产品编号、账簿、交易对手、状态、类型、币种、日期、名义本金和汇率等字段被多类下游共同读取。

证据入口：`evidence.json` 的 `target.degree`、`reviewedEvidence` 中 `E-163672`/`E-211623` 的写入绑定，以及各消费者的 `facts.readOccurrences`、`facts.relations`、`facts.expressions`。

## 2. 自身形成：主来源加关系补充

两个写入任务 `163672`、`211623` 都写入同一物理表，并由 Facts 识别出 `INSERT_OVERWRITE`、静态分区 `busi_date` 和目标字段绑定。两者 query 哈希相同，因此本轮最稳妥的解释是：当前看到的是同一装载逻辑的两个任务承载；没有证据证明它们分别对应不同来源、不同分区或不同业务路径。

写入 SQL 以 `pdata_n.t03_otc_swap_comp_info` 为主来源，并先按业务日期和来源表集合限制输入。随后通过多个关系表和维表补齐：

- 账簿关系/名称：由互换合约协议编号和修饰符关联账簿协议编号、修饰符和名称；这使 `Book_Agt_Id`、`Book_Agt_Modifr`、`Book_Name` 不是简单的原表同名透传。
- 对手方和销售方：通过主体名称表补全全称、简称及英文简称。
- 内部机构、协议静态信息、协议分类、产品关系：分别用于内部机构名称、内部合约编号、业务类型代码、产品源关系等字段。
- 字典/CASE：状态描述、互换类型描述以及 `Swap_Comp_Subdv_Cd` 由来源表映射为 `LONG_SHOR_SWAP_TRD_CFM`、`NORM_SWAP`、`FAST_SWAP`、`LONG_SHOR_SWAP` 或 `OTHER`。
- 日期处理：部分日期用 `SUBSTR(...,1,10)` 转成日粒度；`Task_Name`、数据加载/更新时间等是任务或分区运行上下文字段，不应与交易发生日期混为一谈。

因此，表形成不是“复制一张合约表”，而是一个主来源加多张关系/字典表补全的快照装载。具体来源条件、生效区间和关系类型会改变某一字段能否补出；Facts 仍不证明关联表在键上唯一。

## 3. 一行代表什么：候选粒度，而非已证主键

从目标字段和消费条件看，一行至少围绕以下身份展开：

1. 互换合约协议身份：`Swap_Comp_Agt_Id` + `Swap_Comp_Agt_Modifr`；
2. 业务日期：`Busi_Date`；
3. 产品/来源身份：`Comp_Prd_Id`、`Comp_Src_Prd_Id`，以及形成时的 `Src_Tbl` 映射到 `Swap_Comp_Subdv_Cd`；
4. 业务属性：`Swap_Type_Cd`、`Comp_Stat_Cd`、`Book_Agt_Id`、`Cutp_Pty_Id`、币种和名义本金等。

这是根据写入和消费结构得到的候选粒度。常用连接键不能直接升级为主键：例如 `218601` 用 `Comp_Src_Prd_Id` 连接持仓，用 `Swap_Comp_Agt_Id` 连接事件/合约腿；`171179` 又用 `Comp_Prd_Id + Book_Agt_Id` 连接持仓。不同任务已经显示，业务对象在不同路径上有不同对齐键。

## 4. 关键字段怎样被得到和怎样影响结果

### 合约身份、修饰符和产品编号

`Swap_Comp_Agt_Id`、`Swap_Comp_Agt_Modifr` 是最常见的合约身份字段；`Comp_Prd_Id` 与 `Comp_Src_Prd_Id` 则分别承担产品和源产品对齐角色。它们可能出现在等值 JOIN、输出、过滤或多分支回接中。若把修饰符、产品或业务日期漏出连接条件，可能从属性错配变成跨合约错配；但是否实际发生，需要数据唯一性和匹配数验证。

证据：`E-218601` 的 `facts.relations` 中 `ppd.Src_Prd_Id = trs.Comp_Src_Prd_Id`、`Swap_Comp_Agt_Id` 与事件/合约腿的连接；`E-171179` 中 `Comp_Prd_Id = Prd_Id` 及 `Comp_Prd_Id + Book_Agt_Id` 的持仓连接。

### 业务日期和合约状态

几乎所有已核读消费者都先按 `Busi_Date = '${yyyy-MM-dd}'` 读取快照，再根据任务目的筛状态。例如 `241773` 保留 `101/229/226/225/252`，并按 `Swap_Comp_Subdv_Cd` 区分常速、多空和极速分支；`171179` 排除 `230/218/255/254/253`，另排除内部业务和特定对手方；`176610` 以 `Comp_Stat_Cd != '218'` 并加起始定价日范围。

这些规则改变的是记录集合，不是单纯字段翻译。不同状态集合不能因为都叫“有效合约”就合并；同一任务的 UNION 分支也可能使用不同的细分代码或日期锚点。

### 账簿、交易对手和账户

`Book_Agt_Id` 在下游既是连接账簿资格的键，也是分类/标签输入；`Cutp_Pty_Id` 连接客户或主体信息；`Ast_Acct_Agt_Id` 连接资金账户余额或账户附加信息。`176610` 的不同事件分支用起始、平仓或事件日期分别连接持仓/余额；这说明相同字段名不代表同一时间语义。

INNER JOIN 会在缺匹配时排除合约，LEFT JOIN 通常保留左侧并允许补列为空，但都不能单凭连接类型证明“不扩行”：右侧键若不唯一，LEFT JOIN 也可能扩行，后续 SUM 还可能重复累计。

### 互换类型、细分代码和标签

`Swap_Type_Cd` 是分类输入，但不是所有消费者使用同一集合。`241773` 以 `CROSS_LEND_SWAP`、`HK_LONG_HOLD_SWAP`、`N_CROSS_FUTURE_SWAP` 等组合部门/公司/币种和日期生成标签；`171450` 只选 `S_CROSS_FUTURE_SWAP`，并按指定账簿号映射业务类型；`204172` 则把对手方简称映射为“北向收益互换-利率债/境内收益互换-利率债”。分支顺序和默认分支会改变分类结果，即便最终都输出一个 `busi_type` 或 `tag_id`。

### 币种和名义本金

`204172`、`171450` 等任务将原币名义本金与币种、汇率字段组合：若 `Crrc_Cd='CNY'` 乘 1，否则在本币或结算币种为 CNY 时选对应期初汇率，再用 `SUM` 得到日、月或年累计口径。这里的收益/名义本金数值来自合约表字段和汇率字段，账簿或持仓表可能只提供连接或范围。

如果币种条件都不满足、汇率为空、连接匹配多行，结果可能为空、偏小或重复放大；`NVL(...,0)` 只会把缺失汇总值显示为 0，不证明上游确实没有合约。`GROUP BY` 只把行折叠到指定分组，不能证明组内没有重复合约。

## 5. 下游使用模式

### 5.1 合约资格和范围筛选

`171179`、`176941` 都先取业务日期快照，排除特定状态、账簿、内部业务或对手方；`243650` 将状态、日期、非内部互换等条件叠加到一个 UNION 分支；`138186` 的结构中存在部门条件与合约/标的白名单的 OR 例外。它们都在“决定哪些合约进入结果”，但白名单、状态集合和分支范围不同。

### 5.2 身份和关系连接

`218601` 以 `Comp_Src_Prd_Id` 对齐持仓，以 `Swap_Comp_Agt_Id` 对齐合约腿、结算登记事件等；`171179` 以 `Comp_Prd_Id` 对齐收付款事件，并以 `Comp_Prd_Id + Book_Agt_Id` 对齐持仓；`176610` 还把 `Swap_Comp_Agt_Id` 与事件日/持仓业务日组合使用。必须按每一个比较条件保留对端字段，不能看到同名 `Swap_Comp_Agt_Id` 就把所有用途合为“合约主键连接”。

### 5.3 分类与规则分支

`241773` 将互换分支与期权分支 UNION 到标签维度，互换内部又按来源细分、状态、账簿和日期生成不同标签；`204172` 以对手方简称和账簿/类型生成业务类型；`171450` 以指定账簿号生成南向期货业务类型。这里的 CASE/IF 不是装饰字段，它们会改变下游分类和分组桶。

### 5.4 数值计算和汇总

`204172`、`171450` 对名义本金做币种换算和 `SUM`；`218601` 还把合约字段带入持仓/估值路径。只要连接之前的粒度或匹配数量变化，汇总值就可能变化。即使后面有 DISTINCT、UNION 或 GROUP BY，也只能在特定投影/分组条件下折叠结果，不能笼统说“消除重复”。

### 5.5 多分支、多输出

`171179`、`176941` 等任务对同一目标表有多个读取 scope，服务不同产品或业务分支；`241773` 明确有互换/期权 UNION。某个分支的过滤、连接或输出绑定不能推广到整个任务，更不能用任务级候选写入表明目标表影响所有下游输出列。

## 6. 规则差异如何改变结果

| 规则差异                                        | 直接影响                           | 后续操作可能弱化的条件                             | 不能据此声称                     |
| ----------------------------------------------- | ---------------------------------- | -------------------------------------------------- | -------------------------------- |
| INNER JOIN 与 LEFT JOIN                         | 缺匹配记录是否保留；也可能影响补列 | 后续已有等价过滤，且需逐路径证明                   | 没有扩行或一定符合业务资格       |
| `Swap_Comp_Agt_Id` 单字段 vs 加修饰符/产品/日期 | 匹配身份与匹配数量                 | 只有后续完全相同投影行才可能被 DISTINCT/UNION 去重 | 单字段就是主键                   |
| 状态集合和 `Swap_Comp_Subdv_Cd`                 | 合约记录范围                       | UNION 仅在完整输出行相同才可能去重                 | 各分支覆盖同一业务集合           |
| CASE/IF 分支顺序与默认分支                      | 类型、标签、业务分类               | 后续只按其他字段汇总时分类差异可能不再显式呈现     | 同名输出字段口径相同             |
| 币种回退和汇率选择                              | 名义本金换算和汇总金额             | `NVL` 可把缺失汇总显示为 0，但不恢复缺失事实       | 金额守恒或汇率一定存在           |
| UNION / DISTINCT / GROUP BY                     | 特定投影或分组下的行折叠           | 必须满足完全相同行或相同分组键                     | 它们自动消除多匹配造成的金额重复 |

## 7. 本轮已解释和未解释

已解释：表由什么类型的 SQL 形成；候选粒度为什么不能升级为主键；关键身份/日期/状态/类型/币种/名义本金字段在哪些结构中发挥作用；下游如何做筛选、连接、分类、计算和多分支输出；哪些差异会影响范围、属性、匹配数量和汇总。

未解释：真实数据中的键唯一性、实际 JOIN 扩行、状态覆盖量、白名单命中量、两个写者的运行关系、缺汇率处理、各 UNION 分支贡献和业务口径正确性。它们已登记在 `evidence.json.manualQuestions`，不能用静态证据代替。
