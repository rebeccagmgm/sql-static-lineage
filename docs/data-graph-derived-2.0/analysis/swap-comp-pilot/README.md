# 核心互换合约表消费核验

## 结论先行

这套“图定位 → Machine Facts 提取 → 使用模式与差异 → 业务说明”方法可以迁移到 `pdata_n.t98_sb_otc_swap_comp_info`，而且迁移后得到的认识比“核心合约主数据表”这句元数据标签更具体：

- 目标表由 2 个写入任务形成；两者当前 query 材料哈希相同，均为按 `Busi_Date` 分区的 `INSERT OVERWRITE` 形态。当前静态证据支持“同一形成逻辑被两个任务承载”，不支持宣称它们是不同来源、不同分区或不同业务路径。
- 形成逻辑以 `T03_OTC_SWAP_COMP_INFO` 为主来源，再通过账簿关系/名称、对手方名称、内部机构、协议分类、字典等补充字段；字段既有直接透传，也有日期截断、字典映射、CASE 分类和关联补充。
- 下游不是一种“统一使用”：合约范围筛选、身份/关系连接、业务分类、币种换算与名义本金汇总、多分支输出同时存在。`Busi_Date`、`Swap_Comp_Agt_Id`、`Comp_Prd_Id`、`Comp_Src_Prd_Id`、`Book_Agt_Id` 和状态/类型字段是常见控制面，但没有被本轮证明为主键。
- 已核读 12 个任务、11 个 SQL 材料组；全量结构账本覆盖 33 个直接消费任务、78 个读取观察、32 张候选下游表。剩余任务只做结构盘点或留在缺口中，不能把已核读样本推广成全量业务规则。

## 覆盖与证据边界

固定图版本为 `44e87de15ca82eb40480569c1db59c87b3636f7194b50576137889162425224e`，缓存生成于 `2026-09-08T07:54:52.983Z`。本轮程序复用了固定图缓存、元数据注释和当前任务 Facts；没有修改图、解析器、旧知识库或账簿试点。

程序完成：全量任务列举、候选写入列举、读取观察计数、材料哈希分组、读取 scope/relation/filter/JOIN/表达式/绑定提取、字段统计及 CSV BOM 输出。模型完成：选取首批材料、命名使用模式、解释相似分支的差异及其可能影响。

必须保留的边界：任务级 read×write 只是候选关系；Facts 能说明 SQL 结构，不能证明表键唯一、实际没有扩行、任务运行成功、数据已到达或业务正确。JOIN 对端按同一比较条件的另一侧保存，附加过滤条件和表达式其他输入不冒充关联键。

## 主要业务缺口

最关键的未解问题是：目标表一行的真实业务粒度及唯一键组合；两个写者是否只是重复调度；`Swap_Comp_Agt_Id` 是否必须与修饰符、业务日期等组合；各状态/类型分支的实际覆盖；以及 JOIN 前后行数和汇总金额是否守恒。这些需要数据分布、运行结果或业务确认，静态 SQL/Facts 本身不能回答。
