# 业务认知实验：两个真实加工过程

分析对象：`pdata_n.t98_sb_otc_swap_comp_info`（下称"合约快照表"）。
证据来源：任务 218601、204172 的原始 Machine Facts（`task-projections/tasks/{taskId}/versions/*.evidence-v3.json`）与 raw SQL；`swap-comp-pilot` 试点材料仅用于定位与复用背景。
本文所有 JOIN 条件均已按 Facts 的 `condition_display` 与原 SQL 双向核对。

## 0. 这张表在业务中的位置

`t98_sb_otc_swap_comp_info` 是收益互换（TRS/收益互换）业务线的合约主数据日快照：由写者任务从 `t03_otc_swap_comp_info`（来源 `ODATA_N_TIT.D_REF_TRS`）装载，按 `Busi_Date` 分区，补齐账簿、对手方、状态、类型、币种、名义本金等属性（此段复用试点说明第 2 节，本轮未重查写者）。它处在"交易登记域"与"报表/风控消费域"之间：下游拿它当"某业务日下，哪些合约存在、什么状态、多大本金、什么币种"的权威清单。本轮两个消费任务从两个方向使用它：218601 把它当"合约身份与日期锚点"去和持仓对齐，204172 把它当"可按状态/账簿筛出的金额行集合"直接汇总。

## 1. 过程 A：任务 218601 写 `dm_rsk_n.trs_pal_stmt`（TRS 盈亏报表）

### 1.1 代表路径的选择

任务只有一条语句（`task:218601:slot:query:statement:0`），由 `UNION ALL` 连接两个结构几乎相同的分支：b0 产出 `'存续'`（`grp_id='01'`），b1 产出 `'到期'`（`grp_id='02'`）。写目标是 `dm_rsk_n.trs_pal_stmt`，动态分区 `grp_id, busi_date`（Facts `datasetIo` WRITE / `output-binding:...:0`，`binding_method=TARGET_SCHEMA_POSITIONAL`）。下面只讲 b0 存续分支；b1 的差异单列。

### 1.2 一行输入、一行关联对象各代表什么

- 主驱动 `ppd`：`T98_OTC_BOOK_HOLD_SUM`（`src_tbl='ODATA_N_TIT.D_POS_POSITION_DAILY'`，`Src_Scr_Type_Cd='TRS'`，b0 限定 `busi_Date=当日`）。一行 = 某业务日、某账簿、某产品（`Src_Prd_Id`）的一条 TRS 持仓，携带名义本金、市值、累计收益等全部估值口径（原币/本币三套）。
- `trs`：合约快照表当日分区，一行 = 一份互换合约当日的登记状态。入表条件：`Comp_Stat_Cd <> '218'`、`Swap_Type_Cd NOT IN ('AB_LONG_SWAP','AB_SHORT_SWAP')`、`Swap_Comp_Subdv_Cd = 'NORM_SWAP'`。
- `py`：同一张持仓表取**上一年年末**（`py.busi_date = DATE_SUB(TRUNC(ppd.BUSI_DATE,'YYYY'),1)`，即上年 12 月 31 日）的持仓行，专门用来算"年收益 = 今年累计 − 去年年末累计"。
- `trs1`（`T03_OTC_SWAP_COMP_INFO`，`src_tbl='ODATA_N_TIT.D_REF_TRS'`，当日）：合约登记源表，提供估值处理日期 `Valu_Trmt_Date`。
- `trscr`（`T05_OTC_COMP_RGST_SAC_EVT`，`src_tbl='ODATA_N_TIT.D_TRD_OTC_CONTR_REPORT'`，**无日期过滤**）：合约报送事件，提供实际结算日 `Actl_Sett_Date`。
- `book`：账簿附加信息，只补 `book_full_name` 一个展示字段。
- `TLEG`/`H`：合约腿（`T03_OTC_SWAP_COMP_LEG_INFO`，只取 `STRUCTURE_LEG_TYPE` 等）聚合后的每合约一行，分别给出标的代码串（`collect_list` 拼接）和三类腿方向（`max(case ... then Paid_Dir_Cd)`）。
- `PTLV`：`LEG_VALUATION` CTE，把腿估值表（`T98_OTC_SWAP_COMP_LEG_VALU_INFO`，限 `src_tbl='ODATA_N_TIT.D_POS_TRS_LEG_VALUATION'`）按 `(Src_Prd_Id, busi_date, Book_Agt_Id)` 分组、按腿类型（STRUCTURE/FIXED/FLOAT）`sum` 拆出三类腿的未实现/已实现损益。

### 1.3 三个键各在对齐什么对象

- `ppd.Src_Prd_Id = trs.Comp_Src_Prd_Id`（join.1，INNER）：持仓的"源产品号"对齐合约的"源产品号"。这是**持仓行 ↔ 合约**的对齐，不是合约主键对齐。
- `trs.Swap_Comp_Agt_Id`（join.2/4/6/9，对 trs1/trscr/TLEG/H）：**合约 ↔ 合约级附属对象**（登记源表、报送事件、腿聚合）的对齐。
- `ppd.Book_Agt_Id`（join.3 对 book；join.5 对 py）：**持仓行 ↔ 账簿**及**持仓 ↔ 持仓（跨年份）**的对齐；py 一侧还叠加 `Ivst_Type_Cd`、`Long_Shor_Clas`、`Src_Prd_Id` 三列等值，共四列。

### 1.4 按真实加工顺序

1. 取当日 TRS 持仓行（ppd），按当日分区取合约快照（trs），INNER JOIN 在 `Src_Prd_Id = Comp_Src_Prd_Id` 上（join.1）。注意：**连接条件只有产品号一列，不含账簿**。
2. LEFT JOIN 登记源表 trs1、账簿 book、报送事件 trscr（join.2/3/4），分别取估值处理日、账簿名、实际结算日。
3. LEFT JOIN 去年年末持仓 py（join.5），四列等值 + 日期锚定上年 12 月 31 日。
4. LEFT JOIN 腿聚合 TLEG（join.6，按 `Swap_Comp_Agt_Id` 分组的 `collect_list`）与腿方向 H（join.9）；LEFT JOIN 腿损益 PTLV（join.7，三列等值）。
5. LEFT JOIN 汇率 EX_RATE（join.8）：`trs.Sett_Crrc_Cd = EX_RATE.src_crrc_cd` 且 `datekey2date(EX_RATE.trd_dt) = ppd.busi_date`；输出 `chg_cny_rate = case when src_crrc_cd<>'CNY' then mid_price else 1`。
6. 行级计算：三类腿损益 `nvl` 补 0；"非结构化/非固定/非浮动已实现收益" = 持仓累计已实现 − 三类腿已实现之和（投影第 47–49 行）；年收益 = 当日累计总收益 − 去年年末累计总收益，`round(...,2)`。
7. 过滤（b0 WHERE）：`ppd.busi_date >= trs.Strt_Pric_Date` 且 `ppd.busi_date <` 终止锚点，终止锚点按 `trs1.Valu_Trmt_Date → trscr.Actl_Sett_Date → trs.End_Pric_Date` 优先级取第一个非空。即"定价开始日之后、终止处理日之前"为存续。

b1（到期分支）三处不同：`dura_stat='到期'`、`comp_curr_qty` 直接置 `'0'`（不再取持仓数量）、WHERE 改为 `ppd.busi_date =` 同一终止锚点，且三个 ytd 字段多包一层"当前年份 > 终止年份则置 0"的 CASE；TLEG 额外按 `b.busi_date` 分组并要求其等于终止锚点。

### 1.5 一对多关系：哪些是结构保证，哪些只是猜测

- **结构上保证至多一行的**（GROUP BY 键 = JOIN 键）：TLEG、H（按 `Swap_Comp_Agt_Id` 分组）、PTLV（按三列分组）。
- **有真实扩行风险、无证据排除的**：
  - `trscr`（join.4）：只有 `Swap_Comp_Agt_Id = Otc_Comp_Agt_Id` 一个条件，无日期过滤、无聚合。事件表天然是历史流水，同一合约多笔报送事件会使该合约的持仓行**成倍复制**，而 outputs（名义本金、损益）全部随之重复。
  - `ppd × trs`（join.1）：只按产品号连接。若同一产品在持仓表当日有多行（不同账簿、多空分类），或合约快照当日同产品多份合约，行数相乘。
  - `trs1`、`EX_RATE`：键唯一性（`(busi_date, Swap_Comp_Agt_Id)`、`(src_crrc_cd, trd_dt)`）均未证明。
    这是**结构提示**而非已证事实——没有任何唯一性证据（与试点 README 的结论一致）。

### 1.6 输出粒度

输出一行 ≈ "某业务日 × 某合约 × 某持仓行 ×（可能的）某笔报送事件"，标以 `存续` 或 `到期`。无法证明的部分：合约快照一行是否恰为一个合约；`Src_Prd_Id = Comp_Src_Prd_Id` 是否恰好 1:1；终表在 `(busi_date, comp_no)` 上是否唯一。若 trscr 扩行成立，则"一行"实际上是"合约 × 事件"，粒度被隐性改变。

### 1.7 示意例子（示意数据，不是真实数据）

假设当日 2026-09-09，合约 A（`Comp_Src_Prd_Id` = P100，`Swap_Comp_Agt_Id` = C900）：

| ppd 行              | Src_Prd_Id | Book_Agt_Id | nom_prin  | accum_yield_tot |
| ------------------- | ---------- | ----------- | --------- | --------------- |
| 1                   | P100       | B7          | 1,000,000 | 1,200           |
| py 行（2025-12-31） | P100       | B7          | —         | 1,000           |

`trscr` 中 C900 有 2 笔报送事件（假设）：join.4 使 ppd 一行扩成 2 行。每行都算出 `ytd_yield = round(1200−1000,2)=200`，`ocrrc_nom_prin` 等金额在两行中完全相同。若下游对 `ytd_yield` 求和，C900 的年收益被算成 400——**扩行不会在行内金额上露馅，只会在下游 SUM 时放大**。此例的"2 笔事件"是假设；SQL 只证明了存在扩行的通道（无日期条件、无聚合），实际是否发生需数据验证。

### 1.8 改规则会怎样（绑定本任务实际规则）

1. **把 join.4 改成 INNER JOIN**：凡当日无报送事件的合约整体消失（连 `End_Pric_Date` 回退路径也随之改变，因为 `coalesce(trscr.Actl_Sett_Date,'')` 会命中另一分支）。这是记录集合级别的变化，UNION ALL 不会消除它。
2. **把 b0 的 `ppd.BUSI_DATE < 锚点` 改成 `<=`**：到期当日会同时满足 b0（存续）与 b1（到期）的 WHERE，同一合约持仓当日输出两行（`grp_id` 不同），`UNION ALL` 不去重——终止日在报表里被双计。当前 `<` 正是把终止日从存续分支剥离的关键。
3. **把 py 的 `py.busi_date = DATE_SUB(TRUNC(...,'YYYY'),1)` 改成当年 1 月 1 日**：ytd 变成"相对年初第 1 天"的差值，但 1 月 1 日是假期无持仓行时 LEFT JOIN 不命中，`nvl(py.accum_yield_tot,0)=0`，ytd 变成全年累计而非年内增量——错在数值口径而非行数，且下游 SUM 无法恢复缺失的基准值。

### 1.9 证据与未知

证据直接支持：所有 JOIN 条件（`...setop.b0.join.1..join.9` 的 `condition_display`，与原 SQL 一致）、两个分支的 WHERE（`...setop.b0.filter`、`...setop.b1.filter`）、终止锚点优先级、ytd 公式、汇率 CASE、写目标与动态分区（`output-binding:...:0`，`dynamic_partition_columns=[grp_id,busi_date]`）。
结构解释：TLEG/H/PTLV 经 GROUP BY 至多一行；b1 的 TLEG 按终止锚点对齐事件日是"到期当天的腿持仓"这一读法（依据 join 条件结构，业务含义待确认）。
尚不能确定：trscr 是否一对多；`(busi_date, Swap_Comp_Agt_Id)` 等键唯一性；`Comp_Stat_Cd='218'`、`AB_LONG/SHORT_SWAP`、`NORM_SWAP` 三个过滤的业务含义；为何"多标的"用分号拼接而不是拆行。

## 2. 过程 B：任务 204172 写 `dm_fii_n.adm_trd_bond_swap_scal_sum_day_titans`（利率债互换规模日汇总）

### 2.1 加工叙述

一条语句、三个子查询（Facts 确认三个独立 read occurrence：`root.casttable.d.t` / `y.t` / `m.t`），**读同一张合约快照表的同一分区**，各自聚合后按 `busi_type` LEFT JOIN 拼成一行。共同输入条件：`busi_date=当日`、`book_agt_id in ('10218','10231')`、`Comp_Stat_Cd in ('101','226')`、`Swap_Type_Cd <> 'FEE_SWAP'`。业务类型只有两档：`if(cutp_pty_shor_name='广发全球资本FICC','北向收益互换-利率债','境内收益互换-利率债')`。输出最多 2 行（每 `busi_type` 一行），动态分区 `busi_date`（Facts 绑定 `output-binding` 6 列全部 RESOLVED）。

三个指标的真实差异（均见原 SQL 第 14–70 行）：

| 指标               | 金额字段                        | 日期窗口                              | 语义                       |
| ------------------ | ------------------------------- | ------------------------------------- | -------------------------- |
| `Nom_Prin`         | `Dyna_Nom_Prin`（动态名义本金） | 只看当日快照                          | 当日**存量**               |
| `Nom_Prin_YearAdd` | `Init_Nom_Prin`（初始名义本金） | `Strt_Pric_Date ∈ [当年1月1日, 当日]` | 年内**新增**合约的初始本金 |
| `Nom_Prin_MthAdd`  | `Init_Nom_Prin`                 | `Strt_Pric_Date ∈ [当月1日, 当日]`    | 月内**新增**合约的初始本金 |

动态名义本金（`Ori_Crrd_Dyna_Nom_Prin`）与初始名义本金（`Ori_Crrd_Nom_Prin`）是快照表上两个不同字段：前者随重估变动，代表"现在这笔互换名义上值多少"；后者是成交时点本金，不随后续变动。

### 2.2 币种换算

两个金额字段共用同一个优先级 CASE：

```
Ori_Crrd_* × CASE WHEN Crrc_Cd='CNY' THEN 1
                  WHEN Lcrrc_Crrc_Cd='CNY' THEN Lcrrc_Ori_Bgng_Rate
                  WHEN Sett_Crrc_Cd='CNY' THEN Sett_Bgng_Rate END
```

优先级：合约币种 → 本币币种（用本币期初汇率）→ 结算币种（用结算期初汇率）。三个条件都不满足时 CASE 无 ELSE，结果为 NULL，乘积为 NULL；外层 `nvl(d.Nom_Prin,0)` 把聚合前的单行 NULL 与聚合后整体缺失混在一起归 0——**无法从结果区分"没有合约"与"有合约但换不出金额"**。注意这里用的是"期初汇率"（`*_Bgng_Rate`，快照表自带列），不是 218601 里那种按日行情表取的 `mid_price`。

### 2.3 分组与粒度

三个子查询内部 SELECT 了 `Book_Agt_Id, Swap_Type_Cd` 但 `GROUP BY busi_type` 只剩两档——账簿与互换类型只是参与筛选，不参与分组。输出一行 = "某业务日 × 某业务类型（北向/境内利率债互换）的一组三个规模数"。

### 2.4 为什么不能合称"日月年累计"

- 分母对象不同：`Nom_Prin` 是"当日存在的合约"（按状态筛），y/m 是"定价开始日落在窗口内的合约"（与当前状态无关，只要当日快照中存在且状态在 101/226）。
- 字段不同：存量用动态本金，新增用初始本金。
- 窗口语义不同：d 无窗口（快照即窗口），y/m 是合约开始日的区间过滤，不是对存量按时间切片的累加。
  所以它们是"存量 × 两个不同起点的新增流量"，把三个数说成同一指标的时间累计会同时犯字段错配和窗口错配两个错。

### 2.5 示意例子（示意数据，不是真实数据）

当日 2026-09-09，快照表当日分区中满足共同条件的合约行（假设均为 `广发全球资本FICC` 对手方，归入"北向"档）：

| Swap_Comp_Agt_Id | Comp_Stat_Cd | Crrc_Cd | Lcrrc_Crrc_Cd | Sett_Crrc_Cd | Ori_Crrd_Dyna_Nom_Prin | Ori_Crrd_Nom_Prin | Strt_Pric_Date | Lcrrc_Ori_Bgng_Rate | Sett_Bgng_Rate |
| ---------------- | ------------ | ------- | ------------- | ------------ | ---------------------- | ----------------- | -------------- | ------------------- | -------------- |
| C1               | 101          | USD     | CNY           | USD          | 100 万                 | 90 万             | 2026-02-10     | 7.1                 | —              |
| C2               | 226          | CNY     | CNY           | CNY          | 500 万                 | 500 万            | 2026-08-20     | —                   | —              |
| C3               | 101          | EUR     | EUR           | CNY          | 60 万                  | 60 万             | 2026-03-05     | —                   | —              |

（C3 结算币种为 CNY，但假设其 `Sett_Bgng_Rate` 为空。）

- `Nom_Prin`（存量）：C1 = 100万×7.1=710 万；C2 = 500 万；C3 前两档币种非 CNY，落入结算币档但汇率为空 → 60万×NULL = NULL → SUM 跳过 → 存量 = 1210 万，**C3 的 60 万原币敞口静默消失**。
- `Nom_Prin_YearAdd`：C1、C2、C3 的 `Strt_Pric_Date` 都在年内 → 710+500+(60万×NULL→0) ≈ 1210 万（同上丢失 C3）。
- `Nom_Prin_MthAdd`：只有 C2 落在 8 月之后 → 500 万。

### 2.6 改规则会怎样（绑定本任务实际规则）

1. **把 y/m 的 `Init_Nom_Prin` 换成动态本金**："年新增"变成"年内新增合约**当前**的动态本金"——例子中若 C1 重估后动态本金涨到 110 万，年新增随之从 710 万变 720 万；它不再是成交事实，而是"新增合约的当前市值口径"，且随每天快照漂移，历史不可复现。SUM 不能消除这种漂移。
2. **把 CASE 优先级改成 `Sett_Crrc_Cd` 优先**：C1（Lcrrc=CNY, Sett=USD）会走"结算币非 CNY"→ 仍落空变 NULL；而若某合约 Sett=CNY 且 Sett_Bgng_Rate 与 Lcrrc_Ori_Bgng_Rate 不同，换算金额直接改变。这是金额级变化，`nvl` 与 SUM 都不会暴露它。
3. **把 `Comp_Stat_Cd in ('101','226')` 放宽加入 `'218'`**：已终止合约（218 在 218601 中被显式排除）进入存量与新增——三个数同时变大。由于输出只有 2 行且无明细，任何下游都无法从结果里把这部分剥离。

### 2.7 证据与未知

证据直接支持：三个子查询的过滤条件、金额字段、日期窗口、币种 CASE（原 SQL 14–70 行；Facts 的 3 个 read occurrence 与 6 个 RESOLVED 输出绑定、动态分区 `busi_date`）。
结构解释：LEFT JOIN 按 `busi_type` 对齐在两档取值下不会扩行（每子查询每档至多一行，由 GROUP BY 保证）。
尚不能确定：`101/226` 两个状态码的业务定义；`10218/10231` 两个账簿号对应什么账簿；`Strt_Pric_Date` 与"新增"的业务口径是否含存量续作；对手方简称硬编码是否会随主体更名失效。

## 3. 结论

- **相比"这是一张核心合约快照表"多理解的**：它被下游按两种完全不同的方式消费——218601 把它当"合约身份 + 终止日期锚点"与持仓对齐后生成带存续/到期双状态的盈亏报表行，204172 把它当"可按状态与账簿直接筛出金额"的汇总行源；三个关键键（`Comp_Src_Prd_Id` 对齐持仓、`Swap_Comp_Agt_Id` 对齐合约级附属对象、`Book_Agt_Id` 对齐账簿/跨年持仓）分别服务不同对象，且 218601 的主连接只用产品号一列。
- **最易误解、已澄清的**：`trscr`（报送事件）这个 LEFT JOIN 看似只是补"实际结算日"，实际是全任务唯一既无日期条件又无聚合的合约级连接——用它 1.7 的示意例子说明"扩行后金额逐行重复、只在下游 SUM 时露馅"，比泛泛说"LEFT JOIN 可能扩行"具体得多。另一个澄清是 204172 三个指标的"存量 vs 新增 × 动态 vs 初始本金"四象限错配。
- **现有材料仍不能回答的**：`trscr`、`trs1`、快照表自身的键唯一性（决定扩行是否真实发生）；`101/226/218` 等状态码与账簿 10218/10231 的业务定义；218601 两个 UNION 分支的行数贡献；204172 无汇率命中时的实际发生率。这些都需要数据分布或业务资料，静态 SQL/Facts 无法给出。
