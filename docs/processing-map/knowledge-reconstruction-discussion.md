# 数据地图与知识重建：问题、共识、方案及推进路径

2026-09-07 接续说明：当前目标已收敛为“先把本批 PDATA 整体讲清楚”，请先读 [PDATA 理解与推进指引](pdata-understanding-guide.md)。下文保留较早讨论与当时状态；其中来源展开、方法验证和自动化的顺序不作为本轮执行顺序。

整理日期：2026-09-06。范围：本轮关于 Facts、图谱消费、共享 knowledge、业务分类、字段定义及内容积累的连续讨论。本文整合当前共识和实际进度，供后续接续；建议路径不代表已实施或已启动全域建设。

**当前应保留已有元数据、Machine Facts 和图的能力，把重心转向持续积累可阅读、可查询的业务知识。方法与公共存储已经做了小范围验证，业务内容数量仍明显不足。** 用户希望形成可复用的方法，覆盖来源、贴源、宽表及各加工层；具体样例用于检验方法，同时应产出真正可用的内容。

## 1. 最终要得到什么

用户希望能从地图中看清：整个加工体系有哪些区域，每层内部如何处理，哪些路线并行，宽表如何设计，字段口径如何变化，以及哪里值得进一步审查。HTML 支持不同粒度的展开与收起，Agent 能查询同一份公共知识，内容可以持续补充。

实际关系包含跨层读取、横向参考依赖、源系统视图、产品分支和多个下游。一棵预设的“主题 → 宽表 → 字段”目录不足以替代加工骨架。阅读层级可以收放，实际关联应保留。

方法需要可复用：新整理一张表、一个任务或一个字段后，业务地图、分类目录和字段说明应能一起受益。单个页面里的手写说明不算完成公共知识积累。

## 2. 已暴露的问题与对应方向

| 问题                                        | 本轮判断                                           | 对应处理方向                                                     |
| ------------------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------- |
| 大量元数据和精细 Facts 没有自然长成业务地图 | 证据能力与业务解释之间还需要明确的整理职责         | 定义读者问题、知识记录和消费入口，让证据持续产出解释             |
| 底层血缘不断完善，业务成果交付不足          | 建设顺序和完成标准失衡；不能由此判定底层全部无用   | 每轮交付业务内容，再根据真实使用和成本评估底层调整               |
| 简单字段问题读几段 SQL 也能回答             | 单点 SQL 示例不足以证明全图价值                    | 图用于全貌、成员和路线定位；Facts/SQL 用于精细加工，两者分别验收 |
| 消费层容易退化为“展示节点、边和 JSON”       | 业务理解需要分组、解释、范围、证据和阅读导航       | 明确全貌、宽表说明、审查发现三种阅读单位                         |
| schema 太粗                                 | schema 表达技术位置，内部可能包含多种业务职责      | 在具体对象上补业务分类，再汇总成阅读视图                         |
| “日期展开、NULL 兜底”等技术标签看不出价值   | 技术动作需要连接到日期、粒度、金额或覆盖范围的变化 | 说明“改变了什么、影响哪个业务问题”，再保留动作标签供检索         |
| 希望一套方法通用，又担心每次只做单点        | 方法需要公共结构，也需要真实对象暴露边界           | 用统一记录方式积累不同对象；样例验证不替代后续内容建设           |
| knowledge 内容很少                          | 已跑通公共存储和验证，但业务积累没有同步跟上       | 优先归集现有业务稿，再按区域补表/视图、字段和加工说明            |

早期讨论还提出过 `COLUMN` 与 `PHYSICAL_FIELD` 并存、加工证据读取依赖图 READY 等疑点。它们保留为**架构复核候选**；本轮没有重查这些实现，也没有决定删除节点类型或调整发布器。后续应结合具体消费需求核对当前代码、依赖与迁移成本，不能把讨论意见写成已完成的架构结论。

## 3. 已形成的分工：Facts、图、knowledge、页面

| 部分                     | 负责什么                                           | 边界                                                         |
| ------------------------ | -------------------------------------------------- | ------------------------------------------------------------ |
| 元数据 / DDL / 注释      | 对象类型、字段结构、声明约束、原始名称与用途说明   | 注释和 DDL 都可能过时；声明和实际数据表现有区别              |
| Machine Facts / SQL 证据 | 表达式、来源、条件、日期选择、分支及位置           | 技术观察不自动证明正式业务定义或运行正确                     |
| 图及其投影               | 表/任务成员、来源去向、读写关系及导航              | 表级连接不等于逐字段因果；静态关联不等于运行接续             |
| 共享 knowledge           | 业务分类、字段定义、加工解释、适用范围、证据和问题 | 有依据的归纳可以先使用，后续修订；不能改写原始事实来消除冲突 |
| HTML / CLI / Agent       | 按不同阅读问题组织和消费公共材料                   | 页面布局不成为唯一知识来源；消费入口应说明覆盖和更新时间     |

当前总览已经使用固定图快照中的方向、数字和任务集合；主路线选择、区域职责、节点布局等仍由人工组织。暂不优先追求自动生成一张同样清晰的完整总览。

一个可能更划算的演进方向是：保留阅读骨架，让图更新成员和数字，并提示新增或消失的路线。**这属于后续建议，当前页面仍为固定快照构建，没有自动刷新或变化提醒。**

## 4. 分类方法：对象类型与业务标签分开

### 4.1 对象类型是一条独立信息

表、视图应分别记录并支持筛选。类型优先依据元数据或 DDL；无法确定时保留未知，不从 `v_` 等前缀推断。

一个对象可以是“视图 + 合约主题 + 汇总结果”。按业务阅读时可以放在一起，按技术结构阅读时可以分开。视图在取得定义 SQL 后可展开依赖；物理表可从已知写入任务继续展开。源视图被采集为下游物理表后，仍保留两个对象及其关系，不混成同一身份。

这项区别已经达成讨论共识，**尚未补入现有方法样例的数据合同，也未实现 HTML 的表/视图筛选**。后续落地应明确 `objectType` 等独立属性，并保留判定依据和未知状态。

### 4.2 四个公共分类维度

| 维度     | 回答的问题             | 示例                                             |
| -------- | ---------------------- | ------------------------------------------------ |
| 业务对象 | 这里记录或加工什么？   | 交易、合约、持仓、客户、标的                     |
| 产品范围 | 判断适用于什么产品？   | 期权、收益互换、北上 DMA；必要时限定到分区和条件 |
| 数据角色 | 数据承担什么记录职责？ | 基础记录、事件、快照、历史状态、宽表、汇总结果   |
| 加工职责 | 这个步骤做了什么？     | 采集、整合、折算、日期展开、历史指标补充、交付   |

标签应有定义和适用对象，允许多标签，不强制所有对象归入唯一目录。系统/柜台名称、产品名称和 `grp_id` 分区值不能自动混成同一维度。未分类对象仍然保留在资产清单中，不能为了分类整齐而隐藏。

标签适合归类和筛选；币种、时间口径、候选键、Join 条件和产品公式需要结构化说明。它们可以帮助产生标签，但不能全部压成标签字符串。

## 5. 公共知识的记录与形成方法

建议的最小结构是：**对象 → 若干有范围的判断 → 对应证据**。判断可以是分类、定义或关系；每项分别保存内容、适用对象/条件、依据，以及是原文观察、阅读解释还是候选。

例如同一初始本金字段可以同时记录：DDL 类型为 `string`；注释写“初始名义本金”；某产品条件下取动态本金；最终币种暂时未知。不能将这几件事压成一条不带范围的“人民币本金”定义。

一般整理路径：

1. 绑定对象身份，明确要帮助读者理解什么。
2. 读取已有知识、对象自身 DDL、注释；记录缺失和时间信息。
3. 用图定位相关加工，用 Facts、SQL 核实会改变解释的部分。
4. 分别记录分类、字段定义、日期/粒度变化和业务关系，保留产品与分区条件。
5. 用不同阅读或查询方式消费同一份记录，检查能否复用且不丢范围。
6. 来源变化时，按证据依赖找到需要复核的判断；保留仍然适用的内容。

这条路径允许逐步完成，不要求每张表先查清所有字段。应优先补影响理解的字段：对象标识、产品类型、日期、本金/金额，以及关键关联条件。

字段定义可以沿关系补充，但不直接传播：同名字段可能改变日期含义、单位、粒度或取值范围。确定为未改变语义的透传才可复用上游说明；发生折算、聚合、日期选择等处理的位置记录差异。

### 对 AI 注释的最新校正

用户明确认为“【AI】”标记本身不构成问题。采用以下规则：

- AI 注释可用于初步分类和解释，不因生成者身份停止整理或要求人工批准。
- 结合字段、DDL 和加工逻辑判断内容是否一致；信息不全时可先粗分类。
- 与其他证据冲突，或涉及币种、粒度等重要口径时，再深入核实。
- AI/人工来源只作为来源信息；人工注释同样可能过时。
- 一个对象的注释不能因为相邻或同名而当成另一个对象的原生说明。这是证据适用范围问题，与是否 AI 无关。

[方法 V0](../../../sql-static-lineage-data/knowledge/methods/organization-v0.md)中对 AI 标记的强调应按本节理解，不能执行为使用门槛。本节及上面的表/视图区分是该草案形成之后的最新讨论补充；本次没有改动其 JSON 样例或现有读取器。

## 6. 一个具体推进入口：Titans 可见来源

当前总览的这个节点绑定 `titans_dm` 与 `titans_refdata`。本轮固定图快照分别有 218、16 个表身份节点，共 234 个；数字不代表 Titans 全库，也不代表这些对象已全部确认是物理表。

拟议阅读路径：

**Titans 可见来源 → 表/视图筛选与业务分类 → 具体对象 → 采集或加工任务及去向 → 字段与证据。**

表成员和实际连接由图提供，业务分组与解释来自 knowledge。可先展示全部本批可见成员，已整理部分展示分类与说明，其他部分明确待整理；无需先完成 234 个对象的业务解释才让它们可见。

适合先深入的对象包括已读合约链相关来源。例如 `trd_otc_trade`、`trd_option_event`、`pos_trs_leg_his_pos`、`ref_counterparty` 提供了交易、事件、历史持仓与参考资料的阅读候选。名称只是检索线索，具体类型和含义要由相应材料支持。

源系统内部的完整加工过程可能缺少定义 SQL 或原生元数据。下游采集图能提供可见去向，不能据此补造源系统内部血缘。

## 8. 建议的推进路径与验收结果

以下是建议顺序，没有在本次文档整理中实施搬迁、全域打标或新平台建设。

| 顺序                    | 工作                                                                                 | 应交付什么                                                      | 如何判断完成                                                              |
| ----------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 1. 归集现有业务内容     | 盘点总览、层内骨架、四产品本金及已读加工说明，明确各自唯一维护源；逐项调整读取和链接 | 公共业务知识目录、正文、范围与来源；docs 保留架构/方法/实现入口 | 已有内容从共享入口可找到；HTML/CLI 对已支持范围继续能读；避免维护两份正文 |
| 2. 展开 Titans 来源     | 基于现有图显示可见成员；区分已知表/视图/未知；先补合约链的一批对象                   | 可筛选的来源对象清单、业务分组、一句话用途和实际去向            | 用户能找到某类业务数据，辨别相似对象，并沿真实关联继续读                  |
| 3. 补关键字段与加工     | 用 DDL、注释和 Facts 解释标识、日期、本金及关键 Join；范围随业务问题扩展             | 字段说明、条件公式、粒度意图、上下游变化和未决问题              | 能回答“这一层改变了什么”“两条分支有何不同”，且能定位证据                  |
| 4. 在内容增长中固化方法 | 复用既有词汇，处理同义/冲突，明确草案记录向正式公共内容的映射                        | 稳定而小的分类与记录约定；按实际需求提供查询                    | 新对象接入不必重做页面解释；同份知识支持多种读取，方法文档不替代业务产量  |
| 5. 按实际成本补自动化   | 处理反复出现的成员更新、证据变化定位、批量整理与检索                                 | 对应重复劳动的工具或图消费改进                                  | 有可观察的时间/维护收益，再决定是否扩展底层或简化已有层                   |

第 2 步曾建议先深入约 10～20 张已读链相关来源对象，这只是控制首批阅读范围的建议，不是硬性数量验收，也不限制后续覆盖。公共方法应保持可复用，批次则以实际内容质量收口。

可持续记录的进展应包括：本批可见对象数、已解释对象数、表/视图类型未知数、关键字段的口径覆盖、未决问题和已在消费入口可读的内容。按对象去重统计，标签数、文件数、工具通过数不能替代业务覆盖。

## 9. 谁负责什么，什么时候需要用户参与

Agent 负责材料定位、分类草稿、DDL/注释/Facts 交叉核实、知识整理、公共读取与入口验证；先把已有证据能回答的内容做出来。

用户主要判断阅读是否符合真实业务、对象分组是否有用，并确认少量材料无法决定的重要业务口径。提问时应带着当前解释、证据与具体疑点，不要求用户预先逐表讲解或设计标签体系。

目前留存的业务问题包括源交易表正式粒度与用途、金仕达 03 组初始本金的正式定义及币种。Agent 应先继续找原生 DDL、业务文档等材料；候选键是否实际唯一仍需数据核验，不能由口头预期替代。
