# PDATA 理解与推进指引

更新日期：2026-09-07。本文记录本轮讨论确定的目标、当前基础和建议顺序，是继续“搞清 PDATA”的阅读入口。文档补充已完成；下文的分析、结构化说明和页面深化仍是后续工作。

## 先看这五句话

1. **当前目标：把这批任务中可见的 PDATA 整体讲清楚。** 看懂输入、业务对象、加工路线、结果粒度和下游用途。
2. **现有交互与总分骨架可以继续用，分类需要认真核对。** 当前分支是阅读组织，尚不能作为已经确认的模型分类体系。
3. **先形成区域整体认识，再深入影响整体理解的复杂加工，最后回到整体修正解释。** 深读任务由业务问题选择，几个样例不代表区域全貌。
4. **结果粒度和复杂加工内部过程是重点。** 表名、任务数和 SQL 入口已经存在，接下来要讲清“一行是什么”“每一步改变什么”。
5. **分析过程中保存可复用记录，方法稳定后再固化流水线。** 当前完成条件是 PDATA 可理解、可核对，不是先建成批量标注平台。

## 2. “搞清 PDATA”要回答什么

| 问题                       | 应形成的认识                                                       |
| -------------------------- | ------------------------------------------------------------------ |
| 这里有哪些业务对象和结果？ | 区分基础对象、对象关系、事件、状态／历史记录，以及进一步整合的结果 |
| 为什么有这些表和分支？     | 解释各自职责、相似对象的区别、共享支撑与实际联系                   |
| 数据经过哪些变化？         | 沿真实路线解释标识、记录范围、粒度、日期和金额如何变化             |
| 每份结果怎样理解和使用？   | 说明一行代表什么、时间表示什么、哪些后续加工实际读取               |
| 哪些地方还不清楚？         | 保留具体缺口及其影响；未知成员仍在区域全貌中可见                   |

区域地图应持续呈现：**区域外输入 → 内部各加工分支及其连接 → 形成的数据结果 → 区域外消费者**。展开时保留当前位置和上下游语境。

## 3. 按什么顺序推进

| 顺序            | 做什么                                                                               | 本步交付                                                                     |
| --------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 1. 建立区域对照 | 复用现有完整成员、SQL、DDL、业务资料，核对现有分组；先解释结果和职责，不急于改分类   | PDATA 成员与业务问题对照稿：当前认识、依据、粒度认识、关键疑点及优先深读路线 |
| 2. 解释区域路线 | 沿实际输入输出连接，组织基础对象、关系维护、整合结果和共同依赖；所有可见成员都有位置 | 区域整体解释和路线草图；已有解释与尚待分析部分分别标明                       |
| 3. 深入关键加工 | 对影响分类、粒度、历史或金额理解的复杂任务拆阶段；把发现放回对应分支                 | 复杂加工阶段图、输出粒度说明，以及对区域认识的修订                           |
| 4. 回填现有页面 | 用说明改善节点标题、结果含义和展开内容，校正分组；内容保存到可共同读取的位置         | 完整的“区域 → 分支 → 加工 → 结果／规则 → 证据”阅读路径                       |

**下一步先做第 1 步。** 先交出可讨论的 PDATA 整体认识和问题分布，再决定深入哪里。逐任务分析可以分批进行，不要求先逐字段读完全部任务。

`105529` 的历史关系维护、`107491` 的日期展开是已有材料较充分的深读候选。选择它们的理由是解释 PDATA 的实际职责；具体优先级由第 1、2 步暴露的业务问题决定。

## 4. 分析时保存哪些内容

以**任务的一项实际写入输出**为说明单位。同一任务写入不同结果，或同一表被多个任务、不同来源／分区写入时，分别描述适用范围；不能仅把任务配置目标当成唯一实际输出。

| 项目       | 最小内容                                                                     |
| ---------- | ---------------------------------------------------------------------------- |
| 输入       | 来源对象及其行含义；用于关联和时间选择的关键字段                             |
| 加工       | 做了什么，哪些关联、筛选、汇总、展开或计算影响结果                           |
| 输出       | 结果用途、行含义、时间含义、关键标识及产品／来源／写入范围                   |
| 分类与标签 | 候选模型主题、业务对象、加工职责、结果形态；下游用途单独记录                 |
| 深入理由   | 哪些规则需要拆阶段，为什么会影响理解；简单加工保留简明说明                   |
| 依据与缺口 | 对应 SQL、DDL、Facts／投影观察、业务材料及版本；区分直接观察、解释和待确认项 |

这是一份分析记录约定，尚未发布为新合同。优先复用 [107491 共享说明及读取方式](shared-knowledge.md)，按实际需要扩充；现有 PDATA 的逐任务说明还没有全部接入该共享读取器。

### 结果粒度怎么描述

先分开说明三件事：**一行记录哪个对象／关系／事件，时间表示什么，用哪些字段和条件区分记录。** 逻辑粒度与实际唯一性分别记录。

- 有客户或部门字段，不代表结果就是客户或部门粒度；有日期分区，也不直接决定行粒度。
- 先解释各项写入，再比较同一张表的多条写入路线能否合成统一粒度说明。
- `105529` 可围绕“有效期间内的合约与账簿关系”分析这条写入；不能据此直接定义整张协议关系历史表。
- `107491` 可先确认“合约快照记录展开到计提日期”，关联后是否仍保持候选键唯一需要另列依据。

### 复杂加工怎么展开

每个阶段说明：用途、输入、规则、输出／临时结果、粒度与时间变化，以及证据。把临时表放回产生和消费它的阶段，而不是全部平铺为外部输入。

以历史维护为例，待用实际 SQL 落实的阅读顺序是：**构造当日关系 → 取得历史有效关系 → 按键比较 → 区分新增／变化／消失／不变 → 维护有效区间 → 写入结果**。这不是已经生成的阶段图。

局部与整体通过四段对应关系连接：**SQL 步骤与临时结果 → 具体写入及粒度 → 后续消费路线 → 区域分支及成员**。已有读写关联可以复用，内部步骤和业务变化需要补齐。

## 6. 流水线什么时候做

分析过程中先保留结构化记录，重复取材料和检查引用的操作可用小脚本辅助。等 PDATA 的说明方式、分类依据和复杂阶段表达稳定后，再固化：

**准备材料 → 模型生成概要与标签 → 深入复杂项 → 核对证据与关键语义 → 保存共享记录 → 页面与 CLI 消费 → 汇总区域地图。**

程序负责成员、关系、引用和版本检查；模型负责有依据的解释与归纳。程序检查通过不等于业务语义正确。图的连线来自实际关系，不能由分类标签或模型常识补造；调度依赖辅助定位，不当成字段因果。

## 7. 怎样判断本轮完成

- 用户停在 PDATA 区域图，就能理解主要职责、路线、共享输入及范围边界。
- 当前分支有明确的划分理由和完整成员；未解释部分可见且说明影响。
- 已解释结果能回答行含义、时间含义和使用方式；粒度未确认的地方有具体问题。
- 关键复杂加工能按阶段读懂，并回到实际表、写入和证据。
- 局部发现已回填整体解释，页面读到的内容与共享记录在已支持范围内一致。

静态 SQL、图和说明不证明生产运行成功、数据已送达或实际行唯一。后续需要运行或业务确认的问题单独保留，不把它们悄悄写成已完成。
