# 产品、合约与销售归属

OIS 的产品编号、客户编号、合约编号和人员编号分别描述不同对象。入模时，它们会借助证券资料、TIT 交易资料和 IOA 用户资料转换。真正需要保留的是“采用了哪个标识、如何转换、没有匹配时怎样处理”。

## 1. 产品通过证券资料取得统一证券编号

收益凭证任务 92881/96673 读取 `O_OTC_INCOMECERTIFICATE`，保留本金、收益率、起息到期日、兑付和提前终止等属性。这里的产品类型、产品结构、实际投资人属于收益凭证资料；它与客户类别代码中“作为客户的产品载体”是不同的描述对象。

这两份 SQL 的关键身份连接为：

```sql
a.prd_no = b.scr_cd
-- b 来自 T02_SCR_BASE_INFO，限定 src_id='OTC'
```

匹配成功时，`secu_id` 由证券资料提供。但未匹配时，两条分支采用不同策略：

| 分支 | secu_id 未匹配时 | src_sys_prdno 未匹配时 |
|---|---|---|
| 92881 当前资料分支 | 直接取右表值，允许为空 | 直接取右表值，允许为空 |
| 96673 历史资料分支 | 按 SQL 固定的 FIN 编码格式拼接产品号 | 拼接 `OTC-`＋产品号 |

因此，历史分支有证券编号，并不证明它成功匹配了证券资料或该拼接编号已得到主数据确认；当前分支为空，也不一定是 OIS 没有产品资料。两份 SQL 都没有证明右表在连接条件下唯一。[92881](证据/SQL/92881.json)，原 73–76、154–163 行；[96673](证据/SQL/96673.json)，原 77–79、124–129 行。

产品资金类型还有两层处理：先按 `T02_PUB_COVT_CONST` 的来源 OIS、类别 var00512 转换；名称缺失时，再从 OIS 字典 `G_OTC_DICTIONARY` 的 fund_types 子项回填。**代码和名称采用的回退路径不同**：`fnd_type_cd` 仍来自转换结果，名称可回退到源字典。于是“有中文名但标准代码为空”是 SQL 允许的结果形态，不能据此认为转码已经完成。

92881 同样保留收益凭证属性及统一证券标识，但应按本任务的表达式核对，不能把历史分支 96673 的名称回退自动套用到所有分支。[92881](证据/SQL/92881.json)，原 71–105、116–169 行。

## 2. 提前终止落在产品主题，并不自动意味着一产品只有一条记录

110000 从 `O_EXCHANGE_PRE_TERMINATION_LIST` 生成 `T02_FIN_PRD_PRETERM_INFO`：

| 输出 | 来源与转换 |
|---|---|
| rec_id、src_rec_id | prod_code |
| src_sys_prdno | `OIS-`＋prod_code |
| secu_id | 以 prod_code=scr_cd 关联 OTC 证券资料 |
| 提前终止金额、价格、收益率、兑付金额 | 对应 termination 字段 |
| 提前终止日、兑付日 | 日期字符串标准化 |
| float_income_vchr_rec_id | prod_id |
| trmt_rgst_flag | end_report_flag 的 true/false → 1/0；其他填空 |

目标按来源 OIS、分组 01 写入；所读 SELECT 没有按产品聚合或选取唯一终止记录。源 ID 被写进 remark，不能把 rec_id=prod_code 解释成已验证的物理唯一键。[110000](证据/SQL/110000.json)，原 55–81 行。

当前图查询 `secu_id` 只返回一个输出节点，没有来源边；SQL 却明确给出证券资料关联。这里采用 SQL 解释加工，保留图查询的现状，不把“没有返回边”解释为没有来源。[图查询证据](证据/图谱-110000-secu_id.json)。

## 3. 客户分成和合约分成分别以客户、合约为组织中心

| 对比项 | 客户员工机构分成：135142 | 合约开发分成：134215 |
|---|---|---|
| OIS 主来源 | O_COUNTERPARTY_INTRODUCTION，来源声明及宏 | O_CONTRACT_INTRODUCTION，显式读取 |
| 核心对象 | 客户＋员工＋机构 | 合约＋分成对象 |
| 模型 | T01_CUST_EMP_ORG_COMB_DIV_RATI | T03_AGT_DIV_RATI |
| 比例 | ALLOCATION_PROPORTION | ALLOCATION_PROPORTION |
| 人员 | 保留 CUSTOMER_MANAGER；另用 IOA LOGIN_ID 取 ERP_ID，未匹配回退 | 用 IOA LOGIN_ID 取 ERP_ID，未匹配回退 CUSTOMER_MANAGER |
| 机构 | INTRODUCTION_DEPARTMENT 左补零至四位 | 本条分成投影没有同一套机构映射 |
| 删除记录处理 | 主源限定 IS_DELETED='N' | 保留删除标志，Y/N 转 1/0；主源未按该标志排除 |

所以客户分成比例与合约分成比例不能直接相加或互相替换。135142 中的客户主资料主要补类别，IOA 资料补人员身份；比例值仍由 OIS 开发关系提供。[135142](证据/SQL/135142.json)，原 26–51 行；[134215](证据/SQL/134215.json)，原 33–75 行。

IOA 当前、删除用户两支采用 UNION ALL，均限定主部门和非空 ERP_ID。当前 SQL 没有证明 LOGIN_ID 唯一；发生多匹配时，关系可能展开，比例值本身不因同一次映射变为多份业务分成。

## 4. 合约分成的三个标识需要一起读

134215 用 OIS 的 CONTRACT_CODE 连接 TIT 的 INTERNAL_TRADE_ID，取得交易标识；还尝试连接确认书标识，并通过互换、期权对象判断类型。

```text
Agt_Id     = COALESCE(TIT交易ID, 确认书ID, OIS合约代码)
Src_Agt_Id = OIS合约代码
Agt_Modifr = 互换匹配时20206；否则期权匹配时20207；
             否则确认书匹配时20206-KST；其余为空
```

这三项分别保留目标身份、原始身份和匹配类型。Agt_Id 非空不证明 TIT 匹配成功：它可能来自最后的 OIS 原码回退。修饰符判定也有优先顺序，不能只按一个字段非空判断整条识别链成立。

分成值本身是直接映射 `ALLOCATION_PROPORTION → Div_Rati`，不是由 TIT 金额计算出来。现有图已经确认它经贴源任务接到原库同名字段。[分成字段图证据](证据/图谱-134215-div_rati.json)。该证据没有检验比例单位、总和或业务分配是否正确。

## 5. T99 参数与 T05 审批共同解释管理过程，但不等于已算出收入

OIS 候选索引还包括基础系数、价差系数、资金成本、客户创收系数等对象，多数指向 T99，部分相关结果指向 T98。它们是解释销售归属和参数来源的必要背景，即使本次重点是 T01～T10，也不能将这些引用从认知里抹掉。完整候选见[任务附录](附录/02-全部候选任务.md)。

对已读的 246739，临时价差记录经过六项分组：合约代码、系数类型、合约类型、价差计算类型、年化价差系数、绝对价差系数；组内按更新时间降序取一条，再排除正式表中同日、未删除且六项相同的记录。[246739](证据/SQL/246739.json)，原 95–124 行。

由此能得到三个具体认识：

- 系数值本身参与分组，因此“取最新”不是每个合约只保留一项系数。
- 正式表用于 NOT EXISTS 排除；该分支的系数值来自临时表。
- 这条系数任务未识别合约时 Agt_Id 填空，而合约分成任务可回退源代码。不同模型里是否有合约编号，受具体转换策略影响。

上述结论是 SQL 逻辑解读，不宣称本任务全部输出已完成字段绑定。相关审批事件在 T05 中保留过程记录；审批状态、参数生效及最终收入计算仍是不同环节，不能凭参数记录存在就推出审批通过或收入已确认。
