# 客户身份与主体入模

OIS 客户入模的第一步，是把来源客户号及其属性组织成 T01 当事人资料；后续再分别表达名称、关系、银行资料、受益所有人及协议条件。它们各自具有记录粒度，不能把所有表都当成“一个客户一行”。

## 1. 国内与香港客户进入同一模型，转换规则分别定义

| 内容 | 国内分支：O_OTC_DERIVATIVE_COUNTERPARTY | 香港分支：G_HK_COUNTERPARTY |
|---|---|---|
| 已读任务 | 63168 | 144556 |
| 客户编号 | CLIENT_ID → Pty_Id | CLIENT_ID → Pty_Id |
| 主体名称 | CORPORATE_NAME → Pty_Name | CLIENT_NAME → Pty_Name |
| 类别 | IS_PROD_HOLDER=01 → 110500；02/03 → 210500；其他原样保留 | Individual(PI Confirmed) → 110500；CPI/IPI → 210500；其他原样保留 |
| 状态 | VALID_FLAG=Y/N → 04/07；其他 → 99 | 按 AUDIT_STATUS 查转换表；未匹配时保留源值 |
| 开户日期 | 该分支填空 | 由 OPEN_ACCOUNT_COMPLETE_DATE 转换 |
| 来源筛选 | 当日分区，且 DEPARTMENT<>'HK' | 当日来源分区 |

本地 CD002 中，110500 为“OTC场外衍生品个人客户”，210500 为“OTC场外衍生品对公客户”。这两个标准类别不能反推出全部源客户类别：国内分支的 02 和 03 已被合并表达。字典记录日期为 2021-01-11，属于本地未验证快照。[字典选录](证据/字典选录.json)。

香港状态转换还带有目标表、目标字段、源表、源字段、来源系统五项限定；只拿 AUDIT_STATUS 的码值去找一个通用中文含义，会漏掉代码域。`NVL(DW_CD_VAL,AUDIT_STATUS)` 表示转换失败仍可能有值，非空并不证明已经标准化。

证据：[63168](证据/SQL/63168.json)，原 34–59、94–100 行；[144556](证据/SQL/144556.json)，原 34–59 行。香港客户编号的[当前图路径](证据/图谱-144556-pty_id.json)进一步显示贴源字段与上游原库字段的已确认接续。

## 2. CLIENT_ID 是编号线索，来源和时间限定它的使用范围

两支都写 `T01_PTY.Pty_Id`，并不能证明不同来源里的同值客户号一定表示同一个主体。读取和连接时应同时确认所属来源分支、主体类别及适用日期。`Data_Src_Cd='OIS'` 只能识别系统，`Src_Tbl` 才进一步区分这里的具体源表；`Real_Src_Tbl` 的值也须按本任务解释，不能预设它与分区值永远相同。

国内分支还会读取目标表中同一来源的已有记录，以保留删除日期、比较变化。这种自读是状态维护逻辑。看到图中“模型表读回模型表”，应先看此次写入和来源分区，不能把全部历史写入都接成当前输入。

名称表有另一种时间组织。144561 从香港客户资料写 `T01_PTY_NAME`，保留中文全称、简称和英文简称，英文全称填空；目标按 `Src_Tbl+Busi_Date` 写日快照。不能仅凭名称或历史说明，把这条分支说成按有效起止日期维护的区间历史。[144561](证据/SQL/144561.json)，原 22–47 行。

## 3. “同一客户”入模保存关系，没有替所有客户选择一个主号

149553 读取 `G_SAME_COUNTERPARTY`，按下列条件自连接：

```sql
A.COUNTERPARTY_ID = B.COUNTERPARTY_ID
AND A.CLIENT_ID <> B.CLIENT_ID
```

输出 A 的客户号为 `Pty_Id`，B 的客户号为 `Rela_Pty_Id`，关系类型固定为 01。本地 CD178/01 的名称为“同一个当事人”。因此，COUNTERPARTY_ID 在此承担分组依据，T01 保存组内客户号之间的关系。[149553](证据/SQL/149553.json)，原 30–46 行；[字典选录](证据/字典选录.json)。

例如一个组有 A、B、C 三个不同客户号，连接可以产生六个有向配对。这个例子说明 SQL 的结构，不是实际数据统计。单成员组还可能因 LEFT JOIN 留下关联方为空的行。`DISTINCT` 不会把这些关系选成唯一主客户号。

业务使用时，应先决定按来源客户号看明细，还是按客户关系归并。把全部关系直接连接到交易金额后相加，可能展开原有明细；关系的有效期间也需要与业务日期对齐。

## 4. 银行资料描述客户提供的收付款账户

199856 从 `O_COUNTERPARTY_ACCOUNT` 映射客户号、开户行、银行账号、账户名称和大额支付号，写入 `T01_PTY_BNK_ACCT_H`。账户类型固定为 01，SQL 注释为“交易银行”。它没有生成 T03 的协议编号或协议修饰符，不能仅凭 ACCOUNT 一词与 TIT 资金账户、保证金账户互换。

历史比较使用四项连接条件：**客户号＋银行账户类型＋银行账号＋账户名称**。因此，账户名称也参与记录匹配。源记录与目标开链记录 FULL OUTER JOIN 后，区分新增、删除、变化、无变化，变化时关闭旧版本并加入新版本。读取已有有效记录的条件为 `Strt_Date<=d AND End_Date>d`。[199856](证据/SQL/199856.json)，原 33–73、173–226 行。

这解释了为什么“同一个账号”仍可能出现多个历史版本，也说明按账号去重不足以恢复指定日期的有效资料。

## 5. 受益所有人需要经过客户身份桥接

149557 的路径是：

```text
G_AML_BENEFICIARY.COUNTERPARTY_ID
  → G_AML_COUNTERPARTY.ID / CLIENT_ID
  → O_OTC_DERIVATIVE_COUNTERPARTY.CLIENT_ID
  → T01_BENE_OWNER_DD_INFO.Pty_Id
```

受益所有人源记录 ID 写入 `Bene_Owner_Info_Id`，持有比例来自 `HOLD_RATE`。第一步为 LEFT JOIN，但到客户主资料的第二步为 INNER JOIN；不能匹配客户主资料的记录不会进入该结果。分类、认定类型、性别、证件类型还各有代码转换条件。[149557](证据/SQL/149557.json)，原 62–73、114–154 行。

这张表的粒度围绕受益所有人资料记录，一个客户可以关联多条记录。姓名、持有比例存在，不代表已证明每个客户只有一个受益所有人，或者比例合计符合某个业务规则。

## 6. 协议条件也可能落在 T01

212650 将 `G_HK_THRESHOLD` 写入 `T01_OTC_DERI_CUTP_ISDA_AGT_THRH`，保留源记录 ID、客户号及双方的 CSA、SCHEDULE、最低转移金额相关条件。每组都要一起看**甲乙方、币种、金额、无穷大标志**；true/false 转成 1/0，其余值原样保留。[212650](证据/SQL/212650.json)，原 42–82 行。

这里沿用字段注释理解数据，不扩写协议条款的法律含义，也没有证据把 PARTY A 固定解释为我方。模型中存在这些条件，不等于已建立完整主协议与每笔交易的连接，更不等于 TIT 履保计算已消费它们。

这份 SQL 的业务日期已绑定为 2026-05-29，说明所保存文本的处理日期。它不代表当前协议条件。该任务在本次固定图版本中不在发布范围，以上结论来自本地 SQL。
