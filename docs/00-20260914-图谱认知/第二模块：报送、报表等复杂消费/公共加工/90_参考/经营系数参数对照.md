# 经营系数怎么进入收入：价差、基准与资金成本

阅读定位：本文是参数对照参考，不是118141完整主线。第一遍理解收入，请先读[一份期权怎样成为销售收入日报](../../销售与经营分析/118141_交叉销售收入/README.md)；该主脚本已引用这里的五路消费JOIN。本文保留参数之间的差异，避免与主线重复讲整条流程。

合约主信息告诉我们“是什么合约”，逐日明细告诉我们“某天的本金和费用是多少”。经营系数补的是：**用什么计算方式、按多大的比例，把这些金额算成销售收入。** 人员归属和收入分配是后面的事情。

本文把三个专题接在一起，不重复它们的全部生产SQL。推荐顺序：[价差](../04_经营系数_价差/README.md) → [基准](../05_经营系数_基准/README.md) → [资金成本](../06_经营系数_资金成本/README.md)。每个专题都先说明主体、关联作用和输出，再给来源字段与SQL。

## 一、三个名字分别指什么

| 名称 | 在这段SQL里的实际作用 | 不要误读成 |
| --- | --- | --- |
| 价差系数 | 普通期权／互换收入中的一部分参数，分年化和绝对两种方式 | 已经算好的收入金额；或认为生产SQL一定执行了“报价减成本” |
| 基准系数 | 普通期权／互换收入中的另一部分参数，同样分年化和绝对 | 自动等同于某个市场参考利率；它在此是销售收入基准参数 |
| 资金成本参数 | 在AIRBAG、金仕达等指定分支中参与成本扣减 | 所有合约都统一扣一遍；或与逐日明细同名字段表示同一种数值 |

源参数的业务定价、比例为什么这样审批，不是这些搬运和计算SQL能单独证明的。这里先讲已能从字段与公式看清的处理规则。

**计提日就是“这笔收入算在哪一天”**，加工日是“系统哪天算这次结果”。系统今天重算过去某天，不意味着那笔收入归今天，更不意味着今天已付钱。

## 二、先选参数，再按业务分支计算

```text
销售合约 + 逐日本金／费用
       │
       ├─ 合约价差／客户类型价差 → 选价差类型和系数 ─┐
       ├─ 合约基准／类型基准   → 选基准类型和系数 ─┼─ 普通OPTION／TRS公式
       │                                         │
       └─ 类型资金成本 → 匹配成本参数 ────────────┴─ 仅相应特殊分支使用
                                                   │
                                           当日收入CASE的结果
                                                   │
                              后续收入调整、介绍比例分配与累计（另行展开）
```

图中是参数用途，不表示各分支一起相加。原CASE先判断AIRBAG、特定LONG_HOLD_SWAP、金仕达，再到普通OPTION／TRS。前面命中就不继续使用后面的普通公式。

## 三、五个输入并不是按同一套日期选出来的

`info`是销售合约主信息，`det`是逐日明细；`det.busi_date`是收入计提日，`info.Strt_Pric_Date`是合约期初定价日。

| 输入别名 | 参数层级及来源T99 | 用什么身份连接 | 按什么日期匹配 |
| --- | --- | --- | --- |
| `s_sp` | 合约价差：`t99_deri_comp_sprd_coef_ref` | `Inr_Comp_No = info.Agt_Id` | 生效日分段后，匹配`det.busi_date` |
| `c_sp` | 客户＋类型价差：`t99_deri_cutp_comp_type_sprd_coef_ref` | 客户号＋合约类型 | 适用上下限展开后，匹配`info.Strt_Pric_Date` |
| `s_ba` | 合约基准：`t99_deri_comp_base_coef_ref` | `Inr_Comp_No = info.Agt_Id` | **没有日期匹配，也没有取最新版本的排序** |
| `c_ba` | 类型基准：`t99_deri_comp_type_base_coef_ref` | 合约类型；输入限定OTC部门 | 起始日适用上下限展开后，匹配`info.Strt_Pric_Date` |
| `cc` | 类型资金成本：`t99_deri_comp_type_fnd_cost_ref` | 合约类型；输入限定OTC部门 | 起息／到息区间展开后，匹配`info.Strt_Pric_Date` |

因此有两点不能照搬价差的理解：

- **基准的回退侧是“合约类型”，不是“客户＋合约类型”**。别名虽然同以`c_`开头，`c_ba`的JOIN中并没有客户号。
- **合约基准不是按计提日挑当时生效版本**。若同合约有多条符合筛选的基准行，这一段没有自动选最新，也没有去重；不能把它画成与合约价差相同的历史版本线。

合约级价差、基准在这里都用T99的`Inr_Comp_No`连接销售主信息的`Agt_Id`。它们自己的`Agt_Id!=''`是身份识别成功的筛选条件，不要因同名就改成两个`Agt_Id`相连。

依据：[118141冻结SQL](../04_经营系数_价差/99_证据/证据_118141.sql)，L304–398。各输入的来源分区、删除过滤和生产规则分别保留在对应专题中，不概括成一种通用过滤规则。

## 四、普通收入中的价差与基准怎样组合

先排除已命中特殊分支的情况。对普通OPTION／TRS，可以把原CASE读成“价差贡献＋基准贡献”，但两项各自看自己的计算类型。

| 价差方式 | 基准方式 | 期初定价日 | 后续有效计提日 |
| --- | --- | --- | --- |
| 年化 | 年化 | 当日年化价差＋当日年化基准 | 当日年化价差＋当日年化基准 |
| 年化 | 绝对 | 当日年化价差＋一次性绝对基准 | 仅当日年化价差 |
| 绝对 | 年化 | 一次性绝对价差＋当日年化基准 | 仅当日年化基准 |
| 绝对 | 绝对 | 两项一次性金额相加 | 0 |

两种计算方式的区别是：

- **年化项**：`当日动态名义本金 × 年化系数 ÷ 365`，计提日须在期初定价日至提前终止日／期末定价日之间，含首尾。
- **绝对项**：`初始名义本金 × 绝对系数`，仅在期初定价日计算一次。

构造例子：动态本金365万元，年化价差0.6%，年化基准0.2%，当日符合普通分支及计提区间，则价差贡献60元、基准贡献20元，当日CASE算得80元。这还不是某位人员最后分到的金额，也不是已支付金额。

“基准加上去”不等于任何情况都有收入。价差类型和系数、基准类型和系数都是分别COALESCE，NULL才回退；它们不是整套参数替换。普通公式给缺失价差类型默认ABSOLUTE，但没有给缺失基准类型同样的默认：基准类型不匹配年化或绝对时，普通CASE可能落空为NULL。

上述表格假设类型、金额都可正常参与计算。空串不是NULL，数值运算遇到NULL也不自动变成0；具体缺失处理要按原表达式看。[原始CASE见L227–248](../04_经营系数_价差/99_证据/证据_118141.sql)。

这里还有一个两侧不对称的处理：价差输入先把计算类型的空串转成NULL，因而可触发回退；基准输入的`Calc_Type`却原样读取，合约基准类型为空串时会挡住类型级回退。不要把“空串不回退”不分字段地套到所有输入上。

## 五、资金成本不是在普通公式后面再减一次

在这份118141 SQL中，普通OPTION／TRS四种组合没有统一追加`－资金成本`。资金成本参数出现在更靠前的指定分支：

- AIRBAG非抵扣分支：从经换算的费率中减去`cc.capital_cost`，再结合本金、保证金比例等计算。
- 金仕达分支：在利息、交易收入与交易成本组成的金额里，减去`det.Fnd_Cost × cc.capital_cost / 365`，之后整体乘0.5。

这里两个“资金成本”不能只凭名字理解：`cc.capital_cost`取自T99参数表的`Fnd_Cost`，在公式中按年化成本率使用；`det.Fnd_Cost`取自逐日明细里的金仕达`occupy_cost`源值，在此作为与成本率相乘的计费基数。源字段注释为“用资成本”，仅凭这些静态证据还不能确认维护单位或把它直接叫作本金。具体来源与构造例子见[资金成本专题](../06_经营系数_资金成本/README.md)，不把相乘后的成本金额倒称为任一原字段。

## 六、提前结束为什么可能需要重算

对上面的普通年化分支，提前终止会改变有效计提区间，部分终止可能改变逐日本金，因此受影响日期的收入会变化；并非自动把此前所有收入作废。

需要把三个问题分开：

1. **公式是否受影响**：年化项看有效日期和动态本金；期初一次计算的绝对项不能简单照搬年化逻辑。
2. **加工是否覆盖受影响日期**：107491一次展开有回看窗口，不能只因看到公式就断言任意久远的历史已自动修正。
3. **已经支付的钱怎么办**：结算、支付、退补不由这段收入计算SQL单独证明。

本节只是把“计提”的含义接回数据加工，不把SQL口径提升为适用于所有产品的制度。
