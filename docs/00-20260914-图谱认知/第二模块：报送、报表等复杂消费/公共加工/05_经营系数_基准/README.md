# 基准：一份合约怎样选到系数、算出基准收入

按正在阅读的收入选择入口：本页沿118141串起合约基准、类型基准和每日40元；[对内与香港基准](06_对内与香港基准.md)补齐内部基础系数／基础收益率／分类映射及香港类型基准。对内的基础系数是额外乘数，香港类型侧没有日期展开，不能套用本页118141的整套匹配规则。

**这里解决两个问题：这份合约使用哪一个基准系数，这个系数怎样参与销售收入计算。** OIS维护计算方式和系数，133055／133056把它们整理进T99参数表，118141再按合约或类型匹配。生产SQL传递已有系数，没有从行情计算利率。

先分清两个值：`0.004`是系数；本金365万元按它年化计算，`3,650,000 × 0.004 ÷ 365 = 40元`才是某一天的基准收入项。目标DDL把系数叫“基础收益率”，仅凭这个名称不能认定其市场利率或业务制度含义。

## 第一遍，跟着一份普通期权读

沿用[118141收入主线](../../销售与经营分析/118141_交叉销售收入/README.md)中的构造合约`OPT_DEMO`。这里补出它的基准来源和选择过程，再把结果接回收入主线。金额假设为人民币元，不是真实记录；每路连接先只安排一条匹配记录。

| 已有资料 | 本例值 | 从哪里来、接下来做什么 |
| --- | --- | --- |
| 合约号、经营类别 | `OPT_DEMO`、`OPTION_STOCK` | 合约主信息`info.Agt_Id / Contr_Type_Cd`，用于匹配参数 |
| 期初／期末定价日 | 2026-09-18／2026-09-20；无提前终止 | 合约主信息，决定普通年化收入的计入区间 |
| 初始本金、逐日本金 | 初始365万元；18—20日动态本金各365万元，21日为0 | 初始本金来自主信息，逐日本金来自107491 |
| 合约基准源记录 | 合约号`OPT_DEMO`，`ANNUALIZED`，`0.004`，未删除 | OIS合约基础系数，下面追它怎样成为可用参数 |
| 类型基准 | 第一遍没有匹配记录 | 正常路径之后，再加入类型参数，观察回退 |
| 已选价差、本次加工日 | 年化`0.006`；2026-09-21 | 与118141主线一致；本专题不重复展开价差生产 |

本例按普通OPTION分支计算，未先命中AIRBAG等特殊分支。

```text
OIS单笔合约配置 → 01识别合约身份 → 合约T99 → 03按原合约号匹配 → s_ba
OIS合约类型配置 → 02保留类型及日期 → 类型T99 → 04按类型+期初日匹配 → c_ba
                                  两路并列提供参数
                                         ↓
                    118141同一层SELECT：分别选择类型、系数
                              ├─ 展示年化／绝对基准系数
                              └─ 与本金、日期进入收入CASE
```

03、04在118141的FROM中关联，展示和金额表达式在同一SELECT中使用它们。**收入CASE直接读取两路参数，不是先读取展示列`Annu_Base / Absl_Base`再算钱。**

第一遍先看[01的身份与参数](01_合约级基准生产_133055.sql)，再看[03的匹配条件](03_合约基准匹配_118141.sql)，最后对应[118141的普通期权收入分支](../../销售与经营分析/118141_交叉销售收入/02_原始当日收入.sql)。类型备用参数放在正常路径之后。

## 一、0.004已经在源记录里，01还要加工什么？

它要把“按原合约号维护的一条参数”补成“能够识别业务身份的参数”。主体是配置记录，不是全部合约；没有维护配置的合约不会由本任务自动生成基准。

[01合约级生产](01_合约级基准生产_133055.sql)的连接都围绕这件事：

| 输入 | 为什么读它 | 本例怎样匹配 |
| --- | --- | --- |
| A：`O_CONTRACT_BASE_RATE`合约基础系数 | 提供原合约号、计算方式、系数、经办和奖励 | `CONTRACT_CODE=OPT_DEMO`，系数`0.004` |
| B：`D_TRD_OTC_TRADE`交易表 | 原合约号换成TIT内部交易流水号 | `INTERNAL_TRADE_ID=OPT_DEMO` → `KEY_OTC_TRADE_ID=TIT_DEMO` |
| C：`D_REF_TRS`互换表 | 检查该流水号是否属于互换 | 本例未匹配 |
| D：`D_REF_OTC_OPTION_DEAL`期权表 | 检查该流水号是否属于期权 | 本例匹配`TIT_DEMO` |
| E：`D_KS_TRADE_COMFIRM_INFO`金仕达确认书 | 金仕达按原合约号识别，不经过B转换 | 本例未匹配 |

源表均取`${data_day_str}`指定的快照。身份CASE按**互换 → 期权 → 金仕达**判断；本例命中期权后，输出到`PDATA_N.T99_DERI_COMP_BASE_COEF_REF`：

| 源值／判断 | T99字段 | 本例结果及后续用途 |
| --- | --- | --- |
| D匹配到期权，取B的交易流水号 | `Agt_Id / Agt_Modifr` | `TIT_DEMO / 20207`；识别后的身份 |
| `A.CONTRACT_CODE`原值 | `Inr_Comp_No` | `OPT_DEMO`；保留原合约号，供118141连接 |
| `A.BASE_CALCULATION`原值 | `Calc_Type` | `ANNUALIZED`，即年化 |
| `A.BASE_AWARD_RATE`原值 | `Base_Yield` | `0.004`；不除以100 |
| 本分支固定值 | `Coef_Type` | `CROSS`；交叉销售 |
| `A.IS_DELETED=N` | `Del_Flag` | `0`；本任务转换标志，下游才过滤 |

**这一步没有重算0.004，改变的是参数的身份和字段表达。** 每一行仍是源配置及其身份匹配结果。LEFT JOIN保留未识别的配置；右侧重复可能扩行，不能当作已验证的一合约一行。

## 二、03怎样把这条参数配回销售合约？

[03合约基准匹配](03_合约基准匹配_118141.sql)先限定来源分区、`Del_Flag='0'`、`Agt_Id!=''`，再用原合约号连接：

```text
参数T99.Agt_Id = TIT_DEMO      → 非空，身份筛选通过
参数T99.Inr_Comp_No = OPT_DEMO → 改名为s_ba.Contract_Code
销售主信息info.Agt_Id = OPT_DEMO
                       ↓ 原合约号相等
s_ba.BASE_CALCULATION = ANNUALIZED
s_ba.BASE_AWARD_RATE  = 0.004
```

这里两张表的`Agt_Id`承载的编号不同。**不能把T99的`TIT_DEMO`直接连到销售表的`OPT_DEMO`。** 真实ON条件是`Inr_Comp_No`改名后的`Contract_Code = info.Agt_Id`。

合约基准没有计提日、期初日或“更新时间最新一条”的版本选择。通过筛选的参数可以匹配本次输入中该合约的多条计提日记录。

未识别的配置在01仍会落表，但03会将其排除；118141用LEFT JOIN，缺少合约基准本身不会删掉合约日，接下来还能尝试类型基准回退。

## 三、选中的0.004，怎样变成每天40元？

118141对两个字段分别选择：

```text
计算类型 = COALESCE(s_ba.BASE_CALCULATION, c_ba.BASE_CALCULATION)
基准系数 = COALESCE(s_ba.BASE_AWARD_RATE,  c_ba.BASE_AWARD_RATE)
```

本例合约侧已有年化和0.004，类型侧未匹配，因此两项都取合约侧。接下来，同一SELECT有两个用途：

| 用在哪里 | 本例结果 | 对应SQL |
| --- | --- | --- |
| 展示参数 | `Annu_Base=0.004`；`Absl_Base=''` | [118141合约日与资料](../../销售与经营分析/118141_交叉销售收入/01_合约日与资料.sql)；本目录[05](05_基准选择与奖励展示_118141.sql)只保留定位入口，不复制表达式 |
| 计算原始当日收入 | 年化基准项为`动态本金 × 0.004 ÷ 365` | [118141原始当日收入](../../销售与经营分析/118141_交叉销售收入/02_原始当日收入.sql)的普通OPTION、双年化分支 |

普通年化项仅在`计提日 BETWEEN 期初日 AND COALESCE(提前终止日,期末日)`时计算，包含首尾：

| 计提日 | 动态本金 | 基准项 | 价差项 | 原始当日收入 |
| --- | ---: | ---: | ---: | ---: |
| 9月18日 | 3,650,000 | 40 | 60 | 100 |
| 9月19日 | 3,650,000 | 40 | 60 | 100 |
| 9月20日 | 3,650,000 | 40 | 60 | 100 |
| 9月21日 | 0 | 0 | 0 | 0 |

“基准项”是为读懂公式拆出的金额，不是本查询另行输出的同名字段。0.004按0.4%参与公式；把显示数字0.4直接代入会得到不同金额。

至此，已经走完**源配置0.004 → 合约匹配0.004 → 年化基准40元 → 与价差60元合成原始100元**。继续看[118141主脚本](../../销售与经营分析/118141_交叉销售收入/00_主脚本.sql)的收入调整、分配和累计：同一示例在9月20日还触发保底，把当日收入调整为3,450元。因此这里的100元不是最终日报金额，也不是已支付金额。

## 四、合约参数缺了，类型参数怎样接上？

现在给同一份`OPT_DEMO`增加一条备用配置，合约、日期和本金保持不变。这是变例输入，第一遍的118141样板没有匹配类型参数。

### 02只把一条类型配置写入T99

[02类型级生产](02_类型级基准生产_133056.sql)没有JOIN。假设OIS维护下面一条记录，生产后仍是一条类型配置：

| OIS实际源字段 | 本例值 | T99目标字段 |
| --- | --- | --- |
| `CONTRACT_TYPE` | `OPTION_STOCK` | `Src_Comp_Type_Cd` |
| `BASE_CALCULATION` | `ABSOLUTE`（绝对） | `Calc_Type` |
| `BASE_AWARD_RATE` | `0.003` | `Base_Yield` |
| `DEPARTMENT` | `OTC` | `Src_Dept_No` |
| `CONTRACT_START_DATE_MIN / MAX` | 2026-09-16／2026-09-30 | `Bgng_Prcg_Date_Llmt / Ulmt` |
| `IS_DELETED` | `N` | `Del_Flag=0` |

目标是`PDATA_N.T99_DERI_COMP_TYPE_BASE_COEF_REF`。配置按合约类型维护，没有客户号；下游别名`c_ba`指类型基准。

### 04把适用区间展开，再用合约期初日匹配

[04类型基准适用期](04_类型基准适用期_118141.sql)负责三个连在一起的小步骤，保留在一份SQL中：

```text
① 留下来源正确、未删除、部门为OTC的类型配置
   OPTION_STOCK / ABSOLUTE / 0.003 / 9月16日—30日
                          ↓
② 展开可适用的期初日：一条配置 → 15条日期记录
   OPTION_STOCK / 9月16日 / ABSOLUTE / 0.003
   OPTION_STOCK / 9月17日 / ABSOLUTE / 0.003
   OPTION_STOCK / 9月18日 / ABSOLUTE / 0.003  ← 本例匹配这条
   ……直到9月30日
                          ↓
③ 类型相同，并且展开日期 = info.Strt_Pric_Date（9月18日）
   c_ba.BASE_CALCULATION = ABSOLUTE；c_ba.BASE_AWARD_RATE = 0.003
```

展开后的`c_ba.busi_date`表示**可以适用的合约期初定价日**。本例算9月19日、20日收入时，仍拿9月18日去匹配；不会因为计提日变化而在类型配置中换档。

`EFFECTIVE_DATE`虽然写成`Vld_Date`，本段匹配没有用它；`BUSINESS_TYPE / UNDERLYING_TYPE`也会写成`Busi_Type / Src_Undrl_Type_Cd`，本段连接同样未使用。这些字段存在，不代表都参与参数选择。

## 五、“合约优先”具体优先什么？

以上述变例为起点：合约侧是**年化0.004**，类型侧是**绝对0.003**。两路都匹配时仍取合约侧，原始收入保持每天100元。下面各行都独立从这组输入出发，只改变所列条件：

| 改变什么 | 最终计算类型／系数 | 基准项在9月18日／19日 | 为什么 |
| --- | --- | --- | --- |
| 不变 | 年化／0.004 | 40／40 | 两个字段都由合约侧提供 |
| 合约系数改为NULL | 年化／0.003 | 30／30 | 类型仍用合约的年化；只有系数回退 |
| 合约计算类型改为NULL | 绝对／0.004 | 14,600／0 | 类型从类型侧取绝对；系数仍取合约0.004 |
| 该合约配置不再匹配 | 绝对／0.003 | 10,950／0 | 两个合约侧字段都为NULL，分别回退 |
| 合约系数改为0 | 年化／0 | 0／0 | 0是已有值，不能触发回退 |
| 合约计算类型改为空串 | 空串／0.004 | 普通收入CASE未命中 | 空串不是NULL，没有回退 |

所以回退单位是**字段**，两个字段可能取自不同来源。本例价差始终年化60元，基准绝对0.003时，原始收入是期初日`60+10,950`、次日`60`；基准年化0.003时则是每天`60+30=90`。

普通OPTION／TRS的四种组合，实质是分别计算价差项和基准项，再相加：

| 单项的计算类型 | 取哪个本金 | 什么时候计算 |
| --- | --- | --- |
| `ANNUALIZED`年化 | `det.Dyna_Nom_Prin`动态本金 | 期初至结束日闭区间内，每天`本金 × 系数 ÷ 365` |
| `ABSOLUTE`绝对 | `info.Init_Nom_Prin`初始本金 | 仅期初日一次，`本金 × 系数`；其他日期为0 |

基准计算类型没有默认`ABSOLUTE`。两路计算类型都缺失时，若未先命中特殊分支，原收入CASE没有ELSE，会返回NULL；金额表达式里的系数补0不能使未命中的分支生效。相反，计算类型有效但两路系数均为NULL时，普通公式内才会把该系数补0。

## 六、看懂正常路径后，再核对这些差异

### 一行代表什么，哪里会变多？

| 所处位置 | 当前记录含义 | 行数变化点 |
| --- | --- | --- |
| 01合约生产 | 源配置及身份匹配结果 | B、C、D等右侧多条匹配可能扩行；只有E对确认书号做DISTINCT |
| 02类型生产 | 源类型配置的字段映射 | 没有JOIN，不在这里展开日期 |
| 04内部展开 | 类型配置＋一个可适用期初日 | 正常区间按天展开、含首尾；重叠配置仍保留 |
| 118141匹配后 | 原合约日及匹配到的两路参数 | 同合约多条配置、同类型重叠区间都可能扩行，没有统一择一或去重 |

两路都用LEFT JOIN。即使合约参数已有完整值，类型侧重复匹配也仍可能扩行；COALESCE只选字段值，不能消除重复行，更不能保证后续累计正确。

### 三种日期分别管什么？

| 日期 | 作用 |
| --- | --- |
| 源快照参数日`${data_day_str}` | 133055／133056读取哪天的源记录；目标按`SRC_TBL`分区覆盖，不按业务日保留参数版本 |
| `info.Strt_Pric_Date`期初定价日 | 选择类型基准；合约基准不按此日或计提日挑版本 |
| `det.busi_date`计提日 | 决定收入算在哪一天、是否处于普通公式的计入范围；不是到账日 |

类型日期下限`1900-01-01`会替换为`2019-01-01`，上限`2999-12-31`会替换为运行变量`${yyyy-MM-dd}`，并非无限历史／未来；空值、逆向区间的Hive行为未由本地示例验证。

提前终止会改变年化项截止日，动态本金变化会改变当日金额。历史是否重跑、已付金额如何退补，不能从这段SQL推断；绝对项的期初一次计算也不能直接解释为均摊。

### 额外奖励有没有加进收入？

`A.ADDITIONAL_REWARD → T99.Adtnl_Rwd → s_ba.additional_reward → 118141.Adtnl_Rwd`：03将空串改为0，SELECT展示时再将NULL补0，最后输出此列。`HAVE_ADDITIONAL_REWARD → Adtnl_Rwd_Flag → have_additional_reward`也被带出，但没有控制这里的展示。

**这份冻结SQL的当日收入CASE和上层销售收入调整没有把额外奖励加进去。** 有读取、有输出，不能据此认定已计入销售收入；未核验的后续用途不在这里补猜。

### 同一张合约T99为什么还有133054？

| 生产任务 | 源分区 | 系数类型／系数来源 | 118141本处是否读取 |
| --- | --- | --- | --- |
| 133055 | `ODATA_N_OIS.O_CONTRACT_BASE_RATE` | `CROSS / BASE_AWARD_RATE` | 是 |
| 133054 | `ODATA_N_OIS.G_INR_CONTRACT_BASE_RATE` | `INR / BASE_EARNING_RATE` | 否 |

133054将`DRAFT_BASE_RATE`写入`Dft_Base_Coef`，两列额外奖励填空串；133055将`Dft_Base_Coef`填空串，并传递奖励。它们写同表不同来源分区，不能互换。保留[133054完整证据](99_证据/证据_133054.sql)供对照。

两路生产还传递描述、维护人、维护时间和加工标识。合约侧将`OPERATOR_NAME / INTRODUCTION_OPERATOR_NAME`写成`Main_Oper_Prsn / Intro_Oper_Prsn`，本专题的118141基准匹配未从这些列取经办归属。
