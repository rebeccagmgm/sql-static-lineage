## 4. 复杂业务模块：每块回答一个问题

| 模块 | 问题 | 输入与输出粒度 | 重要规则 |
| --- | --- | --- | --- |
| 期权 / 互换分类 | 合约属于哪个经营类别？ | 使用主查询当前行中的类型、标的、条款、开始日、账簿等属性，输出代码和名称；不新增JOIN | 原样保留先后命中、日期分界、NULL和兜底；同一代码在新旧规则下可能对应不同中文名 |
| 期权条款 | 敲入、敲出、执行价、参与率是什么？ | 条款来源分别按交易键聚合；结算、首条费率保留各自原粒度 | 04_期权条款.sql中保留多个命名CTE，主脚本分别连接，避免先合成大表而改变行数 |
| 普通互换初始持仓 | 初始本金和标的从哪里来？ | 每腿+标的取快照内最早可见持仓，连工具后按腿汇总 | 初始价格×初始数量；工具等维表的连接仍在聚合之前 |
| 普通互换当日持仓 | 当日动态本金是多少？ | 加工日持仓按腿汇总 | 初始价格×当前数量；仍通过初始持仓的腿键连接 |
| FAST初始持仓 | 每个工具的初始本金是多少？ | EOD_POSITION，每工具+wind_code取最早记录，再按工具汇总 | 汇总源dynamic_notional；不是统一的签约当日本金 |
| FAST当日持仓 | 每个工具的当日本金是多少？ | EOD_POSITION且源业务日为加工日，按工具汇总 | 初始、当日结果各自连接交易工具键 |
| 金仕达最新确认及标的 | 采用哪条确认，展示哪些标的？ | 确认按确认键选最新；持仓按确认键+标的选最新，再按确认键汇总 | 保持原排序，并列日期没有新增裁决规则 |
| 本金汇率 | 哪个金额乘哪个汇率，何时归零？ | 在当前结果行计算，不新增聚合和连接 | 保留原币种条件、日期范围、空值及类型 |

本次先把完整原逻辑分离出来。01、02的分类代码与名称仍保留各自CASE，集中在同一模块中；尚未改写为一次rule_id判断。03、04分类和金额很短，直接留在各自字段映射中。

## 5. 阅读文件怎样变成执行文件

原 `branches` 现为 `03_分支主脚本`：平时阅读和维护的入口，保留主线并引用业务模块。原 `expanded` 现为 `05_完整SQL`：把主脚本及所引用模块展开合并的生成结果，不要手工修改。复杂公式并未删除，只是不必在读主线时同时阅读。

分支SQL里的“-- @include”由本地 render.mjs 展开；它不是Hive自带语法。模块中的CTE和表达式会合回同一条查询，因此产品模块不需要新增数据库视图，也不需要新增调度任务。

在 sql 目录执行：

~~~powershell
node render.mjs --write
node --test checks/refactor.test.mjs checks/option-stages.test.mjs
~~~

第一条命令生成 `05_完整SQL` 里的四份完整SQL，保留原来的加工日、任务名等调度占位符；命令不连接数据库、不执行SQL。真实运行前，需要在目标schema建立三个公共视图，再由原调度参数执行对应展开SQL。

## 6. 核对范围与待确认项

本次静态核对原SQL哈希、90列输出表达式与顺序、提取的子查询、连接类型、连接键、状态过滤和分区写入。静态核对不证明Hive运行成功或业务数据逐行一致。

- 统一DDL沿用86840/86841/220650的 Futr_Type。86842原DDL相同位置写的是 Futr_Type_Cd；四份查询均按原90列顺序输出，部署前需核对真实目标表定义。
- 不假定交易键、客户键或保证金属性唯一，不增加DISTINCT或去重。
- collect_list/collect_set的拼接顺序和窗口排序并列仍沿用原SQL；执行计划变化可能改变未规定的顺序。
- 上线验证应覆盖旧规则、新规则及缺失数据场景，核对行数、逐行多集合差异、分类、金额和空值。

来源基准为2026-09-18发布绑定SQL；各任务SHA和来源见 [manifest.json](sql/manifest.json) 与 [原证据索引](../99_证据/README.md)。
