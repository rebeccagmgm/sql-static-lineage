# 从主脚本读起

## 先看01期权的三阶段试点

本轮只改期权，其他分支仍是原来的组织方式。先打开[01期权目录与加工关系](04_业务模块/01_期权/README.md)：公共输入 → 核心加工 → 补充关联 → 金额与输出。九份SQL已按这四层分子文件夹，不再平铺。核心加工依次阅读下面三份文件：

1. [02_合约基础](04_业务模块/01_期权/02_核心加工/02_合约基础.sql)：合格交易、期权合约、结构和源类型字典 → `option_base`。状态过滤在这里；不保证一合约一行。
2. [03_标的及篮子](04_业务模块/01_期权/02_核心加工/03_标的及篮子.sql)：承接基础记录，关联证券、期货、篮子、工具池和标的字典 → `option_underlying`。输出已识别的标的属性。
3. [09_经营分类](04_业务模块/01_期权/02_核心加工/09_经营分类.sql)：只读上一阶段的字段，按新旧规则逐行产生代码和名称 → `option_classified`。

阶段之间直接承接记录，不按合约号重新拼回。分类使用的证券集与展示时BOND改写后的源标的类型分别保留。主脚本后半段仍有15个关联，客户/保证金、条款、估值及本金尚未改成阶段式；12模块只保存原客户与保证金来源。

~~~powershell
# 本轮只展开01，不覆盖其他分支的完整SQL
node render.mjs --write 01_期权
node --test --test-name-pattern='01|shared views|include expansion' checks/refactor.test.mjs checks/option-stages.test.mjs
~~~

核对包括阶段输出穿透后的90列表达式、原子查询和关联条件，以及内存SQLite合成数据的多集合对照（重复行、缺失资料、新旧日期、空字符串）。SQLite仅验证本次重组的关系与表达式，不替代Hive类型/执行计划及真实数据回归。原始SQL快照不修改。

## 展开和检查

~~~powershell
# 在本目录执行；Node内置模块，无第三方依赖
node render.mjs --write
node --test checks/refactor.test.mjs checks/option-stages.test.mjs

# 只将一个分支输出到终端
node render.mjs 02_普通互换
~~~

`03_分支主脚本`（原branches）是阅读和修改入口，其中的 @include 需要展开。`05_完整SQL`（原expanded）是自动合并主脚本和模块的结果，不再有文件引用，仍保留调度占位符。`02_公共视图` 是需要预先创建的三个公共视图；产品模块只是同一条SQL内的CTE/表达式，不新增调度节点。

`06_原始SQL` 是本次冻结源SQL，manifest记录原始SHA。完整检查覆盖四个分支；任一分支输入不完整时应先修复该分支，再做全量展开。本次另对01做本地合成数据对照，尚未在Hive执行。

## 维护约定

1. 修改 `03_分支主脚本` 或 `04_业务模块` 后重新运行render；`05_完整SQL` 仅为派生产物，不手工修改。
2. 分类代码和名称的原始CASE集中存放，未合并为rule_id。
3. 不改变原来的窗口并列排序、列表拼接顺序、聚合前维表JOIN和NULL处理。
4. 目标DDL存在一处历史分歧：86842使用Futr_Type_Cd，其余三份使用Futr_Type；本地统一DDL采用后者，部署前需要核对真实表。
