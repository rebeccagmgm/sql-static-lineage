# 03 金仕达：按业务问题逐步读 SQL

这条分支把**交易确认书、挂钩标的、境内客户**拼成销售基础资料，写入加工日的 `grp_id=03` 分区。它不经过普通互换的交易账簿筛选，也不把持仓数量乘价格作为本分支本金。

先抓住两个区别：**确认书ID不是主合约编号；持仓用于识别标的，本金直接取确认书。**

## 1. 四个文件怎么读

保持现有四份SQL平铺，不增加子文件夹。复杂子查询已经在文件内部拆成有名字的步骤，**先按问题读文件，再按步骤读SQL**。

推荐顺序：**02先认确认书 → 03看标的怎么形成 → 01补客户 → 主脚本看怎么连接 → 11看分类和本金。**

| 文件 | 要解决的问题 | 结果在哪里使用 |
| --- | --- | --- |
| [02_合约及来源属性](02_合约及来源属性.sql) | 选哪条确认书记录？ | 排序 → 选最新；`a`提供合约、日期、本金，旁边的`sct`提供类型中文名 |
| [03_标的及篮子](03_标的及篮子.sql) | 这张确认书挂钩哪些标的？ | 排序 → 选最新 → 补证券 → 按确认书汇总为`ins`；不是期权篮子算法 |
| [01_公共资料](01_公共资料.sql) | 客户名称、行业、资质从哪里来？ | `cp`仅取公共客户的境内来源 |
| [11_输出字段](11_输出字段.sql) | 怎么分类、取本金、填90列？ | 分类及金额规则短，直接写在本文件，不另拆09/10 |

[主脚本](../00_分支主脚本/03_金仕达.sql)保留所有连接和最终过滤；[完整SQL](../../05_完整SQL/03_金仕达.sql)用于连续核读，不手改。

~~~text
02 交易确认书：每确认书取最新业务日期 ── a ──────────────┐
03 日终持仓：每确认书+标的取最新持仓日期，再汇总 ── ins ─┤
01 境内客户：确认书counterparty_id → 客户client_id ─ cp ─┤
02 类型字典：确认书trs_type → CD382代码 ───────── sct ───┘
                                                        ↓
                                    主脚本筛范围 → 11排列90列 → 写入03分区
~~~

这些是来源和依赖关系，不是数据库执行顺序。客户和字典没有在这里去重，最终不保证每张确认书只有一行。

## 2. 第一站：确认书，不是主合约

这里决定“拿哪条确认书记录作为后续加工起点”。同一主合约下可能有不同确认书，不能只按主合约号去重。

| 字段                     | 原始含义       | 本SQL用途                                      |
| ---------------------- | ---------- | ------------------------------------------- |
| `key_trade_comfirm_id` | 金仕达交易确认书ID | 选最新记录、关联持仓；写入目标合约编号 `Agt_Id`                |
| `contract_code`        | 主合约编号      | 同时写入 `Inr_Seri_No` 和 `Ext_Comp_No`，不是上述确认书键 |
| `counterparty_id`      | 交易对手       | 直接接境内客户 `client_id`，不经过TITANS客户映射           |

表名及字段中的 `comfirm`、`postion` 是现有物理拼写，照原SQL保留。

- **最新确认书**：读 `d_ks_trade_comfirm_info` 的加工日快照，按确认书ID分组，取 `business_date` 倒序第一条。然后主脚本才筛合约状态、起始日；不是“先筛有效，再挑最新有效记录”。
- **最新持仓标的**：读 `d_ks_trs_eod_postion` 的加工日快照，按“确认书ID＋标的WIND代码”分组，取 `src_busi_date` 倒序第一条。没有要求持仓日期就是加工日，也没有数量非零条件。
- 两套排序互相独立；一张确认书下的不同标的可能选到不同日期。排序日期并列时均没有进一步的裁决条件。

### 02文件内部的两步

~~~text
ranked_confirmations（给记录排先后） → latest_confirmation（取rn=1）
                                                       ↓
                                            主脚本再筛状态和起始日
~~~

例如同一确认书旧记录是EFFECTIVE、最新记录是CANCELLED，按原规则会被排除；不会回退到旧的有效记录。这个顺序是业务口径的一部分。

## 3. 第二站：把持仓整理成标的清单

原来嵌套的子查询已拆为四个具名步骤，字段来源与中文含义就在各步旁边：

| 步骤 | 输入是什么 | 做什么 | 输出粒度 |
| --- | --- | --- | --- |
| ① `ranked_positions` | 加工日快照的日终持仓 | 按确认书＋WIND代码分组，持仓日期倒序编号 | 仍是持仓记录，多一个rn |
| ② `latest_positions` | 已排序的持仓 | 只取rn=1，留下确认书ID、代码、名称 | 每确认书＋WIND代码一条 |
| ③ `position_details` | 最新持仓标的 | 按WIND代码补证券资料，再按证券集查类型中文名 | 保留实际连接结果，可能一对多 |
| ④ `underlying_summary` | 已补资料的标的 | 按确认书拼接代码、名称、类型、币种 | 每确认书一组清单 |

③输出的字段没有重新计算：`un_code/un_name`来自持仓；`ins_lng_desc/ins_family/currency`来自证券表；`dw_cd_val_desc`来自字典。④只用这些明确的输入汇总，不再嵌套三层查询。

举个阅读示例（不是实际业务数据）：确认书C1下，标的W1最新持仓日是16日，W2是15日。18日加工快照中两者都能被选中，最终是一组“W1;W2”；不是只保留16日或18日的标的。


`03`从日终持仓取标的WIND代码和名称，再按WIND代码连接证券基本信息，补证券全名、证券集、币种，并查CD128类型描述。最后按确认书ID汇总：

- 代码、名称、全名用分号拼接；证券集、类型、币种用逗号去重拼接。没有排序保证，不能按拼接位置一一配对。
- 标的内部ID和标的类型描述固定为空串，不是查到后遗漏。
- 证券匹配不是按证券内码，未证明WIND代码唯一；多条匹配可能重复展示名称。
- 主脚本虽然用LEFT JOIN，但最后要求 `ins.Undrl_Wd_Cd IS NOT NULL`，所以没有匹配标的汇总的确认书会被排除；这不等于拒绝空字符串。

这份持仓模块不计算初始本金、动态本金或市值。不要把它套成普通互换的07/08算法。

## 4. 第三站：连客户，再看分类和本金

客户是并列补充资料：`a.counterparty_id → cp.client_id`。不需要经过TITANS客户映射，也不影响本金来源。源类型字典则按`a.trs_type → sct.dw_cd_val`补中文名；二者的LEFT JOIN均保留缺失侧。

### 11先看三处，不必从90列逐列猜

1. **经营分类**：只判断确认书上的`trs_type`，不是按持仓的证券类型分类。
2. **04 本金**：看初始和动态本金选哪个确认书字段。
3. **09 固定值**：看哪些字段没有查来源表，而是原SQL直接写死。

常规字段保留行末中文释义；期权专属字段在此都填NULL，可先跳过该段。输出列的排列顺序不能为了阅读重新排序。

### 分类与本金对照

| 确认书的源互换类型 | 经营类别代码／名称 | 初始名义本金 | 动态名义本金 |
| --- | --- | --- | --- |
| `B_LONG_SHORT_SWAP` | `TRS_KINGSTAR_SWAP`／金仕达多空互换 | `a.dynamic_notional` | `a.dynamic_notional` |
| 其他（包括条件未命中） | `TRS_LONG_SHORT`／多空互换 | `a.notional` | `a.dynamic_notional` |

这说明特殊类型的“初始名义本金”与“动态名义本金”取同一源字段，不能只按目标名字反推金额口径。本分支没有普通互换的2025日期分界，也没有期权的动态本金日期区间判断。

人民币汇率输出NULL，绝对名义本金固定字符串 `'0.0'`；这里不做汇率换算、不把源本金空值补0。结算币种虽固定输出CNY，**仅凭本段SQL不能证明上游金额已经折成人民币**。

## 5. 最后一站：哪些记录留下，哪些输出是固定的

客户展示字段取自公共境内客户，而不是确认书中现成的 `counterparty_name`、`abbreviation` 等字段。缺失客户仍保留确认书；同号客户多条则可能扩展结果。

主脚本保留：
`EFFECTIVE / EFFECTIVE_PENDING / TERMINATED / TERMINATING / TERMINATING_PENDING`，
并要求 `a.start_date` 非NULL。包含已终止状态，不能简称“仅存续合约”。

| 输出项 | 实际来源或规则 |
| --- | --- |
| 期初/期末定价日、提前终止日 | 确认书 `start_date / end_date / early_termination_date` |
| 初始保证金比例 | 确认书 `mgr_rate`，源注释“履保比例”，未注明单位 |
| 账簿／柜台 | 固定 `10023 / OTC-互换-金仕达合约 / PORTFOLIO_SWAP`，不读取确认书账簿字段 |
| 销售方编号 | 固定 `TIT060-10142`；与买卖方向按 `a.seller` 判断是两套规则 |
| 来源码／部门／结算币种 | 固定 `TIT / OTC / CNY`；来源码TIT不能当作从TITANS合约表起算的证据 |
| 期权条款、利率等NULL字段 | 本分支SQL未提供，不代表其他系统也没有这些业务信息 |

## 6. 证据与维护

逻辑依据是[原始86842 SQL](../../06_原始SQL/86842.sql)，不是按字段英文猜出的规则。表及字段中文取自本地元数据SQLite的Hive同源完整表名匹配：目录构建于2026-09-16，本分支主要记录采集于2026-08-21（境内客户记录为2026-08-29，字典为2026-08-22）。这是离线证据，不是实时业务数据。

`02_合约及来源属性.sql`上一轮已按原SQL补回缺失查询。本轮只把02/03的嵌套查询改成具名步骤，主脚本的连接、最终筛选及90列表达式不变。对照检查会把新步骤还原成原始嵌套结构再逐项比较，并用本地合成样例检查选最新、缺失、重复、多确认书和金额空值等行为；不等于Hive生产环境执行或数据验收。
