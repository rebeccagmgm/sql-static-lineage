# 香港佣金：同一份合约，每天用哪个费率乘哪笔金额？

佣金配置提供的是**费率和计算方式字段**。香港日报的普通互换分支按交易金额计算佣金项，再与价差、基准贡献合计；它不把佣金当成价差，也不统一除365。

第一遍跟`HK_TRS_DEMO`走完：两路配置→按不同日期匹配→优先合约费率→回收入主线接金额。配置生产与参数查询的差异放在后面。

## 两路配置各管一件事

| 输入（均为ODATA_N_OIS） | 一行是什么 | 220979怎么选 |
| --- | --- | --- |
| `G_REV_HK_CONTRACT_COMMISSION_RATE` | 一份合约的一版佣金配置，含`effective_date` | 合约号＋收入计提日；别名`s_cr` |
| `G_REV_HKCPTY_BID_ASK_COMMISSION_RATE` | 一个客户、业务类型、标的类型及适用期初区间的配置 | 客户＋业务类型＋香港标的类型＋合约期初日；别名`c_cr` |

两路均先筛`busi_date='${yyyy-MM-dd}'`且`is_deleted='N'`。读取当日配置快照不表示收入只算当日；日报会在同一快照内回看各个计提日。

```text
合约佣金配置 → 按生效日构造版本区间 → 合约号＋计提日 ─┐
客户佣金配置 → 展开可适用期初区间 → 客户/业务/标的＋期初日 ─┤
                                                     ▼
                       coalesce(s_cr.commission_rate, c_cr.commission_rate)
                                                     │
                        香港收入主线的普通TRS分支读取费率
```

合约版本截止于下一版本生效日前一天，最后一版延至加工日。客户侧`start_date='2023-01-01'`替换为`2024-01-01`、`end_date='2999-12-31'`替换为运行日，再按天展开。日期行只是使条件可JOIN，不把费率按天摊薄。

## 沿香港主线同一份合约读完

下面全部是构造数据，参数无重复，合约未命中特殊RISKY／AIRBAGX／有关联LONG_HOLD_SWAP等前置分支。`HK_TRS_DEMO`客户为`HK_CLIENT_DEMO`，业务TRS、香港标的EQUITY、香港合约类型N_CROSS_SWAP；9月18日期初、9月20日结束、9月21日加工。

| 配置 | 匹配身份／日期 | 佣金费率 |
| --- | --- | ---: |
| 合约配置 | 合约HK_TRS_DEMO，9月18日生效，无后续版本 | 0.001 |
| 客户配置 | HK_CLIENT_DEMO＋TRS＋EQUITY，适用期初9月1日至30日 | 0.002 |

合约侧形成9月18—21日的版本行；客户侧用固定期初9月18日匹配。因此18—21日两路都命中，最终费率均优先取0.001。`commis_calc_type`虽在两路SELECT取出，220979收入CASE并没有依据它区分年化／绝对；不能看到字段名称就给佣金公式补一个÷365。

收入主线另外提供计算基数：期初日取`info.Init_Nom_Prin`；存续期其他日取`coalesce(evt.Occu_Amt,0) × info.Cny_Ex_Rate`。事件金额如何由两路交易按数量绝对值×价格汇总，详见[香港收入主线](../../销售与经营分析/220979_香港销售收入/README.md)，本页不复制金额生产。

| 计提日 | 主线交来的佣金基数 | 选中费率 | 佣金项 | 主线年化价差＋基准项 | 原始当日收入 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 9月18日 | 初始本金3,650,000 | 0.001 | 3,650 | 100 | 3,750 |
| 9月19日 | 事件365,000×汇率1 | 0.001 | 365 | 80 | 445 |
| 9月20日 | 无事件，基数0 | 0.001 | 0 | 50 | 50 |
| 9月21日 | 已超本例结束日 | 0.001仍可匹配 | 日期条件给0 | 0 | 0 |

四日累计4,245。主线继续以70%／30%／0的介绍比例形成累计2,971.5／1,273.5／0。参数能匹配到9月21日不表示佣金必须算到21日；参数适用日与收入分支的计入日期是两个条件。

### 每次只改一个条件

| 从原例改变什么 | 9月19日选中费率／佣金 | 为什么 |
| --- | --- | --- |
| 合约费率改NULL | 客户0.002／730 | 按字段回退；年化项80不变，当日收入810 |
| 合约费率改0 | 0／0 | 0是已有值；当日收入仍有年化项80 |
| 合约生效日改9月20日 | 客户0.002／730 | 19日尚无合约版本；20日起才取0.001 |
| 客户标的类型改INDEX | 合约0.001／365 | 客户侧不再匹配，合约侧完整，结果不变 |

若两路费率都缺失，原式没有第三个默认0，存续期的佣金项可能为NULL，即使事件基数为0也是`0×NULL=NULL`；同一加法中的原始收入也可能变NULL。上层累计另有COALESCE补0，须回主线区分“原始当日为空”与“累计按0加入”。普通OPTION分支不引用佣金，但多条佣金JOIN匹配仍可能扩行，不能以公式未使用便忽略重复输入。

## 224028为什么把佣金写进“价差T99”？

[01_香港合约佣金生产_224028.sql](01_香港合约佣金生产_224028.sql)是一份完整生产查询，独立写入`PDATA_N.T99_DERI_COMP_SPRD_COEF_REF`的佣金来源分区。表名含“价差”不改变这些字段的实际来源。

| 阶段 | 输入与变化 | 输出及用途 |
| --- | --- | --- |
| 读源配置 | 合约佣金源加工日快照；原费率不换算 | `CONTRACT_CODE`保留为`Inr_Comp_No`，`COMMISSION_RATE → Cms_Fee_Rate` |
| 识别身份 | 原合约号连`D_TRD_OTC_TRADE.INTERNAL_TRADE_ID`，得到`KEY_OTC_TRADE_ID` | 非空内部流水号写`Agt_Id`；没有匹配也保留源配置、写空身份 |
| 判断修饰符 | 依次检查TRS、期权、远期、FAST_TRS身份表 | 对应20206／20207／20208／20206；有先后顺序，右侧多条可扩行 |
| 写参考信息 | `COMMIS_CALC_TYPE → Sprd_Calc_Type`，费率进入佣金列，`Bel_Busi_Dept='OTC_HK'` | 年化价差、绝对价差和`Vld_Date`均填空；不是把佣金变成价差 |

```text
合约佣金ODATA ──────────────→ 220979日报按计提日选版本
       ├──────────────────→ 220981参数查询展示最新版本及历史
       └─ 224028身份映射 → 合约价差T99的佣金源分区
```

**现有220979／220981仍直接读ODATA。** 特别是224028把`Vld_Date`填空，不能用这份T99替换日报仍在使用的源`effective_date`。客户佣金源的T99生产者本轮未核验，也不影响已经确认的直接读取链；不据此断言没有生产者。

## 220981参数查询展示什么，为什么与日报不一定一样？

220981对合约佣金按`effective_date DESC`取`ROW_NUMBER=1`，并把各版配置整理为`Cms_Data`；它没有按历史计提日展开版本。客户侧仍按客户、业务、标的与期初日匹配。

- `Cms_Fee_Rate`：合约费率优先、缺失回退客户。
- `Cms_Rate_Calc_Cd`：合约计算方式优先、缺失回退客户；这只是该查询的输出，不能据此认定220979收入按它分支。
- `Cms_Data`：优先合约配置历史，没有时用客户配置构造展示内容；包含历史不等于每条都参与本日日报。

原例把合约新版本生效日改成9月20日后，220981仍可能展示该最新版，但220979的9月19日需要旧版或客户回退。两条SQL是不同的消费方式，不能以参数查询一行替代日报某日选择。
