# 价差：同一份合约，为什么每天从20元变成60元？

本目录保留一份共同的合约价差生产说明，按实际消费分开阅读：

| 正在看哪份收入 | 从哪里读 |
| --- | --- |
| 118141交叉销售收入 | 继续本页，以同一合约走通两路参数与20／60元变化 |
| 114013对内、220979香港 | [对内与香港价差](06_对内与香港价差.md)：同一合约T99怎样按INR筛选、不同后备参数怎样匹配；沿各自主线的合约算例承接 |

下文的客户类型T99和匹配键属于118141；对内后备值来自内部类型附加收益率，香港客户侧直接读香港源配置，不能将下面整套JOIN视作所有收入通用。

这块要解决的是：**给一份合约的某个计提日选出价差类型和系数，再看它在收入公式中贡献多少金额。** 不是在这里重新计算“客户报价减对冲报价”，也不是直接算销售人员拿到多少钱。

第一遍沿下面同一份合约读完，不用先打开五份SQL。参数生产的身份转换、审批信息，以及缺失／重复等情况放在后面查阅。

## 一、先把这份合约和两套参数摆出来

以下均为构造数据，不是生产记录。假设参数和客户等关联资料没有重复，记录满足各自取数条件；本例是普通期权，不命中AIRBAG等更靠前的特殊分支。

| 资料 | 本例值 | 后面用来做什么 |
| --- | --- | --- |
| 合约主信息 `info` | 合约号A1、客户C1、经营类别OPTION_STOCK、业务类型OPTION | 找合约规则，或找客户＋类型规则 |
| 定价日期 | 2026-09-10期初，09-30期末，无提前终止 | 客户参数用期初日期匹配；普通年化公式还检查计提日是否在起止区间内 |
| 逐日金额 `det.Dyna_Nom_Prin` | 09-14、15、16日动态本金均为3,650,000元 | 本例年化项按当天动态本金计算 |
| 主信息初始本金 `info.Init_Nom_Prin` | 另设为3,650,000元 | 绝对价差项使用；不是从逐日表取，也不参与本例年化价差项 |
| 本次加工日 | 2026-09-22 | 读这次源快照，并回看上述三个计提日 |

**9月22日加工，不表示收入都归9月22日。** 我们在同一次加工中，分别问9月14日、15日、16日该用什么参数；不是分别读取三个加工日的历史快照。

源系统维护了两条价差记录：

| 规则范围 | 计算方式及系数 | 日期写的是什么 |
| --- | --- | --- |
| 合约A1专属规则 | ANNUALIZED（年化），0.006，即示例中的0.6% | 从09-15生效，此前没有A1的专属记录 |
| 客户C1＋类型OPTION_STOCK规则 | ANNUALIZED（年化），0.002，即示例中的0.2% | 适用于期初定价日在09-01至09-30之间的合约 |

这两条不是相加的两笔价差。它们是两路可选参数：**先分别匹配，再逐字段优先取合约侧。** 源记录已经维护系数，生产SQL原样传递，不除以100。

## 二、两条记录先整理成参数表，再交给收入计算

[01_合约级价差生产](01_合约级价差生产_133052.sql)和[02_客户类型级价差生产](02_客户类型级价差生产_133049.sql)是两个独立任务，各自把源配置整理到一张T99参数表。T99在这里就是收入计算读取的参数结果，不是收入金额表。

两张T99的职责不同，不能只凭“价差系数”把它们当成一张表：

| T99参数表（均在PDATA_N） | 一行配置针对谁 | 下游匹配方式 |
| --- | --- | --- |
| `T99_DERI_COMP_SPRD_COEF_REF` | 一份合约的参数版本 | 原合约号＋计提日；按生效日延续到下一版本前一天 |
| `T99_DERI_CUTP_COMP_TYPE_SPRD_COEF_REF` | 一个客户的一类合约及适用期初日期范围 | 客户号＋合约类型＋合约期初定价日 |

| 参数结果 | 这份例子整理后，关键字段是什么 |
| --- | --- |
| 合约价差 | `Inr_Comp_No=A1`；`Agt_Id=I1`；年化系数0.006；生效日09-15；删除标志0，系数大类CROSS |
| 客户＋类型价差 | `Pty_Id=C1`；`Src_Comp_Type_Cd=OPTION_STOCK`；年化系数0.002；期初日期适用范围09-01至09-30；删除标志0 |

其中I1是通过交易资料识别出的TIT内部流水号。本例的对应关系是：

```text
OIS合约号 A1 → 交易表内部交易编号A1 → TIT内部流水号I1 → 命中期权合约
      │                                      │
      └─ 保留为T99.Inr_Comp_No                └─ 写入T99.Agt_Id，表明已识别
```

**收入计算找A1参数时，使用的是 `T99.Inr_Comp_No = info.Agt_Id`。** 它不是拿I1去连接销售主信息里的A1。第一遍先记住这两个编号各做什么；完整识别和审批JOIN见后面的来源查阅。

到这里还没有给9月14日或15日选择参数，也没有乘本金。

## 三、给每个计提日分别匹配两路参数

### 合约侧：问“收入算在哪一天”

[03_合约价差有效期](03_合约价差有效期_118141.sql)把合约参数的生效日整理成适用区间：本条生效日到下一条生效日前一天；最后一条延续到加工日。

本例只有09-15这一条，所以本次形成09-15至09-22的逐日参数。按**合约号A1＋收入计提日**连接后：

- 09-14还没到生效日，合约侧没有匹配。
- 09-15、09-16均匹配0.006。
- 这路连接后的别名叫 `s_sp`，即“匹配到的合约价差”。

### 客户侧：问“这份合约在哪一天开始”

[04_客户类型价差适用期](04_客户类型价差适用期_118141.sql)按**客户C1＋类型OPTION_STOCK＋合约期初定价日09-10**连接。

09-10落在规则的09-01至09-30范围内，所以三个计提日都能匹配0.002。这路别名叫 `c_sp`，即“匹配到的客户＋类型价差”。

这里的09-30不是直接用来限制收入计算到哪天，而是限制**哪些期初日期的合约可以使用该配置**。客户记录自己的`Vld_Date`生效日不参与这段选择。

| 当前要算的计提日 | 合约侧s_sp：拿计提日去匹配 | 客户侧c_sp：拿期初日09-10去匹配 |
| --- | --- | --- |
| 09-14 | 未匹配，字段为NULL | 匹配年化／0.002 |
| 09-15 | 匹配年化／0.006 | 仍匹配年化／0.002 |
| 09-16 | 匹配年化／0.006 | 仍匹配年化／0.002 |

**两路都先连接到合约日记录上。** 不是合约侧没找到才执行客户查询，也不是把客户规则改成从09-15开始生效。

## 四、从两路匹配结果选出系数，再算金额

[05_价差选择与收入入口](05_价差选择与收入_118141.sql)带你回到118141主线。主线SELECT读取上一步的s_sp、c_sp，核心选择可以这样读：

```sql
coalesce(s_sp.Spread_Calculation, c_sp.Spread_Calculation) -- 选计算类型
coalesce(s_sp.Annualized_Spread, c_sp.Annualized_Spread)   -- 选年化系数
coalesce(s_sp.Absolute_Spread, c_sp.Absolute_Spread)     -- 选绝对系数
```

三项独立选择，合约字段为NULL时才回退客户字段。本例两路类型都为年化且系数完整，所以09-14选0.002，09-15起选0.006。

普通年化价差项使用：

```text
计提日在合约期初至有效结束日内：
    当天动态本金 × 选中的年化系数 ÷ 365
```

| 计提日 | 最终价差取自哪里 | 展示年化系数Annu_Sprd | 仅价差部分的当日金额 |
| --- | --- | ---: | ---: |
| 09-14 | 客户＋类型规则 | 0.002 | 3,650,000 × 0.002 ÷ 365 = 20元 |
| 09-15 | 合约规则 | 0.006 | 3,650,000 × 0.006 ÷ 365 = 60元 |
| 09-16 | 合约规则 | 0.006 | 60元 |

展示字段`Annu_Sprd`还是系数，不是20或60；本例不展示绝对系数，`Absl_Sprd`为空串。真正的收入计算发生在`Curr_Prvs_Sales_Income`表达式里。

完整普通收入还要组合基准。本例为核对完整CASE，另设**已匹配的基准类型为年化、基准系数为0**，于是原始当日收入也为20／60／60元。这里的“有基准类型、值为0”不等于“基准没配”；基准类型缺失可能让普通CASE无法命中。

这些仍是原始当日收入，不是最终日报金额，更不是已支付给人员的钱。[118141主线](../../销售与经营分析/118141_交叉销售收入/README.md)还会继续进行收入调整、介绍比例分配和累计。本例只讲价差，不把这些后续步骤重复展开。

### 只改一个值，09-15会怎样？

保持合约、日期、两路计算类型及客户系数不变，仅修改合约年化系数：

| 合约年化系数 | 选中的年化系数 | 本例09-15价差金额 | 原因 |
| --- | ---: | ---: | --- |
| 原值0.006 | 0.006 | 60元 | 合约侧有值 |
| 改为NULL | 0.002 | 20元 | 仅系数回退客户侧；计算类型仍可来自合约 |
| 改为0 | 0 | 0元 | 0是一个已有值，不是缺失 |

所以“合约优先”不是整套配置要么全取合约、要么全取客户。这个区别会直接改变金额。

```text

02 客户类型生产 ──→ 04 按客户＋类型＋期初日匹配 → c_sp ─┘
```

| 要追哪一步 | 文件 | 输入与结果的承接 |
| --- | --- | --- |
| A1的0.006怎样进入参数表？ | [01 合约价差生产](01_合约级价差生产_133052.sql) | OIS正式合约参数＋业务身份／审批资料 → T99合约价差 |
| C1的0.002怎样进入参数表？ | [02 客户类型价差生产](02_客户类型级价差生产_133049.sql) | OIS客户类型参数＋客户资料 → T99客户类型价差 |
| 为什么09-14没有合约参数？ | [03 合约价差匹配](03_合约价差有效期_118141.sql) | 生效记录 → 每日可匹配参数 → 合约日的s_sp |
| 为什么三个计提日都有客户参数？ | [04 客户类型价差匹配](04_客户类型价差适用期_118141.sql) | 期初日期适用范围 → 合约日的c_sp |
| 0.002／0.006在哪里变成20／60？ | [05 选择与收入入口](05_价差选择与收入_118141.sql) | 仅导航到118141的01展示和02收入；不再复制另一份公式 |

01、02是两个独立生产查询，各自的`src_table`不同，不能当成共用同一参数的一段串行脚本。两张T99按`SRC_TBL`来源分区，不按`busi_date`分区。

03、04是118141中的LEFT JOIN片段，已由[118141参数匹配模块](../../销售与经营分析/118141_交叉销售收入/03_参数匹配.sql)引用。外部的info来自合约主信息，det来自逐日本金与费用，不在本目录重新生产。

05现在是**纯注释导航，不再保存公式副本**：两项展示系数只维护在[118141合约日与资料](../../销售与经营分析/118141_交叉销售收入/01_合约日与资料.sql)，完整收入CASE只维护在[118141原始当日收入](../../销售与经营分析/118141_交叉销售收入/02_原始当日收入.sql)。主线保留前置特殊分支；第一遍只需定位普通OPTION的年化组合，不必把所有产品公式一起学完。

## 六、来源和边界：需要时再查

### 源字段经过哪些表？

| 路线 | 实际源表 → 参数结果表 | 关键字段去向 |
| --- | --- | --- |
| 合约级 | `odata_n_ois.o_contract_spread_rate`（【AI】合约价差系数表） → `pdata_n.t99_deri_comp_sprd_coef_ref`（衍生品合约价差系数参考信息） | CONTRACT_CODE→Inr_Comp_No；SPREAD_CALCULATION→Sprd_Calc_Type；ANNUALIZED_SPREAD／ABSOLUTE_SPREAD→Annu_Sprd_Coef／Absl_Sprd_Coef；EFFECTIVE_DATE→Vld_Date |
| 客户＋类型级 | `odata_n_ois.o_ctpty_cross_sell_coefficient`（【AI】交易对手合约价差系数表） → `pdata_n.t99_deri_cutp_comp_type_sprd_coef_ref`（衍生品对手方合约类型价差系数参考信息） | CLIENT_ID→Pty_Id；CONTRACT_TYPE→Src_Comp_Type_Cd；CALCULATION_TYPE→Calc_Type；两种价差系数原样带出；CONTRACT_START_DATE_MIN／MAX→Bgng_Prcg_Date_Llmt／Ulmt |

合约级`CROSS_OR_INR→Coef_Type`原样保留；客户级将Coef_Type固定写为CROSS。两者都把`IS_DELETED`的Y／N转成删除标志1／0、其他原样保留，生产时不据此删除记录。

客户源`EFFECTIVE_DATE`也写入Vld_Date，但04不读取它。客户类别、业务类型、标的类型虽然带入参数表，04实际只用客户号、合约类型、期初日期匹配，没有把这些附加属性一起作为匹配条件。

### 身份识别和审批JOIN为何存在？

01先按互换、期权、金仕达的CASE顺序识别身份：

| 命中对象 | T99的Agt_Id | Agt_Modifr |
| --- | --- | --- |
| TIT互换 | 交易表KEY_OTC_TRADE_ID | 20206 |
| TIT期权 | 交易表KEY_OTC_TRADE_ID | 20207 |
| 金仕达确认书 | 原OIS合约号，直接匹配KEY_TRADE_COMFIRM_ID | 20206-KST |
| 均未命中 | 空串 | 空串 |

识别使用LEFT JOIN，生产端保留未识别参数；118141取合约参数时才要求Agt_Id非空。原合约号即使有值，也不代表这条记录一定入选。除金仕达确认书ID做DISTINCT外，其他业务对象查询未统一去重。

`odata_n_ois.g_contract_spread_rate_temp`（交叉销售合约编号价差系数临时表）只补审批事件编号、客户编号和拟稿人，**不覆盖正式表的系数**。按“合约号、大类、合约类型、计算方式、年化系数、绝对系数”六字段分组取更新时间最新记录，再以六个等号连接。NULL键不相等；生效日期不在键中，不能断言审批资料属于同一生效版本。

02的境内和香港客户资料只帮助生成当事人类别，不选择系数，也不决定适用日期。

### 正常例子之外，哪些条件会改变结果？

| 情况 | 必须保留的原SQL行为 |
| --- | --- |
| 参数入选 | 合约侧筛指定源表、未删除、`coalesce(Coef_Type,'')!='INR'`、已识别身份；“非INR”含NULL、空串及其他值，不等于只取CROSS。客户侧筛指定源表、未删除 |
| 形成合约有效期 | 先过滤再LEAD，只按合约号分组、按生效日排序；不按类型／系数大类分组，同日多个版本没有稳定决胜键 |
| 客户日期的特殊值 | 下限1900-01-01改为2019-01-01，上限2999-12-31改为加工日；其他日期保持原值 |
| 两侧都匹配多行 | 客户区间重叠不择一；源表和右表重复可能使JOIN扩行。一行参数不等于每合约唯一，样例没有证明真实唯一性 |
| 计算类型是空串 | 03／04先把类型空串转NULL，允许回退；两个系数的空串不随之处理 |
| 系数是空串 | 空串会阻止COALESCE回退；后续如何转成数字属于Hive执行语义，不能把它当作NULL或0 |
| 类型与系数来自不同侧 | 合约为年化而年化值缺失时，即使客户类型为绝对，仍可能取客户年化字段的残留值；SQL不校验这种组合 |
| 两侧类型均缺失 | 展示价差字段为空串；普通收入公式却把价差类型默认ABSOLUTE。基准类型没有相同默认，普通CASE可能不命中 |
| 改为绝对价差 | 只在期初定价日按`初始本金×绝对系数`计算，不是每天乘动态本金，也不是“本金绝对值” |
| 普通年化超过有效结束日 | 起止区间首尾包含；结束边界优先提前终止日，否则期末定价日。此处日期判断不自动适用于全部特殊产品 |
| 先命中特殊分支 | AIRBAG、指定LONG_HOLD_SWAP、金仕达走更靠前的CASE，不能套普通价差公式；详见118141主线及[资金成本](../06_经营系数_资金成本/README.md) |

“维护了参数但没用上”时，依次查：维护层级 → 来源／删除等入选条件 → 业务身份是否识别 → 匹配的是计提日还是期初日 → NULL／空串／0 → 实际命中的收入分支。是否存在重复、异常区间或缺记录，需要数据核验，不能从文档例子推断。
