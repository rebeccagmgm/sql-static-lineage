# 105743：一份合约最后带上哪些人和机构

**先分开两件事：介绍关系选谁、占多少比例；经办角色分别记录谁。** 它们写在同一张表里，但不是同一套人员，也不是从所有人中选出一个“最终负责人”。

105743输出`pdata_n.t98_otc_comp_mng_rela_info`（OTC合约管理关系信息）。本任务只整理人员、机构和比例，不把收入分给员工，也不把本金乘比例。

## 第一遍先认清这张结果表

| 结果里的人员 | SQL在记录什么 | 是否带介绍分配比例 |
| --- | --- | --- |
| 第1、2、3组客户经理及机构 | 源表中的开发人员／引入人，按介绍关系排名放进三个位置 | 每组有`Allo_Prop` |
| 普通主经办、普通引入经办 | 普通合约参数记录的两个角色，缺失时可向客户资料取账号 | 这两个角色没有对应的三组比例 |
| 内部主经办、内部引入经办 | 内部合约参数记录的两个角色，另行选取 | 不与普通经办合并 |
| TIT经办、TIT客户经理 | TIT合约属性记录的两个角色 | 不用介绍关系的排名和比例 |

这里按SQL来源区分角色，不推断各岗位的制度职责。尤其是**“第1组客户经理”和“TIT客户经理”虽然都叫客户经理，选人来源并不相同**；三个位置也不是主经办、引入经办、客户经理三个职位。

先读下面一份合约的完整例子，再打开[00_主脚本](00_主脚本.sql)。看介绍关系如何选择时，重点对应[03_横排](03_介绍关系横排.sql)和[07_最终输出](07_管理归属输出.sql)；需要追来源再看其余模块。

## 一、同一份合约，从源关系一直看到最终结果

以下为构造数据，所有资料均满足各自取数条件，员工和机构能唯一匹配；不是生产记录。

销售主信息给出一份合约：`Agt_Id=A1`，所属客户`Cutp_Pty_Id=C1`，内部流水号`Inr_Seri_No=I1`，账簿部门为OTC。三个编号各有用途，不是三个别名。

### 1. 源表里有两种介绍关系

| 关系挂在哪里 | 来源 | 人员OA账号／姓名 | 引入部门 | 分配比例 |
| --- | --- | --- | --- | ---: |
| 客户C1 | OIS客户介绍关系 | CA／张三 | 11 | 0.6 |
| 客户C1 | OIS客户介绍关系 | CB／李四 | 12 | 0.4 |
| 合约A1 | OIS合约介绍关系 | KA／王五 | 1 | 1.0 |

这不是把三个人放到一起排名：客户C1的两条关系一组，合约A1的关系另一组。

[01_介绍关系排序](01_介绍关系排序.sql)在各自来源内按对象分组，先按比例降序，再按人员号排序。因此张三、李四分别是客户关系的第1、2名；王五是合约关系的第1名。部门号补成四位：0011、0012、0001。

### 2. 先补资料，再把“多行”摆成“三组列”

[02_人员与机构](02_人员与机构.sql)提供两条查找线：

```text
介绍关系里的人员账号 → 员工表 → 姓名、员工编号、状态
介绍关系里的部门号 → OA部门 → 部门名称 → 所属分公司
```

姓名不是关系源表直接给出来的：本例员工表把CA、CB、KA分别解释为张三、李四、王五。引入部门来自关系记录，不是拿这个员工当前所属部门来替代。

然后[03_介绍关系横排](03_介绍关系横排.sql)把不同名次放进不同列，写入本任务的中间表`otc_div_temp`：

| 中间表里的身份 | 第1组人员／比例 | 第2组人员／比例 | 第3组人员／比例 |
| --- | --- | --- | --- |
| 客户C1；合约号为空串 | 张三／0.6 | 李四／0.4 | 空串／0 |
| 合约A1；客户号为空串 | 王五／1.0 | 空串／0 | 空串／0 |

“横排”就是这个行列转换，不是重新决定谁占多少。这里只缩写展示人员和比例，实际每组还带机构、员工号等字段。

读03时只需先理解第1组的一条公式：

```sql
MAX(CASE WHEN A.seq = '1' THEN A.Customer_Manager ELSE '' END)
```

它让第1名提供人员账号，其他名次提供空串，再聚合为一个字段。姓名、部门、比例分别做同类处理；第2、3组只是改对应名次。本例合约只有王五一条，因此其第2、3组已经得到**空串和0，不是NULL**。

### 3. 再把两种关系挂到合约A1

[04_合约与客户关系](04_合约与客户关系.sql)准备两份中间关系；实际连接和取值在07：

```text
销售合约 A1
  ├─ 合约号A1 → 合约介绍关系 ci  → 王五、1.0
  └─ 客户号C1 → 客户介绍关系 cpi → 张三0.6、李四0.4
                                   ↓
                      每个字段分别优先ci，NULL才用cpi
```

“合约优先”不是重新比较谁的比例大，而是字段取值顺序。例如：

```sql
coalesce(ci.Cust_Mngr_Id_1, cpi.Cust_Mngr_Id_1) -- 第1组账号
coalesce(ci.Allo_Prop_1, cpi.Allo_Prop_1)       -- 第1组比例，独立取值
```

本例最终得到：

| 最终字段组 | 人员 | 引入部门 | 比例 | 为什么 |
| --- | --- | --- | ---: | --- |
| 第1组 | 王五（KA） | 0001 | 1.0 | 合约侧各字段有值 |
| 第2组 | 空串 | 空串 | 0 | 合约侧已有空串／0，不触发客户侧回退 |
| 第3组 | 空串 | 空串 | 0 | 同上 |

**李四并没有自动补进第2组。** 原因不是李四被过滤，也不是只允许一个介绍人，而是合约中间行已经把第2组填成空串和0；COALESCE只认NULL。

### 4. 经办人走另一条线，不从王五那里推出来

仍是A1，假设其普通合约参数里主经办账号为SO、引入经办为SI，员工表分别匹配赵六、周七；客户资料另外维护了CO、CI。本例合约参数有值，普通经办就用SO、SI。

内部参数和TIT属性也各自有记录，最终是并排保留：

| 字段组 | 本例结果 | 查找路径 |
| --- | --- | --- |
| 介绍关系第1组 | KA／王五／比例1.0 | A1 → 合约介绍关系 → 员工资料 |
| 普通主／引入经办 | SO／赵六；SI／周七 | A1 → 普通合约参数 → 选账号 → 员工资料 |
| 内部主／引入经办 | IO；II及各自员工资料 | A1 → 内部合约参数 → 选账号 → 员工资料 |
| TIT经办／客户经理 | TO；TC及各自员工资料 | I1 → TIT属性operator／customerManager → 员工资料 |

这四行不是四种互相覆盖的候选。它们进入不同输出字段，完全可以是不同的人。普通与内部经办的客户回退来源虽是同一份`cp`，两套合约参数仍分别选择。

相关来源分别在[05_普通与内部经办](05_普通与内部经办.sql)、[06_TIT经办与客户经理](06_TIT经办与客户经理.sql)。07里的顺序是**先选账号，再用该账号查姓名和员工编号**；不是姓名查不到就自动换另一个账号。

### 5. 只去掉合约介绍关系，哪些结果会变化？

保持其余资料不变，只让A1没有合约级介绍关系。此时LEFT JOIN找不到`ci`，其字段为NULL，才会使用客户C1的关系：

| 结果 | 原来有王五的合约关系 | 只撤掉这条关系之后 |
| --- | --- | --- |
| 第1组 | 王五／1.0 | 张三／0.6 |
| 第2组 | 空串／0 | 李四／0.4 |
| 第3组 | 空串／0 | 空串／0 |
| 普通经办 | 赵六、周七 | 不变，普通合约参数还在 |
| 内部、TIT角色 | 各自原有角色 | 不变，它们走各自的来源 |

到这里，应能区分：“整条合约关系没匹配到”和“合约关系匹配到了、但第2组没有人”，结果为什么不同。

## 二、这张表怎样接到118141，而不是停在人员名单

本例写出的是账号、姓名、机构、比例，没有收入金额。118141按合约号连接这张表，实际取普通主／引入经办及三组介绍资料；并不把内部、TIT角色都当成同一份收入的收款人。

- 三组比例进入收入计算：如果118141已完成收入调整、待分配的当日收入为1,000元，本例的1、0、0会使三组当日金额成为1,000、0、0。乘法发生在118141，不在105743。
- 普通引入经办ID是否存在，还会影响118141的本金主／引入经办40/60字段；这不是三组收入比例，也不是105743计算的分配规则。

具体怎样计算见[118141贯穿样板](../../销售与经营分析/118141_交叉销售收入/README.md)。该样板独立设置70%／30%关系用来解释收入公式，不是本页这份A1的数据。

118141不是唯一消费。其他消费可以保留三组字段，也可以展开成人员／机构行；是否乘比例、过滤空关系、按哪层机构汇总，由各自规则决定，见[公共结果的消费边界](../07_公共结果如何进入收入与规模.md)。

## 四、正常路径懂了，再核对这些差异

### 介绍关系：缺一列，不等于缺整套

- 三个来源先分别排名再UNION ALL。OIS客户与香港客户如果同号，可各有一个第1名；中间表又不按来源分组。MAX逐字段取值，可能出现部门取自一条、人员取自另一条，不能解释成“按最大比例选中整行”。
- 超过三名没有提前被筛掉；横排只展示前三组，但其他名次仍贡献ELSE空串／0。比例0.4、0.3、0.2、0.1会展示前三项合计0.9，不重新归一到1。
- 合约侧账号有值、姓名为NULL时，最终账号可来自合约、姓名却回退客户；员工号若已补为空串则不回退。若还存在别的名次，其ELSE空串也可能使该姓名MAX为空串。不能只看“有没有合约关系”就判断所有字段。
- 员工编号在三组介绍关系中按Emp_Id → OA_User_Id → 空串回退，只回退NULL；经办角色员工号却直接取Emp_Id。员工状态只是输出，没有统一筛选“只在职”。

### 来源和角色：同样的名字不保证同样的规则

| 对象 | 必须保留的区别 |
| --- | --- |
| OIS介绍关系 | 客户、合约两表都筛参数日及Is_Deleted='N' |
| 香港介绍关系 | 介绍排名只筛参数日；没有补加OIS删除条件 |
| 客户经办cp | OIS客户资料筛delete_flag='0'；香港使用源seq='1'，不是重新按比例排出来的第1名，且用introductor同时填两个经办字段 |
| 普通合约经办 | 合约参数一侧只在账簿部门OTC时匹配；未匹配时可按字段回退cp |
| 内部合约经办 | 参数一侧没有上述OTC部门限制；仍独立回退cp |
| TIT角色 | 按内部流水号找属性，MAX取值不是取最新维护人；无OIS或客户回退 |
| 部门 | 三组介绍关系带的是关系源引入部门；TIT角色带的是员工所属部门，不能互换 |

例如香港源第1条H1比例0.2、第2条H2比例0.8：介绍关系第1名会是H2，客户经办回退却可能是H1。两处用的不是同一种“第一”。

经办优先侧账号有值、但员工表查不到时，不会再换客户账号试一次；NULL账号会回退，空串账号不回退。最终Data_Src_Cd固定为TIT，不代表人员全都来源于TIT。

### 特殊客户：只切换查关系的键，不改输出客户身份

通常按主信息Cutp_Pty_Id找客户介绍关系cpi和客户经办cp。只有主信息客户号为固定值`DEV1100100652`，且按合约号匹配到符合条件的浮动收益凭证，才改用凭证`deal_cutp_no`。

凭证必须属于参数日、OIS来源、01分组，且本金保障比例转double后小于1；实际条件见04和07。切换后输出Pty_Id仍为主信息原客户号，合约介绍关系仍按Agt_Id、TIT仍按Inr_Seri_No查。替代客户号为NULL也不自动回原客户号。没有证据确认该固定编号的业务名称，不凭号码猜主体。


## 验证与证据边界

### 日期和行数仍须按SQL理解

员工用参数日快照；OA部门查询没有日期过滤；分支归属用`default.pretradedate(date_add(参数日,1),1)`。本地函数目录目前只查到内部Presto同名函数签名，不能替代此Hive UDF实现证据，所以不把它翻译为“参数日前一天”。

最终管理归属也按加工参数日分区。用当前归属分区关联历史金额，不自动等于历史计提日当时的人员归属。

原始资料和参数表没有统一去重。最终`DISTINCT`针对全部59个非分区输出值，不能证明每合约一行；多条参数、同号客户资料或重复员工行都可能影响连接结果。我们没有查询生产样本来证明唯一性、比例合计或冲突频率。
