# 资金成本：先分清“率”和“源表用资数值”

本页沿118141的资金成本参数和金仕达算例阅读；[香港资金成本](04_香港资金成本.md)沿`HK_RISKY_DEMO`说明香港源配置、类型＋标的＋期初日匹配及每天120元的形成。两者共用“配置提供费率”的概念，来源、匹配条件和使用分支分别保留。

这里最容易误读的，是两个都叫 `Fnd_Cost` 的字段。**它们不是同一个量，也不是互相替代的来源。**

| 在118141里看到的字段 | 实际来源 | 这段公式如何使用 |
| --- | --- | --- |
| `cc.capital_cost` | OIS `G_BUS_TYPE_CAPITAL_COST.CAPITAL_COST` → T99 `Fnd_Cost` | 作为成本率参数，参与减法或“乘基数÷365” |
| `det.Fnd_Cost` | 金仕达 `D_KS_TRADE_COMFIRM_INFO.occupy_cost` → 107491附加明细 | 在金仕达分支中，作为乘上述成本率的计费基数 |

按SQL的使用方式，可以把前者理解为**年化成本率参数**；但两个源字段的元数据仅分别写“资金成本”“用资成本”，没有证明维护界面的百分数单位、后者的币种或计量单位。不要把后者直接读成“已经算好的每日成本金额”。

## 一、先顺着这条线读

```text
OIS维护的合约类型资金成本配置
  │ 133057：原值映射，不计算金额
  ▼
T99_DERI_COMP_TYPE_FND_COST_REF
  │ 118141：只取指定来源、未删除、源部门OTC
  │         按“合约类型 + 合约期初定价日”匹配起息区间

cc.capital_cost
  ├─ AIRBAG：从调整后费率中扣除，再乘动态本金及比例
  └─ 金仕达：源表用资数值 × 成本率 ÷365，作为收入中的扣减项

```

## 先跟一份金仕达合约走完：配置0.03怎样进入495元？

构造合约`K1`：经营合约类型`TRS_KINGSTAR_SWAP`，期初定价日2026-09-10；本次加工日2026-09-22，先看9月20日的收入。这里使用一致的示例金额单位，不把源元数据未注明的币种／单位补成已知事实。

OIS的`G_BUS_TYPE_CAPITAL_COST`当日快照有两条配置，均未删除、源部门为OTC：

| 源合约类型CONTRACT_TYPE | 起息区间INTEREST_START_DATE／END_DATE | CAPITAL_COST |
| --- | --- | ---: |
| TRS_KINGSTAR_SWAP | 2026-09-01—2026-09-15 | 0.03 |
| TRS_KINGSTAR_SWAP | 2026-09-16—2026-09-30 | 0.04 |

这两条不代表同一合约按9月15日前后换成本率；它们先描述**哪些期初日期的合约适用哪个参数**。

| 环节 | K1在这一步得到什么 | 对应位置 |
| --- | --- | --- |
| 源配置写入T99 | `CONTRACT_TYPE→Src_Comp_Type_Cd`，`CAPITAL_COST→Fnd_Cost`；起息起止日截前10位，`IS_DELETED=N→Del_Flag=0` | 本目录01完整生产SQL；两条仍是两条配置，未计算金额 |
| 筛选与日期展开 | 留下OIS来源、未删除、OTC部门；两条配置分别展开适用日期 | 本目录02的内部查询 |
| 配回K1 | 类型相同，`info.Strt_Pric_Date=09-10`落在第一段；选中`cc.capital_cost=0.03` | 02的ON条件；不是拿计提日09-20匹配0.04 |
| 输入当日金额 | `det.Inta=1000`、`Trd_Cms=100`、`Trd_Cms_Cost=20`、`det.Fnd_Cost=365000` | 107491逐日本金与费用；这是已形成的明细，不由成本参数生产SQL提供 |
| 进入收入分支 | `365000×0.03÷365=30`是本例成本扣减项；`(1000×0.94+100−20−30)×0.5=495` | 主线02的金仕达分支；假设没有先命中AIRBAG／LONG_HOLD_SWAP |

**本例串起的是源参数0.03 → 按期初日选中0.03 → 成本扣减30 → 原始当日收入495。** 后面主线04还会分摊金仕达系统费用，所以495不是最终日报金额，更不是已支付金额。

想继续算到最终日报，转到[金仕达双合约贯通](../../销售与经营分析/118141_交叉销售收入/11_金仕达收入与系统费用贯通.md)。该页另设两份合约，共同展示系统费用分母；本页K1只聚焦成本配置，不将495直接当最终金额。

只把K1的期初日改为9月16日，其余示例金额不变，就匹配0.04：成本扣减40、原始当日收入490。若参数缺失，不是按零成本算510；引用NULL的原式会返回NULL。下面再分别解释生产、适用日期及其他分支，仍围绕这个例子。

## 二、生产阶段只整理参数，不计算资金成本金额

主体是 `ODATA_N_OIS.G_BUS_TYPE_CAPITAL_COST` 的加工日快照。一条源配置输出一条记录，SQL没有聚合、去重或窗口选最新。

- 业务类型、合约类型、标的类型、生效日期、`CAPITAL_COST`均原值映射；资金成本参数没有除100。
- 删除标记仅把`Y/N`转为`1/0`，其他值原样保留。生产端不删除这些记录；消费端只取`Del_Flag='0'`。
- 起息起止时间截前10位，写入`Intr_Strt_Date/Intr_End_Date`。
- 目标按`SRC_TBL`分区，覆盖的是该来源分区，不是新增一个业务日期分区。

这里保留的`Vld_Date`叫“生效日期”，但118141的资金成本连接**没有用它选版本**。不能因为字段名看着像有效期，就套用合约价差的LEAD生效日逻辑。

## 三、究竟按哪一天选参数？

### 先筛来源，再匹配两个键

消费端先取：

```text
src_tbl = ODATA_N_OIS.G_BUS_TYPE_CAPITAL_COST
Del_Flag = 0
Src_Dept_No = OTC
```

随后把起息区间展开成日期行，连接：

```text
参数合约类型 = 合约主信息.Contr_Type_Cd
区间内日期   = 合约主信息.Strt_Pric_Date（期初定价日）
```

**不是按逐日明细的计提日选成本率。** `Busi_Type`、标的类型、`Vld_Date`虽然存进T99，也不在这个JOIN条件里。

上面K1的9月20日仍选0.03，就是这个连接条件的结果。若配置被回改、重新取数，匹配结果仍可能变化，不能进一步推断为“成本率永远锁定不变”的制度。

### 两个哨兵日期和两个风险

- 开始日`1900-01-01`转换成`2019-01-01`；结束日`2999-12-31`转换成本次118141的`${yyyy-MM-dd}`。
- 正常起止区间包含首尾。这里只展开天数，没有按天摊薄参数值。
- 同类型、同一期初定价日命中重叠区间时，没有`ROW_NUMBER`挑一条，LEFT JOIN可能增加行数；不同业务类型或标的类型也不会被当前连接键隔开。
- 日期为空或倒置的Hive展开行为未在本地业务数据上验证，不能据此承诺一定没有输出。下面的构造测试仅模拟正常区间。

## 四、只有三条收入分支使用这项成本率

收入CASE从上向下命中一条就停止。保留这个先后关系，比孤立记一个公式更重要：

| 判断顺序 | 情形 | 资金成本怎样参与 |
| --- | --- | --- |
| 1 | AIRBAG且`Ddct_Ptrn='DEDUCTION'` | 直接返回0，不需要cc成本参数 |
| 2 | AIRBAG非抵扣、无保证金关联合约 | 动态本金 × (1−初始保证金比例) × (费率÷1.06−成本率) ÷365 ×0.3 |
| 3 | AIRBAG非抵扣、有保证金关联合约 | 动态本金 × (1−基准保证金率) × (费率×(1−初始保证金比例)÷(1−基准保证金率)÷1.06−成本率) ÷365 ×0.3 |
| 4 | LONG_HOLD_SWAP且有关联合约 | 直接返回0 |
| 5 | 金仕达`TRS_KINGSTAR_SWAP` | (应计利息×0.94＋交易收入−交易成本−源表用资数值×成本率÷365) ×0.5 |
| 后续 | 普通期权／互换价差与基准组合 | 这些分支没有引用cc，不统一再扣一遍 |

AIRBAG的具体源类型为`AIRBAGX/AIRBAGM/AIRBAGL`；“非抵扣”在SQL里包括抵扣模式为NULL，因为用了`coalesce(Ddct_Ptrn,'') != 'DEDUCTION'`。关联合约ID的NULL和空串均按“无关联”分支；空格串没有被清洗。

这些特殊分支没有再套普通分支的“计提日在合约起止日期之间”判断。它们仍受上游输入范围约束，但不能把普通分支的日期保护自动补进公式。1.06、0.3、0.94、0.5是原SQL系数，本专题不推测其税务或分配制度依据。

### 回到K1：金额还要追到逐日明细

上面的495中，0.03来自本专题参数；1000、100、20、365000来自另一条金额加工链。不要把参数生产和金额生产合成一件事。

`det.Inta`已由107491对源`accrued_interest`乘-1后写出；`det.Fnd_Cost`则直接取`occupy_cost`。两者按源业务日期形成区间延续，所以某计提日读到的值可能来自更早的确认记录；不能把延续值当成该日新发生的现金流。详见[金仕达本金与费用](../03_逐日本金与费用/04_金仕达本金与费用.sql)。

## 五、缺参数不是按零成本计算

本段没有`coalesce(cc.capital_cost,0)`。

- 没匹配到参数，或匹配行的成本值为NULL：引用它的AIRBAG／金仕达公式通常得到NULL。
- 明确维护数值0：与缺失不同，参与计算时成本扣减项可为0。
- 即使用资基数是0，SQL的`0 × NULL`仍是NULL，不会自动视作成本0。
- 普通价差＋基准分支不引用cc，所以不因cc缺失直接变NULL；但若匹配到多行，JOIN扩行风险仍在。
- 完整CASE没有ELSE；没有命中任何业务分支，也会返回NULL。空字符串数字转换属于Hive执行语义，不能等同于NULL或数值0。
