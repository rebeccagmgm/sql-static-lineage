# 全貌与参考分类

本模块围绕一个问题展开：**客户、合约、账户、持仓和业务事件等基础资料，怎样被组织成经营分析、风险分析、运营结果、财务结果和监管报送？**

第一模块帮助读者认识业务对象及其入模表达；本模块进一步解释业务结果的形成：为什么要做、纳入哪些业务、使用什么口径、经过哪些加工，以及最终供谁使用。

本文记录 2026-09-18 确定的整理方向，并根据当日第一轮盘点补充分类。**已有结果请先读 [现有消费全貌与专题目录](01%20现有消费全貌与专题目录.md)**：其中提供当前 7,478 个调度任务的范围底账、代表业务结果及具体缺口。本文保留组织原则；分类仍可随证据调整，不代表生产环境全部消费均已盘清。

当日进一步确定发现顺序：**折叠入模与简单交付细节 → 识别公共基础及候选加工群 → 核对结果分支 → 确定专题目录**。首轮计算见[加工网络发现与边界压缩](02%20加工网络发现与边界压缩.md)。下文六类是业务核对标签，不预先限定分组；单张输出、算法候选组和业务专题是不同的单位。

## 1. 本模块收什么

以具有明确业务用途的结果为入口，包括报表、报送数据、业务指标、查询结果和供下游使用的数据集；为解释结果而需要的中间加工，也纳入相应专题。

| 内容 | 如何处理 |
| --- | --- |
| 为某项业务结果服务的范围筛选、关联、日期展开、计算、分配与汇总 | 在该结果的专题中讲清 |
| 简单统计或直接取数 | 只要属于该业务结果，就一起解释，不按 SQL 难度排除 |
| 客户、合约、账户等基础对象的定义和关系 | 引用第一模块，专题只补充当前用途需要的口径 |
| 系数、日历、汇率、字典等共享输入 | 说明在具体加工中怎样使用；多处复用时链接已有说明 |
| 系统间供数、加工与推送链路 | 由“第四模块：系统间供数与流转”说明提供方、供数内容、加工过程与接收方；本模块侧重业务结果及其形成规则 |
| 只知道表名、尚不清楚用途的结果 | 登记为待确认，核对实际加工与消费后再归类 |

例如，第一模块解释“保证金账户、合约组合、资金流水分别是什么、怎样关联”；本模块解释“如何利用这些资料形成追保分析或客户保证金监管报表”。

## 2. 目录怎样组织

**一级按业务用途，二级按具有共同业务问题的结果群或专题，文章内部解释公共基础和加工分支。** 先发现结构再落目录，不要求一张表一篇，也不要求一个候选加工组只能归入一个用途。

| 层次 | 回答的问题 | 示例 |
| --- | --- | --- |
| 一级：业务用途 | 为什么要做这批加工？ | 销售与经营分析 |
| 二级：专题及结果群 | 哪些结果共同回答一个问题，哪些口径必须区分？ | 销售收入及参数分支、客户规模及周期指标 |
| 篇内：形成过程 | 这个结果如何形成？ | 合约范围 → 管理归属 → 逐日本金 → 计提与分配 |

T94、T95、T98、T99 等模型编号作为查表和查漏的索引，不直接作为本模块的一级分类。同一业务结果可能跨多个模型主题和数据层；同一主题也可能同时包含基础资料、参数、明细和汇总结果。T94 的具体范围仍待核对，不在本文补定业务含义。

专题范围按业务结果贯穿源头、PDATA／NDS、DM 及实际消费位置，不以某个库为终点。分类必须由实际输出盘点修订，不能把预设类别当成完整业务范围。

## 3. 六类参考范围

下表给出候选分类及边界。示例用于帮助识别结果，具体专题是否存在、覆盖多少，需由后续清单确认。

| 参考分类            | 主要回答什么                  | 候选内容                         | 归类时注意                    |
| --------------- | ----------------------- | ---------------------------- | ------------------------ |
| **销售与经营分析**     | 做了多少业务、收入多少、归属谁？        | 销售收入、业务规模、销售参数、人员与机构归属       | 经营收入与财务核算金额可能有不同口径，分别解释  |
| **持仓、风险与盈亏分析**  | 持有什么、价值多少、风险与损益怎样？      | 持仓分析、估值结果、Greeks、盈亏、集中度与限额分析 | 分清源系统已算出的结果与数综新增的加工      |
| **资金、保证金与运营分析** | 资金状况怎样、履保缺口多少、业务处理到哪一步？ | 资金余额分析、组合履保、追保分析、结算与处理状态查询   | 区分余额、应收应付、实际资金变化和处理状态    |
| **财务与估值系统供数** | 如何按财务或估值系统所需口径组织金额？ | 财务盈亏、合约与交易结果、估值交割明细；对账专题待实际输出支持 | 仅有金额字段不足以归入财务类，需要确认用途 |
| **监管与协会报送**     | 按特定报送要求，应提供哪些数据？        | 客户保证金报送、收益凭证报备、协会及其他监管报送     | 以报送项目与接收要求组织；生成数据不代表报送成功 |
| **客户准入与服务管理** | 客户准入及后续服务处理到了哪一步？ | 准入进度、已准入客户管理、估值报告生成与发送查询 | 区分客户基础对象、业务办理进度和服务结果 |

六类是当前有代表结果支持的业务方向。销售归属、逐日本金等作为公共加工复用；用户账簿权限等应用支撑单列索引，不为凑分类而归到某个报表领域。

### 跨分类的内容怎样处理

- **按最终用途确定主归属。** 例如客户保证金监管报表归入“监管与协会报送”，其使用的履保分析链接“资金、保证金与运营分析”。
- **同一加工指定一处详解。** 多个专题复用时引用该说明，各专题补充自己的筛选、时间与金额口径。
- **同源但口径不同的结果分别解释。** 例如销售收入、财务收入和监管口径收入不能仅因名称接近合并。
- **暂时无法定位的内容留在待确认清单。** 不为了填满目录而推断用途，也不把“其他”作为长期杂项分类。

## 5. 怎样判断囊括了多少

**以可辨认的业务输出作为盘点单位，表和任务作为支撑索引。** 一项结果可能对应多张表、多个任务；一张表也可能服务多个结果。不能用 T98 表数或任务数代替专题覆盖数。

后续建立一张覆盖清单，至少记录：

| 字段 | 记录内容 |
| --- | --- |
| 业务输出 | 报表、指标、报送项目、查询或数据集的名称及用途 |
| 用途分类 | 六类参考分类之一或公共／应用支撑；用途不明时记“待确认” |
| 最终载体 | 实际输出表、报表、接口或接收系统；尚未核实则注明 |
| 主要中间结果 | 为该输出服务的模型表和加工阶段 |
| 对应专题 | 正文位置，避免重复编写与遗漏 |
| 当前解释情况 | 已发现、用途已核、关键加工已解释等，并注明未解释分支 |
| 核对依据 | 来源材料、SQL／任务、快照日期及尚缺的证据 |

盘点从两端对照：一端收集已知报表、指标、报送和接口输出；另一端检查已知模型表的实际下游去向。按真实读取和写入核对衔接，调度关系只作为查找线索。

覆盖情况分别回答三件事：发现了多少项结果、多少项已有明确用途和专题归属、多少项已经解释关键加工。这里的“已解释”不等于已验证生产运行、金额正确或业务验收。

已有的 [PDATA 输出定位底稿](../../processing-map/pdata-output-placement.md)和 [PDATA 加工导读](../../processing-map/pdata调研v2.md)可作为盘点线索。它们来自既有固定范围，包含基础对象及未解释分支，不能直接当作本模块的完整消费清单。

## 6. 每个专题讲清什么

以一个具体结果为主线，按读者理解业务的顺序展开：

1. **业务目的与使用场景**：为什么需要这项结果，用它判断什么。
2. **范围与记录粒度**：纳入哪些业务，一行表示什么，日期和关键编号代表什么。
3. **输入对象与关联关系**：用到哪些对象，通过什么键关联，哪些基础定义可引用第一模块。
4. **关键加工规则**：筛选、关联、日期展开、计算、分配和汇总如何改变结果；重点说明容易误解的口径。
5. **最终输出与使用方式**：结果落在哪里，供什么消费，如何理解关键字段。

SQL、任务清单和详细核对材料集中放在证据中，正文保留理解业务必需的字段、条件、公式和关系。尚未确认且影响理解的规则应在相关位置明确标注。

销售与经营分析可作为首个网络核对范例：先解释销售基础、管理归属、逐日本金与费用等公共加工，再核对交叉销售、对内销售、香港销售和规模指标各自的输入、口径及交付。依据发现结果确定专题范围，不只围绕某张销售报表展开。
