# 第二模块分析思路（确定稿）

核对日期：2026-09-21。本稿取代此前同文件中的对话摘录与建设自检表。组织原则仍见 [全貌与参考分类](00%20全貌与参考分类.md)；2026-09-18 盘点过程见 [现有消费全貌](01%20现有消费全貌与专题目录.md)、[加工网络发现](02%20加工网络发现与边界压缩.md)。

**主思路不推翻。要改的是执行顺序：不再把「先全图普查、再写专题」当成建设路径。**

## 1. 本模块回答什么

第一模块解释业务对象及其入模；第四模块解释系统间供数与推送。本模块解释中间这段：

**客户、合约、账户、持仓和业务事件等基础资料，怎样被组织成经营分析、风险分析、运营结果、财务结果和监管报送？**

读者要看到的对应关系是：

**基础输入 → 公共加工 → 专题加工 → 业务结果 → 交付出口**

不是每项结果都经过全部五层。NDS 或源系统已算好的结果可以直接当输入；某张业务结果也可以再被下一专题读取。入模细节和纯推送在专题阅读图里折叠，保留可展开入口，不删除依赖。

## 2. 确定保留

这些点已经用过，继续守：

1. **按业务问题组织，不按库、不按 T94/T95/T98/T99。** 六类方向（销售与经营、持仓风险盈亏、资金保证金运营、财务与估值供数、监管与协会报送、客户准入与服务）是核对标签，不是算法预设，也不是必须一次建成的文件夹清单。
2. **压缩是折叠细节，不是删除依赖。** 第一模块对象直接引用；第四模块推送直接引用。第四模块里带日期选择、业务范围过滤的环节，不因 SQL 短就当作简单搬运。
3. **公共加工指定一处详解。** 被多个结果复用、并且真正改变身份、金额、日期或归属的，才独立成文。字典、日历、高复用维表保留依赖，不单独促成合组，也不自动升格为公共加工。
4. **同源但口径不同的结果分别解释。** 交叉销售、对内销售、香港销售、财务收入、监管口径不能因名称接近合并。一张公共表可以服务多个专题，不必只有一个永久分类。
5. **簇不能只靠连得通。** 共同读取客户、证券、机构、日历，不足以把两组加工合成一个专题。101 个候选组是查漏工具，不是目录生成器，也不是专题总数。
6. **图是主证据，SQLite 是旁证。** 已发布 data-graph 提供节点、读写边和绑定 SQL；表元数据目录补注释，调度证据库核对 SQL 原文是否存在，资产目录提供指标/标签线索。SQLite 不能单独回答「这张表在哪条经营口径里、和谁共用基础」。
7. **静态 SQL 不是业务验收。** 不推断生产运行成功、金额可跨分支加总、报送已被接收或页面已消费。
8. **专题正文同一条阅读主线：** 业务问题 → 结果范围与粒度 → 输入及关联 → 关键加工规则 → 输出与使用 → 未确认部分。

销售与规模的 [公共加工](公共加工/README.md) 已经按上述写法落地：销售基础、管理归属、逐日本金，以及它们如何进入不同消费。后续专题引用这组结果，只写自己新增的筛选、计算、汇总与交付。

## 3. 确定改掉

2026-09-18 把「先发现结构」落实成了全图登记。登记有用，但不能再当主战场。

| 原先做法 | 问题 | 现在怎么做 |
| --- | --- | --- |
| 先给主图全部表和任务贴模块归属，再写专题 | 7,255 张表、7,478 个任务的台账变成建设前置；人工判断只覆盖约 35 个 SQL 任务 | 全图底账留作索引，工作集收回股衍的报表、指标、报送和查询结果 |
| 盘点单位变成物理表 / 写入观察 | `00` 已规定以可辨认的业务输出为盘点单位，后来被全量表/任务台账换掉 | 覆盖清单一行一个业务结果；表和任务做索引，不代替结果数 |
| 「模块归属」写成表的永久字段 | 同一表可以同时是公共结果和某专题输入 | 模块身份是阅读路径上的角色。折叠发生在专题阅读图里，不要求先给全图打第一/第二/第四模块 |
| 共同输入分组和串行接续作为写专题的前置 | 101 组、1,882 个未聚组任务无法穷尽，也不是知识缺口 | 只在当前专题路径上补直接加工关系；不对其余全网铺开 |
| 先建完整导航和全量覆盖清单 | 三份首页重复同一套五层模型；读者入口和发现导出混在一起 | 导航收敛后只保留一篇读者入口；覆盖清单随专题回填 |

**登记范围和分析范围分开。** [建设台账](建设台账/README.md) 可以继续保存主图全部对象，分析时筛选。第二模块正文不解释公司级无关指标、未核用途的整库对象，也不把「九库写入关联」当成股衍业务范围。

**公共加工仍然先在真实专题中看清，被多处复用后再抽独立说明。** 销售与规模这一组已经抽出。互换、期权共同基础仍是候选，等风险或财务专题真正复用后再独立成文，不按候选组整组建目录。

## 3.1 不要重复 Cookbook「销售收入管理」的坑

`E:\02_area\股衍数据-Cookbook\topics\业务专题\销售收入管理` 已经按业务机制拆过同一条线：为何产生、人员归属、参数管理、逐日计算，下面再计划内地/对内/香港三线。并行还有 `otc-business-and-data-foundation` 的对象地图、表卡、任务卡（含 118141）。同一组 T99/关系/逐日对象被写进多套目录，每张输入不够懂就再开一章，章节再引出新输入。结果是专题没有闭环，阅读入口却越来越多。

这不是内容写错，是展开规则错了：**把「理解输入」做成新专题的前置完备性。** 本模块若再把 T99、奖励汇总、审批、OIS 源表逐张升成公共加工，就是同一条路。

| 对象 | 它是什么 | 本模块怎么处理 |
| --- | --- | --- |
| 销售基础、管理归属、逐日金额 | 多个消费共用的**计算结果** | 已有公共加工，引用即可 |
| T99 价差/基准/资金成本 | 运管参数入模 + 消费时按键和日期选取 | 入模身份（OIS 合约码 ↔ TIT/KS）引用第一模块；118141 里只保留本任务的键、日期、`Coef_Type`、`coalesce`。不新开「参数管理」目录 |
| `actl` 奖励汇总 | 期权保底支用到的贴源结果 | 在 118141 保底公式旁说明来源字段，不单列公共加工 |
| Wiki 制度、运管页面、三条业务线划分 | 已有 Cookbook 销售收入管理 | 需要业务语境时链接，不搬正文、不重写教学案例 |

停写条件：当前专题的范围、粒度、连接、公式、未确认项已经能按冻结 SQL 核对。缺的上游用一张「取走哪些字段 / 连哪把键」表钉住，链到已有文章；**不把缺文当成必须先写完的新树。**

## 3.2 工作方式：正文不跟着探索走

乱的过程是固定的：**读一段 SQL → 写成说明文字 → 遇到不懂的表再探索 → 再写一段。** 冻结 SQL 是证据，不是阅读主线。探索可以发生在证据目录或对话里，写进读者正文的只能是已经钉住的事实。

| 做 | 不做 |
| --- | --- |
| 先定本篇只回答哪一个业务输出、哪一个任务 | 不从任务 SQL 从头叙事到结束 |
| 用表固定：范围条件、连接键与日期、公式分支、未确认项 | 不用段落复述 CASE / JOIN |
| 用图固定：本任务读写，深度 1–2 | 不沿上游把每张表再走一遍 SQL |
| 未知记入「未确认」，一行一个缺口 | 不把缺口当成下一篇必须立刻写的正文 |
| 已有第一模块、Cookbook、公共加工则链接 | 不把链接对象再写一遍 |

一次探索的产出是补一行表或一条未确认，不是一篇新散文。图查询、SQLite、打开上游 SQL 都可以，但默认不写进读者路径。

## 5. 证据怎么用

主工作区已发布图 `9dbe5623…`，发布时间 2026-09-16 09:27。查询走正式 CLI（`lineage-graph.ps1` / `graph:query`）。表级追溯默认 `TASK_SCHEDULE` 范围，需要实际读写边；深度和条数边界必须保留，不把候选范围升格为已确认字段因果。

## 6. 覆盖清单记什么

盘点单位是可辨认的业务输出，不是表数、任务数或候选组数。一项结果可能对应多张表、多个任务；一张表也可能服务多个结果。

清单至少记录：业务输出、用途分类、最终载体、主要中间结果、对应专题、当前解释情况、核对依据。用途不明记「待确认」，不为填满六类而推断。

20 项代表结果和 5 项公共/支撑样本，只用来检验写法与分组，不是完整专题目录。指标消费、T95 按项目成组、NDS 已承载加工结果等判断仍然有效，在对应专题里展开，不回到全图重跑。

之后的顺序仍可沿用，但不设为当前前置：

1. 持仓、风险与盈亏，并衔接组合保证金；互换/期权共同基础在这一步才决定是否独立成文。

每完成一个专题，回填：基础输入、公共加工、专题加工、结果分支、交付位置、尚未解释的依赖。缺哪一项写哪一项，不标全貌已完成。
