# SQL拆解与业务说明标准

2026-09-22制定。用于本轮经营系数与118141返工，也作为后续同类整理的验收依据；不是新增开发框架。

**目标：读者能沿一份合约，说明输入从哪里来、在哪一步改变、为什么得到这个结果，并能在SQL中找到对应位置。** 文件数量、注释长度、测试数量都不是质量目标。

参考[107491逐日本金与费用](../公共加工/03_逐日本金与费用/README.md)的连续算例、主脚本与模块承接，参考[合约主信息期权](../公共加工/01_合约主信息/sql/04_业务模块/01_期权/README.md)的核心加工与补充资料分层。借鉴其阅读方式，不照搬文件数量、目录层级或尚未改好的地方。

## 一、先确定读者要看懂的六件事

| 问题 | 必须交付的解释 | 不能用什么代替 |
| --- | --- | --- |
| 这段加工解决什么问题？ | 输入业务对象、结果用途；例如从合约日金额算销售收入 | 任务号、表名列表 |
| 一行是什么？ | 当前记录代表合约、合约日、配置还是汇总结果；哪些操作可能改变行数 | 未经验证就称“合约＋日期唯一” |
| 为什么要读这些表？ | 每个输入补身份、金额、参数、日期或归属中的哪一项 | 逐表翻译中文名称 |
| 结果怎样一步步形成？ | 可连续阅读的主线，各阶段的输入、处理、输出及承接位置 | 散落的JOIN/CASE摘录 |
| 为什么这个例子算出这个数？ | 同一份合约的连续算例，数字对应真实公式和分支 | 每个文件另起一个互不关联的例子 |
| 什么时候会不同？ | 正常路径之后说明分支、日期、缺失和重复匹配的影响 | 开头堆满警告，或为了简洁省掉关键条件 |

“业务含义”须区分已知含义与SQL行为。能解释公式如何使用一个值，不代表已证明其制度依据、维护单位或支付事实；未知就明确留空，不用英文别名猜。

## 二、组织单位是加工主线，不是SQL片段

### 复杂任务：入口、主脚本、模块、完整SQL互相对应

- **README**先说目的和记录含义，给出第一遍阅读路线及贯穿算例，再比较其他分支。文件导航和证据放后面。
- **主脚本**让读者看见主要输入怎样汇合、阶段如何承接、最后输出什么。不能只是一个文件清单，也不能把全部复杂逻辑原样塞回去。
- **模块**承担一个能说清的业务步骤。需要说明读取哪一层结果、产生哪些关键值、在哪里被使用。并列资料画成并列输入，不伪装成串行加工。
- **完整SQL**用于连续核读和与原文对照。模块化整理必须有明确的组合方式，不能要求读者手工猜拼接位置。已有renderer可复用；不为简单任务另建工具。

不是所有模块都必须变成CTE。表达式片段可以保留，但必须由主脚本明确引用，标明所处SELECT层、可用别名及输出字段。没有接入主线的摘录只能叫“参考片段”，不能算完成的模块化。

### 简单任务：完整查询加必要说明即可

一段原值映射、简单取参或短小JOIN，能在一屏附近讲清，就保留完整SQL。不能为了统一模板造出“输入层—加工层—输出层”，也不设拆分数量、文件行数指标。

上游参数生产与下游参数消费要分清：生产说明负责“参数如何形成”，118141主线负责“这份合约怎样选中并使用它”。不能让读者读完三份参数专题以后，自行重建收入主查询。

### 命名与目录

本轮沿用中文编号和平铺目录，不新增子文件夹。编号用于阅读导航；同层的相近步骤尽量一致，不为了对齐编号拆出空步骤。复杂度靠加工关系解决，不靠增加层级。

英文CTE或别名可以保留，但首次出现应就地说明中文用途；新别名要表达业务结果，不能用`enriched`、`tmp2`代替来源解释。改名不是自动提升可读性的理由。

## 三、每份SQL怎样写，才真正降低阅读负担

### 文件开头：简短说明，不写成第二篇README

例如一个参数匹配模块的说明应是：

```sql
-- 用途：给合约日结果补齐基准参数，尚不计算收入。
-- 输入：前一步合约日；合约级参数；类型级参数。
-- 合约号 → 合约参数；合约类型＋期初定价日 → 类型参数。
-- 输出：供收入公式使用的计算类型、基准系数；连接仍可能扩行。
-- 使用位置：主脚本的参数关联阶段。具体来源见下方表与字段注释。
```

这是注释样式，不是要求把现有SQL强改成上述模块。真实输入、输出和连接必须先核原文。

### 注释放在读者需要它的地方

- 源表旁放中文表意；关键字段旁解释中文含义、键的角色，以及已确认的单位/日期含义。无需把元数据所有字段注释全搬进来。
- JOIN旁解释“为主体补什么、用什么身份和日期、匹配不到怎样、多条匹配怎样”；常规语法不逐句复述。
- CASE旁先说分支目的与优先顺序，再解释公式。复杂CASE应按业务分支留白、分行，不能只有一大段总注释、下面仍是压缩长行。
- 公式附近标出关键别名的实际来源。不能只说`mid是汇率`，还应指出来自哪张表、用哪一天连接。
- 对跨SELECT层同名字段，说明当前值已被怎样改写。不能把外层`End_Pric_Date`直接当源期末日，漏掉内层提前终止日回退。
- NULL、空串、0、分支优先级等会改变当前结果的区别，就地说明；快照日期、哈希及一般限制集中放证据区，不在每个文件反复铺陈。

表/字段释义按现有SQLite导航、data-map、DDL等实际资料核对；保留`【AI】`标识和冲突。源注释缺失时可解释SQL用途，但不能把推断冒充字段原注释。

### 格式与文本图

SELECT按业务字段组分段，字段与中文释义就近；JOIN的来源、筛选、ON分行。避免巨大对齐空白，也不要为了对齐中文改动字段顺序。

三条以上来源或多个连续阶段适合短文本图；两句话能讲清的不强画图。图必须对应真实依赖，不能把并列输入画成执行顺序。

## 四、算例必须串起来，而不是装饰

118141先选一份普通期权，使用明确标为构造的数据。第一条路径暂不引入所有特殊产品，但不得假装真实SQL没有前置分支。

同一合约贯穿：

```text
合约身份与定价日期
  → 指定计提日的本金
  → 匹配到的价差与基准（展示匹配键和日期）
  → 原始当日收入
  → 是否触发结束日调整、调整后多少
  → 三组介绍比例怎样分配
  → 累计值及日报字段
```

每一步给出输入值、命中条件、输出值和对应模块。累计与保底涉及历史时，补足前期记录及金额，不能凭空给一个累计数掩盖计算。

先走正常路径，再只改变一个条件，观察结果：例如提前终止、参数缺失、类型参数回退或重复匹配。算例不是业务数据，不用于证明真实唯一性或制度正确性。

## 五、验收：可读性与语义都必须过关

### 阅读验收

不依赖聊天解释，检查读者是否能：

1. 从入口找到先读什么、哪些可以暂时跳过。
2. 沿主脚本找到每个模块的输入及去向，不需要自行拼接片段。
3. 追到一项关键金额的实际来源、日期和公式，不被层层别名挡住。
4. 用贯穿算例算出结果，并解释只改变一个条件后为什么不同。
5. 区分正常路径与特殊分支，以及确定事实和尚未确认的含义。

任一项做不到，就回到阅读结构或SQL组织返工；不是继续加注释凑齐清单。

### 语义验收

- 原始证据保留。只改格式/注释的SQL应逐token对照，保持字符串、公式和字段顺序。
- 抽取CTE、阶段化等结构变化，需有可追溯的展开/还原映射，重点核对JOIN类型与顺序、筛选位置、聚合与窗口作用域、CASE优先级、NULL及输出顺序。不能只对一个简化示例说“等价”。
- 构造案例覆盖本次实际触及的关键行为；测试SQL应取自交付片段，避免另写一套公式自证正确。SQLite适配不能冒充Hive/UDF全语义验证。
- 检查链接、引用文件与完整SQL是否一致。局部测试通过仅证明覆盖部分，不代表阅读验收通过，更不代表生产运行或业务验收。

只有阅读与语义两方面都达到本次明确范围，才能说该部分完成。未展开部分明示，不用“全面完成”概括。
