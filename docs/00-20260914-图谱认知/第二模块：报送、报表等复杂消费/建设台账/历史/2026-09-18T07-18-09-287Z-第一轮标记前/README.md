## 先从哪里填

1. 在表台账筛选 `候选公共加工 = 销售基础、管理归属与逐日金额`，先核对销售基础、管理归属、逐日明细三个结果。
2. 根据该行 `全部生产任务`，到调度台账核对对应输出和写入实例。同一任务有多行时分别判断，不把一行的决定复制到全部输出。
3. 阅读证据后填写 `人工模块归属`、`人工处理方式`、`人工核对状态`、`人工判断原因`。如果准备折叠，说明折叠哪一段、保留哪个结果及其依赖。只筛选分析对象，不从主台账删除其他对象。
4. 补 `人工结果粒度`、`人工使用边界`；只有实际读懂的内容才写入。引用 SQL 时标任务、SQL 槽和行号；引用知识文章时填写仓库相对路径。
5. 作出处理决定时，将该行 `当前基准哈希` 复制到 `人工核对基准哈希`，并填写核对人、日期和证据。自动建议不填入人工证据栏作为唯一依据。

表台账记录公共结果的含义和用途；调度台账记录加工段的处理决定。某张表可以供多个专题使用，`人工业务专题` 用分号分隔。公共结果台账的整体归属不替代每个生产分支的核对。

## 怎样标记

| 字段 | 建议取值 | 含义 |
| --- | --- | --- |
| 人工模块归属 | 第一模块；第二模块-公共加工；第二模块-业务专题；第四模块；本次范围外；待定 | 本轮主要解释位置。若一行仍包含多种职责，在使用边界说明，不强行概括 |
| 人工处理方式 | 展开解释；折叠生产侧；折叠交付侧；保留依赖；本次不展开；保留待判定 | 对阅读结构的处理方式，不删除底层节点、不改变发布图 |
| 人工核对状态 | 未核对；已读关键SQL；已确认处理方式；需复核 | “已读关键SQL”不自动等于已确认可折叠或业务验收 |
| 人工公共加工 | 具体名称，如销售管理归属 | 在核对后填写；自动候选名称只是查找入口 |
| 人工业务专题 | 一个或多个具体业务用途 | 如交叉销售收入；客户规模与周期指标 |
| 人工结果粒度 | 业务对象、日期与必要分组维度 | 逻辑粒度不证明实际主键唯一；未查数据时不要声称已经去重验证 |
| 人工使用边界 | 可使用范围、过滤、日期语义及未核验部分 | 同一表各分支的日期、编号和金额含义可能不同 |

下列是填写规则示意，不代表已经给真实记录作出决定：

- 入模分支已解释清楚：第一模块／折叠生产侧／已确认处理方式，保留模型输出和下游依赖。
- 公共加工需要讲解：第二模块-公共加工／展开解释，并填写结果粒度、使用边界和正文链接。
- 已核对纯推送：第四模块／折叠交付侧，保留接收位置及批次条件。
- 有依据确认属于其他业务：本次范围外／本次不展开，并写明范围理由；对象及依赖仍保留。
- 暂不清楚：人工模块、处理方式可留空或填待定／保留待判定，核对状态保持未核对。

空白不是“不考虑”。`建议模块`、`建议处理`、`自动依据`、`候选公共加工`、`候选加工群` 都属于机器线索，不能作为已确认决定使用。初始 `人工核对状态` 为“未核对”，其余人工字段为空。

`首批分析范围` 用来找回原来圈出的对象；`候选加工群` 和 `跨群复用数` 仍来自首批计算，没有对全图重新聚类。新增对象的分组为空表示尚未分析，不表示没有复用。已存在的全部人工字段原样保留。

已知图表达差异的导出任务 `91973`、`132277` 特别保留为待判定：其 SQL 读取 DM，但当前图未见读取且将该 DM 表关联为输出。台账保留原始观察，并在自动依据中注明原因，不能把这些记录作为反向生产或已确认可折叠的证据。

## 身份与证据怎么认

| 信息 | 使用规则 |
| --- | --- |
| 记录编号 | 方便筛选和关联的确定性短编号；初始化已检查无重复。后续合并同时核对完整身份 |
| 表的完整身份 | `物理身份`；同名不同源的表不合并，不按表名转移决定 |
| 调度记录完整身份 | `调度ID + 物理身份 + 写入实例`；同表多次写入分别保留 |
| 任务占位 | `TASK-` 编号表示当前未见写入的调度，并不是虚构的目标表；有了新证据后需人工比对占位与新写入，不能盲目转移决定 |
| 登记类型 | 区分 `输出写入（finalWrites）`、`其他写入观察（非finalWrites）`、`任务占位（未见写入）` |
| 读取表_任务级 | 整个任务观察到的读取；**不能理解为该输出必然使用全部读取表** |
| 输出限定 | 保留原图的目标识别性质，不提升为生产运行事实 |
| 候选加工群 | 来自本次共享输入计算，编号可能随重算变化，不作为长期身份或专题编号 |
| 当前基准哈希 | 表台账包含物理身份、名称／说明、生产任务证据和读取任务集合；调度台账包含输出身份、输出限定及整个任务的 SQL／投影内容 |
| 人工核对基准哈希 | 人工决定采用的证据基准；和新基准不同，提示重新审查，不直接否定旧决定 |

当前哈希用于保守提示变化，不证明业务含义变化，也不包含生产数据。任务哈希变化可能来自同任务其他输出；必须回到具体写入核对。字段元数据或图外材料也可能发生变化，当前哈希未覆盖所有外部来源。

本次全量版的表生产／读取关系覆盖原始 `WRITES/READS` 观察，包含内部加工，较旧版 `externalReads/finalWrites` 范围更广。表基准因登记口径变化而改变时，不等于 SQL 已修改；`复核提示` 与原人工决定分开保留。`节点关联任务` 仅说明节点在哪些任务投影中出现，不自动构成读取或生产关系。

`证据位置` 中，`证据/...`、`建设台账/...` 从第二模块目录解析；`docs/...`、`.evidence-cache/...`、`../sql-static-lineage-data/...` 等路径从仓库根目录解析。表的生产／读取任务是任务级观察，不能据此自动确认无界跨任务因果链。`库外相邻任务` 沿用首批定位结果，其中的“库外”相对于原九库分析范围，不限制本次全量登记。

## 后续怎样更新而不丢标记

**本次已执行一次全量扩充，并按完整身份保留已有人工字段；尚未接入后台自动刷新。** 两张 CSV 是唯一人工决定主文件；`基线.json` 记录最近一次生成时的信息，不另存一套人工决定。扩充前版本已保存在 `历史/`，具体目录见基线。不要运行初始化生成器覆盖已经填写的台账。

后续有新图或 SQL 时，按下面的规则更新：

1. 先备份两张 CSV 和基线记录，再在临时位置生成新的机器清单。
2. 按完整身份匹配，只更新自动列，保留所有 `人工` 开头的字段。
3. 已有人工决定且基准不同的行，将核对状态改为“需复核”，保留旧核对日期、旧基准和理由，直到重新确认。
4. 新对象新增行，人工字段保持初始状态。消失对象保留旧行，注明“不在新快照中，待核”；不能静默删除。
5. 写入实例变化、物理身份变化或无法匹配的对象，不自动继承原决定；旧新记录保留供人工比对。
6. 补记新图版本、核对日期和实际更新范围。只填写人工标记时不修改机器基准哈希；只有重读新证据后才更新人工核对基准。

如果之后导出 Excel，它应作为浏览副本；需要编辑时修改这两张主 CSV，避免出现两套冲突决定。CSV 为 UTF-8 BOM，可用 Excel“从文本/CSV”导入，将记录编号、调度ID、写入实例、物理身份和哈希列按文本读取。日期填写 `YYYY-MM-DD`。
