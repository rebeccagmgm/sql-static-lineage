# 履保、额度与追保：先找到同一客户，再分清比例、金额和文字

这些指标不在一条公式上相乘。履保比例和追保线来自组合资料，额度来自限额，规模来自主合约，追保来自追保设置。最后各自接回客户。

## 一、履保比例：组合本金决定每个比例占多大权重

“履保”在本篇指SQL里的履约保障相关资料，不自行等同于实收现金保证金。[05.1身份与加权明细](05.1_履保身份与加权明细.sql)先沿身份链带出USCC并算每行权重，[05履保比例](05_履保比例.sql)才按客户求加权和。

```text
T03_OTC_CUTP_MARG_ACCT_PERF_GUAR_RSLT（账户履保结果）
 Comb_Agt_Grp_ID（组合号）
   → T03_OTC_DERI_COMP_COMB_ADTNL_INFO.Agt_Grp_Id（组合附加资料）
   → Cutp_Pty_Id（内部对手方号）
   → T01_PTY_RELA_H.Pty_Id → Rela_Pty_Id（有效映射后的OIS客户号）
   → T01_CORP_CUST.PTY_ID → USCC
```

履保结果取报告日、源`D_BUNDLE_MARGIN_DAILY_RESULT`、`Perf_Marg_Flag='1'`，只让`Dyna_Nom_Prin>0`的记录进入权重。组合资料限定源`D_TRD_BUNDLE_INFO`及TRS/OPTION/MIXTURE，但**没有日期筛选**；当事人关系要求报告日落在左闭右开的有效期，法人客户取报告日OIS资料。不能把这条链简写成“全用当日表”。

本例客户甲/U001有两组合，身份各恰好匹配一次：

| 组合 | `Dyna_Nom_Prin`动态本金 | `Marg_Perf_Prtc_Rati`履保比例 | 05.1权重 | 对05结果贡献 |
| --- | ---: | ---: | ---: | ---: |
| B1 | 100万元 | 20% | 100/400=1/4 | 5% |
| B2 | 300万元 | 40% | 300/400=3/4 | 30% |

客户履保比例`margin_ratio=35%`（存0.35）。不是两个比例的简单平均30%，也不是把两个组合的保证金现金相加。

## 二、追保线：方法相似，但缺值进入分母的规则不同

[06.1身份与权重](06.1_追保身份与加权明细.sql)读取 `T03_OTC_COMP_PERF_MARG_REF`（合约履保参考），源`D_BUNDLE_DAILY_CONTR_PARAM`，使用`Lcrrc_Dyna_Nom_Prin`本币动态本金和`Bail_Apd_Marg_Line`追加保证金线。沿同样用途的组合身份链取USCC，再由[06追保线](06_追保线.sql)求加权和。

本例仍用100万/300万，追保线15%/25%，得到：`15%×1/4＋25%×3/4＝22.5%`。05和06是两份独立源输入，本例刚好用了相同本金，实际不保证相等。

只让B2的相应参数为NULL，两路会不同：

| 单项缺失 | 进入权重前的筛选 | 输出 |
| --- | --- | --- |
| 05的B2履保比例NULL | 只要求正本金，B2的300万仍在分母 | B1贡献20%×1/4=5%；NULL乘积被SUM忽略 |
| 06的B2追保线NULL | 先排除追保线NULL，再算本金权重 | 只剩B1，权重1，结果15% |

因此不能抽成一段“公共加权平均”并统一补零。零比例和NULL也不同：06的零追保线未被NULL筛选排除，会带着本金进入分母。

## 三、额度与规模：300万元和800万元分别是什么

### 3.1 获批额度：有效限额取最大，不是相加

[07获批额度](07_获批额度.sql)取 `T01_PTY_LMT_H`（当事人限额历史）的`Lmt`限额，源`D_RISK_CTPTY_LIMIT_THRESHOLD`，类型`ADMINISTRATORLIMIT`，有效期`Strt_Date<=报告日<End_Date`。经有效客户关系转为公司名称后，取`MAX(Lmt)`，业务代码`Perm_Busi_Type`去重拼接。

本例500万元/OPTION、800万元/TRS两条有效限额，输出获批额度800万元，业务串包含OPTION、TRS。**不是额度合计1300万元，也没有为每个代码分别输出一份限额。**有效结束日恰为报告日的限额已不符合条件。

### 3.2 履保规模：筛出合约，再求主合约动态本金

[08履保规模](08_履保规模.sql)也用 `T03_OTC_COMP_PERF_MARG_REF`，但这次源是`D_REF_OTC_CONTR_MARGIN_PARAM`，不是06的组合参数。只取报告日STATIC/DYNAMIC启用类型，以`Otc_Comp_Agt_Id`连接报告日销售主合约的 **`Inr_Seri_No`内部流水号**，保留grp01/02/03且合约类型描述不为“南下期货”。

本例合格P、B两份主合约动态本金200万和100万，按客户名称汇总为300万元。[14输出](14_统一输出.sql)用同一个结果生成两列：

| 输出 | 实际来源及处理 | 本例 |
| --- | --- | ---: |
| `outst_margin_amount`履保规模 | 08动态本金合计，缺失补0，除10000 | 300万元 |
| `used_quota`已用额度 | **与上一列完全相同的表达式** | 300万元 |
| `approved_quota`获批额度 | 07有效限额最大值，除10000，不补0 | 800万元 |

这里没有独立的额度占用流水，也没有实现“剩余额度=800－300”。把两列相减做业务判断之前，还须确认额度覆盖对象与占用口径可比，不能由本任务替制度确认。移除全部08匹配资料时，两列变0，而07可能仍为800；移除07限额时，获批额度NULL而不是0。

同一主合约匹配两条启用参数，会把本金带入两次；按名称SUM并不自动防止这种重复。

### 3.3 增信措施：当前取的是简称清单

[09增信资料](09_增信资料.sql)将 `T01_CUTP_PERF_MARG_PLAN_INFO`（履保方案信息，源`D_MARGIN_PLAN`）与 `T01_PTY_NAME`（当事人名称，源`D_REF_COUNTER_PARTY`）按`Pty_Id`连接，均取报告日。按`Full_Name_En`分组，收集`Shor_Name_Ch`中文简称。

本例`Full_Name_En='客户甲'`，简称“产品甲简称”，最终`credit_measure`就是这个简称。字段名虽然写“增信措施”，程序并没有在这里读取抵押品明细、担保合同条款或实际质押状态；英文名称字段实际用于回接客户名称，也值得核对真实填值。

## 四、追保及时率：数的是天数，不是完成了几次

[10追保及时率](10_追保及时率.sql)从 `T03_OTC_DERI_COMP_COMB_MARG_CALL_INFO`（组合追保信息，源`G_MARGIN_CALL_SETTING`）读取报告日快照，限定履保日期`Perf_Marg_Date`在2025-01-01～2026-09-22，经有效关系和法人客户归到公司名。

本例四条追保记录：

| 履保日期 | `Defr_Days`递延天数 | `Marg_Call_Amt`追保金额 |
| --- | ---: | ---: |
| 2026-09-01 | 1 | 1万元 |
| 2026-09-02 | 2 | 2万元 |
| 2026-09-03 | 2 | 2万元 |
| 2026-09-04 | 3 | 3万元 |

`margin_call_rate=(1＋2＋2)/(1＋2＋2＋3)=5/8=62.5%`。不是三条≤2天除四条=75%。本段没有用“已缴款完成”状态确认回款，只按递延天数作条件；零分母未保护，负数也没有专门排除，不自行把异常输入改成合理业务值。

## 五、垫资说明：先算统计量，再决定有没有资格拼文字

[11.1垫资统计](11.1_垫资统计.sql)仍取上述来源和期间，但先限定`Defr_Days>=2`，因此本例只剩9月2/3/4日三条。[11垫资文字](11_垫资文字.sql)另读报告日客户标签的“有垫资”，按公司名称连接统计，再填模板。

```text
追保资料 → 11.1算最近季度、频率、天数、金额天数比 ─┐
231146客户标签 → 筛“有垫资”客户 ────────────────┴→ 11拼文字
```

| 模板中的数值 | 本例如何算 | 舍入后 |
| --- | --- | --- |
| 最近季度 | 最大履保日期2026-09-04 | 2026年第三季度 |
| 平均每周频率 | 不同履保日期3×7 / 整个期间630天 | 约0次（保留1位后0.0） |
| 单次时长 | (2＋2＋3)/3=7/3天 | 2天 |
| 金额指标 | (2万＋2万＋3万)/(2＋2＋3)/10000 | 1万元 |

每周约0不等于没发生过，而是长期平均的舍入。频率数的是不同`Perf_Marg_Date`原值，不是追保行数；平均天数按行算，金额分母还将天数转int。这几种分母不能混成一套“平均每次垫资”。

**模板中的“根据托管行资金流水及券商对账单回溯”和“持续但规模可控”是固定文字，不是SQL真的核验了这些证据。**实际金额源为追保金额；不证明实际垫付款项、到账时间或风险可控。

只删掉“有垫资”标签：统计仍可算，但文字不再生成。只重复同名标签：11不去重，可能令最终客户行重复。只看≥2天记录也不能替代[231146原标签条件](../04_标签与协同/01_客户标签_231146/README.md)：本例有同月三天符合记录，与标签样例兼容，实际生产仍须核对标签来源。

## 六、这个拆法解决什么

05.1/06.1负责“原始记录怎样归到客户、谁进入权重”；05/06只看加权汇总。11.1负责数值统计，11负责标签入口和文字。剩下的短查询保留在同文件，不把每个简单JOIN再拆一层。

读到某个结果时，能区分是身份缺失、样本改变、分母改变，还是仅展示文字改变；也能分清“程序实际算到这里”和“制度还需要证明什么”。
