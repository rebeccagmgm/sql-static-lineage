# 互换活跃与费用：一个月的本金变化，三种不同来源的费用

本篇读取[04互换月换手](04_互换月换手.sql)、[12平台费与券息](12_平台费与券息.sql)、[13互换佣金](13_互换佣金.sql)，在[14统一输出](14_统一输出.sql)换单位。三路不是相互相加的收入明细。

## 一、月换手先看本金，再接事件

04保留两段真实计算：创收日报先按USCC＋`Inr_Seri_No`内部合约号归集本金，事件另按`Otc_Comp_Agt_Id`归集，最后连接后按USCC求比。

本金取 `DM_OTC_N.OTC_REV_DAILY_RPT` 的报告日快照，`Busi_Type='TRS'`，保留两类计提行：

- 本月初到报告日，且`Accrued_Date=Strt_Pric_Date`的起始行：累计`Init_Nom_Prin`初始本金。
- 上月最后一天的行：累计`Dyna_Nom_Prin`动态本金。

事件取 `T05_OTC_COMP_DURA_CHG_EVT`（合约存续变动事件），源`D_TRD_TRS_EVENT`，按`Evt_Date`筛本月至报告日，类型CLOSE_STOCKS/EARLY_TERMINATION/TERMINATION，求`Nom_Prin_Chg_Delta`名义本金变动之和。

本例报告日2026-09-22，客户甲有P、N两份互换：

| 输入 | 合约与日期 | 金额 |
| --- | --- | ---: |
| 上月末本金 | P，计提日8月31日 | 动态本金200万元 |
| 本月新增 | N，起始计提日9月5日 | 初始本金100万元 |
| 本月事件 | 内部号IP，9月15日CLOSE_STOCKS | 本金变动+50万元 |

先经`P.Inr_Seri_No=IP=事件.Otc_Comp_Agt_Id`带入事件，再按客户汇总：

```text
月换手率 = (本月新增100万＋事件变动50万)/上月末200万 = 0.75
本月新增输出 = 100万元
上月末规模输出 = 200万/1亿 = 0.02亿元
```

**初始本金描述新开始的量，动态本金描述上月末还剩的量；不是把所有本月每天的动态本金加起来。**金额变动来自事件字段，不由两天本金相减推算。

### 只改事件符号：为什么不能自行补ABS

事件从+50万改为-50万，其余不变，换手变成`(100－50)/200=0.25`。04没有ABS，没有按事件状态过滤，也没有事件分区日条件和汇率换算。它不同于[普通互换230204](../00_创收共同基础/02_普通互换_230204/README.md)中由数量、价格、rate计算平仓佣金的事件分支；不能把上游的处理习惯套到这里。

若只有一份合约的本月平仓事件，但该合约没有进入04本金样本，LEFT JOIN不会主动将它补入。上月末本金为0时除法未保护；无匹配不等于确定客户没有交易，除零的生产行为也须按实际引擎核验。

## 二、平台费与券息：先看“属于哪类合约”，再看腿累计收益

12读取报告日 `T98_OTC_SWAP_COMP_LEG_VALU_INFO`（互换合约腿估值），源`D_POS_TRS_LEG_VALUATION`。使用的是`Accum_Unrlz_Yield`累计未实现收益和`Accum_Rlz_Yield`累计已实现收益，**不是带Lcrrc前缀的本币收益列**。

实际连接键是：

`腿估值.Exp_Comp_No = 销售主合约.Agt_Id`，主合约为报告日grp02。

不要根据“外部合约编号”的字段标签自行换成主合约`Inr_Seri_No`。本次整理保留实际SQL连接，并用构造数据验证此键。

| 主合约源类型描述 | 12将腿收益放入 |
| --- | --- |
| 南下跨境、南下跨境（场内期权）、南下跨境（期货）、多头持券 | 平台费 `swap_platform_fee` |
| 跨境借券、借券互换 | 券息 `swap_bond_interest` |

FLOAT_LEG_TYPE浮动腿和FIXED_LEG_TYPE固定腿都允许进入；**不是浮动腿=平台费、固定腿=券息**。分类依据是合约类型。

本例：

| 合约/类型 | 腿类型 | 未实现＋已实现 | 分类金额 |
| --- | --- | ---: | ---: |
| P/南下跨境 | 浮动腿 | 100＋20 | 平台费120元 |
| P/南下跨境 | 固定腿 | 200＋30 | 平台费230元 |
| B/借券互换 | 固定腿 | 50＋10 | 券息60元 |

最终平台费`(120+230)/10000=0.035万元`，券息`60/10000=0.006万元`。这里取当日快照中的累计收益，**没有截成今年以来发生额，也没有自行换汇**。示例金额统一为元是构造前提，不能仅凭输出/10000证明所有真实来源已统一成人民币。

一项收益为NULL时，原式两项相加可能先成为NULL，再由SUM忽略该行；不能把“缺一个收益分量”自动当0。主合约重复匹配会复制腿金额；没有匹配则这一路缺失，最终没有统一补零。

## 三、佣金：只取符合范围的毛佣金，不再扣一次成本

13读取报告日创收快照中上一年元旦至报告日的 `Trd_Cms`交易佣金，CAST后COALESCE为0，按公司名称汇总。进入范围是：

1. grp03金仕达；或
2. grp02且`Agt_Clas_Cd='TRS_SAC_OTC'`，同时满足`S_CROSS_SWAP＋EQUITY`，或源合约类型为`S_CROSS_OPTION_SWAP`、`S_CROSS_FUTURE_SWAP`。

**不是全部普通互换和金仕达记录无差别相加。**例如普通互换多头持券并不因属于grp02就自动满足这里的源类型条件。

本例符合条件的P、N两行佣金20元、30元，加金仕达K的40元，输出`swap_commission=90/10000=0.009万元`。只新增一条不符合上述范围的grp02佣金1000元，结果不变；缺失佣金值在13内部补0，但整个客户没有13匹配行时，最终仍可能NULL。

`Trd_Cms`是上游的毛佣金展示；`Curr_Rev`是按各业务公式处理后的创收。13没有把佣金再扣佣金成本，也没有把平台费、券息和佣金加成“客户总创收”。回顾[普通互换创收](../00_创收共同基础/02_普通互换_230204/README.md)可看出净佣金已可能进入Curr_Rev，不能再无条件相加。

## 四、三路结果为何不能只按金额大小对账

| 指标 | 时间 | 匹配回客户 | 本例展示单位 |
| --- | --- | --- | --- |
| 换手 | 本月至报告日新增/事件、上月末动态本金 | USCC | 比例；新增万元、上月末亿元 |
| 平台费/券息 | 报告日腿快照内的累计收益 | 公司名称 | 万元 |
| 佣金 | 报告日创收快照、上一年元旦至报告日计提区间 | 公司名称 | 万元 |

同一客户名称改变、身份映射重复、某个源缺失，都可能只影响其中一路。完成这三路解释后，读者应能说清“这列取哪段时间、从哪个字段来、为什么选中、如何换单位”，而不是以为它们来自同一账单的三笔收款。
