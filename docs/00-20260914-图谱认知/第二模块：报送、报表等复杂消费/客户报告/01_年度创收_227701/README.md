# 年度创收：某客户去年和今年分别贡献了多少收入

任务 **227701**，结果表 `DM_OTC_N.BI_OTC_YEAR_REVENUE`（OTC年度创收表）。

**这份报表不重新计算每份合约的创收。它从报告日的创收日报快照中，按公司、年度汇总期权和互换创收，再补一份独立来源的年度交叉销售奖励。**跨境创收是这两类创收中的重叠切面，不能再加一遍。

先读下面的两路输入和连续算例，再打开[完整注释 SQL](01_年度创收.sql)。查询原文仅45行，两次聚合加一次连接已经能完整表达主线，因此保留一份查询，不为统一模板另造主脚本、模块和展开版。

## 一、一行代表什么，哪些客户会出现

在本次读取的报告日快照中，先选择：

- 业务类型 `Busi_Type` 为 `OPTION`（期权）或 `TRS`（互换）。本任务不另筛 `grp_id`。
- 计提日期 `Accrued_Date` 位于**上一年1月1日至报告日，含两端**。

再按 **统一社会信用代码 USCC＋公司全称＋计提年度** 分组，形成客户年度底座。两个年度都有记录才会输出两行，不会为没有记录的年份自动补零。

例如报告日是 **2026-09-22**，读取源表 `busi_date='2026-09-22'` 的快照，使用其中 **2025-01-01～2026-09-22** 的计提记录。2025年是完整历史年度的范围，2026年只到报告日；不是滚动24个月，也不是“只算今天”。

名称是分组的一部分。同一USCC如果出现两个名称，会形成两组；不能把“USCC＋年唯一”当作SQL已经保证的事实。

## 二、完整加工只需要看懂两路输入

```text
OTC_REV_DAILY_RPT 合约创收日报          T98_OTC_DERI_UNDRL_INCOME_RWD_SUM 奖励汇总
报告日快照中的多天合约记录             报告日快照，只取OIS交叉收入奖励来源
          │                                      │
按USCC＋公司全称＋计提年                按公司名称＋核算季度码所属年
汇总期权／互换／非CNY标的创收           汇总拓展方部门所得收入
          │ t1：客户年度创收                     │ t2：客户年度奖励
          └──────── 公司名称＋年度 LEFT JOIN ─────┘
                              │
                 四项金额除以10000；奖励缺失补0
                              ▼
                  客户年度结果，busi_year年度分区
```

图中的 `t1`、`t2` 是原查询的别名，分别代表两路已经聚合好的结果，不是物理表。两路互不依赖：不是先用创收乘一个比例，再得到奖励。

### 2.1 创收：三列金额都来自同一列 Curr_Rev

直接来源均为 `DM_OTC_N.OTC_REV_DAILY_RPT`：

| 字段与中文用途 | 本查询怎样使用 |
| --- | --- |
| `USCC`：统一社会信用代码 | 输出为公司ID `company_id`，参与分组 |
| `Cutp_Pty_Full_Name`：交易对手全称 | 输出为公司名称 `company_name`，参与分组，也用于连接奖励 |
| `busi_date`：源快照日期 | 选择报告日这一份数据，**不负责划分收入年度** |
| `Accrued_Date`：计提日期 | 选择收入期间，用 `year()` 分到2025或2026年 |
| `Busi_Type`：业务类型 | OPTION进入期权创收，TRS进入互换创收 |
| `Curr_Rev`：合约当日创收 | 被求和的金额；不是本金、客户盈亏或销售分配收入 |
| `Undrl_Curr`：标的币种 | 非CNY的行同时进入跨境创收；这里只分类，不换汇 |

三条实际表达式见SQL第一段：`SUM(CASE WHEN 条件 THEN Curr_Rev ELSE 0 END)`。因底座只保留OPTION/TRS，非空创收在期权和互换之间分类；其中非CNY标的金额又会在跨境列展示。这里“跨境”的判定仅指程序使用标的币种，并不等于已经证明业务制度的完整跨境定义。

**本节从已经产生的 `Curr_Rev` 开始。**各类合约怎样得到这笔创收，继续看[创收共同基础](../00_创收共同基础/README.md)。不能拿118141的销售收入公式替代这里的创收生产，也不能由本篇聚合算例宣称所有创收上游已核验。

### 2.2 奖励：按核算季度取数，按公司名称和年份连接

奖励直接来源是 `PDATA_N.T98_OTC_DERI_UNDRL_INCOME_RWD_SUM`，本任务限定 `src_tbl='ODATA_N_OIS.G_CROSS_INCOME_REWARD'`。沿[203358原始映射](../../销售与经营分析/118141_交叉销售收入/08_历史奖励来源_203358.sql)可继续找到：

| 奖励表字段 | OIS实际来源字段 | 当前作用 |
| --- | --- | --- |
| `Pty_Cutp_Name`：公司名称 | `CORPORATE_NAME` | 按名称汇总，连接创收底座的公司全称 |
| `Sett_Time`：核算时间 | `ACCOUNTING_DATE` | 按 `YYYY0Q` 季度码筛选，再截前4位得到年 |
| `Dev_Dept_Rwd`：拓展方部门所得收入 | `EXPANSION_DEPT_INCOME` | 直接求和；不在此处重新计算奖励比例 |

报告日2026-09-22的奖励范围是 **`202501`～`202603`**，即2025年一季度至2026年三季度。`202603`不是3月，也不是日期2026-03-01。原表达式比较季度码字符串，正常解释依赖源值遵循该格式。

**只要报告日快照已有本季度码的记录，就会参与求和。**没有再用核算结束日裁到9月22日，不能把它说成“精确计提至报告当天的奖励”，也不能据此认定三季度已结算完。

聚合后按 `t1.company_name=t2.Pty_Cutp_Name` 且年度相等连接，没有USCC、合同号或业务类型条件。因此，年度奖励是一份公司年度金额，不分别分摊回期权、互换和每份合约。没有创收底座的公司／年度，即使有奖励也不会凭LEFT JOIN新增出来。

`Dev_Dept_Rwd` 是部门所得金额，不是支付流水。203358映射中的实发奖励字段还填空串，不能把这份报表的“交叉销售金额”当成银行到账证明。

## 三、同一客户、多份合约、两个年度，完整算一次

以下全部是**构造数据**，用于复算交付SQL，不是真实客户数据。报告日统一为2026-09-22，公司名称为“客户甲”，USCC为“甲USCC”。金额输入单位为元。

假设报告日快照内，客户甲只有下面六条被选中的创收记录。合约标签帮助跟踪输入，不参与本查询分组；真实源表若有更多合约日记录，都会一同累加。

| 合约 | 计提日 Accrued_Date | 类型 Busi_Type | 标的币种 Undrl_Curr | 当日创收 Curr_Rev（元） |
| --- | --- | --- | --- | ---: |
| 期权O1 | 2025-03-10 | OPTION | CNY | 40,000 |
| 期权O2 | 2025-11-20 | OPTION | USD | 10,000 |
| 互换T1 | 2025-11-20 | TRS | CNY | 20,000 |
| 期权O1 | 2026-01-06 | OPTION | CNY | 30,000 |
| 期权O2 | 2026-05-12 | OPTION | USD | -5,000 |
| 互换T1 | 2026-09-22 | TRS | USD | 50,000 |

这里保留负创收，SQL没有取绝对值，也没有负值截零。期权O1跨年度出现，不会把两年的收入合到同一行。

**第一步：先得到 t1，不考虑奖励。**

| 年度 | 期权创收（元） | 互换创收（元） | 跨境创收（元） |
| --- | ---: | ---: | ---: |
| 2025 | 40,000＋10,000＝50,000 | 20,000 | 10,000 |
| 2026 | 30,000－5,000＝25,000 | 50,000 | -5,000＋50,000＝45,000 |

**第二步：同一快照中的OIS奖励先独立汇总成 t2。**

| 公司名称 | 核算季度 Sett_Time | 部门所得 Dev_Dept_Rwd（元） | 纳入哪个年度 |
| --- | --- | ---: | --- |
| 客户甲 | 202504 | 8,000 | 2025 |
| 客户甲 | 202601 | 6,000 | 2026 |
| 客户甲 | 202603 | 4,000 | 2026 |

因此2025奖励为8,000元，2026奖励为10,000元。即使另有202604四季度记录，它也超过本例季度上界，不会进入本次汇总。

**第三步：名称＋年度连接，四项金额统一除以10000。**

| 公司ID／名称 | 年度 | 期权创收（万元） | 互换创收（万元） | 交叉销售金额（万元） | 跨境创收（万元） |
| --- | --- | ---: | ---: | ---: | ---: |
| 甲USCC／客户甲 | 2025 | 5 | 2 | 0.8 | 1 |
| 甲USCC／客户甲 | 2026 | 2.5 | 5 | 1 | 4.5 |

2026年期权＋互换创收为 **7.5万元**，不是再加跨境4.5得到12万元。奖励1万元是另一项来源金额，本查询没有定义“创收＋奖励”的总收入列，不能自行加成8.5万元当作表内口径。

目标[DDL](02_目标表结构.sql)把四项金额标为万元，实际查询也执行 `/10000`。目标字段类型都是`string`；本篇展示数字便于复算，不代表已经验证线上写入时的精度、格式和隐式类型转换。

## 四、只改变一个条件，结果为何不同

### 改币种，不改创收金额

将最后一条互换T1记录的 `Undrl_Curr` 从USD改成CNY，其余输入不动：

- 2026互换创收仍是5万元，期权仍是2.5万元。
- 跨境创收由4.5万元变成 **-0.5万元**，只剩期权O2那笔负创收。
- 奖励仍是1万元。

说明跨境列是对同一金额按币种重新筛选，并非第三套收入算法，也没有在这一层乘汇率。

### 改奖励中的公司名，不改任何奖励金额

若将奖励记录名称改成“客户甲旧名”，创收底座仍叫“客户甲”：名称不相等，奖励连接不到，输出为0。**这个0表示本查询没有取得非空匹配金额，不证明客户真的没有奖励。**已有公司及创收行不会丢失。

如果反过来删除所有创收底座记录，哪怕奖励仍有8,000和10,000元，结果也是零行，而不是新增两行“只有奖励”的客户年度结果。

## 五、正常例子之后，再看这些边界

| 条件 | 原SQL实际结果 | 阅读时如何解释 |
| --- | --- | --- |
| 某公司只有2026创收 | 只输出2026行 | 不补2025空年度 |
| 重复一条互换50,000元输入 | 本例2026互换创收从5变10万元 | 无去重；“按公司年聚合”不能消除金额重复 |
| 同名但两个USCC | 两个创收底座，各自匹配同一份名称年度奖励 | 连接右侧已聚合，不会给单个底座扩成多行；但奖励可能跨USCC重复展示，不能无条件再总计 |
| 同一USCC在源中有新旧两名 | 按不同名称分为两组 | 不会自动统一客户名称，奖励也按各名称匹配 |
| 币种为NULL | `!= 'CNY'`不成立，跨境CASE走0 | 缺币种不是确认境内，不应把0当分类完整证明 |
| 命中业务类型的创收为NULL | `SUM`忽略NULL；若该CASE所有输入均为NULL，结果仍为NULL | 外层没有对三项创收统一补0；若还有另一类型行，其ELSE 0又可能令本列结果变0 |
| 创收为0或负数 | 按0或负数参与求和 | 不过滤，也不取绝对值 |
| 奖励无匹配或奖励SUM为NULL | `coalesce(...,0)`后输出0 | 两种情况被合并展示；不是支付状态 |
| 公司名称为NULL | 普通等号不会将两侧NULL互相匹配 | 即使两边都有未知名称，也不能自动取得奖励 |

这些行为可以用构造数据复算，但真实数据是否存在重名、重复记录、缺失币种或异常季度码，尚需数据核验。

## 六、结果写到哪里，阅读到这里算完成了什么

查询输出顺序为公司名称、公司ID、期权创收、互换创收、交叉销售金额、跨境创收、年度，共7列。目标`BI_OTC_YEAR_REVENUE`按 **`busi_year`** 分区，没有报告日分区；报告日是本次计算的取数参数，不会作为本查询的一列输出。

因此不能说目标表为每个报告日留存一套历史年度报告。实际覆盖策略、任务运行成功和历史版本保留，不由本查询与DDL单独证明。已发布图的交付关系为 **227701 → DM年度创收表 → 230264 → `gf_otc.bi_otc_year_revenue`**；前台展示、两端数据一致性和交付成功不在本次静态说明的验收范围。

读完应能独立回答：哪份快照、哪些计提日、哪些客户进入；三项创收为何重叠；奖励按什么键和季度进入；算例为何得到两行；缺失和重复时为什么不一样。

上游`Curr_Rev`的生产、制度认可的跨境定义、季度奖励是否最终核算、真实金额与支付情况仍须分别核验，不用本篇八项检查替代这些证明。
