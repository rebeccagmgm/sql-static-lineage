# 部门协同：四个栏目怎样展示关系与交叉销售奖励

任务 **232556**，结果表 `DM_OTC_N.BI_OTC_CROSS_SALE`（OTC部门交叉销售表）。依据2026-09-22平台SQL。

**先从创收日报确定客户范围，为每个客户底座展开托管、财富代销、研究服务、商机转介四个栏目，再分别补说明与奖励。四行并不证明四类合作都发生，更不是四个互斥金额桶。**

本任务不重新计算销售收入、奖励比例或实际支付。三路金额都汇总同一奖励来源的`Dev_Dept_Rwd`，财富代销“有／无”则另看季度指标。关系判断和金额必须分开理解。

## 二、正常例子：两客户，八行，先算再解释

以下是**构造数据**，报告日2026-09-22。金额按奖励源字段原单位演示，不额外换算成万元，不代表已经付款。

### 2.1 客户底座只决定“有谁”

创收日报报告日快照内有以下两家公司，计提日期位于2025-01-01～2026-09-22、分支属于01／02／03：

| 公司名称 | USCC | 合约 | 代签产品名 |
| --- | --- | --- | --- |
| 客户甲 | U001 | A | 产品甲 |
| 客户乙 | U002 | B | 产品乙 |

底座按公司全称＋USCC取DISTINCT，然后各展开四个栏目，得到八行。这里只取客户身份，没有用正创收、当日持仓或“今年才开仓”作为入选条件。只有奖励却没进创收客户范围的公司，不会被LEFT JOIN新增进来。

### 2.2 奖励来源先给出五笔，哪些栏目会用到

假设报告日奖励快照中，客户甲有以下记录，核算时间均为202603（三季度码）；客户乙没有奖励记录。

| `Bel_Inr_Org_Name`所属内部机构名称 | `Dev_Dept_Rwd`部门所得金额 | 本任务怎样使用 |
| --- | ---: | --- |
| 资产托管部 | 100 | 托管金额；也进入商机转介 |
| 发展研究中心 | 200 | 研究服务金额；也进入商机转介 |
| 财富管理与经纪业务总部 | 300 | 财富代销金额；也进入商机转介 |
| 其他介绍部门 | 400 | 商机转介 |
| 股权衍生品业务部 | 500 | 不属于前三栏，商机转介又明确排除 |

所以托管100、研究200、财富300；商机转介为 **100＋200＋300＋400＝1,000**。不是仅取“其他介绍部门”的400。

金额源为 `PDATA_N.T98_OTC_DERI_UNDRL_INCOME_RWD_SUM`，限定OIS交叉收入奖励来源。沿既有[203358来源映射](../../../销售与经营分析/118141_交叉销售收入/08_历史奖励来源_203358.sql)可查到：

| 当前字段 | OIS原始字段 | 本任务用途 |
| --- | --- | --- |
| `Pty_Cutp_Name` | `CORPORATE_NAME` | 公司名称匹配 |
| `Bel_Inr_Org_Name` | `BRANCH_NAME` | 选择／展示协同部门 |
| `Sett_Time` | `ACCOUNTING_DATE` | 按季度码选择期间 |
| `Dev_Dept_Rwd` | `EXPANSION_DEPT_INCOME` | 直接SUM部门所得金额 |

既有源映射对部门所得收入标注元；本查询没有再除10000，目标DDL只写“交叉发放金额”，也没有支付流水或实发状态检查。**不可因为字段名带“发放”，就认定这100已付到客户或部门账户。**币种与实际到账仍需独立证据。

### 2.3 财富关系再走另一条产品指标链

假设公司代签产品正确映射到季度指标，且季度／标签／组合类型都符合条件：

| 产品名 | 2025Q4指标值 | 2026Q3指标值 | 按产品名汇总 | 关系判断 |
| --- | ---: | ---: | ---: | --- |
| 产品甲 | 0.1 | 0.2 | 0.3 | 汇总>0，有财富代销 |
| 产品乙 | 无记录 | 0 | 0 | 不大于0，无财富代销 |

程序先按代签产品名把所选季度／营业部指标求和，再检查汇总值是否>0。本例产品甲合计0.3，产品乙合计0，因此甲有、乙无。这些指标值只用来判断关系，不作为奖励金额，也不能据此把跨季度的0.3解释成某一季度的真实占比。

### 2.4 最终八行是什么

| 公司 | 协同栏目 | 简述summary | 交叉金额（源字段单位） |
| --- | --- | --- | ---: |
| 客户甲 | 托管 | NULL（固定留空） | 100 |
| 客户甲 | 财富代销 | 有财富代销 | 300 |
| 客户甲 | 研究服务 | 有研究服务关系 | 200 |
| 客户甲 | 商机转介 | 资产托管部；发展研究中心；财富管理与经纪业务总部；其他介绍部门 | 1,000 |
| 客户乙 | 托管 | NULL | NULL |
| 客户乙 | 财富代销 | 无财富代销 | NULL |
| 客户乙 | 研究服务 | 无研究服务关系 | NULL |
| 客户乙 | 商机转介 | NULL | NULL |

商机转介说明的部门顺序只是本例展示：SQL用`COLLECT_SET`去重但没有排序，不能承诺每次顺序相同。

客户甲四栏金额硬相加得到 **1,600**，不是唯一奖励合计。因为前三栏的600又包含在商机转介1,000中，这张表不能直接把四栏当互斥分项汇总。客户乙仍有四栏，但金额是NULL，程序没有补0。

## 三、财富代销最容易看错的地方

[03财富代销](03_财富代销.sql)实际做两件独立的事：

```text
主表代签产品名 Sign_Prd_Name
                 │
季度指标 idx ─证券组合grp1→ 第三段产品代码
          └营业部组合grp2约束
                 │ 产品代码
OIS交易对手资料 prod_code → signature_name代签产品名称
                 │
     按signature_name SUM(index_val)
                 │ 与主表代签产品名精确相等
客户范围内至少一个产品汇总指标>0 → “有财富代销”

同公司财富部门Dev_Dept_Rwd汇总 ─────────→ 财富金额（另一条线）
```

各输入的实际位置：

| 别名／字段 | 实际来源 | 作用 |
| --- | --- | --- |
| `r.Sign_Prd_Name` | `OTC_REV_DAILY_RPT`的代签产品名 | 主表侧产品匹配键；r按合约、公司名、USCC、产品名去重 |
| `idx.index_val／busi_quat` | `dm_index_n.index_grp2_TnrAmtProp_Season` | 指标值／业务季度；先汇总所选季度指标再判正，不是奖励金额 |
| `grp1.grp_val` | `dm_index_n.grp_def`，类型NEWS_SECU | SQL按点分割后取索引2，即第三段作为产品代码 |
| `grp2.grp_id` | 同一组合定义表，类型BUSINESSOFFICE | 通过INNER JOIN要求指标第二组合是营业部类型 |
| `prd.prod_code／signature_name` | `ODATA_N_OIS.O_OTC_DERIVATIVE_COUNTERPARTY`报告日快照 | 产品代码与代签产品名映射，按两字段DISTINCT |
| `t_rwd.cross_sale_amount` | 财富部门奖励按公司名称预汇总 | 直接选出来，不用产品指标乘系数计算，也不按合约重复SUM |

2026-08-29元数据快照中，指标表中文名为“**产品×营业部&分公司&总部各部门_保有金额占比_剔除内部户&场外衍生品_季**”，字段注释为`index_val`“指标值”、`busi_quat`“业务季度”。这里消费的是保有金额占比类季度指标，而不是保有金额本身或奖励金额；正常例子的0.1、0.2只用于复算是否大于0，不按钱计价，也不据此确认真实指标采用0～1还是其他比例尺度。

指标筛选固定`tag_id='tag999999999'`，季度范围为上一年Q1到报告日所在季度。没有对idx另加报告日快照条件；不能把产品映射的报告日筛选误写到指标表上。产品缺映射、营业部组合不合格或产品名对不上都会让关系判断落到“无”，但不会自动清除匹配到的财富奖励。

同一公司多份合约引用同一正指标产品时，内部计数可能大于1，但最终只用于`>0`。财富金额已经在t_rwd按名称汇总，SELECT直接读取，不因正常的多合约匹配再次SUM；然而外层USCC连接仍有下一节的扩行风险。

## 四、只改变一个条件，观察关系、金额和行数的不同变化

### 4.1 只将客户乙产品指标改为正0.1：有关系仍可以没金额

产品乙原合计0，增加一条合格指标0.1后总和为0.1，说明变成“有财富代销”。奖励侧没有新增记录，金额仍为NULL。

反过来，只删除客户甲的产品指标，说明会变成“无财富代销”，但财富奖励仍为300。**关系与金额相互独立，不互作必需条件。**

这里再单独检验一个**数学边界，不作为正常业务输入**：若构造同一产品两条指标0.1和-0.1，汇总为0，程序仍判“无财富代销”，尽管其中存在一条正值。这只证明先SUM再判断的顺序，**不证明真实保有金额占比允许负数或生产中存在此类记录**。

### 4.2 只将研究奖励改为0或NULL：仍可有研究服务关系

研究服务说明看的是 `t_tg_yjfw.company_name IS NOT NULL`，不是金额>0。只要对应名称／部门的奖励聚合记录存在，金额为0甚至SUM结果为NULL，仍显示“有研究服务关系”。这个“有”是当前程序的记录存在性判断，不代表另查过研究服务合同或交付事实。

### 4.3 同一个USCC多一个公司名称：四行不是最终数量保证

在正常例子基础上，给U001增加“客户甲新名”，仍关联产品甲。客户底座产生“客户甲／U001”和“客户甲新名／U001”两组。财富子查询也按名称＋USCC分成两行，旧名财富奖励300，新名没有奖励。

外层却只有：`t_base.company_id=t_cfmx.company_id`，没有公司名称条件，也没有`d.coop_dept='财富代销'`条件。

```text
客户甲旧名：4栏目 × 2条U001财富结果 = 8行
客户甲新名：4栏目 × 2条U001财富结果 = 8行
客户乙    ：4栏目 × 1条U002财富结果 = 4行
总计20行，不是12行
```

托管、研究和商机栏目也会重复，即使最终没使用财富说明字段。新名的财富栏目还可能接到旧名那份300奖励。这是当前Join口径，不在本次整理中偷偷补条件修复。

若USCC是NULL，客户底座仍能展开四栏，但普通等号不能把两侧NULL相连，财富说明也可能为NULL，而不是通常的“无财富代销”。

## 五、日期、部门与空值需要明确的边界

| 项目 | 当前SQL条件 | 不应误读为 |
| --- | --- | --- |
| 客户范围 | 报告日快照、grp01／02／03、上一年元旦至报告日计提 | 当日有持仓或仅本年新客户 |
| 奖励范围 | 报告日快照、OIS来源、`Sett_Time`上一年01到本年当前季度码 | 只统计今年、按日截到报告日的奖金或实际支付 |
| 产品指标 | 上一年Q1到本年当前季度、指定tag、合格证券／营业部组合 | 仅当前季度某条正值 |
| 商机部门 | `Bel_Inr_Org_Name!='股权衍生品业务部'` | 只有前三栏之外的其他部门 |
| 部门为NULL | `!=`条件不成立，不进商机 | 自动归入“未知部门” |
| 奖励为负 | 按原值SUM，没有截零 | 发放金额一定非负 |
| 没有奖励 | LEFT JOIN后金额NULL，无COALESCE | 已核实金额为0 |
| 多条同部门奖励 | 部门列表去重，但金额仍逐条SUM | 部门去重也会去掉重复金额 |

报告日2026-09-22时，奖励范围是`202501`～`202603`，产品指标范围是`2025Q1`～`2026Q3`。两者都覆盖上一年和本年至今的季度，但编码不同。当前季度只要快照／指标表里已有记录就纳入，不等于该季度已最终结算。

与[年度创收227701](../../01_年度创收_227701/README.md)也不能直接按行对账：年度创收按年度分开并把奖励除10000；本任务在同一报告日把所选季度范围合并，分栏目展示、金额不除10000，且商机与其他栏目重叠。
