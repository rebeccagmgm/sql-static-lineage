# 客户报告：先理解客户，再看规模、创收、盈亏和风险

本专题整理九张客户分析结果，以及解释关键字段所必需的上游。不是九个串行步骤，也不是把每张 SQL 都拆成期权、互换和金仕达三份。

想先判断整份报告怎样一起读，先看[单客户贯穿案例](06_单客户贯穿核验/README.md)：实际测试样本揭示了单位、快照、NULL和搬运过滤的差别；它明确保留尚未完成的同版上游复算，不把旧落表数据当作当前SQL运行证明。

1. [全貌分析](00_客户报告全貌分析.md)：九张表各自回答什么、怎样共用来源、如何交付；先建立整体关系。
2. [创收共同基础](00_创收共同基础/README.md)：客户、合约、快照日期与计提日期怎样进入共同输入；先分清本金、创收和奖励。
3. [年度创收](01_年度创收_227701/README.md)：同一客户、多份合约、两个年度，完整解释创收汇总与奖励连接，已通过计算与阅读审查。
4. [三种规模与持仓](02_规模与持仓/README.md)：同一客户三份合约，解释每天余额、新增规模、标的分布为什么不能直接混算。
5. [交易与盈亏](03_交易与盈亏/README.md)：交易样本和估值样本怎样相交，持仓底座怎样影响盈亏比例。
6. [标签与协同](04_标签与协同/README.md)：标签依据、关系信号与奖励金额分别是什么，不把程序条件升级成业务事实证明。
7. [客户综合指标](05_客户综合指标_229121/README.md)：以同一客户贯通胜率、履保、额度、追保、垫资文字及互换费用；主脚本直接显示12路匹配。

## 与经营分析怎样衔接

合约主信息、逐日本金费用和奖励来源复用已有专题。客户报表共同读取的却是 `OTC_REV_DAILY_RPT`（合约创收日报），不能用已讲透的 `OTC_SALE_DAILY_RPT`（销售日报）替代其创收公式。

阅读标准沿用之前的经营分析：来源和记录含义先清楚，主脚本能够串起真正的模块，算例对照实际表达式，空值、日期和重复匹配的影响不能省略。简单 SQL 保留完整，不为拆分而拆分。

九张报表和三条必要创收上游已完成本次拆解与说明，具体交付、复算与未核验边界见[全链路阅读与验收](03_全链路阅读与验收.md)。批次记录见[建设计划](01_建设计划与验收.md)，当前取证与旧图差异见[证据基线](02_证据基线与版本差异.md)。这里的“已验收”只指SQL对应与阅读验收，不是生产运行、真实金额或客户页面验收。
