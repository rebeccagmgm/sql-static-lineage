# 客户报告全貌：从合约经营事实到客户规模、创收、盈亏与风险画像

核对日期：2026-09-22。范围：228241、228008、227869、227701、227697、229121、231146、232556、234355，以及理解它们所需的直接输入、创收生产分支和交付出口。

**这不是九个步骤组成的一条流水线，而是围绕客户的九张并列结果表。它们共同读取创收日报，再按各自的问题补充估值、履保、额度、标签或奖励资料。**

本篇先把整体关系讲清，不代替后续逐项公式说明。主要依据是已发布图谱及其保存的 SQL，版本边界和查询方式见文末；不是线上运行、真实数据质量或前台展示验收。

后续建设已于 2026-09-22 补取三个创收生产者和九张报表的当前平台 SQL，见[证据基线与版本差异](02_证据基线与版本差异.md)。本篇图谱覆盖分析保留原版本身份；当前实现以新冻结来源为准。尤其 230204 的 SQL 证据已取得但图未重建，223867 的计算和 229121 的佣金人群存在图后变化，不应再按本篇旧图描述直接复制公式。

## 一、这份客户报告究竟要回答什么

从一家公司出发，报告需要回答六类问题：

| 客户视角的问题 | 对应结果 | 读懂后的能力 |
| --- | --- | --- |
| 做了多少业务，规模怎样变化？ | 业务统计、规模变动、持仓分析 | 分清新增本金、逐日存量、业务类型和标的分布 |
| 给我司贡献了多少创收？ | 年度创收 | 分清期权、互换、跨境维度和交叉销售奖励，不把几项盲目相加 |
| 互换交易有什么特点？ | 互换交易统计 | 理解交易频率、单笔规模、类型排名及胜率的不同样本 |
| 当前持仓盈亏怎样？ | 持仓盈亏 | 解释资金结算、估值结果如何归到客户和标的 |
| 客户有什么特征和风险？ | 客户标签、客户综合指标 | 理解标签触发、履保、额度、追保与垫资的依据 |
| 公司内部哪些部门与客户有协同？ | 部门交叉销售 | 分清合作关系、展示栏目和奖励金额 |

因此，本专题不等于“客户收到的估值报告生成与发送流程”。这里确认的是九张客户分析结果及其数据交付链，尚未核验具体页面、报告模板、权限或发送流程。

### 为什么不能直接照搬交叉销售的拆法

118141 的主问题是“这份合约这一天产生多少销售收入，怎样调整、分配和累计”。客户报告把多个不同问题放到同一客户名下：**规模是余额，创收是期间金额，盈亏有另外的来源，风险资料又来自履保和额度。**

普通期权、普通互换、金仕达仍然重要，但主要是在创收日报等上游生产中区分。九张客户报表首先应按业务问题组织，不能在每张报表下机械复制三套业务分支。

## 二、真实加工关系：一个共同基础，多条并列补充

以下箭头以2026-09-16发布图为底稿；虚线表示该图尚未闭合的230204分支，其2026-09-22平台SQL现已补取并拆解，但没有重建图。为便于阅读，多个具体输入按业务用途折叠，不代表新建公共表。

       │          ┆           │
       └──────────┼───────────┘
                  ▼
      OTC_REV_DAILY_RPT：合约创收日报

                  │
                  ├─→ 228008 业务统计
                  ├─→ 227697 逐日规模序列（表名：规模变动）
                  ├─→ 234355 逐日标的持仓分析
                  ├─→ 227701 年度创收 ← 交叉收入奖励汇总
                  ├─→ 228241 互换交易统计 ← 合约主信息、互换腿估值

三个关键判断：

1. **九张表都直接读取 `DM_OTC_N.OTC_REV_DAILY_RPT`。**这不是之前的 `DM_OTC_N.OTC_SALE_DAILY_RPT`；已有销售收入知识可以帮助理解，但不能代替创收公式。
2. **229121 不是另外八张表的总汇表。**它自己读取 16 张直接来源表，通过并列模块补资料；九张结果内部，本轮确认的直接承接是 `231146 → 229121`，用途为垫资展示资格。
3. **SQL证据已补齐，图谱缺口仍保留。**发布图确认230202、223867写入创收日报；230204仍为`SCHEDULE_ONLY`。现已取得230204当前查询和DDL并完成[普通互换拆解](00_创收共同基础/02_普通互换_230204/README.md)，明确输出`grp_id='02'`，但不宣称新关系已发布回图。

图谱在这里的价值是定位真实共同输入、并列分支和交付出口，同时暴露未覆盖的位置；SQL 则继续负责解释“读进来以后怎么算”。

目标表均在 `dm_otc_n` 下。

| **227697** `bi_otc_amount_change`       | 公司＋计提日                       | 从报告日快照取近 12 个月，每天分别汇总期权／互换动态本金；不是前后两天的差额         | 不必拆；重点讲时间序列与日期转换              |

## 四、共同基础不是“九张报表都用同一套口径”

### 4.1 先区分身份：合约上的客户与风险资料里的客户怎样相遇

创收日报一侧通常直接取：

| 字段                   | 本专题里的角色                         |
| -------------------- | ------------------------------- |
| `USCC`               | 输出的 `company_id`，统一社会信用代码       |
| `Cutp_Pty_Full_Name` | 输出的 `company_name`，合约／创收一侧的客户名称 |
| `Cutp_Pty_Id`        | 交易对手客户编号，可用于关联客户资料，不等于 USCC     |
| `Agt_Id`             | 合约编号，部分笔数按它去重                   |
| `Inr_Seri_No`        | 内部流水号，部分事件、估值连接使用它，不能与合约编号混用    |

履保／追保一侧还会走另一条身份链：

```text
履保或追保记录的交易对手 Pty_Id
   → T01_PTY_RELA_H：按来源与关系生效区间取关联当事人
   → T01_CORP_CUST：取得公司名称和 USCC
   → 汇总到客户，再连接客户报告底座
```

这条链应明确解释“源交易对手如何归到报告中的公司”，不能只把三个表名写在 JOIN 旁。229121 中有的模块按 USCC 连，有的按公司名称连；232556 的不同模块也混用这两种键。名称变化、一号多名、同名及重复关系是否存在，仍需数据核验。

### 4.2 再区分时间：快照日期不是金额归属日期

创收日报消费中，`busi_date` 用于选择某次报告日快照，`Accrued_Date` 用于选择其中哪一天的计提记录。一份快照里可以带着多天的合约记录，不能只按文件名字把它理解成“当天新增的一批收入”。

| 日期用法 | 哪些结果这样用 | 阅读时必须注意 |
| --- | --- | --- |
| 报告日快照＋上一年 1 月 1 日至报告日 | 年度创收、多个客户底座／指标模块 | 不是严格滚动十二个月；不同模块还有其他条件 |
| 报告日快照＋近 12 个月，按 `Accrued_Date` 输出 | 227697、234355 | 输出字段 `busi_date` 已换成历史计提日，不再等于读取源表时的快照日 |
| `Accrued_Date = Strt_Pric_Date` | 新增规模、部分交易笔数、部分标签 | 取开仓／期初日样本，不是把所有合约日都当成一次新交易 |
| `Accrued_Date = 报告日` | 当日存量、持仓底座、前十大标签 | 取存量时点，不是期间求和 |
| `Sett_Time` 按季度范围过滤 | 年度创收的奖励、部门交叉销售奖励 | 与逐日创收不是同一种时间；年度创收再按年份归集 |
| `Perf_Marg_Date`、关系起止日 | 垫资、追保及客户映射 | 发生日期与客户关系有效日期要分别看 |

例如报告日为 2026-09-22：“上一年年初至今”是 2025-01-01 至 2026-09-22；“近 12 个月”宏表达的是另一种边界。本文按 SQL 宏表达区分它们，尚未检查调度引擎对月底等特殊日期的实际展开。

### 4.3 最后区分金额：四种数字不能互相代替

| 数字 | 直接来源／计算位置 | 不应怎样解释 |
| --- | --- | --- |
| 业务规模 | 创收日报的 `Init_Nom_Prin`、`Dyna_Nom_Prin` | 动态本金不是收入；多天余额相加不是累计新增 |
| 合约创收 | 创收日报的 `Curr_Rev`；另有 `Opt_Npv_Curr_Rev` | 不是 118141 的销售分配收入，也不能直接当客户投资收益 |
| 持仓盈亏 | 227869 另读结算资金流水和估值结果；228241 另读互换腿估值 | 名称都有“盈亏／收益”，不代表同一公式、主体和时间范围 |
| 交叉销售奖励 | `T98_OTC_DERI_UNDRL_INCOME_RWD_SUM.Dev_Dept_Rwd` | 不是把 `Curr_Rev` 再求和；有奖励记录也不能证明实际支付到账 |

年度创收把 `Busi_Type` 为 OPTION／TRS 的收入分开，又将 `Undrl_Curr != 'CNY'` 的收入列为跨境创收。**跨境是重叠维度，不是第三块互斥收入**；这里程序以标的币种判断，是否符合业务上所有“跨境”的定义尚需确认。

当前图可见奖励汇总表不止一个写入任务：包括 109089 与 203358。这里两份客户报表都限定 `src_tbl='ODATA_N_OIS.G_CROSS_INCOME_REWARD'`，并且本轮核到 203358 读取该源表。因此说明应落到这一来源分支，而不是把整张奖励汇总表的所有来源混用。尚不据此宣称已经做完写入覆盖及重复数据验证。

## 六、用同一客户看各张报表为什么不能随便对账

以下是**构造的下游聚合示例**，金额统一用万元展示，不是生产数据，也不是上游创收公式的验算。

假设客户甲在 2026 年的有效样本中：

- 期权创收合计 120，互换创收合计 30；其中标的币种非人民币的创收为 20。
- 对应年度奖励汇总为 8。
- 报告日动态本金：期权 600，互换 400。
- 样本各行、客户映射和奖励聚合均无重复匹配。

**年度创收**展示期权 120、互换 30、跨境 20、交叉销售奖励 8。期权＋互换创收为 150，不能再加跨境 20 得到 170；奖励 8 也不是客户交易收益。

**规模序列**在该报告日对应的历史日期行展示期权 600、互换 400。假设前一日互换本金为 350，两天差额是 50，但 227697 的当天结果是 400，SQL 没有输出这个 50。

**标的持仓分析**把该日规模进一步分到标的和业务类型；其 `current_pnl` 仍为空。要看盈亏，需要 227869 的另一套资金／估值计算，不能由 400 的规模直接推出赚了多少钱。

**业务统计**还限定合约期初定价日不早于 2025-04-01。若客户甲的期权样本包含更早开立的合约，这张表就可能不含它，而年度创收未施加这项筛选；两表总额不同不必然是算错。

**客户综合指标／标签**的额度、追保、垫资仍无法由上述数字推出，需要读取各自的风险资料。“客户经营金额已经讲清”与“客户风险画像已经讲清”是两项不同工作。

## 七、复杂部分已经怎样拆开

### 7.1 客户综合指标：先按业务组，不按 JOIN 个数

229121已按以下业务组建立[实际SQL主脚本与模块](05_客户综合指标_229121/README.md)：客户底座加12路并列补充，主脚本直接显示JOIN/ON，类别计数、履保/追保权重、垫资统计另沿原嵌套边界拆出。下图是阅读分组，不改变生产SQL结构：

```text
客户范围与联系销售（主表，决定谁能出现）
   ├─ 交易评价：两类胜率、互换月换手率
   ├─ 履保与额度：履保比例、追保线、存续履保规模、获批额度／类型
   ├─ 风险与保障：及时追保、垫资展示、增信措施
   └─ 互换经营金额：平台费、券息、佣金
                         ↓
               按实际客户键并列连接、输出
```

这里没有“先算完胜率，才能计算履保”的串行关系。[客户与胜率](05_客户综合指标_229121/业务说明_01_客户与胜率.md)、[履保额度与追保](05_客户综合指标_229121/业务说明_02_履保额度与追保.md)、[互换活跃与费用](05_客户综合指标_229121/业务说明_03_互换活跃与费用.md)共用一位客户的完整构造例子；主脚本保留五路USCC和七路公司名匹配。

### 7.2 持仓盈亏：核心是两套金额如何落到同一客户和标的

227869已拆成[结算与估值两路独立识别→UNION及汇总→当前持仓匹配→贡献比例](03_交易与盈亏/02_持仓盈亏_227869/README.md)。其中估值继续分为客户输入、标的识别、按客户标的汇总；两路金额并列，不是资金流水先加工成估值。

必须保留的关键规则包括：资金流标的代码优先、期权结构回退、互换多个标的拼接；资金与估值使用的源分区不同；合并写的是 `UNION` 而非 `UNION ALL`；最终按客户名称和标的代码连接。不能为追求整齐把这些改成一套公共连接。

### 7.3 客户标签与协同关系：规则不同，就保留不同解释

- 标签分为规模排名、交易属性、垫资规则；不能把所有标签都描述成“满足条件打标”，省略窗口、排序和客户归属。
- 部门交叉销售先展开四个固定栏目，再补资料。看到四行不等于四类合作都发生过；“有关系”与“有奖励金额”也不是一套判断。
- 商机转介的部门范围可能与其他栏目重叠，四行金额不应未经证明直接相加成唯一奖励总额。
