# 交易与盈亏：先分清合约表现和标的贡献度

两张表都提到盈亏，但不是同一个指标换一种展示。它们选择的客户记录、收益来源和分母各不相同。

| 问题 | 228241 互换交易统计 | 227869 持仓盈亏 |
| --- | --- | --- |
| 基本对象 | 互换的期初日合约记录 | 报告日的客户标的持仓 |
| 金额来源 | 当前互换腿累计未实现＋已实现收益 | 入选资金快照中的历史结算金额＋报告日指定估值要素 |
| 输出粒度 | 客户＋期间，附交易笔数排名 | 客户＋标的代码和名称 |
| 比例分母 | 胜率用估值匹配后合约数；收益率用全部入选开仓本金 | 当前匹配结果按公司名计算的盈亏绝对值合计 |
| 不应解释为 | 完整生命周期、年化收益，或全部互换客户的无缺失胜率 | 按本金计算的投资收益率，或客户全部历史标的的收益分布 |

```text
共同创收日报
  ├─ 期初日互换记录 → 合约类型排名＋当前腿估值 → 228241交易统计
  └─ 报告日持仓记录 ← 历史资金＋当前估值      → 227869持仓盈亏
```

先读[互换交易统计](01_互换交易_228241/README.md)，理解“同一指标的分子分母也可能不是同一批记录”；再读[持仓盈亏](02_持仓盈亏_227869/README.md)，理解“有历史盈亏不代表当前报表一定展示它”。

两份任务各保留实际主脚本、模块、完整SQL和连续算例。共享的[render.mjs](render.mjs)仅展开本目录白名单任务内的平铺SQL引用，不替换宏、不执行SQL，也不创建生产视图。它沿用第一批已审的路径和生成文件保护，具体计算验证见各任务检查。

金额币种、盈利正负的经济视角、数据是否唯一完整仍以源系统和生产数据核验为准。SQL可以证明程序怎样累计与连接，不能仅凭“盈亏”“胜率”等字段名确认业务制度。
