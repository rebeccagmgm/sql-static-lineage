# 持仓盈亏：结算资金和当日估值，怎样落到客户当前持有的标的上

任务 **227869**，结果表 `DM_OTC_N.BI_OTC_HOLD_PNL`（OTC持仓盈亏表）。依据2026-09-22平台SQL。

**先用创收日报确定客户今天有哪些标的及规模，再给这些标的补一份“历史结算资金＋当日估值”的组合金额。比例是该标的盈亏相对客户当前展示标的盈亏绝对值总和的贡献，不是盈亏除本金的投资收益率。**

这里不读取`OTC_REV_DAILY_RPT.Curr_Rev`作为盈亏。此前讲清的“客户给我司贡献多少创收”和本表的盈亏来源不是一套算法；本表也未自行换汇或统一资金收支正负号，经济含义和币种还须按源口径确认。

## 一、先把三路资料放对位置

```text
结算资金快照                          当日估值结果
  选快照→客户映射→识别标的                客户映射→识别标的
             │                               │
   按客户名称＋标的汇总结算金额      按客户名称＋标的汇总两个估值要素
             └──────── UNION ────────────────┘
                         │ 注意是去重并集，不是UNION ALL
               按报告日＋客户名称＋标的再求和
                         │ pnl：待匹配的盈亏
                         │
创收日报当日持仓底座 ─── LEFT JOIN ───┘
公司USCC＋名称＋标的代码/名称      匹配只用客户名称＋标的代码
                         │
             金额/10000；缺盈亏补0；计算贡献比例
                         ▼
                   客户标的报告日结果
```

资金与估值是**并列输入**，不是结算金额先加工成估值。最终持仓底座又是独立一路，它决定哪些行能展示：一份已经退出底座的标的，即使历史盈亏存在，也不会由LEFT JOIN新增一行。

## 二、先走一份能完整复算的正常例子

以下全部为**构造数据**，报告日2026-09-22，客户名称“示例客户”、USCC为U001；所有身份与标的连接恰好一条。为复算，**本例假定两种来源金额都用元且符号可直接相加**；这是构造输入的前提，不是已核验真实源币种。

### 2.1 当日持仓底座先决定三行

创收日报在报告日快照中，`grp_id`属于01／02／03且`Accrued_Date='2026-09-22'`：

| 标的代码／名称 | `Dyna_Nom_Prin`动态本金（元） | 05汇总后规模 |
| --- | ---: | ---: |
| AAA／标的甲 | 1,000,000 | 1,000,000 |
| BBB／标的乙 | 2,000,000 | 2,000,000 |
| CCC／标的丙 | 500,000 | 500,000 |

分组键是USCC＋公司名称＋标的代码＋标的名称，没有业务类型，所以同客户同标的的期权／互换本金可能合并。它也没有筛“本金>0”；零、负数、NULL的组不因这一段自动消失。

### 2.2 结算与估值分别汇总

资金源选中的`h15`快照共有100,001行：两条合格结算资金，另99,999条其他类型填充记录。**阈值数的是全部源记录，不是已经筛完的两条结算记录。**构造这个数量只是为了执行真实条件，不表示生产数据。

| 来源 | 关键输入 | AAA金额 | BBB金额 |
| --- | --- | ---: | ---: |
| 历史结算资金 | `vr_cap_amount`；2026-09-01发生，类型含“结算”，有备注并能匹配客户 | 200 | -500 |
| 当日估值 | `result`；分区日与business_date均为报告日，指定两个要素之一 | 800 | 100 |

CCC没有对应资金或估值。两路先各按客户名与标的汇总，输出都是“报告日、客户名、标的、金额”四列。

正常例子中两路四列记录并不完全相同，所以UNION不删除其中任何一条。主脚本再次按报告日＋客户名＋标的求和：

```text
AAA：结算200 + 估值800  = 1,000
BBB：结算-500 + 估值100 = -400
CCC：pnl中没有这一标的记录
```

这并不表示“当日赚了1,000”：其中结算一路是历史期间累计金额，估值一路才限定报告当天。`current_pnl`的展示名不能替代实际时间范围。

### 2.3 连接、万元展示、贡献比例

持仓按公司名称和标的代码连接pnl。分母按结果中的**公司名称**计算：

`|1,000|＋|-400|＝1,400`。

| 标的 | 规模（万元） | 当前盈亏展示（万元） | 盈亏比例 `pnl_ratio` |
| --- | ---: | ---: | ---: |
| AAA | 100 | 0.1 | 1,000／1,400＝5／7≈71.43% |
| BBB | 200 | -0.04 | -400／1,400＝-2／7≈-28.57% |
| CCC | 50 | 0 | 缺匹配，输出0 |

数据库比例保存小数，不乘100。这里正负体现源组合金额方向，**不能仅凭这个符号断言客户赚还是我司赚**；示例只是原符号加总。

比例分母不是本金350万元，也不是净盈亏600元。它表达的是相对于绝对盈亏总量的带符号贡献；CCC的0也不证明已查明其真正盈亏为0，只说明本查询没取得非空盈亏。

## 三、正常例子之后，单改一个条件会怎样

### 3.1 只把AAA估值800改为200：UNION会改变加总

两路此时都输出“2026-09-22、示例客户、AAA、200”，四列完全相同，`UNION`只保留一条。最终AAA为 **200，不是400**；BBB仍为-400，比例变为1／3与-2／3。

原程序没有来源标签参与UNION。因此不能无条件用“结算＋估值”当作加法恒等式，也不能在整理时把UNION悄悄改成UNION ALL。是否应保留这一业务行为，需要另作口径确认。

### 3.2 只移除AAA的当前持仓：历史盈亏不再展示

pnl仍有AAA的1,000，但05没有AAA底座，最终只输出BBB、CCC；窗口分母变为400，BBB比例变成-100%，CCC为0。

这解释了为什么“历史累计盈亏相同，今天看到的比例却变了”：窗口样本由当前持仓底座决定，不是对客户所有历史标的做全量比例。

### 3.3 同代码增加一个名称：盈亏可能重复接入

只为AAA增加一组“AAA／甲的新名”持仓。05因名称不同保留两组，06匹配却不看标的名称，两组都接到同一份1,000盈亏：

```text
AAA旧名：1,000；AAA新名：1,000；BBB：-400；CCC：0
分母变为2,400
两个AAA行各占5/12，BBB占-1/6
```

此时比例绝对值加起来仍可等于100%，但盈亏已经重复展示。**比例看起来归一化，不是连接正确性的证明。**同名客户有两个USCC也有类似风险：底座按USCC分开，而连接与窗口都只看公司名称。

## 四、资金快照、客户身份、标的各怎么选

### 4.1 快照：取“超过十万行的最新日期”，不是“数据最多的日期”

02实际顺序是：

1. 只看资金表 `busi_date='h15'` 的记录。
2. 按 `src_busi_date` 计总行数。
3. 保留 **`COUNT(*)>100000`** 的日期，再取其中最大日期。
4. 在选中的源日期内筛资金类型含“结算”、备注非NULL。

这里`LIKE '%结算%'`也能匹配“未结算”，`IS NOT NULL`也允许空字符串备注；它们是程序的文字／空值条件，不足以证明资金已经完成结算或备注格式有效。

因此100,000恰好不够，100,001才够。假设旧日期100,002行、较新日期100,001行，会取较新日期；不是因为旧日期记录更多就选旧的。这个阈值不能证明完整性、业务正确或结算资金齐全。

源日期选择没有`<=报告日`限制。另一个资金发生日期过滤会限制`vr_cap_busidate<=报告日`，两者不能合并解释成“必定使用报告日之前的源快照”。没有任何源日期达标时，MAX为NULL，这一路就没有命中，但最终仍可展示估值或补0。

资金发生日期先 `SUBSTR(...,1,10)`，下界却写 `'2021-01-22 00:00:00'`。本整理原样保留；在本测试的字符串比较下，1月21日和22日都未通过，23日通过，不能直接声称1月22日当天一定包含。具体隐式类型／字符串比较边界仍应按生产引擎核验，不靠文案补成一个日期条件。

### 4.2 客户：两路都是INNER JOIN，但用的源字段不同

| 路径 | 来源字段 | 匹配规则 | 结果 |
| --- | --- | --- | --- |
| 资金 | `d_value_report_cap_flow_p.key_ctpty_id` | 等于`d_ref_counter_party_p.id`，固定h15 | 取得`ctpty_legal_entity`法律主体名称 |
| 估值 | `d_value_report_element_result_pb.remark` | 等于同一交易对手表id，固定h15 | 取得同一用途的名称 |

两边客户表都写`DISTINCT(id,ctpty_legal_entity)`，只去掉相同二元组，不保证一个id只能有一个名称。客户映射不存在时，原金额会在INNER JOIN处消失；最后持仓仍保留并可能显示0，而不是报“客户映射缺失”。

资金的 `vr_cap_remark` 又有另一用途：**精确等于**交易表 `d_trd_otc_trade_p.internal_trade_id`，拿到 `key_otc_trade_id`。不是从一段自由备注中解析交易号。这个连接是LEFT JOIN；只要资金自己有标的代码，交易键缺失也可能继续走完，但备注本身仍必须非NULL。

### 4.3 标的：只在NULL时回退，互换多标的拼成一个值

资金优先级：

```text
资金自身 vr_cap_undrly_code
    NULL才取 → 期权结构 underlying_wind_code
        NULL才取 → 互换持仓代码去重、排序、逗号拼接
```

估值没有资金自身代码这层，直接从期权结构回退互换拼串。期权结构和互换当前持仓／腿表均读固定`h13`分区，不是报告日分区。

互换识别沿 `d_pos_trs_leg_current_pos_p.KEY_LEG_ID → d_ref_trs_leg_p.KEY_LEG_ID → key_otc_trade_id`，把持仓代码 `COLLECT_SET → SORT_ARRAY → CONCAT_WS`。假设同一交易持仓有BBB、AAA、AAA，拼成 **`AAA,BBB`**。它不是AAA和BBB两个可独立匹配、分配的金额行。

最终持仓若分别是AAA、BBB，`AAA,BBB`都不能与它们相等，组合盈亏可能落不到任何持仓行；只有持仓代码本身也恰为`AAA,BBB`才会匹配。资金代码为空串也不会回退，`wind_code IS NOT NULL`还允许空串通过；不要把“非NULL”写成“有效证券代码”。

## 五、估值到底取什么，与资金日期有什么差别

[04估值](04_当日估值汇总.sql)同时限定：

- `grp_id='h15'`。
- 估值源表 `busi_date=报告日`。
- `SUBSTR(business_date,1,10)=报告日`。
- `element_id`只取`vr_opt_contractPV_eur`（期权合约现值）与`vr_trs_floatIncome_eur`（互换浮动收益）。

源 `business_key`直接匹配期权／互换交易键，不像资金先经备注找内部交易号。识别标的后按客户名称、估值业务日、标的求和；这一路没有资金侧的`wind_code IS NOT NULL`筛选，但最终NULL代码不能用普通等号匹配持仓。

本任务直接把 `result`转DOUBLE求和，既没有按要素取不同正负号，也没有引用汇率。源名含`eur`不等于已经证明输出统一为欧元／人民币；原SQL注释中的“元”和目标DDL的“万元”只证明标签与`/10000`行为，不能替代源金额币种和方向的核验。

这也是本篇正常算例显式声明“统一用元、源符号可相加”的原因：可以验证程序如何组合，不把构造前提冒充真实业务事实。

## 六、最后的连接与比例，有哪些不能省略的边界

| 场景 | 原SQL行为 | 读者应如何解释 |
| --- | --- | --- |
| 持仓有、盈亏无 | 仍输出持仓，盈亏与比例补0 | 0可能是未匹配，不是确认无盈亏 |
| 盈亏有、持仓无 | 不输出该标的，亦不进比例分母 | 本表不是全部历史盈亏清单 |
| 本金0、负数或NULL | 没有正本金筛选，组仍可存在 | 不能把底座叫作“只保留正持仓” |
| 同名不同USCC | 底座分开，匹配到同名盈亏，窗口共用公司名称 | USCC不是最终盈亏匹配键 |
| 同代码不同标的名 | 底座分开，但盈亏按代码重复接入 | 名称参与分组却不参与匹配 |
| 全部未匹配 | 每行因`pnl.profit_loss IS NULL`输出比例0 | 不需要分母有非空值才能保留行 |
| 分母为0 | CASE给0，除法还用NULLIF保护 | 比例不是未经保护直接除0 |
| 部分来源为NULL金额 | 聚合可能忽略NULL，最终COALESCE可能补0 | 不能反推原始记录都是0 |
| 源表、结构或客户多匹配 | 可复制金额，再被SUM累计 | 聚合不等于消除连接重复 |

只要一个公司名窗口内有非零可用金额，比例是按**连接后的行集**计算；如果业务希望按唯一客户或唯一标的计算，还要先证明这些连接粒度与数据质量，不能在这次文档建设中擅改口径。

## 七、交付层不等于上述DM计算层

2026-09-03采集的搬运任务230263在读取`dm_otc_n.bi_otc_hold_pnl`时，额外要求`underlying_name NOT LIKE '%;%'`：名称含分号的记录退出，NULL名称也不能通过；选出的字段还不包含`underlying_code`。这不是一条完全原样复制所有行、所有键的链。

若核对234355当日标的规模与本表持仓本金，应先统一源快照，在DM层按USCC＋客户名＋标的代码＋标的名对齐，再跨业务类型求和；不能直接把这条关系用于已缺少代码且另有过滤的gf_otc结果，还须核对另一侧搬运规则。

[单客户测试样本](../../06_单客户贯穿核验/README.md)还发现：3月测试下游盈亏全NULL、表结构与9月输出不同。因此本篇“缺匹配补0”等规则只解释当前冻结查询，不把旧下游NULL当作已由当前SQL算得的0，也不凭9月搬运配置推断3月实际运行原因。
