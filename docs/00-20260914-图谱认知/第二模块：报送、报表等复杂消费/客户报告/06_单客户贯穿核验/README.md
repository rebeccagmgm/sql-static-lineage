# 单客户贯穿：同一客户的数字，为什么不能直接放在一起比

**先看这一页，再去读各张SQL。**这里采用2026-09-23从`gf_otc`测试库实际取得的一位客户样本，匿名记为“案例客户A”。主要报告日为2026-03-25，**不是生产客户事实，也不是9月SQL的运行结果**。

这位客户在业务统计中同时有期权、互换类别，但当日期权存量为0、互换存量为正。它适合说明“做过业务、还有收入、当前还持仓”是三件不同的事，不刻意寻找所有指标都齐全的样本。

## 一、先把这份报告摆在同一张桌上

| 看到的数字 | 实际来源 | 这次可以怎样读 |
| --- | --- | --- |
| 期权存量0；年内期权`real_pnl`为-1,672,774.70 | 228008业务统计，3月25日 | 存量0不等于历史收入0；`real_pnl`在当前SQL读的是我司创收，不是客户投资盈亏 |
| 互换存量1,819,276,731.75 | 同表三个互换类别求和 | 本样本业务统计的元金额基线；不含义不明的比例列加总 |
| 互换规模走势18.19 | 227697的测试下游表，同日 | 数值疑似亿元缩放，不能照“元”注释与上一行直接比较 |
| 持仓规模合计181,927.65万元 | 227869测试下游67行，同日 | 换成元为1,819,276,500，与业务统计还差231.75元，不把“很接近”写成完全对平 |
| 履保规模＝已用额度＝216,012.18万元 | 229121客户综合指标，同日 | 两列同值符合当前SQL同式赋值，不是两个独立额度系统互相验证 |
| 年度互换创收136.43万元；业务统计年内互换创收合计152.23801万元 | 227701年度2026行、228008的3月25日结果 | 同源字段也不能跳过源快照和样本范围直接对账 |
| 持仓盈亏67行全部NULL | 227869测试下游，同日 | 未拿到盈亏值，不是客户盈亏为0；而且不能由9月SQL的“缺失补0”直接解释 |

下文只拆这些已经出现的差异，不再复制九张报表的完整业务说明。所有数值来自[查询结果](02_查询结果.json)，对应[取数SQL](01_案例取数.sql)；两个文件是证据附件，不需要先读。

## 二、18.19到底是什么：先核单位，不能直接判金额错

把相邻三天按同一客户、同一天放在一起：

| 日期 | 业务统计互换存量 | 除以1亿、保留两位 | 测试规模走势值 |
| --- | ---: | ---: | ---: |
| 3月23日 | 1,637,787,455.38 | 16.38 | 16.38 |
| 3月24日 | 1,733,450,691.75 | 17.33 | 17.33 |
| 3月25日 | 1,819,276,731.75 | 18.19 | 18.19 |

三天都吻合，**支持“这些测试值有亿元缩放特征”**。但还不能说“已找到除以1亿的代码”：

- 当前保存的227697查询直接`SUM(Dyna_Nom_Prin)`，没有除以1亿。
- 2026-09-03采集的搬运任务230265也是原样选择两列，没有缩放。
- 2026-08-31的较早源任务证据同样没有缩放；都不是3月实际执行版本。

所以正确结论是：**数值模式已定位，缩放在哪一层发生还没定位。**历史查询版本、旧导入、人工测试写入等都只是待排查方向，不能选一个当事实。原来的9月SQL说明仍保留“源单位不转换”；现在补上不能据此解读旧测试下游的边界。

读者以后遇到“差一亿倍”的两个数，应先确认执行版本与单位，而不是马上去改SUM或JOIN。

## 三、为什么已用额度比持仓规模还大

同日三份规模，先换成相同单位：

```text
业务统计互换存量：181,927.673175 万元
持仓盈亏表规模和：181,927.65     万元
履保规模/已用额度：216,012.18     万元
```

前两者差0.023175万元，即231.75元。67行持仓在下游以万元保留两位，会有逐行舍入的可能；**本轮没有舍入前明细和同版上游，不把差额已经证明为舍入误差。**

后两者差34,084.53万元，不能也用“精度问题”解释。当前229121的两列来自同一个结果：筛选启用STATIC/DYNAMIC履保参数的主合约，再按客户名称累计主合约动态本金。持仓表和业务统计则从创收日报取数，且有各自筛选。

因此：

- “已用额度＝履保规模”是当前SQL程序定义；本样本也同值。
- “已用额度＝全部当前持仓”不是原SQL承诺的等式。
- 本样本差额可能涉及取数范围、身份关系、重复参数或历史实现，但尚未由明细复算定因。
- 不能直接拿获批额度减这列，再宣布得到了业务认可的可用额度。

需要回查时，只读[履保规模输入](../05_客户综合指标_229121/08_履保规模.sql)及[对应说明](../05_客户综合指标_229121/业务说明_02_履保额度与追保.md)，不必重读229121的所有JOIN。

## 四、同样叫收入，136.43和152.23801为什么不能直接对平

业务统计三个互换类别的年内`real_pnl`为：

`96,511.28＋0＋1,425,868.82＝1,522,380.10元＝152.23801万元`。

年度2026行的互换创收为136.43万元，两者相差15.80801万元。当前SQL中两者确实都来自`Curr_Rev`，但存在两道比较门槛：

1. **时间没有证成一致。**年度行只保存year，数据同步时间为3月23日；业务统计3月25日结果的同步时间是3月26日。同步时间不是源快照日，不能倒推出年度金额恰好算到哪天。
2. **样本范围不同。**业务统计限定grp01/02/03、期初定价日不早于2025-04-01；年度创收没有这两项限制。不能只从聚合结果中把旧合约或额外分支补回来。

期权年度值-167.28万元，与业务统计-167.27747万元舍入后接近，只是这一列的数值吻合，**不能证明整个客户两张表使用同一批输入**。

正确核验方式是：取同一源快照，先把被业务统计排除的合约单独列出，再比较共同样本的`Curr_Rev`；跨境创收和奖励不加到这条等式里。现有来源暂未允许这一步完成，保留差额而不编解释。

## 五、盈亏全NULL，查下去还发现“搬运”并非完全原样

这位客户67条持仓的`current_pnl`和`pnl_ratio`均无值。测试表有`underlying_type`，却没有9月查询输出的`underlying_code`。9月SQL又明确给缺失盈亏补0。

这三项共同说明：**旧测试落表结果不能直接当作当前227869查询的完整复现。**既不能把NULL说成0，也不能直接认定当前查询的COALESCE失效。

继续查本地搬运证据发现，230263不是纯复制：

```text
DM层227869：当前持仓＋盈亏，带标的代码
       ↓ 230263
额外排除：标的名称含分号；标的名称为NULL也不能通过NOT LIKE
选择输出：不包含underlying_code
       ↓
gf_otc测试下游：不能按原完整标的键直接复算
```

该配置没有把金额改为NULL的表达式，因此它解释了**哪些行、哪些键可能在交付时减少**，但不能解释这67行盈亏为什么全NULL。配置采集于9月3日，也不能代替3月运行日志。

这已补回[持仓盈亏原说明](../03_交易与盈亏/02_持仓盈亏_227869/README.md)。今后说两张报表可以对账，必须先说明比较的是DM计算层还是gf_otc交付层，不能跨过搬运过滤。

## 六、九张报告的样本覆盖：缺的不能装成0

| 报表 | 这次测试库证据 | 在案例中的处理 |
| --- | --- | --- |
| 规模走势、业务统计、客户综合、持仓盈亏 | 有3月25日该客户记录 | 已取数并核上面差异 |
| 年度创收 | 有2025/2026两行，但没有源快照日 | 已展示；不当同批收入对账 |
| 交易统计 | 全表8行的报告日均NULL；该客户2行 | 可以读字段样本，不能充当3月25日胜率 |
| 客户标签 | 全表100行的报告日均NULL；该客户10个标签 | “有垫资”存在，不证明3月25日垫资资格；不与当日追保直接拼因果 |
| 部门协同、标的持仓 | 两张测试表全表0行 | 未覆盖，不能填0或用构造数据伪装实样 |

案例客户综合里的结束合约创收正值占比为0.625；无报告日交易统计的胜率为0.57377；期权类别串还有另一套比例。**日期已经不可比，算法也不同**，不要求三者相等。三种定义分别见[客户与胜率](../05_客户综合指标_229121/业务说明_01_客户与胜率.md)。

旧期权类别串实际为“个股期权:0.777777…”和“其他期权（除Risky和安全气囊X）:0.222222…”，而当前03.1只会输出“欧式期权”“安全气囊”。**旧串本身也不能由当前模块直接复算**，不能把当前两类别共同分母的说明移用到旧比例上。
