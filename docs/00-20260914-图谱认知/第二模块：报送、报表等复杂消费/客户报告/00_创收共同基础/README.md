# 创收共同基础：九张客户报表为什么都先读这张日报

`DM_OTC_N.OTC_REV_DAILY_RPT`（场外衍生品合约创收日报）把合约上的客户身份、业务类型、逐日本金、计提创收放在一起。九张客户报表以它为共同输入，但各自选取的客户、日期和业务范围并不完全相同。

**先看懂它提供什么，再看三个生产分支怎样算金额。**本篇是共同字段和记录关系的入口，不替代各分支实际公式。

当前已完成[期权创收](01_期权_230202/README.md)、[普通互换创收](02_普通互换_230204/README.md)和[金仕达创收](03_金仕达_223867/README.md)的细粒度说明、组装及算例审查。三个分支均已于 2026-09-22 取得平台 SQL，外层输出均为 74 列（含两个分区字段）。

## 一、两种日报，不要因为名字相近混用

| 对比 | 合约创收日报 `OTC_REV_DAILY_RPT` | 销售日报 `OTC_SALE_DAILY_RPT` |
| --- | --- | --- |
| 本专题关注的问题 | 客户名下的合约，在各计提日带什么本金和创收，如何汇总到客户 | 销售收入如何计算、调整、分配和累计 |
| 已核到的关键生产分支 | 230202 期权；230204 普通互换；223867 金仕达，已取得本次平台 SQL | 已有 118141 等销售收入专题 |
| 共享内容 | 合约主信息、逐日本金费用等 | 同样会用这些公共输入 |
| 不能直接搬用的内容 | 创收参数、创收公式、分支范围、估值分摊及费用扣减 | 销售参数、奖励调整与分配公式不能自动替代左侧规则 |

同一输入可以被两种业务算法消费。已经理解本金来源，不等于创收公式与销售收入公式相同。

## 二、一份合约为什么在同一次报告里出现很多天

以本次取得的三条生产查询共同的合约日连接为例：

```text
info：报告日的合约主信息快照
  PDATA_N.T98_OTC_DERI_COMP_SALE_INFO
       │ 按 agt_id（合约号）INNER JOIN
       ▼
det：逐日本金与费用记录
  PDATA_N.T98_OTC_DERI_COMP_SALE_ADTNL_DET
  取 det.busi_date 在该记录 Strt_Pric_Date～End_Pric_Date 之间的日记录
       │
       ├─ info 提供客户、业务类型、合约日期与基础金额
       ├─ det 提供这一天的动态本金和费用等
       ├─ 并列补估值、参数、行情、费用等资料
       ▼
创收日报输出
  busi_date   = 报告日宏（这一次快照）
  Accrued_Date = det.busi_date（这笔金额归属哪一天）
```

这里不在连接条件中把 `det.busi_date` 限成报告日，因此一份报告日快照中可以包含过去多天的合约记录。`INNER JOIN` 也意味着没有匹配日明细的合约不会靠主表自己生成一条结果。

这只是行结构的解释：没有核验源数据时，不能说“合约＋计提日一定唯一”。同号多主记录、日明细重复，以及后面的多条参数／估值匹配，都可能扩行。

已有公共说明可直接复用：[合约主信息](../../公共加工/01_合约主信息/README.md)、[107491 逐日本金与费用](../../公共加工/03_逐日本金与费用/README.md)。不要在本专题再复制一份同样的公共加工。

## 三、客户报表最常用的字段，实际从哪里取

下表的 `info`、`det`、`cp` 不是新表名，是上述生产 SQL 中的别名；共同字段来源已在本次平台快照核对，分支金额另行解释。

| 输出字段 | 中文用途 | 生产查询的实际来源／加工 | 消费时最容易混淆的地方 |
| --- | --- | --- | --- |
| `Agt_Id` | 合约编号 | `info.Agt_Id`，合约主信息 | 部分笔数 `COUNT(DISTINCT Agt_Id)`，不等于对全部日记录直接计数 |
| `Cutp_Pty_Id` | 交易对手客户编号 | `info.Cutp_Pty_Id` | 是客户资料关联键，不是统一社会信用代码 |
| `Cutp_Pty_Full_Name` | 客户名称 | `info.Cutp_Pty_Full_Name` | 不少报表按名称连接；名称相同不保证为同一业务主体 |
| `USCC` | 统一社会信用代码 | `cp.USCC`；`T01_CORP_CUST` 按 `cp.Pty_Id = info.Cutp_Pty_Id` 左连接 | 客户名称和 USCC 不来自同一个表达式；客户资料缺失时名称仍可能存在而 USCC 为空 |
| `Busi_Type`、`Contr_Type_Desc` | 业务类型、合约类型描述 | `info` 的同名字段 | 业务类型与报表输出分区 `grp_id` 不是同一概念 |
| `Init_Nom_Prin` | 初始名义本金 | 输出取 `info.Init_Nom_Prin` | 创收公式中还可能另用 `det.Init_Nom_Prin`；名字相同不能省略当前来源 |
| `Dyna_Nom_Prin` | 该计提日动态名义本金 | `COALESCE(det.Dyna_Nom_Prin, 0)` | 是余额类规模，不应将每天余额相加称为累计新增 |
| `Curr_Rev` | 当日计提创收 | 各生产分支的实际创收表达式 | 不是直接从主信息拿一个“收入”字段；必须继续看公式 |
| `Opt_Npv_Curr_Rev` | 当日期权 NPV 计提创收 | 期权按柜台、是否期初日及分摊规则计算；普通互换和金仕达固定为 0 | 与 `Curr_Rev` 是不同列，不应未经业务依据相加成唯一创收 |
| `Strt_Pric_Date` | 期初定价日 | `info.Strt_Pric_Date` | 用 `Accrued_Date = Strt_Pric_Date` 选初始日样本，不是把每天都算一次开仓 |
| `End_Pric_Date` | 输出的结束日期 | `COALESCE(info.Early_Term_Date, info.End_Pric_Date)` | 已经做了提前终止回退；空字符串不是 NULL |
| `Accrued_Date` | 计提日期 | `det.busi_date` | 决定期间累计和时点存量取哪一天 |
| `busi_date` | 输出快照日 | 报告日宏 `${yyyy-MM-dd}` | 决定读取哪一次整理结果，不代替计提日期 |
| `Trd_Cms` | 交易佣金收入 | 期权输出NULL；[普通互换按开平仓、比例/每股方式算毛佣金](02_普通互换_230204/08_毛佣金展示.sql)；金仕达取`co.ks_long_fee`累计佣金差分 | 不是净创收，也不是已经分给销售的佣金 |

客户资料 `cp` 还限定报告日、来源 `ODATA_N_OIS.O_OTC_DERIVATIVE_COUNTERPARTY` 和 `DEL_FLAG='0'`。这些条件属于生产时的匹配范围，不能只用“按客户号补 USCC”一句话替代。

## 四、先用两天记录区分本金和创收

以下为构造输入，只演示消费含义，尚不验证 `Curr_Rev` 的上游生产公式。假设同一客户同一合约，在 2026-09-22 的快照里有：

| 合约 | 快照日 busi_date | 计提日 Accrued_Date | 动态本金（元） | 当日创收（元） |
| --- | --- | --- | ---: | ---: |
| A | 2026-09-22 | 2026-09-21 | 1,000,000 | 100 |
| A | 2026-09-22 | 2026-09-22 | 800,000 | 80 |

- 取 9 月 22 日存量：800,000 元，不是 1,800,000 元。
- 取两天创收合计：180 元。前提是这两条为需要累计的创收记录且不存在重复匹配。
- 画规模序列：21 日 1,000,000、22 日 800,000。227697 输出这种逐日余额，并没有在 SQL 中算出 -200,000 元的差额。
- 计算新增交易：还需要期初定价日等条件，不能仅因有两条日记录就当作两笔新交易。

只改变一个条件：如果 22 日的动态本金缺失，生产的 `COALESCE(det.Dyna_Nom_Prin,0)` 会把该输出列变成 0；这不自动说明创收也为 0，因为不同创收分支可能使用费用、估值或未补零的其他字段。
