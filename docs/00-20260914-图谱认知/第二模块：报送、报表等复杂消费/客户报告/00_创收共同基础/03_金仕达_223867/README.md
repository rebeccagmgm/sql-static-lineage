# 223867 金仕达：累计资料怎样变成每天的客户创收

本分支生产 `DM_OTC_N.OTC_REV_DAILY_RPT` 的 `grp_id='03'`。先把合约与逐日明细连接起来，再补金仕达的利息、佣金、占资、成交及报盘费用，计算 `Curr_Rev`（当日计提创收）。客户报告继续按公司和日期汇总这列金额。

**这里不是 118141 的金仕达销售收入。**本任务直接扣每份合约匹配到的费用，不使用 118141 的跨合约系统费用二次分摊。以下实现依据 2026-09-22 取得的平台 SQL；旧图中的利息来源、占资基数和扣费系数已不适用于这份实现。

## 一、第一遍只沿一份合约走

```text
合约主信息 info ＋ 逐日明细 det
           │ 形成合约日，不保证实际数据唯一
           ├─ co：累计利息／佣金 → 按清算日差分
           ├─ bc：实际占资和 remain_contract → 最近交易日资料
           ├─ tc：累计成交金额 → 当日差分
           ├─ cas：报盘费用总计 → 当日差分
           └─ fc：成本参数 → 按生效日期展开
                        ↓
   B_LONG_SHORT_SWAP：利息－净占资成本＋佣金－成交扣费－报盘费
   其他类型：Curr_Rev = 0
                        ↓
   报告日快照中的合约日创收 → 客户年度／其他期间汇总
```

建议先看[主脚本](00_主脚本.sql)里的连接，再读[当日创收](02_当日创收.sql)，最后拿下文例子对照各项实际来源。74 列原始输出集中在[结果投影](01_结果投影.sql)，不用为了理解一项创收先逐列读完。

## 二、五项金额各自从哪里来

主脚本中，`info` 是 `T98_OTC_DERI_COMP_SALE_INFO`（合约主信息）；`det` 是 `T98_OTC_DERI_COMP_SALE_ADTNL_DET`（逐日本金与费用）。`info.Inr_Seri_No` 连接金仕达 `contract_code`（合约内部编号），不能改成客户号或万得标的代码。

| 创收中的项 | 原始来源和字段 | 怎样取这一天 | 在收入中的作用 |
| --- | --- | --- | --- |
| 利息 | `S_V_CONFIRMATION_OVERVIEW.ks_other_profit` | 按合约、清算日期排序，**前一行累计值－本行累计值** | 加入创收；“利息”是当前 SQL 的用途解释，字段元数据中文注释为空 |
| 占资成本 | `S_GF_BK_CONTRACT.actual_occupy_amt`、`remain_contract`；参数表 `value` | 占资资料取计提日当天或之前最近交易日；利率取计提日生效值 | `max(实际占资金额－remain_contract,0) × 成本率 ÷ 365` |
| 毛佣金 | `S_V_CONFIRMATION_OVERVIEW.ks_long_fee` | **本行累计值－前一行累计值** | 加入创收，同时原值展示为 `Trd_Cms` |
| 成交扣费 | `S_GF_BK_CONTRACT.long_trade_amount` | 本行累计成交额－前一行累计成交额，精确匹配计提日 | 日成交额 × `0.0000641`，从创收扣除 |
| 报盘费用 | `M_T_CMP_AGENT_STAT.cust_total_fee` | 报告日快照内先 DISTINCT 三列，再按合约、交易日期取总计差分 | 从创收扣除；不是自动解释为“未结”费用 |

其中 `S_*` 和 `M_*` 表均为 `ODATA_N_LSS` 下的金仕达来源表。成本参数来自 `ODATA_N_OIS.G_CLIENT_REVENUE_COEFFICIENT`，取未删除的 `KS_LONG_SHORT_SWAP / FUND_COST_RATE` 配置，不是销售收入资金成本专题中的参数表。

两个容易翻译错的字段，本次核了离线元数据：

- `remain_contract` 的注释是 **`【AI】合约保证金余额`**。AI 标记必须保留，不能当成已经确认的保证金定义；本文只确认程序将它从实际占资金额中扣除，并对差额取非负值。
- `cust_total_fee` 的来源注释是“交易对手方报盘费用总计”；同表另有 `cust_unsettle_fee` 才叫“交易对手方未结报盘费用”。原 SQL 行注释称“当日未结报盘费”与实际字段注释冲突，不能照抄成确定业务含义。

## 三、为什么不是同一种“取昨天”

| 位置 | 实际规则 | 不等于什么 |
| --- | --- | --- |
| 利息、佣金、成交额的窗口 | 原 SQL `LEAD(值,-1,0)`，同合约按清算日期取前一记录；缺前值默认 0 | 不一定是自然日昨天，也不能先只保留报告日再差分 |
| 报盘费窗口 | 报告日快照内，按合约和交易日期取前一记录 | 不等于清算日序列，也没有统一的最近交易日回填 |
| 占资 `bc` | `datekey2date(clear_date) = pretradedate(date_add(det.busi_date,1),1)` | 与其他三种精确按日匹配不是同一规则 |
| 成本率 `fc` | 生效日起至下一生效日前一天；最后一条覆盖至报告日 | 参数缺失不会自动取 0；重复生效日也未在此去重 |

例如非交易日没有当天利息、佣金、成交额和报盘费匹配行时，金额各自补 0，但占资可能仍取上一交易日。若成本率正常，创收可以仅剩负的占资成本。具体哪天是交易日由生产 UDF 决定，本地测试没有冒充交易日历核验。

## 四、一份合约、两天创收，连续算到年度金额

以下全为**构造数据**。合约 A 是 `B_LONG_SHORT_SWAP`；客户身份、源记录和日参数均唯一匹配。展示 2026-09-21、22 两个计提日，报告日是 22 日；18 日那行用作累计差分的前值，不把它当成本例要汇总的创收行。

### 1. 先给累计输入，不凭空给“当天利息”

| 清算／交易日期 | `ks_other_profit` 累计字段 | `ks_long_fee` 累计佣金 | `long_trade_amount` 累计成交额 | `cust_total_fee` 费用总计 |
| --- | ---: | ---: | ---: | ---: |
| 09-18 | 1,000 | 500 | 10,000,000 | 20 |
| 09-21 | 400 | 650 | 12,000,000 | 35 |
| 09-22 | -100 | 900 | 15,000,000 | 50 |

沿[利息和佣金差分](03_当日利息与佣金.sql)、[成交差分](04_当日成交金额.sql)、[费用差分](05_当日报盘费.sql)得到：

| 日期 | 当日利息：前减后 | 毛佣金：后减前 | 当日成交金额 | 当日报盘费 |
| --- | ---: | ---: | ---: | ---: |
| 09-21 | 1,000－400＝600 | 650－500＝150 | 2,000,000 | 15 |
| 09-22 | 400－(-100)＝500 | 900－650＝250 | 3,000,000 | 15 |

注意利息差分方向相反，这是实际程序规则，不根据“累计字段应该递增”的直觉改写。若 18 日恰是窗口可见的第一行，程序给它的利息是 `0－1000=-1000`；这解释了为什么不能任意截掉差分之前的历史记录。

### 2. 取占资资料及有效成本率

假设计提日映射后的占资资料如下；本例两个日期都有匹配记录。当前生效年成本率为 `0.0365`，按代码直接使用，不再除以 100。

| 日期 | 实际占资金额 | remain_contract | 非负净占资 | 占资成本 |
| --- | ---: | ---: | ---: | ---: |
| 09-21 | 4,000,000 | 1,000,000 | 3,000,000 | 3,000,000×0.0365÷365＝300 |
| 09-22 | 2,000,000 | 500,000 | 1,500,000 | 1,500,000×0.0365÷365＝150 |

这些金额不是从 `det.Dyna_Nom_Prin` 拿来的。动态本金仍作为报表规模输出，但本分支的占资成本有独立来源。

### 3. 扣费后形成 Curr_Rev

| 日期 | 利息 | 减占资成本 | 加毛佣金 | 减成交扣费 | 减报盘费 | 当日创收 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 09-21 | 600 | 300 | 150 | 2,000,000×0.0000641＝128.2 | 15 | **306.8** |
| 09-22 | 500 | 150 | 250 | 3,000,000×0.0000641＝192.3 | 15 | **392.7** |
| 合计 | 1,100 | 450 | 400 | 320.5 | 30 | **699.5** |

随后进入[年度创收](../../01_年度创收_227701/README.md)：这两行对该客户该年互换创收的贡献是 `699.5÷10000 = 0.06995` 万元。若年度还有其他合约／计提日，再按年度查询的范围累计；不能把这两行贡献冒充完整年度收入。

`Trd_Cms` 展示毛佣金 150、250，期间合计 400，已经进入创收公式，不能再加到 699.5 上。年度交叉销售奖励来自独立的奖励汇总，也不是这项佣金。

## 五、只改一个条件，结果为什么不同

以下以 09-21 的 306.8 元为起点，其余输入不变：

| 改变的条件 | 结果 | 原因 |
| --- | ---: | --- |
| remain_contract 改为 5,000,000 | 606.8 | 实际占资减它后为负，程序取 0，占资成本由 300 变 0 |
| 当天生效成本率改为 0.073 | 6.8 | 占资成本由 300 翻倍为 600 |
| 整条成本参数未匹配 | NULL | `fc.fund_cost_rate` 没有 COALESCE；并非按零成本计算 |
| 类型改为 OTHER | 0 | 最外层 IF 不进入多空互换计算；并不代表这份合约不存在或本金也为零 |

参数切换示例：若 09-01 生效率是 0.0365、09-22 新率是 0.073，则第一条覆盖到 09-21，第二条从 09-22 生效。此前两天连续例子将只有 22 日成本变为 300，该日创收由 392.7 变为 242.7。

`0×NULL` 仍会传播 NULL，所以即使净占资被截成 0，缺失成本率也不能解释为不影响收入。这里的本地数值测试证实了适配表达式的传播；仍不替代生产 Hive 对异常字符串等输入的行为核验。

## 六、连接和窗口有哪些不能省略的边界

- 合约范围保留原 SQL：报告日、OTC、金仕达分组、结束日期不早于 2022-01-01，以及三个客户排除名单。名单依据属于制度待确认项，不擅自删除。
- `det` 只按合约号连接；其自身日期过滤不等于强制所有资料统一按合约日去重。
- 利息／佣金和成交的窗口没有限定只读当天；报盘费则先限定报告日快照。
- 报盘费 DISTINCT 包含费用值。同一合约同一天有不同累计费用，仍可留下多行；窗口也没有同日记录的次级排序。
- 成本参数窗口不按币种分组。同一天多个配置、无下一配置等情况必须按原式核对，不能为了“公共取参”自行增加分组或去重。
- 模块中的窗口发生在各自子查询里；主脚本后续多条匹配仍可能扩行。本文不宣称已验证真实数据唯一性。
- 365 与 0.0000641 是程序固定值，制度为什么如此规定、费用计价币种及最终结算事实，需要额外业务证据。
- `gfgreatest` 的普通数值最大值用途有知识库资料；NULL、非法字符串、隐式转换等完整 UDF 行为尚未实机核验。本公式在调用前先对两个占资字段 COALESCE 为 0。
