# 普通互换客户创收：日息差、净佣金、分红与指数盈亏怎样形成日报

任务 **230204**，写入共同创收日报 `DM_OTC_N.OTC_REV_DAILY_RPT` 的 `grp_id='02'` 分支。依据2026-09-22从平台取得的当前SQL；不再以只有调度覆盖的旧图谱节点代替生产SQL。

**先走一份固定利率互换“开仓→次日部分平仓→两日创收→年度汇总”的完整例子，再比较浮动利率、多头持券、指数增强。**它不是所有普通互换都用同一公式：符合条件的四条路径依次判断，其余当日创收为0。

## 一、先看清金额来自哪里

```text
报告日主合约 info ──INNER JOIN── 合约逐日明细 det
                            │
      ┌─────────────────────┼────────────────────────┐
      │                     │                        │
 客户／标的身份       开仓腿参数＋平仓分红事件       当日利率／汇率／生效成本
      │                     │                        │
      └─────────────────────┼────────────────────────┘
                            ▼
                    Curr_Rev的同一个CASE
                    按优先顺序只选一路
               ┌────────────┼────────────┬──────────────┐
               │            │            │              │
           ①固定跨境    ②浮动跨境    ③多头持券     ④指数增强 ← 11账簿盈亏u＋上传分配额x
               │            │            │              │
               └────────────┴─────┬──────┴──────────────┘
                                 ▼
                        本行Curr_Rev净创收
                  （四条均未命中则输出0）

  sh开仓参数／evt事件 → 独立计算Trd_Cms毛佣金展示，不再次加回Curr_Rev
                                 │
                                 ▼
              合约×计提日输出：报告日快照、分支02
```

上述输入多数并列连接，不是先有客户资料才能计算汇率。[00主脚本](00_主脚本.sql)先引用输出，再依次显示输入；[09统一输出](09_统一输出.sql)实际引用[07净创收](07_当日净创收.sql)和[08毛佣金](08_毛佣金展示.sql)。这是原查询SELECT/FROM的书写结构，不声称物理执行顺序。

### 1.1 一行与入口范围

[01底座](01_合约客户与逐日底座.sql)读报告日的[合约主信息](../../../公共加工/01_合约主信息/README.md)，限定OTC账簿、`grp_id='02'`、协议类型不是`TRS_INNER`、`COALESCE(提前终止日,期末日)>='2022-01-01'`。这不是“只取报告日仍存续的合约”，也没有按协议状态再筛一次。

按`Agt_Id`合约编号连接[107491逐日明细](../../../公共加工/03_逐日本金与费用/README.md)，后者只要求明细日期落在明细自身起止日内。没有明细就不出现；本任务没有另写“计提日<=报告日”或按info提前终止日再次过滤。

输出可按合约日理解，但不是唯一性承诺。客户、工具、腿持仓、上传分配表多匹配会扩行；窗口分母在**所有JOIN之后**形成，不能只检查最终是否重复展示。

## 二、正常例子：一份固定利率合约，两天算到底

以下是**构造数据**，不是生产客户。报告日为2026-09-22，客户甲一份合约A于2026-09-16期初定价，17日发生部分平仓；所有关联资料各命中一条。

类型条件为 `Agt_Clas_Cd='TRS_SAC_OTC'`、`Src_Contr_Type='S_CROSS_SWAP'`、`Src_Undrl_Type='EQUITY'`、`Cros_Crrc_Type_Cd='COMPOSITE'`，因此命中07的第一分支。标的币种HKD；结算币种对应的计提日人民币汇率为0.8。

### 2.1 把两天的输入放在一起

| 实际字段与中文含义 | 9月16日开仓 | 9月17日部分平仓 |
| --- | ---: | ---: |
| `info.Init_Nom_Prin` 主合约初始本金 | 3,650,000 | 3,650,000 |
| `det.Dyna_Nom_Prin` 逐日动态本金 | 3,650,000 | 2,920,000 |
| `info.fixed_rate` 固定腿利率 | 6% | 6% |
| `co.FUND_COST_RATE` 资金成本利率 | 3.5% | 3.5% |
| `co.MARGIN_FIXED_RATE` 保证金固定利率 | 0.5% | 0.5% |
| `sh.Cms_Mode_Cd` 佣金模式 | 1：按金额 | 1：按金额 |
| `sh.Trd_Fee_Rate` 交易费率 | 0.1% | 0.1% |
| `co.COMMISSION_COST` 佣金成本率 | 0.02% | 0.02% |
| `evt.Nom_Prin_Chg_Delta` 事件汇总平仓金额（结算币种） | 无 | 912,500 |
| `mid.mid_price` 人民币汇率 | 0.8 | 0.8 |

初始本金和动态本金承接已有主合约／逐日明细口径；固定、浮动分支的日息差段没有再乘mid。平仓金额已在事件侧换算到结算币种，因此佣金阶段再乘人民币汇率。本例912,500×0.8＝730,000，恰好对应动态本金减少额；**实际SQL不是通过两天本金相减得到平仓金额**，只是本例构造得能够相互核对。

### 2.2 第一天：初始本金收开仓佣金，动态本金算日息差

```text
净息差 = 固定6% - 资金成本3.5% + 保证金固定利率0.5% = 3%
日息差金额 = 3,650,000 × 3% / 365 = 300

开仓净佣金 = greatest(3,650,000 × (0.1% - 0.02%), 0) = 2,920
Curr_Rev   = 日息差300 + 净佣金2,920 = 3,220

Trd_Cms毛佣金 = 3,650,000 × 0.1% = 3,650
```

开仓按金额模式用的是**主合约初始本金**，这里没有再乘0.8。不能因为其他佣金分支乘了汇率，就给这一条自行补乘。

### 2.3 第二天：剩余动态本金收日息差，平仓事件收佣金

```text
日息差金额 = 2,920,000 × 3% / 365 = 240
平仓净佣金 = greatest(912,500 × (0.1% - 0.02%) × 0.8, 0) = 584
Curr_Rev   = 240 + 584 = 824

Trd_Cms毛佣金 = 912,500 × 0.1% × 0.8 = 730
```

主合约初始本金仍是3,650,000，但第二天息差使用的是2,920,000的动态本金。日息差从300降到240，原因是**本金变化，不是利率变了**。

### 2.4 两天如何进入客户报告

| 输出字段 | 9月16日 | 9月17日 | 客户报告怎样使用 |
| --- | ---: | ---: | --- |
| `Curr_Rev` 净创收 | 3,220 | 824 | 年度创收把两天加总 |
| `Trd_Cms` 毛交易佣金 | 3,650 | 730 | 另列展示，不能再加到净创收 |
| `Opt_Npv_Curr_Rev` | 0 | 0 | 本分支固定0，不计算期权NPV收入 |
| `Accrued_Date` | 2026-09-16 | 2026-09-17 | 两条记录各自的计提日 |
| `busi_date／grp_id` | 2026-09-22／02 | 2026-09-22／02 | 同一次报告快照、普通互换分支 |

若客户甲今年只有这两条记录，[227701年度创收](../../01_年度创收_227701/README.md)的互换创收是 **(3,220＋824)/10000＝0.4044万元**。因为标的币种HKD，跨境创收也会含这0.4044万元；它是重叠维度，不是再加一次。

毛佣金合计4,380元。净佣金已包含在4,044元净创收内，不能再算成8,424元。两列分别回答“扣佣金成本后的创收贡献”和“按收费参数计算的毛佣金展示”，本任务并未证明实际收款到账。

### 只改一个参数：佣金成本从0.02%升到0.12%

净费率变成0.1%－0.12%＝-0.02%，两天净佣金都经`gfgreatest(...,0)`截为0。日息差不变，创收变为300和240，合计540元；**毛佣金仍为3,650和730元**，因为08没有扣成本。

若新成本恰好在9月17日生效，16日仍用旧成本，17日起才用新成本；并不是拿报告日的最新一条参数覆盖所有历史计提日。参数如何展开见第六节。

## 三、开平仓不是同一套佣金乘数

[04开平仓与分红](04_开平仓与分红.sql)中的`sh`对每条腿 `Leg_Glbl_Seq_No` 按日期倒序取`rk=1`，再按合约内部流水号连接。它**没有限制所取腿记录日期<=计提日**，也不是按合约只留一条：一合约两条腿都能各有rk=1。历史明细可能因此使用后来的腿参数；意图和真实数据需另验。

事件侧先读状态代码`3`及指定类型，再按合约内部编号＋事件日聚合：

| 事件 | 实际汇总 | 后续用途 |
| --- | --- | --- |
| CLOSE_STOCKS、EARLY_TERMINATION、TERMINATION | `ABS(数量)×价格×rate` | 平仓金额佣金 |
| 同上 | `ABS(数量)×rate` | 平仓按股佣金 |
| DIVIDEND_STOCKS | `分红税金额×rate` | 多头持券分红金额 |

这里的rate先做事件明细转换，不能与后续mid人民币汇率混成一个字段。比如事件数量-100、价格10、rate0.8，汇总平仓金额800、数量80；分红税500、rate0.8，汇总分红400。SQL明确这样计算，不因字段叫“数量”而擅自去掉rate。

07净佣金与08毛佣金的选择顺序相同：

| 命中顺序 | 净佣金截零前 | 毛佣金 |
| --- | --- | --- |
| 期初日、模式1 | 初始本金×(交易费率－佣金成本) | 初始本金×交易费率 |
| 期初日、模式10 | 期初数量×(每股佣金－0.03)×Init_Rate×mid | 期初数量×每股佣金×Init_Rate×mid |
| 其他日、模式1 | 平仓金额×(交易费率－佣金成本)×mid | 平仓金额×交易费率×mid |
| 其他日、模式10 | 平仓数量×(每股佣金－0.03)×mid | 平仓数量×每股佣金×mid |

期初日即使同时有平仓事件，也先取开仓公式，不把开平两笔相加。按股模式的`Init_Rate`只在开仓乘；平仓不乘。比如数量100、每股佣金0.05、初始换算率2、mid0.8：开仓净佣金3.2、毛佣金8；其他日平仓同数量时净佣金1.6、毛佣金4。

模式不是1或10时，内部CASE没有ELSE，产生NULL。再交给自定义`gfgreatest`会如何处理，现有UDF资料没有完整证明；不要说成“其他模式自动佣金0”。常数每股0.03和365的制度依据也仍待确认。

## 四、其他三条创收路径：哪些相同，哪些不同

### 4.1 FLEXO：浮动收益率先保底、再封顶

协议与源类型条件沿用第一分支，只把跨币种类型改为`FLEXO`。`S_CROSS_OPTION_SWAP`也符合两分支，且这条OR分支没有另要求源标的类型EQUITY；不能漏写。

实际公式的阅读顺序是：

```text
候选收益率 = fr.intrt/100 + info.Intr_Marg
下限后收益率 = greatest(info.Float_Base_Rate, 候选收益率)
封顶后收益率 = least(COALESCE(info.Flot_Intrt_Ulmt,100), 下限后收益率)
净收益率 = 封顶后收益率 - co.SPREAD - COALESCE(cr.ir/100,0) + co.MARGIN_FIXED_RATE
日创收 = det动态本金×净收益率/365 + 同前面的净佣金
```

构造非开仓、无事件的一天：动态本金3,650,000，下限4%、上限8%、浮动指数源值5、利差1%、成本利差1%、参考成本源值2、保证金固定利率0.5%。候选6%，在4%～8%内；净率6%－1%－2%＋0.5%=3.5%，日创收 **350**。

只把指数源值5改为1，候选2%被下限抬至4%，日创收150；改为9，候选10%被上限压至8%，日创收550。`fr.intrt`和`cr.ir`除100，主合约下限／上限／利差并不再除100。

上限NULL时SQL默认的是**数值100**，不是文档替它规定的100%或1。`cr.ir`缺失明确补0；`fr.intrt`、下限或利差缺失则会进入UDF未知NULL路径，不能用JavaScript的NULL转0替生产引擎作结论。

### 4.2 多头持券：固定利差加分红，不加净佣金

条件为协议`TRS_SAC_OTC`、类型`LONG_HOLD_SWAP`、源标的EQUITY。公式：

`动态本金×(info.fixed_rate－co.FIXED_RATE)/365＋COALESCE(evt.Divd_Tax_Amt,0)×mid`。

动态本金3,650,000、固定6%、成本4%、事件侧汇总分红税500、mid0.8：日息差200＋分红400＝**600**。只去掉分红记录，得到200。

本分支没有加前两分支的净佣金；08毛佣金仍会独立按模式算。看到毛佣金非零，不能推断它已计入LONG_HOLD_SWAP的Curr_Rev。`co.FIXED_RATE`在输出中改名为`LONG_FIXED_RATE`，不要与主合约固定利率混同。

### 4.3 指数增强：先确定池子，再确定谁分配

池子来自[02指数增强盈亏池](02_指数增强盈亏池.sql)：

- `u`从11个账簿的历史持仓汇总标的日盈亏：10016、10015、10014、10008、10012、10162、10190、10191、10192、10193、10202。
- `x`直接连接上传表 `query_upload.otc_rev_allocated`，按计提日＋标的代码取分配金额，没有去重或先汇总。
- 五个标的代码为000905.SH、000852.SH、000016.SH、000300.SH、8841431.WI。

u在账簿标的缺失时，沿报告日有效交易产品关系→报告日结构腿→历史日腿持仓→证券资料取得备用标的。使用报告日账簿／关系资料识别历史持仓，不是所有输入都取同一天快照。

**领取创收的合约范围更窄：账簿10016＋五标的之一＋INDEX_ENHANCE_SWAP。**11个账簿贡献池子，不等于11个账簿的全部合约都进本金分母。

```text
同标的、同计提日：
A合格本金2,000,000；B合格本金3,000,000 → 分母5,000,000
账簿池u=1,000；上传x=500 → 待分配1,500；两行汇率均1
A：2/5×1,500=600
B：3/5×1,500=900
```

只把B本金改为2,000,000，结果变成750／750；只移除上传记录，变成400／600。加一份10015合约，即使同标的同日也不入该分母，其当日创收默认0；不能把“盈亏池来自10015”理解成“10015合约一定领到分配”。

窗口键是 `COALESCE(ins.undrl_clas, info.undrl_wd_cd)＋det.busi_date`，但分母SUM内部还要再判断领取资格。主合约这一处COALESCE**不把空串当缺失**；证券分类为空串时不会回退主合约标的代码，可能不再符合五标的。u内部账簿映射则先把空串变NULL，两处回退不同。

整个合格组本金为0时没有零分母保护。静态代码可以确认未保护，不能靠SQLite的除0结果宣称生产一定返回NULL或0；需按实际执行引擎另验。

## 五、不同资料的日期和币种不能统一成一个“当日”

| 输入 | 采用的日期／币种 | 会影响什么 |
| --- | --- | --- |
| 主合约、客户、账簿、结构腿 | 报告日快照 | 当前资料用于识别历史计提日 |
| 逐日明细、持仓盈亏、事件 | 明细计提日／事件日 | 金额归属到哪一天 |
| sh佣金参数 | 每条腿源记录中最新日期，无<=计提日限制 | 历史日可能使用后来的参数，一合约可多腿 |
| cr资金参考利率 | 报价日向后补到下次报价日前；按**标的币种** | HKD→HIBOR1M，USD→SOFR，JPY→TONAR |
| fr浮动指数利率 | 指数代码＋计提日精确匹配 | 本段未给fr补非交易日 |
| mid人民币汇率 | **结算币种**＋计提日 | 缺失实际按1；不证明就是人民币 |
| co成本配置 | 报告日维护快照中的历史生效区间，按计提日匹配 | 新配置自生效日起改变后续日，非全部历史日 |

这里cr的补日不同于期权气囊“上月末交易日用于下月”的逻辑，不能为了公共化把两分支合并成一份相同规则。`rec_id`拆出fr指数编号、`datekey2date`转换合法日期的行为仍保留原SQL，不改成自造字典或日历。

## 六、成本参数怎样选中，缺一个参数为什么不等于整行缺失

[06生效成本参数](06_生效成本参数.sql)读取OIS客户创收系数的报告日快照，限定`is_del='N'`及类型S_CROSS_SWAP／LONG_HOLD_SWAP。每个**合约类型＋系数类型**分别按生效日排序，下一条生效日前一日结束，最后一条截止报告日，再展开为每日记录。

例如佣金成本0.02%自2026-01-01生效，0.12%自2026-09-17生效：旧值到9月16日，新值从9月17日起。09-16仍是正常例子的3,220元，09-17净佣金归零只剩240元，两日合计3,460元。如果两天都改用新成本则是前文540元——这是两种不同输入，不能混成同一个参数切换例子。

按合约类型＋日聚合时，把记录透视成五项：FUND_COST_RATE、SPREAD、MARGIN_FIXED_RATE、FIXED_RATE、COMMISSION_COST。每项使用 `SUM(CASE WHEN 类型命中 THEN value ELSE 0 END)`。

| 输入情况 | co输出 | 后果 |
| --- | --- | --- |
| 当天有资金成本记录，但没有佣金成本记录 | 该类型／日仍有行，佣金成本列为0 | 可继续按零佣金成本计算 |
| 当天该类型完全没有配置 | 整个co匹配不到，五项为NULL | 不等于五项都为0，公式可能NULL或进入UDF未知路径 |
| 某项命中但value为NULL | SUM忽略NULL；若无其他ELSE0输入可能仍为NULL | 不能把“缺项补0”说成任何NULL都补0 |
| 同一项有重复有效配置 | 可能重复展开并累加，同生效日先后也未明确 | 不能说已自动择一去重 |

最后连接时，将主合约 `S_CROSS_OPTION_SWAP` 映射成 `S_CROSS_SWAP` 查参数，其余按原类型。没有合同级优先、客户级回退或币种过滤；不要把此前销售经营系数的T99匹配规则移植过来。

## 七、边界与输出：哪些未知必须保留

- 输出初始本金取info，动态本金展示用`COALESCE(det.Dyna_Nom_Prin,0)`；但固定、浮动、多头创收直接读det原值，不会因为展示为0就自动把公式NULL变0。
- 提前终止日优先展示为期末日，非空终止标志为1；它没有在07再次过滤已连接行。空串不触发COALESCE回退，却被终止标志判为0；是否不再出现后续计提日要追上游明细。
- 多数缺失事件金额补0，缺mid补1，但这只是程序默认值，不证明资料完整。最新腿、上传行、客户映射重复均可能改变输出和指数窗口。
- `Rev_Contr_Type_Cd`按类型分类，并不完全重复Curr_Rev条件：例如S_CROSS类型即使不是COMPOSITE/FLEXO仍可能有分类码但创收为0。不能仅凭分类码断言命中了某条收入公式。
- 目标外层保持74列，包括当前新增的`Agt_Clas_Cd`和`Src_Undrl_Type`。`busi_date`是报告日，`Accrued_Date`是计提日，`grp_id`固定02；这三者不是同义字段。
