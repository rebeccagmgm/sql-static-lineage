# 历史奖励从哪里来，怎样进入保底？

这页只追溯主线“保底调整”使用的历史金额。[05 历史奖励](05_历史奖励.sql)负责汇总和匹配，[04 收入调整](04_收入调整.sql)使用它；需要确认`actl`究竟是什么时，再回到这里。

## 1. 上游不是重新算收入，而是接收已有记录

[08 历史奖励来源](08_历史奖励来源_203358.sql)是独立任务203358：读取OIS交叉收入奖励表当天快照，把一条源记录映射成T98的一行。

```text
OIS交叉收入奖励记录
  └─ 203358：字段映射、固定空串、跨境标志转换
       └─ T98收入奖励汇总的该源分区
            └─ 118141：筛选历史核算期，按合同汇总
                 └─ actl：历史部门所得收入合计 + 最晚核算结束日
                      └─ 04收入调整：供到期保底调整使用
```

虽然目标表叫“汇总”，**203358这一段没有GROUP BY、JOIN或DISTINCT**；不是先把每合同汇成一行。相同合同可以保留多条记录，源重复行也不会在这里去掉。源ID只是带出，SQL没有证明它唯一。

45个输出字段中，与118141这次读取直接有关的只有四个：

| OIS实际字段 | T98字段 | 118141怎样使用 |
| --- | --- | --- |
| CONTRACT_NO，合同编号 | Contr_Id | 按合同分组，再连接主线Agt_Id |
| ACCOUNTING_DATE，核算日期 | Sett_Time | 筛选核算季度码 |
| EXPANSION_DEPT_INCOME，拓展方部门所得收入（元） | Dev_Dept_Rwd | SUM，得到历史金额 |
| ACCOUNTING_END_DATE，【AI】核算结束日期 | Sett_End_Date | MAX，得到历史核算截止 |

本金、机构、客户、标的等资料仍原样保留在生产SQL中，但并没有加入118141这个聚合的分组键。

## 2. “历史”由本次运行日与核算码一起限定

118141先固定`busi_date = ${yyyy-MM-dd}`和源分区`ODATA_N_OIS.G_CROSS_INCOME_REWARD`，然后筛：

```sql
Sett_Time >= '202502'
AND Sett_Time < concat('${yyyy}0', quarter('${yyyy-MM-dd}'))
```

它读取的是**当前加工快照里符合历史核算期的记录**，不是把多个BUSI_DATE分区全部累加。

SQL用“年份＋0＋季度序号”构造上限，说明它按`YYYY0Q`形式比较核算码；`202502`在这个比较规则里对应2025年第2季度，不能读成2025年2月。源注释只有“核算日期”，未给出独立格式规范；这解释的是SQL的编码预期，没有验证每条实际记录都符合它。

例如构造运行日为2026-09-22，上限是`202603`：正常季度码中，202502、202503、202504、202601、202602被纳入，202603被排除。源值异常、混用月份编码等情况没有在此处校验。

## 3. 金额合计与最晚截止是两项独立聚合

同合同先对全部入选记录执行：

```sql
SUM(Dev_Dept_Rwd) AS Dev_Dept_Rwd,
MAX(Sett_End_Date) AS Qtr_End_Date
```

不是“挑最新一行并拿那行的金额”，也不是先按季度去重。金额来自全部入选行的合计，截止来自这些行中最晚的结束日，两者未必对应同一条源记录；具体金额沿用主线的贯穿算例。

随后连接条件还要求：

```sql
t.Agt_Id = actl.Contr_Id
AND actl.Qtr_End_Date < t.End_Pric_Date
```

这里主线的`End_Pric_Date`已经是“提前终止日优先，否则期末定价日”，不是固定原合同到期日。只有最晚核算截止**严格早于**这个有效结束日，历史聚合才会匹配；相等或晚于时整条聚合不匹配，并非只剔除晚的那条再重新合计。

没有匹配时，04收入调整中的金额回退0，核算截止回退2025-03-31。保底公式如何扣除历史金额、再处理截止之后的逐日收入，由主线贯穿算例说明；不要在这里另起一套收入算法。

## 4. 为什么不能把actl直接叫“已经付出去的钱”？

原118141注释写“累计实发收入”，但实际SUM的是**Dev_Dept_Rwd（拓展方部门所得收入）**。

203358把目标的`Curr_Actl_Rwd（本期实发奖励）`直接填空串，`Curr_Payb_Rwd`、`Curr_Defr_Rwd`、`Mtch_Defr_Rwd`也一样。实际支付日、支付状态或资金流水没有进入这段计算。

因此本文称它“历史部门所得收入汇总（actl）”，既保留它在原保底逻辑中的用途，也不把注释中的“实发”升格为已核实的现金支付事实。
