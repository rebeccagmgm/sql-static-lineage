# 118141：从合约逐日金额到交叉销售收入日报

合约主信息告诉我们“是什么合约”，107491给出“各计提日的本金和费用”。118141接下来做的是：**选择收入参数，计算每天的收入，再做必要调整、分配和累计。** 输出是`dm_otc_n.otc_sale_daily_rpt`；算出的收入不等于已经支付的钱。

第一遍先走下方这一份普通期权。不必先读完全部T99生产脚本，也不必先掌握AIRBAG、金仕达的特殊公式。读完算例，再打开[00_主脚本](00_主脚本.sql)，就能把数字放回对应阶段。

## 先看整条路，而不是所有表

```text
合约主信息info ── 合约号 ── 逐日本金det
       │                     │ 每一条计提日记录
       ├─ 五路参数：价差、基准、成本（并列输入）
       └─ 管理归属m：经办人、介绍机构和比例
                             ↓
01＋02：合约日资料、原始当日收入 contract_day_income
                             ↓
04：结束日保底／系统费用调整  ← 05：历史奖励汇总actl
             调整后收入 adjusted_day_income
                             ↓
06：本金归属、三组收入分配、累计 allocated_day_income
                             ↓
07：按原字段顺序整理输出 → 销售收入日报
```

这是数据承接关系，不是数据库物理执行顺序。三个英文名称是本阅读版给原来三层子查询起的名字，没有把每一步结果另按合约号重新JOIN。

一个关键区别：107491的`busi_date`是计提日；118141把它取名`Accrued_Date`，自己输出的`busi_date`却是加工日。因此同一次日报加工可以包含同一合约的多个计提日。连接没有统一去重，不能据此认定“合约＋计提日”实际唯一。

## 一、让一份普通期权进入加工

以下全是构造数据，金额统一假设为人民币元，不是生产记录。我们只给每个连接准备一条匹配资料，先排除重复匹配的干扰。

| 输入 | 本例值 | 实际来源及作用 |
| --- | --- | --- |
| 合约号 | `OPT_DEMO` | `info.Agt_Id`；后续各阶段承接同一份合约 |
| 业务分类 | OPTION、OPTION_STOCK、分组01 | `info`中的业务类型、合约类型、分组；非AIRBAG等前置特殊分支 |
| 定价日期 | 9月18日期初、9月20日期末；无提前终止日 | `info.Strt_Pric_Date/End_Pric_Date/Early_Term_Date`；年份均为2026 |
| 本次加工日 | 2026-09-21 | 主信息、管理归属按此日取快照，最后写到日报`busi_date`；T99读取现有来源分区，不统一按此日筛选 |
| 初始名义本金 | 3,650,000 | `info.Init_Nom_Prin` |
| 逐日动态本金 | 18、19、20日各3,650,000；21日为0 | `det.Dyna_Nom_Prin`，由107491提供；本任务不再复算期权事件 |
| 归属资料 | 至少一组机构非8846；有引入经办人 | `m`，让本例通过机构范围条件，并进入本金40/60分配 |
| 三组介绍比例 | 0.7、0.3、0 | `m.Allo_Prop_1/2/3`，用于收入分配 |

[01_合约日与资料](01_合约日与资料.sql)先取加工日主信息，排除费用互换、FAST分组和香港部门，再INNER JOIN逐日明细，**只按合约号连接，不再筛选det的日期**。本例因det有四天，先形成四条合约日记录。没有det记录的合约不会仅凭主信息进入本结果。

管理归属是LEFT JOIN，但最终机构条件会限制结果：三组机构均缺失或均为8846时一般不保留，原SQL另有十个合约号例外。本例不是例外，靠有效机构资料进入。

## 二、这份合约用哪组参数？

[03_参数匹配](03_参数匹配.sql)在同一层接入五路资料。它们不是五步先后加工，也不是所有业务都要把五路参数相加。

| 参数 | 本例怎样匹配 | 取到什么 |
| --- | --- | --- |
| 合约价差`s_sp` | 参数原合约号`Inr_Comp_No=OPT_DEMO`；9月18日生效，区间覆盖本例日期；身份识别非空、来源和删除过滤均通过 | ANNUALIZED（年化），0.006 |
| 客户＋类型价差`c_sp` | 本例不匹配 | 合约价差已有值，不需要它补足 |
| 合约基准`s_ba` | 参数原合约号`Inr_Comp_No=OPT_DEMO`；通过来源、删除及身份筛选；这里不按日期挑版本 | ANNUALIZED，0.004 |
| 类型基准`c_ba` | 本例不匹配 | 合约基准已有值，不需要它补足 |
| 类型资金成本`cc` | 本例不匹配 | 普通价差＋基准公式不引用它，不因此缺成本而变成NULL |

价差、基准的计算类型与系数分别优先取合约侧，NULL时才回退到对应的类型侧，不是整套替换。客户类型价差按客户＋合约类型＋**期初定价日**匹配；类型基准没有客户键，也是按期初日匹配。合约价差才按**计提日**匹配生效区间。

本例结果很简单：每天使用年化价差0.6%与年化基准0.4%。0.006、0.004是公式中的小数值；源生产SQL没有在这里再除100。

需要追参数的生产过程时，再看[价差](../../公共加工/04_经营系数_价差/README.md)、[基准](../../公共加工/05_经营系数_基准/README.md)、[资金成本](../../公共加工/06_经营系数_资金成本/README.md)。主脚本通过03实际引用它们的消费JOIN，不要求手工拼接。

## 三、先算原始当日收入：每天100元

[02_原始当日收入](02_原始当日收入.sql)保留原CASE优先顺序。我们的合约没有命中特殊分支，进入[02.3普通期权](02.3_普通期权原始收入.sql)的“价差年化＋基准年化”：

```text
期初日至结束日内：
  价差贡献 = 3,650,000 × 0.006 ÷ 365 = 60
  基准贡献 = 3,650,000 × 0.004 ÷ 365 = 40
  原始当日收入 = 60 + 40 = 100
结束日之后：原始当日收入 = 0
```

所以18、19、20日各100元，21日为0。这时还没有做保底调整，也没有分到三组介绍关系。

特别留意同名字段的层次：

| 所处层 | 字段 | 含义 |
| --- | --- | --- |
| `contract_day_income` | `Curr_Prvs_Sales_Income` | 上面刚算出的原始当日收入 |
| `adjusted_day_income` | `Curr_Prvs_Sales_Income_n` | 做完保底或系统费用调整后的当日收入 |
| 分配层及最终日报 | `Curr_Prvs_Sales_Income` | 将调整后字段重新取这个名字，不再是最内层的原始值 |

因此不能只搜索字段名，就把内外层金额当成同一个计算阶段。

## 四、到9月20日，为什么当日收入变成3,450元？

[04_收入调整](04_收入调整.sql)里的期权保底，是**部分期权结束日的销售收入调整**，不是保障客户本金，也不是客户产品收益的保底承诺。

本例按原SQL顺序核对：

1. 合约类型是OPTION_STOCK，属于此处处理的两个期权类型之一。
2. 计提日9月20日等于本层`End_Pric_Date`。
3. 截至这一天的原始收入累计为`100＋100＋100=300`，小于`初始本金3,650,000×0.001=3,650`。

三项满足，才进入保底表达式。**触发条件比较的是原始收入累计，不是历史奖励加当期应发。** 原注释里的概括不能替代实际判断条件。

接着看需要扣掉什么。历史输入由[05_历史奖励](05_历史奖励.sql)按合同汇总`Dev_Dept_Rwd`、取最大的核算结束日，并要求这个截止日早于合约结束日。本例是当季新合约，没有符合条件的历史奖励行：历史金额补0，核算截止日回退为原SQL固定值2025-03-31。

```text
本例保底金额                         3,650
减：匹配到的历史部门收入                 0
减：核算截止之后的原始收入总和         300  = 100+100+100+0
加：结束日原始收入                     100
────────────────────────────────────────
结束日调整后收入                     3,450
```

为什么末尾加回100？因为前面的300已经包含结束日的100；该表达式是在**替换结束日这行金额**。此前两天仍保留100、100，最后合计`100＋100＋3,450=3,650`，不能再把3,450额外加到原来的三天收入之上。

这里的第二个SUM没有ORDER BY，是当前合同整个输入分区中“核算截止之后”的原始收入总和，不自动等于“截至当前行的当季收入”。本例21日为0，所以仍是300；换别的输入不能直接套用这个数字。

还有两个重要来源区别：

- 本层`End_Pric_Date`已在01中改成`COALESCE(info.Early_Term_Date, info.End_Pric_Date)`。提前终止日非NULL时会成为本层结束日，并非保底完全不看提前终止。
- 历史金额实际来自OIS的`EXPANSION_DEPT_INCOME`，经203358写成`Dev_Dept_Rwd`；不能仅凭别名actl或“累计实发”注释就称为已经付款。见[奖励来源说明](奖励来源说明.md)及[08_历史奖励来源](08_历史奖励来源_203358.sql)。

## 五、再分配、再累计，才是日报金额

[06_分配与累计](06_分配与累计.sql)使用的是调整后收入。我们给三组介绍关系的比例为70%、30%、0%，得到：

| 计提日 | 原始收入 | 调整后／日报当日收入 | 第1组70% | 第2组30% | 日报累计收入 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 9月18日 | 100 | 100 | 70 | 30 | 100 |
| 9月19日 | 100 | 100 | 70 | 30 | 200 |
| 9月20日 | 100 | 3,450 | 2,415 | 1,035 | 3,650 |
| 9月21日 | 0 | 0 | 0 | 0 | 3,650 |

第3组均为0；最后第1组累计2,555，第2组累计1,095。实际SQL只是分别相乘，没有把三个比例重新归一到100%；这里只是假设源比例之和为1。

累计按`Agt_Id＋Contr_Type_Cd`分组、按计提日排序，对调整后当日收入求和，再用`gfgreatest(累计值,0)`给累计结果取下限0。不是先把每天的负收入改成0再相加。当日调整金额本身没有同样的下限保护。

### 不要把本金40/60当成收入分配比例

本例有引入经办人，初始本金另分成：主经办1,460,000，引入经办2,190,000。动态、绝对本金也按各自金额做对应分配。

这套40%／60%作用于`*_Main/*_Intro`本金；上表收入则用`Allo_Prop_1/2/3`。SQL没有让本例收入也先乘40/60，不能把这两套比例叠起来算。

## 七、只改一个条件，再检查理解是否成立

**仅把提前终止日改成9月19日**，先固定上述det输入，观察118141自身规则：

- 01输出的结束日变成19日；普通年化原始收入为100、100、0、0。
- 保底判断移到19日，调整后金额为`3,650−0−200＋100=3,550`。
- 日报当日收入成为100、3,550、0、0，累计成为100、3,650、3,650、3,650。

这说明提前终止不是简单“后面停止算就完了”，还可能改变本SQL的结束日调整。真实重新加工时107491也可能改变本金，本例固定其输入只是为了单独看清118141的影响，不证明真实历史已经重算。

**再单独看参数缺失**：若基准类型变为空串，且本例无其他补足来源，普通收入CASE可能返回NULL。价差类型在输入时做了空串转NULL，基准类型没有，不能把二者当成相同回退逻辑。最终保底是否产出数值仍须逐层看SUM、COALESCE和当日值，不能直接断言“缺参数就补保底”。

## 已覆盖内容与核对边界

本轮已贯通普通期权、普通互换、AIRBAG／关联LONG_HOLD_SWAP及金仕达的主要收入路径；普通互换补四种年化／绝对组合，金仕达以两份合约说明同日系统费用分摊。价差、基准和成本的旧表达式文件改为导航，真实展示表达式在01，原始收入CASE由02及其02.1—02.4模块唯一维护，五个真实参数JOIN仍由03引用。上游参数说明继续保留，不用它们代替本任务的完整主线。

这表示**冻结SQL主要计算路径已有独立可读说明和可复算构造案例**，不表示所有真实数据异常、产品制度和生产运行均已确认。固定系数的制度依据、金仕达用资字段的经济单位、真实匹配唯一性仍有证据边界；不把未确认处写成定论。见[本轮收尾记录](../../建设台账/118141_剩余整理完成记录.md)。

需要继续留意的边界集中在这里：输入或参数重复可能扩行并改变窗口结果；原窗口没有额外同日排序键；核算截止日是MAX而历史金额是独立SUM；保底触发与金额计算用的累计范围不同；det未在118141重新限定日期，累计并不证明覆盖合同全生命周期。它们不是新增规则，SQL均保留原样。
