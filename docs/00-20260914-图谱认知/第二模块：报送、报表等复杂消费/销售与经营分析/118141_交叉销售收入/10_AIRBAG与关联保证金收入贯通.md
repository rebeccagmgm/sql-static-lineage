# AIRBAG：先判抵扣和关联关系，再算费率与成本差

这条收入路径不使用普通期权的“价差＋基准”公式。它先用源合约类型判断是否为 **AIRBAGX、AIRBAGM、AIRBAGL**，再看抵扣模式和保证金关联合约。单独的源类型 `AIRBAG` 不在这组三个码值里，不能因为名字相似就套入。

以下只解释冻结SQL怎样计算。“抵扣”的制度含义、固定系数的制度依据，不能从CASE或字段名自行补出。

## 1. 先看为什么走这条路

[02选择入口](02_原始当日收入.sql)最先引用[02.1_特殊类型与保证金关联](02.1_特殊类型与保证金关联.sql)，按下面顺序取第一个命中分支。02.1只含本CASE的WHEN/THEN，不是独立查询：

```text
源类型在 AIRBAGX / AIRBAGM / AIRBAGL 中？
  是 → 抵扣模式为 DEDUCTION？
         是 → 原始收入0
         否 → Marg_Agt_Id（保证金关联合约）为空？
                是 → 用初始保证金比例计算
                否 → 同时用初始比例和基础保证金率计算
  否 → LONG_HOLD_SWAP且关联合约非空？ → 原始收入0
       否 → 再判断金仕达、普通期权、普通互换
```

这里“否”的准确条件是 `COALESCE(Ddct_Ptrn,'') != 'DEDUCTION'`，所以NULL、空串和其他非DEDUCTION值都会进入非抵扣路径。不是已经证明每一种其他值都在业务上等于“不抵扣”。

`Marg_Agt_Id` 同样仅检查NULL／空串与非空，不读取关联合约本金，也不按关联个数分摊；即使里面拼了多个编号，这一步仍只是走“有关联”公式。

## 2. 公式里的值从哪来？

先区分三个实际输入：合约销售基础 `pdata_n.t98_otc_deri_comp_sale_info`（别名info）、逐日明细 `pdata_n.t98_otc_deri_comp_sale_adtnl_det`（det）、类型资金成本参数（cc）。

| 字段 | 本处含义与实际来源 |
| --- | --- |
| `info.Ddct_Ptrn` | 抵扣模式。经合约组合 `d_trd_bundle_info` 的履保方案ID连接 `d_margin_plan.deduction_pattern`；不是同样带“抵扣”字样的保证金参数表deduction字段 |
| `info.Init_Marg_Prop` | 初始保证金比例，来自 `odata_n_tit.d_ref_otc_contr_margin_param.initial_margin`；源注释为保证金初始线(%)，本收入式直接用 `1−该值`，不再除100 |
| `info.Base_Marg_Rate` | 基础保证金率，来自同表 `basic_margin_rate` |
| `info.Marg_Agt_Id` | 期权方向来自有效的 `f_ref_option_margin_trs_relation`，另限关联互换为LONG_HOLD_SWAP，按期权键汇总互换交易键 |
| `det.Dyna_Nom_Prin` | 107491已算好的逐日本金；本例是期权分组01，来自初始本金和事件累计变化 |
| `det.fee_rate` | 107491从 `odata_n_tit.d_trd_daily_accrual_fee` 的 `ACCRUAL_PREMIUM_FEE` 记录取fee_rate，按工具键、计提日延续；是费率，不是费用金额 |
| `cc.capital_cost` | OIS成本配置经 `T99_DERI_COMP_TYPE_FND_COST_REF.Fnd_Cost` 带入，按经营类型＋期初定价日匹配；不是det的金仕达用资字段 |

需要展开来源时，分别打开[组合履保方案](../../公共加工/01_合约主信息/sql/04_业务模块/00_公共视图/03_组合计划.sql)、[期权保证金与关联关系](00-20260914-图谱认知/第二模块：报送、报表等复杂消费/公共加工/01_合约主信息/sql/04_业务模块/01_期权/12_客户与保证金.sql)、[逐日费率](../../公共加工/03_逐日本金与费用/06_逐日费率.sql)、[资金成本参数](../../公共加工/06_经营系数_资金成本/README.md)。这些是并行补入的资料，不是先后计算的四步。

## 3. 一份无关联合约的AIRBAGX算到底

全为构造数据，金额假设人民币元。合约 `AIR_DEMO`，分组01、业务类型OPTION、源类型AIRBAGX；经营类型取 `OPTION_RISKY_AIRBAGX_CIR_STOCK`，即本例没有进入期权保底的两种经营类型。

| 输入 | 本例值 |
| --- | --- |
| 日期 | 2026-09-18至9月20日，9月21日加工；无提前终止 |
| 初始本金与逐日本金 | 初始3,650,000；无本金变动事件；107491提供18—20日各3,650,000，21日0 |
| 抵扣／关联 | 非DEDUCTION的构造值；`Marg_Agt_Id=NULL` |
| 初始保证金比例 | 0.2，算式里的小数输入假设；不据此确认生产界面的录入单位 |
| 基础保证金率 | 0.1；无关联公式暂时不用它 |
| 计提费率 | 0.106，18日起延续覆盖算例日期 |
| 成本率 | 0.03；类型匹配上述经营类型，适用起止区间包含合约期初9月18日，源部门OTC、未删除 |
| 归属 | 有有效介绍机构、有引入经办人；三组收入比例0.7、0.3、0 |

匹配成本用的是 **9月18日期初日**，不是每天计提日；价差、基准即使匹配到了，本分支也不引用它们。先算18日：

```text
参与这条公式的本金部分 = 3,650,000 × (1−0.2) = 2,920,000
公式调整后的费率       = 0.106 ÷ 1.06       = 0.1
与成本率的差           = 0.1 − 0.03         = 0.07
原始当日收入           = 2,920,000 × 0.07 ÷ 365 × 0.3 = 168
```

`1.06`、`0.3`、`365` 是原式常数；这里能确认除法、乘法和按日折算的位置，不能单靠数值就将其制度依据写成“已确认税率／分成政策”。

本例经营类型既不是金仕达，也不是OPTION_STOCK或OPTION_IDX_ETF，所以[收入调整](04_收入调整.sql)直接保留原始值。再进入[分配与累计](06_分配与累计.sql)：

| 计提日 | 原始／调整后收入 | 第1组70% | 第2组30% | 第3组 | 合约累计 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 9月18日 | 168 | 117.6 | 50.4 | 0 | 168 |
| 9月19日 | 168 | 117.6 | 50.4 | 0 | 336 |
| 9月20日 | 168 | 117.6 | 50.4 | 0 | 504 |
| 9月21日 | 0 | 0 | 0 | 0 | 504 |

这里公式内部的0.3与第2组介绍比例0.3恰好相同，但角色不同：前者先形成整份合约的收入，后者只分配第2组份额，不能合并解释。

最终[日报输出](07_日报输出.sql)中，20日行的当日收入168、累计504、`Accrued_Date=2026-09-20`，加工日`busi_date=2026-09-21`。AIRBAG三个类型还展示 `fee_rate=0.106` 和 `Fin_Rati=1−Init_Marg_Prop=0.8`；这两个展示值不是另一笔收入。

## 4. 只把“保证金关联合约”改成非空

保留所有其他输入，只令 `Marg_Agt_Id='MARGIN_TRS'`，公式变成：

```text
3,650,000 × (1−0.1)
  × [0.106 × (1−0.2) ÷ (1−0.1) ÷ 1.06 − 0.03]
  ÷ 365 × 0.3
= 159
```

所以18—20日变成159、159、159，累计477；每天第1组111.3，第2组47.7。展示的 `Fin_Rati` 仍是0.8，不会因为公式额外用了基础保证金率而改成0.9。

在本例分母非零、数值非空时，可以把费率项和成本项分开检查：

- 费率贡献仍是 `3,650,000×0.8×0.1÷365×0.3=240`。
- 无关联扣成本 `3,650,000×0.8×0.03÷365×0.3=72`，得168。
- 有关联扣成本 `3,650,000×0.9×0.03÷365×0.3=81`，得159。

这只用于读懂算例，不把生产表达式约分重写；基础保证金率为1时原式有除零，不能约分后假装问题消失。

## 5. 三个重要变化

**抵扣模式改为DEDUCTION：** 最前面的CASE直接给原始收入0，成本率缺失也不会落入后面公式。本例后续无特殊调整，因此日报当日收入也为0。一般情况仍要再看04是否命中其他调整，不能把“原始为0”直接等同全部阶段都为0。

**成本率缺失：** 非抵扣公式没有把成本NULL补0，即使某日动态本金为0，`0×NULL`仍不是数值0。原始和当日分配可能为NULL，累计层才对缺失收入补0。本例缺成本时累计为0，不代表真实收入已经确认为零。

**提前终止日改为19日，先固定det不动：** AIRBAG公式自身没有普通年化分支的起止日期IF，20日仍算168。真实重算107491时，其期权本金规则会将结束日后的本金归0；这是上游提供的日期约束，不是118141再做了一遍。不要把两层作用混成一句“到期自动停算”。

## 6. LONG_HOLD_SWAP为何另有一个零分支？

原始收入CASE明确写：`Src_Contr_Type='LONG_HOLD_SWAP'` 且 `Marg_Agt_Id` 非空 → 0。普通互换主信息里的这个关联字段，来自有效关系中按互换键汇总的**期权交易键**，与期权方向相反。

本页确认的是“关联长持有互换原始收入置零”的代码事实。它看起来与期权关联保证金处理配合，但是否意在避免重复计收，需要业务依据，不能仅凭相邻CASE下定论。若该字段为空，则不命中此零分支，继续判断后面的金仕达／普通业务条件。

## 核对边界

构造检查覆盖无关联、有关联、抵扣、NULL抵扣、缺成本、基础保证金率为1、普通AIRBAG码值不命中特殊组，以及LONG_HOLD_SWAP关联切换。检查执行实际收入、调整、分配和输出表达式；SQLite除零为NULL的结果只说明本地适配行为，不承诺Hive在所有配置下同样处理。
