# 220979：从香港合约逐日金额到销售收入日报

香港销售收入要回答：**哪些合约、客户纳入统计，每个计提日用什么本金和参数算收入，结束日是否调整，最后怎样累计到介绍关系。** 结果供 `dm_otc_n.otc_hk_sale_daily_rpt` 使用；收入计提不等于已经支付的钱。

一行是“一条香港范围内的主信息，与一个计提日及各项资料匹配后的结果”。SQL没有统一去重，不能未经数据核验就称“合约＋日期唯一”。同一次加工包含多天计提日，日报的 `busi_date` 是加工日，`Accrued_Date` 才是金额归属日。

先读下面一份普通期权，把原始收入、保底和累计串起来；香港新增的佣金和返息基数则沿[08_普通互换与返息费用贯通](08_普通互换与返息费用贯通.md)的同一份互换走到底。特殊融资收入沿[09_RISKY与关联保证金贯通](09_RISKY与关联保证金贯通.md)读。三条路径均回到同一[主脚本](00_主脚本.sql)，没有各写一套输出口径。

## 先看主线怎样承接

```text
公共合约主信息 → 香港范围、合约分类和标的分类 info
                          │
107491逐日本金 det ────── 合约号；香港客户 cp 必须准入
                          ├─ 03：价差、基准、佣金、资金成本（七路参数）
                          ├─ 04：返息基数、当日汇率、交易事件发生额
                          └─ 管理归属 m：主/引入经办、三组机构和比例
                                      ↓
01的SELECT接入02 → contract_day_income：原始当日收入
                                      ↓
05：期权结束日保底 ← 香港历史奖励直接从OIS读取
              adjusted_day_income：调整后当日收入
                                      ↓
06：本金分配、总收入和三组收入累计 → allocated_day_income
                                      ↓
07：按原82列输出 → 香港销售收入日报
```

英文名称是阅读版给原三层子查询起的名字，不是新建业务表。参数与额外金额是并列输入，不是按文件编号一张接一张生产。主脚本实际引用01、05、06、07；01再在对应的SELECT/FROM位置引用02、03、04。读完整SQL无需自己猜拼接顺序。

以下均为构造数据，不是生产记录。金额示例假设已在同一计价单位，汇率为1；每一路连接仅准备一条匹配记录，先不引入扩行。

| 输入 | `HK_OPT_DEMO`的值 | 在本任务的作用 |

| 账簿 | OTCHK-Option-ISDA | 命中原SQL六类香港账簿之一 |
| 源业务/标的/产品 | OPTION、EQUITY、NORMAL | 不命中特殊排除或融资分支，重新分类为OPTION_STOCK、香港标的EQUITY |
| 合约日期 | 2026-09-18期初、09-20期末；提前终止日NULL | 结束日达到2025-12-01门槛；后续年化区间和保底日期 |

| 107491计提日/动态本金 | 18、19、20日各3,650,000；21日0 | `det.busi_date/Dyna_Nom_Prin`；四条均在2024-01-01以后 |
| 管理归属 | 存在引入经办；一组机构为1234 | 通过至少一组机构非8846的条件；本金后续按40/60分配 |
| 三组介绍比例 | 0.7、0.3、0 | 后续逐日收入相乘、再累计 |

[01_合约日与资料](01_合约日与资料.sql)保留原筛选：六类账簿、结束边界、香港客户准入、机构准入缺一不可。不能仅凭“是香港合约”或“有香港部门”推定已进入结果。

公共主信息并未替本任务完成最终经营分类。01重新生成 `HK_Contr_Type_Cd/Desc` 和 `HK_Undrl_Type`：期权按源标的、源类型、限售标志及特定QIS条件分支；互换保留名单内源类型，其他归TRS_OTHER_SWAP；标的先看两类期货，再看EQUITY/INDEX/FUND，其余OTHER。输出 `Contr_Type_Cd` 实际取这份香港分类。具体分支顺序都在01，不能把交叉收入分类直接套过来。

det只按合约号接入，保留2024年起已有的计提记录；不会因为当前合约结束了就删除所有结束后行。是否归零由收入CASE处理。没有det或没有客户准入记录的合约在INNER JOIN处消失；管理归属虽LEFT JOIN，最终机构条件也会淘汰不满足者。

## 二、参数按哪个身份、哪一天命中

[03_参数匹配](03_参数匹配.sql)是本任务七个真实JOIN的维护位置。本例合约参数都在，不需类型回退：价差年化0.006，基准年化0.004。参数值已经是公式用的小数，没有在本任务再除100。

| 输入 | 实际匹配键/日期 | 对本例的结果 |
| --- | --- | --- |
| 合约价差 `s_sp` | T99的原合约号 `Inr_Comp_No` → 合约号；生效版本展开到计提日 | 9月18日生效，覆盖四日；ANNUALIZED、0.006 |
| 客户价差 `c_sp` | 客户＋业务类型＋香港标的类型＋**期初日** | 本例不匹配 |
| 合约基准 `s_ba` | T99的原合约号 → 合约号；无日期区间 | ANNUALIZED、0.004；额外奖励999只展示 |
| 香港类型基准 `c_ba` | 业务类型＋香港标的类型；**没有日期键** | 本例不匹配 |
| 合约佣金 `s_cr` | 合约号＋计提日，按生效日LEAD展开 | 普通期权公式不用；互换路径再用 |
| 客户佣金 `c_cr` | 客户＋业务类型＋香港标的类型＋**期初日** | 普通期权公式不用 |
| 香港资金成本 `cc` | 香港合约分类＋香港标的类型＋**期初日** | 普通期权公式不用；用于RISKY/AIRBAGX |

价差类型、价差系数、基准类型、基准系数分别COALESCE回退，不能统称为“整套合约参数优先”。合约价差类型先把空串转NULL；基准类型没有相同处理。收入的价差类型两侧均NULL时缺省为ANNUALIZED；展示列却没有这层缺省。因此“年化价差展示空串”与“收入一定为0”不是同一件事。

香港类型基准、客户价差、客户佣金、合约佣金、成本在冻结SQL中直接读取OIS配置表，不能因为仓内有对应T99生产任务，就把T99画成这些资料的必经上游。合约价差确实使用T99，但在LEAD前先连接香港主信息筛选范围；它与118141的消费段并不完全一样。

共用来源、参数生产和各分支差异分别见[价差](../../公共加工/04_经营系数_价差/06_对内与香港价差.md)、[基准](../../公共加工/05_经营系数_基准/06_对内与香港基准.md)、[资金成本](../../公共加工/06_经营系数_资金成本/04_香港资金成本.md)、[佣金](../../公共加工/08_经营系数_佣金/README.md)。这些专题回答参数如何来，本页继续负责这份合约如何用。

## 三、原始日收入为什么是100

[02_原始当日收入](02_原始当日收入.sql)只有一个CASE，先特殊融资/关联保证金，再普通期权四组合，再普通互换四组合。`HK_OPT_DEMO`不命中前置分支，进入“价差年化＋基准年化”：

```text
9月18日至20日（首尾都包括）：
价差贡献 = det动态本金3,650,000 × 0.006 ÷ 365 = 60
基准贡献 = det动态本金3,650,000 × 0.004 ÷ 365 = 40
原始当日收入 = 100
9月21日在结束日之后：原始收入 = 0
```

另外三种组合没有另起业务流程：年化项在存续日用动态本金除365，绝对项在期初日用初始本金一次计算。本例若仅把基准改成ABSOLUTE（系数仍0.004），18日原始收入变成 `60＋14,600=14,660`，19、20日各60；不能把“绝对”再按日分摊。期权不加交易佣金；999元额外奖励也只留在 `Adtnl_Rwd` 展示。

01的动态本金展示列会补0，但02仍引用原始 `det.Dyna_Nom_Prin`。原金额NULL时，不能从展示0倒推出本层收入一定为0。

## 四、结束日100怎样变成3,450

[05_保底与历史奖励](05_保底与历史奖励.sql)只给OPTION_STOCK、OPTION_IDX_ETF两类经营分类做结束日保底。本例9月20日的原始累计300，小于初始本金的0.1%即3,650，所以触发。

历史奖励直接读 `odata_n_ois.g_rev_hk_cross_income_reward`：按合同SUM拓展方部门所得收入、MAX核算结束日；本加工季之前且核算日期不早于202502的记录才入汇总，最大核算结束日还须早于本层合约结束日。本例无符合条件历史记录，金额补0，截止日回退固定值2025-03-31。

```text
结束日调整收入 = 保底3,650 − 历史金额0
                 − 截止日之后原始收入总和(100+100+100+0)
                 + 当前结束日原始收入100
               = 3,450
```

这是替换结束日那一行：之前100、100不变，合计正好3,650。不能把3,450再额外加到三天各100的结果上。第一个窗口按计提日累计用于触发；扣除金额的第二个窗口没有ORDER BY，读整个输入分区中截止日之后的记录，并非自动限于“当前行之前”。

若只新增一条有效历史金额1,000、核算结束日2026-06-30、核算日期202602，则9月20日替换值为2,450，本次输入累计2,650；与历史1,000合计才是3,650。历史金额不是本任务再次输出的一笔收入。源SQL注释说“累计实发”，但字段元数据是“拓展方部门所得收入（元）”，现有证据不证明支付事实。

## 五、收入分配、累计和日报字段

[06_分配与累计](06_分配与累计.sql)取调整后的 `Curr_Prvs_Sales_Income_n`，在外层改名回 `Curr_Prvs_Sales_Income`。因此日报的同名字段不再是原始100。

| 计提日 | 原始收入 | 调整后/日报当日收入 | 总累计 | 第1组累计70% | 第2组累计30% |
| --- | ---: | ---: | ---: | ---: | ---: |
| 9月18日 | 100 | 100 | 100 | 70 | 30 |
| 9月19日 | 100 | 100 | 200 | 140 | 60 |
| 9月20日 | 100 | 3,450 | 3,650 | 2,555 | 1,095 |
| 9月21日 | 0 | 0 | 3,650 | 2,555 | 1,095 |

香港SQL输出三组**累计收入**，没有118141的三组当日收入列。每一日调整收入分别乘该行比例后再累计；比例没有归一化。总累计及组累计最后用 `gfgreatest(累计,0)`取下限，不是先把每天负数清零。金额或“收入×比例”为NULL时，累计表达式将该项补0，但当日字段仍可为NULL。

有引入经办时，初始本金另分主经办1,460,000、引入经办2,190,000；动态/绝对本金各做同样的40/60。**这套比例作用于本金，70/30/0才作用于收入。** 没有引入经办（NULL或空串）时，主经办本金100%、引入0%。

[07_日报输出](07_日报输出.sql)只排列原82列。9月20日这行的主要值为：`Agt_Id=HK_OPT_DEMO`、`Accrued_Date=2026-09-20`、`busi_date=2026-09-21`、`Curr_Prvs_Sales_Income=3450`、`Accum_prvs_sales_income=3650`。三组累计2555/1095/0；额外奖励999依然单独展示。冻结查询没有最终CAST，本阅读版也不补造类型转换或INSERT。

## 六、只改变一个条件

仅把提前终止日改为9月19日，并固定上述det输入：01的结束日变19日，原始收入100/100/0/0，19日调整为 `3650−200＋100=3550`；最终当日收入100/3550/0/0，总累计100/3650/3650/3650。实际重跑时107491也可能改变本金，这个例子只隔离220979自身行为。

若只把基准计算类型改为空串，而客户侧没有可用回退值，则普通期权分支不命中，原始收入可全为NULL；NULL不能直接当0代入保底。若只缺价差类型和系数，保留年化基准0.004，收入CASE用年化缺省值，原始收入变40/40/40/0，展示年化价差却为空串。缺失要逐字段判断，不能用一句“参数缺了按0算”概括。

## 核对范围与复核方式

本阅读版基于[冻结SQL](../../公共加工/99_证据/220979-query.sql)，与2026-09-01采集的调度 `detail.querySql` 规范化换行后相同；发布绑定沿用公共证据索引。见[证据索引](证据索引.json)、[来源字段证据](来源字段证据.json)。元数据是8月离线采集，不能当平台当前状态。

真实多条匹配会放大收入、影响窗口；原窗口没有同日额外排序键。香港成本ON未用已读取的business_type，历史金额SUM与截止日MAX也并非挑同一行。`Accum_Absl_Nom_Prin`原表达式实际重复动态本金的累计，虽然互换当日 `Absl_Nom_Prin` 为0，其累计仍可非0；本阅读版保留并说明，不按字段名擅改。固定系数0.001/1.06/0.3的制度来源、真实源记录唯一性、金额换汇经济口径，尚需另外的业务证据。

在仓库根先运行 `npm run prepare:deps`，再在本目录运行 `node render.mjs --write` 和 `node --test checks.test.mjs`。生成[完整SQL](完整SQL.sql)时保留日期参数，不连接数据库。检查逐层还原全部token和82列顺序；构造案例执行交付SQL的真实SELECT、保底、分配、输出，以及真实事件聚合。收入案例的输入代表已经匹配的参数，未冒充执行Hive的日期展开JOIN。IF/UDF/时间函数采用明确的SQLite测试适配，不能据此声称Hive生产运行或业务验收已通过。
