# 114013：从合约逐日金额到对内销售收入日报

本任务回答：**一份合约每天为内部销售计提多少收入，其中多少归内部主经办人、多少归内部引入经办人，累计到今天是多少？** 结果进入`dm_otc_n.otc_inr_sale_daily_rpt`。它接用公共合约资料和逐日金额，但重新判断对内经营分类、选择对内参数；算出的计提收入不等于已经支付的钱。

第一遍沿下方`INR_DEMO`看“分类 → 参数 → 每日收入 → 内部人员分配 → 累计日报”，再打开[主脚本](00_主脚本.sql)对上SQL位置。B2B与特殊产品看完普通路径再读，参数的生产过程可暂时跳过。

```text
01 当前合约资料与对内分类info
          ├─ 107491逐日金额dy：初始本金、动态本金、保证金比例
          ├─ 客户cp：决定是否进入对内计算范围
          ├─ 02 映射mp → 类型基准b；合约价差sp；合约基准cb
          └─ 03 B2B自身＋关联合约期初估值npv
                              ↓
04 合约日收入contract_day_income：依次判断B2B、特殊类型、普通绝对/年化
                              ↓
05 内部分配allocated_day_income ← 当前合约管理关系m
                   收入100/0或40/60；按合约、计提日累计
                              ↓
06 保留原52列顺序及类型转换 → 对内销售收入日报
```

这是阅读承接，不是数据库物理执行顺序。主脚本把原子查询起成可读的名称，保留原来的连接位置、筛选位置和窗口层次。每一行代表“一条合约资料与一个逐日明细以及各路匹配结果”；各连接没有统一去重，不能直接声称合约号＋计提日唯一。

## 一、先让同一份合约进入计算

以下全是**构造数据**，金额假设为人民币元，费率使用小数。每路资料先只给一条匹配，帮助手算；不是生产记录，也不证明真实配置唯一。

| 输入 | INR_DEMO的值 | 来源与作用 |
| --- | --- | --- |
| 本次加工日 | 2026-09-21 | 主信息、客户、分类映射、类型基准、管理关系取此日快照 |
| 合约身份 | Agt_Id=`INR_DEMO`，客户`CUST_DEMO` | 主信息合约编号与交易对手客户编号；分别连接金额和客户 |
| 业务/源类型 | OPTION / NORMAL；非B2B | 本例不命中B2B或RISKY等优先收入公式 |
| 标的与范围 | EQUITY、Res_Flag=0；标的币种CNY、账簿部门OTC、行业99、分组01 | 用于对内分类；本例非跨境、非同业专门规则，未命中显式经营分类 |
| 定价日期 | 9月18日期初，9月20日期末，无提前终止 | 01生成结束边界；类型参数按期初日匹配 |
| 初始本金 | 每日明细均为3,650,000 | 来自107491的`dy.Init_Nom_Prin`，本任务没有直接改取主信息本金 |
| 动态本金 | 18/19/20/21日：3,650,000 / 2,920,000 / 1,825,000 / 0 | 来自107491的`dy.Dyna_Nom_Prin`，不在本任务重算事件或持仓 |
| 客户资格 | 删除标志0、监控标志1，来源为OIS客户表 | cp只决定范围；没有新增客户维度到输出 |
| 内部人员 | 有主经办人MAIN及引入经办人INTRO | 05使用`Inr_Main_* / Inr_Intro_*`，不是交叉介绍的三组关系 |

[01_合约范围与对内分类](01_合约范围与对内分类.sql)先取本次加工日主信息，要求`COALESCE(提前终止日,期末定价日) >= 2023-01-01`，排除原文指定的两个客户和FAST分组04。[04](04_合约日与当日收入.sql)再INNER JOIN逐日明细，要求明细业务日不早于2023-01-01；**只按合约号接，不另加分组或本次加工日限制**。因此本例的一份合约接出四个计提日。

客户cp也是INNER JOIN：加工日OIS客户来源中，满足“删除标志0且监控标志1”，或属于原文两个客户例外，才能保留。本例客户满足通常条件。没有逐日明细或没有合格客户，主信息本身不能补出一行日报。

两个日要分清：`dy.busi_date → Accrued_Date`是计提日；最终日报`busi_date`固定是本次加工日9月21日。同一次加工包含多个计提日，历史日期使用的是本次读取的资料，并非逐日重取当时的合约快照。

## 二、为什么还要重新分类？

公共主信息已经有合约和标的分类，但对内参数按另一套经营分类维护。[01](01_合约范围与对内分类.sql)分别新增`Undrl_Type_n`与`Inr_Contr_Type_Cd/Desc`，[04](04_合约日与当日收入.sql)最后选定日报分类，不能把这个规则说成公共主信息早已统一完成。

本例先由`EQUITY + Res_Flag=0`得到`CIR_STOCK`（流通股），没有命中显式对内分类。于是进入[02](02_分类映射与参数.sql)的mp映射：演示配置将源类型NORMAL、标的类别ALL_STOCK、子类型NULL映射为CD017/其他。ALL_STOCK展开为PRI_STOCK与CIR_STOCK两条，只有CIR_STOCK匹配本例；子类型NULL在连接时回退主体子类型。

```text
源标的EQUITY、非限售 → CIR_STOCK
源类型NORMAL＋CIR_STOCK＋子类型匹配 → 演示mp配置CD017
日报分类 = COALESCE(01显式对内分类, mp运管分类, 'CD017') → CD017
```

这里NORMAL→CD017是构造配置，不断言真实环境存在这行。即使没有mp命中，默认也会是CD017；仅看最终代码无法区分“配置命中”和“默认兜底”，需回看连接。

01的显式分类顺序值得单独看清：

| 先后 | 触发类别 | SQL给出的经营分类 |
| --- | --- | --- |
| 1 | 2026年起期初、指定港股通汇率模式、RISKY/AIRBAGX/S_CROSS_SWAP | CD025，特殊气囊（港股通） |
| 2 | OPTION、行业11或13、非B2B、非四类特殊期权，且非个股/GDR/QIS | CD002，同业自主对冲真期权（非个股） |
| 3 | 同上同业条件、标的是QIS | CD020，策略指数-同业期权 |
| 4 | OPTION且B2B | CD001，真期权背靠背 |
| 5 | OPTION、非四类特殊期权；OTC账簿＋非CNY，或指定香港客户条件＋CNY | 按非个股、个股/GDR、QIS分别为CD023、CD024、CD021 |
| 6 | 剩余OPTION且QIS | CD022，策略指数-其他期权 |
| 7 | TRS、指定香港客户条件、标的币种CNY | CD018，北上跨境互换 |
| 8 | 剩余TRS且QIS | CD019，策略指数-互换 |
| 未命中 | 交给mp映射，再兜底 | CD017/其他 |

上表名称来自本SQL的CASE字符串；不是从行业代码另推制度定义。具体“指定香港客户条件”和四类排除条件保留在01。**分类CASE和收入CASE是两件事**：港股通特殊条件可能先给出CD025，收入仍会先判断B2B。

## 三、参数并行匹配，再逐字段选择

[02](02_分类映射与参数.sql)负责准备匹配资料，全部ON条件在[04](04_合约日与当日收入.sql)就地可见。它们不是先后执行的四次收入计算。

| 资料 | 实际匹配键和日期 | 本例值 |
| --- | --- | --- |
| 类型基准b | 最终经营分类CD017＋**期初定价日9/18**；源配置9/1生效，覆盖该日 | 计算方式ANNUALIZED；基础系数1、基础收益率0.004、附加收益率0.002 |
| 合约基准cb | `Inr_Comp_No=INR_DEMO`，按原合约号，无日期选版 | 计算类型ABSOLUTE；基础系数2、基础收益率0.003 |
| 合约价差sp | `Inr_Comp_No=INR_DEMO`＋**计提日**，系数类型INR；9/18起生效 | 计算类型ANNUALIZED；年化价差0.002、绝对价差0.01 |

sp与b都先按“本生效日到下一生效日前一天”展开，最后一段延续到加工日。**展开相似，使用日期不同**：sp跟着计提日切换；b以合约期初日固定选中那一段。cb没有按日期取最新一条；多条匹配依然可能扩行。

本例故意让cb与b的计算方式不一致，观察真实选择顺序：

| 要选的值 | 原查询优先级 | 本例结果 |
| --- | --- | --- |
| 普通分支计算方式 | b类型 → cb合约 → sp价差 → ABSOLUTE | ANNUALIZED，取b |
| 基础系数 | cb合约 → b类型 → 公式补0 | 2，取cb |
| 基础收益率 | cb合约 → b类型 → 公式补0 | 0.003，取cb |
| 年化价差 | sp年化价差 → b附加收益率 → 0 | 0.002，取sp |
| 绝对价差 | sp绝对价差 → b附加收益率 → 0 | 普通绝对分支才使用，本例先不用0.01 |

所以不能概括成“合约参数整套优先”。`COALESCE`只因NULL回退，0有效；b/cb的空串计算类型也不会自动回退。sp只有在其查询内先把空串计算类型转为NULL。

继续追源参数生产时，读公共[对内与香港基准](../../公共加工/05_经营系数_基准/06_对内与香港基准.md)、[对内与香港价差](../../公共加工/04_经营系数_价差/06_对内与香港价差.md)。分类映射、类型基础参数、合约基准生产保留在公共加工，114013这里只维护自己怎样匹配、选择和使用，不从113993参数展示查询反推收入规则。

## 四、每天的100、80、50是怎么算出来的？

[04](04_合约日与当日收入.sql)保留一段完整收入CASE，按B2B → RISKY/AIRBAG四类 → B_LONG_SHORT_SWAP → 普通绝对 → 普通年化顺序选择。我们的合约走最后的普通年化：

```text
9/18：3,650,000 × 2 × (0.003 + 0.002) ÷ 365 = 100
9/19：2,920,000 × 2 × (0.003 + 0.002) ÷ 365 = 80
9/20：1,825,000 × 2 × (0.003 + 0.002) ÷ 365 = 50
9/21：        0 × 2 × (0.003 + 0.002) ÷ 365 = 0
```

基础系数是乘数，基础收益率与价差先相加。原SQL在这里没有再除100，年化固定除365，也没有再加“计提日在起止日期内”的IF。9/21为0是因为本例107491输入本金为0；**若只把9/21的输入本金改成3,650,000，这里仍算100**。是否应归零不能靠本段的日期条件来保证。

普通绝对分支则在期初日一次计入`初始本金 × 系数 × (基础收益率＋绝对价差)`，其他日为0；旧合约期初早于2023-01-01时，还允许在2023-01-01一次补记。ABSOLUTE在此是收益率口径，不是把价差字段直接当收入金额。

## 五、收入怎样分到两个人，并累计到日报？

[05](05_内部分配与累计.sql)接04的每条结果t，再按合约号连接当前加工日管理关系。引入经办人ID为NULL或空串时，主经办收入100%、引入0%；否则主40%、引入60%。判断没有验证主经办人是否存在，也没有将空白字符视为空串。

| 计提日 | 当日收入 | 主经办40% | 引入60% | 累计收入 | 累计主经办 | 累计引入 | 累计动态本金 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 9/18 | 100 | 40 | 60 | 100 | 40 | 60 | 3,650,000 |
| 9/19 | 80 | 32 | 48 | 180 | 72 | 108 | 6,570,000 |
| 9/20 | 50 | 20 | 30 | 230 | 92 | 138 | 8,395,000 |
| 9/21 | 0 | 0 | 0 | 230 | 92 | 138 | 8,395,000 |

**40/60分的是收入，不是本金**，也不使用118141的三组介绍比例。累计动态本金只累加起初日至结束日内的`dy.Dyna_Nom_Prin`，是每日本金求和，不是日均本金；收入累计没有这层日期限制。若9/21异常输入仍为365万，当日收入和累计收入会增加100，累计本金仍不增加。

所有累计均按合约号分区、计提日排序，原SQL没有明确写ROWS窗口框架。同日多条匹配会影响累计，不能把结果当作按真实事件先后逐条滚动；构造客户重复一条时，四行变八行，第一天累计收入200，最后累计460。这里没有为了图省事新增去重。

[06](06_日报输出.sql)沿原52列顺序输出。本例9/21那一行：`Accrued_Date=2026-09-21`、`busi_date=2026-09-21`、`Sales_Income=0`、`Accum_Sales_Income=230`、`Accum_Sales_Income_Main=92`、`Accum_Sales_Income_Intro=138`。9/18那一行的busi_date也仍为9/21。原来有CAST的列保持转String；本整理没有另加四舍五入。

## 七、B2B：先合并估值，再一次分配

把同一合约的对冲类型改为B2B。保留同一组日期、逐日本金和内部人员；期初NPV设为1,200，`Rel_Agt_Id='REL_A,REL_B'`，两份关联合约当前快照NPV分别-200、-100。

[03_B2B期初估值](03_B2B期初估值.sql)依次做三件事：拆开逗号分隔的关联合约号 → 按编号连接当前主信息中的关联合约NPV → 按本合约汇总`MAX(自身NPV) + SUM(关联NPV)`。自身值因拆成两行仍只取一次MAX，因此本例是`1,200 - 200 - 100 = 900`，不是把1,200加两次。

| 阶段 | 同一合约的结果 |
| --- | --- |
| 03 | INR_DEMO的initial_npv=900 |
| 04 | B2B分支最先命中；9/18收入900，19/20/21均0；不使用普通基准和价差公式 |
| 05 | 9/18主360、引入540，后面每日0；累计收入始终900，累计分配360/540 |
| 06 | 当日与累计按上述值输出，定价日、逐日本金等字段仍随原记录保留 |

即使源类型同时是AIRBAGX，收入也先走B2B。若期初早于2023-01-01，则2023-01-01可以记这笔估值；这不表示每天重复计提。

若全部关联合约都没匹配到，`SUM(关联NPV)`为NULL，`MAX(自身NPV)+NULL`仍为NULL；04期初日收入保持NULL，05才变0。若只有一份关联缺失，SUM跳过缺失值，仍会用找到的部分计算。重复关联编号或关联表多条匹配可能重复加关联NPV；MAX只防止自身简单重复相加，不能替代关系去重。这里保留原行为，没有补写“缺失关联为0”的业务规则。

## 八、RISKY/AIRBAG：展示融资比例与真实乘数不同

仍沿INR_DEMO，只把源类型改成RISKY、AIRBAGX、AIRBAGM或AIRBAGL中的一种，非B2B；构造映射配置随源类型匹配CD017。其他参数与本金保持不变。主信息初始保证金比例`Init_Marg_Prop=0.2`，逐日明细`Marg_Prop=0.3`，主信息实际费率`fee_rate=0.07`。

在04，日报展示`fee_rate=0.07`，展示`Fin_Rati=1-0.3=0.7`；**真实收入乘数却取初始保证金比例形成的0.8**，fee_rate没有参与本公式。

```text
9/18收入 = 3,650,000 × (1-0.2) × 2 × (0.003+0.002) ÷ 365 = 80
9/19收入 = 64；9/20收入 = 40；9/21收入 = 0
05累计收入 = 184；累计主经办 = 73.6；累计引入 = 110.4
06照此输出；仍显示Fin_Rati=0.7，不能用0.7反算上述收入。
```

特殊公式还保留了一个容易漏掉的判断：初始保证金比例为NULL或恰好1时，`1-IF(COALESCE(初始比例,1)=1,0,初始比例)`得到1，收入回到100/80/50/0，并非全额保证金就收入0。若改为1.2，本公式没有封顶，第一天收入-20、累计-46；外层没有把负收入截成0，主/引入累计分别-18.4/-27.6。该说明是SQL行为，不替它补造制度理由。

## 九、B_LONG_SHORT_SWAP：用当日保证金，缺失不回退初始比例

把同一合约改为TRS、源类型B_LONG_SHORT_SWAP，仍非B2B。01先把**用于参数匹配**的标的类别置空；mp对应源类型也产生空标的类别，二者匹配。04输出标的时才把源标的字符串中的EQUITY替为CIR_STOCK，所以输出是流通股，不代表参数是按流通股匹配的。

继续使用初始比例0.2、当日比例0.3：公式取当日比例，乘数0.7；每日收入70/56/35/0，累计161，主64.4、引入96.6，再由06原样输出。

若只把当日比例改为NULL，**展示Fin_Rati退到初始比例，显示0.8；真实公式把当日比例补0，乘数为1**。此时每日收入100/80/50/0，累计230，主92、引入138。若当日比例大于1，真实公式封顶为1，收入为0；负比例没有下限处理。本分支与上一组初始保证金公式不能合并为一句“本金乘融资比例”。
