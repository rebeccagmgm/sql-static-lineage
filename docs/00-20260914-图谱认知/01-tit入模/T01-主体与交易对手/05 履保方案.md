# 05 履保方案

**履保方案把“为哪个交易对手、按什么方式管理履约保障、启用哪些处理功能”组织成一个有独立编号的配置对象。它关联主体、协议和业务组合；方案参数与每日保证金结果、实际追提保动作分别保存。**

```sql
SELECT
    ID AS "履保方案ID", PLAN_CODE AS "履保方案编号",
    KEY_CTPTY_ID AS "交易对手ID", GROUP_CTPTY_ID AS "管理人交易对手ID",
    PLAN_STATUS AS "方案状态原码", PLAN_PROPERTY AS "方案属性",
    CTPTY_GUARANTEE_ID AS "履保协议ID", ULTRA_CONTRACT_ID AS "大合约ID",
    NEED_MARGIN AS "是否履保", MARGIN_TYPE AS "履保类型",
    MONITOR_PATTERN AS "履保模式", MARK_MARKET AS "盯市类型",
    MARGIN_COLLATERAL_TYPE AS "履约担保品类型",
    UNDERLYING_SCOPE AS "标的范围", JOINT_TYPE AS "连带担保类型",
    DEDUCTION_PATTERN AS "抵扣模式", CHARGE_PATTERN AS "收费模式原码",
    AUTO_UPDATE_MARGIN_LINE AS "自动更新履保线原值",
    AUTO_REMARGIN AS "自动追保", AUTO_WITHDRAW AS "自动提保",
    AUTO_MARGIN_OP_TIME AS "自动追提保时间",
    RECEIVER_MIN_AMOUNT AS "接收方最小转移金额",
    PAY_MIN_AMOUNT AS "支付方最小转移金额",
    SPECIAL_PLAN_REMARK AS "特批方案备注", BUSI_DATE AS "业务日期"
FROM ODATA_N_TIT.D_MARGIN_PLAN
WHERE BUSI_DATE = '2026-09-15'
ORDER BY PLAN_PROPERTY, MONITOR_PATTERN, ID
LIMIT 500;
```

## 1. 贴源与模型：方案配置是一张主表，适用关系另表保存

### 1.1 先看方案本身，再看谁在使用它

| 贴源表 | 保存什么 | 记录怎样理解 |
| --- | --- | --- |
| `ODATA_N_TIT.D_MARGIN_PLAN` | 方案身份、交易对手及管理人、协议与大合约引用、履保模式、担保与收费配置、追提保安排 | 以 `ID` 识别方案，`PLAN_CODE` 为业务编号；结合业务日期读取该日配置。同一客户不能默认只对应一套方案 |
| `ODATA_N_TIT.D_TRD_BUNDLE_INFO` | 业务组合，以及组合选择的履保方案 | `BUNDLE_ID` 识别组合，`KEY_PLAN_ID` 指向方案 `ID`；它补充方案适用关系，不提供方案各项参数 |

**本篇配置内容的主要贴源就是 `D_MARGIN_PLAN`。** 组合表用于解释具体合约怎样找到方案，不是 200060 写入方案模型时必经的中间表。方案中的主体、协议、大合约字段是引用；相应对象的详细资料仍保存在各自主题中。

### 1.2 同一份方案资料有哪些入模与消费去向

| 去向 | 从哪里取得数据 | 保存或使用的内容 |
| --- | --- | --- |
| `PDATA_N.T01_CUTP_PERF_MARG_PLAN_INFO` 交易对手履保方案信息 | 200060，来源盘点指向 `D_MARGIN_PLAN`，SQL 读表使用 `${src_table}` | 将方案配置组织成 T01 模型；保留方案 ID，交易对手与管理人转成 `TIT060-` 主体编号，状态及收费模式尝试转标准码 |
| `PDATA_NDS.MARGIN_PLAN` | 199159 直接读取方案贴源 | 同一源方案的另一条承接路径，不能因同名就认定先经过 T01 |
| `PDATA_N.T98_OTC_DERI_COMP_SALE_INFO` 销售合约汇总 | 86840、86841、220650 从合约经组合关联方案贴源 | 已核实取用抵扣模式 `DEDUCTION_PATTERN → Ddct_Ptrn`；不是本篇全套配置的复制表 |

T01 模型回答“这套履保方案保存了哪些条件”，销售合约汇总中的这条消费回答“这份合约选中方案的抵扣模式是什么”。每日履保余额、应追保额、可提取额和实际收付需要相应结果与流水，本表不把配置加工成这些金额。

## 2. 履保方案把客户约定接到具体交易上

客户资料回答“与谁做业务、客户层有哪些约定”，履保方案进一步回答：**这一组业务采用哪种履保口径，怎样组织盯市，采用现金还是授信，以及怎样安排追保和提保。** 因此它有独立的 `ID` 和业务编号 `PLAN_CODE`，识别方案时需要保留这两个层次，不能把交易对手 ID 当作方案 ID。

方案中的几个主体和协议引用各有职责。`KEY_CTPTY_ID` 指向交易对手，`GROUP_CTPTY_ID` 的元数据明确是“管理人交易对手 ID”：前者说明方案关联的客户，后者另存管理人身份。这里的 GROUP 不是 02 篇的账户组。`CTPTY_GUARANTEE_ID` 和 `ULTRA_CONTRACT_ID` 则分别保存履保协议、大合约引用，把这套配置与相应约定联系起来。

**哪份合约使用这套方案，要看业务组合的选择。** 已核实的期权、互换销售合约汇总通过以下路径取数：

```mermaid
flowchart LR
    C["期权／互换合约<br/>BUNDLE_ID"] -->|"找到所属组合"| B["D_TRD_BUNDLE_INFO<br/>BUNDLE_ID"]
    B -->|"KEY_PLAN_ID = ID"| P["D_MARGIN_PLAN<br/>具体履保方案"]
    P -->|"取 DEDUCTION_PATTERN"| S["销售合约汇总<br/>Ddct_Ptrn 抵扣模式"]
```

这使“客户归属”和“方案适用”有了明确区别：客户身份帮助找到相关资料，组合上的 `KEY_PLAN_ID` 才在这条消费路径中选定方案。仅凭合约与方案属于同一客户，无法替代组合的选择。方案自身另有 `PLAN_GROUP_ID`，其含义是**模板分组**，也不是这里连接合约的业务组合。

这条链还有一个实际价值：销售汇总中的抵扣模式可以追溯到组合选中的方案。字段在源端叫 `DEDUCTION_PATTERN`，在 T01 方案模型中叫 `Comut_Mode_Cd`，在销售汇总中叫 `Ddct_Ptrn`。名称不同，承接的是同一项抵扣配置；销售汇总目前核实的是取模式值，不是计算抵扣金额。

## 3. 理解履保口径，要同时看“类型、模式、盯市范围”

### 3.1 是否履保与怎样履保，分别保存

`NEED_MARGIN` 保存是否履保；`MARGIN_TYPE` 再区分 `DYNAMIC` 动态履保、`STATIC` 静态履保和 `NONE` 否（CD731）。前者给出履保标志，后者给出履保类型。把它们压成一个“是否收保证金”，会丢掉类型信息，也会把后面的授信方式排除在理解之外。

动态／静态并没有在本段入模中展开成计算规则。实际按什么口径管理，还要继续读 `MONITOR_PATTERN`；不能仅从 DYNAMIC 推出每日重算频率，也不能从 STATIC 推出永不调整。

### 3.2 市值、名义本金、多空，是不同的履保模式

`MONITOR_PATTERN` 保存履保模式。市值和名义本金首先区分关注的量：一个指向价值口径，一个指向交易的名义规模。多空相关模式又进一步表达多空及单边口径；**它们改变的是理解履保规则的起点，而不是只换一个显示名称。**

CD1500 的已查码值如下。源字段旧注释只列“市值／名义本金”，实际读数应按具体模式识别：

| 模式码 | 含义及阅读重点 |
| --- | --- |
| `MARKET_VALUE` | 市值，按市值模式理解履保口径 |
| `NOTIONAL_PRINCIPAL` | 名义本金，不能拿市值直接替代其口径 |
| `TRADING` | 交易型，具体规则需对应交易型逻辑 |
| `LONG_SHORT` | 多空，字典本身未说明怎样轧差 |
| `LONG_SHORT_SIDE_MV` | 多空单边（市值），同时带有单边范围和市值口径 |
| `LONG_SHORT_SIDE_NP` | 多空单边（名义本金），与上一项的计量口径不同 |
| `CST_MARKET_VALUE` | 券抵市值，要与普通市值模式区分 |
| `NONE` | 不启用履保 |

这些标签尚未给出履保比例的分子分母、单边取值方法或折扣公式。文档能据此识别模式差异，具体金额仍由对应计算逻辑解释。

### 3.3 逐笔还是组合，决定怎样组织盯市

`MARK_MARKET` 的 `SINGLE` 是逐笔，`PORTFOLIO` 是组合（CD732）。它与履保模式回答不同的问题：**模式说明按什么口径管理，盯市类型说明按单笔还是组合组织观察。** 因此“组合”本身没有说明按市值还是名义本金，也没有说明多空怎样抵消。

还要分清两个“组合”：第二节的 `BUNDLE_ID` 是合约找到方案的关联键；这里的 `PORTFOLIO` 是方案里的盯市类型。合约通过业务组合选中方案，并不因此就证明该方案配置了组合盯市。反过来，看到 PORTFOLIO，也不能从这个枚举直接列出参与盯市的全部合约。

## 4. 担保方式、标的范围和连带担保，分别补足什么

`MARGIN_COLLATERAL_TYPE` 的字段名容易让人以为它列出股票、债券等担保品品种，但当前字典 CD1502 只有 `CASH` 现金和 `CREDIT` 授信。这里首先区分的是**以现金还是授信方式表达履约保障**。CREDIT 不是一笔已缴现金余额，也没有直接给出可用授信金额；额度指标另见 [04 额度](00-20260914-图谱认知/01-tit入模/T01-主体与交易对手/04%20额度.md)。

`UNDERLYING_SCOPE` 则区分 `TRADABLE` 流通、`RESTRICTED` 限售和 `MIXTURE` 混合（CD1694），描述方案的标的范围。它把标的的流通性质带入配置，但没有列出具体证券和数量。读取“混合”可以知道范围并非只含一种流通性质，要知道究竟有哪些标的，还需具体业务明细。

`JOINT_TYPE` 补充连带担保类型：`NONE` 无、`NATURAL_PERSON` 自然人、`MANAGERS` 管理人（CD1695）。这与方案保存管理人身份是两件事：`GROUP_CTPTY_ID` 回答管理人是谁，`JOINT_TYPE` 回答配置了哪类连带担保。仅有管理人 ID，并不等于管理人承担了连带担保。

所以，读一套方案的担保安排时，要把这三层信息合起来：**现金／授信是保障方式，流通／限售是标的范围，自然人／管理人是连带担保类型。** 它们仍未组成担保品持仓清单，也不能替代具体担保协议中的责任条款。

## 5. 抵扣、收费、浮盈开仓，为什么会同时出现在方案里

履保方案除了履保口径，还保存与费用、开仓相关的配置。阅读时要分辨它们改变的是哪件事，尤其不能把所有与期权费有关的字段都解释成“收费”。

**抵扣模式决定是否采用抵扣配置。** `DEDUCTION_PATTERN` 的 `DEDUCTION` 为抵扣，`NO_DEDUCTION` 为不抵扣（CD734）；第二节的销售合约消费路径确实取用了它。方案另外保存 `OPTION_SWAP_FEE_RATIO`，入模含义为“券抵期权费比例系数”。前者是模式，后者是具体用途的比例参数；当前证据没有把两者展开成一套计算公式，也没有说明该比例作用于哪个金额基数。

**收费模式表达收费条件，期权费分拆表达报告展示。** `CHARGE_PATTERN` 源注释列“固定／加权平均”，入模时通过转换表转成标准收费模式。`FEE_SPIN_OFF` 则是“估值报告期权费分拆标志”：启用它表达报告要分拆展示期权费，不是因此又新增一项收费。要解释实际费用，应继续追收费模式、适用参数和计费逻辑，不能用展示标志代替金额规则。

**浮盈开仓涉及开仓配置，尚未给出可开仓金额。** `FLOAT_PROFIT_OPEN` 保存浮盈开仓标志。它使方案能够表达是否启用这项配置，但没有在此把浮盈换算成可开仓额。`CUSTOM_RATIO` 另存客户系数，其参与哪一步计算目前也没有公式证据，不能顺手把它套到浮盈、履保比例或期权费上。

还有一些字段限定业务背景：`TRS_STRUCTURE_TYPE` 保存互换结构类型，`IS_ALLMARKET_PB` 保存一站通标志；`EARLY_LOCK_PL` 的源注释具体指**气囊 X 提前锁定收益**。最后这一项应放回对应产品理解，不能泛化成所有履保方案都具备同一锁盈机制。

## 6. 自动追提保配置，控制的是哪几件事

追保和提保分别对应补充与提取履约保障资金的方向，源资料将它们分开配置：`AUTO_REMARGIN` 控制自动追保，`AUTO_WITHDRAW` 控制自动提保。查到其中一个已启用，并不能替代另一个的值。这种拆分保留了两种处理方向各自的安排。

与它们一起出现的字段又分成三类。

**监控与规则维护。** `MONITOR_PRODUCT_VALUATION` 保存是否监控估值；`AUTO_UPDATE_MARGIN_LINE` 保存更新履保线类型。前者关乎监控配置，后者关乎履保线的更新方式，都不是某日已经算出的估值或履保比例。尤其后者在 SQL 中按类型原值传递，不能因名称以 AUTO 开头就当作普通 Y/N 开关。

**执行时间安排。** `AUTO_MARGIN_OP_TIME` 保存自动追提保时间。它描述配置的处理时间，不是某次追保通知发出、客户确认或资金到账的时间。

**资金转移门槛。** `RECEIVER_MIN_AMOUNT` 和 `PAY_MIN_AMOUNT` 分别保存接收方、支付方最小转移金额。它们约束的是转移金额门槛，区别于履保模式、履保线和业务额度；两个方向分别有值，也不宜压成一个“最小金额”。当前资料没有说明它们在执行中怎样比较、如何处理等于门槛的情况，也未在该投影中提供配套币种，不能据此补出自动转账公式。

这些字段共同描述自动化安排，但本段 SQL 只是保存配置，未展示监控、算额、判门槛、发指令的实际调用顺序。**某日需要追多少、允许提多少是业务结果；是否启用自动处理、何时处理、转移门槛是多少是方案条件。** 两者结合才能解释当天的处理，单看开关无法得出资金已经收付。

账户也有同样的区分：`NEED_ALLOCATE_CAP_ACCT` 表示是否指定资金账户，方案这里保存的是指定账户标志。要找实际资金账户及其余额，需继续进入具体账户关系和每日结果，见 [T03 协议账户与合约](../T03-协议账户与合约/00%20协议账户与合约全貌.md)。

## 7. 标准／特批与生效／审核中，分别说明方案什么状态

`PLAN_PROPERTY` 的 `STANDARD` 标准和 `SPECIAL` 特批（CD1693）说明方案属性；`PLAN_STATUS` 说明方案所处的业务状态。模型状态字典 CD1692 包括 `01` 生效、`02` 审核中、`03` 经办人经办。**特批方案仍需要看状态，标准方案也不能仅凭 STANDARD 就认定已经生效。**

对特批方案，`SPECIAL_PLAN_REMARK` 比单独的 SPECIAL 标签更接近具体约定：读者应把备注与模式、担保和处理配置放在一起，理解特殊安排。现有加工直接承接备注，没有把文字自动转换成另外一套执行规则。

状态和收费模式是本表两项需要特别留意的转码字段：SQL 先查源码到标准码的转换表，未命中时保留源值。因此，上面的 `01/02/03` 是模型字典含义，不能未经核对就直接套在查询 SQL 返回的 `PLAN_STATUS` 原码上。收费字典 CD277 中虽有 `30` 加权平均，也不能把源注释“固定”随意配到字典里某个带“固定服务费”的值。

## 8. 从业务含义回查模型字段

T01 方案模型为 `PDATA_N.T01_CUTP_PERF_MARG_PLAN_INFO`。它把上述配置集中保存，便于按方案和当事人查询；这里没有重算每日履保余额、应追保额或可提取额。

| 业务内容        | 源字段 → 模型字段                                                                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 方案与主体身份     | `ID → Perf_Marg_Plan_Id`；`PLAN_CODE → Perf_Marg_Plan_Cd`；`KEY_CTPTY_ID → Pty_Id`；`GROUP_CTPTY_ID → Mgmt_Cutp_Pty_Id`，两个主体 ID 加 `TIT060-` 前缀，管理人为空时保留空值 |
| 协议、大合约、模板   | `CTPTY_GUARANTEE_ID → Cutp_Perf_Marg_Agt_Id`；`ULTRA_CONTRACT_ID → Ultra_Contr_Id`；`PLAN_GROUP_ID → Tplt_Grp_Id`                                        |
| 履保类型与口径     | `NEED_MARGIN → Perf_Marg_Flag`；`MARGIN_TYPE → Enable_Perf_Marg_Type_Cd`；`MONITOR_PATTERN → Perf_Marg_Mode_Cd`；`MARK_MARKET → Mtm_Type_Cd`              |
| 担保与标的范围     | `MARGIN_COLLATERAL_TYPE → Perf_Guar_Type_Cd`；`UNDERLYING_SCOPE → Undrl_Scop_Cd`；`JOINT_TYPE → Jnt_Guar_Type_Cd`                                        |
| 抵扣与收费       | `DEDUCTION_PATTERN → Comut_Mode_Cd`；`CHARGE_PATTERN → Chrg_Mode_Cd`；`OPTION_SWAP_FEE_RATIO → Scr_Ofst_Opt_Fee_Prop_Coef`                               |
| 报告展示与开仓     | `FEE_SPIN_OFF → Valu_Rpt_Opt_Fee_Split_Flag`；`FLOAT_PROFIT_OPEN → Flot_Prft_Opps_Flag`；`CUSTOM_RATIO → Cust_Coef`                                      |
| 监控、履保线与资金账户 | `MONITOR_PRODUCT_VALUATION → Montr_Valu_Flag`；`AUTO_UPDATE_MARGIN_LINE → Upd_Perf_Marg_Line_Type_Cd`；`NEED_ALLOCATE_CAP_ACCT → Asgn_Fnd_Acct_Flag`     |
| 自动追提保       | `AUTO_REMARGIN → Auto_Remarg_Flag`；`AUTO_WITHDRAW → Auto_Mincom_Flag`；`AUTO_MARGIN_OP_TIME → Auto_Remarg_Mincom_Time`                                  |
| 最小转移金额      | `RECEIVER_MIN_AMOUNT → Recv_Side_Min_Dvrs_Amt`；`PAY_MIN_AMOUNT → Paid_Side_Min_Dvrs_Amt`                                                               |
| 状态与特批约定     | `PLAN_STATUS → Perf_Marg_Plan_Stat_Cd`；`PLAN_PROPERTY → Perf_Marg_Plan_Prop_Cd`；`SPECIAL_PLAN_REMARK → Spec_Plan_Remark`                               |
| 适用业务背景      | `TRS_STRUCTURE_TYPE → Swap_Comp_Stru_Type_Cd`；`IS_ALLMARKET_PB → One_Stop_Shop_Flag`；`EARLY_LOCK_PL → Erly_Lock_Yield_Flag`                            |

布尔标志按 `Y → 1`、`N → 0` 转换，其他原值保留；模式、类型和金额等按各自字段承接。协议及大合约引用在此也没有统一转换成 T03 协议身份。
