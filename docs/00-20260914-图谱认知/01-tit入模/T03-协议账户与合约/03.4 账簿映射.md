# 03.4 账簿映射

**阅读重点：来源去向、筛选条件与盈亏方向。**

```sql
SELECT
    M.ID                  AS "映射关系ID",
    M.KEY_BOOK_ID_FROM    AS "源账簿ID",
    F.BOOK_NAME           AS "源账簿名称",
    M.KEY_BOOK_ID_TO      AS "目标账簿ID",
    T.BOOK_NAME           AS "目标账簿名称",
    M.DIRECTION           AS "盈亏方向转换",
    M.CREATE_DATETIME     AS "创建时间（底稿名称）",
    M.UPDATED_DATETIME    AS "更新时间",
    M.CREATED_BY          AS "创建人",
    M.UPDATED_BY          AS "更新人",
    M.REMARK              AS "备注",
    M.DATA_TIME           AS "数据时间",
    M.BUSI_DATE           AS "业务日期"
FROM ODATA_N_TIT.D_BK_BOOK_MAPPING M
LEFT JOIN ODATA_N_TIT.D_REF_BOOK F
    ON M.KEY_BOOK_ID_FROM = F.KEY_BOOK_ID
   AND M.BUSI_DATE = F.BUSI_DATE
LEFT JOIN ODATA_N_TIT.D_REF_BOOK T
    ON M.KEY_BOOK_ID_TO = T.KEY_BOOK_ID
   AND M.BUSI_DATE = T.BUSI_DATE
WHERE M.BUSI_DATE = '2026-09-14'
ORDER BY M.ID
LIMIT 500;
```

## 1. 业务定位：账簿之间的有向映射

**`D_BK_BOOK_MAPPING` 维护“从哪个账簿映射到哪个账簿，以及盈亏方向如何转换”。** 账簿自身的名称、组织归属和流程开关在 `D_REF_BOOK`；映射适用于哪些数据，还要看 `D_BK_BOOK_MAPPING_RULE`。

这三个对象分别回答：

| 对象 | 回答的问题 | 主要字段 |
|---|---|---|
| 账簿主数据 `D_REF_BOOK` | 这是什么账簿，归属谁，有哪些处理配置？ | `KEY_BOOK_ID`、名称、公司、部门、desk、流程开关 |
| 映射关系 `D_BK_BOOK_MAPPING` | 从哪本账映射到哪本账，盈亏方向怎样处理？ | `ID`、`KEY_BOOK_ID_FROM / TO`、`DIRECTION` |
| 映射条件 `D_BK_BOOK_MAPPING_RULE` | 该映射筛选哪些字段、按什么条件命中？ | `KEY_BOOK_MAPPING_ID`、`COLUMN_NAME`、`OPERATOR`、`CONDITION` |

当前提供的“全量”文件实际含 2026-09-14 的 26 条关系；关系 ID、源目标账簿对在此快照内均唯一。它连接 21 个源账簿和 10 个目标账簿，全部能在同日 274 条账簿底稿中找到名称。“全量”是文件名，本次未重新联网验证平台完整性。

## 2. 换成账簿名称后，映射用途才清楚

| 源账簿 | 目标账簿 | 能从名称与关系确认的内容 |
|---|---|---|
| `10015` OTC-互换-ISDA | `10043` OTCHK-互换-BTB | ISDA 账簿关联到香港互换 BTB 账簿 |
| `10015` OTC-互换-ISDA | `10114` GFGCFICC-互换-ISDA-B2B | 同一来源还有另一目标，不能只保留一个目标 ID |
| `10014` OTC-互换-内部交易 | `10094` EQD-绝对收益大宗-BTB；`10111` EQD-绝对收益多头组合-BTB | 内部交易账簿与不同管理用途的目标账簿关联 |
| `10041` OTC-期权-主动对冲-指数增强 | `10094`、`10111`、`10221`、`10043` | 同一源账簿实际有四个目标；具体哪些数据去哪个目标，必须再看条件 |
| `10118` OTC-互换-跨境期权对冲 | `10119` OTCHK-互换-跨境期权对冲 | 两个不同账簿共同围绕跨境期权对冲命名 |
| `10145` OTC-互换-北向策略指数对冲；`10182` 境外-策略指数-合约-互换 | `10144` HK策略指数-对冲互换 | 多个来源可指向同一目标 |

因此应把映射表达为**有方向的多对多关系**，保留独立的关系 ID；不能在账簿上放一个 `parent_book_id` 就替代它。名称中的 BTB、B2B 和“对冲”提供用途线索，但不单独证明已发生对冲交易、会计记账或损益抵销。

## 3. 字典与方向：组织标签不能代替映射规则

目标账簿中的公司、部门、desk 可按源字典分别解释：

| 字段／字典域 | 本次目标中出现的代码及含义 |
|---|---|
| `company`／`Company` | `GFS` 广发证券；`GFS_HK` 广发全球资本 |
| `department`／`Department` | `OTC_HK` 柜台交易市场(香港)部；`EQD_JDSYZ` 股衍部绝对收益组；`HK_FICC` 香港FICC |
| `desk`／`Desk` | `OTCHK_TRS` HK互换持仓；`JDSYZ` 股衍部绝对收益组；`HKFICC_TEST` 测试账簿；`OTCHK_DYNAMIC_HEDGING` HK期权主动对冲；`OTCHK_QIS` HK策略指数；`HKFICC_N_TRS` 北向TRS |
| 关系类型／仓库 `CD051` | `N05` 账簿协议与账簿协议；具体 FROM→TO 朝向由映射字段及 SQL 决定 |

这些是本次关系端点所用标签；完整字典结构见 [TITANS 字典](%E9%99%84%E5%BD%95B%20TITANS%E6%BA%90%E5%AD%97%E5%85%B8.md)，账簿职责见 [账簿](01.3%20%E8%B4%A6%E7%B0%BF.md)。公司、部门、desk 不是可直接串成父子树的同质层级。特别是 `10114` 的 desk 为 `HKFICC_TEST`，不能仅凭其名称带 B2B 就将全部映射定性为生产对冲规则。

**`DIRECTION=-1` 的含义有字段元数据直接支持：“盈亏方向转换，-1 为与源数据相反”。** 本份 26 条均为 `-1`。它描述方向转换，不是付款方向、买卖方向或所有字段的通用负号，也不证明本金、持仓数量、现金流全部取反。

所查 SQL 把 `DIRECTION` 原值保存到 `Prft_Dir_Tran_Cd`。本地代码域目录尚未命中这一字段的独立域，因此不补造 `1 / 0` 的完整枚举；已查加工也没有给出最终损益乘算实现。

## 4. 筛选条件决定哪些数据使用哪条映射

`D_BK_BOOK_MAPPING_RULE.KEY_BOOK_MAPPING_ID = D_BK_BOOK_MAPPING.ID` 是已确认的关联键；条件表没有直接替代映射表的源、目标账簿字段。入模 SQL 先取当日条件，再与当日映射做内连接：

```mermaid
flowchart LR
    F[源账簿] --> M[映射关系 ID]
    M --> T[目标账簿]
    M --> D[盈亏方向 DIRECTION]
    R[筛选字段、运算符、条件] -->|KEY_BOOK_MAPPING_ID = ID| M
```

由此，`10041` 有四个目标只能证明存在四条配置边，**不能证明它的每笔数据都会进入四个目标**。这次没有取得条件表的业务行底稿，还不能逐条解释命中范围、条件之间是 AND 还是 OR、优先级、规则为空时的默认行为。

同样，一条映射没有匹配的条件行时，在该内连接的规则输出中不会出现；这不等于映射关系被删除，因为关系和规则由不同分支生产。

## 5. 标准模型分三部分保存

| 源事实 | 标准模型 | 保留内容 |
|---|---|---|
| 源账簿→目标账簿 | `T03_AGT_RELA_H` | `Agt_Id=KEY_BOOK_ID_FROM`、`Rela_Agt_Id=KEY_BOOK_ID_TO`，两端修饰符 `20411`，关系类型 `N05` |
| 方向与源关系编号 | `T03_OTC_DERI_AGT_RELA_ADTNL_INFO` | 同一对账簿与 `N05`，另保存 `Prft_Dir_Tran_Cd=DIRECTION`、`Src_Book_Map_Id=ID` |
| 筛选条件 | `T03_OTC_DERI_BOOK_AGT_MAP_REGU` | 条件表提供筛选字段、运算符、条件；映射表提供源目标账簿；保留 `Src_Book_Map_Id` |

关系和附加信息采用历史开闭链，使用时按 **`STRT_DATE <= 业务日 AND END_DATE > 业务日`** 取有效版本，同时限定来源表、两端对象修饰符及关系类型。

不要只读取 `N05` 边就认定拿到了完整规则：方向在附加信息，筛选条件又在另一张表。连接条件表时还需保留源映射编号，不能仅用源账簿 ID。规则目标表的已查分支按来源分区覆盖、未按业务日分区，不能直接当作任意历史日的条件快照。

## 6. 加工与业务图谱中的位置

账簿映射处在“合约归属账簿”之后，但两类关系的作用不同：

- 期权经交易表形成 `N04` 合约→账簿；互换对应 `N03`。它们回答合约归属哪本账。
- 映射形成 `N05` 账簿→账簿，再由方向与条件补足规则。它回答账簿之间有哪些映射配置。
- 已查下游 `T98_OTC_SWAP_COMP_VALU_SUM` 的一个分支会读取来源为本映射表的有效 `N05`，关联账簿持仓汇总中的源目标账簿，说明这些关系被用于互换估值汇总加工。该分支不单独证明映射方向已执行，更不能外推为所有期权采用同一处理链。

字段图谱进一步确认：映射规则目标的 `Tgt_Book_Agt_Id` 值来自映射表 `KEY_BOOK_ID_TO`，不是条件表自行产生目标账簿。这与 SQL 的“条件表补筛选条件、映射表补关系端点”一致。
