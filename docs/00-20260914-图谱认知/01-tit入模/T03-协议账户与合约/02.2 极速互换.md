## 1. 业务定位

**`D_REF_FAST_TRS` 保存极速互换的合约级信息，突出多空动态名义本金、计息规则、日历和送股处理条款。** 它与普通 TRS 分表保存，但共同进入数仓互换合约模型。

本份底稿的互换类型均为 `N_CROSS_DMA_SWAP`，字典 `CD704` 的含义为“北上极速”。这说明本批记录属于该类型，不能据此把整张表定义为只支持北上 DMA：所查入模 SQL 还明确排除 `LONG_SHORT_SWAP`（多空互换），表明加工规则区分不同类型。

“极速”的生成机制、自动化程度和执行速度未在本表中体现。条款取值一致能说明本批配置集中，不能直接证明系统采用固定模板或逐日自动生成合约。

## 2. 对象与关联

| 对象 | 字段或关联方式 | 业务含义 |
|---|---|---|
| 合约 | `KEY_OTC_TRADE_ID`、`CONTRACT_CODE`、`EXTERNAL_CONTRACT_CODE` | 内部合约键与两类合约编号分开；当前入模使用 `CONTRACT_CODE` 填外部合约编号，不能仅凭源字段名互换两列 |
| 交易对手 | `KEY_CTPTY_ID` | 合约的交易对手引用；与 `SELLER`、我司身份 `PARTY` 分开 |
| 资金账户 | `KEY_CAP_ACCT_ID` | 入仓形成 `A17` 合约→资金账户关系；普通 TRS 对应字段名为 `KEY_CAPITAL_ACCT_ID` |
| 组合 | `BUNDLE_ID` | 入仓保存为组合协议编号；标识合约所属组合，不等于资金账户或已确认的主协议 |
| 账簿 | 合约→`D_TRD_OTC_TRADE`→`D_REF_BOOK` | 同日按 `KEY_OTC_TRADE_ID` 关联交易，再按交易的 `KEY_BOOK_ID` 关联账簿 |
| 归属主体 | 交易→账簿的 `KEY_CTPTY_ID` | 加前缀后进入协议持有人；不同于合约交易对手 |

本份 500 条记录的合约 ID 唯一，同一 Bundle 可关联多笔合约。资金账户和 Bundle 是合约上分别保存的引用。

补充的 Party B 底稿有 265 条记录，业务日期同为 2026-09-14，分属 `GFSX000035B`、`GFSX000036B` 两个 Bundle，每个组合下均有多笔合约。但 `KEY_CAP_ACCT_ID` 全部为 `0`，尚未验证其为有效资金账户。因此可确认组合对合约的分组关系，不能据此认定“同一有效资金账户对应多个 Bundle”。Bundle 的实体定义仍未确认，不进一步称为策略、主协议或产品组合。

底稿日期为 2026-09-14；“最新500条”的原始排序条件未附。文首保留字段查询，不声称该 SQL 能重现相同记录。

## 3. 名义本金：同时区分方向、币种与静态/动态

| 维度     | 源字段                                                   | 已核对口径                                              |
| ------ | ----------------------------------------------------- | -------------------------------------------------- |
| 名义本金   | `NOTIONAL_ORG`、`NOTIONAL`                             | 分别进入原币、结算币种名义本金                                    |
| 整体动态本金 | `DYNAMIC_NOTIONAL_ORG`、`DYNAMIC_NOTIONAL`             | 源字段分别标为标的币种、结算币种；当前 SQL 仅将后者填入结算币种动态本金，原币动态本金目标列置空 |
| 多头动态本金 | `LONG_DYNAMIC_NOTIONAL_ORG`、`LONG_DYNAMIC_NOTIONAL`   | SQL 分别进入原币、结算币种多头动态本金                              |
| 空头动态本金 | `SHORT_DYNAMIC_NOTIONAL_ORG`、`SHORT_DYNAMIC_NOTIONAL` | SQL 分别进入原币、结算币种空头动态本金                              |
| 换算信息   | `INIT_EXCHANGE_RATE`、`SETTLEMENT_CURRENCY`            | SQL 分别作为结算期初汇率、结算币种保存                              |

**底稿及源元数据的多空币种注释与 SQL 相反。** 文首四个多空动态本金别名已按 `183091` 的入模口径修正，并保留“入模口径”标识；原 CSV 不改动。SQL 证实的是这些字段的入模用途，不能单独裁定源系统业务定义或其计算实现是否正确。

这些字段表明合约分别保存方向和币种口径，但不提供持仓聚合公式。当前不能将 `DYNAMIC_NOTIONAL` 直接等同于实时风险敞口，也不能认定其必为多头加空头、净额或市值；`NOTIONAL` 也不能直接改称额度。合约终止时样本金额归零，不足以证明所有终止规则或结算已完成。

## 4. 计息、日期和送股条款

| 字段                   | 作用       | 本份数据中的取值及含义                                                  |
| -------------------- | -------- | ------------------------------------------------------------ |
| `DAY_COUNT`          | 计息基准     | `ACT360`：Actual/360；通常表达实际天数按 360 天年基准折算，具体应计金额还需要本金、利率和期间规则 |
| `INTEREST_INTERVAL`  | 起止日期是否计入 | `IN_START_EX_END`：含起始日、不含终止日；空值不自动套用此规则                      |
| `PAYMENT_CALENDAR`   | 兑付日历     | `SSE`：上交所日历                                                  |
| `INTEREST_CALENDAR`  | 计息日历     | 与兑付日历分列，不能因为本批取值相同就合并字段                                      |
| `DEFERRAL_TYPE`      | 非交易日调整方式 | `MODIFIED_FOLLOWING`：先顺延；若跨月，则改为向前调整                         |
| `PAYMENT_DATE_DELAY` | 兑付日延期天数  | 和非交易日调整方式分开；先后顺序需看计算规则                                       |
| `INTEREST_DELAY`     | 计息日延期天数  | 当前 SQL 明确按天数入模；本批为 `0`，不应当作是否计息的布尔开关                         |
| `STOCK_DIV_MODE`     | 送股处理方式   | `ADJUST_INIT_PRICE`：调整期初价格；不等同于现金分红处理                        |

`CREATE_DATE` 是合约创建日期，`CREATED_DATETIME` 是记录创建时间，`START_DATE / END_DATE` 是期初/期末定价日。数仓主表用 `CREATE_DATE` 生成生效日期，是加工口径，不代表审批动作与创建动作必然同时发生。

## 5. 结算币种与跨币种类型

`SETTLEMENT_CURRENCY` 指定结算币种，`CROSS_CURRENCY_TYPE` 指定另一项模式，二者不能互相推导。本份数据同时出现 **USD＋COMPOSITE、USD＋FLEXO**，已足以否定“美元必为 COMPOSITE”的解释。

`FLEXO / COMPOSITE` 的跨币种域定义尚未核实。源字典 `SettlementTypeEnum` 中的同名 `COMPOSITE` 属于交收类型，不能用其“复合”说明替代跨币种业务规则。期初汇率也不足以单独推导后续换汇方向及汇率风险承担。

## 6. 与普通 TRS 的确定性差异

| 维度    | 普通 `D_REF_TRS`                      | 极速 `D_REF_FAST_TRS`              |
| ----- | ----------------------------------- | -------------------------------- |
| 资金账户键 | `KEY_CAPITAL_ACCT_ID`               | `KEY_CAP_ACCT_ID`                |
| 本金字段  | 原币、本币、人民币及动态本金等                     | ==增加明确的多头、空头动态本金字段==             |
| 条款字段  | 参与率、建平仓费率、终止及展期等信息                  | 显式保存计息方式、计息起止、日历、递延和送股模式         |
| 生成来源  | `SOURCE_CHANNEL`、`DATA_SOURCE_ID` 等 | 本表没有对应生成渠道字段，不能从合约数量反推生成流程       |
| 合约模型  | `T03_AGT`＋`T03_OTC_SWAP_COMP_INFO`  | 同样进入这两类表，修饰符同为 `20206`，需保留来源分区区分 |

两份样本的抽取方式不同，不能据状态分布判断普通 TRS 偏历史、极速 TRS 才是当前生产业务；也不能用条款集中度证明两套系统分别“灵活”或“固定模板”。

## 7. 源业务结构与标准模型映射

**源表记录业务属性和引用，标准数仓将它们重新组织为合约主体、对象关系和合约详情。** 这两层分别说明“源数据保存了什么”和“当前 SQL 怎样表达这些信息”，不能互相替代。

| 源业务表达 | 标准模型表达 | 加工依据 |
|---|---|---|
| `D_REF_FAST_TRS` 的合约键、创建日期、状态 | `T03_AGT` 合约主体；持有人另经交易→账簿补充 | `183084` |
| 合约上的 `KEY_CAP_ACCT_ID` | `T03_AGT_RELA_H` 的 `A17`：合约→资金账户，关联修饰符 `10220` | `183087` |
| 交易表上的 `KEY_BOOK_ID`，结合极速合约身份 | `T03_AGT_RELA_H` 的 `N03`：合约→账簿 | `105388` |
| `BUNDLE_ID`、本金、币种、计息和日期条款 | `T03_OTC_SWAP_COMP_INFO` 的组合编号、金额和条款字段 | `183091` |

### 加工范围与信息保留

所查 `183084 / 183087 / 183091` 均含 `TRS_TYPE <> 'LONG_SHORT_SWAP'` 过滤；SQL 比较也不会保留类型为空的行。不能把这一分支当成源表全量入仓规则，更不能假定其他分支范围相同。

源字段有值不代表目标字段一定保留：`183091` 的原币整体动态本金、资金账户协议编号等目标列置空；资金账户关系另在关系表表达。`BUNDLE_ID` 在详情中保留为组合编号，尚不足以确认其具体是策略、主协议或其他组合。
