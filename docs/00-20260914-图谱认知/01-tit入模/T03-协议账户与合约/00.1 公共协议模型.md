# 00.1 公共协议模型

**阅读重点：七张模型表怎样共同描述业务对象。**

> 本篇解释七张公共模型表的分工、信息来源、对象身份、历史关联及消费用途。范围为现有 Excel 的“协议主干”：**7 张模型表、31 个来源分区条目、51 个去重入模调度**，属于本次 TIT 相关覆盖。
>
> 依据 Excel 及不同观察日期的本地 SQL 快照，说明静态加工；示例为说明性记录，未核验当前生产版本或实际运行。

**阅读顺序：** 先看七表分工和来源矩阵，再看第 3 节 S1 示例；身份细节、实现差异和消费用途按需查阅。业务全景见[协议账户与合约全貌](00%20%E5%8D%8F%E8%AE%AE%E8%B4%A6%E6%88%B7%E4%B8%8E%E5%90%88%E7%BA%A6%E5%85%A8%E8%B2%8C.md)，代码域与名称见[标准模型字典](%E9%99%84%E5%BD%95A%20%E6%A0%87%E5%87%86%E6%A8%A1%E5%9E%8B%E5%AD%97%E5%85%B8.md)。

## 1. 全貌：一个对象，三个方向的关系，三类补充信息

把一笔合约想成一份资料包：需要知道“它是谁”，还需要知道“它与什么对象相关、谁参与、涉及什么产品”，以及“它属于哪一类、目前什么状态、还有哪些补充信息”。这七个问题对应当前七张模型表。

| 位置     | 模型表（本章七表均位于 `pdata_n`）          | 业务解释                    | 一行的阅读单位                     |  来源分区数 |
| ------ | ------------------------------- | ----------------------- | --------------------------- | -----: |
| 身份中心   | `t03_agt` 协议                    | 登记账户、账簿或合约等对象的公共身份与共性属性 | 一个来源中的一个协议对象；当前实现另维护更新、删除信息 |      7 |
| 对象—对象  | `t03_agt_rela_h` 协议关系历史         | 表达合约到账户、合约到账簿、账簿到账簿等关系  | 一个对象在某关系类型下的一段关系版本          |      5 |
| 对象—当事人 | `t03_agt_pty_rela_h` 协议当事人关系历史  | 表达谁以何种角色参与              | 一个对象在某角色类型下的一段当事人关系版本       |      7 |
| 对象—产品  | `t03_agt_prd_rela_h` 协议产品关系历史   | 表达合约与交易表产品键的对应            | 一段合约与产品关系版本                 |      1 |
| 分类     | `t03_agt_clas_h` 协议分类历史         | 保存业务类别、SBL 类型、结算类型等     | 一个对象在某分类维度下的一段分类版本          |      2 |
| 状态     | `t03_agt_stat_h` 协议状态历史         | 保存合约状态及变动区间             | 一段合约状态版本；本次状态类型固定为 `10`     |      4 |
| 补充信息   | `t03_agt_stati_info_h` 协议统计信息历史 | 本次实际保存账户代码、归属、内部交易号及说明等 | 一个对象在某属性类型下的一段属性版本          |      5 |
| 合计     | **7 张表**                        | **身份 + 关系 + 描述**        | 不是七种交易，也不是七张必须逐一连接的表        | **31** |

表中的“一行”解释记录含义，未声明已验证的物理唯一键。六张补充表大多直接读取贴源对象、各自构造身份；七表的语义联系不代表加工时先写主表再派生其他表。

账户、账簿、合约在这里共享身份和关系字段；各自业务职责见[协议账户与合约全貌](00%20%E5%8D%8F%E8%AE%AE%E8%B4%A6%E6%88%B7%E4%B8%8E%E5%90%88%E7%BA%A6%E5%85%A8%E8%B2%8C.md)。主干组织公共资料，本金、腿、计息条款、余额及履保结果等由专用模型承载。

## 2. 分支全貌

### 2.1 谁提供信息，信息写到哪里

一笔合约的资料不全放在合约源表中。例如，普通互换源表提供合约身份、交易对手、资金账户等信息，**它归哪个账簿、对应哪个产品、属于哪类业务、内部交易号是什么，则由 OTC 交易主资料提供**。这些信息最终都描述该合约，但输入来源不同。

以下矩阵按信息来源列覆盖，再说明交易资料如何补齐合约信息。

#### B. 按合约看：OTC 交易主资料怎样补齐四类信息

这里的“OTC 交易主资料”特指 `odata_n_tit.d_trd_otc_trade` 这张表。四类合约通过 `KEY_OTC_TRADE_ID` 与它匹配；交易表提供下列业务字段，合约表用于判断对象是普通互换、极速互换、期权还是远期，并设置相应修饰符。

| 合约需要的信息 | 交易表提供的字段 | 写入的模型及含义 |
| --- | --- | --- |
| 归哪个账簿 | `KEY_BOOK_ID` | `t03_agt_rela_h`：合约→账簿；互换为 `N03`，期权为 `N04`，远期为 `N10` |
| 交易表记录的产品键 | `KEY_INSTRUMENT_ID` | `t03_agt_prd_rela_h`：合约→产品，保留源产品键 |
| 属于哪类业务 | `BUSINESS_TYPE` | `t03_agt_clas_h`：分类类型 `05` 下的业务类别值 |
| 内部交易号是什么 | `INTERNAL_TRADE_ID` | `t03_agt_stati_info_h`：属性类型 `09` 下的内部交易号 |

合约表帮助识别对象，交易表提供上述四类内容；完整记录示例见第 3 节。不同输入快照及合约匹配顺序见对应关系、分类和补充信息的任务说明。

## 3. 一份合约怎样读成完整资料

### 5.1 普通互换 S1 的示意记录

假设源记录存在下列值：交易键 S1、资金账户 A1、账簿 B1、交易对手 C1、源产品 P1、内部交易号 I1；B1 的当事人是 C2。以下只演示已读映射，不代表 C1 与 C2 必须不同，也不假设每笔互换都有 SBL 资料。

| 模型 | S1 对应的信息 | 从哪里来 | 怎么读 |
| --- | --- | --- | --- |
| `t03_agt` | S1 / 20206；持有人 `TIT060-C2` | 互换主体，经交易找到 B1，再取账簿当事人 | S1 的模型身份及公共信息 |
| `t03_agt_rela_h` | S1 —A17→ A1 / 10220 | 互换分区 | 合约关联哪个资金账户 |
| `t03_agt_rela_h` | S1 —N03→ B1 / 20411 | OTC 交易分区 | 合约归哪个账簿 |
| `t03_agt_pty_rela_h` | S1 —06→ `TIT060-C1` | 互换分区 | 谁是合约交易对手 |
| `t03_agt_prd_rela_h` | S1 → `TIT-P1`，保留源键 P1 | OTC 交易分区 | 合约对应哪个源产品 |
| `t03_agt_clas_h` | S1 的 `05` 分类值 | OTC 交易的 `BUSINESS_TYPE` | 按哪个业务类别组织 |
| `t03_agt_stat_h` | S1 的 `10` 状态及版本区间 | 互换状态映射 | 指定日期记录到什么状态 |
| `t03_agt_stati_info_h` | S1 的 `09` 属性为 I1 | OTC 交易的 `INTERNAL_TRADE_ID` | 展示或衔接内部交易号 |

这是“一个对象被多个视角描述”，不是“复制出了多笔合约”。账户 A1、账簿 B1 又可以在 `t03_agt` 中拥有自己的身份记录，再分别附上各自的当事人和属性。

表中消费作用包括补身份、归属、筛选和还原源字段，不能把目标任务的全部计算归给主干。消费热度按模型分区已确认的不同目标表去重计数，未确认线索不计入；零值不代表无人使用，也不能逐分区相加当作全局目标数。

跨来源唯一性、重复与空键、多调度启停及当前在用关系仍待核实。主表历史实现和上述两处差异按本地快照解释，未验证生产运行及业务结果。
