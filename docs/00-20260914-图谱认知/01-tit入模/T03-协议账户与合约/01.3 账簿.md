# 01.3 账簿

**阅读重点：业务归属、分类与流程配置。**

```sql
SELECT
    KEY_BOOK_ID               AS "账簿ID",
    VALID_STARTDATE           AS "生效日期",
    VALID_ENDDATE             AS "失效日期",
    BOOK_NAME                 AS "账簿名称",
    DESCRIPTION               AS "描述",
    DESK                      AS "柜台",
    DEPARTMENT                AS "部门",
    COMPANY                   AS "公司",
    CREATED_DATETIME          AS "创建时间",
    CREATED_BY                AS "创建人",
    UPDATED_DATETIME          AS "修改时间",
    UPDATED_BY                AS "修改人",
    SHORT_NAME                AS "账簿短名",
    KEY_CTPTY_ID              AS "账簿归属主体对应交易对手ID",
    ENABLE_FINANCIAL          AS "是否报送财务",
    ENABLE_RISK               AS "是否报送风控",
    ENABLE_REPORT             AS "是否启用报备",
    ENABLE_SETTLEMENT         AS "是否启用结算通知书",
    ENABLE_CONFIRMATION       AS "是否启用交易确认书",
    ENABLE_CAPITAL            AS "是否启用资金模块",
    ENABLE_LIMIT              AS "是否启用风险限额",
    DATA_TIME                 AS "数据时间",
    ENABLE_REPEAT_CHECK       AS "是否启用二次复核",
    MARKET_TYPE               AS "场内外标识",
    MAPPING_WIND_CODE         AS "映射Wind代码",
    BUSI_DATE                 AS "业务日期"
FROM ODATA_N_TIT.D_REF_BOOK;
```

## 1. 账簿的业务定位

**账簿是业务归属和分类记录的单元。** `D_REF_BOOK` 保存账簿身份、公司和部门归属、业务分类、归属主体及流程配置，本表没有持仓、余额或损益金额。

同一业务分类下，可以按不同用途设置多本账簿。底稿中的收益凭证账簿如下：

| 项目 | 账簿 10005 | 账簿 10006 |
|---|---|---|
| 名称 | GFS 广发-柜台交易-收益凭证-合约 | GFS 广发-柜台交易-收益凭证-对冲交易 |
| 公司 | GFS | GFS |
| 部门 | OTC | OTC |
| 业务分类 `desk` | INCOME_SECURITIES_ISSUED_CERTIFICATE | INCOME_SECURITIES_ISSUED_CERTIFICATE |
| 分类的字典含义 | 收益凭证 | 收益凭证 |

**同属收益凭证业务，仍然可以分别设置“合约”和“对冲交易”账簿。** 账簿划分在这里表达的是业务管理用途，而不只是产品类别。

## 2. 公司、部门与业务分类

| 字段 | 业务含义 |
|---|---|
| `company` | 账簿的公司归属标签 |
| `department` | 账簿所属业务部门或组 |
| `desk` | 账簿业务分类，包含业务类型、对冲方式和管理用途 |
| `key_book_id` | 具体账簿的标识 |

`desk` 在底稿中译为“柜台”，对应数仓代码域名称为**“场外衍生品账簿业务分类”**。其取值包含主动对冲、收益凭证、融券、生产验证、限额豁免等，不能仅作为组织岗位理解。

### 2.1 公司与部门字典

下面列出底稿出现的全部公司和部门代码。标签来自 **2026-09-15 查询的 TITANS 测试库 `TITANS_DM.CFG_DICTIONARY_DESC`**，用于理解名称；尚未与 2026-09-14 账簿快照的同日源字典核对。保留字典原称，不把它改写成正式法人名称或当前组织架构。

| 公司代码 | 字典标签 |
|---|---|
| GFS | 广发证券 |
| GFS_HK | 广发全球资本 |
| GFA | 广发资管 |
| GFF | 广发期货 |

| 部门代码 | 字典标签 |
|---|---|
| OTC | 股衍部 |
| OTC_HK | 柜台交易市场(香港)部 |
| GFS_FICC | 固定收益投资部 |
| ED | 权益及衍生品投资部 |
| HK_FICC | 香港FICC |
| EQD_JDSYZ | 股衍部绝对收益组 |
| AM | 另类投资部 |
| GFF_AM | 广发期货资产管理部 |
| HK_GM | 香港GM |
| GFS_FICC_COM | 固收部商品组 |
| HK_FINANCE | 香港FINANCE |

同名代码的含义取决于字段及字典域：

- **`department=OTC` 是部门代码，字典标签是“股衍部”**；不能把它与 `market_type=OTC` 的场外标识混为一谈。
- **`department=AM` 的字典标签是“另类投资部”**；

部门标签中同时有“部”和“组”，也提示：这是账簿管理使用的部门分类，不能仅凭字段名把所有取值视为同一行政层级。

### 2.2 desk 业务分类

以下含义由本地字典代码域 `CD2204` 确认，来源标明为 `ODATA_N_TIT.D_CFG_DICTIONARY_DESC`、`dict_name=DESK`，字典业务日期为 2026-08-21。

| 分类侧重 | desk 代码及字典含义 |
|---|---|
| 按对冲方式区分 | `DYNAMIC_HEDGING` 主动对冲；`STATIC_HEDGING` 被动对冲；`TRS_HEDGING` 互换对冲 |
| 按业务类别区分 | `INCOME_SECURITIES_ISSUED_CERTIFICATE` 收益凭证；`SECURITY_LENDING` 融券；`PORTFOLIO_SWAP` 线性互换；`QIS` 策略指数 |
| 按香港业务用途区分 | `OTCHK_TRS` HK互换持仓；`OTCHK_MARGIN` HK期权保证金；`OTCHK_FEE` HK费用 |
| 按特殊管理用途区分 | `DUMMY` 生产验证；`LAB_TEST` 测试验证；`LIMIT_SKIP` 限额豁免 |

左列按字典含义归纳，非源系统分类层级。

**desk 的分类维度并不单一**：既有业务类型，也有对冲方式、费用归集和验证用途。仅凭 desk 不能建立统一的产品分类或组织层级。

这些是分类名称，不直接代表执行规则。例如 `LIMIT_SKIP` 的字典标签虽是“限额豁免”，具体豁免条件仍要看控制规则；不能据此认定该账簿绕过所有限额检查。

### 2.3 同一业务分类下的账簿划分

底稿中 `10002` 与 `10003` 同属 `GFS / OTC / DYNAMIC_HEDGING`，账簿名分别以“交易员A”和“客户”结尾。

两条记录均属于“股衍部—主动对冲”分类，账簿名进一步区分用途。 名称中的“客户”是区分账簿的线索，不等于该记录本身就是客户资金账户。

同样，公司、部门、desk 相同，也不能代替账簿 ID。识别具体账簿仍应使用 `key_book_id`，并核对来源和日期。

## 3. 归属主体与组织归属

`key_ctpty_id` 的字段含义是“账簿归属主体对应交易对手 ID”。这里的“交易对手 ID”是引用主体的技术键，不能直接理解为“这本账服务的外部客户”。

| 字段 | 关系含义 |
|---|---|
| `company / department / desk` | 组织归属标签及业务分类 |
| `key_ctpty_id` | 账簿归属主体引用 |

SQL 也保留了这个区别：账簿进入 `T03_AGT` 时，`key_ctpty_id` 被加工为协议持有人 `Agt_Holder`；公司、部门和 desk 则进入协议统计信息，作为不同类型的属性保存。

而且，底稿中主体 `10161` 同时出现在 `GFS`、`GFS_HK` 下，`AM` 部门也同时出现在 `GFA`、`GFS` 下。**这说明不能直接把主体、公司、部门拼成一棵严格的一对一组织树。** 这些交叉关系的原因，需要结合主体名称和账簿配置规则继续解释。

## 4. 账簿的流程配置

账簿通过八个开关配置财务、风控、报备、单据、资金及控制功能。

| 业务功能 | 对应配置 |
|---|---|
| 财务、风控报送 | `enable_financial`、`enable_risk` |
| 报备 | `enable_report` |
| 结算通知书、交易确认书 | `enable_settlement`、`enable_confirmation` |
| 资金模块 | `enable_capital` |
| 风险限额、二次复核 | `enable_limit`、`enable_repeat_check` |

底稿既有八项全部启用的账簿，也有只开启风控、或只开启财务/风控/资金的账簿。其意义在于：**不同账簿可以配置不同的业务处理范围。**

但应按字段原意理解：不启用结算通知书，不等于不发生结算；不启用资金模块，不等于没有资金影响。开关的实际生效方式要看消费程序，不能仅凭配置值推导最终业务结果。

## 5. 账簿与合约、账户的职责区别

这些对象分别承载交易约定、业务归属和资金管理信息：

| 对象 | 主要职责 |
|---|---|
| 合约 | 记录交易双方的权利义务 |
| 账簿 | 记录业务归属、分类用途及处理配置 |
| 资金账户 | 记录和管理资金 |
| 保证金账户 | 归集和管理保证金 |

当前底稿未提供这些对象之间的关联表，无法据此确定实际连接关系和对应数量。

`market_type` 则是额外的场内外分类维度，不能用来代替上述对象区分；为空时也不能根据部门名称直接补齐。

## 6. 数仓中的账簿表达

账簿主信息进入 `T03_AGT`，公司、部门和 desk 进入协议统计信息。SQL 映射如下：

| 源信息 | SQL 中的表达 | 含义 |
|---|---|---|
| `key_book_id` | `T03_AGT.Agt_Id`，同时设置 `Agt_Modifr='20411'` | 在协议模型中标识这本账；不能只拿裸 ID 跨对象关联 |
| 账簿对象类型 | `Agt_Cate_Cd='204'`、`Agt_Type_Cd='20411'` | 模型通过类别、类型区分对象 |
| `key_ctpty_id` | `CONCAT('TIT060-', KEY_CTPTY_ID)` → `Agt_Holder` | 保存账簿归属主体引用 |
| `desk` | 统计信息类型 `06` 的 `Stati_Cont_Desc` | 保存账簿业务分类原值 |
| `department` | 统计信息类型 `07` 的 `Stati_Cont_Desc` | 保存部门原值 |
| `company` | 统计信息类型 `08` 的 `Stati_Cont_Desc` | 保存公司原值 |

这里的三类统计信息是把同一本账的三个属性分别存为记录，不是生成三本账。该 SQL 直接保存原值，不负责把代码翻成中文。

公司和部门的中文名有另一条明确线索：账簿部门配置进入 `T04_INR_ORG` 时，SQL 按以下关系取字典标签：

```text
公司或部门代码 = DICT_ITEM_NAME
Company 或 Department = DICT_NAME
取 DICT_ITEM_LABEL 作为内部机构名称
```

字典关联同时限定代码值和代码域，避免将其他域中的同名代码误作公司或部门名称。

账簿被放入 `T03_AGT` 是已经看到的模型表达，但它仍然保持账簿的业务含义。不能从表名“协议”进一步推出它就是法律合同，也不能把上述映射当作模型设计动机的完整说明。
