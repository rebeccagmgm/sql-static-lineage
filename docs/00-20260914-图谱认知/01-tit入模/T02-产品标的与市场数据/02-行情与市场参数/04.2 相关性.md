# 04.2 相关性

**这张表保存一对标的在某个日期的相关性参数。最重要的辨认是：`CORRELATION_X`、`CORRELATION_Y` 都是 TIT 工具内码，入模后虽然叫 `FCTR_X`、`FCTR_Y`，也没有变成 LBR 因子编号。**

源字段注释明确写的是“相关性标的 x／y 的 keyInstrumentId”，已查消费也分别拿这两列关联工具主数据。因而，这里的“一对”可以先读成“工具 X ↔ 工具 Y”，再沿工具信息认出具体对象。

## 1. 从哪里取，进入哪张表

| 取数原表 | 入模表 | 来源／分组 | 调度 |
| --- | --- | --- | --- |
| `ODATA_N_TIT.D_REF_CORRELATION_DAILY_INFO` | `PDATA_NEWS_N.T02_OTH_CORRE_FCTR` | TIT／01 | 117794 |

取源处理业务日的 `BUSI_DATE`，直接接收相关性编号、两端工具、日期、数值和名称。已查 SQL **不读取历史价格序列，也没有重算相关系数或补齐反向记录**。

## 2. 一条记录在描述什么

| 原字段 → 入模字段 | 业务含义 |
| --- | --- |
| `KEY_CORRELATION_ID` → `REC_ID`、`SRC_REC_ID` | 源相关性记录编号 |
| `AS_OF` → `TRD_DT` | 参数对应日期，转为 `yyyyMMdd` |
| `CORRELATION_X` → `FCTR_X` | X 端标的的 TIT 工具内码 |
| `CORRELATION_Y` → `FCTR_Y` | Y 端标的的 TIT 工具内码 |
| `CORRELATION_VALUE` → `VAL` | 源相关性数值，直接承接 |
| `NAME` → `RELA_COEF_NAME` | 源相关性系数显示名称 |
| `SHOW_NAME` → `NAME` | 另一显示名称，保留源字段区别 |
| `UPDATED_DATETIME` → `REC_UPD_TIME` | 源更新时间 |

查数时一起保留 **X、Y、`TRD_DT`、相关性编号、名称与数值**。单看 X 或某个名称，不能认定已经找到了所需的一对参数。

这条入模和下述消费均未乘除 100。当前 SQL 没有给出源相关性的统计窗口、价格／收益率序列选取或估计方法，这些应从源配置或生成逻辑查询，不能由名称反推出。

## 3. 怎样知道 X、Y 具体是什么

消费 **163633 → `DM_RSK_N.V_RISK_CORRELATION_INFO`** 已明确提供一条查法：

```text
T02_OTH_CORRE_FCTR（TIT／01）
  FCTR_X ──→ T02_TIT_SCR_BASE_INFO.IN_CODE ──→ SRC_CD，输出 XCODE
  FCTR_Y ──→ T02_TIT_SCR_BASE_INFO.IN_CODE ──→ SRC_CD，输出 YCODE
              两端均限定 TIT／02、DATE_SRC='WIND'
```

该视图保留相关性编号、日期、数值、名称和 X／Y 原工具内码，再补出两端外部代码。因为两端都要求匹配代码记录，缺少任何一端代码的源相关性，不会出现在这项输出中。

它的字段注释将 XCODE 叫“标的代码”、YCODE 叫“币种代码”；更准确地说，**Y 仍然先是一个工具编号，匹配后得到相应工具的代码**，不是直接存了 `CNY`、`HKD` 这样的币种文本。

## 4. LBR 因子怎样对应这组相关性

消费 **194609 → `DM_RSK_N.CORR_FCTR_MKT_QUOT`** 分三步取得数值：

1. 从 `T02_FIN_FCTR_DEF` 的 **LBR／01** 选 `FCTR_ENGINE_HAND_METHOD='CORR_DEF_SYNC'`，取得相关性因子自身的 `FCTR_ID`。
2. 按 `FCTR_ID` 连接 `T02_FIN_CORR_FCTR_LBR` 的 **LBR／01**，取 `SRC_SYS_PRDNO`、`UNDRL2_SRC_SYS_PRDNO`，各去掉前四个字符的来源前缀，得到第一、第二标的内码。
3. 用第一标的内码对应 TIT `FCTR_X`、第二标的内码对应 TIT `FCTR_Y`，读取日期和 `VAL`。

```text
LBR 相关性因子 FCTR_ID
         ↓ 因子定义
第一标的工具内码 ＋ 第二标的工具内码
         ↓ 按顺序匹配
TIT FCTR_X ＋ FCTR_Y ＋ TRD_DT → VAL
```

**LBR 因子编号代表这一对风险对象的因子身份；TIT X／Y 是组成这一对的工具身份。** 这是两个层次的编号，不能直接用 `FCTR_ID=FCTR_X` 连接。

该消费按照 X／Y 顺序匹配，没有同时尝试反向的 Y／X。查不到时先检查两端工具、顺序和源日期，不要自行复制或倒置记录后认作原消费结果。

## 5. 具体用在期权结果的什么地方

**176827 的期权结果分支**会补充一项相关性数值，实际匹配条件为：

| 匹配内容 | 实际取法 |
| --- | --- |
| 日期 | 期权指标业务日 = 相关性 `AS_OF` |
| X 端 | X 工具代码 = 挂钩标的主数据的 `WIND_CD_SRC` |
| Y 端 | Y 工具代码 = **标的币种源代码 + `CNY.EX`** |
| 输出 | 相关性 `VAL` → 期权结果的 `CORREL_VAL` |

例如，若标的币种源代码为 `USD`，该连接会寻找 `USDCNY.EX` 对应的 Y 工具。这是依据消费公式举例，不是声称已有某条实际记录。

因此，这项具体用途可以读作：**给期权结果补上“挂钩标的与该标的币种兑人民币汇率工具之间的相关性”**。它帮助理解为什么相关性的另一端可能是汇率工具，不能把本表全部记录都叫“两只股票的相关性”。

该期权结果分支主要由 T03／T98 等交易、持仓和指标资料组装，再读取本表补相关性。它并非从 T02 Greeks 结果表取得所有指标，也没有在这项 SQL 中依据相关性重新计算期权价格。

## 6. 常见业务问题怎样查

| 想弄清什么 | 从哪里开始 |
| --- | --- |
| 这条相关性到底配哪两个对象？ | 用 `FCTR_X/Y` 分别查 TIT 工具内码，再取名称、类别和代码 |
| 某个风险因子取的是哪一对？ | 查 LBR `FCTR_ID` 对应的第一、第二标的编号，沿 194609 的顺序匹配 |
| 为什么源表有记录，风控视图没看到？ | 核对 163633 是否能同时匹配两端 TIT／02 WIND 代码 |
| 为什么期权结果没有补上相关性？ | 核对参数日期、标的代码及“标的币种＋CNY.EX”三项条件 |
| 这个数值到底怎么算出来？ | 查源端参数生成规则；本项入模只提供值来源，未保存计算窗口和算法 |

依据：入模 SQL 117794；消费 SQL 194609、163633、176827；`ODATA_N_TIT.D_REF_CORRELATION_DAILY_INFO` 原字段元数据。
