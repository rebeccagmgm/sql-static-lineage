数综内部

同一个 szdata，两条通道

LOCAL · 数据门户 MCP

调查主路径，不打开浏览器

  • table table-ddl table-lineage：表身份、DDL、一层直接血缘。
  • task-sql：经 schedule 通道调用按任务取 SQL，不打开任务页。
  • schedule-mcp-*：依赖、运行实例、状态、日志摘要、失败实例。
  • sql-diagnosis：提交前检查表、字段和语法。
COOKIE · 当前 Chrome

页面上才有的对象

  • 指标、标签、组合类型、目录分类。
  • 宽表、数据集、需求单、权限。
  • schedule-detail 是任务卡片，不能代替完整 SQL，也不能证明跑成功。
  • python-run 默认只预览，明确执行才提交到固定测试节点。
门户路径：/mcp/metadata、/mcp/schedule、/mcp/sql_dignose06

一次调用里做完三件事

task-inspect 把主证据拼在一起

opencli szdata task-inspect --task-ids <id> --include detail,sql,runs
  --begin-date 2026-09-22 --end-date 2026-09-22 -f json
01 详情

schedule.get_schedule_detail。这是 MCP 详情，不是页面命令 schedule-detail。

02 SQL

同一 schedule 通道上的 metadata.get_horae_sql_by_task_id。证明平台返回了这段 SQL。

03 运行

schedule.get_task_run_instances。指定日期的实例，只说明技术运行。

04 边界

单进程、最多 10 个任务、请求有间隔。部分失败只重试失败对象。

05 还不等于

代码里写明：运行成功不证明目标表数据正确。

从表明开始时，先用 table（metadata 通道）找出生产任务，再进 task-inspect07

主线08

Skill 写死的判断

复用的是步骤和边界

先钉对象

任务 ID、库名.表名、指标 ID、接口 ID、流程单号。锚点不清先做有界搜索。表名相同要先消歧到 GUID。

先读证据等级

返回里先看状态、证据级别、限制和失败项。空结果只表示这次没命中。超时、未登录、无权限都不是“不存在”。

三分再说

已确认：命令直接证明的字段。当前解释：你根据 SQL 或命名做的判断。仍未知：没查到的行、环境和下游。

运行成功停在“已确认”。它不能升格成业务数据正确。

主线09

现场可以这样走

两条命令，一种回答

opencli szdata table --db <库> --table <表>
  --view summary -f json

opencli szdata task-inspect --task-ids <id>
  --include detail,sql,runs
  --begin-date <日> --end-date <日> -f json

要指标口径再查 indicator-detail，那一步走登录态。要字段公式再进 SQL 血缘。

回答骨架

  • 已确认。生产任务、平台返回的 SQL、指定日期的运行状态。注明命令。
  • 当前解释。过滤条件或来源表看起来是什么。标明这是阅读 SQL 后的解释。
  • 仍未知。目标分区有没有行、下游库是否更新、口径是否被业务接受。
环境不通就讲这个骨架，不临场猜一张表10
