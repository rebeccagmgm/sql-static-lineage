**前面没有做到你要求的深度，之前的建议下得太早。这一轮补做了同类产品和开源项目调研，结论也比之前具体了。**

**最重要的发现是：你担心的“最后变成人工打标签”确实是一个分界点。值得参考的方案，会把业务含义落实为明确的数据映射；仅有术语、分类和关系名称，还不够。**

这次有三个发现，实质性改变了我对方案的判断。

**第一，你说“不可能完全定制化”，可以通过通用模型和配置解决一部分，但不能消除业务判断。**

DataHub 的自定义关系，可以统一配置方向、反向名称等属性；Ontop 可以用一条映射规则批量生成关系。维护单位可以是一类关系的规则，而非每个节点、每条边。[DataHub 自定义关系](https://docs.datahub.com/docs/features/feature-guides/ontology/custom-relationships)、[Ontop 概念与映射](https://ontop-vkg.org/guide/concepts.html)

但是，“这个字段是不是合约编号”“A18 适用于什么范围”“关联账户是否意味着发生资金交收”，仍然需要依据。**自动化可以执行和检查定义，不能因为画出了边，就替我们确认定义正确。**

对你而言，一部分定义已经在字典、入模 SQL 和知识库里。应优先复用这些已有事实，而不是从零编一套关系词表。

**第二，对 OTC 而言，关键难点是“业务概念对应的数据范围”，不只是“对应哪张表”。**

用你已经整理的“期权合约关联资金账户”举例：

|必须回答的问题|你现有资料给出的内容|
|---|---|
|落在哪张表？|`T03_AGT_RELA_H`|
|表内哪类关系？|`A18`；不能把整张协议关系表都解释成期权合约与账户|
|哪边是合约、哪边是账户？|`Agt_Id` 是合约端，`Rela_Agt_Id` 是账户端，并需结合修饰符|
|来自什么字段？|`D_REF_OTC_OPTION_DEAL.KEY_OTC_TRADE_ID`、`KEY_CAPITAL_ACCT_ID`|
|这条关系能说明什么？|保存资金账户引用；不证明实际收付款，也不证明关联账户已被核验存在|

这些并非我新编的业务设计，而是你现有的[合约→资金账户知识页](E:/02_area/股衍数据-数据cookbook/sql-static-lineage/docs/00-20260914-图谱认知/01-tit入模/T03-协议账户与合约/03.1 合约→资金账户.md)。

因此：

- **贴标签**只能说：这张表与“合约、账户”有关。
- **明确映射**才能说：在哪个来源、关系类型和有效范围下，哪些字段分别代表合约与账户。
- **现有血缘图**可以继续回答：这些字段由哪个源字段、经过什么加工写入。

WrenAI 的 SQL 模型、Ontop 的 SQL 映射，提供了表达第二步的具体机制。**但把这种映射接到你现有 Facts 和血缘节点上，还没有现成适配结果；这部分不能宣称已经解决。**

**第三，要严格区分开源能力、商业自动化，以及源码中的新能力。**

例如 DataHub 官方对照表把自动生成上下文、业务消歧、沿血缘传播等能力列在 Cloud；不能用这些功能来论证“装开源版就省掉人工”。OpenMetadata 的部分新上下文与 AI 功能也有商业版本边界。[DataHub 版本对照](https://docs.datahub.com/docs/managed-datahub/managed-datahub-overview)、[OpenMetadata 版本说明](https://openmetadatastandards.org/breaking-changes/)

而且，“沿血缘传播业务含义”本身需要条件：源表包含合约信息，不代表每个下游结果都仍是合约明细。聚合、过滤和不同粒度都可能改变含义。对你的项目，这一点尤其不能省略。

**落实到你的项目，我现在的推荐顺序是：**

1. **业务知识和资产如何组织，重点参考 DataHub、OpenMetadata。** 它们与当前 data-graph 最接近，能帮助业务定义、文档和技术资产建立可管理的联系。
2. **同一张表中不同业务范围如何表达，重点参考 WrenAI、Ontop。** 借鉴明确映射的机制；目前没有理由直接引入完整 RDF／SPARQL 技术栈。
3. **OTC 概念是否合理，参考 FINOS CDM，并以你们实际模型和业务口径核对。** 不照搬全部行业模型。
4. **DataBuddy 作为语义模型与查询体验参考。** 从它的操作文档看，值得学的是“定义能够落到数据上”，不能只模仿宣传图的三层实体。

呈现上，我倾向于让用户搜“合约”后，进入能读懂的合约页面；点“关联资金账户”，同时看到**关系含义、适用范围、字段映射、加工来源和证据**。图谱负责展示这项关系涉及的资产与加工路径。这个倾向有上述产品机制支撑，但“目录还是图画布作为首页”仍应由真实使用效果决定。

**我能给出的明确结论是：保留现有 data-graph，把已有业务知识准确绑定到资产及其数据范围，值得推进；重新建设一整套业务本体平台，目前证据不足。** 之前那个主要靠写死内容的 demo，没有验证这种绑定如何产生、如何复用、如何随 SQL 变化维护，所以你觉得它更像人工标签页，判断是成立的。
