# 状态、分类、配置与鉴别：分别在描述资产的哪一面

[返回入口](../README.md)

## 1. 一项资产可以同时有三种状态

`t10_ast_stat_h` 的 FAM 分支从同一日源台账 `UNION ALL` 出三组记录。每组仍指向同一个 `ASSET_TAG_NO`，通过状态类型区分正在回答的问题。

| `Ast_Stat_Type_Cd` | 来源字段 | 业务问题 |
|---|---|---|
| `01` | `STATUS` | 资产本身处于什么状态？ |
| `02` | `INSURE_STATUS` | 投保处于什么状态？ |
| `03` | `ENTRY_STATUS` | 财务入账处于什么状态？ |

三组分别查 `REF_CD_CVT_MAP`，按目标表、目标字段、源字段、源系统限定转换记录，未匹配则保留源值。之后按 `Ast_Id + Ast_Stat_Type_Cd` 比较变化并维护历史。[236110.sql，23–91 行](../../../attachments/02-状态分类配置与鉴别/IMG-02-状态分类配置与鉴别-20260914110004246.sql)

“在用”“未保”“已入账”在语义上可以并存，不构成三个资产对象。源行缺少某个状态时，本分支也没有 `WHERE 状态非空` 来排除那一组，因此有一行不代表该状态内容完整。

本地存在旧命名 `FIX_AST_STAT_TYPE_CD / FIX_AST_STAT_CD` 字典，三种类型与本 SQL 注释对应；但未找到 `AST_STAT_TYPE_CD / AST_STAT_CD` 的同名域定义。状态码的最终域绑定保留为候选，不能擅自把旧域改名当作当前合同。[字典绑定边界](../字典/README.md)

## 2. 分类历史为什么不等于主表类别

`t10_ast_clas_h` 同样从同一资产产生三组记录，但这里**没有转码**：

| `Ast_Clas_Type_Cd` | `Ast_Clas_Cd` 的实际来源 | 解释 |
|---|---|---|
| `01` | `ASSET_PARENT` | 源资产大类 ID |
| `02` | `ASSET_SON` | 源资产小类 ID |
| `03` | `ASSET_NATURE` | 源资产性质 ID |

主表的 `Ast_Cate_Cd` 则优先把小类转为仓库资产类别；`Ast_Prop_Cd` 把性质转为仓库属性。这就产生两种并行表达：**主表便于按统一属性理解资产，分类历史保留源分类/性质的期间变化。**[236117.sql，23–65 行](../../../attachments/02-状态分类配置与鉴别/IMG-02-状态分类配置与鉴别-20260914110004892.sql)、[236109.sql，48–60 行及转换条件](../../../attachments/建模基础-身份粒度与时间/IMG-建模基础-身份粒度与时间-20260914110004614.sql)

本地旧固定资产分类类型域只含 `01/02`，没有 `03`。但 `03` 不只是代码注释：本次补查的财务消费者明确筛选 `ast_clas_type_cd='03'` 并把 `Ast_Clas_Cd` 用作资产性质。因此 **`03` 的当前实现用途有 SQL 支持，字典登记仍有缺口**。[财务案例](../05-资产性质进入财务的完整案例.md)

字典还提醒，相同中文“小类”可能对应不同大类下的不同代码。不要拿中文名称做唯一键；分类类型、代码、父类语境应一起理解。

## 3. 配置历史描述的是一组设备属性

`t10_ast_plac_h` 按资产号维护配置变化。源字段对应为 `OPERATE_SYSTEM → Oper_Sys`、`SUPPLIER → Mfr`、`ASSET_MODEL → Mdl`、`NUM → Vol`，而名为 `Plac` 的“配置”列当前固定为空。[236111.sql，23–44 行](../../../attachments/02-状态分类配置与鉴别/IMG-02-状态分类配置与鉴别-20260914110005196.sql)

这里不能凭 `plac` 猜“地点”，也不能仅看 `Mfr` 注释就说它已经是制造商：源表 `SUPPLIER` 注释为“供应商”，Wiki 对接需求也称供应商。当前加工把供应商放入“制造商”列，**供应商与制造商是否相同尚无证据**。

数量 `Vol` 来自 `NUM`，源元数据是数值类型，模型 DDL 为 `STRING`。一个标签号是否总对应数量 1 没有样例证明；按台账行数统计设备件数前，需要核对数量口径。

## 4. 鉴别信息是资产的别名或识别特征，不是统一主键

`t10_ast_idty_info_h` 保存有类型的鉴别内容，按 `Ast_Id + Idty_Info_Type_Cd` 维护历史。

| SQL 固定类型 | 来源内容 | 已读分支说明 |
|---|---|---|
| `40101` | `MAC_ADDRESS` | SQL 注释称 MAC 地址1；本地 CD006 只有 `40100 / MAC地址`，不能自动替换 |
| `40201` | `DISK_SERIAL_NUM` | 硬盘序列号，CD006 命中 |
| `40200` | `SN_NO` | 序列号，CD006 命中 |

签发地、签发机构、签发日期、到期日期、年检日期等通用列在该分支均写空。它也没有把一段 MAC 文本拆成多块网卡，不能认为每行对应单个规范化 MAC。[236114.sql，29–88 行](../../../attachments/02-状态分类配置与鉴别/IMG-02-状态分类配置与鉴别-20260914110005232.sql)

Wiki 的云管同步以 SN 是否存在作为准入条件，而该 T10 鉴别生产没有相同非空筛选。两者筛选范围不同，更不能据 SN 字段相似就画成已经核实的接口链路。
