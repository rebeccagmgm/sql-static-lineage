## 1. 哪个编号在识别什么

源台账同时有内部主键、固资标签号和 FA 编号。它们由不同字段承担，不能因中文都出现“资产编号”就互换。

| 来源字段 | 模型字段 | 标识的对象 |
|---|---|---|
| `ASSET_TAG_NO` | 主表及历史表 `Ast_Id`；附加表 `Fix_Ast_Id` | 固资系统的资产标签号 |
| `ID_` | `Fix_Ast_Src_Id` | 源台账内部记录主键；源注释称主键，不代表标签号唯一 |
| `ASSET_CODE` | `Fa_Ast_Id` | 财务 FA 资产编号 |
| `NEW_OLD_REFER_NUM` | `Ast_Ref_No` | 资产参考号；未从 SQL 得到完整新旧号映射定义 |
| `SN_NO` | 鉴别表 `Idty_Info_Cont`，类型 `40200` | 序列号，是资产的一种鉴别信息 |

主模型加工通常在来源分区内按标签号比较新旧记录。因此识别至少保留 **物理表来源 + `src_tbl` + 资产号**；元数据中的 `data_source` 是物理身份信息，业务列 `data_src_cd` 和 `real_src_tbl` 则记录业务来源，职责不同。

证据：[源字段](../../attachments/建模基础-身份粒度与时间/IMG-建模基础-身份粒度与时间-20260914110004243.json)、[主表 SQL](../../attachments/建模基础-身份粒度与时间/IMG-建模基础-身份粒度与时间-20260914110004614.sql)、[附加表 SQL](../../attachments/01-资产身份与固定资产台账/IMG-01-资产身份与固定资产台账-20260914110004761.sql)。本次没有全量数据或主键约束证明标签号、FA 编号或两者映射唯一。

## 2. 一行是什么

| 表的角色 | 已读加工使用的比较身份 | 查询一行还要带什么 |
|---|---|---|
| 主表 | `Ast_Id` | 来源分区、删除状态；主表没有历史区间 |
| 配置历史 | `Ast_Id` | `Strt_Date/End_Date` |
| 状态历史 | `Ast_Id + Ast_Stat_Type_Cd` | 状态维度和期间 |
| 分类历史 | `Ast_Id + Ast_Clas_Type_Cd` | 分类维度和期间 |
| 鉴别历史 | `Ast_Id + Idty_Info_Type_Cd` | 鉴别类型和期间；MAC 与序列号不能混在同一值域 |
| 员工、机构、账簿关系历史 | `Ast_Id + 对应关系类型` | 关系角色、方向和期间 |
| 联系人历史 | `Ast_Id + Lkman_Type_Cd` | 联系人角色和期间 |
| 固定资产附加快照 | 投影 `Fix_Ast_Id`，没有按该字段去重的步骤 | `src_tbl + busi_date`；不能假定每天一号一行 |

这列“比较身份”说明程序怎样识别变化，不是数据库已强制的主键。比如同一责任角色若有两个员工，当前模板并没有以员工 ID 作为自然键单独表达两条并存关系。

## 3. 三类时间不能互换

**源数据日期**：生产 SQL 读取 `W_ASSET_ACCOUNT.busi_date=d`。它指定本轮源快照。

**模型维护日期**：历史表在 `d` 开闭链，消费条件为 `strt_date <= d AND end_date > d`。新开链结束日为 `2099-12-31`。这首先是加工观察到变化的日期，不能一概替代真实交接日、报废日或合同生效日。

**专门业务日期**：使用开始、入库、租借起止、保险起止分别回答对应业务问题。主表中的 `Data_Etl_Date` 为入仓维护字段，变更分支保留旧加载日并更新 `Data_Upt_Date`；附加表按 `busi_date` 每日落分区。`Data_Time` 是加工写入的时间信息，不能与业务生效时间等同。

所以，“某天资产是谁负责”应查当时有效的员工关系；“某天记录的净值”应查附加表那一天的快照；主表不是完整历史属性表，不能只加一个日期条件就恢复过去全部资产资料。

## 4. 一个小例子解释行数膨胀

**教学示意，非业务样例**：资产 A 当天有三种状态（资产、投保、入账），也有三种分类表达（大类、小类、性质）。如果两个历史表都仅按 `Ast_Id` 连接，即使各自已限定同一有效日，也可能得到 `3 × 3 = 9` 行。

这九行不是九项资产。如果每行再带入同一笔原值并求和，就会重复计量。应先确定问题只需要哪种状态、哪种分类；或先把各类型明确投影成列，再与资产快照连接。

## 5. 连接成立的顺序

先确认编号体系，再限定来源和日期，再选角色/类型，最后检查每个连接键的重复与缺失。不能仅靠 `DISTINCT` 修饰最终结果：它只消除整行相同的重复，无法决定同一用户对应多个员工时应该取谁。

更完整的日期与重跑推演见[历史维护与连接推演](实现详解/历史维护与连接推演.md)；真实消费者中不同时间口径的组合见[财务案例](05-资产性质进入财务的完整案例.md)。
