## 1. 下游想拿到什么

`dm_fin_n.erp_fix_ast_ast_nature` 的建表注释为“估值系统固资系统资产性质”，输出五列：固资资产编号、财务资产编号、资产性质、开始日期、截至日期。本次在 2026-09-14 重新取得任务 `236331` 的 SQL，不只依赖调度邻居推断用途。[本次 SQL](证据/SQL/236331-current.sql)、[查询回执](证据/236331补查.json)

这个消费者要连接两套信息：**性质变化保存在 T10 分类历史，FA 资产编号保存在 T10 固定资产附加快照。**

## 2. 从源头逐步推导五个输出字段

| 输出 | 直接来源 | 再向上追到 FAM |
|---|---|---|
| `Ast_Id` | 分类历史 `Ast_Id` | 资产标签号 `ASSET_TAG_NO` |

| `Strt_Date` | 分类历史 | 模型观察到新性质时的开链日 |
| `End_Date` | 分类历史 | 模型闭链日或开链结束占位日 |

上游证据：[分类历史生产](证据/SQL/236117.sql)、[附加信息生产](证据/SQL/236119.sql)。注意下游的 `Ast_Clas_Cd` 中文注释是“资产性质”，不能用主表已经转码的 `Ast_Prop_Cd` 替代。

## 3. 实际连接条件很短，含义却有三层

下面是对当前 SQL 的等价阅读节选；省略包装 SELECT，未改变连接条件，也不用于直接运行：

```sql
FROM (
  SELECT * FROM pdata_n.t10_ast_clas_h
  WHERE ast_clas_type_cd = '03'
    AND src_tbl = 'ODATA_N_FAM.W_ASSET_ACCOUNT'
) a
LEFT JOIN (
  SELECT * FROM pdata_n.t10_our_fix_ast_adtnl_info
  WHERE busi_date = '${yyyy-MM-dd}'
) b ON a.Ast_Id = b.Fix_Ast_Id
```

第一层，左侧选的是 FAM 的“性质历史”，没有只选当前有效链，所以包含符合来源/类型条件的全部期间。

第二层，右侧只选某一天的附加快照，用它提供 FA 编号。右侧没有在这段 SQL 中限制 `src_tbl`，也没有按 `Fix_Ast_Id` 去重。

第三层，使用左连接。没有当天 FA 对应的资产仍保留性质历史行，`Fa_Ast_Id` 可以为空；这不是内连接意义上的“所有输出都已经找到 FA 号”。

配置快照将目标写为 `dm_fin_n.erp_fix_ast_ast_nature`、写入方式 `overwrite`，与当前 SQL 的目标建表定义一致。查询主体本身是 SELECT，写入由任务配置承担，不应补造一条不存在的 INSERT。[配置证据](证据/来源与消费者配置.json)

## 4. 用一个反例看清时间口径

**教学示意，非生产样例**：资产 A 在 6 月的性质为“员工资产”，7 月变为“闲置资产”；到 9 月查询时，当天附加快照把 A 映射到 FA 编号 F2。

这份 SQL 会给 6 月、7 月两段性质历史都带上当天取得的 F2。如果 FA 号曾发生变化，它不会自动恢复 6 月时的旧 FA 号。当前代码回答的是“用查询日的 FA 对应看资产性质历史”，不是已经核实的“每一段历史使用当时的 FA 对应”。

这是否正是财务要求，现有 SQL 无法自行证明；需要消费者确认业务口径。这里记录的是代码行为，而非直接判定代码错误。

## 5. 三个具体使用条件

| 条件 | 不满足时会怎样 | 本次证据状态 |
|---|---|---|
| 当天附加快照中每个标签号的映射符合预期基数 | 同一性质区间可能被复制成多行 | 未取得业务行数据核验 |
| 同标签号跨来源不会误碰，或右侧已限定正确来源 | 右侧未限定来源时可能混入其他分区映射 | 当前 SQL 确认缺少该来源条件；实际是否发生未知 |
| 历史性质 × 当天 FA 号符合财务需求 | 若要历史时点还原，当前查询不能直接满足 | 业务意图尚待消费者确认 |

金额没有出现在这张用途表，不能把它描述为固定资产估值金额计算。它的贡献是把性质期间与两套编号组织为财务可读取的结构。
