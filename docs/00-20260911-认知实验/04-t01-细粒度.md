# T01（PTY / 当事人）细粒度理解

> 当前专题按平台分类、业务章节和实现证据统一从 [T01 专题入口](t01专题/README.md) 阅读。本文件保留原有研究内容及版本范围，分类解释以新入口和各章对照为准。

## 0. 先给结论

T01 不是一张“客户主表”，也不是所有 `T01_*` 表的平铺集合。它当前更像一个**多源主体事实的标准化汇聚层**：不同业务系统把个人、机构、交易对手、资管客户、TA、托管人、销售商、管理人等主体，转换成统一的 PTY 结构，再按来源和日期写入 T01。

读者理解 T01，应该沿着下面这条路线，而不是从表名清单开始：

```text
业务源系统
  ↓
源表当天快照
  ↓
T01 专属任务转换
  ↓
TEMP / MID 临时比对
  ↓
T01 按来源、日期落盘
  ↓
T98 汇总表、报表或其他下游
```

## 2. 业务上“当事人”是什么

“当事人”是比“客户”更大的概念，指参与业务的主体：

```text
T01 / PTY 当事人
├── 公共身份：编号、名称、类别、状态、开户/销户
├── 基础资料：名称、证件、地址、联系人、重要日期
├── 生命周期：状态历史、分类历史、评级、评分、偏好
├── 主体类型：个人、对公客户、资管客户、TA、托管人等
├── 主体关系：主体与主体、主体与产品、主体与员工/账号
└── 业务专题：OTC、履保、风险、CRM、RMS、期货等
```

核心表和含义：

| 表 | 读者应该怎样理解 |
|---|---|
| `pdata_n.t01_pty` | 主体公共身份主干；表注释为“每天增量更新，存放当事人开户信息” |
| `pdata_n.t01_pty_name` | 主体名称历史；一名主体可以有多段名称有效期 |
| `pdata_n.t01_pty_idty_info` | 身份证件/鉴别信息；一个主体可以有多个证件，因此一对多 |
| `pdata_n.t01_pty_addr_info` | 地址和联系方式 |
| `pdata_n.t01_pty_stat_h` | 主体状态历史 |
| `pdata_n.t01_pty_clas_h` | 主体分类历史 |
| `pdata_n.t01_pty_rat` | 评级或测评历史 |
| `pdata_n.t01_pty_rela_h` | 主体和另一个主体之间的关系历史 |
| `pdata_n.t01_indv` | 个人主体的专属属性 |
| `pdata_n.t01_corp_cust` | 对公/机构主体的专属属性 |
| `pdata_n.t01_otc_deri_cust` | OTC 衍生品客户的协议、资格、联系人、投资范围等 |

最常见的身份脊柱是 `pty_id + pty_cate_cd`。但 SQLite 没有保存主键或唯一性约束，因此只能说它们是核心关联候选，不能直接断言在所有来源和日期下全局唯一。

## 3. 源头：同一张逻辑表由很多源系统共同写入

从任务 SQL 中统计到的代表性结果：

| 逻辑目标表 | 任务数 | SQL 中发现的源表数 |
|---|---:|---:|
| `T01_PTY` | 46 | 31 |
| `T01_PTY_NAME` | 44 | 28 |
| `T01_CORP_CUST` | 27 | 16 |
| `T01_INDV` | 14 | 10 |
| `T01_PTY_RELA_H` | 11 | 11 |
| `T01_PTY_STAT_H` | 24 | 14 |
| `T01_OTC_DERI_CUST` | 5 | 2 |
| `T01_CUTP_PERF_MARG_INFO` | 2 | 2 |

例如 `T01_PTY` 的来源包括 RCC、OIS、OOM、TA5、ECR、RMS、HPB、GPB、TMC、TIT 等系统。任务脚本名中的 `RCC002`、`OIS017`、`TMC003` 是不同的来源加工实现，目标通常仍是同一张逻辑 T01 表。

因此，T01 的“统一”主要是**字段结构和语义统一**，不等于已经完成跨系统主体去重或 MDM 黄金记录合并。来源系统可能使用不同编号空间，例如：

```sql
concat('TMC003-', ID)          AS Pty_Id
concat('RMS001-', CUSTOMER_ID) AS Pty_Id
```

这可以减少编号碰撞，但不能仅凭编号证明两个来源中的主体是同一个人或机构。

需要区分两类 source：

- SQLite `tables.source`：`opencli`、`input-pack`、本地快照等，表示元数据采集来源；
- SQL 中的 `Source Table`、`Real_Src_Tbl`、`data_src_cd`、`src_tbl`：表示业务数据来源的线索。

## 4. 加工：一条主体数据如何进入 T01

### 4.1 普通主体表：TMC003

代表性任务：`PDATA_N.T01_PTY_TMC003`。

```text
ODATA_N_TMC.G_T_AMAC_ACCOUNT_0001
  → T01_PTY_TEMP_TMC003
  → T01_PTY_MID_TMC003
  → T01_PTY 的 TMC 源表分区
```

当天源表会被转换为 T01 标准字段：

```sql
concat('TMC003-', ID)      → Pty_Id
NAME                       → Pty_Name
'211003'                   → Pty_Cate_Cd
LOGOFF                     → Pty_Stat_Cd
BUILD_DATE                 → Oact_Date
LOGOFF_TIME                → Clos_Date
```

状态码还会通过 `PDATA_N.REF_CD_CVT_MAP` 做码值映射。

随后任务把当天结果和目标表中该来源已有记录按 `Pty_Id` 比对，并标记：

```text
I = 新增
U = 变更
D = 删除
S = 无变化
```

最终通过 `INSERT OVERWRITE` 重写该来源分区：

- `S`：保留原记录；
- `I`：插入新记录；
- `U`：写入变更后的值；
- `D`：保留记录但设置 `Del_Flag='1'`、`Del_Date`。

所以 T01 中的删除可能是逻辑删除，而不是物理删除。

### 4.2 历史关系表：XPB001

代表性任务：`PDATA_N.T01_PTY_RELA_H_XPB001`。

它不是简单地覆盖当天数据，而是从多个源表组合出关系：

```text
ODATA_N_XPB.T_ACCOUNT_ACCOUNT
  + ODATA_N_RCC.A_FUNDACCOUNT
  + ODATA_N_RCC.A_CLIENT
  + ODATA_N_RCC.A_CLIENTINFO
  → T01_PTY_RELA_H
```

任务会使用主体、关系类型、关联主体等字段判断是否为同一条关系：

```text
Pty_Id
Pty_Rela_Type_Cd
Pty_Cate_Cd
Rela_Pty_Id
```

关系变化时：

```text
旧记录：End_Date = 业务日
新记录：Strt_Date = 业务日，End_Date = 2099-12-31
```

这就是 T01 中“历史表”的含义：它保存关系在业务时间上的有效区间，而不仅是 ETL 运行时间。

## 5. 分区：同一张表里的数据范围

分区不是另一种业务实体，而是同一张逻辑表的数据范围。例如：

```text
T01_PTY
├── SRC_TBL = ODATA_N_RCC.A_CLIENT
├── SRC_TBL = ODATA_N_OIS.G_HK_COUNTERPARTY
├── SRC_TBL = ODATA_N_TA5.D_TA_TCUSTOMERINFO
└── SRC_TBL = ODATA_N_TMC.G_T_AMAC_ACCOUNT_0001
```

`T01_CORP_CUST`、`T01_OTC_DERI_CUST`、`T01_PTY_NAME` 等还常按 `BUSI_DATE + SRC_TBL` 分区。

因此查询 T01 时必须同时回答：

```text
看哪张逻辑表？
看哪个来源？
看哪一个业务日期？
看当前有效记录，还是历史记录？
```

忽略 `SRC_TBL` 或 `BUSI_DATE` 直接合并，可能把不同系统、不同日期的记录混在一起。

## 6. OTC 例子：T01 如何被下游使用

OTC 相关对象可以这样组织：

```text
OTC 源系统
├── 衍生品交易对手维护表
├── 交易对手属性表
├── 交易对手履保信息
└── 履保方案表
        ↓
T01 标准化主体层
├── T01_PTY
├── T01_CORP_CUST / T01_INDV
├── T01_OTC_DERI_CUST
├── T01_CUTP_PERF_MARG_INFO
└── T01_CUTP_PERF_MARG_PLAN_INFO
        ↓
T98_OTC_TRD_CUTP_HK_INFO
```

下游任务会实际 Join：

```text
T01_PTY
  → 取有效主体和主体名称

T01_CORP_CUST / T01_INDV
  → 补充机构简称、统一社会信用代码等

T01_OTC_DERI_CUST
  → 补充代签产品、OTC 客户属性等

  → 输出 T98 报表结果
```

这说明 T01 是标准化事实层，T98 才是面向具体报表或业务场景的组合结果。

## 7. 读者应该按四层消化

```text
第一层：主体是谁
  T01_PTY、名称、证件、地址

第二层：主体是什么类型和状态
  个人、对公、状态、分类、评级

第三层：主体和谁有什么关系
  关系、产品关系、员工关系、联系人

第四层：主体参与了什么具体业务
  OTC、履保、TA、CRM、RMS、资管等
```

再把每张表的物理身份补上：

```text
platform + data_source + qualified_name
```

最后再看加工证据：源表、任务 SQL、TEMP/MID、分区、历史有效期和下游 Join。

## 8. 当前证据能说明什么，不能说明什么

可以确认：

- T01 的主题边界和主要业务对象；
- 表注释、字段注释、字段类型和分区；
- 多源系统、多任务写入同一逻辑表的事实；
- 代表性任务的源表、转换、比对、拉链和下游消费逻辑。

不能仅凭这份 SQLite 和静态 SQL 确认：

- 当前最新业务日期；
- 某个分区当前是否有数据；
- 最近一次任务是否运行成功；
- `pty_id` 是否全局唯一；
- 两张表 Join 后是否一对一；
- 多个来源中的主体是否已经完成统一合并；
- 业务结果是否正确。

因此，T01 的“结构和加工规则”已经可以讲清楚；但“当前数据状态、唯一性和业务正确性”还必须结合运行结果和数据抽样验证。
