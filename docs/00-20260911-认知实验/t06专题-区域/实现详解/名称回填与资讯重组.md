# 名称回填与资讯重组：消费侧怎样改变区域含义

## 1. 从编号取名称，不只是增加展示字段

[38151](attachments/名称回填与资讯重组/IMG-名称回填与资讯重组-20260914105650266.sql)／[61593](attachments/名称回填与资讯重组/IMG-名称回填与资讯重组-20260914105652165.sql) 将机构地址中的省市代码关联 T06，读取全名；两组区域查询都筛 `DEL_FLAG='0'`，并限定 RPA 来源。输出是机构所属分公司信息的一部分，不是区域自身的组织结构。

[152801](attachments/名称回填与资讯重组/IMG-名称回填与资讯重组-20260914105653048.sql) 也在一个机构同步分支中由省市码取全名，但区域查询仅筛有效标志，没有同样的来源限制。两个消费结果的区域覆盖范围因此不能直接视为一致。

正式表本次 MANUAL 样例说明，前一种来源过滤确实会排除这类行。是否需要排除，取决于业务覆盖要求；本次只确认条件和范围，不代替业务决定。

## 2. CRM 机构地址：先转源代码，再查区号

[34789](attachments/名称回填与资讯重组/IMG-名称回填与资讯重组-20260914105653464.sql)／[61641](attachments/名称回填与资讯重组/IMG-名称回填与资讯重组-20260914105653731.sql) 先用 `REF_CD_CVT_MAP` 对 CRM 城市代码转码，再以转换值关联 `T06.ADDR_ID`，取区域表的电话区号。省市代码还存在来源原值兜底，因此“城市列非空”不等于所有来源都已成功转码。

这段 T06 关联没有显式筛来源、删除和层级。转码表的实际记录不在当前已确认码值导出中；字典 `REF_DW_CD_VAL` 与源代码转换 `REF_CD_CVT_MAP` 分属不同用途，不能用一个代替另一个。

## 3. 员工地址拼接：业务历史与区域版本错开的可能性

[35069](attachments/直接读取任务对照/IMG-直接读取任务对照-20260914105653916.sql) 与 [61573](attachments/名称回填与资讯重组/IMG-名称回填与资讯重组-20260914105654050.sql) 使用员工联系地址的省、市、县区代码多次关联 T06，把名称与详细地址拼接。员工地址按有效期过滤，T06 关联没有显式的删除或来源过滤。

因此，区域重复可能在多次 Join 中放大结果；历史地址可能被配上区域表当前可见的名称。本文没有检查员工个人记录，只分析与 T06 相关的字段和 SQL 范围。

[105420](attachments/直接读取任务对照/IMG-直接读取任务对照-20260914105650270.sql) 的查询直接选择 T06 的全部字段并添加空的同步管理列，没有 WHERE 过滤。它提供“标准化国内行政区划地区数据”的同步查询证据；SQL 中只有目标建表与查询，不能仅靠目标表名证明同步已实际落到下游系统。

## 4. 资讯消费者为什么不直接复制 T06

任务 [122045](attachments/直接读取任务对照/IMG-直接读取任务对照-20260914105653231.sql) 输出 `pdata_news_n.tyzx_admin_area`。它除了读取有效 T06 区域，还关联 `odata_n_uip.d_t_admin_division_code`；目标按 `BUSI_DATE` 分区，字段中增加区域简称与备注，并重新组织层级。

目标用途可从 SQL 的显式注释与变换理解为“构造供资讯消费的区域结构”。它与 T06 的来源维护模型不同，不应拿目标的层级规则覆盖 T06 原始模型解释。

| 处理 | 已见代码行为 | 对消费语义的影响 |
|---|---|---|
| 四个直辖市 | 从一级节点派生 `前两位+0100` 二级节点；重庆再派生 `前两位+0200` | 新增原模型没有的中间节点，明确服务三层结构 |
| 直辖市区县 | 将 `CITY_ID` 改为原 `UPPER_ADDR_ID` | 区县指向新补的二级节点 |
| 保留直辖市一级 | 单独保留其一级记录 | 一级节点与新增二级节点同名时不能按名称去重 |
| 直辖县级行政单位 | 按 T06 编号对照 UIP 的 `MCA_CODE`，用 `TYPE_CODE` 补二级或改上级 | 引入来源编号映射，不能仅靠截断数字推断结构 |
| 其他地区 | 去除短名称中的 `☆`，保留主要属性 | 原始名称与消费名称可能不同 |
| 区域简称 | 优先已有简称，再 UIP 简称，最后去除“市”“县” | 简称是消费加工结果，不是唯一标识 |
| 东莞、中山 | 排除原有下级记录，再追加 UIP 中相应三级记录 | 明确改变这两个地区的下级范围与来源 |
| 备注 | 按省份名称 CASE 写 `PROV_MEM` 等内容 | 与 T06 的 `CPTL_NAME` 不是同一条权威映射 |

## 5. 两个阅读细节能避免误判

第 155 行所在分支的注释提到启信宝编号，但实际输出的 `ADDR_ID` 仍是 `pt.addr_id`；改变的是 `CITY_ID` 与 `UPPER_ADDR_ID`，来自 `qx.type_code`。所以判断身份变化要看投影表达式，不能只读注释。

部分 UIP 关联使用 LEFT JOIN；没有匹配时，派生节点编号或上级编号可能为空。代码末尾还显式保留 `addr_id is null` 的一类记录。该程序没有因为“要构造三层树”就自动证明所有父节点存在、无重复、无空编号；这些仍需数据验证。

## 6. 应怎样选择数据

需要解释来源维护的区域资料时，从 T06 的具体来源和有效状态开始；需要复现资讯消费者的层级时，查它的 `tyzx_admin_area` 输出及对应日期。二者通过加工相关，但它们的节点集合、时间粒度、简称和编号来源已经不完全相同。
