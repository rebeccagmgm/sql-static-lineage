# 手机号归属区域：有模型草稿，落地状态尚未证明

[返回入口](README.md)

## 1. 为什么它属于另一种对象

行政区域的身份是“哪个地方”，手机号归属的身份则是“哪个号段”。同一个地方可对应多个号段，一个号段记录还需要运营商等信息。因此合理的理解顺序是：号段 → 归属区域属性 → 对照行政区域编码。它与客户登记的手机号码、联系地址分别属于不同粒度。

Wiki 将手机号归属区域列在 T06 下。本次两个手工任务关联的共享脚本都能看到 `T06_MOBILE_BEL_AREA` 建表及加工草稿，位置为原文件 5862–5954 行；整段仍是 SQL 注释。[原节选](attachments/04-手机号归属区域/IMG-04-手机号归属区域-20260914105650253.txt)、[代码版本与哈希](attachments/03-来源职责与交叉矩阵/IMG-03-来源职责与交叉矩阵-20260914105652248.json)。

## 2. 草稿表达了什么

| 字段组 | 草稿中的字段 | 对象含义 |
|---|---|---|
| 号段身份 | `MOBILE_NUMBER` | 注释定义为“手机号段”；没有给出号段长度或匹配算法 |
| 通信属性 | `MOBILE_SVC` | 手机号运营商 |
| 区域归属 | `PROV_ID`、`PROV_NAME`、`CITY_ID`、`CITY_NAME`、`BEL_AREA_FULL_NAME` | 归属省市编码、名称与组合名称 |
| 辅助信息 | `ZIP_CODE`、`AREA_CD` | 邮编与区号 |
| 加工标记 | `DATA_SRC_CD`、`TASK_NAME`、`DATA_ETL_DATE`、`DATA_UPT_DATE`、`DATA_TIME` | 来源和加载信息 |
| 分区 | `SRC_TBL` | 草稿采用来源分区 |

这是 14 个普通字段加 1 个分区字段的设计线索，未计入正式物理对象与字段数量，也没有借用 T06 行政区域表的元数据来填补它。

## 3. 草稿如何把号段资料接到区域

草稿从测试源 `GFSTEST.MOBILE_ADDRESS` 读取 `NUMBER`、`OPERATOR`、`PROVINCE`、`CITY`、`EMAIL_CODE` 和 `AREA_CODE`。其中 `EMAIL_CODE` 被写入邮编字段，这是已见字段映射，不能按其英文词面理解成电子邮箱。

区域候选来自 RPA 源表派生的 `ADMIN_AREA_TEMP`，限定了字面日期 `2023-11-15`。草稿分别尝试二级、一级、三级区域，以区号相等和城市名称前两字相等关联，再用 `COALESCE` 选取省市编号。安顺、遵义、本溪、克州、海西、阿盟另写硬编码分支。

由此能推导出的设计意图是：解决手机归属来源与行政区域名称、层级不完全一致的问题。但硬编码是否仍适用、模糊名称是否唯一、号段是否完整，以及来源的实际更新时间，本次没有验证。

## 4. 能说到哪里，不能说到哪里

| 证据 | 可以成立的结论 | 仍缺什么 |
|---|---|---|
| Wiki 主题定义 | 手机归属是 T06 的设计范围之一 | 当前表和任务状态 |
| 注释中的 DDL | 存在明确字段与分区设计 | 正式表是否创建、当前结构是否相同 |
| 注释中的 SELECT | 存在按区号与名称补区域编码的历史方案 | 是否执行、怎样调度、数据覆盖及消费者 |
| 当前本地目录未命中 | 本次元数据与平台目录快照没有找到该对象 | 快照不完整，不能宣称平台不存在 |

手机号归属本身也不能证明客户当前居住地、开户地址、GPS 位置或 IP 所在地；这些是不同来源记录的事实。草稿没有提供把完整手机号映射到号段的实际消费者，因此不补造一个已经上线的匹配流程。

继续核实时，最有价值的证据是正式表身份、有效生产任务、号段规则和一个真实消费者。当前专题保留这一支完整的对象解释及设计证据，不用行政区域案例替代它。
