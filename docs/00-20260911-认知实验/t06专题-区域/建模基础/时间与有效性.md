# 时间与有效性：保留删除记录，不等于完整历史

[返回入口](00-20260911-认知实验/t06专题-区域/README.md)

## 1. 四种时间不能混在一起

| 时间 | 在哪里 | 能说明什么 |
|---|---|---|
| 源业务日期 | RPA 源表 `BUSI_DATE` | 主加工选取哪一天的源分区 |
| 任务逻辑日期 | `${data_day_str}` | 主加工写入加载、更新和删除日期的参数 |
| 加工时间 | `${data_today}` 对应目标 `DATA_TIME` | 本次处理时间标记，具体运行参数需另核 |
| 证据获取时间 | SQL 文件头、目录采集时间、本次查询日期 | 我们何时取得证据，不代表业务数据的时点 |

61790 用 `DATE_SUB(d,-1)` 读取源分区，即参数日的次日。这里能确认日期偏移的写法；为何如此安排、上游何时到达、当天是否完整，需要任务运行与源分区数据才能回答。

本次 SQL_MCP 补查虽然成功返回文本，其中仍含 `2026-05-20` 等已渲染日期。获取日期是 2026-09-14，文本日期是另一件事；不把这次接口成功当作最新运行验证。

## 2. 新旧比较实际保存什么

主加工先以同一来源的 `ADDR_ID` 全外连接新旧记录，再按内容变化分为 I、U、D、S。以下为已读 SQL 的投影结果。

| 分支 | 条件 | 区域内容 | 删除信息 | 加载与更新时间 |
|---|---|---|---|---|
| I 新增 | 旧无、新有 | 取新值 | `0`、删除日期空 | 加载日与更新日取 d |
| U 更新 | 新旧都有、内容有差异 | 取新值 | `0`、删除日期空 | 保留旧加载日，更新日取 d |
| S 未变 | 新旧都有、比较内容相同 | 取旧值 | 重新写 `0`、删除日期空 | 沿用旧加载日、更新日和数据时间 |
| D 源中缺失 | 旧有、新无 | 保留旧值 | `1`；原删除日期非空则保留，否则写 d | 首次标删更新日期，持续删除保留原时间 |

比较内容包括名称、归属、层级、邮编区号、驻地、人口和面积，不包括旧删除状态。因而原来已标删的区域重新出现、内容恰好相同时，可落入 S：标志恢复为 `0`，但更新时间仍沿用旧值。`DATA_UPT_DATE` 因此不是完整的状态变化日志。[61790 SQL 第 132–276 行](attachments/01-区域对象与层级/IMG-01-区域对象与层级-20260914105651381.sql)。

## 3. 为什么不能完整还原过去

假设区域 A 原名“甲区”，d 日变为“乙区”。U 分支把内容覆盖为乙区，没有额外保留带起止日期的甲区版本。删除分支则保留内容并标删，两种行为不同。

所以本模型的能力是“维护更新后的区域属性与源缺失标记”，不是“一行一个历史有效期版本”。`DEL_FLAG=1` 首先说明对比的新源集合中没找到该编号，不能独立证明行政区在法律上撤销；源分区缺失或采集不完整也可能触发同类代码路径。

## 4. 下游历史地址并不自动获得历史区域解释

员工或机构地址表可能按 `STRT_DATE <= d AND END_DATE > d` 取业务当时的地址编码，但随后关联 T06 时没有对应区域版本区间。得到的是“业务历史地址编码 + 查询时区域表可见属性”。

如果要解释“当时叫哪个名称、当时属于哪个上级”，还需历史区域快照或正式变更记录；本次未验证此类完整来源。资讯派生表虽按 `BUSI_DATE` 保存输出，也不能据此认定它补齐了所有历史时期和所有来源。
