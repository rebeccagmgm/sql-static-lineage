# 待核问题：哪些缺口会改变使用结论

[返回入口](00-20260911-认知实验/t06专题-区域/README.md)

这些是证据缺口或由静态 SQL 推出的条件性风险，不是已经认定的数据事故。本次没有修改平台数据、业务代码或 T04/T05 整理成果。

| 问题 | 当前能确认的事实 | 对使用的影响 | 最小后续证据 |
|---|---|---|---|
| 正式表到底有哪些来源 | RPA 写入逻辑已见，MANUAL 首屏样例已见，历史注释另提一个来源标记 | 限 RPA 可能缩小地域覆盖；不限定来源可能遇到同码冲突 | 主表完整来源枚举、每来源行数与更新时间，随后按目标业务范围核对 |
| 区域编号是否唯一 | 61790 在来源内按编号比较，DDL 无 PK，质量检查仅有配置 | 关联可能一对多，多个地址字段可能累计放大 | 指定来源和有效状态后的编号重复及跨源冲突检查 |
| CITY_ID 的省级源行分支 | SQL 注释写直辖市，条件只筛省级后缀 | 普通省级原始行存在时可能改变城市归属 | 同一源业务日的省级行全集与关联结果 |
| 自动补省级是否重复 | 原始行与聚合补行使用 UNION ALL | 同编号可来自两个分支，DISTINCT 多字段不保证唯一 | 同日两个分支按编号的交集与内容差异 |
| 层级是否完整可遍历 | 直接上级由编码派生；资讯消费者显式补中间节点 | 直接上级未必在 T06 内可找到，不能默认完整三级树 | 同来源有效节点的父节点覆盖、孤儿及循环检查 |
| 删除能否解释行政撤销 | D 分支由新源缺失触发 | 源缺失也可能造成标删，不能直接解释法定撤销 | 源完整性、运行日期及权威变更记录 |
| 能否还原历史区域名称 | U 覆盖属性，无起止版本链；S 可恢复标志而不更新时间 | 历史业务地址可能配上不同版本名称 | 区域历史快照或变更记录及与业务日期的对应规则 |
| 人工分区由谁维护 | MANUAL 实际行存在；两个手工任务共用脚本，相关语句已注释 | 行内 TASK_NAME 不能证明当前维护责任 | 有效写入配置、源码、修改记录和一次对应分区写入证据 |
| 手机归属是否落地 | Wiki 与注释 DDL/SELECT 存在，当前本地正式目录未命中 | 可以解释设计，不能承诺可直接查到完整号段数据 | 正式物理表、有效生产任务、号段规则、一个消费者 |
| 客户名称匹配是否歧义 | 多个分支截断地名，部分缺来源、父级或删除条件 | 可能未匹配、误匹配或放大业务行 | 指定业务日的未匹配率、多匹配明细及抽样业务确认 |
| 资讯派生是否无空无重 | 有 LEFT JOIN、UNION ALL、允许空编号的分支 | 三层结构的目标不等于结果已经是完整树 | 指定 BUSI_DATE 的重复、空编号、父级覆盖与来源映射 |
| 主题目录为何 4 对 3 | 主题快照计数 4，本地任务目录 3 | 不能把当前 3 条称作主题完整任务全集 | 同时点的主题任务分页与权限范围 |
| 图谱与 Facts 覆盖 | 图服务不可用，常用注册入口未定位到 61790 | 本次只能引用 SQL 直接关系，不能声称全图或字段闭包完整 | 服务恢复后的有界查询与主任务正式 Facts；无需为本稿重建全域 |

若继续推进业务使用，优先核对“来源范围＋有效编号唯一性”，然后才是完整区域内容、历史解释与手机号落地。统计总表数或重复绘制大图不会解决这些问题。
