# 基金、销售、托管与两融：同一个“产品”背后的不同对象

[返回入口](../README.md) · [组合定义](../资料/组合类型.json)

## 1. 基金与份额先分开

一个基金安排可以有不同份额类别。它们共享管理人等资料，却可能有各自证券代码、费用和净值。只按基金名称合并，会把需要分别计价和登记的份额压成一行。

实际 TL 分支 69826 从 `q_fund` 出发，按 `fund_id` 连接 `q_fund_class`，再用份额 `security_id` 连接 TL 证券主档 `in_code`，将统一编号写入 `T02_FND_BASE_INFO`。这条路径直接体现“基金→份额→证券身份”，不是凭表名推测层级。[69826，143—287行](../证据/SQL/69826.sql)

管理公司和托管人分别以源机构号连接 TL 企业主档，并补机构资料。至少 `mgmt_corp_cd` 写入模型 `corp_id`。所以不能把基金专档中的机构信息一概说成“只有名称”；但资讯企业号仍不自动等于 T01 的 `Pty_Id`。

费用分支按份额和费用类型取 `BEGIN_DATE` 最近的一条，未见统一增加“截至某个历史查询日”的限制。它适合解释这段加工选了什么，不足以恢复任意历史日的当时费率。

## 2. 销售产品档案增加的是业务安排

`T02_PRD_FIN_INFO` 描述产品中心管理的产品，包括销售、风险、策略、成立到期和控制属性。它与证券主档可以来自同一张 `p_basicproduct`，分别生产；不是先把证券主档扩成一张销售宽表。

66204 用源 `SECUCODE`、类型及市场调用编号函数；将原始 `SECUTYPE`、`STRATEGY` 等保留到产品字段；再按产品号接控制记录。控制记录按状态排序，并按失效时间倒序取一条。它会影响最终展示的产品控制属性。[66204，139—281行](../证据/SQL/66204-hive-task.sql)

该表在本地结构及此脚本中都不是 `src_id` 分区表。不能把“所有 T02 取数必须写 src_id”当成可直接套用的规则。策略字典还存在元数据与脚本注释冲突，见 [分类与口径](../建模基础/03-分类常量与口径.md)。

## 3. 托管产品关注服务和生命周期

托管需要知道产品如何募集、由谁服务、怎样分级、是否锁定、何时清盘。这些安排不等于市场证券的上市状态，也不等于渠道是否销售。

69852 写 `T02_CSTD_PRD_BASE_INFO` 的 MOT 分区，但有效源已经是一组 CAP 表。SQL 先构造兼容 MOT 的基本和扩展临时结构，再按产品代码连接服务属性，按外部流水号连接清盘日期和 MOT 主档身份。

| 来源/连接 | 结果含义 |
|---|---|
| CAP 基础、募集、服务、分级等表 | 形成托管产品资料，而非一张源表直接搬运 |
| 过滤外部流水号非空及生命周期状态不为F | 源里有记录，不保证进入模型产品集合 |
| 清盘表按外部流水号取最大清盘日 | 一个产品可有多条过程记录，最终选择经过聚合 |
| 主档 `rec_id = outserialno` | 用该分支的兼容身份取得统一编号 |
| `src_id='MOT'`、旧 MOT `src_tbl` | 保留兼容标签，不能代替真实 FROM 来源 |

[69852，CTE及473—588行](../证据/SQL/69852.sql)。本版展开了主体连接，未宣称逐项审计了所有 CAP 服务子表及其基数。

## 4. 两融表里有两个不同的“证券编号”

`T02_MARG_BASE_INFO` 的已读分支保存两融合约，不是单纯的可融资融券资格名单。65994 从 YGT 历史合约读取合同号、合约号、状态、客户账户、利率、交易标的，分别生成：

| 目标字段 | 编号输入 | 标识的对象 |
|---|---|---|
| `secu_id` | 类别CT、`COMPACT_ID`、市场转换 | 两融合约身份 |
| `src_sys_prdno` | `MG-` + 合约号 | 源合约标识 |
| `tgt_secu_id` | 股票类型、代码、市场 | 合约交易的标的证券 |

采集脚本包含不止一段有效写入：前段把当日RCC合约与已有RCC分区结果合并、排序；后段再把指定日期范围的YGT合约与已有结果合并，按源合约号及数据时间等取记录，覆盖同一RCC分区。不能只凭后段就说全任务唯一输入是YGT。[65994，50—187及322—502行](../证据/SQL/65994-hive-task.sql)

一个标的可以出现在许多客户合约中，不能把这些合约行当成多只标的。这里确认两类身份及多段静态写入，没有验证各语句运行时的实际状态与执行结果。

组合 `TGT_SECU` 的属性键明确是 `TGT_SECU_ID`，定义 SQL 按该字段分组取股票名称；它从已见合约抽取标的集合。本次证据不支持把这个集合直接称为“交易所或公司批准的可交易资格名单”。

## 5. 组合类型是消费规则

| 组合类型 | 属性表/关键定义 | 阅读含义 |
|---|---|---|
| NEWS_SECU | 证券主档，键为 SECU_ID；定义另选五类来源 | 指标中的产品维，不代表全部主档来源 |
| TGT_SECU | 两融表，键为 TGT_SECU_ID | 合约涉及标的，与该表 SECU_ID 不同 |
| CSTD_MOT_PRD | 证券主档 | 与 NEWS_SECU 属性表相同，也不表示成员定义相同 |
| TA_PRD | TA5 产品档案 | TA 业务编号要按自身定义解释 |
| CSTD_AMAC_PRD / CSTD_MKT_POF | TMC产品 / 基金专档 | 协会产品和市场公募采用不同属性入口 |
| CSTD_TA_PRD / CSTD_TA_STRU | T98托管相关表 | 有的产品维实际已经由汇总层供给 |

具体定义以 [本地组合快照](../资料/组合类型.json) 为准。TA、协会及全部组合成员的生产未在本版逐一展开；它们在这里作为明确的业务边界，不以表名推断成员完整性。
