# 公告、研报与事件：一份文档可以描述多件事

[返回入口](../README.md)

## 1. 文档身份和业务事件身份分开

一次分红可能有预案、实施公告及更正公告；一份研报可能讨论多家公司。文档数量、事件数量、证券数量分别回答不同问题。

| 模型层次 | 本地入口 | 一行需要解释什么 |
|---|---|---|
| 公告资料 | `T02_ANN_INFO`、`T02_ANN_INFO_EXT` | 文档编号、标题、日期、栏目、正文/链接和关联对象 |
| 研报主体 | `T02_RD_BASE_INFO`、研究报告扩展表 | 报告身份、类型、状态、文档版本、报告日期 |
| 研报作者与附件 | `T02_RD_AUTHOR_INFO`、`T02_RD_ATT_INFO` | 一份报告有哪些参与人和文件；不天然一对一 |
| 业务事件 | 股票发行、分红、企业治理和信用事件表 | 事件本身的对象、阶段、发生/有效时间及数值 |

## 2. WD 公告怎样取得证券与栏目

69312 读取 `w_ashareanninf`，保留 `object_id`、公告ID、标题、公告时间、收集时间、正文/链接等；用源 Wind code LEFT JOIN WD 主档的 `in_code`，补证券与企业编号；用栏目代码连接当日公告栏目表，补栏目名称，写 WD／grp01。

| 字段或连接 | 解释 |
|---|---|
| `ann_id` / `rec_id` | 保留源文档与源记录标识，不能用证券号代替文档号 |
| `ann_date` | 从公告时间提取日期 |
| `collect_time` | 来源收集时间，与公告日期分开 |
| `secu_id/corp_id` | 根据所关联证券补齐的身份，可能因主档未命中而为空 |
| 栏目代码与名称 | 文档分类，并非其中事件的唯一类型 |

[69312，49—73行](../证据/SQL/69312.sql)。最终源 SELECT 未见限制公告日为处理日，不能把“覆盖一次来源分区”直接解释成“只加载今天公告”。

## 3. RMS 研报还有版本与附件选择

61490 从 `n_ir_report` 读取报告身份、名称、类型、状态和 `docversion`，保留关系报告ID、翻译报告ID等；通过 `n_sirm_entitysetting` 中的 `reportdate` 取得报告日期。

附件分支限定 `filetype='pdf'`、`convertstatus='1'`、`sourceentity='REPORT'`，并排除类型1和4；再按 `sourceid` 分组、附件对象号倒序取一条。它是在选择本次输出关联的附件，并不意味着原报告只有一个文件。报告主表的 `pub_date` 在该分支直接写空，不能用“任务有结果”证明已经发布。[61490，108—208行](../证据/SQL/61490.sql)

`docversion` 与字段 `version` 也不同：前者投影为报告版本号，后者在 DDL 中说明为乐观锁。不能把技术更新版本当成用户看见的报告版次。

## 4. 看一个更正场景

教学假设：公司发出分红公告 A，随后发布更正公告 B。统计“共发布几份文档”可按文档身份得到两份；回答“最终每股分红是多少”还要识别 A/B 是否描述同一事件、更正覆盖哪一项，以及哪一份在查询时点有效。

本次已读公告生产保留了原标识和时间，但没有完成全量事件归并及更正关系算法。因此可以展示文档事实，不能直接把文档去重等同于事件口径已经统一。

## 5. 下游使用的三个判断

做资讯检索时，确认按文档、版本还是附件展示；做事件监测时，确认触发事件及更正关系；做历史研究时，使用公告/可得时间，而非把后来收集的信息提前放回历史日。

对研报“提交、转换、发布、阅读”也应分别统计。已读生产并未提供所有对外发布或阅读行为的闭环，不能从一条报告记录推断这些动作全部完成。
