# 债券、发行条款与偿付：一只债不等于一笔付款

[返回入口](../README.md)

## 1. 沿着债券要回答的问题拆对象

先知道是哪只债、谁发行，再问约定怎么付息还本、实际发生了什么、今天怎样计价、信用情况怎样。前后问题有关，但不能共用一行记录。

| 层次 | 本地代表模型 | 业务解释 |
|---|---|---|
| 身份与条款 | `T02_SCR_BASE_INFO`、`T02_BOND_BASE_INFO` | 公共身份与发行、计息、到期、含权等约定 |
| 发行企业及评级 | `T02_CO_BASE_INFO`、`T02_BND_ENTY_RAT`、`T02_BOND_RATING` | 评价谁、由谁评价、什么时间和级别；主体与债项须分开 |
| 计划与现金流 | `T02_BND_CASH_FLOW`、`T02_BND_ACTL_CASH_FLOW`、`T02_BOND_INTR_PAY` | 条款形成的安排、源报告的实际现金流与付息兑付事项 |
| 市场与估值 | `T02_BND_QUOT_H`、`T02_BOND_VALU_ANLS`、收益率曲线 | 观察价、估值价与曲线参数，必须带计价口径 |
| 变化与风险 | `T02_BND_DEFLT_EVT`、`T02_BND_DEFLT_PROG`、可转债条款与转股价格变动表 | 违约进程、行权或条款变化，有独立的事件与时间 |

以上模型存在及说明来自元数据；下面的生产解释限定到已读主档和 OIS 凭证分支，不把目录中每张表都说成已完成全链核验。

## 2. 债券主档怎样从源条款形成

69289 从 `w_cbonddescriptionzl` 读取债券资料，以 Wind code 连接 WD 证券主档，再连接交易方式、附息利率品种、发行方式、息票品种、承销/担保方式等代码资料，并通过资讯常量转换货币等属性。

模型既保留发行及计息日期、发行规模等源字段，也通过 CASE 表达是否跨市场、可赎回、提前兑付、净价/全价等特征。它把“这只债有哪些约定”组织在一起，没有因此生成每笔现金流的已付款事实。[69289，128—257行](../证据/SQL/69289-hive-task.sql)

该采集 SQL 中存在 `'{data_day_str}'` 等占位写法，与其他任务常见 `${data_day_str}` 不同。本文保留原文，不能把这份静态快照当成已验证可直接执行的脚本。

## 3. 计划、发生与计价分别推理

教学例子：某债券约定一年付息两次，每次3元。条款可以导出两项应付安排。若第一项后来延期，债券身份没有变，原条款、当前安排、实际支付和风险进度却可能分别变化。

查询“下一次应该付多少”，进入计划与有效条款；查询“已经付了多少”，进入对应实际记录和状态；查询“这只债今天值多少”，进入估值或行情，并明确净价、全价、单位和日期。三种金额不能相加成一条“债券金额”。

这段是对象层次的教学推导。本次没有对全部现金流任务、实际兑付状态和真实到账进行验证。真实业务须回到具体模型列、源定义及消费规则。

## 4. OIS 收益凭证让层次更具体

92881 从 OIS 收益凭证对象读取产品号、存量本金、最低/预期收益率、起息到期兑付日期、实际兑付金额、是否保本及提前终止等，写 `T02_BND_INCOME_VCHR_OIS`。身份通过 `prd_no` 连接 OTC 主档分区的 `scr_cd`，资金类型用 OIS 常量 `var00512` 转换。[92881，71—166行](../证据/SQL/92881.sql)

同一行可以同时含约定属性和源提供的结果字段，因此不能仅按“有金额”将它归为交易流水。该模型也不是每名客户每次付款的明细；关联投资人、认购或客户交易时要再明确对象和粒度。

资管侧另有已读偿付分支，使用不同的债券市场编码，并区分每手与每百元单位，见 [跨库模型中的资管偿付](10-跨库产品模型与编码差异.md)。

## 5. 可转债与 ABS 为什么需要关系和结构

可转债涉及债券本体、正股、转股价及条款触发；ABS 涉及项目、分档证券和偿付安排。本地有 `T02_ABS_BASE_INFO`、`T02_ABS_BOND_RELA`、`T02_BND_ABS_CLASF` 等结构，以及可转债价格变动、赎回、回售和转股类表。

它们说明“某项目有多档债券”“一只债关联一只正股”与“一次偿付”是不同层次。此处保留结构入口；具体关系类型、有效期及各来源的构造未全部验证，不将所有这些关系一律归到通用证券关系表。

读者应能先定位自己问的是债券身份、条款、现金流、价格还是信用事件，再进入对应实现，而不是先按债券代码拼全表。
