# 分类、常量与口径：同一个“类型”为什么会有不同答案

[返回入口](../README.md)

## 1. 先分四个层次

产品中心的原始 `SECUTYPE` 描述其管理体系中的产品类型；证券主档把它转成 FD、PF、AM 等工具类别；XLA 分类再按 PRD01 表达业务类型和投资类型；最后报表筛掉不符合条件的产品。每一步回答的问题不同。

平台给表贴“基金”“行情资讯”标签，是资产导航。它没有给表内每一只基金完成分类。

## 2. 三种基础结构各管什么

| 结构 | 代表字段/表 | 用法 |
|---|---|---|
| 对象分类记录 | `T02_SCR_TYPE` 的 `src_id + scr_type_std_cd + secu_id` | 先选来源和分类标准，再解释该标准下的各列 |
| 资讯常量字典 | `T02_PUB_CST_INFO` 的来源、常量类型、常量码与中文 | 解释某类资讯代码；字段存在不代表当前全部实值已采集 |
| 资讯常量转换 | `T02_PUB_COVT_CONST` 的 `src_const_cd → const_cd` | 在限定来源和常量类型后转换；必要时还带匹配类型等条件 |

仓库 `REF_DW_CD_VAL`/`code_values` 的 CD060、CD106 等属于另一套代码域。只有明确的字段定义或转换证据才支持引用，不能因为都叫“基金类型”就互套。

本地组合和码值快照为 UNVERIFIED。原始字典含义、字段注释、SQL 中的 CASE 翻译应分别记录来源，不以某一份自动覆盖其余。

## 3. 一列叫中文名称，实际却写代码

65938 的 PRD01 分支将 `prd_busi_type` 写到 `type_cd`，将 `prd_inv_type` 写到 `type_name_zh`，把 `prd_collection_type` 写到 `remark`。因此这里的 `type_name_zh` 并不是应直接显示给用户的中文名称。

该任务先从产品中心类型、资产类型和募集属性派生分类，又接 OIS 收益凭证信息处理保本/收益相关条件；另一次 INSERT INTO 写 PRD02 人工标签。**同一张表、同一来源下，不同标准的列用法也需要分别解释。** [SQL 65938，46—161行](../证据/SQL/65938-hive-task.sql)

这能解释为什么只给读者一张“字段名—中文注释”表还不够：实际加工可能采用兼容性写法。

## 4. 产品策略存在真实的证据冲突

| 证据 | `strg` 的写法 |
|---|---|
| 本地表元数据 | 1 管理期货、2 固定收益、3 主观多头、4 量化多头……16 其他 |
| 66204 脚本的 DDL/行内旧注释 | 1 定向增发、2 股票多空、3 股票多头、4 管理期货……15 其他策略 |
| 66204 的实际投影 | `a.STRATEGY AS Strg`，没有做上述两套体系之间的转换 |
| 100743 消费 CASE | 使用与本地表元数据接近的 1—11 解释，2 按固定收益过滤 |

所以本版可以准确复述“该报表把 2 当固定收益排除”，不能声称已证明所有产品中心实际数据和所有历史时期都按这套值域填写。冲突需要源系统字段当前字典、变更时间和真实值核验。这里只修正文档，不替业务选择权威版本。

## 5. 状态先问“哪个对象发生了什么”

证券主档 `scr_stat`、产品中心状态、申赎状态、交易日状态、托管生命周期、研报处理状态各有含义。61577 甚至把产品中心上架/下架等原始状态映射到证券主档的上市类状态代码，这是模型投影语义；不能由主档一列反推所有交易资格。

查“能不能买”，需要落到具体市场、销售渠道、产品和日期；查“研报已发布”，要核对报告状态、发布时间和发布流程。状态列名称相似不能替代这些对象判断。

## 6. 把解释写成完整的一句话

“本报表对 XLA／PRD01 能匹配到的产品，采用产品中心 `scr_type/ast_type/strg` 形成筛选；其中策略数字的当前权威值域尚有证据冲突。”这句话同时交代了对象集合、字段职责和证据边界，比笼统说“取产品类型”更可执行。
