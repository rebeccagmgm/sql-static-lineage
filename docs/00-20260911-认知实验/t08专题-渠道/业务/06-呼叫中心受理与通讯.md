# 呼叫中心：受理入口与通讯设备是两种对象

[返回入口](../README.md)

## 1. 为什么需要两条模型链

呼叫中心要知道业务从哪里受理，也要配置录音或留言等通讯设备。受理来源由 `C_CCB_ACCEPT_FROM` 提供，通讯设备由 `C_CCB_IPCC_SITE` 提供；没有证据支持把二者编号直接等值连接。

| 模型链 | 编号 | 内容 |
|---|---|---|
| 受理来源 → `t08_chan` | `CC2035-ACCEPT_FROM` | 渠道身份、名称和类别12“呼叫中心受理渠道” |
| 受理来源 → `t08_cc_acpt_chan_plac_info` | 源配置 ID + 渠道编号 | 同步接口、同步参数、互联网客服标志；来源/日快照 |
| 受理来源 → `t08_chan_stati_info_h` | 渠道编号 + 属性类型02 | 渠道受理类型写到 `Stati_Subdv_Cd` |
| 通讯设备 → `t08_dvc_base_info` | `CC2036-IPCC_SITE_ID` | 通讯设备共用身份与属性 |
| 通讯设备 → `t08_cc_pst_dvc_plac_info` | 同上 | 名称、标识、状态、通讯类型、链接和备注；来源/日快照 |

证据：[210930](../../../attachments/06-呼叫中心受理与通讯/IMG-06-呼叫中心受理与通讯-20260914110950613.sql)、[210932](../../../attachments/06-呼叫中心受理与通讯/IMG-06-呼叫中心受理与通讯-20260914110951653.sql)、[212190](../../../attachments/06-呼叫中心受理与通讯/IMG-06-呼叫中心受理与通讯-20260914110953014.sql)、[210931](../../../attachments/05-设备状态与使用者/IMG-05-设备状态与使用者-20260914110954356.sql)、[210933](../../../attachments/06-呼叫中心受理与通讯/IMG-06-呼叫中心受理与通讯-20260914110954498.sql)。

## 2. “统计信息历史”这里存的是受理属性

212190 写 `Chan_Stati_Info_Type_Cd='02'`，将 `ACCEPT_SOURCE` 放在 `Stati_Subdv_Cd`，其他统计数值字段为空。CD1591 的02表示渠道受理类型，邻近CD1789定义1电话、2在线、3离线受理。因此这是一项有历史的配置属性，不能把每行当作一次电话或把2解释为两次受理。

独立代码域与该细项字段之间的适用关系仍需结合来源；这里以 SQL 字段、属性类型和代码说明共同解释，不声称已验证所有历史取值。

## 3. 本次解决了一个结构冲突

本地字段库中的 `t08_cc_pst_dvc_plac_info` 只有9个字段，包含事件、客户和联系方式，且注释为空；任务DDL显示另一套15字段的设备配置结构。2026-09-14按精确GUID读取平台DDL，确认是13个普通字段加2个分区字段，与任务DDL的配置结构一致。

阅读目录采用本次平台DDL；原字段快照留存，作为明确的冲突记录，没有覆盖原库。新增的受理配置表也取得平台DDL，共13个字段。[设备DDL](../../../attachments/字段目录/IMG-字段目录-20260914110952354.json) · [受理配置DDL](../../../attachments/字段目录/IMG-字段目录-20260914110950626.json)

## 4. 仍不能据此认定两张表状态码一致

210931 的设备基础投影连接了状态转换表，但实际输出 `ENABLE_FLAG AS Dvc_Stat_Cd`；210933 的设备专有配置输出 `NVL(B.DW_CD_VAL,ENABLE_FLAG)`。二者对同一来源字段的处理不同，可能产生不同代码域的值。

CD1786 的通讯设备类型取值1为录音设备、2为留言；它适用于 `Pst_Dvc_Type_Cd`，不能替代 `Dvc_Stat_Cd`。是否启用、是否在线、是否实际录音成功是不同问题。本次没有取得通讯执行日志或传输结果，也没有发现这一分支的直接消费SQL候选。
