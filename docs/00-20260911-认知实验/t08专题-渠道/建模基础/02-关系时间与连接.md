## 1. 关系表表达的不是同一种关系

| 表 | 关系两端 | 区分条件及已见语义 |
|---|---|---|
| `t08_chan_rela_h` | `Chan_Id → Rela_Chan_Id` | 已读 AUM 特殊渠道来源为 `YLQD1 → YLQD2`，类型 01；未取得独立完整代码域定义，不能扩大为通用父子树 |
| `t08_chan_inr_org_rela_h` | `Chan_Id → Inr_Org_Id` | CD1004：01 归属机构、02 引流营业部、03 特殊引流营业部、04 锁定营业部 |
| `t08_chan_user_rela_h` | `Chan_Id → User_Id` | LLM 来源使用 01；OAO 来源注释给出 2 申请人、3 联系人。前导零与来源保持原样 |
| `t08_chan_stati_info_h` | 渠道 → 某类型的属性值 | CD1591：01 打折标志、02 受理类型、03 预约有效期；不一定是可加的统计指标 |
| `t08_dvc_user_rela_h` | `Dvc_Id → User_Id`，还可能带应用渠道 | 区分设备类别、关系类型和来源用户 |
| `t08_dvc_inr_org_rela_h` | 实际设备标识 → 内部机构 | 字段仍叫 `Chan_Id`，LIA 来源写的是设备源键；不能据此直接连接渠道主表 |

“归属营业部”“引流营业部”“锁定营业部”可以不同。应按问题选择关系类型，不按同一渠道号把三种机构当成同一组织。

## 2. T08 至少有三种时间模型

| 时间模型 | 典型表 | 合适的读法 |
|---|---|---|
| 更新后的属性及删除标志 | `t08_chan`、`t08_shop_info`、多数附加信息 | 限来源分区、按业务需要判断删除标志；加载/更新时间不等于完整属性版本链 |
| 有效期历史 | 多张 `_h` 表 | 已读 SQL 使用 `Strt_Date <= d AND End_Date > d`，即左闭右开 |
| 来源与业务日期快照 | 直播、SIP 入口、名单、开户限制、呼叫中心配置 | 同时限定 `Src_Tbl` 和 `Busi_Date`，再解释具体事件时间 |

已读历史加工常用 `2099-12-31` 作为开链结束值。这里不能套用别的主题或组合定义中的 `2999-12-31`。源表 `BUSI_DATE`、直播计划时间、真实开播时间、费用月份、配置生效时间也各有用途。

例如一条直播记录在连续日期快照中都带累计点赞数。跨日相加累计字段会重复计算；是否需要当天增量，必须另有差分或事件级口径。反过来，某日交易连接到最新渠道分类，只能称为“用该分类快照解释历史交易”，不能说取得交易当日的历史分类。

## 3. 一个安全的关系理解例子

假设要理解某一天渠道的“引流营业部”，概念上应从选定来源的渠道集合出发，连接当天有效、关系类型为 02 的机构关系，再确认机构编号所属体系。下列只是阅读示意，没有对实际数据执行：

```sql
-- c、r 已各自限定来源分区；d 是所需业务日期
c.Chan_Id = r.Chan_Id
AND r.Chan_Org_Rela_Type_Cd = '02'
AND r.Strt_Date <= d
AND r.End_Date > d
```

如果业务问的是“锁定营业部”，选择的是 04。若同一渠道同日仍匹配多行，不能用任取第一行掩盖：可能是合法多值，也可能来源、键或历史链有问题。应先看生产时的匹配键，再核查实际行。

## 4. 下游实际 SQL 可能比这更宽

67780 的网上开户分支读取渠道关系时限定类型 01；另一个特殊引流分支只写了有效期条件，没有同样的类型过滤。此处报告的是已读实现差异，不替它补上条件。84962 对渠道分类支持正则匹配，有意允许一条客户来源命中多个配置，再通过 SQL 中的优先规则压缩结果。

这种消费规则是归因口径的一部分。T08 主表没有一个字段可以直接代替“客户最终归哪个渠道”的全部计算。[客户归因案例](../实现详解/01-开户渠道如何成为客户归因.md)

## 5. 已知不能直接套用的连接

- MSC 设备基本信息写 `Dvc_Cate_Cd='USER_DVC'`，设备用户关系来源写 `MSC_USER_DVC`。不能要求两表类别文字相等后才连接。
- LIA 设备机构关系中的 `Chan_Id` 是设备标识，不是 `t08_chan.Chan_Id` 的已验证外键。
- 店铺主表来源的类型是 `05020`，店铺专有表来源的类型是 `0520`。本地字典找到前者，未找到后者；不能据此认定这两个文字值相等。
- 金钥匙 `Mode='like'` 的消费条件是 `rlike`，不是 SQL `LIKE`，更不是精确主键关联。

详见[证据差异与待核问题](../证据/来源覆盖与待核问题.md)。
