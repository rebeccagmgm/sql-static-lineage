# 身份、粒度与分类：四个字段不能互相替代

[返回入口](../README.md)

## 1. 先回答“一行是什么”

`t08_chan` 的一行是某来源分区中的渠道描述；`t08_shop_info` 是店铺属性；`t08_chan_cust_list` 是名单项；`t08_chan_dvrs_fee` 是来源费用记录；`t08_chan_user_rela_h` 是某段时间内的渠道用户关系。把它们都称为“渠道信息”会掩盖一对多关系。

例如一个渠道可能有多个联系人、多个费用月份、若干素材配置和很多名单项。把这些表一起按 `Chan_Id` 连接，可能形成联系人 × 月份 × 名单项的组合。先确定要得到“每个渠道”“每月费用”还是“每个名单成员”，再选择关系和聚合顺序。

## 2. 仓库编号与源编号

`Chan_Id` 常由一个历史命名空间前缀加源键组成，`Src_Chan_Id` 保留源键。不能用“当前系统缩写 + 源键”通用公式替代实际 SQL。

| 来源对象 | SQL 中的身份表达 | 关键解释 |
|---|---|---|
| OAO 开户渠道 `C_CHANNELTYPE.CHANNEL` | `GKS030-` + `CHANNEL` | 来源已为 OAO，身份仍保留 GKS030 |
| AUM 普通/特殊/打折引流渠道 | `CRM049-` + `CHANNEL` 或 `YLQD1` | 三条来源共用旧 CRM 命名空间，并通过排除规则补齐 |
| 金纽带银行组织 `M_UNION_ORG.ID` | `GKS032-` + `ID` | 银行组织作为渠道对象，不等同内部机构编号 |
| 网店 `G_SHOP.ID` | `WOS018-` + `ID` | 店主另用用户编号 |
| 直播间 `W_ROOMS.ID` | `WOS007-` + `ID` | 源直播间编号用于部分下游组合与活动连接 |
| 运营位 `BUSICODE` | `MIO054-` + `BUSICODE` | 与 MIO014 来源的运营位保留两个命名空间 |
| 智能体应用 `P_APPS.ID` | `LLM013-` + `ID` | 租户用户使用另一套 `LLM014-` 编号 |
| 企微二维码 `SOURCE/SUB_SOURCE` | `WCM028-` + `SOURCE` + `-` + `SUB_SOURCE` | 是复合来源键；企微应用 WCM032 又是另一类对象 |
| 结算分发 `CHANNEL_ID` | `CSO019-` + `CHANNEL_ID` | 下游解析路径仍需分发专有表 |

上表是已读来源的表达，不是全平台唯一性证明。对应 SQL 见[来源交叉矩阵](../资料/来源与对象交叉矩阵.md)。源编号本身还可能是一条分类匹配模式：`t08_gks_chan_info.Mode='like'` 的下游用 `rlike` 匹配 `Src_Chan_Id`，不能把它一概理解为一个真实开户入口的唯一编号。

## 3. 类别、类型、平台分类各回答什么

| 维度 | 例子 | 回答的问题 |
|---|---|---|
| `Chan_Cate_Cd`，CD1412 | 01 金钥匙开户渠道、10 AGENT 平台应用、16 结算数据分发渠道 | 这是什么种类的渠道对象 |
| `Chan_Type_Cd`，CD434 | 02 APP、05018 直播、0601 企业微信、08001 等运营位分类 | 它呈现为何种入口或更细的业务形态 |
| `Lvl1_Cate/Lvl2_Cate/Lvl3_Cate` | 金钥匙人工分类；SIP 销售入口三级分类 | 具体消费体系怎样归类 |
| 平台资产分类 | 渠道信息、信息资产管理、客户服务信息等 | 目录管理怎样给表分类 |

类别和类型是两个代码域，不能将 `Chan_Cate_Cd='02'` 解释为 APP：CD1412 的 02 是金管家引流渠道，APP 是 CD434 的 02。也不能拿平台分类替代行级类别。

字典有某个类别，不代表所有相关行都填写了它。网店主表来源的 SQL 将类别留空；PRD102 应用来源写入类别 02，而该值的字典文字是金管家引流渠道。这种冲突必须保留，不能靠类别值把整个 PRD 来源认成金管家业务。[代码实值与冲突](../字典/类别类型与代码实值.md)

## 4. 三种来源表达

`Data_Src_Cd` 表示数据来源系统；`Src_Tbl` 是当前写入分区；`Real_Src_Tbl` 记录加工中明确声明的真实来源。迁移后的来源可能继续写旧分区，以维持消费接口。

真实例子：62882 从 `ODATA_N_AUM.R_TAPP_CHANNELTYPE` 读入，`Data_Src_Cd='AUM'`，写旧 CRM 来源分区，`Chan_Id` 仍以 `CRM049-` 开头。三个字段不一致有明确 SQL 依据。另一方面，`Real_Src_Tbl` 只是行上声明的主要来源；62891 还连接分类、打折、联动和优先级表，不能只看这个字段就说只依赖一张表。

## 5. 不依赖 Chan_Id 的对象

SIP 销售入口表用业务类型、一级入口、二级入口、来源和业务日期定位。设备表用 `Dvc_Id`；名单中的 `Cust_Id` 需配合 `Cust_Type_Cd`，10 表示手机号，2 表示广发通账号。短信黑名单的 `Chan_Id` 在 SQL 中明确为空，强制内连接渠道主表会丢掉这一分支。

这些是模型设计和加工证据所支持的候选身份。实际唯一性、空值覆盖和多对多程度需业务行数据才能确认，本次没有把字段名中的“编号”当作数据库已验证主键。
