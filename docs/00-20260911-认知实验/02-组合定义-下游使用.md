## 统计口径先说明白

| 名称 | 本文含义 | 不应误读为 |
| --- | --- | --- |
| 消费任务数 | 读取 `dm_index_n.grp_def`，并在固定证据中提取到相关 `grp_type_code` 的任务数；按任务 ID 去重 | 运行成功的任务数、实际产出数据的任务数 |
| 使用任务数 | 某个 schema 内引用某个码值的不同任务数 | 该码值出现了多少次、返回了多少行 |
| 显式码值数 | 某个 schema 内去重后的字面量码值数量 | `grp_def` 中实际存在的类型数量 |
| 关联目标表数 | 这些任务在图中关联到的不同写入目标表数量 | 已确认每个目标字段都由该码值因果影响 |
| 原始命中记录 | 固定证据中每一处码值命中的记录；本次共 2,641 条 | 去重后的任务数或码值数 |

统计不按 `FILTER`、`JOIN`、`CASE` 等 SQL 用途拆分：条件过滤、关联条件、投影表达式中的直接字面量都算“使用”。因此同一任务可以同时使用多个码值，各码值的任务数不能相加来推导任务总数。

## 统计来源与限制

- **范围来自图**：先找读取 `dm_index_n.grp_def` 的任务，再按这些任务的写入目标 schema 分组。
- **码值来自发布证据**：读取发布 manifest 固定的 evidence 文件，使用 relation 中带物理字段绑定的 `predicate_tree` 常量，以及绑定表达式中的直接码值比较和类型归一化。
- **本轮没有读取什么**：未读取 `sqlSources` 正文，未重新解析原始 SQL，也未逐个调用平台核对每条 SQL。这样做的好处是统计与发布版本绑定，但不能替代逐任务 SQL 审阅。
- **显式出现不等于实际选入**：即使码值出现在排除条件、关联条件或 `CASE` 表达式中，也计入“使用”；该数字不表示运行时结果包含多少该类型对象。
- **`CLIENT` 要单独理解**：有 13 个 `dm_index_n` 任务将个人／机构客户归一化成 `CLIENT`。本次按“所有用途都包含”的要求计入，但它是表达式中的归一化值，不是平台字典中查到的 `grp_type_code`，也不证明 `grp_def` 当前存有这个类型。
- **动态值不猜**：仍有 6 个任务的 7 处字段对字段比较，没有显式常量。这些引用保留在证据附件的 `gaps` 中，但无法从静态比较得出运行时的全部码值。545 个任务都至少提取到一个显式值，不代表每个任务的动态值也已穷尽。
- **目标表是任务级关联**：某任务读取该码值并写入某表，只能说明该任务与该 schema/目标表存在图上的关联；多输出任务不能因此提升为逐输出确认的因果血缘。
- **测试范围保留**：`dm_om_test`、`dm_otc_test`、`dm_co_test` 和 `temp` 单独展示，不与其他 schema 混合。
