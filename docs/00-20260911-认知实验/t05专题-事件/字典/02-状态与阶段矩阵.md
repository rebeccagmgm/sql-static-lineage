# 状态与阶段：同一个“成功”，究竟成功了什么

**先选业务对象和处理层次，再解释状态码。** 状态字典可以按“受理、复核、业务处理、回访”等含义分组，也可以拆成“执行场景×结果”；但码值列表没有提供前后迁移规则，不能直接画成一条必经流程。

本页使用CD594、CD797、CD758、CD1164、CD109，共58条原码值。来源为本地资产目录，查询日2026-09-14，码值快照`UNVERIFIED`；来源、备注、逐条记录业务日期保存在[原值附件](重点代码域原值.md)。分组列为本专题阅读整理，不是新增状态字段。

## 2. NBO受理：按办理环节读23种状态

CD594 `ACPT_STAT_CD`中的NBO记录来自`ODATA_N_NBO.U_SYSDICTIONARY`，`dict_entry=1000002`，记录业务日期均为2026-08-21。

| 阅读分组 | 原代码与原含义 | 读者应分清的问题 |
|---|---|---|
| 受理 | `0` 受理中；`1` 受理成功；`2` 受理取消 | 受理层的结果，不等于后续业务处理结果 |
| 复核 | `3` 复核中；`4` 待复核签收；`5` 复核拒绝；`9` 复核驳回；`12` 临柜复核取消 | 待签收、审核过程、拒绝和驳回保留不同原义 |
| 业务处理 | `6` 业务处理中；`7` 业务成功；`8` 业务失败 | 这是受理状态域中的业务处理表达，仍不替代执行表状态 |
| 补正及作废 | `10` 补正后作废；`11` 未补正作废 | 作废前是否补正是两种不同标签 |
| 挽回 | `13` 待挽回；`14` 挽回成功；`15` 挽回失败 | 本地字典未给出哪些业务必须进入此环节 |
| 回访 | `16` 待回访；`17` 回访中；`18` 回访成功；`19` 回访失败 | 回访的成功不等于交易、支付或账户业务成功 |
| 确认与签章 | `20` 已确认；`21` 待企业签章；`22` 待线上电签 | 保留原义；不能仅按代码大小断言先签章再确认 |

这张表可以帮助把“卡住了”具体化为待签收、复核中、处理中或待签章。它没有说明这些状态的转移条件、是否可回退、重试是否新增记录，也没有证明每种业务都会经过全部分组。

**同域中的CC2两条应单列。** CD594还包含`50` 暂存、`51` 异常终止，来源表为`MANU_MATN`，备注明确“CC2受理单表受理状态”，日期2024-05-30。它们属于本域25条的组成部分，但不能因此加入NBO23种状态。`t05_cc2_call_in_acpt_evt`有同名字段，仍需其生产转码证明具体绑定；本次未将元数据同名当成已完成映射。

## 3. NBO执行：同一受理单的另一层状态

CD797 `ACPT_EXEC_STAT_CD`来自NBO字典`dict_entry=1000021`，记录业务日期2026-08-21。任务82077把`EXEC_STATUS`写到执行模型；它与受理主模型使用的`ACPT_STATUS`是两个字段、两个代码域。

| 阅读分组 | 原代码与原含义 |
|---|---|
| 等待与执行 | `0` 未处理；`1` 处理中 |
| 执行结果 | `2` 成功；`3` 失败 |
| 调整或中止 | `4` 延期；`5` 暂停；`6` 停止；`7` 过期 |

例如“受理状态为`1`，执行状态为`1`”按两个域分别解释为“受理成功、执行处理中”。这组含义并不自相矛盾；但本次没有查业务行证明这一组合实际发生过。实际连接需保留受理单坐标及来源，不能直接令两表`Evt_Id`相等。[办理模型与连接说明](../业务/04-业务办理与流程留痕.md)

## 4. DRC审核状态与其他事件状态分开读

| 阅读分组 | 原代码与原含义 |
|---|---|
| 编写与审核 | `1` 草稿；`2` 审核中；`3` 审核通过；`5` 审核不通过 |

## 5. OIS报告：把6个状态拆成场景与结果

CD1164 `VALU_RPT_EXEC_STAT_CD`的6条均为`MANU_MATN`，记录业务日期2024-03-04。以下两列保留原代码与原含义：

| 执行场景（阅读整理） | 成功结果 | 失败结果 |
|---|---|---|
| 一般执行：原文仅写成功/失败，未指明首次生成 | `1` 成功 | `2` 失败 |
| 重新生成 | `3` 重新生成成功 | `4` 重新生成失败 |
| 手动发送 | `5` 手动发送成功 | `6` 手动发送失败 |

这比把1、3、5统一叫“成功”多保留一层业务解释。统计时可以分别讨论执行成功、重新生成成功、手动发送成功；不能把三种次数相加当作客户收到的报告份数。

OIS019的记录身份包含配置相关ID、状态、估值日和更新时间，因此状态不同可能形成不同记录身份。OIS028另有“生成成功”“发送邮件”两个标志，由`TRUE/FALSE`转为`1/0`；它们不是CD1164。两代模型关联、去重和历史报告内容覆盖仍需单独看。[报告案例](../业务/07-报告生成与执行.md)

## 6. RCC成交：同域内也要区分来源

CD109 `MTCH_STAT_CD`有6条。其定义备注指向零售柜台字典条目1213，但不能用这个域级备注覆盖每一条的来源差异。

| 来源分组 | 原代码与原含义 | 日期与适用范围 |
|---|---|---|
| 明确RCC来源 | `0` 成交；`2` 废单；`4` 确认 | 2026-08-21；行备注指向RCC字典`dict_entry=1213`，与37305的`REAL_STATUS`来源相互支持 |
| 人工维护补充 | `21` 撤单；`22` 更新；`23` 应急 | 来源表`MANU_MATN`，来源标记原文`20240109新增`，记录业务日期却为2025-01-09；未据此修正日期，也未证明37305分支会产生这些值 |

成交记录存在、状态含义和最终交割是不同问题。对成交量做筛选时应把适用来源及状态条件明确写出，再核对后续确认、撤销、交割口径。[委托成交与交割](../业务/01-委托成交与交割.md)

## 7. 一个最小判断例子

仅看到数字`1`，可能是NBO“受理成功”、NBO“处理中”、DRC“草稿”、OIS“成功”。因此一条可复核的解释应写成：**某模型的某来源分支，某字段，代码域及来源限定，原代码与含义，记录时点。** 若只拿到同名字段或缺少转码行，就保留待确认；若要判断当前业务结果，再核对业务记录及后续产物。
