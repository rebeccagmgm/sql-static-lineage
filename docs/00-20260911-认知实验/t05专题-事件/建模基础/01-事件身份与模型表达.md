# 事件身份与模型表达

## 1. 为什么不能先找一张“事件总表”

本次 `pdata_n` 的 T05 元数据有 602 条记录，其中 598 条已解析；已解析记录里有 96 条没有名为 `Evt_Id` 的字段。这个统计描述字段名称覆盖，不能据此判断表缺主键或设计错误。期货成交就是一个具体反例：已读 FCT006 SQL 投影成交编号、报单编号、交易日和市场等字段，没有生成 `Evt_Id`。

所以 T05 的共性是围绕业务事项组织记录；并没有得到一项证据，支持把整个主题当作“统一事件 ID + 通用事件类型”的单一实体模型。

## 2. 同叫 Evt_Id，构造含义可以不同

| 模型与来源          | 已读 SQL 的编号规则                                               | 直接影响                 |
| -------------- | ---------------------------------------------------------- | -------------------- |
| 保证金变动 TIT279   | `TIT279-` + `KEY_MRG_LEDGER_ID`                            | 指向一条保证金台账记录          |
| TRS存续事件 TIT229 | `TIT229-` + 事件日 + `KEY_TRS_EVENT_ID` + `KEY_OTC_TRADE_ID`  | 源事件、合约和日期都参与身份       |
| OIS报告执行 OIS019 | `OIS019-` + `ID` + `STATUS` + `VALUE_DATE` + `UPDATE_TIME` | 配置、估值日、状态、更新时间共同区分记录 |
| TA5交易申请        | `TA5-` + 租户 + 申请号 + 申请日 + 销售商 + TA代码                       | 申请号不能脱离所属命名空间        |
| TA5总确认         | `TA5-` + 租户 + 确认流水                                         | 与申请身份不同              |
| BSS客户行为        | `BSS001-` + 去连字符的 `uuid()`                                 | 重加工不能保证同一源行为仍获同一事件编号 |
| OAS流程流转        | `OAS-` + 按 `docid DESC` 生成的 `row_number()`                 | 排名变化可能改变编号；并非源系统固定流水 |

以上是表达式事实，均未实测行级唯一性。将 `COUNT(DISTINCT Evt_Id)` 作为统计规则之前，必须先确定要统计的是源业务、状态版本、生成记录还是采集行。

## 3. 一件业务，六种信息表达

| 表达 | 它回答的问题 | 实例 |
|---|---|---|
| 事项主体记录 | 提出了或发生了哪件事？ | 交易申请、成交、受理单、存续变动 |
| 内部明细 | 这件事具体拆成哪些部分？ | TA确认明细、存续事件结构化腿明细 |
| 关联关系 | 这件事连接另一件事或哪个参与者？ | 结算通知与收付单、事件服务员工 |
| 状态或版本 | 它现在处在哪个阶段，保存了哪次版本？ | 报告执行状态、操作风险事件版本 |
| 金额与变化 | 请求、确认、实际发生分别是多少？ | 申请/确认金额、调整前后本金、操作前后余额 |
| 执行与操作留痕 | 谁执行了什么，结果或异常是什么？ | 报告生成、流程步骤、客户操作日志 |

它们是解释维度，不能和“期货、托管、TIT”混成一组并列分类。

## 4. 用一个小例子检验理解

假设一份申请请求赎回 100 份，之后得到一张确认单，并拆出两条分别为 40 和 60 份的明细。这里的数字是教学假设。

- 申请层回答“请求赎回多少”：100。
- 总确认层回答“确认多少”：100。
- 明细层回答“100怎样拆开”：40 + 60。

将申请、总确认、明细全部相加会得到 300，却没有对应业务含义。连接总确认与两条明细之后，若再次对总确认金额求和，也会把父记录重复两次。这正是 T05 需要首先讲清粒度的原因。

## 5. 模型身份与物理身份各有用途

`Evt_Id` 等字段识别业务记录；`platform + data_source + qualified_name` 区分物理表。二者不可替换。

附件用 `physical_ref` 保留后一种身份的哈希引用，避免暴露内部数据源编号。遇到 `pdata_n`、`spdata_n`、`pdata_nds`、`pdata_hk` 的相近表名，分别核对来源、字段和日期；相同短表名不表示可直接拼接。目录里的 MID/TEMP 对象也要与正式业务记录区分，不能因为名字中含 `mid` 就判成中间表，例如“业务资金中间变动事件”本身是业务含义。
