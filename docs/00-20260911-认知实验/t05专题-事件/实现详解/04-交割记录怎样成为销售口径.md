# 交割记录怎样成为销售口径

任务66277提供了非TIT的直接消费案例：从 `pdata_n.t05_exch_scr_deli_evt`加工到 `pdata_n.t98_cust_prd_sale_info`，再用T02分类补充产品属性。[完整SQL](../../../attachments/04-交割记录怎样成为销售口径/IMG-04-交割记录怎样成为销售口径-20260914110158584.sql)

## 1. 消费者没有把全部交割都当作销售

这份SQL固定取 `2026-05-18`、来源 `ODATA_N_RCC.H_HIS_DERIVDELIVER`，只接受业务标志 `582943`与`582986`，在代码里分别标记 `scrp`和`purch`，渠道写 `OTC`。另有指定产品排除及一项产品与客户组合排除。

这些是任务的实际过滤事实；本次没有从码值库独立验证这两个源业务标志的完整语义，也没有把历史例外名单扩写成现行通用制度。

## 2. 粒度在这一层已经变化

源记录中的产品号通过连字符拆分形成新的长/短产品号，然后按：

```text
当事人 + 机构 + 产品长码 + 产品短码 + 购买方式 + 渠道 + 业务日
```

汇总份额、金额和费用，数值转换为 `decimal(18,4)`。所以T98的一行可以合并多条T05交割记录；销售行数不再等于交割笔数。编号拆分规则也只适用于本分支约定的编码格式，不能推广到含不同连字符结构的产品号。

## 3. T02补充的是分类，不是让交易重新发生

聚合结果以短产品号左连接 `pdata_news_n.t02_scr_type.scr_cd`，分类表限定 `src_id='PRD'`与 `scr_type_std_cd='PRD01'`，将类型及备注转换为产品业务/资产/资管/公私募分类字段。

这一Join发生在金额聚合之后。如果分类表在该条件下同一个产品有多条，金额仍可能被复制；字段和SQL本身未证明唯一性。也不能将这里PRD来源分类与T02专题其他案例的XLA映射混用。

## 4. 从例子得到的认识

T05保留交割事项，下游根据来源、业务标志、例外、产品身份与分类形成“销售”口径。为什么T05明细与销售报表不同，可以先沿这五个条件复核，再检查粒度和Join；不应先认定某一边漏数。
