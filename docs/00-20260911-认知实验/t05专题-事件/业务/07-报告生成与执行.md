# OIS报告：配置、生成、执行与发送

## 1. 配置不是执行，生成不是对方收到

配置说明报告怎样产生、给谁发送；生成记录保存某次生成的结果；执行记录保存状态、时间与失败原因。用户最终看到的是实际文件或邮件内容。模型中的成功状态可以用于解释系统记录，但不代替收件人实际可读的验证。

本次重点读两个模型：`pdata_n.t05_otc_cutp_valu_rpt_exec_evt`与 `pdata_n.t05_otc_deri_send_cust_valu_rpt_create_evt`。不把它们自动当作一对一，也不认定某张表已取代另一张。

## 2. OIS019执行记录：一个配置能留下多种状态记录

源表是 `ODATA_N_OIS.G_VALUE_REPORT_EXECUTION`。SQL将源 `ID`写入 `Valu_Rpt_Cfg_Id`，事件号则拼为：

```text
OIS019-ID-STATUS-VALUE_DATE-UPDATE_TIME
```

它按 `ID, VALUE_DATE, UPDATE_TIME, STATUS`分组，用发送时间倒序取 `row_number()=1`。去重覆盖本次读取窗口中的同组记录，不是“每个配置只保留最新一次”；全目标历史分区中的身份唯一性仍未核验。

读取窗口为调度日向前三个月（含边界），保留源 `Busi_Date`写目标分区。字段分别保存估值日、报告日、定时时间、发送时间、更新时间、文件路径与失败原因。因此统计报告数量、执行尝试数、重新生成次数时，应先选择不同的业务定义。[147451](../../../attachments/07-报告生成与执行/IMG-07-报告生成与执行-20260914110158581.sql)

本地代码域CD1164的记录为：1成功、2失败、3重新生成成功、4重新生成失败、5手动发送成功、6手动发送失败。来源 `MANU_MATN`，记录业务日期 `2024-03-04`，快照状态 `UNVERIFIED`。这些标签保留了生成与发送的区别，不能把1、3、5不加解释地统称为“客户收到报告”。[字典](../字典/README.md)

## 3. OIS028生成记录：源生成号与源配置号分开

源表是 `ODATA_N_OIS.G_VALUE_REPORT_GEN_RESULT`。事件号为 `OIS028-A.ID`，`Src_Create_Id`也是 `A.ID`，`Src_Plac_Id`取 `A.CTPTY_CONFIG_ID`。生成成功和发送邮件两个标志分别由源 `TRUE/FALSE`转为 `1/0`，其他值保留。

SQL还按 `A.ID=B.ID`左连接当天 `G_VALUE_REPORT_API_DATA`，将 `B.VALUE_DATA`作为报告内容。主表回看三个月，内容表只取调度日，所以历史生成记录有没有匹配到内容，需要另查；不能看到模型有报告内容字段就认定历史报告都可读。

这里的配置号与OIS019模型的配置号来自不同源字段。单凭目标字段中文都含“配置编号”，不足以证明它们可以直接相等连接。[169162](../../../attachments/07-报告生成与执行/IMG-07-报告生成与执行-20260914110159756.sql)

## 4. 一个读者可以执行的排查顺序

先确定要查某次生成还是某个配置在某日的执行，再同时看估值日和报告日；失败时读失败原因或告警信息；成功时区分生成标志与发送标志，并检查实际产物。跨表拼报告内容时保留源ID、配置ID和各自时间窗口。

本次没有发送邮件、访问客户报告文件或验证收件结果；专题解释的是已读模型和SQL的记录语义。
