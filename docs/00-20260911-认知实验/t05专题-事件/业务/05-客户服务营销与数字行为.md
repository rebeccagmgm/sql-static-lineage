# 客户服务、营销执行与数字行为

## 1. 三类行为记录要先分开

服务记录描述一件服务事项；数字行为描述用户或设备的一次操作；活动执行描述某个活动流程在批次、节点、用户上的执行情况。三者可能相互触发，但仅凭同一客户或同一天，不能认定因果。

## 2. CRM服务：主体是服务事项

`pdata_n.t05_crm_cust_serv_evt`来自 `ODATA_N_CRM.C_TKHFWJL`。`Evt_Id = CRM028-ID`，客户号 `KH`补至12位进入 `Pty_Id`，营业部 `YYB`补至4位进入 `Inr_Org_Id`。

围绕这条服务记录，模型分别保存服务类别与细分、发起类型、请求渠道、服务人员、发生日期/时间、详细内容、工单号、问卷答题纸标识及回访/录音等线索。这说明一行主要是服务事项，不是客户主档，也不是一通电话或一个问卷答案的通用替代。

该SQL读取 `Busi_Date > date_sub(d,3)`的源分区并按源日期写入；没有在这段谓词中给出上界，不能不加条件地描述为“恰好最近三天”。不同日期重复出现的服务ID是否为更正或重采，需要数据核验。[64594](../../../attachments/05-客户服务营销与数字行为/IMG-05-客户服务营销与数字行为-20260914110158579.sql)

服务事件与服务员工关系也有来源区别：RMS的 `t05_evt_emp_rela_h`使用 `RMS005-SERV-SERID`，并以 `SERV_EMP`说明员工角色，不是CRM事件号。来源内员工映射失败还会保留源员工号。[38361](../../../attachments/05-客户服务营销与数字行为/IMG-05-客户服务营销与数字行为-20260914110159624.sql)

## 3. BSS行为：身份可能每次加工重新生成

`pdata_n.t05_meg_cust_act_evt`接入 `ODATA_N_BSS.F_SENSOR_EVENTLOG`。已读实际写入段落从 `Properties`提取客户、用户、广发通用户、页面、功能、设备等属性，保留源神策编号与源事件类型，按 `SRC_EVT_TYPE + BUSI_DATE`分区。

它的 `Evt_Id`在SQL里调用 `uuid()`生成，而不是取源事件流水。所以跨日或重跑对比时，不能仅用该编号判断“这条行为以前是否发生过”。`Src_Bss_Id`和用户/设备等字段提供进一步追查线索，但本次未证明其中任何组合是业务唯一键。

数字行为中客户号和用户号也可能来自不同属性，不能把“有一个用户标识”直接解释为“已识别为T01客户”。空身份、登录前后识别与客户端重复上报规则尚未核验。[57578](../../../attachments/01-事件身份与模型表达/IMG-01-事件身份与模型表达-20260914110201341.sql)

## 4. MIO活动执行：一行带着活动、批次、节点和用户

`pdata_n.t05_mio_prom_log`来自 `ODATA_N_MIO.FILE_OPERATION_RECORD`。事件号拼入 `FLOW_ID-BATCH_ID-NODE_ID-DT_ID`，活动号使用 `MIO010-FLOW_ID`；还保留节点名、分支、节点数据、最后操作时间、超时时间和统计时间。

因此这里可以先理解为活动流程中的用户节点记录，不是“每行一个完整营销活动”。统计触达客户、执行节点数、活动批次数分别需要不同粒度；`DATA`进入名为 `Node_Date`、注释为“节点数据”的字段，也不能望文生义按日期处理。

本次读到的是业务日固定为 `2026-05-22`的SQL快照，体现当时执行文本，不证明现行定时任务仍固定该日。[84127](../../../attachments/05-客户服务营销与数字行为/IMG-05-客户服务营销与数字行为-20260914110201690.sql)

## 5. 其他服务及数字场景怎样放回全貌

元数据还有呼叫中心受理/回访/答卷、企微聊天与好友变化、直播签到/评价、课程评论、消息发送、AI会话与消息、产品关注、积分与优惠券核销等。应首先区分会话与消息、活动与参与、权益与消费、发送与送达，再分析来源字段。

对这些分支本次保留对象定位，未编造统一转化漏斗。若需要证明“活动带来交易”，还需明确身份映射、触发或归因规则、时间窗口及对照口径；同一用户的事件串并不足以证明活动贡献。
