# TIT 与 OIS：从两套来源读懂 T01，再连接到交易消费

核对日期：2026-09-12。本篇是系统阅读线，跨越主体资料、角色、关系、评价和履保方案；业务概念仍以 01–05 各章为主。优先配合 [交易对手视角](00-20260911-认知实验/t01专题-当事人/视角/交易对手.md) 阅读。

## 1. 先统一名称，再确定学习范围

| 来源代码 | 本地 CD100 中文名称 | 名称证据与边界 |
|---|---|---|
| TIT | 场外衍生品投资管理系统 | 字典备注含 TITANS；记录业务日期 2021-06-18 |
| OIS | OTC综合业务平台 | 字典备注含 OTCISP；记录业务日期 2021-06-18 |

这两项是本地数据源名称。日常称呼“OTC运营管理平台”是否与 OIS 完全对应，本次没有应用注册或页面证据确认，不直接等同。以下均采用有本地证据的名称。

从已核对的 T01 加工看，TIT 提供交易对手参考资料、对手映射、扩展参数和履保方案等；OIS 提供客户主体资料、个人／机构资料、证件、状态、评价和业务扩展资料等。两边存在重叠，不能归纳成“TIT只有交易、OIS只有客户”，也不能据此划定整个应用的最终业务权责。

## 2. 系统视角与业务视角怎么对应

| 学习问题 | TIT 重点入口 | OIS 重点入口 | 对应章节 |
|---|---|---|---|
| 谁是主体，怎样登记？ | 两种交易对手参考表、`TIT060-`编号 | 香港、一般场外、固收等来源分支，部分直接使用 CLIENT_ID | 01 主体公共资料、02 身份与角色 |
| 为什么在两边看起来是同一个客户？ | `D_REF_CTPTY_MAPPING` 及其 T01 关系输出 | 关系另一端对应的 OIS 主体资料 | 03 身份对应与关系 |
| 对手怎么分类、评级？ | 参考资料及扩展参数形成分类、评级记录 | 例如固收来源分支的五种评级 | 04 分类评价与状态 |
| 业务资格和方案是什么？ | `D_MARGIN_PLAN` 履保方案 | OTC客户扩展、引入、报告配置等入口 | 05 业务记录与配置 |
| 下游最终读取什么？ | 合约交易中的对手编号 | 经映射后补充的名称、证件和业务资料 | 本篇第5节 |

## 3. TIT：先看编号、参考表和映射，再看履保方案

### 3.1 同一模型有两条参考表分支

| 本地源表 | 代表任务 | 已核对的 T01 交易对手规则 |
|---|---|---|
| `ODATA_N_TIT.D_REF_COUNTERPARTY` | 105379 / TIT339 | `Pty_Id='TIT060-' + A.ID`；关联 `D_REF_CTPTY_EXT_PARAM` 补充参数 |
| `ODATA_N_TIT.D_REF_COUNTER_PARTY` | 105518 / TIT162 | `Pty_Id='TIT060-' + ID`，直接读取该参考表 |

两者名称仅相差下划线，却是不同来源表，不能当作拼写别名。两份 SQL 都按 `CTPTY_TYPE='INDIVIDUAL'` 写 `190400`，否则写 `290203`；CD002 对应“我司个人关联人”和“自营交易对手”。两份 SQL 的 `Cutp_Cate='TIT_DM'`、`Cutp_Clas_Cd='1'`，后者由 CD389 解释为外部对手。

这也说明业务直觉不能代替字典：源类型为个人，并不意味着这里会写“OTC场外衍生品个人客户”。它实际采用的是另一种登记身份。

两条来源分支构造相同前缀，不证明来源 ID 一定互斥，也不证明目标已完成跨来源去重。消费时继续保留 `Src_Tbl` 和来源范围。

### 3.2 映射表把两套编号连接起来

任务 105079 读取 `ODATA_N_TIT.D_REF_CTPTY_MAPPING`，生成 `T01_PTY_RELA_H` 的关系记录：

```text
TIT060- + KEY_CTPTY_ID  → Pty_Id
OUTSIDE_CTPTY_CODE      → Rela_Pty_Id
01                     → Pty_Rela_Type_Cd（同一个当事人）
210500                 → Rela_Pty_Cate_Cd（OTC场外衍生品对公客户）
```

这是来源维护的身份对应，不是通过名称相似度推出来的。任务 150759 又用相同源映射生成 `T01_SAME_PTY_RELA_ADTNL_INFO`：外部编号写入 `Same_Pty_Id`，来源字段 `OUTSIDE_SOURCE` 写入关系来源，证件、识别原因、有效标志等字段填空。

150759 的开始日取创建时间日期，结束日固定 `2099-12-31`，直接覆盖来源分区。不要把这一附加表的维护方式推广到 `T01_PTY_RELA_H`；它们虽然读同一映射表，目标字段和时间算法不同。

### 3.3 履保方案是一件事，不是一名客户的一组静态属性

任务 200060 读取 `ODATA_N_TIT.D_MARGIN_PLAN`（履保方案表），将 `ID` 写为 `Perf_Marg_Plan_Id`，将 `KEY_CTPTY_ID` 加 `TIT060-` 前缀写为主体号，另保留方案代码、履保协议、大合约、签署日期等。

以下字典可以直接帮助读该任务对应字段：

| 字段／代码域 | 本地定义 | 阅读重点 |
|---|---|---|
| Perf_Marg_Plan_Stat_Cd / CD1692 | `01`生效；`02`审核中；`03`经办人经办 | 状态与源 PLAN_STATUS 有转码及未命中兜底；字典不是流程顺序 |
| Perf_Marg_Plan_Prop_Cd / CD1693 | `SPECIAL`特批；`STANDARD`标准 | 方案属性，不等于额度大小 |
| Perf_Marg_Mode_Cd / CD1500 | `MARKET_VALUE`市值；`NOTIONAL_PRINCIPAL`名义本金；`TRADING`交易型；`LONG_SHORT`多空；另有单边、券抵市值和不启用履保等值 | 说明处理模式；公式和计算范围需要消费逻辑 |
| Mtm_Type_Cd / CD732 | `PORTFOLIO`组合；`SINGLE`逐笔 | 盯市组织方式不同 |
| Jnt_Guar_Type_Cd / CD1695 | `MANAGERS`管理人；`NATURAL_PERSON`自然人；`NONE`无 | 连带担保类型，不证明已经履行担保 |

CD1692、CD1693、CD1695 示例日期为 2025-05-15，CD732 为 2023-05-30；CD1500 记录日期跨 2024-10-31 至 2026-05-22。具体来源和原始备注以资产库记录为准。这些定义解释方案参数，不能推出实际保证金余额、追保金额或现金收付。

## 4. OIS：一个来源对象拆出多类 T01 资料

### 4.1 香港来源是一个完整的入门案例

`ODATA_N_OIS.G_HK_COUNTERPARTY` 被不同任务分别读取，并不是先生成一张 T01 主表，再依次产生所有附表。

| 任务 | 目标模型 | 关注点 |
|---|---|---|
| 144556 | T01_PTY | 主体编号、名称、状态；此分支直接使用 CLIENT_ID |
| 144557 / 144558 | T01_INDV / T01_CORP_CUST | 个人与机构资料分开 |
| 144559 | T01_PTY_IDTY_INFO | 鉴别资料，不能从表名推定每条有多证件 |
| 144560 | T01_PTY_STAT_H | 状态及来源转换 |
| 144561 | T01_PTY_NAME | 当日名称快照 |
| 144562 | T01_OTC_DERI_CUST | OTC业务资料、部门、引入及报告相关字段 |
| 144563 | T01_PTY_CUTP | 对手类别、类型与内外部分类 |

144563 的 `Cutp_Cate='OIS_HK_OPT_DERI'`，`Cutp_Type_Cd=NVL(DW_CD_VAL,CLIENT_TYPE)`，`Cutp_Clas_Cd='1'`。类型可能保留未转换的源值；不能假定全部符合 CD388。144562 新记录的 `Sign_Prd_Name` 固定为空，不能只因下游存在“代签产品名称”列，就认为来源已提供内容。

### 4.2 不要把香港分支当成全部 OIS

本地还找到 `O_OTC_DERIVATIVE_COUNTERPARTY` 一般场外来源，以及任务 179723 使用的固收分支。179723 写入 `Pty_Cate_Cd='210501'`，并按 PI_LVL、RISK_LVL、AML_LVL、CRED_LVL、OTC_CUTP_LVL 形成不同评级记录。反洗钱评级实际取值源与目标分区标签还不同，不能只用分区标签说明所有字段来源。

来源任务也覆盖联系人、引入、同一主体附加关系、受益所有人尽调、估值报告配置等。例如 124884 联系人、149556 同一主体附加关系、149557 受益所有人尽调、147452 估值报告配置。本篇仅将它们作为学习入口，未逐项重新认证全部字段与消费规则。

## 5. 一条实际消费路径：TIT 合约身份怎样补到 OIS 客户资料

任务 123781 输出 `pdata_n.T98_OTC_TRD_COMP_INFO`。本次精读其互换分支，并观察到期权分支也使用相同关系连接形式：

```text
互换合约的 Cutp_Pty_Id
  → T01_PTY_RELA_H.Pty_Id
     限定 Src_Tbl = ODATA_N_TIT.D_REF_CTPTY_MAPPING
     限定 Strt_Date <= 业务日 < End_Date
  → Rela_Pty_Id
  → OIS 来源的 T01_PTY.Pty_Id
     补充个人/机构资料与 T01_OTC_DERI_CUST
  → 合约交易信息输出中的客户资料
```

实际使用条件决定最终结果：

- 关系取有效区间，但该子查询没有额外筛关系类型；不能把“字典存在01”当成下游已经过滤01。
- OIS 主体限定一般场外与香港两个来源，且 `Del_Flag='0'`。
- 机构和个人资料使用 `UNION ALL` 后左连接主体；OTC业务资料在客户资料子查询内部是内连接。
- 合约到映射、映射到客户资料采用左连接：客户资料子查询不成立可能让补充字段为空，不能直接推断整笔合约交易被剔除。
- 机构／个人和OTC业务资料使用表达式 `default.pretradedate(date_sub('{busi_date}',-1),1)` 取日期。本次未核验该函数与交易日历，不直接称为“昨天”。

同一对手若有多条有效映射，或 OIS 客户资料在所选范围内重复，会造成结果扩行。这是静态 SQL 可见的关联风险，当前是否发生需要实际行数据验证。

这条路径解释了为什么两套来源值得放在一起学：TIT 的交易引用身份与 OIS 的客户资料，在实际消费里通过关系模型衔接。它不能反过来证明两套系统在业务上已经实现全部客户同步。

## 6. 推荐阅读顺序

1. 先读香港来源的拆表例子，理解主资料、角色、状态和业务扩展各自存什么。
2. 再读 TIT 编号及两种参考表分支，避免把两个来源表或两套编号混用。
3. 读映射与第5节消费路径，明确两端身份、来源条件和有效区间。
4. 对照 04 的分类／评级字典，再进入 TIT 履保方案，区分评价结果、业务资格和方案参数。
5. 做具体取数时，再沿选定任务核对来源版本、字段转换、日期、删除标志及连接基数。
