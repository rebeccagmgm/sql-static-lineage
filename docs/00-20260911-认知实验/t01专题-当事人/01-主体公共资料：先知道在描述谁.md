## 1. 先用一句话理解

T01 的第一问不是“它发生了什么交易”，而是：

> 这一行数据描述的是哪个业务参与主体？这个主体的编号、来源、类别和时间口径是什么？

因此，主体公共资料应先按下面的顺序理解：

```text
源系统中的一条主体记录
        │
        │ 取源编号、名称、类别、状态、日期等
        │ 生成或转换 T01 语境中的 Pty_Id
        ▼
T01_PTY：主体公共注册资料
        │
        ├── T01_PTY_NAME：主体有哪些名称表达
        ├── T01_PTY_IDTY_INFO：主体用什么证件或识别信息证明自己
        ├── T01_PTY_ADDR_INFO：主体在哪里、如何联系
        ├── T01_PTY_STAT_H：主体状态怎样变化
        ├── T01_PTY_IMP_DATE_H：主体有哪些重要日期
        └── 身份对照表：其他系统的编号是否可能指向同一主体
```

上图表示资料之间的阅读联系，不表示所有附表都从 T01_PTY 加工而来；同一来源可以分别生成这些表。

这些表共享 `Pty_Id` 这个主体编号语境，但不共享“一行代表什么”的粒度。名称可以有多种，证件可以有多个，状态可以有多段历史，地址和联系人也可能分别变化。把它们直接拼成一行，通常会产生重复或错误组合。

## 2. “主体”到底是什么

这里的主体不是“客户”的同义词，而是参与公司业务、需要被识别和管理的一方。它可以是：

- 经纪业务个人客户、机构客户、潜在客户；
- 资管客户、TA、销售商、托管人、管理人、银行；
- OTC 交易对手、PB 客户、投研客户；
- 供应商、外部专家、公司核心人员等其他业务参与方。

所以，看到一条 T01 记录时，不要先问“这是客户吗”，而要先问三个问题：

| 问题           | 对应含义                              |
| ------------ | --------------------------------- |
| 它描述的是谁？      | `Pty_Id` 以及源系统中的主体编号              |
| 它以什么类型出现？    | `Pty_Cate_Cd`、个人/机构等类别信息          |
| 它在什么业务角色中出现？ | 客户、交易对手、托管人、销售商等角色信息，通常还要看专属表或业务表 |

“主体类别”和“业务角色”不能混为一谈。一个机构可能既是客户，又是交易对手；同一自然人也可能在不同业务中有不同的角色。`Pty_Cate_Cd` 只是一个类别代码，不能单独替代完整的业务角色判断。

## 3. 公共资料的核心对象地图

### 3.1 `T01_PTY`：先建立主体的公共注册记录

**主体类别的字典依据已补齐：** `Pty_Cate_Cd` 对应 CD002「当事人类别代码」，本地有 131 个不同码值。它既含对私/对公，也含个人客户、管理人、销售机构等角色及来源业务细分，不能只理解为个人/机构二分。业务解释见 [02](00-20260911-认知实验/t01专题-当事人/02-主体类型与业务参与角色：明确它以什么身份出现。.md)，完整含义、备注和版本统一查 [CD002 附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

已核对的 `T01_PTY` 建表定义包含以下字段：

| 字段 | 中文含义 | 读者应怎样理解 |
| --- | --- | --- |
| `Pty_Id` | 当事人编号 | 当前模型分支中的主体标识；不是天然证明“全平台同一主体”的全球 ID |
| `Pty_Name` | 当事人名称 | 该来源主记录提供的名称，不能替代全部名称历史 |
| `Pty_Cate_Cd` | 当事人类别代码 | 个人、机构、交易对手等类别的代码；具体含义需查码值或任务映射 |
| `Pty_Stat_Cd` | 当事人状态代码 | 该来源主记录中的业务状态；不能与 `Del_Flag` 等同 |
| `Oact_Date` | 开户日期 | 在该来源或该业务口径下的开户/建立日期，不自动等于公司成立日期 |
| `Clos_Date` | 销户日期 | 在该来源或该业务口径下的销户/关闭日期，不自动等于主体消亡日期 |
| `Del_Flag` | 删除标志 | 模型记录生命周期标志；源记录不再出现时，任务可能保留记录并标为删除 |
| `Del_Date` | 删除日期 | 模型识别或写入删除的日期 |
| `Data_Src_Cd` | 数据来源代码 | 任务约定的来源系统代码，如 `TMC`、`TIT` 等 |
| `Task_Name` | 任务名 | 哪个加工任务写入或更新了这条记录 |
| `Data_Etl_Date` | 数据加载日期 | 数据进入数仓的日期 |
| `Data_Upt_Date` | 数据更新日期 | 该记录被加工更新的日期 |
| `Data_Time` | 数据时间 | 任务写入时记录的时间信息 |
| `Real_Src_Tbl` | 真实源表 | SQL 写入的行级来源标签；需要结合 FROM/JOIN 核对，不代表完整字段血缘，也不保证等于 SRC_TBL 分区 |
| 分区 `SRC_TBL` | 源表 | 同一目标表按来源表分开保存，读取时通常应把来源分区一起限定 |

因此，一条 `T01_PTY` 记录更准确的解释是：

> 某个源系统、某张源表、某个处理时间口径下，对一个业务参与主体的公共注册资料投影。

它不是“所有系统合并后的唯一客户主档”。特别是很多任务会把来源前缀编码进 `Pty_Id`，例如：

- TMC 任务使用 `concat('TMC003-', ID)`；
- TIT 名称任务使用 `concat('TIT060-', ID)`；
- IBS、RCC 等来源也有各自的主体编号生成方式。

这说明 `Pty_Id` 在很多分支里带有来源或任务语境。不能因为两条记录名称相同，就把它们的编号直接当成同一个主体；也不能因为编号不同，就断定一定是两个主体。跨来源认定需要看身份对照、证件、名称、业务规则和来源优先级。

### 3.2 `T01_PTY_NAME`：回答“它叫什么”

建表字段包括：

```text
Pty_Id、Pty_Cate_Cd、Full_Name_Ch、Shor_Name_Ch、
Full_Name_En、Shor_Name_En、Data_Src_Cd、Task_Name、
Data_Etl_Date、Data_Upt_Date、Data_Time
分区：SRC_TBL、BUSI_DATE
```

它解决的是名称表达问题，而不是重新定义主体：

- 一个主体可能有中文全称、中文简称、英文全称、英文简称；
- 不同来源可能提供不同名称；
- 名称变更需要通过 `BUSI_DATE`、来源和任务时间观察；
- 某个名称为空，不代表主体不存在，只代表该来源没有提供该名称表达。

这里有一个容易误读的地方：表名和注释常把它称为“名称历史”，但已核对的通用表结构主要通过 `SRC_TBL + BUSI_DATE` 保存每日来源快照，并没有像状态历史表那样直接提供 `Strt_Date/End_Date` 区间字段。因此，不能看到“名称历史”四个字，就直接把它当成已经整理好的有效期拉链表。

### 3.3 `T01_PTY_IDTY_INFO`：回答“凭什么识别它”

建表字段包括：

| 字段组   | 字段                                                                    | 含义                    |
| ----- | --------------------------------------------------------------------- | --------------------- |
| 主体    | `Pty_Id`、`Pty_Cate_Cd`                                                | 证件或识别信息属于谁、主体类别是什么    |
| 类型与内容 | `Idty_Info_Type_Cd`、`Idty_Info_Cont`                                  | 身份证、护照、统一社会信用代码等类型和内容 |
| 签发信息  | `Idty_Info_Addr`、`Idty_Info_Iss_Addr`、`Idty_Info_Iss_Org`             | 证件地址、签发地、签发机构         |
| 时间    | `Idty_Info_Iss_Date`、`Idty_Info_Exp_Date`、`Idty_Info_Insp_Annu_Date`  | 签发、到期、年检日期            |
| 追溯    | `Data_Src_Cd`、`Task_Name`、`Data_Etl_Date`、`Data_Upt_Date`、`Data_Time` | 来源和加工时间               |
| 分区    | `BUSI_DATE`、`SRC_TBL`                                                 | 业务日期和源表               |

一个主体有多个证件时，应允许多行。实际查询时至少要保留：

```text
Pty_Id + Idty_Info_Type_Cd + Idty_Info_Cont + 来源 + 日期
```

这只是阅读时的粒度坐标，不把它宣称为全局正式主键。证件内容也不应在未脱敏、未确认权限的情况下直接展示或用于随意匹配。

### 3.4 `T01_PTY_ADDR_INFO`：回答“在哪里、如何联系”

这张表不是一行一个地址，而是把一个来源提供的主体联系资料包放在一行中。字段可以分成四组：

| 资料组 | 代表字段 |
| --- | --- |
| 居住/联系地址 | `Nationality`、`Prov`、`City`、`Cty`、`Home_Addr`、`Zip_Cd`、`Home_Phone` |
| 办公地址 | `Ofc_Nationality`、`Ofc_Prov`、`Ofc_City`、`Ofc_Cty`、`Ofc_Addr`、`Ofc_Zip_Cd`、`Ofc_Phone` |
| 电子和即时通信 | `Email`、`Web_Addr`、`Fax`、`Qq`、`Wechat` |
| 联系与对账偏好 | `Perm_Cont_Method_Cd`、`Perm_Cont_Freq_Cd`、`Stmt_Send_Freq_Cd`、`Stmt_Send_Way_Cd` |

因此，地址资料的正确问题是“这条来源记录提供了哪些联系资料”，而不是“一个主体只有一个地址”。不同来源、不同日期、办公地址和联系地址都可能形成不同记录。省、市、县区代码还要结合 T06 区域代码解释，不能只凭数字猜中文地名。

### 3.5 `T01_PTY_STAT_H`：回答“状态怎样变化”

状态历史表的关键字段是：

```text
Pty_Id、Pty_Stat_Type_Cd、Pty_Cate_Cd、Pty_Stat_Cd、
Strt_Date、End_Date、Data_Src_Cd、Task_Name、Data_Time、SRC_TBL
```

它表达的是某一种状态类型在某个时间区间内的状态，例如某来源下的客户状态、交易对手状态等。一个主体可以有多种状态类型，也可以有多段状态历史。

要特别区分三件事：

1. `Pty_Stat_Cd`：业务状态，例如有效、注销、暂停等，具体码值要查来源映射。
2. `Strt_Date/End_Date`：该状态记录的有效区间。
3. `Del_Flag`：模型记录是否因源记录消失而被标记为删除。

“状态是注销”不等于“模型行被删除”；“模型行被标记删除”也不等于主体在所有业务中都注销。

### 3.6 `T01_PTY_IMP_DATE_H`：回答“有哪些重要日期”

重要日期表用 `Pty_Imp_Date_Type_Cd` 区分日期类型，并保存：

```text
Pty_Id、Pty_Cate_Cd、Pty_Imp_Date_Type_Cd、Strt_Date、Date、End_Date
```

它适合表达“某主体的某类重要日期”，例如某项备案、报备、资格或业务相关日期。一个主体有多个重要日期时应形成多条记录；不要把 `Date` 误认为所有场景下统一的“开户日期”。`T01_PTY` 里的 `Oact_Date/Clos_Date` 是公共主记录字段，`T01_PTY_IMP_DATE_H.Date` 是按日期类型组织的扩展资料，两者用途不同。

## 4. 这些表怎样拼成“我知道它是谁”

可以把公共资料分为三层：

### 第一层：主体坐标

先锁定：

```text
Pty_Id + 来源分区 SRC_TBL + 业务日期或有效时间
```

必要时再带上 `Pty_Cate_Cd`。这一步回答“当前要查的到底是哪一条主体记录”。

### 第二层：主体基本属性

从 `T01_PTY` 取名称、类别、状态、开户/销户日期、删除标志和来源追溯字段。此时得到的是“这个来源怎样登记它”，不是全平台唯一真相。

### 第三层：主体扩展资料

按问题再去取：

- 想知道别名或中英文名称：`T01_PTY_NAME`；
- 想知道证件和识别信息：`T01_PTY_IDTY_INFO`；
- 想知道联系方式和地址：`T01_PTY_ADDR_INFO`；
- 想知道状态变化：`T01_PTY_STAT_H`；
- 想知道特殊日期：`T01_PTY_IMP_DATE_H`；
- 想判断跨系统编号是否可能是同一主体：ECIF、源系统对照、同一当事人关系等对照对象。

扩展表不能无条件全部 Join。假设一个主体有 3 个名称、2 个证件、2 个地址，直接三表连接就可能产生 12 行组合；这些行并不表示主体真的有 12 份对应关系。

## 5. 源头到 T01：加工到底做了什么

T01 的加工不是简单改一个表名，通常至少包含以下步骤：

```text
读取某源表的某个业务日期
        ↓
过滤源记录、处理空值和源删除标志
        ↓
按来源规则生成 Pty_Id
        ↓
把源类别、状态转换为模型代码
        ↓
统一日期格式和字段名称
        ↓
写入来源、任务、加载时间、真实源表等追溯字段
        ↓
按来源分区做新增、变更、删除或快照覆盖
```

### 5.1 TMC 示例：主表的增量比对

已核对的任务 `PDATA_N.T01_PTY_TMC003` 读取：

```text
ODATA_N_TMC.G_T_AMAC_ACCOUNT_0001
全市场协会机构信息表
```

这个任务做了几件具有代表性的事：

- 用 `TMC003-` 加源表 `ID` 生成 `Pty_Id`；
- 固定写入类别代码 `211003`；
- 用 `PDATA_N.REF_CD_CVT_MAP` 把源字段 `LOGOFF` 转换为 `Pty_Stat_Cd`；
- 把 `BUILD_DATE` 转换为 `Oact_Date`，把 `LOGOFF_TIME` 转换为 `Clos_Date`；
- 以 `Pty_Id` 对比该来源已有分区，将记录分为新增 `I`、变更 `U`、删除 `D`、无变化 `S`；
- 对删除记录不立即物理删除，而是保留并写 `Del_Flag='1'` 及删除日期。

这说明“当事人主表”实际上保留了来源加工痕迹，状态码和日期也可能经过来源专属规则转换。不能把一个 TMC 任务的类别映射复制给 OIS、RCC 或 TIT。

### 5.2 TIT 示例：名称表的来源字段映射

已核对的 TIT 名称任务读取：

```text
ODATA_N_TIT.D_REF_COUNTERPARTY
```

它使用 `TIT060-` 加源 `ID` 形成主体编号，把 `LONG_NAME`、`SHORT_NAME`、`NAME_ABBREVIATION` 映射到名称字段，并根据 `CTPTY_TYPE` 把个人和非个人映射为不同的类别代码。

这个例子说明：名称表也不是统一从 `T01_PTY` 复制出来的。它可以直接从业务源表构造主体编号和名称资料，因此在查询时必须保留 `SRC_TBL`、`BUSI_DATE` 和来源任务，不能默认所有名称都经过同一条主表链路。

## 6. 当前资料、历史资料和删除资料怎么区分

读 T01 时至少要同时看三个时间概念：

| 时间/标志 | 回答的问题 | 常见位置 |
| --- | --- | --- |
| `BUSI_DATE` | 这批来源数据代表哪一天的业务/快照？ | 名称、证件、地址等快照表分区 |
| `Data_Etl_Date` | 什么时候加载进数仓？ | `T01_PTY` 等表字段 |
| `Data_Upt_Date` / `Data_Time` | 什么时候被加工或更新？ | 任务写入字段 |
| `Strt_Date` / `End_Date` | 这条历史记录在哪个区间有效？ | 状态、重要日期、关系等历史表 |
| `Del_Flag` / `Del_Date` | 这条模型记录是否已被来源删除？ | 主体主表及部分业务表 |

所以“取最新”不是一个通用 SQL：

- 快照表通常要按 `BUSI_DATE` 取目标日期或最新分区；
- 历史表通常要按有效区间判断某个时点是否生效；
- 主表还要判断 `SRC_TBL`、`Pty_Stat_Cd` 和 `Del_Flag`；
- 不同来源的“最新”不能直接混在一起排序后取一行，除非已经有明确的来源优先级和合并规则。

## 7. 最容易犯的五个错误

### 错误一：把 `T01_PTY` 当成全平台唯一客户主档

更准确的说法是：它是多个来源按各自规则写入的主体公共资料集合。是否跨来源合并，要看身份对照和业务规则。

### 错误二：只按 `Pty_Id` Join，不看来源和日期

同一目标表可能按 `SRC_TBL` 保存多个来源；名称、证件、地址也有日期分区。只按主体编号 Join，容易把不同来源或不同日期的资料拼到一起。

### 错误三：把 `Pty_Name` 当成唯一、永远正确的名称

它只是主记录中的一个名称。名称多值和变更要看 `T01_PTY_NAME`，正式全称、简称、英文名还要看字段语义。

### 错误四：把 `Pty_Stat_Cd`、`Del_Flag`、销户日期当成同一件事

它们分别描述业务状态、模型记录生命周期和来源日期。三者可能同时出现，也可能不同步。

### 错误五：把所有带 `Pty_Id` 的表都当成“一主体一行”

`Pty_Id` 只是连接到主体的线索，不决定表粒度。证件、评级、联系人、关系、名单、分成和履保方案都可能是一主体多行，甚至还要再按产品、员工、方案或期间展开。

## 8. 读者实际查询时的推荐顺序

遇到“某个客户/交易对手是谁”的问题，可以按这个顺序走：

1. 先确定业务问题和时间点：查当前、某日快照，还是历史时点。
2. 找到来源系统和源表：不要只看任务名里的主题前缀。
3. 确认 `Pty_Id` 如何生成，以及是否带来源前缀。
4. 在 `T01_PTY` 中确认类别、状态、开户/销户日期、删除标志和 `SRC_TBL`。
5. 根据问题选择一个扩展表，不要把所有扩展表一次性连接。
6. 如果要跨系统合并，先查 ECIF/源系统对照/同一当事人映射，再进行业务 Join。
7. 最后才连接 T03 协议、T05 事件或 T98 汇总表，确认下游所需的业务粒度。

一个安全的思维模板是：

```text
我查的是：某来源下、某业务日期/有效时点的某个主体记录
主体坐标是：Pty_Id + 来源分区 + 时间口径
主表告诉我：它如何被登记、分类和标记状态
扩展表告诉我：名称/证件/地址/日期等某一类资料
我还不能据此断言：跨来源一定是同一主体，或这就是所有业务下的最新真相
```

## 9. 本节结论

“主体公共资料”可以压缩成四句话：

1. **先确认描述谁**：`Pty_Id` 只是主体坐标，要连同来源和时间理解。
2. **再确认它怎样被登记**：`T01_PTY` 提供类别、状态、开户/销户和加工追溯。
3. **需要什么再取什么**：名称、证件、地址、状态历史、重要日期分别由不同对象承载。
4. **最后才谈合并和下游使用**：跨来源同一主体、当前有效值和业务汇总都需要额外规则，不能从 T01 前缀或字段名自动推出。

因此，T01 的公共资料更像“主体识别坐标系”，不是一张已经替读者做完所有实体合并、历史裁剪和业务解释的最终宽表。
