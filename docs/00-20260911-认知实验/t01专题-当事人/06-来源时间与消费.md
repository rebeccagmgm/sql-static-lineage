## 1. 一张表为什么会对应几十个任务

一张模型表通常承载多个来源分支。应该从“表名”继续下钻到：

```text
物理对象
  → 来源分支 / 写入分区
    → 本次写入的记录种类
      → 身份构造、筛选、字段映射、时间保存
        → 调度任务及 SQL 版本
```

任务 ID 数既不是来源系统数，也不是独立加工规则数。

| 目标限定名 | 写候选任务 ID 数 | 不同任务名数 | SQL 正文字节指纹数 |
|---|---:|---:|---:|
| pdata_n.t01_pty | 97 | 76 | 76 |
| pdata_n.t01_pty_name | 82 | 61 | 62 |
| pdata_n.t01_pty_rat | 26 | 19 | 23 |
| pdata_n.t01_pty_rela_h | 19 | 17 | 17 |

指纹从 `-- createSql` 标记开始取原文字节，没有消除空白、注释或日期。指纹相同只说明留存正文相同，仍可能有不同调度、参数绑定或运行环境；指纹不同也可能只是留存日期不同。既不能把 97 个任务说成 97 个来源，也不能把它们粗暴合成一个模板。

要合并解释，至少核对：实际读源、输出身份、分区赋值、过滤、展开/聚合、匹配键、码值映射以及更新方式。任务名后缀可帮助定位，不能替代这些条件。

## 2. 身份：Pty_Id 是来源模型的身份合同

`Pty_Id` 的构造因来源而异。原有 OIS 案例直接取 CLIENT_ID，TMC 案例拼来源前缀；本轮 GPB 任务 `128885`/`128887` 则使用 `CONCAT('GPB010-', BROKERID)`，虽然任务名后缀为 GPB026。

因此不能根据任务名机械拼接主体编号，更不能认为 `count(distinct Pty_Id)` 自动等于现实世界去重主体数。跨来源是否能直连，要有明确的身份对应规则；同一个人可能有多种身份，同一编号格式也不能单独证明全局唯一。

GPB 这两个任务都使用 `ROW_NUMBER() OVER(PARTITION BY BROKERID)` 后取 RN=1，**没有 ORDER BY**。这能压缩同一 BROKERID 的记录数，但没有规定冲突记录应选哪一条；不能在正文中写成“取最新资料”。见[差异案例证据：128885、128887](00-20260911-认知实验/t01专题-当事人/证据/差异案例证据.md)。

消费端也依赖这种身份合同：任务 `71118` 从 TA5 分支读取 `T01_PTY`，用 `split(pty_id,'-')[1]` 还原账户标识，再与 TA 交易账户关联。同一任务的 RMS 分支直接用 pty_id。它证明“如何编码”会进入下游 Join 逻辑，编号不能被当作无业务含义的任意字符串。

## 3. 粒度：一行不总是一个主体

| 对象类别 | 应检查的一行内容 | 不能只用什么去关联 |
|---|---|---|
| 主体登记 | 一个来源身份的状态记录 | 仅假设现实主体全局唯一 |
| 名称、证件、地址 | 哪种资料、是否多值、哪一天/哪段期间 | 无条件只用 Pty_Id |
| 分类和评级 | 主体 × 类型，可能还有评级机构、日期或其他维度 | 不筛评级类型只连主体 |
| 主体间关系 | 两端身份 × 关系类型，可能含区间 | 只连一端主体 |
| 方案、材料、业务办理 | 方案号、材料号、事项号及其所属主体 | 把关联主体当作整表粒度 |
| 分配和计量 | 主体 × 人员/机构/席位 × 期间等 | 忽略业务对象与期间 |

这张表是核验顺序，不是凭表名宣告主键。具体例子如下。

### 评级：同一主体可以贡献多种不同记录

任务 `179723` 对 `T01_PTY_RAT` 先 OVERWRITE，再用多个 INSERT INTO 追加，类型包括 `PI_LVL`、`RISK_LVL`、`AML_LVL`、`CRED_LVL`、`OTC_CUTP_LVL`。它将不同评级事实装入共同字段结构；不能把整表描述成“一位客户一个等级”。

`PI_LVL` 经过码值映射并允许回退原值，`RISK_LVL` 直接取风险等级，`AML_LVL` 来自另一张反洗钱风险表。相同 `Rat_Cd` 字段需要结合 `Rat_Type_Cd` 和来源解释。

任务 `104300` 与 `105077` 都写 `OTC_CUTP_LVL`，前者从扩展参数读取并关联主体表，后者从其绑定来源直接读取。两者编号取值点分别是 KEY_CTPTY_ID 与 ID。来源字段、Join 和潜在重复条件并不相同，不能仅凭评级类型相同就判定为可互换分支。

### 关系：多值展开会改变记录数和键

任务 `91801` 把 CIP 客户的基金账户串拆分展开，构造 `TA5001-账户` 与 `CIP001-客户` 两端编号，关系类型为 `01`。随后按展开后的客户、类型、账户分组。

它的新旧匹配键是 `Pty_Id + Pty_Rela_Type_Cd + Rela_Pty_Id`；主体类别在差异比较中，未放入 ON 条件。原 XPB 案例的匹配键还包含主体类别。**同一张关系表也不能用某一个来源的比较键代表全体来源。**

这些条件描述 SQL 怎样维护记录，不证明输入数据没有重复，也不证明现实世界中的同一主体关系已被正确识别。

## 4. 来源：三种标签要分别理解

| 字段/证据 | 回答的问题 | 本轮发现的边界 |
|---|---|---|
| Data_Src_Cd | 模型赋予什么来源代码 | 可沿用业务来源标签，不能仅从库名前缀反推 |
| Src_Tbl | 哪个分支/分区负责保存和更新记录 | 可能是分支归属标签，并非每一行实际取值源 |
| Real_Src_Tbl | 该行被加工代码标注为什么真实来源 | 是 SQL 写入的字段值，不等于自动提取的完整血缘 |
| FROM/JOIN 和表达式 | 数据实际从哪些输入读取、怎样组合 | 临时表、多输入、宏及版本必须继续追踪 |

最直接的反例仍是任务 `179723`：反洗钱评级写入的 Src_Tbl 分区是 `ODATA_N_OOM.F_OTC_DERIVATIVE_COUNTERPARTY`，Real_Src_Tbl 却填 `ODATA_N_OOM.F_AML_DERIV_RISKREP`，该段 FROM 也读取后者。

所以按 Src_Tbl 统计是按分支归属统计；按 Real_Src_Tbl 统计是按行内来源标签统计。即使标签和某一输入一致，也不能代表辅助 Join、码值表以及全部字段来源。两种统计都不应直接称为“真实主体数”。

本轮 JSON 中的 `sourcePartitionLiterals` 只是文本中找到的静态 `src_tbl='...'` 值，不含所有动态宏，也没有绑定到单次写入；它只用于定位分支，不能作为来源全量清单。

## 5. 时间：保存形式与维护算法必须同时说明

| 保存/处理形式 | 必须检查的 SQL | 消费时的意义 |
|---|---|---|
| 当前分支状态 | 新旧如何比较，删除是否保留，重跑如何处理 | 当前内容可能含逻辑删除记录 |
| 日/月快照 | 哪个分区被覆盖，取哪一天输入，是否追加多类记录 | 日期条件决定所取快照 |
| 区间历史 | 新开链、关链、保持、重跑，以及起止边界 | 用明确区间谓词取当时有效记录 |
| 固定起止值全量映射 | 是否每次覆盖，起止值是否仅常量 | 不能因为有起止日期或 `_H` 就说保留了变化历史 |

关系表 `T01_PTY_RELA_H` 是关键反例。任务 `91801` 从开链集合做新旧比较；任务 `76047` 却直接覆盖分支，按管理人信用代码与另一来源的许可证号相等建立关系，并给起止时间固定值 `1900-01-01` / `2099-12-31`。后者没有在该脚本中维护历次关系变化。

因此“这是一张历史表”不足以解释使用方式，必须说明当前来源是持续维护区间，还是把当天映射装入带区间字段的结构。

日期还应区分：来源数据日、目标快照日、业务发生日、模型区间起止、加载/更新时间和 SQL 观测时间。数据库里留有 9 月观测到的 5 月固定日期 SQL，不能据此断言 9 月实际生产执行了哪个日期。

## 6. 两类证据冲突：先保留，不能补猜

### 名称任务的建表段与写入段不一致

任务 `63792` 的 CREATE 段含 Strt_Date、End_Date，SELECT 写入段未输出这两个位置。其 SELECT 明确使用当天来源并输出 BUSI_DATE。

这说明留存脚本的建表说明与加工段不能直接合成可信的字段位置映射。不能仅因 CREATE 中出现区间列，就把这个名称来源归为区间维护；也不能据此认定线上一定列数错误，因为留存 DDL 和实际既有表版本尚未核齐。

### 死亡材料：已找到 SQL 和默认库，目录结构仍冲突

目录记录 42330 对应 `pdata_n.t01_pty_deces_matrl_info`，已解析，但描述为空；字段为 cust_no、cust_name、sex、inr_org_id、mobile 等共 20 列，与本轮 SQL 的材料结构不一致。

任务 `231126` 的 SQL 写未限定库名的 `T01_PTY_DECES_MATRL_INFO`，头部 hiveDb 为空。进一步查到调度详情 `detail.database=pdata_n`，据此补齐默认库并纳入写候选；没有用任务名猜库。这补齐了 163 个可解析对象的限定名覆盖，但仍未证明数据源物理身份及 DDL 版本一致。

该 SQL 明确从死亡材料来源取客户号、一码通账户、材料编号、材料名称和归档日期：可把**这段加工意图**解释为主体相关材料记录（C3）；不能直接给目录记录补上这些字段或宣告二者结构一致。

此前“该对象缺少可解释 SQL”的印象应修正为：**已发现加工证据并补齐默认库，元数据结构仍需核对。**

## 7. 消费：下游实际按什么条件取 T01

已有读取候选分布在 EDW_SUM、DM_INDEX_N、DM_CSTD_N、SEDW_SUM 等多个主题。目录仅帮助定位，具体消费合同需要读 Join 与过滤。

| 人工核对案例 | 实际消费行为 | 对专题解释的影响 |
|---|---|---|
| 63338，账户信息 | RCC 主体分支按客户号 LEFT JOIN；机构客户分支带日期、Del_Flag=0、机构分类，并 INNER JOIN | 不同 T01 表在同一消费任务中承担补充信息与准入筛选两种职责 |
| 71118，TA 账户信息 | TA5 主体编号拆前缀后匹配账户，RMS 分支直接用主体号 | 来源身份格式是下游依赖，不能随意统一重编码 |
| 122891，销售收入 | 名称日快照关联别名区间；席位映射优先，其次全称/简称/别名匹配；再用 ROW_NUMBER 择一 | 名称在该业务里参与身份匹配，存在多匹配及择一规则，不能只说是展示字段 |
| 原 123779，香港对手宽表案例 | 当前主体、日快照客户资料、OTC 分支的日期与删除过滤不同，且混用 LEFT/INNER JOIN | 需要核对各分支基数和筛选，不能由表级连线推出一对一 |

上述案例证明了实际代码中的消费方式；没有查询业务数据验证命中率、重复率或最终金额。尤其是 LEFT JOIN 也可能放大行数，GROUP BY 或 ROW_NUMBER 则可能合并、择一；是否符合业务口径仍需要相应粒度的数据证据。

调度上下游只说明任务依赖配置。任务详情、上下游证据、SQL 的 AVAILABLE，以及静态解析完成，都不能证明数据到达、运行成功或业务验收。

## 8. 怎样查证据、哪些结论还不能下

阅读顺序建议：先用第 1 节找到对象类别，再从[全对象表—任务对照](00-20260911-认知实验/t01专题-当事人/证据/表与任务对照.md)找到候选任务，最后查[本轮差异案例](00-20260911-认知实验/t01专题-当事人/证据/差异案例证据.md)或原始 SQLite 的对应 SQL。全对象导航与细粒度语义是两种交付，不能相互替代。

本轮已完成：

- 对所有 AVAILABLE hive-task SQL 做同口径子句检索，不再限定 22 个样例或单个主题。
- 将 718 个前缀对象及 59 个相关名称逐项列入表—任务对照；同名物理身份未核实时明确标注。
- 核实 1,250 个核心目录任务的 SQL 与调度证据覆盖；保留手工任务缺失项。
- 对 12 个新增差异案例人工核对，修正身份、粒度、来源、时间和消费的解释。

仍未完成的认证包括：每个对象所有来源的字段表达式/匹配键审读；未限定名称与动态宏的全量解析；任务数据源与表目录物理身份对齐；不同快照版本冲突消解；消费基数与业务结果验证。因此，现有研究不能称为“718 个对象逐字段业务验收完成”。

### 检索方法和证据边界

1. 只读 SQLite 的 `evidence`、`horae_task_catalog` 以及表元数据目录，没有访问远端 Wiki，也没有执行业务 SQL。
2. SQL 读取候选复用仓库 `extractSqlReadTableNames`，识别限定名称的 FROM/JOIN 并屏蔽注释、字面量；它是发现工具，不是正式语义血缘。
3. 写入候选扫描屏蔽注释/字面量后的 INSERT INTO/OVERWRITE，仅保留目标末段以 t01_ 开头的名称。未限定名称优先使用 SQL 头部 hiveDb，其次使用任务类型详情中的 hiveDb，再使用调度详情中的 database；不从任务名猜库。最后一步补齐了 63 个任务的默认库，本轮选入写候选已无未限定名称。
4. 不覆盖全部 CTAS、MERGE、动态对象、未限定读取及运行期参数；候选可能漏检，信号字段如 fullOuter/intervalColumns 也只表示脚本中出现，不代表某一目标的维护算法。
5. 表对照按限定名匹配。平台和数据源身份尚未与任务逐项对齐，因此保留目录 ID，不合并同名对象、不生成正式跨任务血缘。
6. [任务读写候选 JSON](attachments/表与任务对照/IMG-表与任务对照-20260914111022611.json)保留 task_id、目录主题、观测时间、SQL 哈希、写入行号及发现信号；[表与任务 JSON](attachments/来源差异与系统核验/IMG-来源差异与系统核验-20260914111024090.json)和[调度覆盖 JSON](attachments/任务覆盖口径/IMG-任务覆盖口径-20260914111022602.json)可复核本文数字。
