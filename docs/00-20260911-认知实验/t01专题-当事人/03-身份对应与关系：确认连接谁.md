# 身份对应与关系：确认连接谁

完整推导与上下文见 [对象层次与关系推导](00-20260911-认知实验/t01专题-当事人/深度分析/对象层次与关系推导.md)，本章按具体业务问题展开。

[返回专题入口](README.md) · [平台分类对照](00-20260911-认知实验/t01专题-当事人/00-平台分类与业务阅读对照.md)

本章把原研究中的身份整合、主体关系、人员关系集中起来。01 建立主体坐标，02 解释角色；这里回答“两个编号怎样对应”和“这个主体与谁、以什么方式关联”。这两种问题不能混成一种关系。

## 1. 平台归属与业务区别

在本次 `pdata_n` 目录观察中，`T01_PTY_RELA_H` 同时挂在“关联人关系信息”和客户模型下的“其他私人关系”；`T01_PTY_EMP_RELA_H` 挂在营销服务的“客户关系信息”。这些是平台目录归属，不能据“私人关系”这一标签断言关系表所有分支都描述私人关系。

SQL 的反例是 CIP 分支：它把 TA 基金账户身份与 CIP 客户身份连接，关系类型为 01。目录可以帮我们找到表，关系含义仍要读具体类型、两端编号和来源。

## 2. 四组对象

| 内容 | 对象入口 | 必须保留的区别 |
|---|---|---|
| 统一身份与来源对照 | `T01_PTY_ECIF_MAP`、`T01_PTY_SRC_SYS_COMPR_INFO`、`T01_SAME_PTY_RELA_ADTNL_INFO` | 对照类型、来源系统、对应编号、日期；不自动等于全平台实体合并 |
| 主体间关系 | `T01_PTY_RELA_H`、代理人及关联关系附加表 | 两端身份、关系类型、方向、有效区间 |
| 主体归组 | `T01_PTY_GRP_H` | 成员关系与主体组定义不同；组编号不是另一位主体的编号 |
| 主体与其他业务对象 | `T01_PTY_EMP_RELA_H`、用户/机构/产品/银行账户关系 | 另一端可能是员工、用户、产品或账户，不都属于 Pty_Id |

主体组还应分开看：`T01_PTY_GRP` 以 `Pty_Grp_Id`、组名称、类型等描述组定义；`T01_PTY_GRP_H` 保存主体与组的成员关系。这里依据既有字段结构解释对象分工，尚未认证成员生产规则与唯一性。投研客户席位中的客户号、席位号和席位使用客户号也属于连接坐标，不应只因带月份就按业绩记录理解。

联系人姓名、任职公司名称等描述字段也不能直接当成已经建立的独立主体关系。应先确认是否存在另一端的可用身份和转换规则。

## 3. 已核对的身份对应机制

| 原研究任务 | 实际作用 | 仍不能宣称什么 |
|---|---|---|
| 63187，ECIF 对照 | 将主体对应到 Ecif_Id、Unif_Cust_Id，中间按外部客户号和系统等维度择一 | 最终仅按主体号与外部客户号关联，不能因此认定跨系统编号唯一或全量映射成功 |
| 148891，来源系统对照 | TARGET_OBJ_ID 与 SOURCE_OBJ_ID 分别形成主体号和对照号，并保存对照类型 | 两个字段不能不看对照类型就任意互换 |
| 150759，同一主体附加关系 | 接入来源维护的交易对手映射；主体号带 TIT060 前缀 | 某些证件、识别原因、有效标志填空，不能说 SQL 已完成独立同人识别和有效性核验 |

这些是[原建模研究第 3 节](00-20260911-认知实验/t01专题-当事人/证据/案例详解与SQL索引.md)中已有案例的重新归并，未在本章重新认证所有来源版本。

## 4. 相同关系表也可能采用不同的记录键和历史算法

[来源分支差异证据](00-20260911-认知实验/t01专题-当事人/证据/差异案例证据.md)中，91801 把一个客户的基金账户串展开，形成多条 TA 身份与 CIP 身份的关联；新旧匹配使用“主体号＋关系类型＋关联主体号”。类别变化作为属性比较。原 XPB 案例还把主体类别放进匹配键，不能用一个来源的键代表整张表。

76047 同样写 `T01_PTY_RELA_H`，却按代码相等建立管理人映射、覆盖分支，并把起止日期固定为 1900-01-01 / 2099-12-31。它没有在该脚本中保留历次映射变化。`_H`、区间字段和真实区间维护算法是三件事。

人员关系也有额外转换：原 RMS140 案例 213009 展开经理列表，通过用户与员工关系转换编号，并以员工号、用户名、原始经理号依次兜底。字段叫 Emp_Id，不保证每条值都已标准化为员工编号。

## 5. 结合 CD178，看清“同一身份”与“不同主体的关系”

2026-09-12 核对本地 `Pty_Rela_Type_Cd` 代码域 CD178，共 34 条记录。下表按阅读用途分组，组名是本文解释；码值含义来自字典。

| 阅读用途 | 代码与含义 | 连接时关注什么 |
|---|---|---|
| 身份对应 | `01`同一个当事人；`02`客户-TA编号 | 两端可能是同一主体的不同编号；还要核对来源身份转换 |
| 联系人 | `04`投研客户联系人与投研客户；`05`当事人与其联系人 | 联系人不自动与客户为同一主体；原文顺序不能替代实际两端字段方向 |
| 控制与组织 | `03`上级当事人；`07`同一控制人；`11`实控人；`13`子公司 | 同一控制人与实控人是不同关系语义；须核对箭头方向和多层关系 |
| 风险关联 | `06`一致行动人；`08`担保关系；`09`共同债务 | 存在关系不代表可合并主体，更不能直接汇总风险敞口 |
| 产品与管理 | `10`同一管理人；`12`同一委托人；`14`母产品 | 同一管理人的产品仍是不同对象；管理关系与身份对照分开 |
| 自然人关系 | `15`夫妻关系；`16`子女关系 | 不适用于所有机构主体，也不自动意味着同一控制关系 |

这些记录来源均为 `MANU_MATN`（手工维护标记）：01 日期为 2021-06-30，02 为 2022-08-01，03 为 2022-10-11，04/05 为 2023-07-27，06–16 为 2024-01-18。06、07 的原始描述带尾空格，阅读表省略，原始明细保留。

结合本章 CIP 案例：虽然处理的是 TA 身份与客户身份，任务 91801 实际写的是 `01`。不能因为字典另有 `02=客户-TA编号`，就将已有 SQL 改述为02；字典提供解释候选，实际采用什么类型由来源加工决定。

完整记录见 [字典附录](00-20260911-认知实验/t01专题-当事人/字典/分类评价关系与名单字典.md)。字典快照为 `UNVERIFIED`；本次补充的是关系类型定义，没有验证业务表里的实际关系、唯一性或身份命中率。

## 6. 关联前写清一句话

> 我连接的是 A 来源中的哪种编号，与 B 来源中的哪种编号；依据什么对照或关系类型，在什么时间范围内成立；两边是否可能各有多条记录。

不要把同名认作同人，不要把有关系认作同一人，不要把调度依赖认作数据关联。实际查询还应保留两端、类型与时间，避免按起点主体去重时丢掉合法的一对多关系。
