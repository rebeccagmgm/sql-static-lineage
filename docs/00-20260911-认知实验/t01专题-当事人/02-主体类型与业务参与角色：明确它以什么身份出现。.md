# 主体类型与业务参与角色：明确它以什么身份出现

完整推导与上下文见 [对象层次与关系推导](00-20260911-认知实验/t01专题-当事人/深度分析/对象层次与关系推导.md)，本章按具体业务问题展开。

> 01 回答“正在描述谁、怎样识别它”；02 接着回答“这个主体具有哪类特征，在什么业务中承担什么角色，这些角色又怎样落到不同的资料表”。同一主体可以有多种角色，每张角色相关表也不一定是一主体一行。

整理日期：2026-09-11。依据本地表元数据、SQLite 留存任务 SQL，以及已整理的本地 Wiki 主题边界。本文以 Hive `pdata_n` 的实现为主；其他库的同名对象不能直接套用这里的字段和编号规则。

## 1. 先区分四个问题

原目录中的个人、机构、资管客户、交易对手、潜客、银行、经纪商、托管人、管理人、销售商、供应商、TA、外部专家等，并不处在同一个分类维度。读这一组表，要先分清：

| 问题 | 含义 | 对象例子 |
| --- | --- | --- |
| 它是什么类型的主体？ | 描述主体自身或来源登记的类型特征 | 个人资料 `T01_INDV`、对公客户资料 `T01_CORP_CUST` |
| 它在什么业务中出现？ | 描述公司或某业务系统怎样与它开展业务 | 资管客户、OTC 客户、投研客户、潜客 |
| 它承担什么参与角色？ | 描述该主体在业务协作中的职责或身份 | 交易对手、托管人、管理人、销售商、经纪商、供应商 |
| 这张表记录的是角色本身，还是角色下的某件事？ | 区分角色档案、关系、配置、网点、资格和业务明细 | 销售商档案、代销资料、销售网点、持牌业务 |

**个人/机构与客户/交易对手并不是二选一。** “个人”可以与“OTC 客户”同时成立；一个机构也可能在不同业务中分别作为客户、交易对手或供应商出现。业务上角色可重叠，不代表当前模型已经把跨来源记录合并成了同一个编号。

银行又是一个交叉例子：“银行”可描述机构类型，但某银行在一笔业务中究竟是托管人、销售商还是账户开户行，还要看具体关系和业务记录。仅凭 `T01_BNK` 中有记录，不能认定这些角色全部成立。

### 1.1 模型实际怎样编码主体类别：CD002

本地字典已明确：`Pty_Cate_Cd` 对应 **CD002「当事人类别代码」**，编码方式为“仓库特有编码”，本次查到 131 个不同代码。[完整码值附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)统一保留字典原文、备注、来源和业务日期。

因此，前面区分“主体类型”和“业务角色”，是在解释业务概念；**现有字段的实际编码已经把主体性质、角色、来源业务语境组合在一起。** 不能把它简单解释成自然人/法人二分，也不必把已有字典明确说明的代码继续当作未知。

|字典中明确存在的类别代码|字典名称|
|---|---|
|100000 / 200000|对私 / 对公|
|110000 / 210000|个人客户 / 对公客户|
|120000|市场交易员|
|190000|其它个人人〔字典原文〕|
|220000|支付机构|
|230000|销售机构|
|240000|登记机构|
|250000|发行管理机构|
|260000|托管机构|
|280000|其它中介服务机构|
|290000|其它机构|

代码名称是字典事实；下列父子层级是据命名和码形归纳的阅读示意，并非查询到了正式父子关系：

```text
对公（200000）
  其它中介服务机构（280000）
    经纪商（280200）
      恒生PB经纪商（280201）
      投易通PB经纪商（280202）
```

不能把“每两位固定代表什么”宣称为正式规则，也不能据此前缀推造不存在的码值。尤其是管理人既有客户语境的 21100x，又有发行管理机构语境的 2501xx；交易对手也跨 OTC 客户与 2902xx 分支。要问的是“该来源将这条身份登记成什么”，而不是“这个现实主体永远只能属于哪一类”。

### 1.2 字典、赋值和真实数据分别证明什么

|证据|可以确认|不能直接确认|
|---|---|---|
|CD002 字典条目|某个仓库代码的登记含义、备注|该代码已被生产任务使用或当前仍有效|
|任务 SQL 的 CASE、常量或转码|该来源如何生成 Pty_Cate_Cd|实际所有结果都命中字典、每条数据分类正确|
|业务数据及身份关联|相应时点有哪些记录、不同身份怎样对应|不能脱离来源和时间直接外推|

已核对的例子：144557/144558 分别赋 110500/210500，128888 赋 280202，204549 赋 290701，对应下文 OTC 客户、经纪商、供应商的字典含义。字典中存在上层概括代码也不证明它只是目录节点、不会被直接写入。

这份字典记录的业务日期覆盖 2021-01-11 至 2026-06-17，快照状态为 UNVERIFIED；本文据实际记录说明含义，不称其为当前线上完整枚举。

## 2. 对象地图：按阅读问题组织，不画成继承树

```text
已经有主体坐标：来源身份 + 编号 + 时间口径
│
├─ 类型资料：个人、对公客户、主体的产品资料
│    看这个身份具有什么类型特征
│
├─ 客户及业务对象档案
│    资管客户、OTC 客户、投研客户、潜客、席位使用客户等
│    看它在某条业务线中怎样被登记、服务和管理
│
├─ 业务协作角色档案
│    交易对手、托管人、管理人、销售商、经纪商、供应商、专家、TA 等
│    看该来源记录了哪些角色专属属性
│
└─ 角色下的明细、关系和配置
     代销资料、网点、持牌业务、合作资料、产品参与方等
     继续确认记录粒度和关系对象
```

这里的连线表示阅读方向。并不要求先有 `T01_PTY`，再由它生成所有类型表和角色表。实际任务常从同一原始业务来源分别加工主体公共资料、个人/机构资料和业务角色资料。

同样，`T01_CORP_CUST → T01_CSTD_INFO → T01_MNGR_ORG_INFO` 也不是一个上下级链条。后两者不是前者的逐级细分；一个角色档案是否能够与某条机构客户记录关联，需要独立核对身份。

## 3. 第一组：个人、对公客户与产品身份资料

### 3.1 `T01_INDV`：个人有哪些专属属性

**类别代码对照：** CD002 的 110000 是“个人客户”；其业务细分包括 110100 经纪业务个人客户、110300 TA5个人客户、110500 OTC场外衍生品个人客户、111800 投资研究个人客户。它们按业务语境区分，不是一个通用个人代码覆盖全部来源。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

个人资料主要围绕出生日期、性别、国籍、籍贯、个人分类等组织字段。公共资料已经回答“是谁”，这张表继续描述该来源登记的个人特征。

| 字段组  | 代表字段                                                          | 阅读含义            |
| ---- | ------------------------------------------------------------- | --------------- |
| 主体坐标 | `Pty_Id`、`Pty_Name`、`Pty_Cate_Cd`                             | 描述哪个来源身份        |
| 个人特征 | `Indv_Clas_Cd`、`Birt_Date`、`Sex_Cd`、`Nationality`、`Nat_Place` | 该身份的个人分类及基础属性   |
| 保存范围 | 分区 `BUSI_DATE`、`SRC_TBL`                                      | 哪一天、哪个来源分支的个人资料 |

**表的描述范围与来源的入选条件要分开。** 任务 `144557` 并非把所有“看起来像个人”的记录放入表中，而是明确筛选 OIS017 来源的：

```sql
CLIENT_TYPE = 'Individual(PI Confirmed)'
```

随后直接用 `CLIENT_ID` 作为 `Pty_Id`，赋类别代码 `110500`。字典已确认 `110500` 为“OTC场外衍生品个人客户”；这里的 CLIENT_TYPE 筛选仍只是该来源实现，不能推广为全部个人来源的判定规则。

### 3.2 `T01_CORP_CUST`：对公客户有哪些组织属性

**类别代码对照：** CD002 的 210000 是“对公客户”；210100、210500、210600、210700 分别表示经纪业务对公客户、OTC场外衍生品对公客户、投资研究机构客户、PB机构客户。字典说明登记类别，实际哪些来源进入本表仍由 SQL 决定。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

这张表的原始注释是“对公客户”。它包含组织类型、中英文全称/简称、国籍等属性，是理解机构类客户的重要入口，但不应扩大解释成“全部法人和全部非自然人的统一注册表”。

OIS017 的任务 `144558` 与个人分支使用同一来源，筛选条件却是：

```sql
CLIENT_TYPE <> 'Individual(PI Confirmed)'
```

该分支赋 `Pty_Cate_Cd='210500'`，还将来源 CLIENT_TYPE 映射到 `Corp_Cust_Clas_Cd`。

需要把三层含义分开：

- 表名说明这是一份对公客户资料结构。
- WHERE 决定本来源实际把哪些记录放进来。
- 字段中的类别/分类决定这些记录在该模型中怎样被标注。

这个 SQL 条件不是法律主体性质认定规则。CLIENT_TYPE 为 NULL 时，等于和不等于两个条件都不成立，记录不会因为“个人分支没选中”就自动落入对公分支。因此，不能断言个人表与对公客户表必然覆盖全部公共主体，或两者并集一定等于 `T01_PTY`。

### 3.3 `T01_PTY_PRD_INFO`：以主体身份出现的产品相关资料

产品相关主体不能简单塞进“个人或机构二选一”的解释。该表保留 `Pty_Id`，同时记录 `Prd_Type_Cd`、`Src_Prd_Cd`、产品名称、结构、规模及管理人/托管人等信息。

两个已核对的来源展示了差异：

| 任务 | 主体编号 | 实际补充内容 |
| --- | --- | --- |
| `63113`，RCC068 | `CLIENT_ID` | 从客户产品属性中取产品代码、名称、结构、规模，以及产品管理人/托管人的描述字段 |
| `63068`，TA5001 | `CONCAT('TA5001-', C_FUNDACCO)` | 取产品类别和源产品代码，产品名称、成立日期、管理人等大量字段填空 |

因此，这里首先是“某来源主体身份的产品相关属性”。它不是把全量产品主数据统一到了一张表，也不能默认 `Pty_Id = Src_Prd_Cd`。

管理人全称、托管人简称等**描述字段**也不是已确认的主体外键。需要关联独立管理人或托管人档案时，不能直接把这些名称当作对方的 `Pty_Id`。

## 4. 第二组：同一个主体进入不同业务时的档案

### 4.1 `T01_AMS_CUST`：资管客户身份

**类别代码对照：** 资管相关类别并非一个代码：110901/210901 是资管直销柜台个人/对公客户，110902/210902 是资管投资者数据库个人/对公客户，110903/210903 是资管定向产品个人/对公客户。它们是字典分支说明，不代表下方单个任务会使用全部这些代码。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

这张表同时保存 `Pty_Id`、`Ams_Cust_Id`、客户名称、类别、开户/销户日期及地区等字段，目录分区为 `SRC_TBL`。它回答“在这个来源的资管客户管理中，这个身份如何登记”，不是所有资管相关参与方的总表。

任务 `63155` 按来源字段构造不同编号：

| 来源条件 | Pty_Id 构造 |
| --- | --- |
| PROD_CODE 为空，FUND_ACCOUNT 以 98 开头 | `STA001-` + FUND_ACCOUNT |
| PROD_CODE 为空，FUND_ACCOUNT 不以 98 开头 | `TA5001-` + FUND_ACCOUNT |
| PROD_CODE 非空 | `AMS032-` + FUND_ACCOUNT |

这表明同一个资管客户任务可能协调多种编号语境。看到“资管客户”，不能一律给编号加 AMS 前缀；也不能把 `Ams_Cust_Id` 与 `Pty_Id` 当作同义字段。

### 4.2 `T01_PTY_CUTP` 与 `T01_OTC_DERI_CUST`：交易对手视角和 OTC 专属资料

**类别代码对照：** 字典明确 110500/210500 是 OTC场外衍生品个人/对公客户；另有 290200“交易对手”，细分 290201 资管交易对手、290203 自营交易对手、290205 商贸交易对手。所以不能只过滤 2902xx 就宣称已取全交易对手；也不能不核对业务语境就把所有这些代码合并为同一种身份。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

| 表 | 主要问题 | 代表字段 |
| --- | --- | --- |
| `T01_PTY_CUTP` | 这个主体以哪种交易对手身份出现？ | `Pty_Id`、`Pty_Cate_Cd`、`Cutp_Cate`、`Cutp_Type_Cd`、`Cutp_Clas_Cd`、`Mkt_Type` |
| `T01_OTC_DERI_CUST` | OTC 业务还管理哪些专属资料？ | `Pty_Id`、`Pty_Cate_Cd`、`Src_Corp_Nature`、`Prof_Org_Flag`、`Sign_Prd_Name`、`Main_Agt_Id` 等 |

两表目录都按 `SRC_TBL + BUSI_DATE` 保存，但不能据此判断两者内容或来源范围相同。公共交易对手结构与 OTC 专属结构会有重叠字段，实际语义仍取决于来源。

OIS017 的 `144563` 在交易对手表中写 `Cutp_Cate='OIS_HK_OPT_DERI'`，并保留个人/机构类别映射；`144562` 则写 OTC 专属资料。两者都用 CLIENT_ID，但承担的描述职责不同。

由此可以理解一种常见组合：某来源记录既进入个人资料，又进入交易对手及 OTC 客户资料。它们分别说明“个人特征”和“业务角色”，不是三位不同的主体，也不是三张表彼此逐级生成。

专属档案中即便存在协议、权限或代签产品字段，也要核对是否真正赋值。OIS017 任务中 `Sign_Prd_Name` 的注释是“代签产品名称”，该字段填空；字段存在不能证明已完成相关业务登记，更不能代表当前允许开展所有交易。

### 4.3 `T01_PCUS_INFO`：潜客阶段的来源身份

**类别代码对照：** CD002 中，190500 为“潜在客户”，190502 为“潜在客户(客户旅程商机)”；另有 290500“对公潜在客户”。不能把所有潜客都套用手机号身份，下方 MIO058 是具体来源案例。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

潜客是业务接触和转化阶段的描述，不是个人/机构之外的第三种主体自然类型。

任务 `175394` 使用：

```sql
CONCAT('MIO058-', MOBILE_NO) AS Pty_Id
```

姓名、年龄、开户进入标志、当前开户步骤和渠道等来自标签 JSON。它保存的是该来源下按手机号组织的潜客资料，不能假定已经取得正式客户号。

因此，从“潜客”转为“正式客户”不能靠把角色标签换掉来解释。还需要找到潜客编号与客户编号的对应证据，并核对转换时间；手机号构造的编号也不证明一个手机号永久对应一个自然人。这里仅解释编号表达式，不展示实际手机号。

### 4.4 其他业务专属档案

以下对象在本地目录中可定位。本节依据字段和注释说明导航位置，尚未逐一审读其全部来源 SQL。

| 对象 | 应回答的业务问题 | 必须进一步区分 |
| --- | --- | --- |
| `T01_RMS_CORP_CUST`、`T01_RMS_IDNV_CUST` | 投研业务怎样管理机构及个人客户？ | 投研客户类型/级别与通用主体类别不同 |
| `T01_RMS_FRGN_CUST_DET` | 海外客户明细怎样对应投研客户？ | 表中同时有 Pty_Id 与 Rms_Cust_Pty_Id，不能抹成同一编号 |
| `T01_SEAT_USE_CUST`、`T01_CSS_SEAT_USE_CUST` | 哪个主体作为席位使用客户登记？ | 客户档案与具体席位使用关系分开 |
| `T01_FUTR_OPT_IVSTR_INFO`、`T01_SGE_CUST_INFO`、`T01_XSM_FND_IVSTR_INFO` | 在期货期权、金交所、基金等来源中如何登记投资者/客户？ | 来源客户类型、交易所客户号、席位号并非公共主体号的同义词 |
| `T01_GLM_CUST_ADTNL_INFO`、`T01_GFSM_CUTP_ADTNL_INFO` | 租赁客户、商贸交易对手有哪些业务附加信息？ | 角色字段、业务类型、客户号与主体号分别解释 |

`T01_STRG_CUST_BUSI_INFO` 虽然在旧目录的“业务身份档案”组中，但它含业务模块、业务名称和明细业务日期，应按具体业务记录继续识别粒度，不能因包含“客户”二字就当作纯角色主档。

## 5. 第三组：银行、经纪商、托管人和管理人

### 5.1 `T01_BNK`：银行资料，不等于所有银行相关关系

**类别代码对照：** 220000 的字典名称是“支付机构”，其细分包括 220100 三方存管银行、220400 银行联行号、220600 席位托管银行信息。托管角色又有 260102 资管托管行、260103 结算交收托管行。银行相关记录可以处于不同代码分支，不能把“银行”和“托管人”直接画等号。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

银行资料包含 `Pty_Id`、`Pty_Name`、`Bnk_Type_Cd`、`Inr_Org_Cd` 及服务时间等结构，分区为 `SRC_TBL`。

任务 `123799` 用 `CONCAT('GBE002-', LHH_NO)` 构造主体号，来源为银行联行号相关记录；`Bnk_Type_Cd` 在该分支填空。因此：

- 一条银行来源记录不自动等于一个已统一识别的银行法人；需确认源编号描述的是哪一级对象。
- 有银行表记录不证明它是某产品的托管人，也不证明是某客户账户的开户行。
- 查客户银行账户应转向 `T01_PTY_BNK_ACCT_H` 等关系/账户资料；查产品托管方要找产品与托管方的关联证据。

### 5.2 `T01_BROK_INFO`：经纪商作为业务参与方

**类别代码对照：** 280200 的字典含义是“经纪商”，备注明确“包含券商、期货经纪商等”；280201/280202 分别为恒生PB经纪商、投易通PB经纪商。因此下方任务的 280202 含义已有字典支持，不只是依据任务注释推断。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

这张表的主体字段叫 **`Brok_Pty_Id`**，不是统一拼写的 Pty_Id；另有经纪商名称、分类、交易所会员编号及业务参数等字段。

任务 `128888` 使用 `CONCAT('GPB010-', BROKERID)`，与同来源公共主体、名称任务的编号表达式相同。这提供了同来源关联的依据，但还需核对记录时间与去重条件。

该任务对 BROKERID 做 ROW_NUMBER 择一，未设置 ORDER BY；许多会员编号和业务参数填空。不能把建表字段清单当成已经具备的完整经纪商能力清单。

### 5.3 `T01_CSTD_INFO`：托管人角色资料

**类别代码对照：** 260000 是“托管机构”，260100 是“托管人”，260101/260102/260103 分别为托管人-托管估值、资管托管行、结算交收托管行。这些类别帮助确定登记语境，不证明每位托管人都同时持有各业务资格。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

托管人信息保存主体号、机构代码、机构类型、商业银行类型、组织形式、公司性质及控股背景等属性，目录分区是 `BUSI_DATE + SRC_TBL`。

任务 `63222` 用 `CONCAT('CVS048-', FID)` 生成主体号，将 JGBH 写为机构代码，并对机构类型、组织形式、公司性质做码值转换。由此可见，`Pty_Id` 与 `Org_Cd` 不是同一字段，也不应直接把机构代码拿去连接公共主体号。

“托管人档案”回答这位参与方在该来源的属性；“托管了哪个产品”“具有什么持牌业务”“是否获准开展某项业务”分别需要产品关系、`T01_CSTD_LICS_BUSI_INFO` 等资格/业务证据。

### 5.4 `T01_MNGR_ORG_INFO`：管理人角色资料

**类别代码对照：** 管理人需要跨分支理解：211001“资产托管-管理人”、211002“托管5.0-管理人”、211003“管理人综合信息-管理人”按代码形式归入客户相关分支；250100“管理人”、250101“产品户管理人”又出现在发行管理机构相关分支。两者并非自动互斥，也不能仅凭名称相似合并身份。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

管理人信息包含经营状态、管理基金主要类别、实际产品数量、基金规模、组织性质等，目录分区是 `BUSI_DATE + SRC_TBL`。

任务 `99935` 用 `TMC003-` + ID 生成主体号，和 TMC003 公共主体案例采用相同身份表达式。该任务同时保存来源组织性质和转换后的组织性质，并有针对特定来源记录的显式修正规则。这些是来源加工口径，不能拿一个字段覆盖全部来源的组织类型解释。

更关键的是，该分支把 `Acs_Flag`（准入标志）填空。因此，**存在管理人档案不等于已经准入**；档案内有准入字段也不代表每个来源都提供准入状态。

### 5.5 `T01_TMC_CSTD_CO_CUST_INFO`：托管合作客户不是“托管人”的同义词

**类别代码对照：** 字典也保留了这一区别：290300 为“合作客户”，290301 为“托管合作客户”，与 260100“托管人”不同。这是角色语义的对照，不代表本文已确认每个合作客户任务都赋 290301。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

任务 `73085` 从合作客户信息构造 `CMI001-` + ID，保存机构编号、引入机构/人员、合作方式、准入级别和服务级别等。

这张表的重点是“托管合作业务如何管理其客户”。不能因为表名含 CSTD，就把记录主体一律解释为提供托管服务的机构；主体在这个业务中的角色方向必须分清。

## 6. 第四组：销售商、代销、网点和 TA 的完整例子

这一组最能说明为什么“角色存在”与“一行记录什么”需要分开。

| 对象 | 描述层次 | 关键字段或匹配维度 |
| --- | --- | --- |
| `T01_CHREM_PRD_SLER` | 理财产品销售商档案 | Pty_Id、Pty_Name、Sler_Type_Cd |
| `T01_SLER_AGNT_INFO` | 销售商在代销渠道/TA 下的业务资料 | Pty_Id、Agnt_Type_Cd、Ta_No、Agnt_Stat_Cd |
| `T01_SLER_NET_INFO` | 销售商下的网点资料 | Pty_Id、Agnt_Type_Cd、Net_No |
| `T01_TA_INFO` | TA 编号对应的登记资料 | Pty_Id、Ta_Cd、Agcy_Id、Ta_Prd_Type_Cd、状态和控制信息 |

### 6.1 销售商主档：可以按优先规则压成一条来源记录

**类别代码对照：** 销售机构大类为 230000，230100/230200 分别表示 TA5销售商、分TA销售商。与之相关的 TA 采用 240000“登记机构”、240100“TA”的类别语境；销售商和 TA 的关联不能被类别同一化替代。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

任务 `63826` 用 C_AGENCYNO 作为主体号，按该编号执行 ROW_NUMBER，优先取 C_TACODE='87' 的来源记录；还关联另一个来源补销售商名称。

这里的“87 优先”是该任务的显式规则，不是通用销售商定义。同一优先级内的排序也未进一步规定；补名称的 Join 是否唯一，仍需查数据。

### 6.2 代销资料：同一销售商可能对应不同 TA

任务 `63645` 同样以 C_AGENCYNO 作为 Pty_Id，但还写入：

```sql
'TA5' AS Agnt_Type_Cd
CONCAT('RCC065-', C_TACODE) AS Ta_No
```

它维护新旧记录时采用的 ON 条件是：

```sql
A.Pty_Id       = B.Pty_Id1
AND A.Agnt_Type_Cd = B.Agnt_Type_Cd1
AND A.Ta_No        = B.Ta_No1
```

所以不能只用销售商号理解这份代销资料。代销类型、TA 也是已核对分支的记录匹配维度；这段 ON 条件并不是经数据唯一性验证的正式数据库主键。

### 6.3 网点资料：主体号仍指销售商，网点另有编号

任务 `63836` 将 C_AGENCYNO 写为 Pty_Id，将 C_NETNO 写为 Net_No，并保存网点名称、地址和状态。一个销售商可有多个网点，不能把每个网点行都当作一个新的销售商主体，也不能遗漏 Net_No 后假设一对一。

### 6.4 TA：编号体系中的独立参与对象

任务 `63078` 使用 `CONCAT('RCC065-', PRODTA_NO)` 作为 TA 的 Pty_Id，同时把原 PRODTA_NO 保存为 Ta_Cd，并提供名称、状态、销售商代码、产品类别和控制串。

它与代销任务的 Ta_No 使用相同的 RCC065 编码形式，是继续核对关联的依据；仍应核对两边编码值域、来源分区与日期，不能仅凭前缀相同宣布已验证全量匹配。也不能默认一个 TA 编号就等于一个独立法人。

### 6.5 拼表时究竟会发生什么

```text
销售商主档：销售商 S
    ├─ 代销资料：S × TA甲
    ├─ 代销资料：S × TA乙
    ├─ 网点资料：S × 网点1
    ├─ 网点资料：S × 网点2
    └─ 网点资料：S × 网点3
```

这是粒度示意，不是实际数据统计。若只按 S 把两条代销资料与三个网点连接，会出现六种组合；但现有示意并没有证明每个网点都属于每个 TA。因此，应先确定要查“销售商有哪些 TA”“有哪些网点”，还是“某 TA 对应哪些网点”，最后一种问题还需要网点与 TA 的关系依据。

`T01_FND_SERV_CLR_ORG_ADTNL_INFO` 等清算机构附加信息也应按这个原则阅读：机构主体号、结算账户和参与机构等字段描述不同对象，不能全部压成一个“机构身份”。

## 7. 第五组：供应商与外部专家

### 7.1 `T01_SPLR_INFO`：采购协作中的供应商身份

**类别代码对照：** 290700 为“供应商”，290701/290702 分别为外部供应商、内部供应商；下方 PPM005 任务实际赋 290701。它解释的是该来源登记的供应商类别，不自动等于供应商类型字段 Splr_Type_Cd。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

供应商信息有 `Pty_Id`、`Splr_Id`、供应商类型、往来单位及创建/更新时间等。任务 `204549` 用 `PPM005-` + BSBI_SUPPLIER_NO 生成主体号，另将原编号保存为 Splr_Id；该分支还取经营范围、地址和备注。

这里可以明确看到“来源供应商编号”和“模型主体编号”的区别。供应商是与公司开展协作的角色，不应先假定其必然是证券客户。供应商评级则应结合评级表与评级类型解释，而不是把供应商类型直接当信用等级。

### 7.2 `T01_EXT_EPRT_INFO`：专家角色及对客展示资料

**类别代码对照：** CD002 中 190300 为“外部专家”，190301 为“投研外部专家”；联系人则有 190600 及 ECR/投研来源细分。专家、联系人和普通个人客户都有不同登记语境；但字典存在这些代码不证明下方专家扩展表本身一定保存了 Pty_Cate_Cd。 代码及版本见[统一附录](00-20260911-认知实验/t01专题-当事人/字典/CD002当事人类别代码.md)。

专家表使用 **`Eprt_Pty_Id`**，保存专家简介、对客展示名称/简介、任职公司、职位、引入信息及审批状态等。

任务 `98513` 用 `RMS049-` + ID 生成专家编号，筛选 REMOVE_TAG='0'，并排除电话会议和线下专家标识均为 '0' 的记录。因此，它不是源表所有人员的无条件全集。

任职公司名称是描述字段，不等于已解析的公司主体关联；展示名称也不等于法定名称。该任务会保留、转换审批状态，但已查看的入选 WHERE 并没有要求“审批通过”，不能把“专家表中存在”解释成“已获准参加所有业务”。

## 8. 角色怎样判定、怎样关联

### 8.1 先确定希望证明哪一层

| 想表达的结论            | 至少需要什么证据              |
| ----------------- | --------------------- |
| 来源把它登记为某类主体       | 来源字段、类型映射、该分支筛选条件     |
| 来源维护了某种角色资料       | 角色表中的记录、对应来源和时间范围     |
| 它当前可开展某项业务        | 角色资料之外的状态、准入、资格或权限规则  |
| 它在某产品/协议/交易中担任该角色 | 具体产品、协议或事件与主体的关系      |
| 两个来源角色属于同一现实主体    | 身份对应与合并规则，不能仅凭名称或角色相同 |

`Pty_Cate_Cd` 不是唯一入口。已核对来源中，它既承担个人/机构区分，也有银行、经纪商、供应商等来源类别赋值。含义先按 CD002 字典精确查询，再逐来源核对赋值或转码。代码的分层外观可以辅助阅读，但没有明确规范时，不能把位数规则或推断的父子关系当成正式合同。

`Cutp_Type_Cd`、`Org_Type_Cd`、`Agnt_Type_Cd`、`Splr_Type_Cd` 也分别服务不同对象；同样叫“类型”的字段并不是一个公共枚举。

### 8.2 关联前核对四项

1. **编号表达式**：连接的是 Pty_Id、Brok_Pty_Id、Eprt_Pty_Id，还是原始客户号、机构代码、TA 编号？两侧表达式是否对应？
2. **来源选择**：两边应分别取哪个来源分支？有关联不要求分区字符串完全相同，例如销售商档案和网点就来自不同表。
3. **时间选择**：本地目录既有只按 SRC_TBL 保存的角色档案，也有日快照；快照日期不等于源业务角色生效日，不能无条件把当前角色档案用于历史交易。
4. **记录粒度**：一个主体在目标表可能有几个 TA、网点、分类或业务事项？需要保留什么维度、筛选什么条件？

“记录存在”“记录未逻辑删除”“业务状态有效”“具备准入资格”也不是同一件事。不同任务可能保留删除行、转换状态或填空，必须按来源核对。

## 9. 把 01 与 02 连起来理解

以一个来源中的机构身份为例：

```text
01：我知道正在描述谁
    主体编号、来源、名称、证件、地址、时间

02：我知道这个来源怎样看待它
    对公客户资料：组织特征
    交易对手资料：交易对手类型和专属属性
    管理人资料：在管基金和经营资料
    销售商资料：销售渠道和业务配置

后续：我知道它与谁发生了什么
    管理哪个产品、在哪个协议中担任哪一方、发生哪些交易或服务
```

上面是阅读层次，不代表这四类角色一定全部存在，更不代表它们自动共用一个全局身份。角色档案先建立理解入口，具体参与关系再把主体放回产品、协议、账户或事件之中。

读完 02，应能回答：**这一条记录是在描述主体类型、业务角色，还是该角色下的明细；它的身份如何生成，角色在什么来源和时间中成立，还有哪些结论需要关系或准入证据。**
