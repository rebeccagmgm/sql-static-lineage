# 组合定义表：dm_index_n.grp_def

## 一句话

**`grp_def` 是指标体系的公共身份对照表：把不同类型的业务对象转换成统一的 `grp_id`，也供下游将这个 ID 还原为业务编码和名称。**

## 使用理解

这部分补充了 **`grp_def` 如何被下游使用**。结合前面的结果，可以把它理解成一张**统一身份对照表**，有两个方向：

| 使用方向         | 做什么                | 示例                        |
| ------------ | ------------------ | ------------------------- |
| **生产指标、标签时** | 业务标识 → `grp_id`    | 根据客户号和组合类型找到组合 ID         |
| **消费指标、标签时** | `grp_id` → 业务标识、名称 | 把指标中的组合 ID 还原成客户号、机构号或员工号 |

此外，它还承担**筛选作用**：通过组合类型、状态等条件限定对象。使用内连接时，没有匹配定义的记录会被排除，所以它不只是补充名称。

简要说明可以写成：

> **`dm_index_n.grp_def` 是指标体系的公共身份对照表。它将不同类型的业务对象统一映射为 `grp_id`，也帮助下游将组合 ID 还原为业务编码和名称。消费任务还会利用组合类型、状态或有效期筛选记录，因此它同时承担身份映射与结果筛选作用。具体关联条件因任务而异。**

## 最重要的使用笔记

### 1. 组合不一定是客户，更不一定是投资组合

`grp_id` 是平台对象身份，具体是什么对象要看 `grp_type_code`。已查样本包括个人客户、机构客户；本地 Wiki 还有直播组合类型示例。

| 字段 | 怎么理解 |
| --- | --- |
| `grp_id` | 平台统一的组合 ID，不要直接当客户号 |
| `grp_type_code` | 组合对象类型 |
| `grp_val` | 该类型对应的业务标识，如客户、机构或员工编码 |
| `grp_name` | 对象名称 |
| `begin_date / end_date` | 有效区间，使用方式和边界需看具体规则 |
| `status` | 记录状态，是否过滤要核对消费 SQL |

### 2. 映射时要同时理解业务编码与对象类型

从业务数据找到 `grp_id` 时，不能只按 `grp_val` 匹配而忽略类型：同一个编码字符串可能属于不同对象类型。部分 SQL 会将个人客户和机构客户归到共同的客户类型后匹配，这是具体任务的规则，不能推广到其他类型。

### 3. 关联会影响结果，不只是补名称

用 `INNER JOIN` 关联时，没有匹配定义，或类型、状态不符合条件的记录会被排除。因此排查“为什么少了数据”，应检查组合映射是否命中。

如果同一关联条件命中多条定义记录，也可能放大结果。**字段名称和 DDL 不证明唯一性**，还要核对实际数据及有效性规则。

### 4. 多个组合 ID 的角色由具体指标决定

有些多维指标用 `grp_id1 / grp_id2 / grp_id3` 分别关联 `grp_def` 的不同别名，解码客户、机构、员工等维度。

编号不规定角色。不能把“1=客户、2=机构、3=员工”当成全体系固定规则，要看指标定义和对应 SQL。

### 5. 个别任务的转换不等于公共字典规则

存档分析提到的 `8888 → ERP-0` 是特定 SQL 中的编码处理，不表示关联 `grp_def` 就会自动执行这个转换。类型筛选、状态过滤、日期判断也需要逐个场景确认。

## 与相邻表的区别

| 表 | 回答的问题 |
| --- | --- |
| `grp_def`：组合定义 | 这个组合是谁，属于什么类型？ |
| `grp_form_config`：组合筛选公式 | 按什么规则筛选属于组合的持仓？ |
| `grp_hold_relation`：组合持仓关系 | 这个组合关联哪些持仓？ |
| 组合标签结果表 | 这个组合具有什么标签？ |
| 组合指标结果表 | 这个组合的某项指标值是多少？ |

`grp_def` 本身不保存指标值，也不是组合持仓成员清单。以上用于解释体系分工，不表示所有组合指标都必须经过持仓汇总。
