# 来源职责：同一个模型如何容纳不同业务

[返回入口](../README.md) · [按来源系统统计](../资料/来源系统汇总.md)

## 1. 按对象看来源，而不是按系统重建另一套主题

T00的主要入口是项目、任务、档案等对象。来源系统解释这些对象在各业务中的具体含义，不应把对象层级和系统名单混成同一棵树。

| 对象 | 已见主要来源及职责 | 模型入口 | 本次深入的区别 |
|---|---|---|---|
| 项目 | PMS采购补充、IBS投行、GLM租赁、ECR种子基金、CRM激励计划；另有稽核及其他项目来源 | 项目主表、关系历史、来源附加表 | 前缀并不总等于直接来源；项目、客户关系、投资产品各有粒度 |
| 需求与任务 | JIR需求；BPM/OA/IPM业务办理；BDP调度；MIO短信、WCM群发；WAS智能体调度 | 需求快照、任务主表、模板、专属附加表 | 需求日快照、调度配置、流程模板与运行记录分开 |
| 整改 | DRC风险检查来源、ADM稽核来源 | 问题及整改事项 | 状态可来自事项的多条办理记录 |
| 档案与附件 | CC2回访归档、DMS档案管理、TIT S3、OOM附件与OIS客户映射；另有RMS、尽调、入职等 | 档案、附件、关联和管理状态 | 空标识、跨系统同前缀、源合约/客户编号尚需映射 |
| 印章 | BPM流程平台 | 印章及人员/机构关系 | 所属、保管与专管责任不同 |
| 试卷与知识 | RCC柜台评分、CC2回访题库、IBS适当性、CRM问卷；GKS金钥匙、IQA智能应答 | 题库、试卷、评分、知识问题和答案 | 题库类别、试卷版本、评分范围和答案状态维度 |
| 内容集合 | LMS专栏、ESS主题及其他内容来源 | 内容集合及来源附加表 | 内容组织、展示配置与实际学习行为分开 |
| 系统与组件 | ACM配置管理、BDP系统登记/API、ISM系统标识、TIT等功能清单、MIO技能工具 | 系统、应用、API、功能及组件关系 | 登记体系、版本编号、声明调用与执行证据不同 |
| 数据资产 | BDP旧metastore、Atlas的Hive/RDBMS/Kafka对象 | 库、表、字段、分类、标签及关系 | 数字ID、GUID、业务唯一命名和库表名各有用途 |
| 池与策略 | PRD产品中心、TIT券源、XIR自营池、FS2策略 | 池头、池成分、专属配置和策略 | 集合定义、成员类型、当前属性与业务有效期 |

系统中文名称以CD100原值为优先；未命中时保留代码并按具体源对象说明职责。例如LMS和WAS在本次CD100匹配中没有中文原值，不补造正式系统全称。

## 2. 用四组来源交叉理解

**同一表，多来源。** `t00_proj_base_info` 的PMS补缺、IBS投行和其他项目分支，输出共同字段，但ID构造、状态转换和来源覆盖不同。共同字段是统一表达的接口，不表示同质数据。

**同一源，多模型。** TIT券源名称管理同时产生通用池头和场外专属池附加表；CC2档案来源同时产生档案对象及档案事件关系；Atlas字段导出同时供字段资料和字段上下游关系。不能按源表名把这些目标归并为一张表。

**同一业务，多种证据。** 需求、模板、任务配置、运行事件、文件归档分别描述业务生命周期的不同段。任意一个状态为“有效”都不代表其余段已发生或已成功。

**同一目标，两类编号消费。** Atlas表信息以GUID供搜索聚合；DB_TBL组合以旧metastore资料生成库表名。连接身份要服从消费合同，不能拿熟悉的“表名”替换GUID。
