## 1. 先辨认这一行在描述什么

| 表的角色   | 例子                                                                | 一行优先怎样理解                              |
| ------ | ----------------------------------------------------------------- | ------------------------------------- |
| 对象基本资料 | `t00_proj_base_info`、`t00_prd_pool_info`                          | 某来源体系中的一个项目或池；是否唯一还要看源SQL             |
| 来源附加资料 | `t00_seed_fnd_proj_adtnl_info`、`t00_otc_deri_prd_pool_adtnl_info` | 一个对象在某来源中的专属属性；Join可能扩行，不能仅凭“附加”断言一对一 |

| 关系与责任  | `t00_proj_pty_rela_h`、`t00_api_app_rela_h`                        | 两端对象之间某种关系在一段期间内的记录                   |
| 状态历史   | `t00_proj_stat_h`、`t00_knwlg_ans_stat_h`                          | 对象在某一种状态维度下的一个版本                      |

| 对象 | 已见身份构造 | 连接规则及边界 |

## 3. SRC_TBL 不应机械地两边相等

它首先隔离同一模型里的来源分支。Wiki《基本的设计思想》明确说明按来源分区独立写入；已读大量SQL也先限制本来源存量，再与当天来源比对。[Wiki](../证据/Wiki-255522174.json)

但两张有关联的模型表通常由不同源表生产。例如PRD池头来自 `P_CUSTOM_PROD_WAREHOUSE`，池成员来自 `P_CUSTOM_WHS_PROD_REL`。连接时，应分别限制各自的正确来源，再按 `Pool_Id` 和适用类别等身份条件连接；要求两边 `Src_Tbl` 字符串相等反而会丢失关系。

应分别识别：物理身份（平台、数据源、完整表名）、业务来源代码（`Data_Src_Cd`）、来源分区（`Src_Tbl`）、真实源表说明（`Real_Src_Tbl`）和对象编号。OIS050的业务来源写OIS，注释源表是OOM；PMS项目编号带IPM前缀，都是这些维度不能合并的例子。

## 4. 三种“关系”不能混画

| 关系 | 已见表达 | 能说明什么 |
|---|---|---|
| 业务关系 | 项目→客户，档案→事件，试卷→题目 | 对象的参与、归属或组成 |
| 调度依赖 | `t00_task_rela_h` 中 Task_Id→Rela_Task_Id，代码01 | 当前任务依赖某上游任务；不证明读了哪张表或哪一分区 |
| 元数据上下游声明 | `t00_tbl_rela_h` / `t00_tbl_fld_rela_h` | Atlas导出中登记了上下游标识；未包含本项目SQL分区因果证明 |

不能通过“这条边的起止节点都存在”就把声明升级为事实血缘。反过来，SQL没有命中某个字面表名，也不能判定配置关系不存在。
