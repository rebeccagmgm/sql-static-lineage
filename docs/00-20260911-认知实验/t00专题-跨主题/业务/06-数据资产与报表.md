# 数据资产与报表：业务表自身也成为管理对象

[返回入口](../README.md) · [本组字段](../资料/字段/06-数据资产与报表.md)

## 1. 这里的一张表，是被描述的对象

`t00_tbl_info` 的一行描述一张表的元数据，不是那张表的一行业务数据。`t00_fld_info` 描述字段，而不是字段里的客户或交易值。想了解数据地图、分类分级、表字段说明和声明关系时，这一支比简单的表名清单更接近它们的业务来源。

| 层次 | 模型入口 | 管理内容 |
|---|---|---|
| 数据库与存储 | `t00_db_info`、数据库文件存储及各引擎附加表 | 库身份、所属系统、存储及引擎专属资料 |
| 表 | `t00_tbl_info`、Hive/RDBMS/Kafka附加表 | 通用表身份及来源专属元数据 |
| 字段 | `t00_fld_info` | 名称、类型、顺序、说明、代码集、标准与分类分级线索 |
| 关系 | `t00_tbl_rela_h`、`t00_tbl_fld_rela_h`、`t00_tbl_sys_rela_h` | 平台登记的表/字段上下游及系统关联 |
| 分类、标签与说明 | `t00_db_obj_clas_info`、`t00_db_obj_lbl_info`、`t00_meta_use_info`、`t00_meta_user_cmnt` | 对象如何被分类和解释，不等于业务内容已验证 |
| 模型与标准 | `t00_data_mdl_*`、`t00_data_std_*`、制品及版本信息 | 数据设计、标准、版本与管理责任 |
| 报表与访问关系 | `t00_rpt_info`、`t00_bdp_rpt_adtnl_info`、报表用户/机构关系 | 报表对象、附加属性及关联角色 |

## 2. Atlas表与字段怎样落到T00

Hive表分支读取 `FILE_ATLAS_EXPORT_HIVE_TABLE`，只选择 `STATUS='ACTIVE'`，用GUID作Tbl_Id，DB作Db_Id，保留表名、类型、视图HQL和创建更新信息。[113440.sql，36–64行](../证据/SQL/113440.sql)

字段分支从 `FILE_ATLAS_EXPORT_HIVE_COLUMN` 取GUID作Fld_Id，源 `TABLE` 写入 `Tbl_Fld_Id`，保留NAME、TYPE、POSITION、注释，以及CODEID、DATASTANDARDID、分类分级、负责人等。[113442.sql，41–74行](../证据/SQL/113442.sql)

这里 `Tbl_Fld_Id` 的注释叫“表字段ID”，但实际投影值是所属表的标识。要理解它能连谁，应优先看来源表达式；不能只根据字段中文名猜一个新的字段实体。

旧metastore来源还有 `M_TBLS / M_DBS / M_COLUMNS_V2`；RDBMS和Kafka又各有来源分支。GUID和旧数字ID不应混用，当前模型统计必须保留来源身份。

## 3. 两种“表字段关系”要区分

字段属于哪张表，可从字段源对象的 `TABLE` 识别。`t00_tbl_fld_rela_h` 在本次Hive分支中则保存**字段与另一字段之间的上下游关系**：拆分源UPSTREAMS/DOWNSTREAMS，再回查关联字段所属表，输出两端字段ID与表ID。[227291.sql，29–78行](../证据/SQL/227291.sql)

不要把这个关系表误读成“表包含字段”的清单。表级关系 `t00_tbl_rela_h` 同样拆源表的上下游列表；01为下游、02为上游，均相对当前对象。[200740.sql，27–54行](../证据/SQL/200740.sql)

| 所见证据 | 可以回答 | 仍不能回答 |
|---|---|---|
| T00元数据对象 | 平台收录了哪些表和字段、如何描述 | 表里现在有多少真实数据 |
| T00的Atlas关系 | 导出记录声称哪些标识互为上下游 | 具体字段表达式、分区因果、实际运行 |
| 本项目静态SQL/Facts | 在已解析范围内有哪些读写与变换证据 | 当前数据已到达、业务结果正确 |
| T00任务依赖 | 上下游调度约束 | 某次写入究竟被下游哪次读取 |

## 4. 下游已经怎样使用这些资料

`dm_hr_n.search_bdp_table_info` 的SQL将T00通用表信息与Hive/RDBMS附加表按Tbl_Id连接，并各自限定Atlas来源；分类、分级、标签、系统关系先按表聚合后再回连。它需要的中文名、业务唯一命名和认证信息并不全部来自一张通用表。[137827.sql，147–243行](../证据/SQL/137827.sql)

资产目录库中的 `DB_TBL` 组合定义则读取旧metastore来源的T00表、库信息，按Db_Id连接，生成小写 `库名.表名` 作为组合值。这与Atlas GUID不同；定义中的属性主键还登记为TBL_NAME，使用方不能把它直接当全库唯一键。[组合定义原记录](../证据/组合定义消费.json)

这两个例子证明同一套T00元数据有不同消费方式。一个按GUID连接丰富的目录说明，一个生成业务检索键；它们不是一套可互换的身份合同。完整推导见[数据资产实现案例](../实现详解/02-数据资产从Atlas到查询消费.md)。
