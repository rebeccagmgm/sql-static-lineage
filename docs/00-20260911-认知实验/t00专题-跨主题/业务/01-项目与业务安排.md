# 项目与业务安排：把一项安排和参与它的对象分开

[返回入口](../README.md) · [本组全部字段](../资料/字段/01-项目与业务安排.md)

## 1. 项目为什么不等于合同或产品

项目描述一项需要被推进、管理和追踪的安排。它可以处于立项、尽调或准备投资阶段，尚未有已生效合同；一个项目也可以连接多个客户、成员或投资产品。因此，项目不能用合同数量或产品数量代替。

| 模型层次 | 主要表 | 一行要回答的问题 |
|---|---|---|
| 项目公共身份 | `t00_proj_base_info` | 哪个项目、叫什么、属于哪类，源业务代码是什么 |
| 状态及立项 | `t00_proj_stat_h`、`t00_proj_setp_info` | 在什么期间处于哪类状态，立项安排是什么 |
| 参与与责任 | `t00_proj_pty_rela_h`、`t00_proj_emp_rela_h`、`t00_proj_inr_org_rela_h`、`t00_proj_mem_info` | 哪个客户、员工、部门或成员以何种角色参加 |
| 经营资料 | `t00_proj_fin_info`、`t00_proj_purch_info`、`t00_proj_stkhold_info` | 项目的财务、采购项及股东资料，不能都视作项目一行属性 |
| 来源业务扩展 | 种子基金、激励计划、租赁、稽核、股票发行、乾和、GFP等附加表 | 保留各类业务独有字段 |
| 投行业务专属 | `spdata_n.t00_ibs_proj_*`、`t00_ibs_bond_issue_proj_adtnl_info` | 内核、立项、风险排查、重要时点等投行结构 |

48个名称均在[对象目录](../资料/逐表对象目录.md)归位。以下五个案例解释不同的建模理由，不将一个项目系统的口径推广到所有项目。

## 2. 采购来源的 IPM 编号，是补缺逻辑

`t00_proj_base_info` 的PMS分支从采购管理的 `ODATA_N_PMS.G_WT_CGXM` 获取项目，构造 `Proj_Id='IPM-'+XMID`、类别 `PURCH-IPM-PRJ`。先按XMID选择XGSJ最新的一行，再左连同一天IPM立项资料 `P_PMS_LX_JBXX`，只保留 `B.ID IS NULL` 的项目。[62906.sql，36–63行](../证据/SQL/62906.sql)

因此它是**采购侧掌握、但当日IPM立项资料未匹配到的项目补充**。不是把采购全部项目与IPM再重复入库，也不能从IPM前缀倒推其直接来源是IPM。这里 `ROW_NUMBER` 只按修改时间降序；同一项目同一修改时间并列时，未见额外稳定排序。

## 3. 租赁项目怎样连到客户

租赁关系生产从 `ODATA_N_GLM.P_PRJ_PROJECT` 取当天 `DEL_FLAG='N'` 的项目，构造：

- 项目：`GLM012-` + `PROJECT_ID`。
- 客户：非空 `BP_ID_TENANT` 拼 `GLM003-` 前缀；原编号同时保留在 `Src_Cust_No`。
- 关系类别01：主客户，得到CD1146原值支持。
- 创建用户：非空 `CREATED_BY` 拼 `GLM004-` 前缀，它与客户身份不同。

历史比对包含项目、关系类别、源记录ID和客户ID，按左闭右开期间维护。若主客户换人，旧关系闭链、新关系开链，不能把历史所有客户直接Join到当前项目后再统计项目金额。[162666.sql，32–72及130–183行](../证据/SQL/162666.sql)

SQL注释写“投行项目-客户关系”，而实际来源和字段为GLM租赁对象；本稿按实际来源与投影解释，保留注释不准确这一差异。

## 4. 投行项目：记录编号、项目代码和负责人是三套身份

`spdata_n.t00_proj_base_info` 的IBS026分支从 `G_V_TH_PRJ_PROJECT` 取得未删除项目，`SN` 用于拼模型ID，`PROJECTCODE` 写入源项目编号。负责人并非直接写 `PRINCIPAL_ID`，而是通过当天 `I_V_ECRM_FORP_USER.ID` 匹配后取 `ERPID`；状态通过转换表映射，项目类型则保留 `TYPESNODE`。[100819.sql，37–69行](../证据/SQL/100819.sql)

读者因此可以分别回答：模型记录是谁、业务人员看到的项目代码是什么、负责人用哪套工号。尚未核实用户表中每个ID是否唯一；不能把一次LEFT JOIN的代码存在说成负责人覆盖100%。投行内核、风险排查和债券发行附加表已列字段，但本次没有全量精读所有投行来源。

## 5. 种子基金：项目进度不等于产品已经投资

`t00_seed_fnd_proj_adtnl_info` 从ECR种子基金源构造 `ECR069-ROW_ID`，分别保存管理人 `ACC_ID`、绩效系统管理人编号 `ORG_ID`、当前步骤、项目状态、子状态，以及进入观察库、备投库、投资库和赎回库的时间。[145620.sql，49–94行](../证据/SQL/145620.sql)

这些字段是项目推进维度，不能用“进入投资库”直接替代成交或持仓证明。产品侧另有 `t00_seed_fnd_proj_ivst_prd_info`，保存 `Proj_Id/Prd_Id`、产品代码、投资日份额/总资产、预警线与平仓线等；外部编号映射又有独立表。实际统计先决定是在数项目、数拟投产品，还是计算某日真实持仓。

145620还以项目ID左连 `S_CX_SEED_FUND_LAND_PRICE` 取落地对价说明，未见该Join前聚合或去重。若来源有多条对价记录，会出现项目属性扩行的可能；未读取业务数据验证，不宣称实际重复。

## 6. 激励计划：宽字段集不代表每一来源都填满

CRM176行权融资分支给 `t00_inctv_plan_adtnl_info` 写入 `CRM176-ID`，保留证券代码和标的证券；授予价格、授予人数、授予数量、摊销等大量通用字段在这份SQL中显式留空。[125483.sql，93行起](../证据/SQL/125483.sql)

所以空值可能是来源职责差异，不应先判定采集失败。激励对象另表 `t00_inctv_tgt_info` 持有项目、当事人、证券、获授数量及授信额度；解锁期也有独立信息表。项目、计划、参与人和期间各自计数，金额不沿一对多Join重复累加。

稽核、股票发行、乾和、GFP、采购项及其他项目扩展已纳入表和字段目录；本次到达的是整组对象解释与上述代表加工，其他来源的完整生产、角色唯一性和财务消费仍待逐案核实。
