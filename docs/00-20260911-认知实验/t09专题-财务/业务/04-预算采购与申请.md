## 通用申请承载不同业务意图

`T09_BDGT_FEE_APP_DOC` 保存申请编号、名称、预算类型、申请类型、状态、申请机构、预算金额及相关人员。采购申请、报销申请、出差申请和预算调整可以共享通用表达，但各自需要不同的附加内容。CD443 提供这些申请类型的本地码值，不能因为一个分支都是采购就把整张表叫采购申请表。

| 对象层次     | 模型                                                   | 应怎样阅读                    |
| -------- | ---------------------------------------------------- | ------------------------ |
| 通用申请     | `T09_BDGT_FEE_APP_DOC`                               | 提出了什么请求、预算是多少、谁发起、处于什么状态 |
| 业务补充     | 预算调整附加信息与明细、出差附加信息、采购附加信息                            | 同一申请在不同业务里的专用要素          |
| 采购申请明细   | `T09_PMS_APP_DOC_DET`                                | 物资、数量、规格、预算与归属等明细层次      |
| 项目与分包    | `T09_PMS_PROJ_INTVB_INFO / T09_PMS_PROJ_SCONTR_INFO` | 招标项目怎样组织和拆分              |
| 供应商参与及结果 | 报名供应商、供应商报价、中标结果                                     | 参与、报价、中标分别记录，不能由报名推断中标   |
| 审批与关联    | 立项审批、审批关系、申请关系、机构关系、项目关系、分包与明细关系、BPM 关联              | 用明确的两端身份把各层对象连起来         |

## PMS 分支怎样进入通用模型

已读 PMS002 把源申请 `ID` 加上 `PMS002-` 前缀，固定申请类型为 `01`，状态通过转换表映射。联系人和起草人不是把 OA 编号原样当员工号，而是通过在职、删除用户资料中的 OA—ERP 对应补 ERP 编号。

采购明细使用 `PMS004-`，项目分包使用 `PMS011-`。这些前缀表达对象来源，不能拆掉之后把相同尾号当同一对象。分包与申请明细的桥接表保留两端编号，说明需求明细和采购执行组织是不同层次。[身份与状态实现](00-20260911-认知实验/t09专题-财务/实现详解/03-记账单状态与采购身份.md)

## 预算、申请金额和最终记账不是一回事

申请预算说明拟使用额度或预算背景；报价、中标、采购明细和记账金额分别处在不同阶段。当前没有一条已核实链路把所有阶段对应到最后付款、资产卡片及凭证。可以用业务过程理解它们，不能用表名顺序制造端到端血缘。

采购明细 SQL 62909 已展开固定日期；分包关系 SQL 76301 中还出现临时表创建、删除和后续读取的顺序疑点。两者保留原始片段和限制，不能把这些快照直接当作可运行模板。
