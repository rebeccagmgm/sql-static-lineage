# 建模基础：身份、粒度与时间

[返回入口](README.md)

## 1. 先分物理表身份和业务记录身份

物理表至少按 `platform + data_source + qualified_name` 区分。同名 `pdata_n`、`pdata_nds`、`spdata_n` 对象不可串用字段和注释；完整来源身份保存在 [原始元数据](attachments/README/IMG-README-20260914110758878.json)。

业务记录身份则取决于来源和对象。`inr_org_id` 可能是柜台四位码、`ERP-` 加机构代码、OA 的部门 ID、TIT 字典值。`emp_id`、来源档案 ID、`user_id` 又是另一组区别。前缀是来源命名规则的一部分；有映射证据才能跨体系连接。

## 2. 一行究竟代表什么

下表是从字段及已读 SQL 归纳的**粒度候选**，不是数据库已验证主键。

| 表 | 一行首先应当理解为 | 不能直接压缩掉的维度 |
|---|---|---|
| `t04_inr_org` | 一套来源中的机构档案 | 来源、类别及本分支的更新方式 |
| `t04_emp` | 当前加工口径下一个工号的员工记录，含保留的旧工号或删除记录 | 类别、状态、删除标志、旧新号关系 |
| `t04_emp_pos_asgn_h` | 某员工的一条职位分配及其有效版本 | 分配编号、有效期间、主分配标志、源版本编号 |
| `t04_inr_org_rela_h` | 一端机构与另一端的某类关系及其期间 | 关系类型、来源、类别、开始结束日期 |
| `t04_user_emp_rela_h` | 一种系统用户到员工的对应记录 | 用户体系、对应类型、来源、日期与删除语义 |
| `t04_user_role_rela_h` | 用户与角色的一种关系 | 关系类型、模型保存期间、业务授权有效期间 |
| `t04_role_righ_h` | 角色对某类对象的一项权限 | 权限类别、对象类型、对象标识、启用标志及期间 |
| `t04_emp_emp_grp_divd_rati_h` | 员工在团队中某种关系和分成类型的比例 | 团队、成员类型、分成类型、期间 |
| `t04_inr_org_exam_rslt_det` | 某考核方案、期间、对象与因子上的结果记录 | 结果 ID、机构／员工、指标、月份和数据日期 |
| `t04_user_less_score_info` | 来源提供的一条用户课程学习与学分记录 | 用户、课程、学习／获分时间；是否可重复尚未验数 |
| `t04_busi_opty` | 某来源、某日的一条商机档案 | 商机 ID、来源、业务日期；部门和成员另外展开 |

一个员工可能有多个有效角色，一门课程可能有多个学习人；把这两份明细直接按员工拼到一起，会产生乘法扩张。应先固定目标粒度，再分别聚合或明确保留明细。

## 3. 四种时间不能套一个模板

| 时间表达 | 已读例子 | 怎样使用 |
|---|---|---|
| 当前来源分区覆盖 | PAS 机构主表；TIT 部门附加信息 | 不能凭 `data_etl_date` 恢复已覆盖的旧版本 |
| 由模型差异维护的区间 | OA 机构关系；TIT 部门公司关系 | 已读分支用 `strt_date <= d AND end_date > d` 判断开链 |
| 源业务给出的起止日期 | PAS 职位分配；OA 用户员工对应；DIA 分成 | 先核源日期语义和边界，不能自动当成模型拉链 |
| 按日保留的快照或结果 | 商机的 `src_tbl+busi_date`；考核结果的多日期写入 | 先限制快照日期，再看记录内部的业务月份或时间 |

`setp_date/canc_date` 是机构成立注销，`entr_date/leav_date` 是入离职，`vld_strt_date/vld_end_date` 是业务授权期间，`data_etl_date/data_upt_date/data_time` 是加工相关时间。它们并不是一组可互换的日期。

`_h` 仅是命名线索。OA 用户员工对应的 `strt_date/end_date` 直接来自入离职日期；PAS 职位分配读来源历史版本；两者都不能仅凭后缀套用“每天比较、变更开闭链”的说法。

## 4. 来源标签可能延续旧系统

| 已核 SQL | 实际读入 | 写出的来源标签 |
|---|---|---|
| PAS 机构主表 `61476` | `J_HSSORG_ORG` 与 `J_HSSORG_ORG_VER` 当前版本 | `src_tbl=ODATA_N_ERP.A_GF_ORGANIZATION_UNITS_V` |
| OA 机构主表 `61543` | `ODATA_N_IOA.I_GF_DEPARTMENT` | `src_tbl=ODATA_N_OAS.P_GF_DEPARTMENT`，`real_src_tbl` 写 IOA 表 |
| PAS 职位分配 `61524` | `J_HSSEMP_EMPLOYEE_POST` 及版本、前置员工名单 | `src_tbl=ODATA_N_ERP.H_PER_ALL_ASSIGNMENTS_F`，`real_src_tbl` 写 PAS 表 |
| 员工主表 `61645` 的 PAS 分支 | 智慧人力员工档案、分配和状态 | 依员工类型保留 ERP／MMS 来源标签，`data_src_cd=PAS` |

因此“筛 ERP 分区”和“只读 ERP 系统生产的数据”并不是同一个意思。正确做法是同时检查源 `FROM/JOIN`、`src_tbl`、`real_src_tbl` 和 `data_src_cd`。[SQL 索引](00-20260911-认知实验/t04专题-内部机构/证据/案例证据索引.md)

## 5. 实际连接前的最小推导

先写清输出需要的是一个员工、一次任职、一条商机，还是一笔交易。接着逐个说明右表提供什么：例如机构关系提供身份转换，机构主表提供名称，用户关系提供账号，分成表提供比例。

每次连接必须能指出：两端编号怎样产生、属于哪套来源、采用哪类关系、取哪个时间、是否还有多条候选。没有这些证据时，保留缺口，不能用 `DISTINCT` 或任取第一条假装解决。
