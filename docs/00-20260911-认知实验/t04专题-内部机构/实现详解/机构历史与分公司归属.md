## 1. 为什么补读文件缓存

SQLite 中 `61609.sql` 只有最终投影，引用 `result/result_grp2/result_grp3/result_grp4` 却缺少这些 CTE 定义。对应文件缓存的 2026-09-08 采集结果包含完整前置部分，SQL 内业务日期展开为 `2026-07-09`。因此以下结论来自 [IMG-机构历史与分公司归属-20260914110757631.sql](attachments/机构历史与分公司归属/IMG-机构历史与分公司归属-20260914110757631.sql)，不能把较晚采集日说成较新业务数据。

这是同一任务的不同证据形态。其他 40 个样例也做了文件缓存对照，差异记录保存在 [比较结果](attachments/机构历史与分公司归属/IMG-机构历史与分公司归属-20260914110800364.json)，没有覆盖旧证据。

## 2. 第一层：从源版本得到关系期间

源组织版本含机构代码、父机构 ID、一级机构 ID、统一公司编码、财务机构段／部门段和有效起止日期。代码以源组织主表存在、状态满足条件为范围，对普通源结束日加一天，将 `4712-12-31` 转为 `2099-12-31`。

这使关系可以按左闭右开区间读取。例如，**说明性例子**中源期间 `[1月1日,1月31日]` 转为 `[1月1日,2月1日)`；下一段若从 2 月 1 日开始，前后就有可比较的接点。

不同关系怎样找到另一端也不一样：

| 关系 | 另一端来源 | 重要限制 |
|---|---|---|
| `11` 柜台映射 | 统一公司编码取后四位 | 限定机构类型及明确例外名单；源过滤仍要求统一公司编码非空，不能声称所有空值均被财务机构段兜底 |
| `10` 上级机构 | `PARENT_ID` 连另一组织 ID，再取代码 | 此处父机构代码按源结束日倒序取一条，未完整按两端历史区间相交 |
| `18` 一级机构 | `FIRST_LEVEL_ORG_ID` 连当前组织版本 | 与直接父机构不是同一个概念 |
| `21/22` 财务机构段／部门段 | `INSTITUTION_CODE/DEPT_CODE`，拼 `ERP-CO-` 或 `ERP-DE-` | 代码含义有 SQL 注释和表达式支持；本地 CD018 未收录这两个值 |

因此一个历史关系区间不一定意味着两端所有属性也都按历史同时点解释。版本选择是每段 SQL 的具体决定。

## 3. 第二层：把相邻、同内容的关系压成一段

代码按关系两端分组，按开始日期排序，用 `LAG(end_date)` 取上一段结束日；仅当上一段结束等于下一段开始时延续原组，否则开始新组。再按组取最早开始和最晚结束。

继续上面的说明性例子：同一机构持续对应同一个柜台编号，1 月和 2 月两段相接，就可合并成一段；中间存在空档则分开。**这里是相邻期间合并，不是任意重叠区间都做通用并集。** 不能把该算法描述为已经消除了全部重复或时间重叠。

## 4. 第三层：营业部与分公司需要穿过不同层级

关系 `14` 不是简单取 `parent_id`。SQL 先得到父、祖父及更高一层的候选，依机构类型选择分公司层次，同时用 `GREATEST(开始日)` 和 `LEAST(结束日)` 计算候选期间交集，保留开始小于结束的组合。

来源中存在不同级别营业部，因此有的记录直接用父机构，有的需要更高祖先；另有若干总部直属营业部被明确指定到特定分公司。它们是样例代码中的业务规则，不能从树形距离自动推断全部归属。

最后 `result_grp4` 在输出前才给本端 `CODE` 加 `ERP-`。如果只读 SQLite 中最终 `CODE AS Inr_Org_Id`，会误以为它未加前缀，进而误判与关系 `11` 的连接不一致。完整 CTE 消除了这个疑问。

## 5. 回到下游：两条关系各有用途

`61593` 读取 `14` 取得营业部与分公司行政编号，再读取 `11` 把两端转换为柜台编号。前者决定业务归属，后者决定可交付给柜台业务的数据坐标；都使用来源限定和当天有效期间。[消费 SQL](attachments/07-从模型到下游消费/IMG-07-从模型到下游消费-20260914110757601.sql)

该链路已解释到源版本、关系构造、区间处理和消费者。但仍没有验证源版本是否重叠、特殊名单是否现行、源转换表是否一对一，也没有验证当日数据实际落地。上述问题不能由静态 CTE 推导替代。
