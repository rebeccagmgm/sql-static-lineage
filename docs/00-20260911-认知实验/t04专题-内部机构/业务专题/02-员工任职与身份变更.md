# 员工与任职：同一个人不等于一个不变的工号

[返回入口](00-20260911-认知实验/t04专题-内部机构/README.md)

## 1. 员工、档案、任职和账号分别是什么

员工是人事与业务管理中的参与者；工号是模型常用连接坐标；源档案 ID 用来连接源系统的版本和明细；任职分配说明在哪个期间担任什么职位；系统账号则说明通过哪个身份操作系统。这五件事不能只用一个 `emp_id` 表示。

| 对象 | 主要模型表 | 应当理解的粒度 |
|---|---|---|
| 员工共性资料 | `pdata_n.t04_emp` | 工号对应的员工记录，包括状态和来源；存在保留旧号的处理 |
| 姓名、鉴别、地址、分类、状态 | `t04_emp_name_h`、`t04_emp_idty_info_h`、`t04_emp_addr_h`、`t04_emp_clas_h`、`t04_emp_stat_h` | 某类资料或状态在一个期间的记录 |
| 任职分配 | `t04_emp_pos_asgn_h` | 员工的一次职位分配及有效版本 |
| 职位与职务 | `t04_pos_info_h`、`t04_job_info` | 岗位对象及职务定义；与员工当前属性分开 |
| 员工与机构 | `t04_emp_inr_org_rela_h` | 所属机构、OA 叶子节点、费用段或负责人等不同关系 |
| 旧新工号 | `t04_same_emp_new_old_emp_id_merg_info`、`t04_emp_rela_h` | 来源给出的合并或对应关系，不是按姓名去重 |
| 员工与账号 | `t04_user_emp_rela_h` | 一个特定系统身份与员工的对应 |

## 2. 员工主表是加工过的人群

已读 `61645` 不是“把人力源表搬进来”。活跃 SQL 的 PAS 分支把员工主档与当前档案版本连接，再接主分配、人员状态版本、组织和离职记录；按工号对分配开始日期、状态排序取一条。它还过滤无效档案、部分营销范围、根节点／无部门、测试名称及暂停分配，并保留子公司范围的例外。

这说明两件事：源系统里有一条档案，不保证员工主表一定出现；一个工号的展示状态也是加工选择的结果，而非所有源历史的并列列表。[61645.sql，568–699 行](attachments/02-员工任职与身份变更/IMG-02-员工任职与身份变更-20260914110757619.sql)

源文件开头有大量被注释掉的旧 ERP 分支，不能计入当前执行来源。当前 PAS 分支仍将 `emp_cate_cd` 写为 `1/2`，并沿用 ERP／MMS 的 `src_tbl` 标签。字典 `CD012` 的 `1` 名为“ERP员工”，也不能反推真实来源仍是 ERP。

同一任务还从 PPM 读取合作方员工：限定源人员类型，写员工类别 `4`，映射状态，排除明确测试工号。故 `t04_emp` 的覆盖也不等于正式员工在职名册。[61645.sql，517–563 行](attachments/02-员工任职与身份变更/IMG-02-员工任职与身份变更-20260914110757619.sql)

## 3. 旧工号为什么不会自动消失

主表本身无分区定义，`src_tbl` 是普通字段。任务先清理当日加载的旧结果，再把前置名单标为“曾用工号”的记录补回临时结果，并排除已出现的工号。最终将未在新结果中出现的旧记录标为删除，与新结果合并覆盖。[61645.sql，800–955 行](attachments/02-员工任职与身份变更/IMG-02-员工任职与身份变更-20260914110757619.sql)

`t04_emp_frnt` 在这里是人群和当前／曾用号控制对象，不能作为另一类员工实体。`190085` 的 SQL 将当前名单、在职转序列名单、二次入司转序列名单合并后排序取一条，但前置临时名单的构造没有全部包含在这份 SQL 中；本版没有宣称已还原完整人群算法。[IMG-02-员工任职与身份变更-20260914110759402.sql](attachments/02-员工任职与身份变更/IMG-02-员工任职与身份变更-20260914110759402.sql)

独立的合并信息任务 `175778` 用主档 ID 与合并档案 ID 各自连当前版本，取 `Main_Emp_Id/Merg_Emp_Id` 和两端全局识别号，并保留合并类型、状态和标志。源注释明确提示：全局调动下两个档案可能有相同工号而不同 ID。因此 `count(distinct emp_id)` 也不是天然的自然人人数。[175778.sql，29–65 行](attachments/02-员工任职与身份变更/IMG-02-员工任职与身份变更-20260914110802200.sql)

## 4. 任职分配不是“员工当前部门”的同义词

`61524` 的主要投影可概括为：

| 来源／加工 | 模型字段 | 解释 |
|---|---|---|
| 分配主表与所有匹配版本按 `POST.ID=POST_VER.EMP_POST_ID` 连接 | `Src_Pos_Asgn_Id/Src_Pos_Ver_Id` | 保留源分配及版本；此处没有把分配版本限制成当前版本 |
| 源 `REF_ID` 非空优先，否则主表 ID | `Pos_Asgn_Id` | 有兼容旧编号的逻辑 |
| 前置员工名单，当前工号分支 | `Emp_Id` | 源员工档案 ID 经名单换成工号 |
| 岗位当前版本 `CODE` 加 `PAS-` | `Pos_Id` | 职位标识，不能当员工号 |
| 组织当前版本 `CODE` 加 `ERP-` | `Bel_Inr_Org_Id` | 行政机构坐标，虽然真实来源是 PAS |
| `ATTRIBUTE_ID` 加 `PAS021-` | `Job_Id` | 职务坐标，与职位字段分开 |
| 源 `MAIN_FLAG` | `Pri_Asgn_Flag` | 是否主分配；查询单一主岗时必须考虑 |
| 源 `EFFECT_START_DATE/EFFECT_END_DATE` | `Strt_Date/End_Date` | 任职业务有效期间 |

任务通过 `UNION ALL` 另外处理曾用工号，所以不能只读第一段就说所有任职都只归当前工号。它对岗位和组织取当前名称／代码版本，分配却保留历史版本；因此“历史任职 + 当前组织解释”可能出现在同一记录中，不能直接当成历史组织全貌。[61524.sql，114–364 行](attachments/来源表与模型映射明细/IMG-来源表与模型映射明细-20260914110805436.sql)

## 5. “所属机构”必须带上关系类型

`CD183` 中 `10` 为员工所属内部机构，`11` 为所属 OA 叶子节点，`13/14` 为费用公司段／费用部门段，`15` 为部门负责人（分配、薪酬相关），`17` 为部门负责人（发文）。这些关系回答不同问题，不能只按员工号拼出一个“部门”。[关系字典](00-20260911-认知实验/t04专题-内部机构/字典/关系与权限.md)

后续员工宽表实际区分行政归属、费用段、负责人和 OA 显示字段，并对部分 PAS 历史取“截至当天的最近记录”，而非统一过滤仍有效区间。若重建报表要与原宽表一致，就必须复现这些选择。[消费详解](00-20260911-认知实验/t04专题-内部机构/07-从模型到下游消费.md)

## 6. 跨库分支也有实际业务范围

`pdata_nds.t04_emp_mms` 不是 `pdata_n.t04_emp` 的天然副本。已读 `169039` 从 MMS 的 `_PB` 源表读取，明确限定 `GRP_ID='h22'`，并与同组扩展资料和字典关联；它有自己的营销人群边界。[169039.sql，89–139 行](attachments/来源表与模型映射明细/IMG-来源表与模型映射明细-20260914110807002.sql)

元数据还收录香港员工名片 `pdata_hk.t04_emp_busi_card`、受限模型中的投行人员关系、面试和津贴。这里只读结构和加工代码，不取个人行数据；它们已在目录中标识来源范围。香港分支当前仅有元数据证据，尚未还原名片生产流程。
