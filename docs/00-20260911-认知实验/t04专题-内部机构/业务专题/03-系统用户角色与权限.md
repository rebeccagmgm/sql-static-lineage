## 1. 系统用户不一定是员工

`t04_user` 表示来源系统中的用户。它既可以来自内部办公、交易或运营系统，也可以来自对客平台。`t04_user_emp_rela_h` 连接员工，`t04_user_pty_rela_h` 连接当事人；不同关系的存在本身就说明“用户”不能直接换成“员工”。Wiki 对用户范围也作了相同区分。[Wiki 正文](attachments/03-系统用户角色与权限/IMG-03-系统用户角色与权限-20260914110757618.json)

`t04_user` 有类别、类型、状态、开户销户等共性字段；OA、PB、广发通、微信、开户平台等附加表描述不同来源的专属属性。建立跨表关联时，必须先知道 `User_Id` 在该来源是原登录名，还是带系统前缀的 ID。

附属资料也未必是权限。例如 `t04_ia_ics_home_page_info` 保存投顾投资圈主页信息，字段包括投顾用户、员工、虚拟团队和主页展示渠道；它可以帮助理解用户怎样对外呈现，不能据此推导授权。该对象已纳入用户资料目录，本版没有逐源复原其生产逻辑。

## 2. 从 OA 登录名到员工号，有筛选和优先级

`61612` 从 `I_GF_USER` 和 `I_GF_USER_DEL` 取当天、主部门记录，得到登录名和工号。删除历史中的工号缺失时按人员类别使用 ERP 号、销售号或登录名兜底；过滤空工号，再按工号排序，优先当前源记录、再看离职和入职日期，最后 `RN=1`。

结果写关系类型 `10`，`User_Id=LOGIN_ID`、`Emp_Id=CODE`，起止日期直接来自入离职日期；来源分区仍沿用 `ODATA_N_OAS.P_GF_USER`。因此这是一条**经过取舍的账号员工对应**，不能据它还原一个人曾拥有的所有 OA 账号，也不能把起止日期当成账号关系被数仓发现的日期。[61612.sql，32–73、125–129 行](attachments/03-系统用户角色与权限/IMG-03-系统用户角色与权限-20260914110759269.sql)

ERP 用户分支 `155174` 又不同：用户号拼 `ERP103-`，经 `EMPLOYEE_ID=PERSON_ID` 连接人力人员号，并限制有效版本和可匹配的人群，写关系类型 `25`。相同的源数字在这两个体系里不是同一个用户。[155174.sql，32–56 行](attachments/03-系统用户角色与权限/IMG-03-系统用户角色与权限-20260914110802035.sql)

## 3. 用户、角色、权限对象是三个层次

| 表 | 一行表达什么 | 不应误读为 |
|---|---|---|
| `t04_role` | 系统角色定义 | 任意用户已经拥有它 |
| `t04_user_role_rela_h` | 用户与角色的一种关系及期间 | 一定是普通角色成员；还可能是角色管理员 |
| `t04_role_righ_h` | 角色对某个对象的一项权限 | 已在源系统实时生效的许可 |
| `t04_user_righ_h` | 用户层面的权限记录 | 必须由角色间接取得 |
| `t04_user_role_dept` | 用户、机构、角色及关系类型的联合记录 | 三条可以任意拆开后再组合的独立边 |
| `t04_user_prd_righ_info`、`t04_xir_user_acct_righ` | 产品或交易账户维度的授权资料 | 产品／账户主档 |

联合记录尤其容易被误读：若一个用户在机构甲是角色 A，在机构乙是角色 B，拆成用户—机构和用户—角色后再做笛卡尔组合，会虚构另外两种授权。`242873` 直接从 `U_T_USER_ROLE` 保留用户、机构、角色三元关系，按日快照写入；不能为了画二元图丢掉该组合约束。[242873.sql，31–54 行](attachments/03-系统用户角色与权限/IMG-03-系统用户角色与权限-20260914110802071.sql)

## 4. 一条具体的角色菜单路径

IPS 样例中：

```text
源 USER_CODE → IPS004-用户号
源 ROLE_ID   → IPS006-角色号
源 MENU_CODE → IPS008-菜单标识

用户角色关系：用户号 + 角色号 + 关系类型 01
角色权限记录：角色号 + 功能权限 1 + 菜单对象类型 11 + 菜单标识
```

用户角色任务 `246064` 与角色权限任务 `246059` 使用一致的 `IPS006-` 角色构造，可以解释两段如何相接；它们各自的历史比较键还保留关系／对象类型。采集 SQL 中日期已展开为 `2026-08-27`，这只能说明该份日期绑定代码，不能证明今天生效。

权限任务把 `Enable_Flag` 留空，不能把空值解释成“已启用”。此外该任务 DDL／投影有 `Righ_Id`、`User_Righ_Cd`，本地物理字段快照却列 `Righ_Cd` 且缺 `Righ_Id`。读者可以理解其业务映射，但在实际查询或按位置复原写入前必须核实部署表结构。[用户角色 SQL](attachments/03-系统用户角色与权限/IMG-03-系统用户角色与权限-20260914110803965.sql)、[角色权限 SQL](attachments/03-系统用户角色与权限/IMG-03-系统用户角色与权限-20260914110805749.sql)、[差异台账](00-20260911-认知实验/t04专题-内部机构/证据/已知差异与待核实事项.md)

## 5. 角色关系也有业务时间和不同职责

`CD661` 区分 `01` 用户所属角色、`0101` 长期角色、`0102` 临时角色、`02` 可编辑管理员、`03` 可授权管理员。“能管理这个角色”不能直接解读成“拥有这个角色全部业务权限”。

AUM 样例 `237094` 从授权成员记录中按用户和角色排序取一条，解析角色关系类型；缺省写 `0101`。它同时把源 `KSRQ/JSRQ` 放到 `Vld_Strt_Date/Vld_End_Date`，另用模型 `Strt_Date/End_Date` 保存变化。所以判断某时点的业务授权，不能只看模型开链状态，还要解释源授权有效期。[237094.sql，30–68 行](attachments/03-系统用户角色与权限/IMG-03-系统用户角色与权限-20260914110807286.sql)

## 6. 权限代码要连同对象类型和条件一起读

`CD662` 中 `1/2/3` 分别有功能、数据、产品权限，另有业务、技术和标签使用等值。`CD663` 对部分对象类型给了条件备注：菜单 `11` 对应功能权限，表 `21` 和权限包 `22` 对应数据权限；又有交易账簿、交易对手、定价环境等业务对象。

不能把所有 `Righ_Obj` 当表名，也不能把相同数字跨代码域作同义解释。完整原码值保留备注、来源表和日期，包含尾随空格也保留，不在解释阶段悄悄改写。[关系与权限字典](00-20260911-认知实验/t04专题-内部机构/字典/关系与权限.md)

Wiki《内部机构编码开发规范》说明，一部分分支权限包会按机构字段转成查询过滤条件。这解释了为何开户机构、营销机构、分公司等字段需要准确命名；但字段名合规不等于当前用户已获权，模型权限数据也不能替代应用实际鉴权。[规范正文](attachments/07-从模型到下游消费/IMG-07-从模型到下游消费-20260914110801685.json)
