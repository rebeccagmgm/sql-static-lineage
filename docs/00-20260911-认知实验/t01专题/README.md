## 2. 平台分类与阅读章节有何不同

平台“客户基本信息”下分个人、机构、产品；但 NAME、ADDR_INFO 同时归入三者。把公共资料放在 01，比为三类客户各复制一份名称/地址说明更容易理解。

平台把销售商、代销、网点归入“产品客户基本信息”。02 保留这个归属，同时说明三者分别是角色档案、代销资料、网点资料；目录同类不意味着粒度相同。

“客户衍生信息”又同时容纳主体、交易对手、托管人、状态和重要日期。它适合说明平台归属，不足以充当这些对象的业务定义。因此本专题把它们分到 01、02、04，并在各章保留分类对照。

分级、数据重要性、开放范围独立作为治理标签；不与主体类型、角色、来源系统或加工层级混在同一棵树中。

| 前期元数据目录中 t01_ 前缀对象 | 718 个 | 另一套表元数据快照，含跨库、临时和未解析对象 |

前两项与后两项的来源、去重身份及快照不同，尚未做物理身份差集核对，不能相加，也不能由 352 小于 718 推断删表。平台目录整体状态为 PARTIAL；没有分类标签不代表不属于相关业务。

“按客户模型分类”有实际返回记录；“数仓建模-数据分类”本次虽有入口，返回 total 为 0。没有数据的入口不作为建模结论依据。

## 5. 阅读时始终保留的区别

- **平台已观测分类**：来自本次 catalog.sqlite 的资产标签，保留原文和资产 GUID。
- **业务解释**：本专题对对象职责和阅读层次的归纳，允许与平台目录一对多对应。
- **实现证据**：某版本任务 SQL 的编号、过滤、匹配键和时间处理，不能推广为所有来源的规则。
- **业务结果**：当前数据是否唯一、映射是否命中、角色是否有效、任务是否成功，不能单靠静态 SQL 和目录标签证明。

旧 2.0、3.0、3.1 保留在父目录，分别承担对象清单、原框架和系统核验的参考作用。继续完善专题时，优先更新对应业务章节，并补上分类与实现证据；不再通过增加一个并列总版本来分散入口。
