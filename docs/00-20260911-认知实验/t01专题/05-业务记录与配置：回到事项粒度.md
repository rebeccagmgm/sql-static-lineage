# 业务记录与配置：回到事项粒度

[返回专题入口](README.md) · [平台分类对照](00-平台分类与业务阅读对照.md)

本章收纳围绕主体发生的方案、材料、资格、配置、认领和计量记录。它们仍在 T01 专题里，但主体号只是关联坐标，一行往往还代表某件事、某份材料或某段期间。

## 1. 平台分类与业务内容

本次 `pdata_n.T01_CUST_CMS_DECT_DET` 的平台归属是“营销考核及奖励信息”，区别于个人/机构客户基本信息。整个平台 T01 前缀对象还观测到“客户服务信息”“非居民涉税信息”“客户合约合同信息”等路径，但不同路径覆盖哪些具体表，应以[逐对象原始清单](00-平台分类与业务阅读对照.md)为准，不能仅按表名代填标签。

从业务阅读角度，这些内容分为下面几组。分组沿用已有元数据和 SQL 案例的解释，不冒充平台统一分类标准。

## 2. 四组业务记录

| 组别 | 对象入口 | 一行还可能需要什么坐标 |
|---|---|---|
| 尽调、材料、报告与涉税资料 | 背景调查、尽调附件、财务报表明细、个人/机构/控制人涉税资料 | 记录号、流程号、附件、报表项目、报告期、版本 |
| 准入、名单与服务配置 | 持牌业务、黑白名单、行情试用、通知/订阅、服务申请 | 业务类型、名单类型、服务或产品、申请/有效时间 |
| 方案与业务参数 | 履保方案、保证金率、费率、额度、银行账户附加资料 | 方案号、协议、产品、币种、账户、期间 |
| 认领、分成与计量 | 客户佣金提成、收入协作、创收目标、指标价值切分 | 业务流水、员工/机构、产品、席位、月份、指标 |

实际有哪些字段、各字段属于哪个对象，见[对象目录](../04-t01-对象目录-2.0.md)与[原业务层级映射](../04-t01-层级映射-3.0.md)的 C1–C4。这里没有把每个入口都认定为完成了全部来源核验。

## 3. 三个已有案例说明为什么不能一客一行

### 履保方案：记录的是方案及参与方

原任务 200060 将源 ID 写为 Perf_Marg_Plan_Id，将交易对手键构造为主体号，还保留管理人主体号、履保协议和大合约编号。方案 ID 与主体 ID 承担不同作用：一个主体可以关联多个方案，一个方案又有多个参与角色。

方案参数不能直接解释成当日已发生的保证金收付；把方案表按主体连接后求和，也要先明确要统计的是方案还是资金事实。详见[原建模研究第 2.3 节及证据 S18](../04-t01-建模理解-2.0.md)。

### 客户提成：字段存在不等于金额已有取值

原任务 63116 的提成明细分支主要提供客户、类型、状态和月份备注，部分编号、金额等字段填空。它虽然属于提成相关对象，也不能仅凭表名和金额列存在就当作可汇总的实际收入事实。分成规则、目标值、业务认领和实际金额应分别识别。

### 死亡材料：事项粒度与元数据冲突同时存在

任务 231126 的 SQL 输出客户号、一码通账户、材料编号、材料名称和归档日期，说明这段加工在组织主体相关材料。调度详情可补齐默认库，但目录记录的字段结构与该 SQL 不一致，不能按目录字段位置直接绑定。此案例的冲突及原文见[3.1 第 8 节](../04-t01-建模专题-3.1.md)。

## 4. 名单、材料和配置不能替代业务判断

有附件不等于尽调完成，有名单记录不等于获准开展业务，有试用配置不等于已经使用服务。名单是允许集合还是排除集合，要看下游消费条件；材料是否齐备、配置何时生效，要有明确状态和时间规则。

同一主体同时有三份附件和两个方案时，直接按主体号连接会产生六种组合。这个数字只是粒度示意，不是实际统计。若只问“是否存在材料”，需要先定义符合条件的材料范围；若要看“哪个方案对应哪份材料”，需要方案与材料之间的关系依据。

## 5. 从业务问题回到取数路径

先把问题写成“哪个主体的哪件事，在什么时候，归哪个对象或人员，以什么规则计量”。再选择事项表、裁剪期间和状态、确认与主体的关联，最后才补名称和角色资料。

[3.1 的实际消费案例](../04-t01-建模专题-3.1.md)表明，下游会混合主体当前资料、名称快照、关系区间、席位和月度分配规则。表级连线只能帮助定位；Join 筛选、重叠期间和多行组合决定最终结果，静态证据不能代替业务数据验收。
