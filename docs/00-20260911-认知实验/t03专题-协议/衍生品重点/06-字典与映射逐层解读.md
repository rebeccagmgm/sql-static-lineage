# 字典与映射：怎样从码值读出业务结构

字典和 map 确实能让 T03 讲得更清楚，但必须先判断它们各自解决什么问题。中文翻译、身份对齐、组合成员关系、账簿规则和来源优先级，会以不同方式改变数据；不能把所有 MAP 都理解成代码对照表。

## 1. 六种常见机制，分别改变什么

| 机制 | 输入与输出 | 本专题例子 | 对理解结果的影响 |
|---|---|---|---|
| 码值释义 | 代码域＋码值 → 中文含义 | CD719 履保状态、CD1164 报告执行状态 | 解释值，不一定改变原始代码 |
| 源代码标准化 | 来源系统、源表字段、目标表字段＋源值 → 标准值 | `REF_CD_CVT_MAP` | 缺映射可产生空值或源值回退；不同来源的同码不能混用 |
| 身份桥接 | 源合约号／工具ID／登录号 → 目标业务身份 | OIS 合约→TIT交易；IOA登录号→ERP员工号 | 决定这条事实属于谁，也可能改变行数 |
| 成员或同一主体关系 | 一组业务对象 → 对象之间的连接 | 组合→合约、组合→保证金账户、同一客户关系 | 决定聚合与归并范围，不能随意直接求和 |
| 规则配置 | 字段、运算符、条件、顺序 → 规则描述 | TIT 账簿映射规则及条件 | 记录规则，不等于已经执行规则或产出归属 |
| 来源选择与优先级 | 多套候选记录 → 保留某行／某字段 | 合约与客户归属 COALESCE；临时系数 NOT EXISTS 正式系数 | 决定最终保留什么，可能按字段而非整行选择 |

学习 map 时，至少问：它改变值、改变身份、筛选行，还是展开关系？一条映射可能同时影响值和行数，但需要逐个表达式和连接条件确认。

## 2. REF_CD_CVT_MAP：五项限定之外，还有源值

本地 SQL 常见限定是 `SRC_SYS_NAME`、`SRC_TAB_NAME`、`SRC_FLD_NAME`、`TGT_TAB_NAME`、`TGT_TAB_FLD`，最后用源业务字段连接 `SRC_CD_VAL`。同一个 ENABLED 或 STATUS 字段，不能跨源表直接共享转码含义。

例如账户启用状态、互换合约状态、期权合约状态，都可以投向仓库的协议状态，但来源字段和源表不同。另一个容易忽略的点是：配置中的源表名可能是逻辑名称 `REF_TRS`，物理来源却是 `ODATA_N_TIT.D_REF_TRS`；不能要求两者字面完全相等而丢掉已写出的转换配置。

本次从 SQL 中整理 **237 处 TIT/OIS 转换配置检索位置**，见 [[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/代码转换条件索引|可读条件索引]] 和 [[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/代码转换条件索引.json|JSON]]。它来自转换表后有限行窗口检索，可能有重复或未完整捕获的条件，不是 237 个独立代码域，也不是转换表的映射行。

本地资产 SQLite 原先只有 `REF_DW_CD_VAL` 的码值记录，未确认独立 `REF_CD_CVT_MAP` 数据。用户允许样例后，另行从数综平台 sample 取到了转换表 10 行，这补充了**实际映射行的结构证据**。样例中既有 DZA→DZA 的同值标准化，也有行业 2411→C2411 的代码转换，证明“映射”不一定总是改变字符值。

这 10 行没有命中 TIT/OIS，不能据此补造它们的实际对应关系；样例的更新日期也不同，不能称为全部当前规则。[[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/样例观察|样例观察及日期]]。

另外，216975 读取转换表后使用的是源代码说明 `SRC_CD_DESC`，不是标准值 `DW_CD_VAL`。所以“用了转换表”与“输出已标准化”仍要分开判断。

## 3. 履保字典：至少是七个维度，不是一列状态

| 维度     | 本地代码域与全部命中值                              | 解释                |
| ------ | ---------------------------------------- | ----------------- |
| 监控结果状态 | CD719：0正常、1预警、2追保、3未知、4平仓                | 结果状态，不是参数类型       |
| 参数类型   | CD730：`DYNA_REF`动态参数、`STC_REF`静态参数       | 区分动态输入与静态设置       |
| 启用履保类型 | CD731：`DYNAMIC`动态履保、`STATIC`静态履保、`NONE`否 | 是否启用及启用哪类         |
| 盯市类型   | CD732：`PORTFOLIO`组合、`SINGLE`逐笔           | 盯市组织方式            |
| 保证金方向  | CD733：`CHARGE`应收、`PAY`应付                 | 收付方向，不是买卖方向       |
| 履保类型   | CD1498：1逐笔、2组合、3组合＋逐笔                    | 不能和上面的盯市代码直接混为同一域 |
| 履保模式   | CD1500：见下表                               | 模式的计算基础及组织方式      |

CD1500 本地全部 8 个值：

| 码值                   | 中文含义       | 记录日期       |
| -------------------- | ---------- | ---------- |
| `MARKET_VALUE`       | 市值         | 2024-10-31 |
| `NOTIONAL_PRINCIPAL` | 名义本金       | 2024-10-31 |
| `TRADING`            | 交易型        | 2024-10-31 |
| `LONG_SHORT`         | 多空         | 2025-08-14 |
| `CST_MARKET_VALUE`   | 券抵市值       | 2025-12-04 |
| `LONG_SHORT_SIDE_MV` | 多空单边（市值）   | 2026-05-22 |
| `LONG_SHORT_SIDE_NP` | 多空单边（名义本金） | 2026-05-22 |
| `NONE`               | 不启用履保      | 2026-05-22 |

这些值使我们知道为什么“市值”和“名义本金”不能随便替换、为什么只看一个保证金比率不够。但代码名称不能自动提供完整公式，也不能证明某客户启用了该模式。CD1502 另有 `CASH`现金、`CREDIT`授信，是履约保障类型，又是一层区分。

以上来自本地码值快照，状态 UNVERIFIED；记录日期不是业务生效日期。各域逐行来源和日期见 [[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/字典实值附录|完整码值附录]]。

## 4. 组合关系的 13、14：SQL 已见，旧字典未齐

任务 141596 的合约组合成员分支固定关系类型 13，141600 的组合与保证金账户分支固定 14。当前 CD631 本地快照只命中：10 协议与衡泰账户树、11 协议与信用交易头寸组、12 协议与利息头寸组。

因此正文可以依据这两条 SQL 的连接对象解释 13/14 在分支中的用途，但不能伪造“本地字典正式中文名称”。缺口是字典快照没有这些值，并不是 SQL 没有这些关系。

反过来，也不能因为域中出现 10/11/12，就说 TIT 履保组合同时使用了这些类型。字典提供可能的含义集合；具体任务决定实际使用哪几个。

## 5. TIT 源字典：141 行里不只是买卖方向

本地 `code_values` 中归属于 `ODATA_N_TIT.D_CFG_DICTIONARY_DESC` 的记录共 141 行，日期均为 2026-08-21。它们是仓库整理出的源字典记录，**不是 TIT 原始字典表全量**。

| 代码域 | 行数 | 业务知识 |
|---|---:|---|
| CD082 源交易所类型 | 68 | 包含境内外证券及期货等市场；不能把相近缩写当成同一交易所 |
| CD1290 源交易来源 | 5 | TIT 可以保存来自其他交易平台的交易，入仓来源与最初交易来源是两个层次 |
| CD1291 源交易方向 | 19 | 不止 BUY/SELL，还包含申购、基金申赎和公司行为等方向标签 |
| CD2204 场外衍生品账簿业务分类 | 49 | 帮助解释 DESK：互换、期权、对冲、验证等业务归属 |

交易来源的 5 个值为 CALYPSO、CTP、ESUNNY（易盛）、GFSOTC（OTC综合业务平台）、PT_O32（自营O32）。前两个在此次记录中未提供可进一步扩写的中文名称，保留原名。这里的 `GFSOTC` 与 Data_Src_Cd 为 TIT 可以同时成立：一个说明原始交易来源，另一个说明这一条模型输入来自 TIT。

DESK 中例如 AIRBAGX 为静态对冲、DYNAMIC_HEDGING 为主动对冲、DUMMY 为生产验证、GFA_FORWARD/GFA_OPTION/GFA_TRS 分别为资管远期/资管期权/资管互换。它们帮助辨认业务归属，不能据此把带“验证”的所有记录自动排除，也不能用源字典码替代具体账簿 ID。[[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/字典实值附录|141 行完整展开]]。

## 7. OIS 原始字典：连接键必须在具体类别内确认

`G_DICTIONS/G_DICTIONS_DETAILS` 的客户标签分支，用来源 OTC/FICC、类别 xz/nation 和码值连接。`G_OTC_DICTIONARY` 的资金类型分支则按 `dict_entry='fund_types'`，取 subentry 作为来源匹配值。这两套机制不能只看“字典表”三个字就套用同一个键。

用户允许样例后，本次读取 `G_OTC_DICTIONARY` 10 行，全部属于 city，业务日期 2023-11-04。9 行的 subentry 都是“辽宁省”，中文内容分别是不同城市。这证明 **subentry 在整张表内不是唯一值**；在 city 类别里甚至更像上级分组信息。

它并不证明 fund_types 类别也有重复，因为样例未命中该类别。正确做法是在具体 dict_entry 中核对字段角色、唯一性和日期，不能从城市样例推导全部资金类型枚举。[[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/样例观察|样例观察]]。

## 8. 报告字典揭示“业务类型、模板版本、执行状态”三层

CD1160 的 1/2 分别为衍生品估值报告、收益凭证估值报告，是大类。CD1161 有 17 行，除互换、期权、多空互换等名称外，还包含免责声明页、香港报告、双安、灰度、并行等模板或版本信息。**不能把这 17 行直接画成 17 种衍生品。**

CD1164 的 6 个状态又区分普通成功失败、重新生成、手动发送。它是在解释执行记录；模板类别相同，不意味着执行动作和状态相同。三域的全部码值都在 [[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/字典实值附录|附录]]，不只给缩写或域编号。

## 9. 仍未取得的字典，要准确留下问题

本次尚未确认收付款类型/方向/状态、互换存续期事件类型、部分观察属性等字段的完整独立代码域。字段名检索未命中，不能直接套用中文相近的域，例如“收付款转移类型”不能自动解释所有收付款方向。

同样，SQL 中的 CASE 可以证明它枚举了哪些值、其他值怎样处理，却不代表源系统永远只允许这些值。条件保留原值、填空、返回 NULL 三种策略，各自会留下不同的数据形态。

对后续学习最有用的补充，是带着具体字段回到转换配置及来源样例，而不是追加一个没有证据的“推测代码大全”。本次把已见实值、SQL 条件、样例观察和未覆盖项分别保留下来，便于继续扩展。
