# 一笔衍生品交易：用同一个互换例子理解模型

一笔交易为什么会出现在合约、腿、持仓、履保和收付款等多张表里？下面始终跟着同一份合约 **S1**：先看双方约定了什么，再发生一次部分终止，最后看剩余部分怎样结算。每增加一种记录，都先解释它解决了什么新问题。

> **示例约定与系统证据分开。** S1 的人物、编号、价格、公式和后续事件都是教学假设。它们用于推导对象之间的区别；第6节再与本地已有的模型和静态 SQL 对照。示例不代表真实客户条款，也不用于复算 TIT 的估值或履保结果。

## 1. 先有双方的约定，才有需要保存的合约

甲客户希望按照股票 X 的价格变化取得约定收益，乙证券公司承担对应的付款责任并收取费用。双方给这份约定一个编号 **S1**。本例只按价格变化计算，不包含股息、税费或其他交易条件。

| S1 的约定    | 本例取值                                       |
| --------- | ------------------------------------------ |
| 参考股票及起始价格 | 股票 X，100元                                  |
| 初始参考数量    | 10,000份                                    |
| 初始计算本金    | 100元 × 10,000份＝100万元；本例不交换这100万元           |
| 存续期限      | 第0天生效，第30天结束                               |
| 价格变化部分    | 终止数量 ×（终止时价格－100元）；为正时乙付甲，为负时甲付乙           |
| 费用部分      | 终止部分对应的初始计算本金 × 年费率3.6% × 已存续天数 ÷ 360；由甲付乙 |
| 部分终止      | 允许先结束一部分参考数量；剩余部分继续以100元为起始价，费用从第0天累计      |
| 付款安排      | 本次价格变化金额与费用相抵，形成一次应收付要求，再办理付款              |

这里的“参考数量”服务于合同金额计算，不表示甲已经买入了10,000股现货。甲与乙要履行的是 S1 中约定的付款责任。

因此，第一类记录是**合约档案**：它需要标识“甲与乙做了哪份交易”，保存期限、状态及合约级条件。甲的客户档案和股票 X 的产品资料各自有用途；即使甲明天再做一笔参考同一股票的交易，也需要另一个合约身份，不能拿客户号或股票代码代替 S1。

## 2. 一份合约内部，为什么还要拆出“腿”

现在让系统回答“到终止时，应当算哪几笔钱”。S1 有两条计算规则：

| 条款记录 | 根据什么计算 | 付款责任怎样确定 |
|---|---|---|
| L1：价格变化部分 | 参考数量、起始价、终止价 | 正收益乙付甲，负收益甲付乙 |
| L2：费用部分 | 初始计算本金、费率、存续天数、计息基准 | 甲付乙 |

两条规则虽然属于 S1，但使用不同的输入。修改费率会改变 L2；股票价格变化会改变 L1。保存它们时，需要既知道“都属于 S1”，又能分别找到“哪一条规则”。

**互换的腿，就是独立表达这些收益或支付组成的一层结构。** 合约编号回答是哪笔交易，腿标识回答其中哪一个组成。某次结算可以把两个组成相抵成一个净额，但两条原始规则仍然需要分别保存和解释。

这也说明了拆表的理由：如果把两条腿都当成两份合约，交易数量会翻倍；如果只保留最后的净额，就无法解释这笔钱由哪些约定算出，也无法单独修改或检查其中一条规则。这里用两条腿讲清分工，实际合约的组成数目须看具体条款。

## 3. 第10天部分终止：合约没换，仍在履行的规模变了

第10天，股票 X 涨到110元。甲乙约定终止其中4,000份，其余6,000份继续履行。

按 S1 的教学条款，终止部分产生：

- 价格变化金额：4,000 ×（110－100）＝40,000元，由乙付甲。
- 费用：400,000 × 3.6% × 10 ÷ 360＝400元，由甲付乙。
- 相抵后，本次要求乙向甲支付39,600元。

这次变化同时产生了两个问题：**已经结束的部分应收付多少，以及仍有多少数量继续参加后面的计算。** 合约主档只能告诉我们仍然是 S1；它不能代替这两个问题的记录。

下表只跟踪 L1 的参考数量，演示业务状态如何变化：

| 观察时点 | 合约 | 已累计终止的参考数量 | 尚未终止的参考数量 | 尚未终止部分的初始计算本金 |
|---|---|---:|---:|---:|
| 第0天成立后 | S1 | 0份 | 10,000份 | 100万元 |
| 第10天部分终止前 | S1 | 0份 | 10,000份 | 100万元 |
| 第10天部分终止后 | S1 | 4,000份 | 6,000份 | 60万元 |

合约身份未变，初始约定也仍可追溯；变化的是继续履行的范围。因此需要**持仓或存续记录**，把某个组成在某个业务时点的数量及相关数值保存下来。部分终止还形成了本次结算信息，39,600元不能塞进“剩余数量”一列。

这个变化足以推导出三个查询区别：

1. 查“甲做了几份交易”，这里仍计一份 S1。
2. 查“第10天部分终止后还有多少参考数量”，应找到相应腿及业务时点的存续信息，得到本例的6,000份。
3. 查“这次部分终止要求付多少”，应进入对应结算记录，得到本例的39,600元。

表中的三个观察时点是为了比较状态，不是对仓库历史保存方式或行数的承诺。“尚未终止部分的初始计算本金”也是本文定义的量，不能仅凭中文相似就等同 TIT 的动态本金或市值字段。实际模型分别保存数量、价格、市值和多种收益，字段口径要回到来源核对。[^position]

## 4. S1 还在存续：为什么履保要另看组合和账户

S1 仍有6,000份继续履行，后续价格变化可能让任何一方产生新的付款责任。“履约保障”关注这类责任如何获得保障，例如按约定提供保证金；它关注的金额和处理情况，与上一节的39,600元交易结算不是同一个问题。

继续设定：甲还有另一份交易 S2。甲乙约定，用一笔共同的保障资金支持 S1、S2，每次综合观察这组交易后，提出一项追加或提取要求，而不把资金预先划成“S1专用”和“S2专用”两份。

这时，只看 S1 就漏掉了同样使用这笔保障资金的 S2；分别查看两份交易并把同一笔保障资金各算一次，又会高估可用保障。要回答“这项共同安排是否充足”，必须先确定纳入了哪些交易。我们把这个范围命名为 **G1**，把本例用于登记相关保障资金、办理收取和提取的账户命名为 **M1**。

有了这个安排，系统需要区分：

| 需要知道什么 | 为什么要单独记录 |
|---|---|
| G1 包括 S1、S2 | 这是成员关系；它界定本次观察包括哪些交易 |
| G1 关联 M1 | 这是账户关系；知道成员是谁，并不能自动知道使用哪个保证金账户 |
| G1 本次监控要求追加多少 | 这是结果；它随业务日期及输入变化，不是在重新登记成员 |
| 这次追加要求怎样处理 | 这是处理记录；要求已经算出后，还可能等待确认、递延或办理 |

组合 G1 回答“哪些交易共同参与”，账户 M1 回答“相关保障资金记在哪里、通过哪个账户管理”。因此，仅有 G1 的成员名单，还不足以找到对应的资金账户；仅有 M1 的账户资料，也不知道哪些交易参与了这项安排。本地历史需求确有把期权和互换纳入同一组合观察的设计，并限定了适用客户。这里只借它解释这种管理需求，不将历史公式推广成当前所有客户的规则。[^group]

现在仅假设源系统给出一条结果：**G1 本次应追加20,000元**。这个数没有在本例中重算，也没有分摊到 S1、S2。

如果将该结果连接到成员关系，会得到两行：“S1所在G1，应追加20,000元”和“S2所在G1，应追加20,000元”。两行引用的是同一项要求，直接相加成40,000元就重复计量了。**展开关联对象会增加展示行数，却不一定增加业务金额。**

反过来，监控显示“应追加20,000元”，也还没有回答是否确认、是否延后、最终如何办理。查询处理记录是下一步，而不是把监控数值解释为已经追加。本地保存组合结果与追保处理的任务来自不同源对象，目前不能把它们画成已验证的一对一加工流水线。[^margin]

## 5. 第30天结束：结算要求与付款动作各保存什么

回到 S1 本身。第10天终止了4,000份，第30天剩余6,000份到期，股票 X 此时为120元。

仍按同一份教学条款：

- 剩余部分的价格变化金额：6,000 ×（120－100）＝120,000元。
- 这部分从第0天持续到第30天，费用为600,000 × 3.6% × 30 ÷ 360＝1,800元。
- 本次要求乙付甲118,200元；完成这次终止后，尚未终止的参考数量变为0。

S1 现在有两次结算。为继续演示，假设每次均在次日一次性完成付款：

| 对应业务变化 | 形成结算要求的时间 | 应付金额及方向 | 本例假设的实际付款 |
|---|---|---|---|
| 部分终止4,000份 | 第10天 | 乙向甲付39,600元 | 第11天付39,600元 |
| 剩余6,000份到期 | 第30天 | 乙向甲付118,200元 | 第31天付118,200元 |

第10天已经可以回答“这次应付多少”，却不能提前回答“第11天是否真的付成”。因此需要两种表达：**结算信息**保存某次业务变化产生的应收付要求，**收付款事件**记录后续资金办理动作及其时间、状态和金额。

这也解释了为什么不能只保留合约的一列“结算金额”：一份 S1 已经发生两次结算，而且每次的计算日期和付款日期不同。若第二次付款改为分两次办理，合约仍是一份，结算要求仍是那次到期要求，收付款动作却会增加。

本例特意设定每次只付一笔，真实关系不能据此假定一对一。本地已有 T03 结算信息与 T05 收付款事件的独立表达；SQL 记录的事件状态仍须按来源含义解释，不能替代真实到账核验。[^settlement]

## 6. 理解业务变化后，再落到本地模型和来源

前面没有用表名定义业务。现在可以带着明确的问题去查表，而不是看到“一笔合约关联出很多行”就判断重复。

| 要回答的问题               | 本地已见的模型表达                                                                                  | 定位时要分清什么                  |
| -------------------- | ------------------------------------------------------------------------------------------ | ------------------------- |
| 这是哪份普通互换             | `T03_OTC_SWAP_COMP_INFO`                                                                   | 合约身份与业务使用的合约代码            |
| S1 有哪些收益、支付组成        | `T03_OTC_SWAP_COMP_LEG_INFO`                                                               | 所属合约、腿标识和合约内序号            |
| 某个组成在某时点保存了什么数量和数值   | `T03_OTC_SWAP_COMP_HOLD_INFO`                                                              | 持仓记录编号、腿、标的及业务日期          |
| S1 被放到哪个履保组合         | `T03_OTC_DERI_AGT_AGT_GRP_RELA_ADTNL_INFO`                                                 | 合约身份与组合身份之间的关系            |
| 该组合关联哪个保证金账户         | `T03_AGT_AGT_GRP_RELA_H` 的已读组合—账户分支                                                        | 关系类型、两端身份及有效期间            |
| 组合本次监控结果是什么、追加要求如何处理 | `T03_OTC_CUTP_MARG_ACCT_PERF_GUAR_RSLT` 的组合来源分支；另查 `T03_OTC_DERI_COMP_COMB_MARG_CALL_INFO` | 结果与处理分别定位；不能把整张结果表都当成组合粒度 |
| 本次应收付多少、后续有什么付款动作    | `T03_DERI_COMP_SETT_INFO`；`T05_OTC_RECV_PYMT_EVT`                                          | 合约、具体结算记录与具体收付款事件         |

这些表不是按表名顺序逐张生产的流水线。已读普通互换、腿、持仓主要由 TIT 提供；组合结果与追保处理分别来自各自源对象；已读合约结算分支来自 CSS，收付款事件分支来自 TIT。**业务上围绕同一笔 S1，需要通过各自有证据的身份与关系重新对齐。**

例如，查 S1 某时点的持有情况，需要把持仓记录定位到它所属的腿，再关联到合约。实际来源使用各自的编号，不能把本文的“S1”或业务人员提供的一个合约号，直接当成所有表共用的键。先核对身份怎样对应，再检查关系是否匹配、是否产生多行；本文没有证明整笔交易的所有记录都已成功逐一关联。[^identity]

S1 把这些主题连接起来：甲是谁归入当事人资料，股票 X 是什么归入产品资料；交易约定、结构及存续信息进入相应 T03 模型，资金动作又涉及 T05。业务过程跨主题，不意味着所有相关记录都应塞进 T03 合约主表。

## 7. 换一个条件，看看哪些记录应该变化

下面仍使用 S1 的教学规则，可以直接检查前面的解释是否足以支持判断。

**如果第10天价格是90元，而不是110元？** 终止4,000份产生负40,000元价格变化金额，费用仍是400元，所以变成甲向乙付40,400元。付款方向和金额变了，S1仍是一份合约，L1和L2仍是两项组成；方向变化不应让我们凭空新增一份交易。

**如果第30天的118,200元分成两次付款？** 到期结算要求未变，但要分别记录两次动作的金额和时间。只数付款行数，不能反推出发生了几份合约或几次结算。

**如果 G1 的成员展示增加到三份合约，而仍引用同一条20,000元追加要求？** 展示会增加一行，要求本身没有因此变成60,000元。要计算组合总要求，应回到结果自身的范围，不能在展开成员后直接求和。

到这里可以停下来：你已经沿一份 S1 区分了交易身份、内部条款、存续状态、管理范围、计算结果和办理动作。查询前先说明自己要回答哪一个问题，再选择相应记录。
