## 1. “进入模型”应落实到业务对象，不只看源表是否被引用

同一TIT源表可能同时生产通用协议、专用合约、关系、状态及分类；也可能在某任务中仅用于识别交易类型。比如期权合同要素表在履保参数任务中只是帮助判断修饰符20207，不能据此声称履保比例来自期权合同主表。

## 2. 普通互换、极速互换、确认书分支怎么共存

普通互换103941采用 `KEY_OTC_TRADE_ID / 20206`，从TIT对手键构造 `TIT060-...`，资金账户使用10220；`CONTRACT_CODE`写入外部合约号，`BUNDLE_ID`写入组合编号。合约状态与组合类型分别按各自的 `REF_CD_CVT_MAP` 条件转换。

极速互换183091仍采用交易ID与20206，却将资金账户字段填空，并有 `TRS_TYPE<>'LONG_SHORT_SWAP'` 的来源过滤。这说明修饰符识别的是协议类别体系中的对象，未必区分所有业务路径。

确认书112119更换了编号来源和修饰符：`KEY_TRADE_COMFIRM_ID / 20206-KST`，交易对手直接采用 `COUNTERPARTY_ID`。如果做互换全景，应把三条分支的字段填充和身份规则逐项对照，再决定如何合并；如果做普通TRS持仓链，应明确源分支限定。

一个具体反例是：查询者先取全部互换主表，再按照资金账户连接账户资料。普通TRS可能匹配，另外两条分支的账户字段却为空；若账户资料无法匹配这些空身份，INNER JOIN就会将它们排除，把“全体互换”变成“能够匹配账户的互换”。这不是同一业务总体。

103941的来源声明还有一处冲突：物理源表是 `D_REF_TRS`，中文注释却写“客户资金账户信息”（源SQL第151行）。投影包含互换合约、腿数量和名义本金，本文据物理来源与投影解释为互换来源，保留这条注释不一致的事实，不能把注释原样当成业务定义。

本地还有PB及其他任务版本。它们已经在全源索引中保留，但未通过读三个代表分支就判定所有变体语义一致。[[00-20260911-认知实验/t03专题-协议/证据/SQL/103941.json|103941]]、[[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/SQL/183091.json|183091]]、[[00-20260911-认知实验/t03专题-协议/证据/SQL/112119.json|112119]]。

## 3. 为什么交易ID之外还有工具ID、产品ID和合约代码

`KEY_OTC_TRADE_ID` 定位交易，`KEY_INSTRUMENT_ID` 定位工具或结构载体，`INTERNAL_TRADE_ID`服务内部合约代码连接。不同来源的 `CONTRACT_CODE` 有时在目标中称内部合约号、有时称外部合约号；不能假设所有同名源字段有统一语义。

在141596中，组合与合约映射源的 `ENTITY_ID` 实际先连接交易主信息的工具ID，再取得交易ID；同一ENTITY_ID还构造 `TIT-...` 产品编号。也就是说，某个映射源并没有直接给出协议ID，它给出的是工具ID。仅把列名改成Agt_Id会把对象身份错置。

期权也需要从工具找到交易，再识别是否属于期权合约；具体投影见第6节。这些关联回答“这个经济组成属于哪份交易”，不是给同一个编号换几个名字。

## 4. 互换腿：收益组成和支付方向

103942将 `D_REF_TRS_LEG` 写入 `T03_OTC_SWAP_COMP_LEG_INFO`。合约编号指出腿属于哪份合约，腿标识则区分合约内部的组成：

| 目标字段 | 源表达式 | 查阅时如何理解 |
|---|---|---|
| Swap_Comp_Agt_Id / Modifr | KEY_OTC_TRADE_ID / 20206 | 所属合约身份 |
| Leg_Glbl_Seq_No | KEY_LEG_ID | 源腿标识；持仓及下游107018用它连接 |
| Leg_Seq_No | LEG_SEQ_ID | 腿顺序号，未被证明跨合约唯一 |
| Swap_Comp_Leg_Type_Cd | LEG_TYPE | 固定、浮动或结构化收益类型 |
| Paid_Dir_Cd | DIRECTION | 支付方向 |
| Undrl_Cd | UNDERLYING_INS_ID | 直接保留的源标的编号，该表达式没有做Wind代码映射 |
| Fix_Ratio / Intr_Marg | FIXED_RATE / SPREAD | 固定利率与利差，不能当成同一费率 |
| Inta_Bm_Cd | NVL(映射值, DAY_COUNT) | 计息基准；未匹配映射时保留源码 |

代码域CD709中，FIXED_LEG_TYPE、FLOAT_LEG_TYPE、STRUCTURE_LEG_TYPE分别为固定、浮动、结构化收益。支付方向来自DIRECTION；多空由另外的LONG_SHORT字段表达。买卖方向、支付方向、多空方向分别回答交易动作、付款角色和风险/持仓取向，不能只保留一个“方向”。

每条腿还可以有自己的币种、日历、支付周期和重置参数。计息基准决定日期如何进入计算；但保留这些要素，不等于任务提供了完整估值程序。SQL也没有限定一份合约恰有两条腿，典型教学结构不能替代实际基数核验。

SBL腿信息通过 `KEY_LEG_ID` 补充HAIRCUT。不能由这个补充字段就把所有互换都判定为证券借贷业务；需要腿类型、合约业务类型及来源共同限定。`DAY_COUNT`、`EXCHANGE_RATE_TYPE`、`INTEREST_TYPE`等字段各有转码条件，并在未匹配时回退源码；不能只用码值字符串解释业务。尤其 `EXCHANGE_RATE_TYPE` 被写入注释为“利率类型”的 `Rate_Type_Cd`，源名与目标注释的业务口径仍需另核，本文不擅自统一。[[00-20260911-认知实验/t03专题-协议/证据/SQL/103942.json|103942]]77—167行。

## 5. 持仓到底以什么为一行

105392从腿历史持仓取得 `KEY_LEG_POSITION_ID→Swap_Comp_Hold_Id`，`KEY_LEG_ID→Leg_Glbl_Seq_No`，`UNDERLYING_INS_ID→TIT-产品ID`，然后用当日腿表补出合约ID。源业务日期截取为目标Busi_Date，并通过临时更新日期集合选择需要更新的日期。

这意味着至少需要同时意识到“持仓记录、腿、标的、业务日期”这些维度。它不是账户余额，也不是每份合约一行。若只按合约号连接，可能把全部腿和标的混在一起；若忽略业务日，还会叠加不同日期的存量。

数值字段也不是一套可替换的同义词：

| 源字段示例 | 目标含义 | 使用时需要确定 |
|---|---|---|
| QUANTITY / INIT_QUANTITY | 当前/期初数量 | 是看当前暴露，还是期初基数 |
| PRICE / INIT_PRICE | 行情/期初价格 | 是否还需要乘数、汇率或其他约定 |
| VALUE_ORG / VALUE_RMB | 原币市值/人民币市值 | 币种及是否已经转换 |
| VALUE_ORD_BASE / VALUE_EUR_BASE / VALUE_ASIA_BASE | 本币流通股/欧式/亚式市值 | 不同业务评价口径，不能随意求和 |
| 源收益字段 | 已实现、未实现等各类收益 | 是否累计、是否已经交收、与哪一视角相关 |

已读分支将目标 `Sett_Amt`、`Sett_Crrc_Cd`、`Tot_Unsett_Rlz_Prft` 等后加字段填空。元数据有列，不等于该来源已供值。字段的填充覆盖应按来源分支解释，而不是只从DDL列数估计系统成熟度。[[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/SQL/105392.json|105392]]144–167、245–302行。

## 6. 期权为什么需要主合约、子交易、观察日三层

主合约103943来自 `D_REF_OTC_OPTION_DEAL`，身份为 `KEY_OTC_TRADE_ID / 20207`，保留交易对手、资金账户、规模和日期。其中名义本金、绝对名义本金及其币种、初始本金、动态本金、结算币种分别保存，不是一个金额的多种叫法。合约状态、复核状态、限额审批状态、大额名义本金审批状态也分别取值和转码；例如复核状态取 `REPEAT_CHECK_STATUS`，限额审批状态来自关联的限额审批记录，不能用“合约有效”替代其他维度的判断。

该任务把障碍表的 `SEQ='0'`、`SEQ='1'` 分成两次连接，参与率表也各按0和1连接，共四路，再输出障碍价1/2和参与率1/2。它明确选择了要展开的序号；没有证明源侧“交易ID+序号+日期”唯一，也没有把所有附表变成天然一对一。[[00-20260911-认知实验/t03专题-协议/证据/SQL/103943.json|103943]]226—229、276—285行。

子交易105395来自期权工具信息 `D_REF_INS_OPTION_INFO`。工具记录的 `CONTRACT_INS_ID` 先连接交易主信息的 `KEY_INSTRUMENT_ID`，取得主交易编号，再连接期权合同要素表识别20207修饰符；外部子交易号与序号则分别取 `EXTERNAL_TRADE_ID`、`SEQ`。主交易编号和修饰符能否同时填充，取决于这两步连接，具体缺失情形见[[00-20260911-认知实验/t03专题-协议/衍生品重点/07-合约结构与模型对应#4. 为什么交易编号有值，期权修饰符却是NULL|编号有值但修饰符为空的问题]]。

同一子交易还保存工具产品编号 `TIT-KEY_INSTRUMENT_ID`、源产品编号、账簿编号、BUY/SELL转换的买卖方向及 `COEFFICIENT→Sub_Trd_Coef`。日期包括生效/到期、终止、定价、观察起止、兑付等，执行类型也单独记录。方向、系数和日期共同帮助解释这个组成，SQL没有据此提供完整期权收益公式。一个主合约可关联多个组成，因此不能在连接子交易后重复累计主合约本金。[[00-20260911-认知实验/t03专题-协议/证据/SQL/105395.json|105395]]100—132、182—186行。

观察日112813则记录某一观察日期上的上下障碍、百分比、票息、轧差票息、分档票息、计息天数和支付日期。`KO`是此分支写入的障碍类型常量；表中存在一个观察日，并不等于在该日已经实际触发敲出。需要区分约定条件、观察输入、源系统计算结果和实际终止事件。

这张观察日表既有结构性条款，也有CLOSE等观察数据，不能简单叫“纯参数表”。任务最后INNER JOIN当日期权合同要素表，意味着孤立观察记录会被过滤；这种准入条件影响覆盖，即便主表字段不直接出现在所有输出列中。[[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/SQL/112813.json|112813]]。

## 7. LIZARD观察日：名称容易懂，关联层次更需要认真读

156494将 `D_REF_OPTION_LIZARD_OBS_DATE` 写入子交易观察日属性，类型固定 `LIZARD_ATTR`。源记录的KEY_INSTRUMENT_ID先找期权工具信息B，再由B.CONTRACT_INS_ID找到交易C。输出同时保留主合约ID、外部子交易ID、工具产品ID和观察日期。

还保留轧差票息率、票息率、参与率、障碍比例、障碍价格和兑付日。比例与绝对价格不是同一单位，不能因为值都可转数字就互换。

该任务源读取按日，但目标只按SRC_TBL分区，DDL没有Busi_Date分区。**观察日期是业务条款/观察维度，加载日期是加工信息，两者都不意味着目标保留每天一份快照。** 这是此前按“期权附表都是日快照”解释会遗漏的差别。[[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/SQL/156494.json|156494]]34–73行。

## 8. 外汇远期：两种货币和多个汇率不能压成一个金额

163771从 `D_REF_FX_FORWARD` 写入远期主信息，以交易ID和20208识别合约，保存交易对手、内部合约号、名义本金、动态本金、状态、实际审批生效日、约定兑付日、实际兑付日及提前终止结算金额。

163772从 `D_REF_FX_FORWARD_STRUCTURE` 写结构表，保留同一合约身份，并区分三组要素：

| 结构要素 | 保存内容 |
|---|---|
| 标的与定价 | TIT前缀产品编号、源标的编号、由UNDERLYING_WIND_CODE取得的标的代码、定价起止日 |
| 交割与货币 | 交割方式、FIRST_CCY、SECOND_CCY、SETTLEMENT_CCY、销售方支付两币种数量 |
| 汇率 | 交割汇率、结算汇率、期末汇率 |

从业务上看，这些字段是理解双方约定如何交换经济结果的必要上下文。主表Nom_Prin不能直接作为“这笔交易所有现金收付总额”，币种1和币种2数量也不能未经转换相加。“销售方支付”还需要结合我司角色解释，不能默认销售方就是我司。

这两项任务将条款与源结果保留到模型，没有证明主结构一对一，也没有给出全部资金流计算逻辑。[[00-20260911-认知实验/t03专题-协议/证据/SQL/163771.json|163771]]、[[00-20260911-认知实验/t03专题-协议/证据/SQL/163772.json|163772]]。

## 9. 期权结算结果是另一种对象

112816从 `D_TRD_OPTION_DEAL_SETTLEMENT` 进入T03期权结算信息，区分SETTLEMENT_AMOUNT、NET_PNL、FIX_PNL、FLOATING_PNL以及期权费实际支付日、实际兑付日、实际结算日。模型没有把这些金额合成一个“收益”。

如果用户问最终收了多少钱，需要明确是结算结果、交易净收取还是实际收付款事件；如果问利润，还要核对固定与浮动收益、费用和币种。SQL将源NET_PNL命名为交易净收取金额，并不能只按缩写推导其等于会计利润。

这也是为什么TIT重点不能止步于合约主表：主表定义业务，结构表达经济组成，持仓表达存续状况，结算表保存结果，T05收付款进一步记录动作。每层的目标不同。[[00-20260911-认知实验/t03专题-协议/证据/衍生品补充/SQL/112816.json|112816]]。
