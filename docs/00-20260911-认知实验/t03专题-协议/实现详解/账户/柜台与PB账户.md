# 柜台与PB账户：一个资金账号为何对应多个模型身份：模型与加工证据

业务背景与模型定位见[[00-20260911-认知实验/t03专题-协议/业务专题/账户/柜台与PB账户|柜台与PB账户：一个资金账号为何对应多个模型身份]]。本篇按需核对源字段、身份构造、连接、转码及时间维护，不作为必须顺序阅读的课程。

## RCC：资金账户与证券账户怎样分工

资金账户承载==资金侧账户档案和业务配置==；证券账户定位==特定市场的证券登记账==户。已读模型将两者编码为：

| 模型 | 来源 | 协议编号 `Agt_Id` | 修饰符 `Agt_Modifr` |
|---|---|---|---|
| `T03_AST_ACCT` 资产账户 | `A_FUNDACCOUNT` | `FUND_ACCOUNT` | `10201` |
| `T03_SCR_ACCT` 证券账户 | `A_STOCKHOLDER` | `FUND_ACCOUNT` | `10101-EXCHANGE_TYPE-STOCK_ACCOUNT` |

**证券账户的协议编号列也使用资金账号，证券账号保存在修饰符中。** 因此模型中的证券账户身份包含“资金账号、市场、证券账号”三个部分。

以构造数据为例：资金账户身份为 `F001 / 10201`，它下面两个市场的证券账户可以是 `F001 / 10101-M1-S001`、`F001 / 10101-M2-S002`。这三行的编号相同，但分别定位资金账户与两条证券账户记录。按资金账号查看账户集合有意义；定位其中一个证券账户，则需要完整修饰符。

### 资产账户专表还保存了什么

`T03_AST_ACCT` 保存持有人、所属营业部、资金卡号、主账标志、内部资产账号，以及费用、折扣、委托方式、权限、限制和核算配置。**账户档案解释“这个账户怎么使用与管理”；余额另由余额模型记录。**

任务35803的加工有两项明确取舍：

- **部分属性按资产属性切换来源**：`ASSET_PROP='B'` 时，费用类型、折扣模板、允许委托方式、权限、限制及盈亏计算方式取期权资金账户表；其他情况取 `A_FUNDACCOUNT`。连接条件是客户号和资金账号。这里的B保留源代码，不另猜其完整业务定义。
- **RCC与ICC并非简单全量拼接**：ICC分支要求匹配当日现金账户记录且 `CASHGROUP_NO<>'12'`，再排除当日RCC中已存在的同资金账号。也就是该实现对重叠账号优先保留RCC分支。

账户身份与专用属性是两件事：相同的 `FUND_ACCOUNT / 10201`，其部分属性可能由关联表补充，能否入模还受来源筛选影响。

证据：[[00-20260911-认知实验/t03专题-协议/证据/SQL/35362.json|证券账户35362]]、[[00-20260911-认知实验/t03专题-协议/证据/SQL/35803.json|资产账户35803]]。

## XPB：先理解父子账户，再看模型如何保存

### 为什么这里不只有一个“资金账号”

这里的PB是主经纪商业务，XPB是迅投PB主经纪商系统。阅读它的账户数据，需要分别知道：系统内部管理的是哪个账户对象、它对应哪个资金账号、又关联哪个产品。这三个问题可能使用不同编号。

从任务130260实际读取的源表看，XPB把信息分在父账户和子账户上：**父账户保存可被引用的账号与共用属性，子账户保存自身身份及子账户侧的管理信息。** 子账户通过 `PARENT_ACCOUNT_ID` 找到父账户。这样的结构允许多个子账户引用同一父账户，而不必把它们的内部身份合并。

这里能确认的是信息分工：父账户有名称、账户类型、平台编号；子账户有自己的ID、公司编号、剩余资金比例和交易类型。至于子账户在业务上是否专用于某个策略、交易员或资金分配单元，这份SQL没有说明，不能给它补上一个未经确认的用途。

### 用两个子账户的例子看“身份”和“账号”的区别

下面是依据连接规则构造的例子，不是真实业务数据：

- 父账户：内部ID为 `P10`，`NAME` 为 `F888`。
- 子账户：`S01`、`S02`，两者的 `PARENT_ACCOUNT_ID` 都为 `P10`。
- 产品关联：父账户 `P10` 通过一条main类型的产品—账户关系关联产品 `PR01`。

按已读T系列分支的加工规则，两条子账户记录会形成：

| 模型中的对象 | `Agt_Id` | `Agt_Modifr` | `Fnd_Acct` | `Bel_Prd_Id` |
|---|---|---|---|---|
| 子账户S01 | S01 | 1020201-XPB | F888 | XPB-PR01 |
| 子账户S02 | S02 | 1020201-XPB | F888 | XPB-PR01 |

**两行资金账号相同，是因为它们引用同一父账户；两行仍分别代表两个子账户。** 所以查“系统里管理了几个子账户”和查“涉及几个资金账号”，可能得到不同结果。产品编号在两行重复，也是同一父账户关联被带到了各子账户上，不表示有两个产品。

这里还有一个命名细节：源列叫 `NAME`，但任务把它写入目标 `Fnd_Acct`（资金账户）。可以确认该字段赋值；它是否始终保存券商侧实际资金账号，还需源系统说明或样例确认。

### 模型怎样把这几层信息组合起来

目标表叫 `T03_PB_FND_ACCT`。该任务以子账户为起点，补齐父账户属性和产品归属；因此在这个来源分支中，它保存的是**子账户身份及其关联的资金账户信息**。

```mermaid
flowchart LR
  A[子账户：独立ID及自身管理信息]
  B[父账户：账号、类型、平台]
  D[产品—账户关系：限定main类型]
  E[产品：产品代码]
  A -->|父账户ID| B
  B -->|账户ID| D
  D -->|产品ID| E
```

| 取数位置 | 具体源表与字段 | 写入模型的内容 |
|---|---|---|
| 子账户A | `T_ACCOUNT_SUBACCOUNT` 的 `ID / COMPANY_ID / FUND_PROPORTION / STK_TYPE` | 协议身份、持有人、剩余资金比例、交易类型 |
| 父账户B | `T_ACCOUNT_ACCOUNT` 的 `NAME / TYPES / PLATFORM_ID` | 资金账户、账户业务类型、内部平台编号 |
| 关联D | `T_PRODUCT_ACCOUNTS` 的 `ACCOUNT_ID / PRODUCT_ID`，限定 `ACCOUNT_TYPE='main'` | 找到父账户对应的产品关联；main是这张关系表的筛选值 |
| 产品E | `T_PRODUCT_PRODUCT.CODE` | 非空时加 `XPB-` 前缀，写入所属产品编号 |

实际连接依次是 `A.PARENT_ACCOUNT_ID=B.ID`、`B.ID=D.ACCOUNT_ID`、`D.PRODUCT_ID=E.ID`。可见所属产品是沿父账户找到的，子账户自身并未直接提供这个产品代码。
### 同一任务有两套子账户来源

| 来源分支 | 协议身份 | 持有人身份 |
|---|---|---|
| `T_ACCOUNT_SUBACCOUNT` + `T_ACCOUNT_ACCOUNT` | `A.ID / 1020201-XPB` | `XPB008-A.COMPANY_ID` |
| `P_ACCOUNT_SUBACCOUNT` + `P_ACCOUNT_ACCOUNT` | `A.ID / 1020201-XPB-02` | `XPB021-A.COMPANY_ID` |

两套分支通过 `UNION ALL` 汇合，协议类型都为 `1020201`，修饰符区分来源身份；两者的产品连接均使用T系列产品关系表。T/P各自的完整业务分工尚未确认，不能只凭前缀命名。

还有两个直接影响理解的加工细节：

- `Pb_Acct_Busi_Type_Cd` 实际对父账户 `B.TYPES` 转码；映射筛选却写 `SRC_TAB_NAME='ACCOUNT_SUBACCOUNT'`。因此解释取值时应跟随真实表达式。转换未命中时保留原 `B.TYPES`；CD239的“资金账号、股东账号、交易卡号”等含义需结合目标码值核对。
- 本任务两分支的 `Brok_Id`、`Brok_Org_Id` 均填空。仅凭这张表的这些字段无法回答“对应哪家经纪公司及营业部”；`Agt_Holder` 则是按公司来源编号拼出的持有人身份，不能直接替代经纪商角色。

目标按业务日期和来源分区保存；上述是字段与关联构造，源端关系是否唯一仍需样例或约束核验。HPB、GPB的账户层级另查其实现。
