# 订单与办理：从提出请求到业务完成：模型与加工证据

业务背景与模型定位见[[00-20260911-认知实验/t03专题-协议/业务专题/订单与办理|订单与办理：从提出请求到业务完成]]。本篇按需核对源字段、身份构造、连接、转码及时间维护，不作为必须顺序阅读的课程。

## 订单：办理过程、投资指令与成交结果的分层

### 保险订单

任务 105812 从 PRD（产品中心）的 `P_INSURANCE_ORDER` 读取 `ID`，以 `2040210` 为协议修饰符及类型写入 `T03_ORD`，状态来自源 `STATUS` 的转码。这是一条具体的保险订单分支，而不是证券委托成交分支。

代码域 CD283 的订单类型还包含预约、咨询、潜客转化和流失挽回，部分记录备注限定金钥匙订单。由此可以确认，订单这个模型词覆盖业务办理过程，不是一个天然可汇总为成交笔数的统一事实。若用 T03_ORD 的总行数描述“交易次数”，会把不同业务行为混在一起。

更合适的方式是先按来源和订单类型形成业务集合，再解释状态，以及订单连接的主体、产品或账户。订单状态与支付状态也应区分：提交成功、支付完成、业务生效、签署完成是否对应不同字段，要逐来源确认，不能由一个“正常”码值包办。[[00-20260911-认知实验/t03专题-协议/证据/SQL/105812.json|105812]]、[[00-20260911-认知实验/t03专题-协议/字典/核心代码域与码值.json|代码域导出]]。

### 网上开户订单是一项办理记录

网上开户订单模型 **T03_OAO_ORD_INFO** 的已读分支从 OAO（网上开户系统）`C_TSYS_ORDER` 取 ID，修饰符 2040204，UUID 另存申请编号。它同时记录订单状态、处理步骤、审核人员及时间、最终审核结果、电话回访、激活标志、销户标志、跑批状态等。

这些字段将一项业务办理拆为不同判断：审核通过不等于激活成功；跑批状态不等于开户状态；销户标志也不是订单本身的删除标志。订单业务参数和账号信息仍以字段保存，不能从一条订单自动推导已经形成几张账户。

来源读取条件为业务日期大于等于 D−180，没有在所读条件中加上界。目标仅按来源分区。它意味着这份任务包含滚动读取和目标维护逻辑，不能当作一份按 D 日新发生订单切片的简单装载。[[00-20260911-认知实验/t03专题-协议/证据/全域分支补充/SQL/51626.json|51626]]，86–152 行。

### 智能条件单把半结构化指令拆成字段

智能条件单模型 **T03_INTEL_COND_ORD** 的已读分支从 BCE（经纪业务智能条件单系统）的数据导出表 `S_MICRO_IPO_DATADUMP_DATADUMP` 读取 ORDERID、ACCOUNT 和 DOC。模型身份为 ORDERID/204020701，资产账户为 ACCOUNT/10201；DOC 内的日期、市场、证券、触发条件、状态、柜台委托号、失败原因等通过 JSON 表达式提取，还连接柜台账户补机构、连接转换表统一市场和状态。

这里既有指令与触发参数，也有执行申报量、成交量等来源字段。它确实比保险订单更接近交易，但仍不能把条件单创建、触发、提交柜台和成交混为一次动作；要按需要选择阶段字段。保留原 DOC 也很重要，它是回查源指令结构的入口。[[00-20260911-认知实验/t03专题-协议/证据/全域分支补充/SQL/80254.json|80254]]。
