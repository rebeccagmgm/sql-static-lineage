# 模型表达维度：同一个对象有哪些不同信息

阅读目标：固定一个已经认识的业务对象，分清它的身份、属性、关系、组成、业务事实和控制信息。这些是解释角度，不是要求所有表只能属于其中一类，也不是一条表生产流水线。

## 用一份合约贯穿理解

| 信息方面 | 在问什么 | 实际表达方式 |
|---|---|---|
| 身份 | 这是哪一份对象？ | 协议编号和修饰符，通用模型为 `T03_AGT` |
| 属性 | 它叫什么、是什么类别、处于什么状态？ | 名称、类型、分类、状态、日期等；既可在主表，也可在通用属性表 |
| 关系 | 谁参与、关联什么账户或产品？ | 主表引用字段或协议主体、协议关系、产品关系表 |
| 内部组成 | 合约内部怎样拆出不同条件或支付部分？ | 互换腿、期权子交易、观察日期等各自的明细 |
| 业务事实 | 某时点记录多少持仓、余额或结算结果？ | 在对象身份上增加标的、币种、日期、头寸等维度 |
| 控制与安排 | 适用什么权限、额度或参数？ | 权限、限额、履保参数等；要与已用额或处理结果区分 |

同一张专表可能保存其中多方面内容。例如两融合约表既引用账户，又保存成交金额和归还信息。因此不能把这些方面简单切成六类互斥表，也不能用模型数量代替业务对象数量。

## “业务分类”和“属性分类”究竟差在哪

“互换合约”用来辨识对象种类；“这份合约在某种业务分类下是什么角色”是在给同一个对象增加描述。类别与类型通过 `Agt_Cate_Cd / Agt_Type_Cd` 表达；分类表通过 `Agt_Clas_Type_Cd` 指定分类问题，`Agt_Clas_Cd` 给出该问题下的答案。

例如本地字典将 `AB_MAIN=主合约` 限定在分类类型05，把 `DAD=见款付券`、`FOP=纯券过户` 限定在类型07。它们回答不同问题，不能与“账户、互换、订单”放在同一层排成分类树。这是码值定义的例子，不宣称同一条业务记录同时具备上述取值。

类别与类型如果存在确定的上下级对应，确实可能有信息冗余；分类属性则未必由对象类型唯一决定。具体代码范围见[[00-20260911-认知实验/t03专题-协议/字典/分类状态额度与转码|字典解释]]。

## 关系与内部组成也要分开

合约关联账户，是两个独立对象之间的关系；一份互换有几条腿，是它内部结构的展开。两者都可能产生多行，但业务含义不同。通过关系找到另一个对象时使用关系两端身份；读取内部明细时，还需该明细自己的腿号、子交易号或序号。
