## 1. 连接条件来自哪里

| 连接方向 | 已见证据 | 不应省略的条件 |
|---|---|---|
| 活动→专项详情 | WOS007 主表与直播详情都生成 `WOS007-` + `ID` | 同来源、同数据范围；先确认各侧唯一性 |
| 策略→活动 | MIO015 专门关系表，关系类型 `01` | 来源分支、有效期、名称匹配是否唯一 |
| 活动→服务事件 | RMS010 产生 `RMS011-ACT-` → `RMS005-SERV-` | 关系类型、两端前缀、关系有效期 |
| 活动→日程→员工 | RMS051 日程号连接 RMS052 的 `Sched_Id` | 员工参与类型，计划与实际不能合并计数 |
| 礼品→归属人 | PRD058 关系类型 `01` | 券身份、关系时间与当事人编号体系 |
| 合集→元素 | RMS079 集合与 RMS081 元素由 RMS080 关联 | 内容类型、排序、有效状态；不能把元素号当活动号 |

证据：[策略关系](attachments/差异与待核问题/IMG-差异与待核问题-20260914110643041.sql)、[服务关系](attachments/02-关系时间与连接/IMG-02-关系时间与连接-20260914110643755.sql)、[日程参与](attachments/02-关系时间与连接/IMG-02-关系时间与连接-20260914110647398.sql)、[归属关系](attachments/02-关系时间与连接/IMG-02-关系时间与连接-20260914110647452.sql)、[合集元素关系](attachments/02-关系时间与连接/IMG-02-关系时间与连接-20260914110650569.sql)。

## 2. 三个不能直接按同名字段连接的例子

**产品中心活动。** 主表 167365 写 `PRD086-` + `ACTIVITY_ID`；产品关系 165629 把裸 `ACTIVITY_ID` 写入 `Prom_Id`。这是已读 SQL 的编号差异，不能直接等值连接，也不应擅自全量去前缀。是否存在源号已带前缀、后续修正或其他消费映射，需另证。

**CPL 客群。** 86912 分群规则写裸 `ID`，143762 关系左端写 `CPL001-` + `CLUSTER_ID`。规则还按名称保留最大 ID，一项旧关系的规则端点可能不在该快照中。对齐编号与确认版本是两个独立问题。

**RMS 合集。** 134984 的 `Set_Id` 加 `RMS079-`，但 `Prnt_Set_Id`、`Drft_Set_Id` 直接取源 `PARENT_ID`、`DRAFT_ID`。自连接之前要核对是否需要同来源的编号转换。

这些是静态差异，不是已验证的线上断链。[差异台账](00-20260911-认知实验/t07专题-营销/证据/差异与待核问题.md)

## 3. 把四种时间分开

| 时间 | 回答什么 | T07 例子 |
|---|---|---|
| 活动业务时间 | 何时开始、结束、开放报名 | 活动起止、直播实际开播、报名窗口 |
| 关系或状态版本 | 在哪个区间成立 | `Strt_Date <= d AND End_Date > d` |
| 观察时间 | 何时统计、分群、执行、更新 | `Seg_Time`、`Exec_Time`、源统计值的观察日 |
| 采集与分区时间 | 读取哪个源快照，写到哪里 | `Busi_Date`、`Data_Etl_Date`、`Data_Time`、`Src_Tbl` |

消息广播 99670 读取当日源快照，却按消息 `TIME` 的日期写分区，并限制近七天；定向消息 99671 回看含当日在内的四个源日期。不能从一次调度日期推断只处理当天业务。[消息 SQL](attachments/04-消息分发与回访/IMG-04-消息分发与回访-20260914110643014.sql)、[定向消息 SQL](attachments/04-消息分发与回访/IMG-04-消息分发与回访-20260914110645151.sql)

MIO 某些字段显式加 8 小时，而另一些直接取源值。这是字段级加工事实，不能统一对整表再加 8 小时。[MIO 活动](attachments/01-活动内容与销售安排/IMG-01-活动内容与销售安排-20260914110643001.sql)、[定向策略](attachments/02-策略模型与规则/IMG-02-策略模型与规则-20260914110648217.sql)

## 4. 历史表怎样使用

已读 MIO015 策略活动关系按调度日取新快照，与当前开链记录比较；变化时关闭旧版本并建立新版本。结束日按左闭右开解释，开放结束日为 `2099-12-31`。[完整维护 SQL](attachments/差异与待核问题/IMG-差异与待核问题-20260914110643041.sql)

这说明的是**加工观察到的关系历史**。源系统晚到变更，或一天内发生多次变更，是否完整保留还需要源事件与运行证据。活动本身的开始结束时间也不是关系历史的生效边界。

`t07_prom_stati_info_h` 同样带有效期，但存的是统计值变化的版本。某直播 PV 先为 100，后为 150，两行历史相加为 250 没有合理的“总浏览”含义。应先选时点，再解释该来源的计数方式。

## 5. 防止一对多关系把金额或次数放大

一场活动若有 3 个产品、2 个主办员工和 100 个报名记录，三张明细直接 Join 后可能形成大量组合。不能随后 `SUM(活动金额)` 或 `COUNT(*)` 当作活动效果。

先定义输出粒度；每一类明细先按该粒度去重或聚合，再连接。对于参与人，要保留身份类型；对于员工，要保留角色；对于指标，要保留类型、单位、日期及观察范围。这个例子是说明连接风险，不是本次查得的业务样本。
