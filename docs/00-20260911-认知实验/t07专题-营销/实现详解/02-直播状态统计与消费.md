| [88565](attachments/02-直播状态统计与消费/IMG-02-直播状态统计与消费-20260914110646204.sql) | `t07_live_act_info` | 主播、计划与实际时间、受众约束及直播属性 |

| [88665](attachments/02-直播状态统计与消费/IMG-02-直播状态统计与消费-20260914110652223.sql) | `t07_prom_stati_info_h` | PV、UV、点赞等观察值的历史 |

四段均显示对 `IS_TEST_USAGE` 的过滤，但保存的状态和数量口径不同。过滤相同不代表字段值已完全同义。

## 2. 主表转码，历史表直接存源状态

88559 主表使用 `NVL(DW_CD_VAL, STATUS)`；88565 详情也调用状态转换；88662 状态历史却直接将 `STATUS` 写入 `Prom_Stat_Cd1`，类型为 `01`。

因此，“同一直播、同名状态列”不保证主表与历史值相同。主表还有转换失败回退源值的机制，可能混存仓库码与源码。使用历史做状态筛选前，需要按来源核对原状态域；不能照搬主表 `Prom_Stat_Cd='4'`。

这项差异来自已读 SQL，不是已经查得了线上错数；转换表内容与实际行值未核验。

## 3. 统计类型是可见的具体投影

88665 将同一直播拆成三种统计类型：`02` 对应 PV、`04` 对应 UV、`01` 对应点赞，值放入 `Stati_Num_Info`。这几个含义由该分支 SQL 直接支持；本地代码域清单未命中 `PROM_STATI_INFO_TYPE_CD`，不伪造全局统计字典。

源字段已经是统计量，本段没有明细去重过程。UV 是按什么用户身份、什么窗口去重，本次没有源统计定义。按历史有效期选某时点的记录，也不能把跨活动 UV 直接相加当总人数。

## 4. 短视频提供“来源声明≠实际读取”的例子

88560 的注释仍指向 `T_MEDIA`，实际读取 `F_TR_MEDIAS`；88664 统计分支也读取 `F_TR_MEDIAS`，并明确写 `Real_Src_Tbl` 为该表。它给点赞、PV 和热度分别生成统计行。[短视频主表](attachments/01-活动内容与销售安排/IMG-01-活动内容与销售安排-20260914110647990.sql)、[短视频统计](attachments/02-直播状态统计与消费/IMG-02-直播状态统计与消费-20260914110654372.sql)

对来源的解释至少分开：源说明、真实 FROM、目标 `Src_Tbl`、`Real_Src_Tbl`。不能看到旧来源分区名就断言仍直接读取旧表。

## 5. 下游怎样进一步缩小业务范围

104076 的销售关联分支选取有 T05 直播销售事件的直播，限制直播业务类型、`Prom_Stat_Cd='4'`、`del_flag='0'`，提取主播信息后再连接 T04 用户员工关系。[SQL](attachments/00-全貌与范围/IMG-00-全貌与范围-20260914110650127.sql)

121294 的历史 SQL 还显示，直播汇总需要组合、T08 直播入口、观看指标及产品关联等资料。该快照存在压缩语句，因此这里只用它说明消费引用范围，不把其完整汇总口径标为已审计。[历史消费快照](attachments/02-直播状态统计与消费/IMG-02-直播状态统计与消费-20260914110655492.sql)

部分消费引用字段如 `Live_Busi_Type` 未在较早解析字段列表中出现，较新目录有更丰富字段记录。应结合两份结构及任务 DDL 核对，不能仅凭旧字段缺失判定消费无效。

## 6. 可以怎样正确提问

“指定来源、指定有效时点，处于已核对状态的直播有多少”需要对象与版本筛选；“观看人数”需要去重身份和统计窗口；“销售额”还需要销售事实与归属规则；“带来的增量销售额”则需要额外的因果评估。T07 本身不能替代后面这些证据。
