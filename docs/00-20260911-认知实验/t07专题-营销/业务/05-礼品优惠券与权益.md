## 1. 先认清四类对象

| 对象 | 核心问题 | 典型表 |
|---|---|---|
| 礼品资源 | 有什么礼品、限制、总量和剩余量 | `t07_gift_info` |
| 优惠券专项属性 | 券适用什么产品，优惠规则和记账规则是什么 | `t07_prd_coup_adtnl_info` |
| 活动/当事人关系 | 礼品属于哪个活动，归哪个主体 | `t07_prom_gift_rela_info`、`t07_gift_pty_rela_h` |
| 权益与页面配置 | 提供什么服务资格，如何展示、领取和关联产品 | `t07_equi_info`、`t07_meg_equi_cfg_info`、`t07_meg_oper_prom_gift_adtnl_info` |

这四类表不自动形成统一的“礼品发放流水”。本次未把库存变化、归属关系或活动配置当成真实发放/核销记录。

## 2. PRD016 优惠券主资料与附加属性

79213 从 `P_SRV_COUPON` 生成 `Gift_Id=PRD016-ID`，保留总量、剩余量、领取限制、生效及到期时间；状态经映射后回退源值。79218 对同一来源生成 `Gift_Coup_Id=PRD016-ID`，保留券的专项属性。[主资料](attachments/05-礼品优惠券与权益/IMG-05-礼品优惠券与权益-20260914110643016.sql)、[附加属性](attachments/05-礼品优惠券与权益/IMG-05-礼品优惠券与权益-20260914110645293.sql)

两端业务身份可以对照，但同来源范围、删除和有效期仍要限制。目标礼品类型固定写 `10`，本地 CD468 的 `10` 为“权益积分”，并非“优惠券”。这是值得复核的代码语义差异；不能为了贴合表名把它改解释为 `01`。

附加属性的券类型映射使用 `REF_CD_CVT_MAP_TEMP`，不是自动等于标准转换表。字段注释与加工引用均应保留。

## 3. PRD058 新客理财券与归属

PRD058 相关 SQL 中，券身份为 `PRD058-ID`；活动礼品关系的 `Prom_Id` 直接取源 `ACTIVITY`，类型为 `NEW_CUST_CHREM`。礼品当事人关系用类型 `01` 记录源 `CLIENT_ID`。[活动礼品](attachments/05-礼品优惠券与权益/IMG-05-礼品优惠券与权益-20260914110649125.sql)、[礼品归属](attachments/02-关系时间与连接/IMG-02-关系时间与连接-20260914110647452.sql)

CD1197/01 的本地含义是“归属”。它不能证明客户在关系开始日实际领取了券，更不能证明用了券。该来源的活动号与 PRD086 销售活动是否同一身份，本次没有据此建立通用关系。

这些快照含固定渲染日期和部分压缩 SQL，本文只使用可见投影与关系信息，没有将其完整维护过程标为当前已核验。

## 4. MSA 权益配置

146679 将 `I_MAGIC_EQUITY_CONFIG` 的权益编号拼为 `MSA016-ID`，权益类别、形式、适用等级、价值、领取限制/方式等来自源配置。相应 MEG 权益表还含展示文案、券号、产品关联、跳转与运营中台接入标志。[SQL](attachments/05-礼品优惠券与权益/IMG-05-礼品优惠券与权益-20260914110651822.sql)、[字段](attachments/来源与覆盖/IMG-来源与覆盖-20260914110644101.json)

不要看到 `Equi_Val` 就当成实际收入，看到关联产品号就当作已售产品。`EQUI_CATE_CD` 的本地代码域同时存在证券权益类别和营销服务权益条目，需要按来源和码值核对；不能把整个同名域机械解释为营销权益。

## 5. 礼品分析先定计量对象

如果问题是“还有多少可用礼品”，先确认在数配置总量、券数量、批次余额还是服务资格；再限制来源、有效窗口、状态和删除标志。不同来源的总量/剩余量未必具有同样的单位或守恒关系。

如果问题是“某活动发给了哪些人”，活动礼品和礼品归属只能提供关联候选。需要发放/领取/核销事件及成功状态，才可回答实际发生。香港礼品还有独立的批次及库存模型，见[下一章](00-20260911-认知实验/t07专题-营销/业务/07-香港礼品与库存.md)。
