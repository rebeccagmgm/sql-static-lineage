## 1. T98 的来源可以来自不同层

已读员工、机构资料宽表从 T04 模型拼接属性；全产品销售的一支从 T05 交割事件取数，并用 T02 补产品分类；场外销售基础表的四支直接读取 TIT 贴源数据；场外附加明细又读取 T98 基础表并补充事件和持仓。

因此，不能预设每张 T98 都只从 T01—T10 加工，也不能预设进入 T98 后就已完成全部业务计算。来源与消费在代表页按具体 SQL 说明。

| 已读路径 | 能确认的内容 | 仍不能确认 |
|---|---|---|
| T04 → 员工／机构宽表 | 资料选择、历史条件、目标写入 | 实际一对象一行、全部来源完整性 |
| T05 + T02 → 客户销售 | 一支流水筛选、聚合、分类补充 | 全品类全来源销售口径 |
| TIT 贴源 → 场外销售基础 | 四个写入任务的目标表和 grp_id 分支 | 当天运行、全部合约覆盖、结果正确性 |
| 场外销售基础 → 附加明细 | 日期展开、分支计算、写入日期 | 每个连接的实际基数、金额验收 |
| 场外基础 + OIS 等 → 管理关系 | 合约级与客户级归属资料的选用 | 分配比例单位、总和约束、实际重复 |
| 配置 + 估值数据 → 指标结果 | 按科目、账户及列名选择值 | 配置唯一性、下游展示及实际用户取数 |

## 2. 逐表索引为什么仍叫候选

1,727 份任务 SQL 文本包含 T98 名称。本次按三种方式索引到表：完整 schema.表名、未限定表名加头部默认库提示、无默认库的未限定名称。三种方式在[覆盖表](证据/逐表SQL候选覆盖.md)中分列。

文本出现的位置可能是读取、写入、建表、注释、脚本头或未启用代码。完整表名也不能消除不同数据源的身份歧义。只有代表页进一步读了语句上下文的关系，才写成“该 SQL 写入／读取”。

这个区别尤其影响未限定库名的 T98 写入：只检索 `pdata_n.t98_...` 会漏掉 `INSERT ... T98_...`。本次保留默认库提示，但没有把提示升级为唯一物理绑定。

## 3. 组合属性表是独立消费入口

本地组合类型快照有 47 条配置在属性表字段或定义 SQL 中涉及 T98，其中 42 条声明了 T98 属性表，合计 11 个表名；27 条定义 SQL 也包含 T98 名称。两类数量有重叠。

例如，`BRANCHOFFICE` 的组合成员定义读取 T04 机构及关系，而属性表配置指向 `t98_org_inr_org_base_info`。两者职责分别是确定成员集合和补充成员属性，并不要求从同一张表生成。详见[配置原文与索引](资料/组合属性配置索引.md)。

配置中的 `BUSI_DATE,INR_ORG_ID` 等是应用声明的匹配字段；不是已经证明的数据唯一键。托管管理人的不同配置还分别声明 `BUSI_DATE,PTY_ID` 与 `BUSI_DATE,ORG_CD`，不能只看属性表名就采用同一个连接键。

资产目录另外找到 6 条与本次候选任务集合有关的资料关联记录，涉及 4 个指标和 1 个标签维度；标签详情与标签目录各有一条记录，不能算成两个标签。它们见[任务关联资产](资料/任务关联资产.json)。这些是原资料声明的关联，未完成指标定义、任务 SQL、目标字段和下游展示的一一核验。

本次对标签 SQL 和指标定义字段的 T98 字面搜索未命中；这只说明这些字段中未出现目标字符串，不能解释成 T98 没有标签或指标消费者。

## 4. 存量图谱用来补什么

复用了现有加工地图的只读 CLI，对 `pdata_n.t98_otc_deri_comp_sale_info` 查询一次存量邻域。返回 25 个节点、24 条边，包含四个写入任务；结果因 `NEIGHBOR_LIMIT` 截断。查询未生成新投影，结果与版本保存在[代表查询](证据/存量图谱代表查询.json)。

四个写入目标和分区另经 SQL 核对。其他返回的读取边仅按存量投影证据保留，没有逐条验证，也没有把这个有界邻域称为全部消费者。此处消费的是已保存的投影，不据此判断图库实时服务是否可用。

## 5. 真正取数前的连接顺序

先确定具体物理对象，再选择来源分区及业务时间；随后确认两侧各自的一行含义，最后检查连接是否把事实展开。名称相近、字段同名、有图上的边，都不能代替这几个判断。

取场外销售归属时，先保留基础事实的业务日、分支及合约身份，再研究管理关系是否需要合约级优先、客户级补充和多槽位展开。实际是否一对一、是否漏匹配或重复计量，仍需业务行数据验证。本版没有对这些性质作保证。
