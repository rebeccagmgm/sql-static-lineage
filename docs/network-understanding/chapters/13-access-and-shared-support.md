# 权限与人员：谁在什么系统中，能操作什么对象

权限加工把员工、系统账号、角色和资源关系整理成核查清单。它解释了为什么股衍加工网络会连接柜台、资管、算法、财务等许多系统：当前图中的这部分连接服务于人员和权限汇总，不意味着这些系统的全部业务都属于股衍交易流程。

本章覆盖 `DM_CTMS_N` 的 17 项：跨系统人员角色汇总及导出、TITANS 六种权限清单及导出，以及三项邮件任务。14 项取得 SQL，其中账簿、标的池两个导出查询来自当前 Pack 补证；邮件正文和执行配置仍缺失。公共用户、角色和权限对象怎样入模，先见[组织与权限模型](../topics/organization-and-access.md)。

<a id="access-four-objects"></a>
## 先分开员工、账号、角色和资源

| 对象 | 回答的问题 | 在本章中怎样连接 |
|---|---|---|
| 员工 | 这个人是谁，属于哪个部门、什么岗位或任职状态？ | ERP 编号、OA 账号、员工部门资料 |
| 系统账号 | 他在某个系统中使用哪个登录身份？ | 系统内部用户号，或统一模型中带来源前缀的用户号 |
| 角色 | 账号通过哪一组授权获得权限？ | 用户角色关系和角色定义 |
| 资源与操作 | 对哪个菜单、账簿、标的池或定价环境，有什么操作权？ | 角色资源关系、资源类型、操作代码和资源名称映射 |

一个员工可以有多个系统账号，一个账号可以有多个角色，一个角色可以关联多个资源。所以清单中一行通常是某种“账号—角色—资源”的组合，不能直接用行数统计员工人数。没有匹配到员工资料，也不等于系统账号不存在。

<a id="tit-user-roles"></a>
## TITANS 角色清单保留什么人

207500 从统一用户模型读取 TITANS 来源、用户类别 50、`Del_Flag='0'` 的用户；通过类型 12 的用户属性取外部 OA 编号，再连接用户角色关系、角色定义和 TITANS 员工部门表。用户属性和用户角色关系取 `End_Date='2099-12-31'` 的当前版本，角色要求未删除。

用户状态 101、102、121 分别展示为正常、冻结、注销。SQL 没有只保留正常用户；“未删除模型记录”与“正常可用账号”是两个条件。其他状态没有 `ELSE`，会落成空值。

员工部门连接使用外部 OA 编号，员工来源行要求 TITANS 编号和 ERP 编号非空；但这是左连接，匹配不到的人仍可留在结果中，ERP 或部门为空。这张角色清单也没有对同一 OA 的多条员工部门记录先选一个版本，因此实际唯一性取决于来源。

输出业务日是参数日期，注册日期由开户日期去除横杠得到。表名后缀 `rt` 不能证明本次清单正在实时更新；当前 SQL 展示的仍是按业务日保存的结果。207507 导出参数日记录，并把用户名、部门、角色的空值改为一个空格。空格是接口占位，不能当作已补齐业务内容。

<a id="tit-menu-rights"></a>
## 菜单和功能：四级菜单加第五级功能

207529 沿同一用户和角色关系构造一到四级菜单，再把角色下的功能接到第四级菜单。菜单使用父菜单编号逐层连接，功能使用功能—菜单映射；最终第五级展示的是功能编号和名称。

菜单授权关系取当前结束日期，功能资源则从角色权限历史表筛资源类型 52。后者在这份 SQL 中没有按 `End_Date` 再筛当前版本；不能把用户角色取当前版本的条件自动套到功能权限上。功能权限的访问类型通过码表反向映射回来源值，但最终输出没有访问类型列。因此这张菜单清单不能用来区分同一功能是只读还是可写。

多条员工部门记录在这里与角色清单处理不同：按 OA 分组，按部门名称降序选一行。它不是按生效时间选最新部门；名称相同但其他资料不同的行，也没有更细的排序规则。

每层菜单是左连接，可以出现只带部分层级或空菜单的账号行；但较深层级必须通过父菜单编号接到上一层。如果某个角色只出现深层授权而缺少对应祖先层，这个查询不能凭空补出完整路径。结果适合检查展示路径，不能单靠第五级为空判定这个账号没有任何功能授权。

207617 导出参数日的菜单列，但没有导出本地清单中的 `user_status`。因此消费端仅凭这份导出字段不能区分正常、冻结与注销账号。

<a id="tit-counterparty-rights"></a>
## “交易对手权限”展示的是业务分区，不是客户名单

207571 读取角色资源类型 51、权限代码 08（SQL 注释对应 `READWRITE`），再把资源编号 10001—10011 映射为股衍、资管、公共、香港业务、固收等业务分区名称。这里的 `counterparty_name` 并不是客户主体表中的逐个交易对手名称。

只要资源编号非空，就显示“读写”；未知资源编号会落成空格名称。用户和角色采用左连接，未匹配到这一种资源的账号仍可能留下空资源行。查询没有枚举只读权限，也没有筛角色资源历史的结束日期。

因此，这张表可以解释哪些角色关联了所列业务分区的读写授权，不能代替某一客户的业务关系、合同归属或逐客户访问清单。207618 只是导出参数日这些字段。

<a id="tit-book-pool-pricing"></a>
## 账簿、标的池、定价环境使用另一条来源链

208179、208180、208181 直接读取 TITANS 源侧用户、用户角色、角色资源和员工日快照，没有使用前面统一用户模型的 `Del_Flag` 筛选。各源表取参数业务日，员工资料允许任职状态为空或 `CURRENT_POST`。

| 清单 | 必须具备的资源条件 | 输出规则 | 关键边界 |
|---|---|---|---|
| 账簿，208179 | `RESOURCE_TYPE='BOOK'` | 按 OA、角色、账簿等分组；将 READ/DELETE/UPDATE/WRITE 翻译为查/删/改/写，去重拼接 | 其他操作代码译为空；没有把所有权限概括为读写 |
| 标的池，208180 | `INSTRUMENT_POOL` 且 `READWRITE` | 连接当天标的池配置，固定显示读写 | 只读池权限不在这一清单中；池编号未导出，只保留名称 |
| 定价环境，208181 | `PRICINGENV` | READWRITE/READONLY 分别显示读写/只读；用定价环境曲线表补名称 | 环境名称找不到则回退资源编号；名称映射没有日期条件 |

这三项把 `RESOURCE_TYPE` 条件放在来源查询的 `WHERE` 中，虽然前面写的是左连接，最终仍要求匹配对应类型的资源。与会留下空资源账号的菜单、对手分区清单不同，它们不是完整用户清册。

三者先按 OA、资源编号、访问类型、角色名称做 `ROW_NUMBER`，排序只用该组内相同的 OA，并取第一行；这不能证明按时间选择了最新授权。同名角色的不同内部编号也可能在这个步骤相遇。账簿后续还按角色编号参与分组，但前面的选行条件没有用角色编号区分。

定价环境名称接到 `pdata_news_n.t02_fin_prcg_env_curv` 中 `src_id='TIT'`、`grp_id='02'` 的记录。连接键是资源号对 `rec_id`；没有去重或日期过滤，所以不能未经约束就假设每个权限只会匹配一条环境记录。这里展示的是环境访问权，不是采用该环境计算出的价格或敏感度。

208345、208346 的当前补充 SQL 分别导出参数日账簿与池清单；208717 的发布 SQL 导出定价环境清单。这些导出都没有携带业务日列，业务日只在查询条件中使用。当前证据不证明目标端保存了历史批次。

<a id="cross-system-access"></a>
## 跨系统汇总与权限导出

134442 将不同系统的账号、角色和部门信息整理为同一列结构，74272 再根据操作分支机构等条件选择导出记录。它们不是把 TITANS 清单简单复制一遍，而是含有 33 个可见系统或总部分类标签、不同的员工编号回退和状态翻译。

完整分支及导出差异见[跨系统人员角色汇总](../topics/cross-system-user-roles.md)。其中两点对全貌尤其重要：相同 `sys_num` 不保证在不同系统中指同一账号；机构所属部门与有权操作的分支机构也不是同一维度。

<a id="access-notifications-and-gaps"></a>
## 这些清单可以解释什么变化

若员工 OA 对照改变，ERP 和部门信息可能变化，但系统内部授权记录未必变化；若角色菜单映射改变，菜单路径可能变化，但不代表所有资源访问类型都被修改；若只读标的池权限新增，上述“仅 READWRITE”清单仍可能不出现它；若权限清单导出省略用户状态，消费端不能据此识别冻结账号。

139809、139813、139814 的名称说明它们与 PWC 员工部门变化或人员状态邮件有关，但当前范围内没有邮件正文或查询 SQL。这里只能定位其通知职责，不能确认发送条件、收件规则和业务已接收。

以上都是 SQL 实现及其合理解释。清单内容不是对实际授权是否生效的实机验证，也没有据此判定任何人的具体权限。
