# 先看整体：同一批业务事实，为什么会长成一整片加工网络

> 编写中的整体导读。这里已经核对范围与关键连接方式；各过程的深入章节及全范围内容审阅仍在推进。

## Executive Summary

**这片网络把“业务发生了什么”整理成多种可以使用的数据结果。** 交易系统保存交易、合约、账簿、对手方、持仓和资金记录；数据加工把这些记录落地、统一标识、关联历史、补充行情与归属；不同消费者再形成风控、财务、经营分析、销售考核和业务查询所需的结果。同一笔业务会被多次使用，每种用途保留的对象、时间和粒度不同。

**读懂整体，需要同时抓住业务对象、过程和口径。** 表之间相连说明存在可调查的读写联系，却没有自动回答“一行代表什么”“哪些记录被排除”“用哪天的归属”“金额为什么不同”。这些问题决定同一份合约事实为什么会变成不同的风险值、交割记录、日均规模和机构考核贡献。

**本书的范围还包括与股衍相连的公共及跨业务加工。** 当前发布图含有 3,615 个任务、2,903 个物理表身份、130 个 schema。schema 是数据库中的命名空间，不能直接等同于业务系统或部门。权限汇总、员工与机构、客户资产等共享加工会把其他业务的数据带入图中。因此，本书既要解释股衍主要过程，也要解释这些连接带来的周边部分；它们各自只代表当前图能看到的片段。[范围证据：scope-inventory.json](../evidence/scope-inventory.json)

## 先从三个问题理解这片网络

### 第一问：最初被记录的是什么？

想象你在跟踪一项场外业务：谁和谁发生业务，约定了什么合约，交易怎样变化，记在哪个账簿，持有哪些资产，资金与保证金发生了什么。交易、合约、账簿、账户、持仓、事件分别回答不同问题，不能互相替代。

例如，已核对的源交易表用 `KEY_OTC_TRADE_ID` 标识交易记录，同时另有合约相关的 `KEY_INSTRUMENT_ID`；源账簿表的声明主键包含账簿号和生效、失效日期。这意味着“交易号”“合约号”“某段有效期内的账簿版本”不能都简化成一个通用 ID。后续加工若只按名称理解这些字段，很容易把交易发生、合约存续与历史归属混在一起。源表定义及落地 SQL 的完整说明见源系统章节；这里先记住：**先辨认对象，再看它们如何关联。**

### 第二问：为了被共同使用，这些记录要经过哪些整理？

首先需要落地。源表被采集到数据平台，常常增加采集时间、按日期保留快照，或者生成面向不同批次的副本。这个阶段说明数据在哪里、以什么形式留下来，未必产生新的业务计算。

随后需要组织对象及关系：统一客户或证券标识，建立合约与账户、账簿、标的、员工及机构的关系，保留有效期，整理期权结构、互换资产腿、日持仓和资金事件。这里开始出现“用哪个编号连接”“取哪一个历史版本”“把哪些业务统一到同一种结果”的决定。

最后，各用途选择自己需要的事实和口径。财务接口关心业务类型、日期、账户、币种、交割金额；风险结果关心持仓、价格、敏感度、账户和保证金映射；销售考核关心合约规模、归属、比例和统计期间。它们从共享事实出发，各自组织结果。

### 第三问：为什么都来自同一份数据，结果却不能直接比较？

因为加工改变的不只是字段名称，还可能改变五件事：

| 需要分清的事情 | 读结果时应问什么 |
|---|---|
| 纳入范围 | 哪些业务类型、账户或状态被保留？哪些被排除？ |
| 时间 | 这是哪天采集的记录、哪天发生的业务、哪段计提期间、还是哪天的归属？ |
| 归属 | 金额属于哪个对手方、账簿、机构和员工？是否经过分配或机构调整？ |
| 计量 | 这是数量、余额、发生额、变化量、损益，还是经过分母处理的平均规模？ |
| 粒度 | 一行按合约、子交易、账户、客户、机构还是月份组织？哪些差异已被汇总掉？ |

这五个问题会贯穿各章。读懂它们，才能判断两项结果是否应该相等，以及发现差异后应该从哪里检查。

## 这片网络有哪些主要过程

下面是本书的过程组织，不把 schema 当成互斥的业务分类。同一张宽表可以进入多个过程，同一个过程也可能横跨多个 schema。当前表与任务目录为这些过程提供范围定位；各章继续用实际 SQL 和业务资料验证具体规则。

| 主要过程          | 这一部分要讲清的业务问题                               | 当前图中可见的材料入口                                   |
| ------------- | ------------------------------------------ | --------------------------------------------- |
| 源系统与数据落地      | 交易系统保存什么，什么被快照或转存，哪些数据又提供回业务系统？            | TITANS 各源域、ODATA_N_TIT、ODS_TITANS 及相关传输任务     |
| 客户、账户、账簿与公共标识 | 谁、什么账户、哪个合约、什么证券，怎样通过稳定编号和有效期连接？           | PDATA_N 的当事人、协议、账簿、账户、员工机构，以及证券公共数据           |
| 合约、交易、结构与持仓   | 期权结构、互换资产腿、交易事件和持仓分别代表什么，怎样形成可用模型？         | PDATA_N 的期权与互换模型、PDATA_NDS 源侧模型、相关日视图         |
| 行情、参数与估值输入    | 证券身份、价格、利率、汇率、曲线和参数怎样服务不同计算？               | PDATA_NEWS_N、定价因子与曲线、估值数据接口                   |
| 资金、清算与保证金     | 资金发生、账户余额、保证金账本、履保结果和清算事件如何联系？             | 保证金及资金账户模型、清算流水、保证金组合结果                       |
| 风险、损益与监控      | 合约风险、期权敏感度、互换损益、日内批次和曲线异常怎样形成？             | DM_RSK_N、风险源视图、相关持仓及账户结果                      |
| 经营分析与客户服务     | 日报怎样形成规模、创收、持仓、业务统计和客户观察？                  | DM_OTC_N 的合约日报、客户指标、业务统计和运管视图                 |
| 销售归属、标准资产与考核  | 合约贡献如何分给机构和员工，怎样进入日均资产、机构评价和零售考核？          | 合约销售及管理关系、DM_INDEX_N、DM_OM_N、DM_CO_N、相关人员考核输出 |
| 财务与估值接口       | 业务事件如何映射为交割流水、账户、币种和估值输入？                  | DM_FIN_N、GFVAL、相关财务落地与分发                      |
| 香港业务及跨境分发     | 哪些对象和业务分支进入香港数据产品，日终与日内材料有什么区别？            | DM_HK_N、香港相关模型、ODS_TITANS 与业务系统接口             |
| 固收用途及其他专业消费   | 同一交易和持仓基础如何服务北向期货、债券互换、期权规模与固收经营？          | DM_FII_N、相关持仓、资产腿和规模结果                        |
| 合规、报送、权限与共享支撑 | 交易与客户怎样进入合规数据，用户/角色/账簿权限如何跨系统汇总，调度如何支撑数据链？ | GFHEGUIDB、DM_CMPL_N、报送结果、DM_CTMS_N、质量检查与传输任务  |

这些过程的说明要接回输入与使用方。比如“风险”不会被写成与“资金”无关的一章：保证金账户与合约映射同时是资金管理的对象关系，也是风险结果的输入。“销售考核”也不能只解释公式：它必须接回合约、日规模、机构员工及有效关系。

## 为什么图里会出现许多看起来不属于股衍的系统

一个具体例子是跨系统用户角色汇总。任务 134442 的发布证据包含 27 个源 schema、115 个不同外部读取表名；最终输出按员工、系统、系统用户、角色、组织、用户状态等列组织。SQL 将多个来源分支合并，并补充员工岗位信息。这里连接许多系统，是为了汇总权限和人员信息，不能由此把这些系统的全部业务解释成一条股衍交易链。

这个例子也解释了本书的范围处理：**共享加工连接到的部分需要说明，其图外的整个业务系统没有因此被纳入。** 在权限这一部分，我们需要讲清用户、员工、系统和角色如何对应；没有证据时，不会顺带讲述其他系统全部交易流程。

证据：任务 134442 发布 `query` 的第 217—267 行为最终汇总，第 251 行补充员工岗位；其外部读取清单见任务目录。SQL 中的具体日期是该证据文本中的日期，不能直接作为当前每日运行配置。[任务底账](../evidence/task-catalog.json)

## 阅读主线与各部分之间的联系

建议先建立源对象和公共关系的认识，再进入合约、交易、持仓与资金。接着分别理解风险、经营和财务如何消费同一批事实；在销售贡献进入机构考核时，再学习日均、归属和标准资产的进一步处理。香港与固收部分说明相同基础在不同业务和分发场景中的变体。合规、权限和调度说明这些主要过程还依赖什么。

每章会就地解释用到的背景。阅读另一章是为了继续深入，不应成为读懂当前半句话的前提。关键规则旁边保留简短证据定位，原始 SQL、逐任务审阅和完整范围底账在附录中查阅。

## “完整说明”仍然需要明确边界

本书固定于当前发布快照，并区分三类认识：

- **SQL 确认的实现事实**：例如按什么字段关联、筛选哪个状态、怎样计算、向哪个结果写入。
- **依据实现和业务资料形成的解释**：说明这个处理解决什么问题，并标清解释依据。
- **尚待确认的内容**：例如真实输入是否唯一、某个代码是否仍代表原业务含义、结果是否已在业务端使用。

当前 857 个任务被发布材料标为预期调度引用，373 个被标为材料缺口。这两类都保留在范围里；前者应解释其支撑职责，后者需要逐项补证或说明对理解的影响。已匹配的源表元数据中还有 18 个对象带 `DELETED` 登记状态；它不等于已经证明物理表不存在，也不能省略后把对象一律写成在用。[范围与状态证据](../evidence/scope-inventory.json)

后续章节中的“计算日”指所分析 SQL 的参数日期或该快照中已展开的日期，“当前图”指本书固定的发布版本。解析成功、哈希一致和图连接成立，分别提供技术证据，不代替实际运行、数据到达或业务验收。
