# 01　业务怎样进入这片数据网络

这片网络把业务系统里分散记录的交易、对象、事件和参数，组织成可以继续计算与交付的数据。理解它，首先要分清三件事：业务动作在哪里发生；平台怎样保存和解释这些记录；结果最终交给谁。TITANS 在其中同时承担数据提供方和数据接收方，不能把整个网络看成一条只向报表流动的管道。

本章以固定发布中的 SQL 和精确物理身份匹配的表定义解释实现，以两篇业务文档补足用途。文档是当时的设计或职责说明；SQL 是已收集的实现快照，二者都不代替当前生产运行和实际使用的证明。来源及时间见[证据附录](../evidence/business-context.md)。

## 先建立一幅职责图

| 环节           | 在业务上解决什么问题                                 | 本章核实到的实例                                           |
| -------------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| 业务发生与记录 | 记录交易、主体、账簿、资金事件等业务事实             | TITANS 的交易、账簿、交易对手和保证金台账                  |
| 贴源采集       | 把源对象的所选字段带入平台，保留来源，并安排采集分区 | `titans_dm.trd_otc_trade` → `odata_n_tit.d_trd_otc_trade`  |
| 模型加工       | 统一事件和对象的表达，补关系、转代码、确定业务日期   | 保证金台账 → 保证金变动事件                                |
| 面向用途的加工 | 按具体需求选记录、拼信息、计算或汇总                 | 从场内证券成交事件中筛出指定客户与资金账户的流水           |
| 交付使用方     | 将所需结果写到应用或分析的接收对象                   | 成交流水写回 TITANS TRADEFLOW；代收代付明细写入 TITANS ETL |

这是从已核读任务中归纳的职责分工，并非规定每张表必须按这个顺序经过所有层。`OData`、`PData`、`DM` 在这里是具体数据层和表的组织方式；不能仅凭一个前缀，就断定表是否原始、是否经过业务加工，或者是否已经被业务成功消费。[S1]–[S8]

## TITANS 提供的不是一个“交易总表”

《TITANS系统交易部分T1级保障方案》的关键功能集列出境内期权客户端，以及境内、南下、北上的多头和空头互换的下单、撤单功能。因此，TITANS 的一部分直接服务客户交易，而这片数据网络接触的是这些业务产生或使用的持久化对象。[S1]

四类已经核对的对象可以说明为什么必须拆表理解：

| 对象                               | 一行首先应怎样理解                 | 重要标识与关系                                                                                        |
| ---------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------- |
| OTC 交易 `TRD_OTC_TRADE`           | 一个由内部交易流水号标识的交易记录 | 源 DDL 主键为 `KEY_OTC_TRADE_ID`；另有合约标识 `KEY_INSTRUMENT_ID`、账簿标识 `KEY_BOOK_ID` 和业务类型 |
| 账簿 `REF_BOOK`                    | 一个账簿在指定有效期内的配置记录   | 主键包含 `KEY_BOOK_ID`、`VALID_STARTDATE`、`VALID_ENDDATE`；含柜台、部门、公司和归属主体标识          |
| 交易对手 `REF_COUNTERPARTY`        | 一个系统登记的交易对手对象         | 主键为 `ID`；类型注释包含产品、机构、个人，另存主体名称、注册码和内部标识                             |
| 保证金台账 `MARGIN_ACCOUNT_LEDGER` | 一次保证金账户操作形成的流水       | 主键为 `KEY_MRG_LEDGER_ID`；另有账户、合约、发生金额、操作前后余额和触发事件                          |

这些行含义来自 DDL 约束、注释与所采集字段，并不宣称当前数据已经通过唯一性检查。尤其要记住：交易流水号、合约号、账簿号和交易对手号分别识别不同对象；把它们都称为“客户交易编号”，会丢掉关系。[S2]–[S5]

账簿也不只是显示名称。源表存有是否报送财务、报送风控、启用资金模块、启用结算通知书等开关。这说明同一个业务记录进入不同用途时，可能还要看账簿配置。配置字段的存在已确认；哪个下游具体执行哪个开关，仍须看该下游 SQL，不能在这里推定所有开关都生效。[S3]

交易对手也不能直接等同于统一客户。在已核读的期权综合销售信息加工中，系统另从 `odata_n_ois` 的境内与香港交易对手维护表补充公司名称、简称等信息，用映射中的外部交易对手编号连接 `client_id`。境内分支排除删除记录和香港部门，香港分支采用自己的表。这解释了为什么一条交易链还会接到另一套主体维护数据：交易系统中的对象标识与经营使用的主体信息，需要通过明确关系对接。本次只确认这些表的维护内容和实际连接方式，未据此扩写 OIS 整套系统的所有职责。[S9]

## OData 保留了什么，又没有自动保证什么

四个代表采集任务都是从源对象直接选择字段，写入对应 OData 表，并设置 `busi_date` 采集分区。查询中没有按业务日期筛源记录的 `WHERE`；因此，它们查询的是执行时源表中全部可见记录的所选字段，不意味着只采集当天新发生的业务，也不意味着保留了源库每一次变化。[S2]–[S5]

这里最容易混淆的是三种时间：

- **采集分区日期**：平台把这一批数据放在哪个 `busi_date` 分区，由任务配置提供。
- **采集时间**：这些查询用执行时的 `SYSDATE` 生成 `DATA_TIME`，不能拿它当业务发生时间。
- **业务本身的日期**：保证金台账把源 `BUSI_DATE` 改名为 `SRC_BUSI_DATE`，并单独保留 `ACTUAL_BUSI_DATE` 生效业务日。

假设一条 5 月 17 日发生的流水，5 月 19 日才进入某批采集，批次日期和发生日期就不同；若生效业务日又是另一天，三者仍不能合并。这个例子用于解释字段关系，没有声称真实发生过这样的延迟。[S5]

源与落地表也未必完全同构。交易源表的编号是数值类型，OData DDL 将这些编号声明为字符串；源账簿存在的“是否检查负持仓”字段，并未出现在所核读的账簿采集查询里。对下游而言，“源系统有这个字段”和“这一条数据链拿到了这个字段”是两回事。[S2]、[S3]

## 模型层让源记录能够与其他业务对象接上

保证金事件加工提供了一个完整例子。它读取 OData 保证金台账，生成 `pdata_n.t05_otc_deri_cutp_marg_chg_evt`：在源流水号前加 `TIT279-` 形成事件编号；保留源流水号与账户号；连接保证金账户以补出交易对手；把源合约号转换成带来源前缀的产品编号；通过代码映射表转换资金变动类型，未命中时保留源代码。[S6]

它还把台账日期写为发生日期和输出分区，把 `ACTUAL_BUSI_DATE` 写为生效日期。因此，读者在模型表里看到的业务日期，已经是这项加工明确选择的口径，不能简单套用入口采集分区的含义。

这一步产生的价值是：一次源系统账户操作被整理为具有事件、账户、交易对手、产品和时间语义的记录，可以被后续过程继续使用。它尚未计算月日均、机构贡献或业务收益，那些是另一层用途中的问题。

还有两个实现边界需要保留。该任务以不同业务日的记录数差异选择历史重算日期，仅凭这一条件无法发现“条数不变、金额变了”的历史修改；账户连接也未显式限定账户表分区。静态材料能够指出这些条件，但本次没有用实际数据判断是否已产生重复或漏更新。[S6]

## 数据还会回到交易系统，且会先按用途筛选

ATP 成交流水这一支说明了网络的另一方向。任务从统一的场内证券成交事件中读取当日数据，使用前一日的账簿交易流水映射规则，按**客户编号与资金账户同时匹配**选记录。两类条件通过规则号配对。随后推送任务把成交价格、数量、金额、订单状态等字段映射到 `TITANS_TRADEFLOW.TRANS_SMT_ATP_T_REPORT`，按交易日期清理并重写目标记录。[S7]

因此，TITANS 接收的是满足这套范围规则的数据。如果源柜台有一笔成交，TITANS 对应接收表没有这笔记录，排查不应只看“柜台是否产生了成交”，还要看客户、资金账户、规则配对、规则日期和推送日期。这里确认的是筛选及写入实现，尚未核实目标应用实际读到的数据。[S7]

ETF 相关支路进一步说明“同一业务需要几种不同信息”。设计文档区分交易所静态文件、柜台表、平台表、TITANS ETL 表及 TITANS 基础信息和历史表；当前发布也包括把 ETF 申赎成分股成交数据写入 TRADEFLOW，以及把代收代付明细写入 TITANS ETL 的任务。成分股回报回答数量、价格、金额等交易信息，代收代付明细另带清算业务类别、交收状态、清算日期等；它们不能互相代替。[S8]、[S10]

该 ETF 文档还明确区分保留历史快照的平台接口与只保留最新成功批次的 TITANS ETL 接收表。代收代付推送 SQL 中的全表清理与此方向一致。这只能支持该支路的保存方式；不能推广成所有 TITANS 表都只存当天数据，也不能证明当前批次已经成功。[S8]、[S10]

## 把全部源落地任务放回业务对象中

<a id="source-family-trade"></a>

### 交易与存续事件：交易主记录和后续动作分别保存

这一族包括场内成交 `TRD_DEAL`、OTC 交易主记录，以及期权、互换和极速互换的存续期事件；还包括南下成交回报、票据交易流水和已出借记录。源系统把它们拆开，是因为“一笔交易”和“交易生命周期里的一次调整”具有不同粒度。

以互换事件为例，`TRD_TRS_EVENT` 的主键是事件 ID，另带所属交易 ID、事件日期、名义本金调整前值、变动额、调整后值和事件状态。源注释还把录入时间与实际成交时间分开，后者注明与审批结束时间有关。所以，同一交易可被不同事件引用，事件日期也不能自动等于首次交易日。当前采集保留这些字段，并不负责在此重放完整生命周期；状态代码含义仍需对应字典。[S12]

场内 `TRD_DEAL` 的部分采集会纳入“交易日在目标日，或更新日在目标日”的记录，另一条 `titans_dm.trd_deal` 则只看更新日期窗口。迟到修改是否进入这一批，要按具体任务的条件判断。家族共同的是记录交易或事件，采集边界并不相同。[S13]

<a id="source-family-structure"></a>

### 期权互换与产品结构：合约、结构、腿和观察安排不能压成同一层

期权合同要素 `REF_OTC_OPTION_DEAL` 保存交易对手、对外合约编号、交易达成日、期权费支付日、兑付日和名义本金等；`REF_OPTION_DEAL_STRUCTURE` 另外保存类型、方向、期初期末定价日、观察安排及挂钩标的。两者都以内部交易标识关联，但所回答的问题不同：前者偏向双方达成的合同，后者偏向收益结构的定义。[S12]

结构继续向下拆成执行价格、参与率、票息、障碍价格、敲入敲出观察日、自动赎回、Lizard、区间累积、累购累沽和 RESET 调整等表。一个观察安排可以需要多条日期或参数记录，不能见到共同合约号就假定一对一。互换则拆成合约与腿：`REF_TRS_LEG` 的主键是全局腿号，另有所属交易号和交易内腿序号，记录腿类型、方向、挂钩标的和计息参数。固定腿、浮动腿等具体类型码仍以字典为准。[S12]

本范围还包含极速互换、SBL、外汇远期的合约与结构，以及产品、票据和底层资产。它们属于同一“定义交易安排”的入口层，但本次没有仅凭名称补写各产品完整收益公式。观察日表的 `KI`/`KO` 名称及历史注释还存在不完全一致的地方，采集方式可核实，精确经济含义须由对应结构与业务说明共同确认。

<a id="source-family-position"></a>

### 持仓估值与风险结果：源系统已经计算过，入口层还可能改变快照组成

这一族有账户每日持仓、互换腿当前及历史持仓、腿和标的估值、日终持仓指标、外汇敞口、压力测试、集中度、限额指标以及面向财务和风险的结果视图。它们提供的是状态或计算结果；入口查询读到 `value`、`pnl` 或风险指标，并不意味着查询本身实现了估值模型。

例如 `POS_EOD_CALC_METRICS` 的源主键是“持仓 ID＋计算日期”，`POS_EOD_FX_EXPOSURE` 的源主键还加入货币序号。一个持仓在不同日期、不同币种下可以有多行。源查询保留账户、合约、账簿、原币/折算币种及各类指标字段；把这些维度忽略后直接求和，会改变结果含义。[S12]

本族存在两种重要的入口加工。第一种把已终止或最后估值记录带入当期快照，让累计结果继续可见，同时将不属于目标日的部分日盈亏字段改成零；第二种按“合约引用＋账簿”取不晚于目标日的最新源业务日期。两者是在组织结果快照，不是重新给合约定价。同一个源视图还有不同日期范围的采集，必须依据后文的差异表比较。[S13]

<a id="source-family-cash"></a>

### 资金保证金与收付款：账户、余额、流水、参数和计算结果各司其职

这组材料同时包含客户资金账户、保证金账户、当前余额、每日余额、流水台账、履保方案、账户与合约/组合的映射、每日履保结果及不参与计算的账户记录。它们组成的是“账户是什么—关联哪些业务—余额怎样变化—按什么规则计算”的关系，而非一张可以直接代表所有资金的表。

当前余额和每日余额也不同。每日资金余额查询保留源业务日期、可用、冻结、应收、总额等字段；保证金每日余额查询则单独保留账户、源业务日期和余额。它们都可能在一个采集批次中含多个历史业务日。台账记录一次发生额及前后余额，不能把多条台账的操作后余额相加，当作账户总资产。[S5、S12]

收付款 `TRD_TRANSFER`、费用定义与支付安排、按日计提费用、预付金返息和结算记录接在这组材料旁边。它们记录应收应付或计提安排，与实际资金余额不是同一种事实。入库查询还存在空字符串占位：例如部分风控资金账户查询将可用、冻结、应收等输出列写为 `''`。这表示本条采集没有提供值，不能解释为金额零。[S13]

<a id="source-family-party"></a>

### 账簿交易对手与关系：关系本身也是需要保存的业务事实

这一族补足前文的账簿与交易对手：除主对象外，还有账簿映射、映射条件、部门配置、交易对手映射、账户组绑定、授权业务和属性参数。两个系统各有对象编号时，关系表告诉下游怎样对接；需要按客户与资金账户共同选择流水时，映射条件表提供具体选择规则。

不能把所有“交易对手”表合并成一个概念。`REF_COUNTERPARTY` 是系统静态交易对手对象，`REF_COUNTER_PARTY`、`REF_CTPTY_MAPPING` 和账户组绑定保存的是不同层面的参数或关系；本章只在读到明确键、DDL 注释和使用 SQL 的位置确认关系。账簿的有效期是主键的一部分，这也说明“按现在的关系解释历史交易”与“按历史有效关系解释”需要不同证据。[S3、S4、S9]

<a id="source-family-market"></a>

### 证券行情与定价参数：主数据、观测值和参数选择需要连在一起

证券基本信息、证券编码、期货和场内期权定义回答“这个标的是什么”；每日行情、汇率、利率和限售股折价回答“在某个日期观测到了什么”；曲线、波动率曲面、相关性、日历、字典和定价环境配置回答“使用哪套参数和解释方式”。这些材料共同服务后续计算，但本次并未把读取行情表等同于实际完成定价。

粒度差异在源 DDL 中很具体：收益率曲线以“曲线内码＋行情日期＋期限”为主键，相关性以“相关性 ID＋日期”为主键，波动率曲面选择配置则以“定价环境＋挂钩标的＋看涨看跌标识”为主键。曲线上的不同期限点不是同一数值的重复；同一标的也可能按不同定价环境选择不同曲面。[S12]

每日行情还有单独的更新逻辑：采集条件按更新时间取窗口；后续将日内批次与已有行情合并，以“证券内码＋行情日期”为组，按采集时间倒序取一条。这里的“最新”是该 SQL 指定的采集时间顺序，未证明它一定等于行情业务上最后发生的修订。[S13]

<a id="source-family-access"></a>

### 用户权限与工作流：提供操作范围与处理过程的背景

用户、员工、部门、角色、菜单、功能及其映射解释“谁属于哪里、通过什么角色拥有哪项功能”。例如 `ADM_USER_ROLE` 的源主键是“用户 ID＋角色 ID”，一行是一项授权关系；角色本身另有 ID、名称和说明。因此，用户数、角色数和授权关系数代表不同数量，不能混报。[S12]

流程部分有流程定义及历史实例。流程定义保留定义 ID、BPMN 标识、业务模块、流程名称和可执行状态；历史实例保留业务键、流程实例和定义标识、起止时间及状态。它们可用来连接业务对象与处理过程，但本范围缺少完整状态字典，不能把某个状态值直接宣布为“业务完成”，也不能从没有结束时间推断当前仍在审批。[S12]

<a id="source-family-delivery"></a>

### 接口报送与文书：记录交付对象的状态，不自动证明已交付

合约报备保存内部合约 ID、报价系统编号、数据报备状态、报备日期、截止日和附件状态；交易确认书、合约文件和结算通知书则各自保存文书或通知的相关对象。结算通知书有自己的主键，再关联合约、资金账户、交易对手和结算日期。它不是一条交易流水，也不是保证金账户余额。[S12]

这些表让下游知道某项报备或文书处于什么记录状态。字段名含“报送”“确认”“通知”，不能证明监管或客户实际收到了内容。已核实的是本网络采集了哪些记录；外部接收回执、发送结果和当前使用仍需对应运行证据。

## 同一家族也可能采用不同采集和保存方式

650 项 SQL 的方式可以完整归纳为下列九组。每项归属与原样筛选条件保存在 `source-review.json`，包括对应 SQL 槽位、行号、哈希、生成表达式和发布输入输出；没有用表名相似来消除差异。[S11、S13]

| 已核实的方式            | 任务数 | 读者应保留的含义                                                                   |
| ----------------------- | -----: | ---------------------------------------------------------------------------------- |
| 无行过滤地选择字段      |    538 | 读取执行时源表可见的所选字段；可有日期、空值或时间戳等生成列，不保证逐字段原样复制 |
| 发生日或更新日命中      |      5 | 当天发生或当天修改均可进入；不能只按发生日解释批次                                 |
| 按业务日期选取范围      |     16 | 有单日、两日、年初至目标日或仅下界等不同条件                                       |
| 按创建/更新时间选取范围 |     11 | 捕获的是创建或修订窗口，未必对应同一天发生的业务                                   |
| 风险盈亏跨期补齐        |     11 | 合并在续与终止/最后估值记录，部分旧日期的日盈亏置零                                |
| 多来源 UNION ALL        |      6 | 对齐字段后保留来源标识合并，没有自动去重                                           |
| 日内批次保存            |     54 | 将批次分区写入带批次与日期的保存表；日期来源并不统一                               |
| 行情按组保留最新        |      4 | 合并日内与已有数据，按证券、行情日和采集时间选记录                                 |
| 合约结果按组保留最新    |      5 | 按合约引用与账簿保留最新源日期，有些先合并旧保存结果                               |

### `_p`、`_pb` 和日期字段要看实际 SQL

在已经核实的日内保存链中，`_p` 表的 `busi_date` 可以是 `h13`、`h15`、`h0730` 等批次标签；保存任务把它选出，再写到 `_pb` 表的 `grp_id＋busi_date` 分区。标签说明选哪批数据，不足以证明调度实际在标签所示时刻执行。这是此处任务的实现模式，不是所有 `_p`/`_pb` 名称都必须遵循的命名公理。

保存日期主要有三种来源：大部分写配置中的目标日期；保证金余额、互换腿历史持仓和日终持仓部分 `h0730` 保存任务按 `src_busi_date` 写分区；指标结果按 `create_time`、部分对冲持仓按处理后的源业务日期写分区。于是，“同在一个日内批次里”和“同属一个业务日期”不是一回事。[S13]

### 具体差异决定怎样解释变化

- **行情不是只取当天。** 每日行情采集的已发布条件覆盖目标日零时至参数次日 15 时，含上界；不能描述为严格的单个自然日窗口。行情合并又按采集时间取最新，存在相同时间值时未规定第二排序键。
- **同源视图也有不同时间口径。** 权衍合约盈亏任务 `72224` 将未终止当日记录与年内终止记录合并；`92677` 直接读取年初至目标日。任务名字及源视图相同，不代表记录集合相同。
- **“最近几日”未必有上界。** 保证金余额、腿历史持仓和日终持仓的部分采集只有 `>=` 下界；不能自动补成“仅最近两日”。`-1e`、`-2e` 的平台日历含义未在本章独立核验，账本保留原参数。
- **最后估值日期与实际结算日有区别。** 部分风险合约盈亏分支用 `NVL(VAL_TERM_DATE, ACTUAL_SETTLEMENT_DATE)` 筛年内记录，另一组只用 `ACTUAL_SETTLEMENT_DATE`，且日期偏移参数不同。不能把它们归为一个已验证的同口径查询。
- **空字符串不是经济上的零。** 某些资金余额列、互换腿的限售类型、履保结果的计算标识在采集中被显式写为 `''`；另有互换视图将二进制 ID 转成十六进制。字段名保留不代表值或类型原样保留。
- **合并不意味着没有重复。** 保证金参数、账户及互换监控的入口使用 `UNION ALL` 合并 TITANS 与另一套 OTC 来源，写入来源标签。期权参数合并中，零售分支大量字段用空字符串补齐。两分支是否存在相同业务对象，本次没有以实际数据排重。

这些规则来自已发布 SQL 快照。快照中的具体日期有些是已展开的历史日期，另一些仍是参数；本章不把它们改写成“每天当前运行都如此”。[S13]

## 后续阅读时，始终保留四个问题

每进入一个具体过程，先确定它在解决谁的问题，再确认一行代表什么、使用哪一天的关系与事实、交付给谁。源系统对象提供事实，贴源采集确定可见材料，模型加工建立通用表达，面向用途的加工决定纳入与计算，接收表决定交付形态。这样才能继续解释：为什么同一合约出现在多张表，为什么同一金额会有不同口径，以及为什么源端存在记录仍不等于业务端已经收到。

本章未核实的重点是：完整源系统业务流程与状态迁移、各接收应用当下的实际消费、源表历史有效期数据的真实唯一性、以及运行期间的延迟与重算效果。它们影响具体业务判断；不能由系统名称、DDL 注释或图上的连接补成确定结论。
