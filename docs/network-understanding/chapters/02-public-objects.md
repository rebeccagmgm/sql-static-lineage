# 先把人、合约、账户、账簿和证券分清

> 本页提供公共对象的总览。主体、组织、账户账簿、产品身份、历史区间及公共参数已有独立说明；各页仍保留具体未核边界，整库尚未完成验收。

继续深入：[主体与客户怎样形成](../topics/party-and-customer.md) · [组织、用户、角色与权限](../topics/organization-and-access.md) · [公共身份与历史](../topics/public-identity-and-history.md) · [码表、系数与配置](../topics/reference-codes-and-parameters.md)。

## 一项业务有多个对象，每个对象回答不同问题

理解这片网络，可以先想象一项示意业务：某个主体签订了一项合约，业务被记录在一个账簿上，涉及一种或多种标的，资金通过账户收付，还可能由某个机构和员工负责。这里至少包含主体、合约、账簿、标的、账户、机构和员工。它们有各自的编号和状态，不能用一列“客户”或“合约”统包。

公共模型的作用，是让不同加工能沿着这些对象重新找到彼此。后续的风险、财务和经营统计使用相同对象基础，却不一定选择同一种关系，也不一定使用同一天的关系。

## “当事人”“客户”“交易对手”是不同层面的描述

`T01_PTY` 保存当事人的共性信息，包括当事人编号、名称、类别、状态、开户、销户和删除日期。可以先把当事人理解为数据模型中“参与业务的主体”。这个层面还没有讲完它在具体业务中的角色。

`T01_OTC_DERI_CUST` 的模型进一步容纳 OTC 衍生品客户信息，包括协议、业务资格及费用参数。不过，有列不等于当前分支填入了信息：已读生产分支 150757 从扩展参数取得主、补协议编号及港美佣金等参数，多项协议签署日期、履约保障协议、审核和报备字段则填空。因此，知道一个主体存在，并不能代替知道它具备哪些业务协议及状态；看到表里有状态列，也不能据此断言当前加工已采集该状态。[实际填充规则](../topics/party-and-customer.md#party-business-profile)

`T98_CUTP_BASE_INFO` 则组织交易对手信息，保留当事人编号和另一列 ECIF 编号，同时有交易对手类型、名称、状态等属性。两套编号同时出现，本身就提醒我们：**跨系统统一主体需要明确映射，不能因为字段都叫客户编号就直接关联。** 名称适合阅读，正式连接应先看代码实际使用的编号及关系条件。

这些解释依据本次精确匹配的 Table Pack 及 DDL。它们确认字段与模型说明，不证明现实中一个主体只对应一条数据，也没有替我们完成客户身份一致性的业务验收。[对象定义来源](../evidence/public-object-notes.md#party)

## 为什么账户和合约都会出现在“协议”表里

在这套模型中，“协议”是一个较宽的共性对象。`T03_AGT` 的模型说明明确把各类账户、合约和合同纳入其中，使用协议编号和协议修饰符区分对象。这里的“协议”不能只理解成一份签字文档。

已经核对的实际加工给出了具体例子：

| 模型中的对象     | 源侧用什么作为协议编号               | 怎样区分种类       |
| ---------------- | ------------------------------------ | ------------------ |
| 保证金账户       | 源保证金账户编号 `KEY_MRG_ACCT_ID`   | 协议修饰符 `10219` |
| 资金账户         | 源资金账户编号 `KEY_CAPITAL_ACCT_ID` | 协议修饰符 `10220` |
| 普通互换相关协议 | 互换源记录中的 `KEY_OTC_TRADE_ID`    | 协议修饰符 `20206` |
| 期权相关协议     | 期权源记录中的 `KEY_OTC_TRADE_ID`    | 协议修饰符 `20207` |

这几条映射分别来自任务 105053、105054、105055、105522。后两条尤其容易误解：模型字段叫 `Agt_Id`，其值实际从源交易键取得。只看模型字段的中文名称，不能判断它对应源系统的合约键还是交易键。[映射规则来源](../evidence/public-object-notes.md#agreement-ids)

协议修饰符的用途可以通过一个示意例子理解：假设某个资金账户和某个合约在各自系统里都恰好编号为 `123`，如果只保留编号，二者可能被误当成同一对象；保留对象种类和来源，才有条件区分。实际 SQL 是否按足够的键关联，还需要逐个消费场景核查。模型说明中列出逻辑键，不等于每条 SQL 都已经正确使用该键。

### 业务状态、删除标志和历史版本分别看

`T03_AGT` 同时保留协议状态、删除标志、删除日期、业务生效和到期日期、加载和更新日期。它们不是一个状态的不同名字：

- 业务状态说明账户或合约在源业务中的状态，常需要通过代码表转换。
- 删除标志说明本次模型维护怎样标记记录，不直接等于合同法律关系终止。
- 业务生效或到期日期描述协议相关日期；加载和更新日期描述数据处理。

期权示例任务先按来源限定目标数据，与新提取记录做全外连接，再区分新增、变更、未变化、删除等情况，最后覆盖该来源分区。它按 `Agt_Id` 连接新旧记录；本段代码没有因为表说明写着“历史拉链”就自动证明所有历史状态都可从这张表恢复。判断历史查询能力，要继续检查真实保留字段及维护逻辑。[维护片段来源](../evidence/public-object-notes.md#agreement-maintenance)

## 协议关系表保存的是“谁和谁是什么关系”

知道合约和账户分别存在，还不足以知道它们怎样连接。`T03_AGT_RELA_H` 的元数据把它定义为协议关系历史，涉及资金账户、其他账户、合同和合约之间的联系，并指向协议关系类型代码 `CD051`。

因此，读取这种表至少要分清关系两端、关系类型及关系有效期。相同两个编号之间可能因关系种类或时间不同而出现多条记录；一条历史关系也不应自动解释成计算日仍有效。具体消费者用哪一端接合约、哪一端接账户、如何选择有效期，由 SQL 决定。

后面的资金与风险过程会使用账户和合约映射，销售过程会使用管理或引入关系。它们共享“通过关系连接对象”这一做法，但不能把不同关系表、关系代码或有效期条件视为等价。[关系模型来源](../evidence/public-object-notes.md#relationships)

## 账簿、账户和机构为什么都要保留

这三个词经常同时出现，却不能相互替代。

**账簿**在交易与持仓组织中提供一个归属位置。源账簿的声明主键包含账簿号及有效起止日期，后续还会有账簿附加信息、所属部门、控制参数等。因此，账簿号相同不必然代表所有历史属性都相同。

**账户**承载资金、保证金或证券等账户信息。一个业务过程可能需要从合约找到对应账户，再取得余额或流水。财务接口中还会出现内部证券账户及账套映射，这属于面向财务处理的进一步映射，不能直接等同于源业务账户。

**机构**描述组织维度。`T98_ORG_BRCH_DIV_INFO` 的元数据说明：机构编号使用柜台编号，机构名称使用 ERP 机构名称，所属分公司信息也来自 ERP。一个“机构信息表”内部就可能融合不同系统的属性。这个说明不意味着当前研究范围包含该表的完整生产链；本次图内未见其最终生产任务。

所以，看到一个结果既有账簿、账户又有机构，并不表示信息重复。读者需要知道每个字段回答哪种归属问题，以及代码怎样把它们连接起来。[组织与账簿来源](../evidence/public-object-notes.md#organization)

## 证券基础信息帮助统一身份，也会参与计算规则

证券基础表里同时存在统一证券编码、证券代码、源系统信息和源证券类别。`T02_TIT_SCR_BASE_INFO` 的源类别说明包含股票、期货、基金、场内和场外期权、收益互换、货币对、策略指数等。这里的“证券基础”覆盖的对象范围，比日常说的股票代码更广。

读者应区分两个问题：第一，这个业务使用的是哪个标的；第二，哪一种属性参与了当前规则。统一标识解决前一个问题，货币或类别等属性可能决定后一个问题。

例如，已核对的交叉销售月日均任务用源标的编号关联证券基础，读取货币代码，再与账簿部门、标的类型、合约类型等条件一起决定输出标签。证券基础表在这里提供的是分支条件的一部分。不能只因为它是公共基础，就认为它对业务结果只有装饰性作用。[证券模型及消费来源](../evidence/public-object-notes.md#security)

## 员工与机构关系进入计算时，必须带上时间和比例

员工表回答某个员工是谁、属于什么组织或处于什么状态；合约管理关系则回答某份合约在某个日期怎样归属给机构与员工。两者的职责不同。

以已经核对的交叉销售任务为例，管理关系取计算日数据，日规模取月初到计算日的数据；分配过程中还会按机构条件选择归属槽位，再乘对应比例。这里不能简单地说“第几个员工就拿第几个比例”，也不能默认它按历史每天的员工关系分别归属。后续销售与考核章节将完整展开该过程。

这一认识可以推广为阅读方法：遇到任何“归属”字段，至少检查**归属对象、关系日期、比例和例外选择**。这些信息决定金额归到谁名下，不能仅靠员工和机构名称判断。

## 一组可以带到后续章节的识别规则

| 看到的字段或概念                    | 先做的区分                                             |
| ----------------------------------- | ------------------------------------------------------ |
| 客户、当事人、交易对手编号          | 分清主体共性、业务角色及跨系统身份映射                 |
| `Agt_Id`                            | 找到该生产分支实际使用的源字段，并保留对象修饰符与来源 |
| 合约、交易、子交易、资产腿          | 先辨认对象层级和编号关系，再判断一行代表什么           |
| 账簿、账户、机构                    | 分清交易组织、资金或证券账户、组织归属，逐项核查映射   |
| `Busi_Date`、生效日、计提日、加载日 | 看字段在当前输入和输出中的职责，不能统一叫“日期”后略过 |
| 历史表、状态字段、删除标志          | 核对保留和维护逻辑，以及消费者实际使用的有效条件       |
| 公共代码、证券属性、归属比例        | 检查它是名称补充、行筛选、金额来源，还是决定计算分支   |

这些规则不会替代后续业务解释，但能防止一个常见问题：整张图看起来每个名字都认识，真正关联或比较结果时，却把不同对象、不同时间或不同口径放在了一起。
