# 数据如何交付：传输、回执、后处理与检查

把一张结果表算出来以后，网络还要把它送到消费端、记录接口状态，有时还要在目标端补齐归属或汇总。这些支撑任务解释了图中许多调度连接。理解它们时，应分清四件事：产生业务记录、搬运记录、修改消费端数据、写一个完成标记。

本页纳入当前图中的 146 个 `exeSql` 任务和 31 个脚本、邮件、告警与控制任务。其中 104 项记录了 SQL 核读，70 项未取得处理正文，3 项复杂指标后处理交由考核主题继续解释；只显示过程调用的 9 项也保留内部规则未知。普通采集和推送的业务规则分别放在[源系统](01-sources-and-systems.md)、[香港](10-hongkong.md)、[财务](07-finance-and-valuation.md)等消费主题。本页不声称全部传输任务已经逐项解释。

<a id="delivery-stages"></a>
## 同一条交付链中，几类任务分别负责什么

| 环节 | 可以从材料确认的行为 | 还需要什么证据才能确认结果 |
|---|---|---|
| 采集或导出查询 | 选哪些列、哪些日期、哪些业务分组，是否做转换 | 实际运行读取的数据与执行日志 |
| 导出前清理 | 删除当天分区、某个分组，或清空目标表 | 删除与写入的真实顺序、事务和失败处理 |
| 目标端加工 | 更新属性、合并关系、按人员汇总奖励 | 目标端实际执行、主键约束和结果核验 |
| 完成标记 | 写入日期、接口号、字面状态，有时附带记录数 | 标记与真实业务写入之间的执行依赖及验收约定 |
| 告警或检查 | 查询某个条件，返回 0、1 或明细 | 返回值怎样被平台判定、如何处置失败 |
| 邮件、脚本或实时任务控制 | 目前部分只有任务类型和名称 | 实际脚本、配置、正文、接收规则或消费记录 |

例如，某个任务先删除目标分组，再将源记录写入；失败发生在删除之后时，是否回滚由事务及平台行为决定。静态 SQL 可以说明这两条语句，却不能证明它们已作为一个不可分割的事务执行。相似地，源端 `COUNT(*)` 与目标端 `COUNT(*)` 回答的也是不同问题。

<a id="risk-completion-markers"></a>
## 风控日志：写了“1”，实际执行的是一条登记语句

`DM_RM`、`EM_RSK_N` 中一组当前补充 SQL 向 `dm_rm.base_etl_log` 插入记录。共同内容包括参数业务日、一个编号、一段对象标签、当前时间和字面量 `'1'`。这些语句没有读取被标记表、没有比较记录数，也没有检查业务字段。

以 170568 为例，写入的编号是 `121575`，对象标签是 `PDATA_N.T98_SB_TIT_DAY_HOLD_INDX_TIT209`。这说明日志中的编号不一定是写日志任务自身的编号。104440、144029 等标签还带 `risk.etl_log_` 前缀；部分 `mc`、`kxc` 标签把点改成下划线。它们首先是日志协议中的字符串，不能自动当作一张已验证存在的物理表。

部分语句多写两个字符串：一个表标签，以及逗号分隔的任务编号列表。例如 190593 标记结算异常监控的多个分组，205726/205727 标记协议关系的不同任务集合，211424 单独标记同一结算监控表的 `grp01`。这些字段表达了标记的声明范围，不能代替逐一核验这些任务确已完成。

有三个具体差异需要保留：

- 196209 的名称指向期权子交易信息，SQL 中登记的却是期权子交易期限定价指标；196214 也登记同一个定价指标标签。名称不能覆盖实际字符串。
- 138259 的编号字符串含前导制表符；241339 的扩展表标签也含前导制表符。后续是否去除空白尚无证据，因此不应先假设它们能与干净编号或表名严格相等。
- 194623/194624 等同类曲线处理标记共用对象标签，却保留不同编号。对象标签相同不等于同一次执行或同一业务分支。

这里可以解释为“下游接口完成登记的实现”，不能表述为“已证实风控收到正确数据”。逐任务字符串和 SQL 哈希保留在[交付审阅记录](../evidence/delivery-review.json)及其[证据索引](../evidence/delivery-evidence.md)。

<a id="finance-completion-markers"></a>
## 财务打标：接口分组与业务表内容是两层信息

当前补充 SQL 中，214118、214126、214134 分别向 `gfedw.civ_itf_tagging` 写入行情、信息、交易三类接口标记。流水号由参数日期拼固定后缀产生；开始时间和结束时间都取当前时间；`result` 直接填 `COMPLETED`。

224938、225247、225621、225623、225625、225628 进一步区分互换信息、期权行情、场外期权、香港期权、香港互换和香港票据交易流水，并在 `def1` 中列出相关接口表名。这里的表名清单有助于理解接口分组，例如香港互换指向 `civ_trd_otc_trs_deli_dtl_day_hk`；但 SQL 只是把名字写入字符串列，没有查询该表来判断完成程度。

重复执行同一业务日会再次构造相同的流水号。是否禁止重复、覆盖旧标记或报错，取决于目标约束和平台执行方式，现有语句本身没有给出答案。接口打标也没有提供每个业务分组的真实处理耗时，因为开始和结束时间均在打标时生成。

<a id="counted-delivery-log"></a>
## 资金部推送回执：有记录数，但计数范围不同

144442 和 203181 都向 `GFKN.SYNC_TABLE_DATA_LOG` 写入一条回执，并实际查询 `GFEDW.T98_FMS_AST_TRD_EQUI_DERI` 的记录数。它们比纯字符串标记多了一项内容证据，却仍然有明确范围：

| 项目 | 144442 | 203181 |
|---|---|---|
| 计数业务日 | 参数业务日 | 参数业务日 |
| 业务分组 | 排除 `grp_id` 为 `02`、`07` 的记录 | 只取 `grp_id='02'` |
| 回执表标签 | `T98_FMS_AST_TRD_EQUI_DERI` | `T98_FMS_AST_TRD_EQUI_DERI_O32` |
| 回执任务编号 | 固定 `114802` | 固定 `114802` |
| `STATUS` | 字面量 `'0'` | 字面量 `'0'` |

203181 的回执标签有 `_O32`，实际计数仍来自没有这个后缀的基础表，只是分组不同。两条回执都没有计入 `grp_id='07'`；分组为空的记录也不会通过 `NOT IN ('02','07')` 条件。不能把这两个数相加当成全表交付记录数。

记录数为零时，聚合查询仍会产生一行计数结果，SQL 仍可写出回执。`STATUS='0'` 的业务含义没有在语句中定义，不能套用其他检查的 0/1 约定。回执能留下执行时目标表的一个计数快照，不能证明金额正确，也不能证明另一消费端已经读取它。

<a id="delivery-postprocessing"></a>
## 后处理会改变业务内容，不能全部归入“搬运”

有些 `exeSql` 任务确实在目标端加工业务数据。它们的任务类型与写日志相同，实际职责却不同。

- 45199 同步 CRM 项目的销售部门和销售团队关系，并补充收入类型映射；有的来源会删除失效关系，有的来源只追加关系。
- 140202 更新融资融券潜在客户月表，取不晚于计算日的交易日信息，保留已有客户行，按主资金账户和其他客户资料补字段。
- 50615 将上月网上开户奖励按营销员工汇总，写入本月奖励账期；删除和插入之间存在单独提交。
- 198986 仅在项目 `TYPE` 为空且 `BUSINESS_TYPE` 非空时补齐类型，不覆盖已有 `TYPE`。
- 164991、156254、166545 属于机构和员工指标的后处理，其业务逻辑接在[标准资产与考核](09-performance-and-assets.md)主题，不能只凭名称当成简单回执。

前三项的完整规则、粒度和例外见[目标端业务后处理](../topics/delivery-postprocessing.md)。

<a id="calls-and-checks"></a>
## 调用了过程、返回了常量，不等于看到了内部业务

11175、13378、43993、43995、43996、45828、73878、134808、163208 的发布 SQL 只显示一个过程调用或一个调用包装块。例如 `gf_sync_acct_pkg.gf_project_stage_to_base` 暗示项目暂存到基础数据的处理，但过程体不在当前证据中。这里可以确认调用入口、参数日期是否出现；无法确认过程内部的读表、写表、删除范围、汇总口径和事务行为。

152833 是一种更具体的通知：把 `gf_otc.sync_titans_data` 中名称为 `EXCHANGE_TITANS_TO_SPS` 的记录改为 `DONE`，同时更新时间和操作方标签。SQL 没有附带行数条件或内容检查，目标表若存在多条同名记录，也会都满足更新条件。

172920 和 191236 名称含 `check`，发布 SQL 却都是 `select now()`；223985 名称指向 ATP 成交流水告警，SQL 是 `select 0`。这些语句没有读取被命名的业务表。它们可能承担平台控制约定中的角色，但仅凭 SQL 不能声称已检查资产或成交数据。

209504 的检查具有实际业务读取：它在 `dm_fii_test.CSTD_OTC_DERI_CUST_BAIL_INFO` 中查参数日、来源 `ODATA_N_XIR.T_VTRD_A1020` 的记录，存在至少一行就输出 1，否则输出 0。这是一个“指定来源在指定日是否有记录”的条件，不检验是否覆盖全部客户或保证金金额是否正确；读取对象是测试命名空间，不能用它证明正式报送已到达。

更完整的重复、字典、历史区间、分配与金额检查原理见[检查与证据边界](../topics/quality-and-evidence.md)。不同任务的成功值必须逐项看实际规则。

当前图另有 Kafka 发送脚本、Easystream 启停、Python 处理、HTTP 任务、邮件和数据就绪标记检查。已检查到的部分当前 Pack 只有任务名称、类型、调度邻居与空 `sqlFiles`，没有脚本正文。因此下表只说明其可见元数据，不能推断实际运行行为。

| 可见任务组 | 在网络中的可见位置 | 尚缺什么，影响哪些判断 |

| 139953、139957 | 名称分别为实时权限任务停止与启动 | 缺执行配置，不能确认实际启停状态或重启间隔 |
| 206823、206827、207029 | 可转债处理与 Python 模型链 | 缺模型和脚本，不能把名称解释成已验证的算法或预测结果 |
| 149527、192716、205767、243754 | 就绪标记或数据库检查 | 缺具体配置/查询；205767 的说明声明 SQL 返回 1 成功，但没有该 SQL 正文 |

<a id="supplemental-evidence-boundary"></a>
## 本页为什么同时引用固定发布和当前补充脚本

固定发布中，部分支撑任务只保留了调度引用。对没有发布 SQL 的 415 项，另按准确的任务类别、任务号与 `task.json.sqlFiles` 声明检查当前本地 Pack，发现 116 项有可核验 SQL。这个发现补充了脚本内容，并没有改变固定发布的图边、解析状态或历史证据。

每份补充脚本保留采集时间、Pack 元数据哈希、声明相对路径、SQL 哈希与所读行段。这里的“补充”不保证与固定发布同时，也不保证此后没有变化。[补充材料发现底账](../evidence/supplemental-pack-inventory.json)只记录材料是否可读；[逐项审阅](../evidence/delivery-review.json)另外记录实际读了什么、能解释什么。

读完本页后，判断一个变化的影响应更具体：修改回执字符串主要影响完成登记与下游识别；修改导出分组改变交付范围；修改目标端 `MERGE` 改变客户或归属数据；修改前置检查改变放行条件。这几类影响不能混成一个“表有下游”的结论。
