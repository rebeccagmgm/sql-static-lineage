# 质量检查究竟证明什么

[返回知识库](../README.md) · [主体与客户](party-and-customer.md) · [组织与权限](organization-and-access.md)

一条加工结果旁边出现质量检查，说明平台配置了某个检查动作。要知道它能证明什么，必须继续看检查范围、判断条件和返回值。这与“已经运行并通过检查”仍是两回事。

本次范围含 690 个 `qualityTask`，其中 669 个有发布 SQL、21 个没有。本页先讲清已核读的主要检查方式与具体边界；全体检查的参数变体仍在复核，不能把本页当作 690 项已经完成审计。检查任务在发布图中作为调度参考保留，不因此成为一条业务金额血缘。

<a id="quality-keys"></a>
## 唯一性检查实际约束的是它分组的那些列

当事人主表的检查 49548 按 `Pty_Id` 分组，筛出数量大于 1 的组，最多返回一行；角色主表的 51088 则按 `Role_Id` 分组。名称表 53767 带上业务日期筛选，分组为当事人编号与类别。协议名称历史 55220 使用协议编号、修饰符和开始日期。

这说明“主键唯一性”不是一条可以套在所有表上的统一规则。检查是否包含来源、对象种类和日期，会改变它能发现的重复。`LIMIT 1` 适合回答“有没有出现某种重复”，不会给出重复总量，也不能据结果只有一行判断问题只有一处。

这些查询返回的是异常明细；无异常时可能没有结果行。平台怎样把空结果判为通过，仍要看任务执行协议。本页只解释 SQL 检查条件，不替它补出执行日志。[已读证据](../evidence/quality-foundation-evidence.md#quality-keys)

<a id="quality-dictionary"></a>
## 字典检查通过，不意味着所有字段都填了

一组个人属性检查使用 `NOT EXISTS`，找出不在 `REF_DW_CD_VAL` 指定字典中的值，再把“发现异常”转成 `check_result=0`，“没发现异常”转成 `1`。

但很多查询先排除了空值，且排除条件不完全相同。例如，性别检查排除 `9` 和空串；学历检查只看未删除记录，还排除若干默认值；职业检查进一步排除两类来源记录。这里检查的是**指定范围中、未被豁免的值是否在字典里**。

所以，业务客户模型或个人模型中许多字段为空，与这些字典检查“未发现异常”可以同时成立。要判断必填信息是否齐全，需要相应的非空规则；要判断所有来源是否合规，需要先确认检查确实纳入了那些来源。本页不把豁免规则解释为对应数据已经正确。[已读证据](../evidence/quality-foundation-evidence.md#quality-dictionary)

<a id="quality-history"></a>
## 历史检查分辨区间错误、重叠、断开和不必要的版本

| 检查 | 已读实现怎样判断 | 实际回答的问题 |
|---|---|---|
| 开始不早于结束 | 55221 找 `Strt_Date ≥ End_Date` | 是否出现零长度或倒置区间 |
| 交叉链 | 55223 用同一协议及修饰符下下一条开始日，查当前结束日是否更晚 | 相邻历史区间是否重叠 |
| 断链 | 154818 用下一条开始日，查当前结束日是否更早 | 相邻组织关系区间中是否有空档 |
| 重复链 | 55224 连接相邻版本，比较所列业务字段；不连续的区间单独放行 | 是否为没有相关属性变化的相邻版本另开了一条链 |

这些规则不能彼此替代。一张表没有重叠区间，仍可能有空档；相邻区间连续，也可能重复保存相同属性。55224 还排除了特定来源，因此它的结果不能推广到被排除的全部历史。

比较相邻版本需要先选对分组键。按协议编号和修饰符排序，与只按协议编号排序，可能把不同对象的历史混到一起。源代码里是否有足够的排序键、同一天多条版本怎样排列，也需要结合该表的数据与约束判断。[已读证据](../evidence/quality-foundation-evidence.md#quality-history)

<a id="quality-counts"></a>
## 行数一致只验证数量，不验证字段值一致

主体关系记录数检查 126848，将计算日有效、指定来源的模型关系数，与源映射表计算日行数比较。它先要求模型数量非零，再要求两边数量相等。这里带上了关系有效期和来源，所以比较对象不是整张历史表。

即使两边各有 100 行，客户映射错了一条，也可能仍然各有 100 行；反过来，模型合法去重或展开时，源与目标本来就可能不是一行对一行。行数检查的意义取决于具体加工的预期粒度，不能只凭“数量相等”证明业务内容相同。

“及时性”任务 198209 更窄：发布 SQL 只有从结果表中 `SELECT 1 LIMIT 1`，没有日期过滤。它能观察表里是否存在某行，不能据这条 SQL 单独证明今天的数据已到达。任务名比实际条件表达的范围更宽。[已读证据](../evidence/quality-foundation-evidence.md#quality-counts)

<a id="quality-business-rules"></a>
## 业务检查把特定口径写进条件，解释时要保留它

销售日报分摊检查 152678，检查计算日三列分摊比例之和，在转成两位小数后是否不等于 1。它检查的是这一精度下的合计；没有在这条 SQL 里要求每一列非空、非负或不大于 1。示意上，一正一负的比例可能合计为 1；含空值的求和也可能因 SQL 的 NULL 比较规则未进入异常集。这都说明合计规则与各列有效性是不同的检查。

汇率多源检查 144585 会先把 `100JPY/CNY` 报价除以 100、保留六位小数，再按交易日与币种对比较各行报价和组内均值的差异，阈值为 `1e-10`。但是实际查询只纳入 `MD/TL` 两个来源、指定组别和 2023 年以来的数据。名称中出现某个 TITANS 采集任务，不等于这条查询实际比较了 TITANS 来源。

标准资产行数波动检查 197640，用参数指定的月份窗口、且不早于当年一月的各标签月行数，计算均值加减三倍总体标准差，再检查当月数量。窗口包含当月；返回列中的 `0` 表示未触发，`1` 方向表示触发，与前面的 `check_result=1` 通过不是同一约定。它是行数波动检查，也不能替代金额准确性或客户归属检查。[已读证据](../evidence/quality-foundation-evidence.md#quality-business-rules)

<a id="quality-contradiction"></a>
## 一个必须公开的边界：检查 SQL 自身也可能没有检出能力

任务 223385 名称表示比较模型与贴源数据。它将贴源履保参数与 `T03_OTC_COMP_PERF_MARG_REF` 做全外连接，在连接条件中要求：

```sql
SUBSTR(a.SRC_BUSI_DATE, 1, 10) = b.Busi_Date
```

但最后的筛选又要求同样的两个表达式：

```sql
SUBSTR(a.SRC_BUSI_DATE, 1, 10) <> b.Busi_Date
```

按通常 SQL 三值逻辑，成功匹配的行已经满足相等，不能再满足不等；未匹配行的一端为空，不等比较结果为未知，也不会通过 `WHERE`。因此，这份发布文本按所示逻辑不会留下待计数的差异行，随后 `count=0` 会返回通过值。这个推导不依赖于假设当前数据恰好完全一致。

本页保留这一静态发现，未修改检查，也没有据此声称某次生产运行已经误报通过。它说明：**存在一个“模型一致性检查”任务，并不足以构成模型内容一致的证据。** 需要检查逻辑本身具有检出相应差异的能力，再结合实际执行结果判断。[完整发布证据及范围](../evidence/quality-foundation-evidence.md#quality-contradiction)

<a id="quality-missing"></a>
## 没有检查 SQL 的 21 项仍保留为缺口

这 21 项包含用户状态、主体关系主键、若干模型对源比对，以及期权或互换要素变化等检查名称。名称可以说明配置意图，但无法证明实际检查列、阈值、比较日期或返回协议。因此它们仍在总范围里，不能因质量任务属于调度参考就被悄悄排除，也不能从相似检查复制一套条件当成它们的实际规则。

整库会将“检查定义”“检查是否有效”“某次执行是否通过”“业务结果是否可用”分别呈现。当前材料主要支持第一层及部分第二层，后两层需要运行和消费证据。
