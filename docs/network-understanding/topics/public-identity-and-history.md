# 公共身份与历史：账户、账簿、产品和用户怎样保持关联

公共模型给不同业务提供共同的对象入口，但“共同”不表示编号可以通用。本页解释当前范围内 20 项 `FDM_*` 加工，以及将其中账簿资料重新组织给下游的 37259。它们使用 `spdata` 命名空间；不能仅按字段名称与 `pdata_n` 中的对象合并，也不能只凭命名判断已经停用或被替代。

本页所引发布 SQL 有的已经展开为具体日期，例如 `2026-08-27`。下文用 D 表示该份材料的处理日期；这便于说明规则，不表示已证明源码模板写死日期或已验证任意日期重跑。

<a id="public-identity-domains"></a>

## 同一个数字，放在不同对象里就是不同身份

| 对象                   | 本组 SQL 构造的身份                                       | 阅读时要保留的区别                                             |
| ---------------------- | --------------------------------------------------------- | -------------------------------------------------------------- |
| 当事人、机构           | TIT 分支为 `TIT-` 加交易对手源 ID；XIR 分支沿用 `PARTYID` | 两个来源没有在此按名称或证照合并为同一主体                     |
| 账簿在账户模型中的表示 | `TIT-T10-` 加 `KEY_BOOK_ID`，账户类型 `'T10'`             | 这里的账户是账簿表示，不是客户银行账户或资金余额账户           |
| 产品                   | 以 `KEY_INSTRUMENT_ID` 为投管产品内码                     | 内码、证券来源、来源代码值需要分别保留；外部证券代码不等于内码 |
| 期权协议状态与属性     | `OT10-` 加 `KEY_INSTRUMENT_ID`                            | 它与新模型的协议编号、修饰符不能直接视为相同编码域             |
| 用户与角色             | 分别为 `TIT-` 加用户 ID、角色 ID                          | 相同前缀不代表相同实体类型；用户外部编号另有字段               |
| 期权交易事件           | `TRADE_DATE` 加 `KEY_TRADE_ID`                            | 事件号、交易号、合同号和产品编号各司其职                       |

例如源编号都是 `123`，`TIT-123` 的用户、`TIT-123` 的角色和 `TIT-T10-123` 的账簿仍是不同对象。关联时必须同时知道表、对象类型和编码域，不能只对字符串做去前缀处理。

来源：31943、32003、32004、36705、36710、37016、37017、37018、37020、37062、37063 的具体映射见[本页审阅记录](../evidence/public-foundation-review.json)。

<a id="public-party-details"></a>

## 机构基本资料与交易对手附加资料为什么分开

32003 将 XIR 与 TIT 资料组织成机构：名称、组织代码、信用代码、机构类型等。XIR 分支通过银行代码连接交易会员与债券会员，以前者英文名优先、后者补充，并根据债券会员是否匹配构造标志。TIT 分支保留名称和类型，很多证照字段直接为空，删除标志由源 `IS_DELETED` 映射。

32004 则补充交易关系需要的资料。XIR 分支主要提供托管账号、席位、支付系统代码、联系人及交易资格；TIT 分支主要提供法律主体、创建更新信息和履保调整系数。两边共享主体编号，并不意味着两边具有同样完整的资料。尤其该任务 TIT 分支把删除标志写为常量 `'0'`，与 32003 的源删除标志映射不同，不能不加区分地比较两表“有效客户数”。

31943 单独保存名称历史。需要还原过去显示的名称时，应使用它的有效期，而不是用机构当前名称替换所有历史记录。其 XIR 英文名关联使用 `PARTYID = MEMBER_ID`，不同于 32003 中使用银行代码的关联；两表英文名称可能因此不同。

来源：32003 `create` 42–99；32004 `create` 58–142；31943 `create` 9–32。

<a id="public-book-bridge"></a>

## “账户”怎样重新组合成下游账簿

36705 将账簿装入 `spdata.acct`，开户日期取账簿创建时间，持有人、币种、状态和销户日期在该来源分支为空。37015 的 `acct_tit_book` 保存部门、柜台、公司及创建更新信息；37066 的 `acct_name_h` 保存名称历史。

37259 读取这三者生成 `dm_tit.ref_book`：从账户 ID 的第九个字符起恢复源账簿 ID，以 D 日有效名称补充账簿名，以账簿附加资料补充组织信息。名称历史使用 `Strt_Date <= D < End_Date`，最后要求名称关联成功；因此一个账户存在但没有当日有效名称，并不进入结果。销户日期为空时输出失效日期 `2099-12-31`。

这条链能证明三个公共对象怎样组成一个实际下游结果，但不能证明所有源账簿都有唯一、连续的名称历史。查询也没有在账户和附加表上统一过滤删除标志；最终是否保留某账簿，要按整个连接条件判断。

来源：36705 `create` 33–48；37015 `create` 10–25；37066 `create` 33–70；37259 `query` 6–31。

<a id="public-product-references"></a>

## 产品身份、名称、期货条款和行情是四种信息

36710 保存“投管产品内码 × 证券来源”的代码关系，来源是 `R_REF_INSTRUMENT_CODE`。此分支的统一 `Prd_Id` 直接为空；它提供来源代码关系，不等于已经解析出了统一证券主键。身份关系历史的比较键还包含证券来源，省略来源就可能把不同代码体系混在一起。

36711 保存证券简称、全名、类型、市场、币种和发行人等。空市场映射为 `'XXX'`，`OTC` 映射为 `'Other OTC'`；这些是该模型的编码处理，不应在后续未经核对就改成别的市场代码。37058 保存名称历史，其中英文简称从期货属性补入；37059 将最后交易日与最后交割日展开成日期类型 `'10'`、`'11'` 两类历史记录。

37060 保存期货条款，包括交易代码、标准合约、连续合约类型、合约乘数和期货标的编号。合约乘数与数量计量有关，但此任务只搬运条款，没有计算持仓金额。37022 则按日搬运买卖价、开高低收、昨收、复权信息、结算价、行情类型及数据源；它没有在这里统一选择“唯一收盘价格”。

所以，更换证券代码关系可能影响行情和持仓关联；更改最后交易日影响到期判断；更改乘数可能影响下游金额换算。不能用其中一张表同时代替产品身份、交易日历和价格选择规则。

来源：36710、36711、37022、37058、37059、37060 的映射与来源行段见审阅记录。更完整的行情消费见[证券、行情与定价输入](../chapters/04-market-and-pricing-inputs.md)。

<a id="public-history-semantics"></a>

## 历史区间与当前状态表，怎样保留变化

名称、协议状态、附属属性、用户角色、产品代码及重要日期等历史表，按各自对象键比较 D 日来源与 `Strt_Date <= D < End_Date` 的有效记录，区分新增、删除、变更和不变；变更通常关闭旧区间、开启新区间，无变化保留旧区间。它们保存的是本次装载观察到的有效期，不自动等于真实业务变化发生的时间。

| 历史内容     | 比较键             |
| ------------ | ------------------ |
| 当事人名称   | 当事人编号         |
| 产品代码关系 | 产品内码、证券来源 |
| 协议状态     | 协议编号           |
| 协议附属属性 | 协议编号、属性名称 |
| 用户角色关系 | 用户编号、角色编号 |
| 产品名称     | 产品内码           |
| 产品重要日期 | 产品内码、日期类型 |
| 账户名称     | 账户编号           |

NULL 处理不是所有历史表都一样。31943 的名称、37017 的状态和 37018 的属性值直接使用 `<>`；只有 NULL 与非 NULL 发生差异、其他条件不为真时，SQL 三值逻辑可能让它进入“无变化”。36710、37058、37059、37066 则对所比较的属性使用 `NVL(...,'')`，把 NULL 与空串视为相同。不能把所有历史表统称为同一个已经验证的变更模板。

另一方面，机构、账户、产品基本资料等表的维护过程，会把旧有但本次来源缺失的对象保留并标为删除；出现于本次来源的对象更新属性，并可能沿用旧记录的 `Busi_Date`。例如 32003 对已有对象使用 `NVL(旧 Busi_Date,D)`。因此其业务日期不一定是“本行所有字段都在这天产生”的日快照日期。把这类表直接筛成 `Busi_Date = D`，可能排除仍存在且已更新的老对象。

这些维护脚本也包含针对当日记录的清理、关闭或重开步骤；本页没有因此宣称任意中间状态下都能安全重跑。实际唯一性、执行顺序和恢复行为需要运行证据。

<a id="public-daily-results"></a>

## 日终和压力结果保存了什么

37016 的期权交易事件保存期权费、支付日、两个名义本金字段和参与率；37021 的期权日终指标保存源 PV、Greeks、单位 Greeks、定价环境，以及各类定价输入的日期；37069 的压力结果另外保存标的价格与波动率扰动条件。三个任务没有在此重新做期权定价，也没有将两个名义本金字段证明为可互换。

日终表里的分区日期、`AS_OF` 定价日、标的价格日期、曲线实例日期、波动率实例日期是不同字段。压力结果还必须按情景区分，同一合约多个情景的 PV 不能相加成为普通日终 PV。

<a id="public-user-and-source-labels"></a>

## 用户角色与来源标签的边界

37020 保存用户和角色的关系历史，37062 保存角色资料，37063 保存用户的外部编号。角色表的 `Role_Eff_Flag` 对本次来源中的角色写 `'0'`、对来源缺失的旧角色写 `'1'`；不能按字段中文名先入为主地把 1 解释为有效。角色关系存在也不能代替具体资源权限，完整权限消费见[权限与人员](../chapters/13-access-and-shared-support.md)。

另有三处来源标签与实际读取不一致：31943 的 XIR 标签指向债券会员而实际读取交易对手及交易会员；37015 标签指向期权通用信息，实际读取账簿；37060 标签指向另一命名空间，实际读取 `odata_n_tit.r_ref_future_properties`。因此本文以 SQL 的实际读取为据，保留标签差异；不能把 `Src_Tbl` 字符串直接升级为数据血缘。
