# 主体与客户：从源交易对手到可共同使用的业务身份

[返回知识库](../README.md) · [公共对象总览](../chapters/02-public-objects.md)

同一个业务参与方，会在模型中表现为当事人、交易对手、自然人、业务客户、联系人和关系两端。理解这组加工的关键，是保留同一个主体身份，同时分开描述它是谁、以什么角色参与业务、有什么参数，以及这些信息在哪一天有效。

本页覆盖本次发布 `EDW_PTY` 下的 23 个加工任务。它们共同生产主体的不同侧面；这不是全公司的客户主数据字典，也不把每个输出字段都当成已被业务审核的事实。逐项来源、已读范围和缺口见[主体与组织审阅记录](../evidence/public-objects-review.json)。

<a id="party-identity"></a>
## 身份主干：源编号加前缀，角色继续细分

当事人主表 `T01_PTY` 的两条生产分支，都把源侧 `ID` 加上 `TIT060-` 前缀作为 `Pty_Id`，把源长名称写成当事人名称。源类别为 `INDIVIDUAL` 时写入类别代码 `190400`，其余统一写 `290203`。这意味着主表这一列只提供较粗的分类：公司、产品等不会在这个表达式里分别保留类别。

更细的业务角色留在交易对手表 `T01_PTY_CUTP`：`COMPANY`、`PRODUCT`、`INDIVIDUAL` 分别映射为机构、产品、个人代码，其他值沿用源值；其中 `MARKET` 分支也沿用原值。该任务的注释提到检核，但这条查询本身没有按这个类别排除行。

因此，示意主体 `TIT060-123` 可以在主表里被归为非个人，同时在交易对手表里被进一步识别为产品。两张表回答的问题不同。前缀使编号来源容易辨认，却不证明源 `ID` 在所有时间和来源中绝对唯一；消费端仍要保留来源与所需日期。

这里同时存在实际名称不同的两套源表：`D_REF_COUNTERPARTY` 与 `D_REF_COUNTER_PARTY`。例如，任务 77078 实际读取前者，写出的逻辑 `Src_Tbl` 标签却仍为后者，另用 `Real_Src_Tbl` 保留实际源名。任务 76984 则实际读取后者。不能根据同一个目标分区标签，就认定两份输入相同或互为别名。[证据 P76984、P77078、P105379、P105518](../evidence/public-objects-evidence.md#party-identity)

<a id="party-attributes"></a>
## 名称、个人、评级和资质不是同一份“客户属性”

| 侧面 | 实际加工提供的内容 | 使用时的边界 |
|---|---|---|
| 名称 `T01_PTY_NAME` | 源长名、短名及英文简称，按来源和业务日期保存 | 英文全称在这两条分支里填空；名称不能代替身份键 |
| 自然人 `T01_INDV` | 339 分支只纳入 `CTPTY_TYPE='INDIVIDUAL'`，保留姓名和删除标志 | 多个人属性为空或默认值，不能因有出生、职业等列就认定已采集完整个人资料 |
| 评级 `T01_PTY_RAT` | 评级类型固定为 `OTC_CUTP_LVL`，结果来自 `DEALER_LEVEL` | 评级日期、机构、生效和到期日期在已读分支均为空；不能解释为一套完整信用评级历史 |
| 分类 `T01_PTY_CLAS_H` | 分类类型固定为 `41`，值来自扩展参数 `APTITUDE` | 代码的业务值域仍需字典确认；该页不替原值补出未证实的等级含义 |
| 鉴别信息 `T01_PTY_IDTY_INFO` | 类型 `24000` 下保存 `UNIFIEDSOCIAL_CODE` | 这是采集的识别内容，不证明它已通过唯一性或真实性核验 |
| 重要联系人 `T01_PTY_IMP_LKMAN` | 从扩展参数分别生成法定代表人、实际控制人两支，类型为 `01`、`10` | 联系方式和证件等大量字段为空；不能据此视为完成尽职调查 |

评级还有一个具体的来源差异：任务 105077 直接从 `D_REF_COUNTER_PARTY` 取得 `DEALER_LEVEL`；104300 从 `D_REF_CTPTY_EXT_PARAM` 取得，再按 `KEY_CTPTY_ID=ID` 左关联另一份当事人源表补类别。后者在关联未命中时仍可保留扩展参数行。交易对手实际控制人和产品编号也有类似差异：105379 需要左关联扩展参数，105518 则直接从其源记录取得。

这些任务常把不同真实来源写入相同的逻辑来源分区。分区标签适合组织输出；查证字段出处时，应继续读实际 `FROM` 和关联表达式。[证据 P104299、P105076、P104298、P104300、P105077、P105380、P219164、P150755](../evidence/public-objects-evidence.md#party-attributes)

自然人的旧分支 105075 仍有一个实质缺口：本次发布的 `create` 只含目标表定义，`query` 从 `TEMP.T01_INDV_MID_TIT162` 按增、改、不变、删四类写出，但未包含该中间表的构造。已检查本地对应 Input Pack，也只有这两个 SQL 文件；图内未见其最终生产任务。因此可以解释它怎样写出结果，不能借另一条 339 分支替它证明上游筛选和字段来源。

<a id="party-business-profile"></a>
## 业务客户页把参数接到主体上，但不会自动填满模型

任务 150757 用计算日的 `D_REF_COUNTERPARTY` 作为主体，左关联同日 `D_REF_CTPTY_EXT_PARAM`，条件为 `ID=KEY_CTPTY_ID`，形成 `T01_OTC_DERI_CUST`。主体行是否存在由左侧决定，扩展参数负责补充业务信息。

当前分支实际提供三组重要内容：

- **业务组织与协议标识**：主、补协议编号分别取扩展参数中的双方协议编号字段；引入机构、客户经理、经办人也来自扩展参数。
- **港美业务费用与利息参数**：港美佣金模式、费率、每股佣金、利差、固定利率、计息基准和利息区间等。部分模式先查转换表，未命中时沿用源代码。
- **业务控制参数**：名义本金上限、资质复核信息、关联方和内部主体等标记。其中部分布尔值转换为 `1/0`，未识别值的处理要看各自表达式。

与此同时，模型中多项主、补协议签署日、履保协议、审核、报备等字段在当前分支填空。表的设计范围大于这条任务已经取得的信息。使用这张表回答“客户费用参数是什么”与“客户协议是否审核通过”，证据条件并不相同。

它的时间维护也有明确职责：新提取记录与**上一个交易日**同来源分区比较，按 `Pty_Id` 判增、改、不变、删，然后把四类结果写到计算日分区。源记录消失时仍输出一条带删除标志的旧记录。因此当日分区包含的并不一定都是源侧当前有效客户；使用方是否排除删除行，要继续检查消费查询。[证据 P150757](../evidence/public-objects-evidence.md#party-business-profile)

<a id="party-properties"></a>
## 通用统计表里存了部门、佣金和业务许可

`T01_PTY_STATI_INFO_H` 使用“主体＋信息类型＋内容”表达多种属性。只读 `Stati_Cont_Desc` 或只按主体连接，会丢掉决定含义的信息类型。

| 信息类型 | 已核对的源值 | 这条信息回答什么 |
|---|---|---|
| `36` | `DEPARTMENT` | 交易对手在源侧所属业务部门 |
| `46` | `CTPTY_FEE_RATE` | 港股相关交易对手佣金率参数 |
| `75` | `GROUP_FLAG` 转换结果 | 是否为交易对手账户组 |
| `59` | `ALLOWBUSITYPE` | 允许的业务类型，一名交易对手可以有多项 |

114401 的三支包含 `36/46/75`；114423 的旧源分支只产生 `36/46`。不能因为同写一张目标表就认为二者属性覆盖相同。173975 单独产生类型 `59`，其新旧关系匹配键明确包含业务类型值 `Stati_Subdv_Cd`，以保留一对多许可。

例如，同一客户获准两种业务时，许可表可以有两行。把这张表只按客户号连接到一笔金额上，可能把金额扩成两行；是否出现重复取决于实际数据与连接条件，静态证据足以说明为何必须带上信息类型和业务类型，却不能证明当前生产数据已经重复。[证据 P114401、P114423、P173975](../evidence/public-objects-evidence.md#party-properties)

<a id="party-relationships"></a>
## 身份映射与账户组关系：两端的角色不能交换

`T01_PTY_RELA_H` 的关系类型 `01` 分支，把带 `TIT060-` 前缀的本方交易对手连接到 `OUTSIDE_CTPTY_CODE`。新旧匹配使用本方主体、关系类型、主体类别以及外部编号。相同外部编号属于哪个外部来源，还应结合映射附加信息：任务 150759 将 `OUTSIDE_SOURCE` 放入关系来源，并保存创建时间等信息。它没有把外部编号强行改造成另一个 `TIT060-` 编号。

类型 `29` 则来自交易对手账户组关系：一端取账户组源记录 `ID`，另一端取 `KEY_CTPTY_ID`，两端分别加主体前缀。其含义与跨系统同一主体映射不同，不能互相替代。

该 29 分支还有一个需读者知道的实现细节：查询分别连接两端的交易对手信息，但两端类别表达式都取第一端别名 `B`，第二端别名 `C` 未用于对应类别。这里保留代码实际行为，不据此替第二端推断正确类别；类别影响后续关联时，需要专项确认。[证据 P104301、P105079、P150759、P219175](../evidence/public-objects-evidence.md#party-relationships)

<a id="party-margin-limit"></a>
## 履保方案和额度，是附着在客户上的两类控制信息

履保方案 `T01_CUTP_PERF_MARG_PLAN_INFO` 从 `D_MARGIN_PLAN` 取得方案编号、交易对手、履保协议、担保品类型、抵扣方式、盯市方式、名义结构、分配资金账户标志、自动追保提保参数及最小转移金额等。它描述**这项方案怎样配置**，不是已经发生的保证金流水，也不是计算后的保证金余额。

任务 200060 把源交易对手和可选的管理人交易对手分别转为带前缀的身份；方案状态与收费方式查临时转换表，未命中沿用源代码。它保留源删除标志，没有在该查询里过滤删除方案。因此，后面的资金与风险过程需要自行判断使用哪些方案。

额度历史 `T01_PTY_LMT_H` 则来自 `D_RISK_CTPTY_LIMIT_THRESHOLD`。任务 229973 先按客户、转大写后的额度指标、批准业务类型分组，按创建时间倒序取一条，再维护历史区间。额度值为 `LIMIT_INDEX_VALUE`；其新旧匹配键也包括这三个维度。创建时间相同却值不同的记录没有额外排序键，本次未证明这种并列情况是否存在。额度类型和数值的单位不能仅由表名补全。

所以，“客户有履保方案”“客户有某项额度”和“客户今日还有多少可取资金”是三个问题。前两者提供配置与约束，第三个问题还需要账户、余额、持仓及计算规则。[证据 P200060、P229973](../evidence/public-objects-evidence.md#party-margin-limit)

<a id="party-history"></a>
## 三种保存方式决定怎样回答历史问题

| 保存方式 | 本页中的例子 | 能读出的时间含义 |
|---|---|---|
| 来源分区内保留当前状态与删除标记 | 当事人主表 | 数据更新后主要反映维护后的状态，不能仅凭表说明断言能还原每日所有旧值 |
| 每业务日期保存快照 | 名称、交易对手、业务客户等 | 读取哪天分区就决定观察日；部分分支仍带入已删除记录 |
| 维护开始和结束日期 | 关系、分类、通用属性、额度 | 开链条件为 `Strt_Date ≤ d < End_Date`，变化时关闭旧区间并打开新区间 |

历史关系任务会先撤销计算日的新增或闭链痕迹，再重新比较、关闭和打开区间。这描述代码试图重算当日的方式，不证明任意执行顺序或故障重试都已通过运行验收。特别是相同边界日，旧区间不再有效，新区间开始有效；消费端若改用两端都包含的条件，就可能在变化当天同时取到新旧关系。

本页未将同名任务、相同 `Src_Tbl` 或相似模板视为可互换。字段来自哪个源、是否有完整中间加工、是否保存历史，均以本次固定 SQL 为依据。后续问题应先确定身份和日期，再继续读[风险](../chapters/06-risk-and-pricing.md)或[财务](../chapters/07-finance-and-valuation.md)怎样消费这些信息。
