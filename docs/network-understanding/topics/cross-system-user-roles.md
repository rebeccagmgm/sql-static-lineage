# 跨系统人员角色汇总：把不同账号口径放进同一张清单

134442 的输出将 ERP 姓名和编号、员工任职状态、系统名称和用户编号、系统账号状态、角色、ERP 部门、所属分支机构、操作分支机构、审核权限、岗位和注册日期放在一起。它提供跨系统核查所需的对照，不是统一所有系统身份的主数据，也不是某一交易的处理过程。

<a id="cross-system-employee-base"></a>

## 公共员工底表和日期

员工底表来自 `pdata_n.t98_org_emp_base_info` 的计算日快照，补员工类型、状态字典和岗位描述。“内退”且员工类别为“返聘人员”的记录显示为“内退返聘”。系统账号通过 ERP 编号、OA 账号或各自回退规则连接这份员工资料。

固定发布 SQL 已把很多日期展开为 2026-08-26。部分源直接取这个日分区，柜台等部分取 `pretradedate(date_add(该日,1),1)` 所指定的交易日；统一模型的关系则经常取结束日期为 2099-12-31 的当前版本。这些不是一套完全相同的历史截面，不能说输出分区中所有属性都代表该业务日当时有效的状态。

最终各临时结果内部常有 `DISTINCT`，它们之间仍用 `UNION ALL` 合并。统一列结构不代表一个人一行，或不同分支不会出现相同账号。员工岗位的最后一次补充连接也只包住前一组分支，后面单独接入的算法、ATP、TITANS、总部分类等分支不都经过同一补充步骤。

## 导出为何会减少操作分支

74272 读取参数日汇总，按以下思路构造导出候选：对一般系统，如果某个系统用户号存在操作分支为“广发证券”的记录，就保留这类记录；如果没有，保留其非空操作分支记录。另外保留操作分支为空或 NULL 的记录；新意系统和旧标签“ATP快速交易系统”走整组保留分支。最后按全部输出列分组去重。

这不是单纯的 `SELECT *`，三个实现细节会影响结果：

1. 上述“存在广发证券分支”的判断和接回明细只按 `sys_num`，没有同时加 `sys_name`。如果不同系统恰好使用相同用户号，其中一个系统的分支记录可能影响另一个系统的候选范围。是否实际发生取决于数据，不能先宣称跨系统编号唯一。
2. NULL 操作分支同时满足前面候选与单独保留条件，可能从多个分支进入；最后全列分组可以消除完全相同的重复，但不解决不同列值的重复或身份歧义。
3. 源汇总现标签为 `ATP-IS极速柜台`，导出特殊条件仍写 `ATP快速交易系统`。对现标签而言，它会进入一般系统规则，不能按注释理解为仍享有旧特殊保留逻辑。

输出包含业务日，却没有带注册日期。由本导出形成的消费结果，无法单独支持注册日期核查。其目标物理表也应以明确传输配置为准，不能把 `SELECT` 的源表或任务名自动解释成目标。

来源：74272 `query` 35–82、101–132、134–173、175–190 行。

## SQL 片段可以解释规则，执行顺序仍有明确疑点

134442 固定 `query` 文本先删除若干临时表，再出现对其中临时表的写入和读取；181–215 行又删除一组随后在最终合并中读取的临时表。例如第 1 行删除 `pwc_psn_sys_user_roles_temp`，第 9 行又对它 `INSERT OVERWRITE`。按这些文本直接顺序执行，所需临时表的存在性无法成立。

已检查该任务当前准确 Pack，`create` 和 `query` 哈希均与发布相同，所以不能把问题简单归因于已经被当前本地脚本修正。平台是否按槽位内部重新拆分前后置语句，需要执行配置或运行证据。这里按各 SQL 分支解释其表达的数据规则，同时明确：**现有材料不能证明整个脚本可以按展示顺序成功运行，也不能证明这份权限汇总已经交付。**

这项执行边界不会让已经可读的条件、关联和输出表达式消失，但会限制“已产生正确结果”的结论。静态规则理解与运行验收应分别查证。
