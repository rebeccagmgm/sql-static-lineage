# 怎样比较两份结果：先对齐对象、时间、范围与计量

读完整个知识库后，最有用的能力不是记住表名，而是能解释：为什么两张表都叫合约、客户、规模或收益，结果却可能不同。本页把各业务主题反复出现的判断方法连在一起；具体规则仍以各主题的 SQL 证据为准。

## 一行究竟在记录什么

先把结果翻译成一句完整的话：“在某个时间范围内，按哪些标识，记录哪个对象的什么事实。”

| 结果形态 | 一行可能代表的内容 | 不能直接替代什么 |
|---|---|---|
| 交易记录 | 一次交易或成交事件 | 某个合约的全部存续历史 |
| 合约主信息 | 一份协议或合约的属性 | 合约下全部资产腿、观察日或交易事件 |
| 持仓、余额 | 某个时点对象上的存量 | 当天发生额或全部历史流入 |
| 损益 | 指定对象、期间和计量规则下的结果 | 资金账户现金变化或会计收入 |
| 归属、分配结果 | 对业务贡献按机构或人员关系拆分后的结果 | 未分配的原始规模 |
| 人员权限清单 | 员工、账号、角色、资源的一种组合 | 员工人数或当前实际授权成功次数 |

例如，一名用户有两个角色，每个角色关联多个账簿，权限清单出现多行是自然结果。把它与员工主表直接比较行数，会把关系数量误认成人数变化。[权限与人员](../chapters/13-access-and-shared-support.md)解释了这种组合粒度。

对象编号也要带上来源与类别理解。统一协议模型中的修饰代码区分对象类别，某些协议关系使用的类别与看似同名的宽表字段并不一致；去掉类别后仅凭数字或名称关联，可能接到另一类协议。[合约与持仓](../chapters/03-contracts-and-positions.md)保留了这些具体差异。

## “同一天”至少有五种含义

| 时间含义 | 它在回答什么 | 本库中的具体差异 |
|---|---|---|
| 来源业务日 | 源系统认为事实属于哪一天？ | 有些采集把源业务日另存为 `SRC_BUSI_DATE`，再添加落地日期 |
| 加工或输出分区日 | 本批输出写在哪个分区？ | 一个当前分区里可能保留多个计提日或历史事件 |
| 历史有效期 | 某个属性或关系在什么时候有效？ | 常见半开区间与少数含两端的 `BETWEEN` 并存 |
| 统计期间 | 累计、日均、月度或同比使用哪段窗口？ | 月末基期、上月奖励、本月入账、年内累计不等价 |
| 日内批次 | h15、h13、h0830 等代表哪次快照？ | 有的批次写在 `busi_date` 字符串中，有的写时间标签，有的仅出现在任务名称 |

一个示意例子：某客户关系在日期 D 开始生效，普通 ATP 成交按 D 的前一交易日账簿映射筛选，ETF 成分股成交按 D 当日股卡清单筛选。即使成交都发生在 D，两份结果也可能纳入不同账户。这是口径可能导致的差异；是否实际有差异还要看该客户在两份清单中的数据。两条实际 SQL 的证据见[交易与结算](operations-trading-and-settlement.md)。

再看奖励：开户奖励后处理从上个月取金额，写入本月奖励账期。核对时应将“来源奖励月”和“输出账期月”错位对齐，不能直接以同名月份连接。[目标端奖励入账](delivery-postprocessing.md#online-account-reward-posting)提供实际条件。

## 连接不仅补字段，也会改变纳入范围和行数

`LEFT JOIN` 不保证左侧所有记录最终保留。如果随后 `WHERE` 要求右表某字段非空，匹配不到的记录仍会被排除。证券主题中的部分期货映射、权限主题中按资源类型筛选，都有这种行为。

反过来，如果右侧同一个键有多条记录，连接可能扩展行数。一份合约连接多个销售关系、一个 OA 账号连接多个部门版本、一项定价环境权限连接多条环境曲线记录，都需要先解释右侧的粒度，不能把新增行全部当作业务增长。

`DISTINCT` 只能消除所有所选列完全相同的重复。它不能证明源主键唯一，也不能保证不同业务含义的同号记录被正确区分。`ROW_NUMBER` 也只说明选了一行；如果排序不是业务时间或组内排序值相同，就不能把它描述为“取最新”。

## 金额相同的单位，不代表相同的计量

资金发生、余额、名义本金、市值、损益、奖励和标准资产可以都表现为数字，甚至使用同一币种，但它们回答的问题不同。

财务接口中的数量有时是事件方向标志；部分交易导出中的 `qty` 可能是数量，也可能是比例因子，`amt` 也可能按回报类型承载现金替代或成交金额。只有字段名，无法安全地决定求和或与另一张表对账。[财务接口](../chapters/07-finance-and-valuation.md)与[交易结算](operations-trading-and-settlement.md)分别解释这些复用。

标准资产则包含业务规模的系数折算、归属分配和封顶。读公式时应明确先分给机构再封顶，还是先对全量封顶再分配；这两种运算一般不会产生相同结果。不同链的系数也可能不同，应保留各自版本和使用范围。[标准资产与考核](../chapters/09-performance-and-assets.md)及其子页逐项说明。

## 用同一种变化穿过整条链

下面列的是依据已读规则可以推断的影响方向，不是已经观测到的真实业务异常。

| 假设变化 | 应沿哪条联系检查 | 不应直接得出的结论 |
|---|---|---|
| 客户 OA 或 ERP 映射改变 | 员工对照 → 人员角色清单、部门补充、按人员输出 | 不能据此认定源角色授权也改变 |
| 证券代码映射缺失 | 主证券身份 → 标的连接 → 期货/定价/成交输出的纳入条件 | 不能一概认为只少了一个展示名称 |
| 账簿归属关系改变 | 合约与账簿 → 香港范围、经营归属、客户或机构汇总 | 不能假定所有分支使用同一天关系 |
| 合约终止 | 存续筛选 → 持仓与风险 → 日损益、累计损益、财务事件 | 不能假定终止后所有结果都应无记录 |
| 分配比例或折算系数改变 | 分配明细 → 标准资产 → 日均、增长率、评价 | 不能只比较最终总额，需分清计算顺序与期间 |
| 字典描述或备注改变 | 当前码表与历史区间 → 使用当前/历史解释的消费者 → 展示或检查 | 不能直接认定金额计算也已变化；备注在部分历史模型中参与身份 |
| 合约系数的映射或优先级改变 | 内部合约号 → 协议编号与修饰符 → 销售参数及日报 | 不能把参数审批事件存在当成已审批或已生效 |
| 接口打标为完成 | 打标 SQL → 真实推送执行 → 目标记录 → 消费端使用 | 不能把常量 `COMPLETED` 当成金额核对或实际送达 |

上述公共规则详见[身份与历史](public-identity-and-history.md)及[码表、系数与配置](reference-codes-and-parameters.md)。

## 怎样形成一个可复核的比较结论

一次有效的比较，应能写出这样的说明：“这两份结果是否记录相同对象；使用什么日期或批次；各自纳入哪些分组；怎样连接和分配；字段单位及计算顺序是什么；因此哪部分应该一致，哪部分允许不同，剩下哪个条件还缺证据。”

如果这些条件尚未对齐，差异首先是待解释问题；如果已经对齐，才有依据继续检查源记录、执行结果或实现缺陷。质量检查能提供某个条件的证据，但它通过了什么条件，也需要单独阅读。[检查与证据边界](quality-and-evidence.md)给出了具体反例。
