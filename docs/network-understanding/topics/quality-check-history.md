# 历史检查：区间合法、交叉、断开与重复版本

[质量检查总览](quality-check-families.md) · [逐任务证据](../evidence/quality-review.json)

40 项历史检查分成四组：13 项单行日期合法性、13 项相邻区间交叉、1 项断链、13 项重复链。它们共同返回一行 `check_result`：未发现所查异常为 `1`，发现为 `0`。聚合后的 `LIMIT 10` 不表示只检查了10行，也不返回10条问题明细。

## 单行日期：严格大于与大于等于不同

55221、58213、64958、65284、72774、72836、154819、185854、188519、188818、195772、208105 查 `strt_date>=end_date`，因而同时纳入零长度和倒置区间。71468 则是 `strt_date>end_date`，相等日期不属于它的异常集合。

| 协议名称、主体关系、主体统计                                     | 55221、58213、64958                            | 无来源或日期切片                                          |
| 用户角色关系                                                     | 65284                                          | 排除 `data_src_cd='BDP'`                                  |
| 协议主体关系                                                     | 71468                                          | 没有其他有效过滤；仅检查严格倒置                          |

开始日或结束日为 NULL，不会因为普通 `>=` 或 `>` 比较而被选中。这类规则本身没有证明日期必填，更没有判断业务上正确的生效日。无输入行时 `COUNT=0` 也会返回 `1`。

## 交叉链：先按指定对象分组，再比较下一次开始日

基本形式为：

```sql
lead(strt_date, 1, end_date)
  over (partition by <object keys> order by strt_date) as next_strt_date
-- 外层检查
where end_date > next_strt_date
```

默认下一开始日设为本行结束日，所以每组最后一行不会因“没有后续版本”而触发。相邻区间刚好首尾相接不属于重叠。分组和来源过滤决定哪些记录算同一条链。

## 断链：只有一项专门查相邻区间空档

154818 对 `pdata_n.t04_inr_org_rela_h` 按 `Inr_Org_Id,Inr_Org_Rela_Type_Cd` 排序，用同样的LEAD默认值，但外层条件是 `end_date<next_strt_date`。它查相邻版本中间是否有空档，不查第一条之前或最后一条之后是否缺历史。

这份断链与154820交叉链的窗口键不同：后者多了 `Inr_Org_Cate_Cd`，并排除部分来源和标识。因此不能直接合并两者结果，声称同一对象集合“既不交叉也不断链”。

### 64934 实际比名称表达的规则更窄

连接已经要求 `A.User_Id=B.User_Id`，之后唯一的属性比较却是：

```sql
nvl(A.User_Id, '') <> nvl(B.User_Id, '')
```

在成功匹配的行上，这个比较不会为真。因此只要同用户、角色和关系类型存在一个能匹配到的下一版本，且两段连续或重叠，它就会被归入重复，不能识别其他业务属性是否变化。其定义可以解释，但不能据此声称检查了整行属性冗余。

### 所有重复链都要保留的边界

`NVL/COALESCE(x,'')` 会合并NULL和空串的差异；未列出的字段变化不会影响判断。多条同日记录、窗口键缺少必要来源、a/b过滤不对称，都可能改变实际配对和计数。若b侧被过滤到无法匹配，后续NULL比较和默认值可能使结果偏离“比较下一版本”的直觉。本文指出条件，不假设这些情况在某次数据中已经发生。

历史规则与日期完整性、业务生效口径、运行成功仍是不同证据层。完整原始行段及任务映射见[审阅账本](../evidence/quality-review.json)。
