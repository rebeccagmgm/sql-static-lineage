# AML 名单与辅助控制：候选、清理和检查各能说明什么

名单加工、地址比较、设备清理和数据检查是不同环节。名字中有“黑名单”不代表已经完成制裁认定；检查表出现“正常”也不代表本次执行了所有业务检查。下面按已核读 SQL 说明各自作用，并把文本完整性疑点与实际业务结果分开。

<a id="aml-list-candidates"></a>

## 特殊客户名单怎样进入候选

79859 从 `aml_blacklist` 中选择三类名单代码，映射到特殊客户分类，限制证件号码长度，并写入 `amlci_specialclient`。其注释分别对应境外政要、密切关系人和家庭成员，但具体客户是否确实属于这些类别，不能仅由分类代码证明。

这份文本先把 `amlci_specialclient` 中来源不为零的记录再次追加到同一表；随后生成名单记录，行号排序没有稳定顺序，生效开始与结束日期也使用同一个字面日期。因而不能把生成编号当作长期稳定身份，或据此认定名单覆盖了一个持续有效期间。追加是否伴随外部清理，尚未确认。

78394 把个人、机构、产品及公共客户整理成候选视图，再按证件号连接特殊客户名单，并结合开户/名单创建日期；另一个分支读取既有名单关系中的特定类型与处置状态，排除已识别对象。产品分支使用管理人证件参与关联，因此产品与管理人的名单关系不可混为同一对象身份。

其后可见覆盖写名单关系的语句，大量字段使用常量，并按关联结果更新备注。这是需要核对原始执行脚本的重点，当前不能直接宣布客户身份被实际覆盖。完整的 95819 黑名单汇总任务尚未完成业务核读，不能把这两个辅助任务当成全部名单匹配规则。

<a id="aml-cleanup"></a>

## 清理条件不能只按任务名称理解

80597 的覆盖保留条件为“创建日期不等于指定日” **并且** “来源属于两个指定提供方”。它不是简单地删除“指定日且属于这两个来源”的记录；按文本执行时，其他来源也不在保留集合中。是否有专用输入范围使这种写法符合预期，需要上游合同。

80777 先保留设备信息表中日期大于指定日的记录，再按日期不等于指定日筛选，并追加当日委托设备数据。按这一片段，旧日期记录不会因第二步重新回来。后续过滤指定委托方式，归一化重复字符等 IP、MAC、设备编号占位值。它说明设备字段怎样整理，不能证明真实设备身份已验证，或历史明细可按任意日期回溯。

<a id="aml-address"></a>

## 地址比较有一个应单独保留的文本疑点

78326 整理个人和机构地址，利用地区字典补省市，再与营业部地区比较；但最终条件中的两条配置分支分别要求字面值 `'10' = '1'` 或 `'10' = '0'`。两条在所读文本中都不成立，因此仅按该文本求值不会筛出结果。

这不等于已经证明生产地址检查一直为空。配置参数如何展开、采集是否取得了完整原始表达式仍未确认。使用这条检查前，需要先确认有效配置与原始执行表达式；不能把空结果解释为“没有异地地址风险”。

<a id="aml-data-check"></a>

## 数据检查结果的格式化不等于执行检查 SQL

165402 的可见片段根据已有 `check_result` 和配置阈值拼接检查说明：数量为零、数量超过阈值、比例与阈值比较等分支有不同正常/异常含义。比例先按四位小数处理，再格式化为百分比。没有看到执行记录中 `sql_code` 内容的步骤，因此此片段更适合解释为已有检查结果的整理。

文本还出现删除检查表后再读取该表、中间表创建与替换步骤不闭合的问题。当前 Pack 与发布文本一致，只说明材料复制一致；它们来自相同 SQL 缓存采集链，不能排除共同遗漏包装步骤。这里记录的是**静态材料的执行顺序疑点**，没有把它升级为已验证的运行故障。
