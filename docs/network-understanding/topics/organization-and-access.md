# 组织、用户、角色与权限：业务归属和可见范围怎样连接

[返回知识库](../README.md) · [公共对象总览](../chapters/02-public-objects.md)

这组加工同时提供两种基础：业务属于哪个账簿部门与公司，以及源系统用户通过什么角色接触哪些资源。组织关系帮助理解业务归属，权限关系帮助理解数据可见或可操作范围；它们不能用同一列“机构”或“人员”互相替代。

本页覆盖固定发布 `EDW_ORG` 的 11 个任务。它说明源配置如何进入公共模型，不把静态权限记录当成当前用户已经获得访问权，也不覆盖所有应用最终的鉴权逻辑。[逐项证据](../evidence/public-objects-evidence.md#organization-model)

<a id="organization-model"></a>
## 账簿部门和公司先形成组织，再形成上下级关系

任务 165634 从 `D_BK_DEPARTMENT_PROPERTIES` 当天记录分别提取去重后的 `DEPARTMENT` 与 `COMPANY`，合并成公共组织。两类对象的类别同为场外衍生品账簿部门大类，细分类型区分业务部门和业务公司。名称通过字典中的“编码＋字典类别”取得，避免仅按文本编码找名称。

任务 165635 用同样两支来源生成组织名称历史；简名与全名在当前分支都取同一个字典标签。任务 165637 则生成“部门→公司”的上级关系，关系类型为 `10`，并保留有效区间。

可以用一条示意关系理解：某个账簿由部门 A 管理，配置中 A 隶属公司 B。部门与公司各自成为组织记录，上级关系再把 A 连到 B。账簿本身到部门的连接仍由账簿相关模型提供，不能把“部门属于公司”的关系直接解释为每笔交易的财务账套。

还有一个身份边界：组织主表新旧比较仅用 `Inr_Org_Id`；源提取虽然区分 Department 与 Company，但本次没有证明两类编码永不重号。名称查询带类型，不等于整个模型每一步都保留了同样的身份区分。

<a id="organization-parameters"></a>
## 部门附加信息还携带币种与履保配置

任务 165638 把部门配置记录的源 ID、部门、公司、本币及跨币种履保开关写入 `T04_OTC_DERI_DEPT_ADTNL_INFO`。开关 `Y/N` 转为 `1/0`，其他值沿用。这个结果提供部门层面的参数，不能直接代替某个客户或合约的履保方案。

211773 保留同样字段映射，但在发布文本里使用 `${src_table}`、`${data_day_str}` 等未替换参数。它不是一份已经证实按某个日期执行的记录；解析和消费该变体前，要明确参数怎样绑定。两项同名任务同时出现在范围内，不足以证明谁是当前唯一运行者。[证据 P165638、P211773](../evidence/public-objects-evidence.md#organization-parameters)

<a id="access-identities"></a>
## 用户编号、外部人员编号与角色编号各有用途

公共用户 `T04_USER` 用 `TIT007-` 加源 `KEY_USER_ID` 形成用户编号；名称、描述、开户日期来自 `A_ADM_USER`，用户状态先查转换表，未命中沿用源值。另一个历史属性任务把 `OUTSIDE_ID` 写入类型 `12` 的用户统计信息。因此，源应用用户编号和其外部编号是两列不同信息，不能省略映射直接当作员工号使用。

公共角色 `T04_ROLE` 用 `TIT005-` 加 `KEY_ROLE_ID` 形成角色编号，保存角色名称、描述与创建人。创建人再带用户前缀，使角色的维护人可以连接到公共用户。角色状态在这一分支填空，角色有记录不等于角色当前启用。

用户角色关系 `T04_USER_ROLE_RELA_H` 把两种编号连接起来，关系类型为 `01`。新旧匹配使用“用户＋关系类型＋角色”，因此一个用户可以保留多个角色关系。模型另有业务有效起止字段，但当前源提取将它们填空；实际维护的是数据历史的 `Strt_Date/End_Date` 区间，两者不应混为一个日期概念。[证据 P159420、P159422、P159423、P177461](../evidence/public-objects-evidence.md#access-identities)

<a id="access-resources"></a>
## 资源权限和菜单权限落在同一模型，表达的对象不同

资源权限任务 159421 读取 `A_ADM_ROLE_ACCESS`，形成角色、资源类型、资源编号和访问类型。资源类型与访问类型分别查代码转换表，未命中时保留源值。其新旧关系匹配键包含角色、资源类型、资源对象和用户权限代码。

菜单权限任务 178884 读取 `A_ADM_MENU_ROLE_MAPPING`，去重后把菜单编号转换成带 `TIT288-` 前缀的权限对象；权限类别为 `1`，对象类型为 `11`。它与资源权限写入同一张 `T04_ROLE_RIGH_H`，但来源分区和权限类别不同。只按角色合并权限而忽略对象类型，就无法分清“看某个菜单”与“访问某类资源”。

读一条完整权限路径，需要依次回答：用户是谁、当前应选择哪段角色关系、角色拥有哪种权限、权限针对什么对象。最终应用还可能施加其他条件，本页没有把这组关系转换为实际访问许可。[证据 P159421、P178884](../evidence/public-objects-evidence.md#access-resources)

<a id="organization-history"></a>
## 历史与典型变化：会改变哪一类结果

组织名称、组织上级、用户外部编号、用户角色以及角色权限都维护开始和结束日期；它们按 `Strt_Date ≤ d < End_Date` 选开链记录，变化时关闭旧区间、打开新区间。用户、角色和组织主表则在来源分区内维护当前信息及删除标记。读取某一天的历史关系时，不能随手连接今天的主表属性后仍称它为完整历史快照。

| 变化 | 从本组实现可以判断的影响 | 仍取决于下游的事项 |
|---|---|---|
| 部门更换所属公司 | 上级关系将形成新旧区间 | 报表是否按发生日关系或当前关系归属 |
| 用户更换角色 | 用户角色关系发生变化 | 应用何时同步、是否还有其他鉴权条件 |
| 角色增加菜单或资源权限 | 对应权限对象关系新增 | 用户最终可见页面或数据是否改变 |
| 字典名称修改 | 组织名称可能更新，身份编码未因此必然改变 | 报表是显示当前名称还是保留历史名称 |
| 部门跨币种履保开关修改 | 部门附加配置改变 | 哪项保证金计算实际读取并采用该开关 |

这些关系说明了为什么一张业务加工图会连接很多用户、菜单、组织和权限表。它们可能共同支持业务可见范围与归属，但不是金额从上一张表流向下一张表的证据。后续跨系统权限汇总页会继续说明这些对象怎样与其他业务域会合。
