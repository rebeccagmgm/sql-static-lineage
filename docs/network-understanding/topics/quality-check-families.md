## 先看查询返回什么，再讨论平台怎样判定

| 返回形态 | 本范围中的实际例子 | 不能直接推导的结论 |
|---|---|---|
| 一行 `1` 表示无所查异常、`0` 表示发现异常 | 码表、外键、多数区间检查 | `1` 不证明所有字段完整或所有来源受检 |
| 一行 `1` 表示达到数量条件、`0` 表示未达到 | 记录数对比、必要类别存在性 | 两边都空有时仍返回 `1`；必须检查是否另有非空条件 |
| 一行 `0` 表示未触发、`1` 表示触发 | 173126、173127；3σ 的各标签列 | 不能套用“1 通过” |
| 返回异常明细或空集 | 主键分组、比例、Delta 缺失、外键缺失 | `LIMIT 1` 不是异常总数；空集怎样映射任务状态需执行协议 |
| 返回符合条件的成功行或空集 | 155614/155638/155639 的业务日期行、206127 的 `CASE=1` 行 | 不能把所有空集都当作通过 |
| 返回数量、数量差、重复行差值 | 64401、223331、209812、209840 | 数字本身不是平台已判定的通过/失败 |
| 查询逻辑使结果恒为空或恒为通过值 | 156838、223385 | 有检查任务不等于具有预期检出能力 |

外层 `WHERE`、聚合前后的过滤、`COUNT` 与 `SUM` 的空输入行为都属于返回协议的一部分。`COUNT` 空输入得到 0；没有分组的 `SUM` 空输入通常得到 NULL。`NULL <> x`、`NULL = x` 都不会在 `WHERE` 中变成真。正文中的逻辑推导以通常 SQL 三值逻辑为基础，方言、占位符替换和平台结果判定仍需对应执行配置核实。

## 这套检查真正覆盖的层次

主键规则检查指定粒度是否出现重复；码表规则检查纳入范围的值是否能在指定字典中找到；历史规则检查指定分组内的区间或相邻属性；数量规则检查两种集合构造后的基数关系。业务规则进一步限定比例、合约状态、日期、币种换算或波动阈值。这些定义是可以逐项解释的，但任一类都不能独自证明整个加工结果正确。

以下区别贯穿所有任务：

- **检查定义存在**：本次发布有可核读 SQL。
- **定义具有对应检出能力**：需核对条件逻辑；本文已公开发现的矛盾和盲区。
- **某次运行通过**：需要执行日期、参数、日志和平台判定，本文没有据静态 SQL补出这些事实。
- **消费结果可信**：还要验证下游实际读取的数据、业务对象和金额口径。

`qualityTask` 在发布图中作为调度参考保留，其调度邻居不因此成为字段值来源或业务金额血缘。本文也没有给这些任务新增图边。
