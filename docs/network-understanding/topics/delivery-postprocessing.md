# 目标端业务后处理：关系同步、客户补齐与奖励入账

本页解释三个有完整 SQL 的后处理，以及一个简单属性补齐。它们展示了业务结果在进入消费端后仍可能发生变化。过程名或任务类型本身不足以说明是否只是搬运。

<a id="crm-project-relationships"></a>

## CRM 项目的销售归属怎样同步

45199 的处理对象是 CRM 中 `TYPE='Project'` 的业务项目。项目不是股衍合约号，销售部门关系也不是前文期权/互换合约的分配比例；这里的 SQL 没有计算比例或金额。

对 `SYNC_SOURCE='ACS'` 的项目，SQL 用项目内部产品代码连接 ACS 部门、员工关系视图。部门关系以“业务项目行号、部门号、`Sales_Dept`”匹配；团队关系以“业务项目行号、岗位号、`Sales_Team`”匹配。旧目标关系如果不再出现在来源中，会被删除；新的关系由 `MERGE WHEN NOT MATCHED` 插入。

另一条分支从交叉销售商机进入：要求 `CROSS_FLAG='Y'`、存在关联项目及集成编号，再通过集成编号找到业务项目。部门只取“拓展方部门”，员工只取“拓展方员工”。这条规则说明“参与商机”与“被登记为项目销售归属”之间仍有角色和映射筛选。

员工归属部门优先取员工历史部门：按商机成员记录的 `CREATED` 时间落在历史岗位的 `START_DT` 与 `END_DT` 之间，再映射部门；找不到时才取当前员工部门。这个时间是成员关系的创建时间，不能直接替换为交易日或当前统计日。历史匹配使用含两端的 `BETWEEN`，重叠区间是否存在需要数据约束确认。

有三项会改变如何理解结果：

1. 非 ACS 部门旧关系的删除排除了 `SIEBEL` 来源，但插入分支只排除 ACS；删除和插入范围并不完全相同。
2. 非 ACS 员工旧关系的删除整段被注释掉，活动 SQL 保留新增 `MERGE`。来源关系消失时，不能据此期待目标旧关系也随之消失。
3. 各 `MERGE` 只有未匹配时插入，没有匹配时更新。已有同一项目与岗位关系的 `HIS_DIVN_ID` 不会因为这段插入逻辑而更新。

随后，SQL 把收入暂存表中尚未登记的 `TYPE_CD` 插入 `CX_REVENUE_MAP`；只填外部收入类型，CRM 收入类型与业务标志、业务类型都填空。这表示生成了待映射入口，不能说收入类别已经被成功统一。最后还调用 `GF_SYNC_ACCT_PKG.GF_BUSI_PROJ_CONT`，过程内部逻辑没有在本脚本中展开。

来源：45199 发布 `query` 1–123 行为 ACS 与部门关系，126–161 行是已注释删除，163–191 行为非 ACS 团队插入，194–211 行为收入映射与后续调用。多段 `COMMIT` 表明代码分段提交，不能把全脚本当作一次整体回滚的事务。

## 融资融券潜在客户月表怎样补字段

140202 先根据交易日历找“不晚于参数日”的最大交易日，然后更新 `CRMII.TRZRQ_QZKHXX_M_NEW` 中已经存在的参数日客户行。它同时取这一天的目标表作为客户集合，连接交易日潜客基础、风险资料、客户资料、主资金账户、首次交易日、股东账户和黑名单。

其目标匹配条件是客户编号加参数日；只有 `WHEN MATCHED UPDATE`，没有新客户插入。因此这一步是对已有名单补字段，不负责生成全部潜在客户名单。

主资金账户来源要求 `MAIN_FLAG=1`、`ASSET_PROP='0'`，并采用必须匹配的连接；其他多项资料采用外连接。缺少符合条件主资金账户的目标客户不会进入本次更新集合。多个符合条件账户能否唯一对应客户，需要约束或实际数据验证。

几个字段值得直接区分：`CLEAR_ASSET` 与 `TOTAL_ASSET` 都取同一个源总资产；客户状态直接赋 0，信用标志直接赋空值；股东账户标志依据有效沪深股东账户是否存在产生 1/2；黑名单标志依据客户证件号是否匹配名单产生 0/1。字段名“清算资产”不能让相同的源赋值自动变成另一个已计算口径。

来源：140202 发布 `query` 3–6 行为日期，42–65 行为客户集合和连接，67–87 行为仅更新行为。这里解释的是静态规则，没有读取真实客户名单或判定任何个人的信用情况。

## 上月开户奖励为什么进入本月账期

50615 的当前补充 SQL 先删除 `rdmp.t_exam_v21_bonus` 中参数月份、类别“开户”、子类别“网上开户业务奖励”的记录，删除条件还要求账期不早于 202110。删除之后单独提交。

随后从 `KDHIVE.DM_ECOM_OPENACCOUNT_REWARD` 读取参数月份的上一个月，要求来源月份不早于 2021-09、员工类型为“营销员工”、`delete_flag` 为空。按 `erp_no` 汇总 `reward`，写入参数月份的奖励账期：自有奖励与总奖励均为汇总值，分配奖励为 0，奖励代码固定 `C81011`。

例如参数账期为 2026 年 9 月，查询窗口表达的是 2026 年 8 月来源奖励，而输出账期是 9 月。这个例子只解释参数关系，不表示已核查这两个月的真实奖励。源月份、奖励记账月份和查询执行日期应分开。

源端没有符合条件的奖励行时，按员工分组的查询不产生输出；若当期旧结果已经删除，本次脚本不会保留旧奖励。由于删除和插入分段提交，中途失败是否自动补偿没有在脚本中定义。`extra_comment` 列实际接收当前时间表达式，也不能依据列名推断里面是业务备注。

来源：50615 当前补充 `query` 2–10、12–44 行；采集时间及内容哈希见[交付证据索引](../evidence/delivery-evidence.md#task-50615)。本节解释的是奖励入账步骤，原始开户资格和奖励金额计算见考核主题。

## 只补空类型，不重分类已有项目

198986 当前补充 SQL 对 `SIEBEL.CX_INF_PROJ` 执行一条更新：仅当 `TYPE IS NULL` 且 `BUSINESS_TYPE IS NOT NULL` 时，把后者复制到前者。它没有日期范围，也不覆盖已有类型。因而某条已有 `TYPE` 与 `BUSINESS_TYPE` 不一致的项目，不会由这一步自动纠正。
