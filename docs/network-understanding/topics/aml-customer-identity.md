# AML 客户：业务客户号怎样接到内部身份

AML 需要把分散在各业务条线的客户资料接到可共同使用的内部身份。这里的关键不是把所有客户表拼起来，而是保留业务来源与营业部，选择对应资料，再确定哪条记录代表这个业务客户。客户数量、账户数量和统一主体数量因此不是同一指标。

本页解释已核读 SQL 中的客户接入与身份选择。没有逐列验收全部接口，也没有证明这些静态材料已在实际运行中执行成功。

<a id="aml-client-integration"></a>
## 从合规资料到 AML，已经有直接读取证据

机构转换任务 73353 读取 `dm_cmpl_n.unit_cust_info`，加入 `aml_client_inte_unit`；产品转换任务 73354 读取 `dm_cmpl_n.pdt_cust_info_all`，加入 `aml_client_inte_product`。因此，[合规客户资料](compliance-customer-info.md)与 AML 之间已有明确的 SQL 消费关系。它证明转换任务使用这些表，不证明某一批数据已经送达或完整纳入。

机构资料按投行、托管、股衍、固收分别选择证件类型码表版本，不能用一个来源的代码解释所有来源。产品资料的这个接入分支只纳入投行、股衍、固收，并按来源系统与客户号关联既有产品资料，补取管理人证件起始日期等信息。此处产品客户与产品管理人仍是两个对象。

两份发布文本的日期也不同：机构接入为 `2026-05-25`，产品接入为 `2026-05-22`。这是所读 SQL 文本的事实，不能直接解释为系统长期采用不同日期；字面日期可能来自模板展开，需要原始配置才能判断。

<a id="aml-cross-business"></a>
## 跨业务标志决定选哪套资料

机构转换中，ECIF 资料分支按营业部和客户号关联 `aml_ecifinfo`，要求 `is_cross_business = 1`；再按业务条线与客户号关联综合机构资料，补充部分字段。另一分支追加非跨业务的综合机构资料。产品转换也有 ECIF 与综合产品资料两条路径。因此，来源优先级是具体字段和分支的规则，不能概括成“所有字段统一以 ECIF 为准”。

最终机构和产品结果都按 **客户号、营业部** 分组，按 `inner_client_id` 排序取第一条。这个排序不是“最近更新”。过滤条件是 `trim(inner_client_id) is not null`，也不等于显式检查修剪后的字符串不为空。多个内部身份竞争、排序并列和空字符串的实际表现，需要结合引擎语义与数据约束判断。

例如，同一个客户号出现在两个营业部，按此规则可以留下两行；同一个营业部和客户号对应两个内部客户号，则只选择其中一行。结果行数变化未必意味着现实中客户数量变化。

<a id="aml-inner-identity"></a>
## 内部客户号、当前状态与多账户标志

77827 的前段合并个人、机构、产品和公共客户资料，按营业部与客户号关联已有身份及 ECIF 信息。ECIF 候选按 ECIF 编号倒序选择，内部客户号优先使用可取得的 ECIF 身份，否则沿用业务来源中的身份；这个排序也不能直接称为“最新身份”。

后续片段将本次资料中缺失的客户标为状态 `3`，并写入相应变更与注销日期；按内部客户号统计状态 `0` 的行数，把一行与两行及以上映射为不同的多账户标志。它统计的是所纳入记录，不是去重后的现实主体或独立业务事件。

这份发布文本还出现删除中间表后再读取该表的语句顺序。当前 Pack 中的文本与发布材料一致，但二者来自相同采集链，不能当作独立原始脚本交叉验证。原始执行包装、建表替换或采集提取是否完整尚未确认。因此，本页只能说明可见片段的身份规则，不能断言整套身份更新能按这个文本独立执行。77827 的其余客户同步字段仍未逐项核读。

## 使用这些结果时要保留什么

需要同时保留业务来源、营业部、客户号、内部客户号与所用日期。涉及客户限制措施或复评时，还要区分资料补充、计算标志、候选对象和实际处理结果；这些环节见[合规主线](../chapters/12-compliance-and-reporting.md#aml-review-workflow)。机构/个人/产品出口字段、受益人完整关联仍是本版的具体缺口。
