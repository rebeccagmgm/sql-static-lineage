## 4. A：临时表 CTAS 被误当普通 DDL

### 问题与已确认原因

典型 SQL 形态如下，CTAS 指“用查询结果建表”：

```sql
CREATE TABLE temp_table AS
-- 业务说明
SELECT a.party_id, a.party_name
FROM source_table a;
```

`taskLocalCreateSchema` 用 `AS` 后直接跟空白再跟 `SELECT/WITH` 的正则排除 CTAS。注释夹在中间时不能命中，随后调用普通 DDL 解析。

`parseDdlSchema` 向后寻找第一个括号作为列定义区，可能把函数参数或子查询内容当成列定义。错误结构登记后，`deriveTaskLocalSchemas` 又因 `records.has(target)` 跳过查询输出列推导。

代表性已核验样例：

| 任务 | 临时表 | 冻结结构 | 候选字段 |
| --- | --- | --- | ---: |
| 150757 | `pdata_n.t01_otc_deri_cust_temp_tit339` | 仅 `a` | 132 |
| 179726 | `pdata_n.t01_otc_deri_cust_temp_ois030` | 仅 `major_mechanism` | 132 |
| 63115 | `temp.t03_marg_comp_info_temp` | 仅 `branch_no` | 77 |

28 个任务均已核对到异常的 1～2 列临时表结构；前两个精读了建表 SQL 和代码路径。实施时仍应逐任务验证是否全部由同一触发条件造成，不能将 887 当作必然恢复数量。

### 建议方案

1. 复用现有 SQL 词法/语法信息识别普通建表、CTAS、CREATE LIKE，不靠未经词法处理的跨关键字正则区分。
2. 普通 DDL 只接受真正的列定义区；不允许跳过 `AS` 后把查询中的括号当列定义。
3. CTAS 从其自身 SELECT/WITH 输出推导字段结构；无法完整推导时明确保留缺口。
4. 无效或不完整的结构不能以“已有记录”为由压住更强的本任务查询输出证据。
5. 保留 statement、写入顺序、SQL slot 和物理身份边界；不要借此把同名临时表跨任务或跨写入合并。

相关入口：

- `scripts/machine-facts/input-pack-machine-facts.ts`：`taskLocalCreateSchema`、`deriveTaskLocalSchemas`。
- `scripts/plans/ddl-schema.ts`：`parseDdlSchema`、括号定位与列定义解析。
- `scripts/plans/plan-adapter.ts`：查询输出和输入字段绑定。

### 验收要求

- 有/无注释的等价 CTAS 获得相同输出结构；覆盖行注释、块注释、WITH、查询内函数括号。
- 普通建表和 CREATE LIKE 不退化；字符串、引用标识符中的注释符号不被错误删除。
- 覆盖同任务多个写入、临时表重建与 UNION 输出，不能只验证第一条简单 SELECT。
- 对 150757、179726 检查临时结构、输出绑定和实际源字段链，不只检查候选标签消失。
- 对 28 个任务逐一列出修复前后变化及仍残留的原因；允许有合理残留。

## 5. B：分析输入缺少源表结构

集中样例：

- 223123：`y_vd_fi_balance_his_p`，165 个字段。
- 223111：`y_vd_fi_balance_p`，164 个字段。
- 62747：`ecif_e_t01_cust_base_info_temp`，41 个字段。
- 62746：`ecif_e_t00_cust_acct_ref_temp`，27 个字段。

前两个合计 329 个，占本组 56.14%。它们证明分析快照缺结构，不证明外部平台没有结构。

建议逐来源分流：

1. 本地 Input Pack 有完整且同物理身份的结构，但未选入：修复选择/名称解析。
2. 本任务已有建表或写入 SQL：先复用本任务结构推导，检查是否属于 A 的衍生问题。
3. 仅其他生产任务有输出证据：先验证目标物理身份、输出字段和适用范围，再决定是否可作为结构证据；不得直接确认跨任务运行接续。
4. 确实没有可用证据：登记精确采集对象并补采，不能用消费者 SELECT 列表自证源表字段存在。

尚未完成上述四类的全量归因，不应承诺 586 个都可以只改代码解决。

## 6. C：结构与 SQL 引用列不一致

代表性样例为任务 222844：

```sql
SELECT security_code AS Subj_Cd
FROM odata_n_sip.file_hk_hhzg;
```

发布时使用的源表结构包含 `Subj_Cd` 等加工后的名称，却缺少 `security_code`。该 DDL 的来源为任务建表 SQL。调查时确认其内容哈希与冻结 schema snapshot 一致，排除了仅当前文件变化造成的表象。

这是源表与目标表结构疑似错配的具体信号，但没有据此认定全组 420 个字段均为相同原因。

建议方案：

- 追踪 DDL 原文、采集任务、创建目标、默认库和完整物理身份，核查是否将无库名前缀的目标建表语句挂到了另一个库的同名源表。
- 分开记录：错误对象归属、结构不完整、快照与 SQL 版本不一致、标识符处理问题、真实字段不存在。
- 对错误归属先修采集/绑定来源，再重建受影响 Pack 与派生产物；禁止直接给现有错误表结构追加消费者列名。
- 同尾名不能作为 DDL 归属的唯一依据。

实施验收应证明结构属于正确物理来源，并检查原已确认字段是否发生错误改连；候选下降不是唯一标准。

## 7. D：表记录存在，字段列表为空

典型样例：213683 读取的两张 `h_his_refcashcompact` 源表，其 DDL 是：

```sql
CREATE TABLE h_his_refcashcompact LIKE temp_n.some_backup_table;
```

DDL 没有展开字段，分析快照列数为 0。这是本组一个已核验原因，不能未经核对将全部 237 个都归为 CREATE LIKE。

建议先区分 CREATE LIKE、DDL 缺失/解析失败、其他空结构来源。对 LIKE，复用已有继承机制，沿精确来源补全结构，设置循环检测和有界递归；被引用表缺失或身份不唯一时仍保留未知。

不要重复采集同一条未展开的 LIKE 语句并将采集成功当作结构补全。

## 8. E 与 F：不能通过放宽规则消除

### E：同尾名、不同完整名称

- 182505：49 个字段。读取 `odata_n_lss.s_v_ks_trs_eod_postion`，快照只有 `pdata_nds.s_v_ks_trs_eod_postion`。
- 182514：7 个字段。对应的 contract_underly 表也存在库名差异。

这只是相似结构线索，不是身份等价。补查源表自己的结构或有证据的身份映射，禁止跨库直接借列。

### F：上游候选的传递

33 个输出自身的表达式可为 PHYSICAL，但沿已解析的中间加工追溯后仍落到候选来源。样例包括 37058、37059、59441。

应修复最早缺失证据的节点后重新计算，不改页面标签来隐藏。统计时将直接修复与传播恢复分开，避免把同一根因的多个受影响输出计作多个独立修复。

### 10.1 本次交付边界

### 10.2 实施前对照

1. 在实际承接分支重新核对上述函数和数据入口是否迁移或已重写，记录承接分支的提交锚点。
2. 若该分支已接入新的解析器，保留本文的行为要求和回归样例，在新职责边界内修复，不机械复制旧实现。

4. 重点检查冲突区域：Input Pack schema 选择与推导、DDL 解析、表达式适配、Facts 版本/缓存标识。发布与页面代码可能有行为依赖，即使文本没有冲突也需要联验。

### 10.3 缓存和产物

代码合入不等于已发布图谱更新。需要沿现有流程依次刷新受影响的结构证据、Facts、任务投影和依赖这些结果的图谱产物。

- 核对实际语义版本、schema/Facts 哈希与 projection cache key 的依赖关系。凡行为变化而输入哈希不足以触发失效的环节，应使用现有版本机制显式失效。
- 不硬编码本文观察到的旧版本号作为新版本，不为了绕过缓存删除全部产物。
- 先在隔离的输出目录验证样例和受影响任务；避免两个分支并发覆写同一 Facts/投影输出根。
- 若合入分支已经发布新版本，重新建立其候选基线，再对同一输入比较修复前后；不能用跨版本总量变化代替修复证据。
- 完成验证后再走既有发布流程，并从 CLI 与页面实际读取已发布结果。
