# 图谱消费：需求定义与价值验证

- 更新日期：2026-09-15
- 状态：需求讨论稿；尚未通过真实工作验证，未冻结产品形态与一期范围。

## 1. 本文要解决什么

本文回答三个问题：

1. 用户借助 SQL、字段和加工关系，最终要完成什么工作、形成什么判断？
2. 相比在现有 Agent 工具中直接提问，新增消费方式能带来什么增量价值？
3. 哪些需求值得进入设计，哪些假设需要验证，哪些方案可能没有必要建设？

前期讨论过的图谱内聊天、任务内补查、会话持久化等架构，只作为技术备选。此前的多方架构评审说明相关技术问题已在设计层面得到处理，**不代表用户需求或产品收益已经得到验证**。本文是后续需求讨论的入口；本文中的待验证事项不能被旧架构默认覆盖。

本文止于需求定义与验证方法，产品形态和实现方案在需求验证后另行决策。

## 2. 已确认方向与当前事实

### 2.1 用户已表达的方向

- 核心关注是高精度字段血缘／加工事实，以及合适的消费方式。
- 希望利用当前查看的 SQL、字段和相关证据直接提问，减少手工拼接上下文。
- 希望评估图谱内问答相对现有 Agent 的价值，不预设新增聊天界面一定值得做。
- 消费范围不应先被限定为单点；路径、多对象和专题等方式也需要比较。
- 本轮明确选择的主要卡点是“证据已有，但加工逻辑仍难理解”与“已经能理解，但核对、对照和复用费力”。
- 当前先聚焦需求，文档想清楚后再决定设计与实施。

首要使用者是当前用户。个人本地使用、可提供模型 API 是此前表达的条件，但不能据此推导出“必须自建模型调用和聊天系统”。同事等潜在使用者尚未直接调研，其使用频率、工具熟悉程度和需求不作为当前已证实收益。

### 2.2 已有能力是比较基线

2026-09-15 核对当前文档与源码，已有以下基础：

| 已有能力 | 当前能提供什么 | 不能据此认定什么 |
| --- | --- | --- |
| Agent 图谱 CLI | 搜索、字段、上下游追溯、加工详情、SQL 分段读取及字段加工解释 | 查询入口存在不等于每个业务问题都能被回答 |
| 多任务字段对照 | 并列返回字段绑定、表达式等材料 | 不等于已经完成业务口径或语义差异判断 |
| 图谱分析范围 | 多个表／任务作为起点，展开关系，继续字段分析，保存探索范围 | 不等于已经组织出完整的专题理解或调查结论 |

来源：[Agent 查询说明](agent-graph-cli.md)、[当前 CLI 合同](../packages/data-graph/src/asset-graph/cli-help.ts)、[字段对照实现](../packages/data-graph/src/asset-graph/cli.ts)、[分析范围说明](../packages/data-graph-ui/src/analysis-scope/README.md)。以上是现有能力核对，不是本轮可用性或业务验收结果。

因此，解释 SQL、读取血缘和调用模型本身不能直接算作新增界面的收益。新增消费方式必须与“现有 Agent 已能访问同样证据”的基线比较。

## 3. 需求目标与用户完成工作的标准

### 3.1 当前需求假设

> 当我调查某次加工、某个字段或一组相关对象时，希望系统利用准确的对象身份和相关证据，帮助我理解取值规则、记录范围、数据粒度及关键条件，并围绕疑点继续查证。我应能方便地核对依据、形成有边界的判断，知道哪些已经说明、哪些仍需核实，从而减少定位材料、拼接上下文和反复阅读 SQL 的工作。

这是一条待真实工作验证的目标，不预先规定通过聊天、图形、表格或文档实现。

### 3.2 评价完整工作，而不只评价一条回答

用户可能带着明确疑点进入，也可能先看加工材料、再形成值得查证的问题。两种情况下，工作链条是：

**带着疑点进入／从材料中形成关注点 → 找到相关对象与材料 → 理解加工 → 核对依据 → 形成判断或下一步 → 必要时复用理解。**

一次有用的结果至少应让用户明确：

- 本次试图回答什么，实际回答到了哪一层；
- 有哪些可依据的加工事实、合理解释与未决问题；
- 是否已有足够依据完成本次工作；若没有，具体还缺什么。

少复制几次 SQL、回答流畅、有引用、工具调用成功，都只能作为辅助信息。不能单独据此认定需求得到满足。

## 4. 候选使用场景与预期结果

以下是需求地图，不是同一期要共同证明的功能清单。示例用于说明问题类型，不代表已采集的真实需求样本。**下一步先选一个主场景，必要时再选一个自然延伸的相邻场景；其余留在地图中。**

| 编号 | 用户正在做的工作 | 最终要形成的理解或判断 | 有用的结果应包含什么 |
| --- | --- | --- | --- |
| S1 | 阅读陌生加工 | 这项加工如何组织输入、得到输出，关键步骤在哪里 | 输入输出、粒度、步骤、关联和过滤、重要例外及缺口 |
| S2 | 核对某个字段规则 | 当前规则是什么；有明确预期时，哪些部分符合、不同或不能判断 | 取值、记录范围、空值／例外、预期来源、逐项依据 |
| S3 | 沿加工路径调查疑点 | 某个值或状态在哪些环节发生转换、过滤、汇总或覆盖 | 与问题相关的路径、逐阶段变化、关键断点、待核实来源 |
| S4 | 对照多个任务或结果 | 看似相同的字段有哪些共同点与差异，是否具有可比性 | 对象含义、粒度、来源、条件、换算／聚合规则的对照及证据 |
| S5 | 为规则修改准备核查 | 哪些静态依赖值得检查，后续需要核实什么 | 潜在依赖清单、相关路径、证据范围与核查事项 |
| S6 | 理解一个业务专题 | 相关对象如何分工，来源、加工和消费之间是什么关系 | 对象导航、来源与职责矩阵、代表性加工、未确认的业务解释 |

场景边界：

- S2 没有明确预期规则时，只能解释实际加工与疑点，不能直接宣称“符合业务要求”。
- S4 同名字段不天然具有相同含义，不能跳过粒度、单位和范围直接比较表达式。
- S5 静态依赖不等于实际业务影响，也不能证明某个未出现的下游一定不受影响。
- S6 图结构和 SQL 只能支持相应的结构／加工判断，业务职责需要相应证据，不从表名和连线自动认定。

### 4.1 如何选主场景

根据近期真实工作，简要比较三个维度即可：发生频率、当前负担、判断的重要性。不要求打分或精确计时，也不以出现次数最多作为唯一标准。

- 主场景：优先选择近期有实例、卡点清楚、改善后对工作有意义的一项。
- 相邻场景：只选同一次工作里自然接续的一项；没有自然接续就暂不选。
- 每项使用自己的完成标准。例如阅读要能说明关键加工，对照要能识别有依据的异同，路径调查要能定位变化或断点，不能合成一个“问答有用”的评分。

本轮用户已选择“分析与证据组织不足”和“消费体验费力”两类卡点。依据这项反馈，先作以下工作性选择：

| 项目 | 本轮初选 | 依据与尚待确认的内容 |
| --- | --- | --- |
| 主需求 | 将已有加工证据组织成能理解、能核对的解释 | 两类卡点由用户明确选择；不据此认定所有所需材料都已齐全 |
| 主场景 | S1：看懂一段已有加工，理解步骤、粒度、条件与例外 | 先验证分析组织；这是一项试验优先选择，不是已测得的最高频场景 |
| 相邻动作 | 核对同一份解释与原始 SQL／字段依据是否一致 | 对应 S2 的实际规则核对部分；暂不扩为有业务预期的符合性审查 |
| 保留线索 | 多对象对照、延后复用、必要的路径调查 | 用户已提到对照和复用的负担，但三者的相对重要性及近期实例还未明确 |

因此，当前先试“解释是否能帮助理解，依据是否方便核对”。这不预定用聊天或说明卡交付，也不将对照、复用一起扩成完整功能。具体案例若表明真正负担在其他场景，应调整初选，不能反过来改写用户的问题。

### 4.2 区分回答疑点与发现疑点

“先不知道问什么”是跨越上述场景的一种进入方式，不额外扩成第七项功能。

观察用户是带着明确疑点进入，还是希望先发现关键变化、难理解的步骤和值得查证的条件。后者的有用结果可能是少量关注点、对应依据和下一步问题，而不一定是直接给出业务结论。

例如 Join 后可能改变记录粒度值得关注，但缺少键唯一性或实际数据时，只能提出有依据的核查问题，不能断言数据一定重复。是否需要默认说明或主动提示，取决于真实使用中哪种进入方式更常见，尚未冻结。

## 5. 问题范围：精确对象不等于完整问题

同样选择一个金额字段，“怎么算的”可能是在问不同层次：

| 问题层次 | 需要回答什么 | 可能需要的证据 |
| --- | --- | --- |
| 表达式 | 当前值怎样计算，分支和空值怎样处理 | 表达式及所属语句 |
| 记录范围 | 哪些记录进入计算，哪些被排除 | 关联、过滤、分支及相关状态规则 |
| 数据粒度 | 一条输出代表什么，是否发生汇总或记录扩张 | 分组、窗口、关联键及可用的唯一性证据 |
| 来源与过程 | 输入值本身怎样产生，中间改变了什么 | 相关任务内步骤，必要时跨任务证据 |
| 业务符合性 | 是否符合预期口径，差异是什么 | 实际加工证据及明确的业务定义／预期 |

例如以下构造示例（非真实需求样本）：

```sql
SELECT customer_id, SUM(amount) AS amount
FROM trades
WHERE status = '1'
GROUP BY customer_id;
```

“按客户汇总状态为 1 的金额”解释了当前语句，但不能回答是否混加币种、状态 1 是否包括撤销记录、输入金额是否已经换算。后续需要什么证据，取决于用户本次要形成的判断。

默认解释当前加工是可验证的候选行为。遇到明显涉及其他层次的问题，应说明覆盖范围并补充证据或作具体澄清，不能把局部表达式解释当成问题已经完整解决。

“先限制当前任务”曾作为成本取舍讨论，但产品边界尚未成立。应记录真实问题能否在任务内形成有用结果；尤其保留“当前 SQL 只是透传，上游才有核心规则”的案例。不能为适配实现范围而排除这些问题。

## 6. 相对现有 Agent 的增量价值

### 6.1 公平比较的条件

基线使用用户当前的 Agent 工具，并允许它访问现有图谱查询能力。尽可能固定模型、证据版本、问题、允许读取的材料和最终完成标准；无法一致时记录差异，不把模型升级或多给材料的收益归因于界面。

两种方式从同一份原始问题和用户当时已经知道的对象／材料开始。为 Agent 整理准确对象、准备上下文以及切换工具的工作都计入过程，不能事先替基线完成后漏记。候选结果若有人额外搜索、筛选或判断，也必须单独记录，不能当成产品已具备的能力。

新增消费方式可能带来的价值包括：

- 准确传递当前对象，减少同名字段、多写入或版本理解错误；
- 让解释与 SQL、路径、对照材料容易一起核对；
- 帮助用户发现与问题有关的材料，减少盲目展开和反复查询；
- 让一个调查在多个相关对象之间保持连贯；
- 便于再次使用已核对的理解；
- 对没有现有 Agent 使用习惯的用户降低门槛——此项需另行调研。

这些是候选增量，不是已测得收益。将相同模型放到页面里，不会自动提高业务理解或解释正确性。

### 6.2 需要比较的消费方式

| 候选方式 | 更适合解决的障碍 | 需要证明什么 |
| --- | --- | --- |
| 现有 Agent 直接查询 | 自由调查、多材料整理 | 现有能力是否已经足够，具体卡在哪里 |
| 轻量对象／上下文交接 | 对象定位与上下文准备 | 仅改善交接是否已经解决主要问题 |
| 面向工作结果的展示 | 路径理解、规则对照、依赖核查 | 路径图、对照表或清单是否更容易理解与核验 |
| 图谱内问答 | 边看证据边围绕疑点追问 | 是否明显改善完整工作，而不是只更换聊天位置 |

单点说明、路径说明、多对象对照、依赖清单和专题文档都是可能的消费结果。图谱负责提供关系与证据，最终结果不必全部显示成图，也不必全部经过聊天。

### 6.3 先归因卡点，再选择改进方式

| 主要卡点 | 如何辨别 | 优先处理方向 |
| --- | --- | --- |
| 证据不足 | 所需关系、规则定义或数据尚未取得，无法支撑当前判断 | 补证据、明确范围，或调整能够回答的问题 |
| 分析与证据组织不足 | 相关材料已经有了，仍不能清楚说明粒度、条件及它们的作用 | 改善分析方法和材料组织，核对模型解释能力 |
| 消费体验费力 | 已能解释，但选对象、核对、对照、连续调查或复用太麻烦 | 改善交接与结果展示，按具体卡点选择交互 |

“用户找不到”不等于“证据不存在”：若材料已有、只是入口难找，应归入获取和消费障碍，不能误判为需要重新采集。三类卡点可能同时存在，每个案例只需记主要阻碍，必要时补一句次要阻碍，不要求先做完整根因分析。

同一场景可能有不同卡点，同一卡点也可能出现在多个场景。不能仅根据“阅读／对照／路径”标签直接决定要做界面，也不能将材料缺失归因于模型解释能力。

## 7. 不依赖产品形态的需求约束

| 编号 | 需求 | 判定原则 |
| --- | --- | --- |
| R1 | 对象准确 | 用户能确认讨论的是哪一份加工；不同物理来源、写入和阶段不被无声合并 |
| R2 | 解释有用且范围明确 | 回答服务于用户本次要完成的工作；局部解释不冒充完整回答 |
| R3 | 依据易核对 | 关键结论能回到实际使用的材料；核对过程本身纳入可用性评价 |
| R4 | 事实、解释和未知可辨 | 静态加工、模型推断、业务定义与未取得证据有清楚区分 |
| R5 | 调查连贯 | 浏览相关对象不会让正在解决的问题和重要上下文无声变化 |
| R6 | 结果与材料变化可辨 | 若提供历史恢复或结果复用，用户能知道当时依据是什么、当前是否变化 |

R5 需要区分：**浏览对象**是当前看的对象，**提问焦点**是当前追问的内容，**调查主题**是最终要解决的问题。一个主题可以涉及多个对象；如何组织会话仍待验证。

数据尚未读取、范围被截断、无法确认关系与确实没有相应规则，不能使用相同的“没有”表述。`COMPLETE`、图谱可达或查询成功，也不能代替实际运行、数据到达或业务符合性的证明。

## 8. 需要验证和决定的需求问题

| 编号 | 未决问题 | 验证所需观察 | 当前状态 |
| --- | --- | --- | --- |
| H1 | “看懂加工＋核对解释”是否是合适的优先选择？ | 用户已确认分析组织与消费体验两类卡点；用近期实例辨别它们的实际表现、频率和负担 | 已作工作性初选，具体实例尚待补充；其他场景不共同承担本轮价值证明 |
| H2 | 当前任务内是否能交付独立价值？ | 任务内完成、需要跨任务、需要业务资料的案例分布及重要性 | 未冻结一期边界 |
| H3 | 用户带着疑点进入，还是先希望发现值得问的问题？ | 真实工作的进入方式、提示是否形成有用关注点，以及固定问题是否重复 | 据此比较默认说明、主动提示和直接提问，均未冻结 |
| H4 | 是否需要图谱内聊天？ | 与现有 Agent、轻量交接及结构化结果的完整工作对照 | 尚无增量价值结论 |
| H5 | 调查应按什么组织？ | 同一问题是否频繁切换字段、条件、任务和路径 | 不预定一个对象一段会话 |
| H6 | 需要保存什么？ | 用户下次要继续的问题、认可的理解、原始依据或分享结果 | 继续调查与复用理解分别验证 |
| H7 | 所选工作适合哪类消费结果？ | 针对主场景比较说明、路径、对照表或清单如何帮助形成判断 | 随主场景收窄，不同时验证所有形式 |

“继续调查”需要恢复问题、相关对象、已查材料和未决疑点；“复用理解”需要重新找到认可的解释并检查依据是否变化。保存聊天记录不能自动代表两项需求都已解决，收藏回答也只是候选办法。

历史窗口长度、工具调用次数、模型接口、聊天页签、数据库、向量检索和缓存，均不在本文中冻结为需求。前期实现估算不作为本轮需求价值的证明。

## 9. 真实工作验证方法

### 9.1 验证力度与投入相称

| 试验投入 | 怎么验证 | 能支持什么决定 |
| --- | --- | --- |
| 轻量交接、一份说明或一张对照结果 | 围绕主场景用 1—2 个真实问题快速试，使用下面四项记录 | 决定保留、调整或放弃这项小改进 |
| 完整聊天、持续会话、独立模型接入等较大建设 | 在已出现帮助的主场景中观察重复使用，再补比较和恢复等证据 | 决定是否值得承担完整产品的建设与维护 |

低成本试验不以精确收益、完整表单或预先确认收益阈值为前提。真实问题可以在工作中随手记录，未知项暂不填。无需先凑齐六类场景或固定数量样本，才有资格尝试小改进。

### 9.2 初次试用只记四件事

| 记录项 | 简要内容 |
| --- | --- |
| 当时要完成什么 | 想形成什么判断；若没有明确疑点，想先看清或发现什么 |
| 原来卡在哪里 | 实际障碍，粗分证据、分析组织、消费体验；允许混合或尚不确定 |
| 换一种方式解决了什么 | 本次换了什么、带来什么帮助；有额外人工准备则在此注明 |
| 还要自己做什么、是否愿意再用 | 尚缺材料或理解、剩余核对工作、愿不愿在同类问题中再用及原因 |

这些记录可以直接来自对话，不要求用户另填表。准确解释、有依据的关注点或可执行的下一步都可能有价值；由用户结合当时工作判断是否推进。

### 9.3 出现价值后，再按需要深入

准备扩大投入时，由已有案例决定需要补哪些信息，不默认全部收集：

- 重复使用：是否在相近真实工作中再次有帮助，还是只有一次新鲜感。
- 公平比较：共同起点、模型和材料差异、额外人工准备；不同条件下的收益不全部归给界面。
- 连续或延后使用：只有需要会话恢复／结果复用时，才验证跨对象追问及稍后再次使用；未验证的不宣称成立。
- 完成边界：主场景是任务内足够，还是核心判断经常需要跨任务、业务定义或实际数据。
- 建设取舍：用户希望持续减少的负担是什么，是否值得新增操作习惯和维护成本。

手工组织的结果可以先证明“这种结果有帮助”，不能直接证明产品已能自动稳定产出。同题重复试用还可能有熟悉效应，应如实说明；初验不要求建设一套正式对照实验。

### 9.4 判断有帮助，不等于批准大规模建设

**可靠性底线：**不得问错对象、混淆材料版本、伪造引用、把候选说成确认或将静态证据说成业务结果。低成本试验也不放松这些底线。

**用户价值：**重点看原来的障碍是否减少、能否理解或形成值得查证的问题、是否减少剩余人工工作，以及用户是否愿意再用。大量只指出未知而不能推进工作，不算已经解决需求。

小改进出现明确帮助可以保留并继续试，不必等待量化收益证明。完整产品则需要与其投入相称的重复使用证据；一次正确或方便的回答不能单独证明完整聊天系统值得建设。未经测量不填写效率提升百分比。

目前没有真实案例结果。技术样例只能支持可靠性边界，不能代替用户价值验证。

### 9.5 验证后的决策出口

- 现有 Agent 已足够：保留现有消费方式，仅处理验证中实际出现的可发现性或使用障碍。
- 主要障碍在对象交接、核对或对照：围绕该障碍验证轻量交接、结构化展示或问答，不预定其中一种必然需要建设。
- 轻量方式解决了具体障碍，用户愿意再用：可以保留或迭代该小改进，不自动扩展成完整产品。
- 较大建设在主场景中已有重复使用价值：按该方式明确覆盖范围、结果形态和验收标准，进入相应设计；手工支持尚未消除的部分另列为可行性待验证。
- 多种方式均有效：比较用户操作、学习负担与后续建设维护成本；较轻方式能够满足同样工作目标时，优先选择较轻方式。
- 多数重要问题必须跨任务：调整范围或暂缓该版本，不能将用户问题改写成任务内问题后宣称完成。
- 主要缺口是业务定义、实际数据或基础证据：先明确资料与事实边界；新增聊天不应被当成缺口已经解决。
- 高频工作不明确、收益微弱或额外负担更大：保留暂停或不建设的结论。

下一步围绕初选的“看懂已有加工＋核对同一份解释”，取 1—2 个近期真实问题，用四项简记试一种低成本消费方式。重点分开观察：解释是否变得容易理解、核对是否变得省力。若主要阻碍实际在跨对象对照或复用，就据案例调整初选；其余场景继续保留在需求地图。
