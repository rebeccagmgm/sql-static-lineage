107491 用本次读取的销售合约快照，重建一段逐日分析资料。它先生成“这条销售记录对应哪些计提日”，再把事件、历史持仓、金仕达记录和有效参数分别整理到可按日关联的形态，最后按产品分支选择本金规则。

**日期展开决定生成哪些日期，产品公式决定每个日期上的金额。** 它们不是同一个条件。输出中的计提日可以早于加工日，而部分客户、标的、初始本金及折算系数仍来自本次销售快照。

## 当日销售基础

主记录来自 `T98_OTC_DERI_COMP_SALE_INFO` 的加工日分区。先用 `COALESCE(Early_Term_Date, End_Pric_Date)` 得到后续使用的结束日：有提前终止日时，优先使用提前终止日。

源记录还需满足结束日晚于 2021-09-30，以及起始计价日不晚于结束日。这是销售快照的参与条件，不是最终逐日金额的全部过滤规则。

此时仍是一条条本次销售快照记录，四类产品的 `Grp_Id`、销售编号和产品号都还保留。上游如果已经因腿或其他关联形成多行，本任务不会先把它们统一压成“一合约一行”。

## info：展开计提日期

对每条参与的销售记录，从起始计价日和“加工日往前 150 天”中取较晚者，用日期位置展开到本次加工日，得到 `Accrued_Date`。

```text
日期序列起点 = max(Strt_Pric_Date, 加工日 - 150天)
日期序列终点 = 加工日
每条销售快照记录 → 多条「原记录 + Accrued_Date」
```

**这里没有把序列统一截到结束日。** 结束日随后用于部分产品的本金公式，不能用“合约结束了”直接推断该任务不再产生结束日之后的日期行。

示意，非真实数据：9月7日加工，销售记录从9月5日起始；展开后有9月5、6、7日三条计提资料。若9月6日提前终止，9月7日这条日期仍可能存在，只是其金额需再看所属产品的规则。

## evt：期权事件累计

期权事件来源先限定为本次数据分区中已生效的部分终止和提前锁盈事件。一个合约同日可能有多条事件，所以先按 `key_option_deal_id、event_date` 汇总：整理变动前后本金，并汇总变动额。

随后依据变动前后大小确定变动额方向，按合约和事件日期累计。`LEAD(event_date)` 给出下一事件日；再从本事件日展开到下一事件日前一天，把这段期间适用的累计变化带到每一天。最后用合约技术 ID 对应销售 `Inr_Seri_No`，再匹配 `Accrued_Date`。

示意，非真实数据：9月5日累计减少本金100万，下一次事件在9月8日，那么9月5、6、7日使用这次事件之后的累计变化。它表达的是**截至该日的累计本金变化**，不是把同一筆“当日发生额”重复确认三次。最终期权本金还需与销售初始本金及折算系数组合。

## his_dy：互换历史持仓

普通互换先取结构腿，再按腿编号连接历史持仓。历史持仓的源业务日期限定在本次回看窗口内，随后按交易技术 ID 和源业务日期分组。

动态本金口径使用 `SUM(Init_Price × Quantity)`；同一段子查询还计算了初始价格乘初始数量的金额。这里的合并对象是腿／持仓，产物是交易日金额，不是销售管理归属。

回接时用 `his_dy.key_otc_trade_id = info.Inr_Seri_No`，并匹配计提日。这一步使用的是销售内部流水号对应的技术 ID，不能换成销售 `Agt_Id`。多条结构腿的金额在子查询中先汇总，再进入最终产品公式。

## ks：金仕达状态延续

金仕达的动态本金、应计利息和占资成本按确认编号读取业务记录。对每个确认编号用下一条业务日期划分有效区间，再把本条状态延续到下一记录日前；最后一条记录延续至本次加工日。

产物是“确认编号＋日期”的状态金额，按销售 `Agt_Id = key_trade_comfirm_id` 和计提日回接。它使用确认编号入口，与期权、普通互换使用 `Inr_Seri_No` 的入口不同。

示意，非真实数据：9月5日有一条动态本金记录，下一条在9月8日，则9月6、7日也能取得9月5日记录表达的状态。状态延续只说明 SQL 怎样填充日期，不证明来源记录没有重复或遗漏。

## ks_t：实际日佣金

佣金收入和费用成本另取 `profit、fee_cost、business_date`，只保留回看窗口内的业务日期，再按确认编号和实际业务日回接。

这一支**没有像 ks 那样向后展开有效期**。同样以确认编号关联，动态本金和利息等采用状态延续，佣金及其成本采用实际业务日；不能因为都来自金仕达记录，就把两种时间处理合并讲成一种。

最终输出对应字段为 `Trd_Cms、Trd_Cms_Cost`，未匹配到值时按 SQL 的 `COALESCE` 取零。

## nd：极速互换日终持仓

极速互换读取日终腿持仓，按产品号及源业务日汇总动态本金，形成产品日金额。它回接销售 `Otc_Seri_No` 和计提日，使用的是产品号入口。

这和普通互换的交易技术 ID 入口不同。最终公式取 nd 金额乘销售快照中的折算系数，未匹配时取零；不能只因两支都叫“互换”，就把它们的关联键和本金来源写成同一套规则。

## prop：保证金比例

保证金比例按合约号和生成日期先保留一条记录，再通过下一生成日期把该记录向后展开到每天，形成每日适用的 `Marg_Prop`。

关联条件是 `prop.CONTRACT_ID = info.Agt_Id`，同时要求计提日相同。这里得到的是一个比例属性，不是保证金余额、补缴流水或组合履保金额。按合约日保留一条的窗口操作，也不替代对同日重复来源如何选中的业务核验。

## fee：计提费率

费率来源筛选 `ACCRUAL_PREMIUM_FEE`，按产品的计算日期取下一记录日，再展开出每日适用的费率。回接使用 `fee.KEY_INSTRUMENT_ID = info.Otc_Seri_No` 及计提日。

这里的 `fee` 是107491内部的子查询阶段，向输出提供 `fee_rate`。它不能与 PDATA 的 `T98_OTC_OPT_COMP_EDAY_PRVS_FEE` 结果表混为一谈：后者是另一份日计提费用事实，已确认被230202创收读取。

## 按产品形成逐日金额

`info` 分别左连接上述阶段后，按 `Grp_Id` 选择动态本金表达式。相同的日期序列，在不同产品中采用不同金额规则：

| 分支        | 起始日                     | 起始日之后、未超过结束日                              | 结束日之后                         |
| ----------- | -------------------------- | ----------------------------------------------------- | ---------------------------------- |
| 01 期权     | 优先取销售初始本金         | 累计事件变化 × 销售折算系数 ＋ 初始本金；按表达式回退 | 动态本金置零                       |
| 02 普通互换 | 优先取销售初始本金         | 历史持仓动态本金 × 销售折算系数；未匹配取零           | 动态本金置零                       |
| 03 金仕达   | 取 ks 动态本金             | 取 ks 动态本金                                        | 此 CASE 中没有同样的结束日归零条件 |
| 04 极速互换 | 取 nd 金额折算，未匹配取零 | 取 nd 金额折算，未匹配取零                            | 此 CASE 中没有同样的结束日归零条件 |

01、02 的判断顺序是先判断是否起始日，再判断是否超过结束日。03、04 没有同一项结束日归零表达式，不等于承诺来源在结束日后必然有非零金额。

此外，应计利息取 ks 值并乘负一；资金成本取 ks 占资成本；佣金及费用成本取 ks_t；保证金比例和费率分别取 prop、fee。**把资料关联齐和选择输出公式是两个层次：不是每一种产品都用上每一个来源的所有金额。**

## 写入计提日结果

结果写入 `T98_OTC_DERI_COMP_SALE_ADTNL_DET`，按 `busi_date、grp_id` 分区覆盖。其中 `Busi_Date = Accrued_Date`，而 `Data_Etl_Date、Data_Upt_Date` 使用本次加工日。

示意，非真实数据：9月7日重建9月5、6、7日的记录，三个计提日的 `Data_Etl_Date` 都是9月7日。历史日本金可以来自各日持仓，但客户、标的分类、初始本金或折算系数仍可能来自9月7日读取的基础。

所以，一行应理解为**本次销售快照记录在某个计提日上的分析资料**。末尾没有再按合约和日期整体去重；上游多行及关联重复可能保留，不能宣称一合约一天必然只有一行。

118141用这份日明细参与销售收入计算，230202按自己的期权范围用于创收；两个消费者还有各自的参数、归属或费用输入。118143参数快照与收入并行消费基础及归属，不是这份日明细之后必须经过的一步。
